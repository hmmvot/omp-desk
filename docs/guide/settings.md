# Settings

OMP Desk's settings are under **OMP Desk** in VS Code's Settings editor. The **Settings** view in the OMP Desk side bar lists the same settings and changes them in place, with the layer each value comes from. These are OMP Desk's own settings; OMP's settings are in the [OMP Settings editor](omp-settings.md#omp-settings).

| Setting | Default | Meaning |
| --- | --- | --- |
| `ompDesk.toolCallDetail` | `overview` | `overview` groups routine tool calls; `detailed` shows each call. Applies live to every open Chat. |
| `ompDesk.desktopNotifications` | `true` | Windows desktop notifications when a session finishes or asks for input, unless its editor is active and visible in the focused window. Display questions may remain in Windows notification history and appear on the lock screen. |
| `ompDesk.showWorkspaceFolders` | `true` | Show the folders VS Code has open in any window, or every folder of a multi-root workspace, in Sessions next to the pinned folders. It applies to all windows, so every window shows the same list. When off, only pinned folders (and folders with a running session) are listed. |
| `ompDesk.runSessionsAtRepositoryRoot` | `true` | Run sessions at the root of the version-control checkout the opened folder lies in, and use that folder for **OMP Settings**, Models and Agents project settings (`<root>/.omp`), so a Unity project opened as `<repo>/omp-vscode` runs its sessions, and saves its project settings, at `<repo>`. Git (also worktrees and submodules), Mercurial, Sapling, Jujutsu, Subversion, Plastic SCM / Unity Version Control, Bazaar, Fossil, Pijul, Darcs, CVS and Perforce (a `P4CONFIG` file) are recognised by their marker (`.git`, `.hg`, `.sl`, `.jj`, `.svn`, `.plastic`, `.bzr`, `.fslckout`, `.pijul`, `_darcs`, `CVS/Root`, `.p4config`); the nearest one wins, and your home folder or a drive root is used only when it really is a checkout. A folder in no checkout runs where it is. Turn it off for a folder (or workspace) of a monorepo to run sessions in that folder itself. Sessions already recorded keep the folder they ran in. Replaces `ompDesk.useAgentRootFolder` and `ompDesk.ompSettings.useNearestAncestorOmpFolder`: an explicit `false` of the first is carried over at the next start, the second is dropped. |
| `ompDesk.launchInFolderWindow` | `true` | Start a session in the window that has its folder open: New Session, Resume Session and opening a stopped session of a folder that is open only in another window run there, and that window comes to the front with the session's tab. A folder open in this window, or in no window, starts here. A Unity project (a folder with `ProjectSettings/ProjectVersion.txt` and `Assets/`, found in the folder or two levels below it) always runs in a window that has the project folder open, or in a new window opened on it, because the Unity extensions need it; the session's working directory stays the repository folder. If that window does not answer, a message says so and nothing starts. When off, every launch starts in the window you used. |
| `ompDesk.sessionsGrouping` | `flat` | `flat` shows one list of every session, labelled with its folder; `folders` groups sessions under their folders; `terminals` lists the background processes (session processes and terminals) instead. The layout button in the Sessions title bar (its icon shows the current layout) opens a picker that changes it. |
| `ompDesk.linkCodeSymbols` | `true` | Link inline code symbols in Chat replies (`Session`, `SessionData.Load()`, `[Tracked]`) to their definition when VS Code's language extensions report exactly one definition of the symbol in the session's folders. A partial class or overloads link to one of their declarations; a symbol with several different definitions links to the symbol search; unknown symbols stay plain code. The same setting turns on linking a bare file name (`session-index.ts:849`) to the file VS Code's file search finds in the session's folders; several files of that name link to a list to choose from. When off, only the links the model writes itself and file paths are links. |
| `ompDesk.linkReminder` | `false` | After every prompt you send, remind the model to write the files and folders it mentions as paths in inline code and every code symbol in its Chat replies as a link with its definition line. The reminder (about 120 tokens) is a separate message that goes to the model only; it is never saved to the session or shown, and your prompt is not changed. Applies to sessions started or resumed afterwards. |
| `ompDesk.toolIntentDescriptions` | `false` | Ask the model to describe each tool call, in the line OMP shows beside the tool name in Chat, in terms of your task: the question the call answers or the change it makes, naming the feature, bug, file or agent, in at most 10 words (`Find where the tool card menu is drawn`), instead of OMP's built-in two-to-six-word verb phrase (`Find menu`). It replaces OMP's own rule for that line and adds one paragraph (about 190 tokens) to the system prompt of Chat sessions; subagents and Terminal sessions are unchanged. It has an effect only while OMP's `tools.intentTracing` is on (the default). Applies to sessions started or resumed afterwards; a running session keeps the value it started with. While it is on, a tool row that has such a line puts it first, before the file or command, in every Chat at once (see [Chat](chat.md#tool-calls-thinking-and-the-overview)). |
| `ompDesk.chatHtmlPages` | `true` | Show a closed `html` block of an assistant reply in Chat as a live page (Page \| Source toggle, Copy) instead of code, and tell the model in Chat sessions that it may write one (one short paragraph, about 240 tokens, added to the system prompt of Chat sessions only; subagents and Terminal sessions are unchanged). The page runs in a sandboxed frame served from a loopback address of this window, with no network, no storage and no access to Chat, VS Code or your files, and reads the theme as CSS variables. Off: every `html` block stays code and the model is told nothing. The prompt applies to sessions started or resumed afterwards; turning the setting on needs a window reload for Chats that were already open. |
| `ompDesk.chatLinkRules` | none | Your own links in Chat: a list of rules, each a regular expression (`pattern`) and a web address (`url`, with `$0` to `$9` for the match and its groups), that draw matching text of an assistant reply as a link opening that address in your browser, for example the issue numbers of your tracker (`#(\d+)\b` and `https://github.com/<owner>/<repo>/issues/$1`). Optional `ignoreCase` and `name` (shown in the tooltip). At most 20 rules; a rule that is not valid is skipped and reported once. Read from your user settings only: a rule in a workspace or folder `settings.json` is ignored, so a repository you open cannot add links. It is edited in `settings.json` (the Settings view shows it read-only); a change reaches open Chats at once. See [Your own links](chat.md#your-own-links). |
| `ompDesk.chatSendWith` | `enter` | Which key sends a message in Chat. `enter`: `Enter` sends (steers while a turn runs) and `Shift+Enter` inserts a newline. `shiftEnter`: `Shift+Enter` sends (`Alt+Shift+Enter` queues a follow-up while a turn runs) and `Enter` inserts a newline. It covers every message box that sends on `Enter`: the composer, a side question's follow-up row, the `/review` instructions box and an ask's "Other" field. `Ctrl+Enter` sends in both modes, an open `/` or `@` list still takes a plain `Enter` to accept a row, and `Enter` during an IME composition never sends. Applies at once to open Chats. |
| `ompDesk.chatColumn` | `true` | Open sessions in their own locked editor group on the left, with files on the right. When off, a session opens in the active editor group. |
| `ompDesk.executablePath` | empty | Absolute path of the OMP to run: the `omp` program itself, or a Bun-installed `omp.exe`. Empty uses the first `omp` on PATH. When set it is the only OMP Desk considers: if it cannot be used, Desk says why and does not search PATH. User settings only (a workspace cannot set it); applies to sessions started, resumed or read afterwards. The Settings view's row for it has a **Test** button that resolves the typed path without saving it. |
| `ompDesk.chatBrokerRuntime` | `auto` | Which program keeps a Chat's OMP process alive in the background. `auto` uses the `bun.exe` that runs the session's OMP, so a running Chat survives a VS Code update (the updater ends every `Code.exe` of the install and, with them, the Chats whose background broker was one); Desk first proves that Bun (Bun 1.4.0 or newer, installed where only you and administrators can change it) and otherwise falls back to VS Code's own executable. An OMP installed as its own program (winget, `omp.sh`, mise) has no Bun of its own to share and always uses VS Code's executable. `vscode` always uses VS Code's own executable. Terminals, folder shells and Stats always use it. The OMP Desk output says which one each Chat broker uses. User settings only; applies to Chats started or restarted afterwards; a running broker is never restarted for it. |
| `ompDesk.agentDebugger.enabled` | `true` | Give the agent of a Chat session tools (`vscode_debug_*`) to drive VS Code's debugger: set breakpoints, start a launch configuration, wait for a stop, read the stack and variables, step, and hand the paused program to you. The agent works through VS Code's own debug sessions, so you see the same breakpoints and paused state in Run and Debug and can take over at any time. The tools are available in the main session of Chat editors only. These permissions are consent prompts, not a sandbox: a launch configuration can run programs and tasks, and the agent can also edit your workspace. Applies to sessions started or resumed afterwards. |
| `ompDesk.agentDebugger.start` | `ask` | Whether the agent may start a debug configuration of your `launch.json` (or an Attach to Unity Editor preset) without asking: `ask` prompts first, naming the folder, the configuration or preset, its type and request, and its program; `allow` starts the configurations the agent chooses without asking. Only the agent's own starts can be controlled by it; sessions you started are read-only to the agent. |
| `ompDesk.agentDebugger.expressions` | `ask` | Whether the agent may run code in the debugged program: evaluating an expression, and breakpoint conditions and log messages (all of them run code in the debuggee). `off` forbids it, `ask` prompts before each expression (the prompt shows the debug session and the exact expression), `allow` runs the expressions the agent chooses without asking. |

The settings that name a program or its runtime (`ompDesk.executablePath`, `ompDesk.chatBrokerRuntime`) are machine settings: set them in your User settings, because a workspace cannot set them.

Earlier versions used the names `omp.*`; see [Upgrading](upgrading.md).
