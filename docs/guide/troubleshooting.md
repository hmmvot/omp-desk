# Troubleshooting

- **OMP not found.** Make sure `omp --version` works in a new terminal, then reload the window. To use a specific program, set [`ompDesk.executablePath`](settings.md).
- **Something looks wrong.** Open **View > Output** and choose **OMP Desk**, and run **OMP Desk: Show Diagnostics**. Include both when you [report a bug](https://github.com/hmmvot/omp-desk/issues/new/choose). See [The OMP Desk log](#the-omp-desk-log).
- **Upgrading from an early local build.** See [Upgrading](upgrading.md#from-the-unpublished-local-build).
- **A message says Windows blocked OMP Desk's native module (or it is missing).** See [The native module is blocked or missing](#the-native-module-is-blocked-or-missing).
- **A message says another Windows account has access to OMP Desk's folder (for example when VS Code runs as a different user).** See [Another Windows account can reach OMP Desk's folders](#another-windows-account-can-reach-omp-desks-folders).
- **A Chat tab froze or stopped responding.** See [A Chat tab that stops responding](#a-chat-tab-that-stops-responding).
- **Chat replies stop arriving, or a sent message is reported as unconfirmed.** See [Chat replies stop arriving](#chat-replies-stop-arriving).
- **OMP became its own program after `omp update`, and the settings editors or the Skills, Tools, MCP and Extensions views stopped opening.** See [After `omp update` changed Bun's launcher](#after-omp-update-changed-buns-launcher).
- **A session ended with `identity-mismatch`, or a session appears twice, after OMP started the same file elsewhere.** See [A session that continued in a newer file](#a-session-that-continued-in-a-newer-file).

## After `omp update` changed Bun's launcher

OMP 18.13 needs Bun 1.4.4 or newer. When `omp update` finds that the launcher Bun installed cannot run the new release (the usual cause is an older Bun: `omp update` printed `bun did not install a working omp … launcher … installing the standalone binary`), it replaces Bun's `omp.exe` with OMP's own compiled program and prints `This install is no longer managed by bun`. Bun's global package folder (`%USERPROFILE%\.bun\install\global\node_modules\@oh-my-pi\pi-coding-agent`) stays on disk, but nothing starts from it any more, and later `omp update` runs replace the program only; the package is never updated again and may fall behind the program.

OMP Desk follows `omp` on your `PATH`, so it now starts that program, exactly as for the compiled program in the table of [Getting started](getting-started.md#requirements):

- **Chat and Terminal work** (host control is carried in `BUN_OPTIONS` after a one-time check of the program).
- **The Models, Agents and OMP Settings editors, the Skills, Tools, MCP and Extensions views and the stopped-session rename say that OMP has no source on disk.** They read OMP's own TypeScript source, which the compiled program carries inside the executable. Desk deliberately does not read Bun's leftover global package instead: a package of the same release number is not proof that it is the source of the program you run, and after the next `omp update` it would not be. `/settings`, `/agents` and `/model` in the session's Terminal view do the same work.
- **A Chat no longer survives a VS Code update.** Chats keep running through an update only when OMP runs on a `bun.exe` Desk can share ([Sessions](sessions.md#the-vs-code-update-exception)); the compiled program has none, so its Chats run as `Code.exe` like Terminals.

To get the full set back, install OMP with Bun again: run `bun upgrade` (to 1.4.4 or newer), then `bun install -g @oh-my-pi/pi-coding-agent`. Bun writes its launcher over the compiled program and `omp --version` then runs from the package again. Close every OMP session first: Windows does not let Bun replace an `omp.exe` that is running. A running session started before the update may also print `Bun runtime must be >= 1.4.4` when OMP starts one of its helper processes, because the files on disk are already the new release; restart such a session after the update.

## A session that continued in a newer file

OMP 18.13 can move a session to a new file when it cannot keep writing the old one: for example when you open the same session file with `omp --session <file>` in another terminal while OMP Desk still holds it, or when another program changes the file under a running session. The new file is in the same folder, has its own session id, and records which file it continues. Asking OMP for the old file afterwards opens the newer one.

OMP Desk follows that move. When a Chat or a Terminal reports the newer file, OMP Desk reads the files' headers and accepts it only if the newer file really continues the one it asked for; the session keeps its one row in Sessions, its tab and its editor, and the row now points to the newer file. Reload Window, Stop and Resume, and Resume from a folder's history work as before, and History lists the conversation once.

- **A session still ends with `identity-mismatch`, `identity-diverged` or a refused terminal start.** The file OMP opened is not a proven continuation (an unrelated session, a file from another folder, a damaged or missing header, a link that loops). Use **Restart**; when Restart refuses, Forget the row and open the file OMP used from the folder's history.
- **Sessions shows two rows for one conversation.** They were created before OMP Desk learned about continuations. OMP Desk does not merge them; resume the newer one and forget the older.
- **A Chat page that kept running while the extension restarted stays disconnected after its session moved.** The page's saved connection names the old file. Reload Window or reopening the editor makes a new one (Stop and Resume does not).

## The OMP Desk log

The log shows activation, restores, launches and failures at its default level (Info). One `window timing: restore tab … attached in N ms · admission … · reconcile … · attach … · persist …` line per restored Chat shows where a slow restore spent its time. One `window timing: new session <tab> start timeline, ms from the command: admission 5 · stage 25 · … · omp spawned 325 · omp control published 3825 · omp ready 24325 · host control verified 24425 · chat live 24625` line per session you start (`new session`, `resume`, `open`, `restart` or `view switch`) shows where a slow start went: every step is the milliseconds since you gave the command, in the order it happened, so a long gap between two steps is where the time was spent (a gap before `omp ready` is OMP itself starting; a gap before `runtime check` or `broker spawn` is OMP Desk checking the runtime that hosts the session, which takes longest the first time after an extension update; the step `runtime proof` is the wait for the broker runtime a Terminal needs, and a Chat does not wait for it). A Terminal start ends at `host control verified`, a Chat start at `chat live`. A start that fails or is cancelled writes the steps it reached and where it ended: `start ended after N ms, failed or cancelled at <step>; ms from the command: …`. The other per-step timings and diagnostics are at Debug: raise the level with the gear in the Output panel's toolbar, or run **Developer: Set Log Level…**, choose **OMP Desk** and then **Debug** (it applies at once and returns to Info when the window reloads; start VS Code with `--log=hmmvot.omp-desk:debug` to keep it).

After an extension update, several windows that reload together check the runtime once between them: one window runs the check and the others take its result, which the log shows as `PTY runtime proof reused from …: ready in N ms; waited N ms for another window's check that was running and took its proof`. A window whose own OMP runs through a Bun shim also starts, in the background right after it opens, the Bun check its first Chat needs, and logs it as `Bun runtime pre-check ahead of the first Chat: …` (nothing is logged at Info for an OMP that is a standalone program, or when the setting `ompDesk.chatBrokerRuntime` is `vscode`). A wait that runs out never blocks anything: that window runs its own check, as before.

The log is also a file that is written as it happens, whether or not the Output panel is open: `<VS Code logs folder>/<session>/window<N>/exthost/hmmvot.omp-desk/OMP Desk.log`, one file per window that every Reload appends to (**Developer: Open Logs Folder** opens the folder).

## A Chat tab that stops responding

A visible Chat page tells OMP Desk that it is alive every 2 seconds (sooner while something happens in it), and the **OMP Desk** log shows at its default level (Info) when that stops. A report holds counts and kinds only: no message text, no draft and not which key you pressed. A freeze is a page whose main thread does not run; the extension host keeps running, so the rest of the log carries on as usual.

- **`tab <id>: no report from the Chat page has reached the host for 10 s while it was visible (its last report, #<n> (<reason>), came 10 s ago); its last events before it: …`** No report arrived for 10 seconds. The events are what the page did last, oldest first, each with how long before that report it last happened: `rx:<type>` is a message of that type from the extension host (`×N` for a run of them), `render` a redraw of the conversation, `key`, `pointer`, `input`, `paste` and `drop` an input of that kind, `visible` and `hidden` a change of the page's visibility. The last entries are what it was busy with: a long run of `rx:omp:chat-event` followed by `render` points at drawing a very long reply, for example. The last half second before a freeze can be missing from the list. `and said the page was hidden` after the report's age means the page had reported itself hidden and has not said it is visible again since you left the window or the tab and came back to it.
- **`tab <id>: the Chat page reports again after 47 s without a report; its own timer was 46 s overdue`** The page answered again. The first figure is how long the host heard nothing. The second is how overdue the page's own timer was when it reported, which is how long the page's main thread was stuck: a figure close to the first means the page was stuck, no second figure (or one near zero) means its reports were held up on the way, in VS Code's window or in the connection to the extension host. `the page had reported itself hidden, so its own timer figure cannot tell whether it was stuck` means the page's last report before the silence said it was hidden, and a hidden page has no timer to measure, so only the first figure is known. `this window's extension host was itself paused meanwhile` means the host did not run either (a blocked host or a sleeping computer), so the figure may include that; `the page was reloaded` means a new page document reported, not the stuck one. `tab <id>: the Chat page was closed after 15 s without a report` is a stalled tab that was closed before it answered, and `was replaced after 15 s without a report` one whose page was swapped for another document (a mode switch, for example); the end of a stall is logged only for a stall whose first line was logged.
- **`tab <id>: the Chat page ran one task for 2.6 s, self in window, scripts: user-callback:TimerHandler:setTimeout - - 2.6 s; its last events: …`** The page measured one task of a second or more and then recovered. This is the page's own measurement, so it reaches the log even when the stall lines above do not appear (a page that was stuck for less than ten seconds, for example). After `scripts:` come up to three entries, longest first, each as: what started it (the browser's kind of caller and the handler or callback), the function name as the page's bundle has it (`-` when anonymous or unknown), the file name and character position in the page's script (`guest.js:812345`, or `-`) and how long it ran. `no script attribution` means the browser named none. The log shows at most one such line a second and 50 for a page, and at most 20 stall lines for a page; a page that reaches a bound says so once, and the bound belongs to that page document: it applies for the rest of its life, even if the page restarts its own counters.

Nothing is reported for a Chat tab that is not visible (another tab is in front, the window is minimised or covered): a hidden page's timers are slowed down by the browser and its silence is not a freeze, and a page counts as silent only after ten seconds in which it was visible. A tab that is hidden and frozen at once is reported ten seconds after you show it. Include these lines, and the lines about the same `tab`, when you [report a bug](https://github.com/hmmvot/omp-desk/issues/new/choose).

## Chat replies stop arriving

A Chat talks to OMP through a small background process, the broker, that keeps OMP's recent output and hands it to the window. When that hand-over stalls (a long session after a reload is the usual case) OMP still answers, but the answer reaches the window late. The **OMP Desk** log says what happened, at its default level (Info):

- **`the broker connection closed: <reason>; last seq 120345, 3 lines since the attach; read 311 frames in 40 reads (…)`** The connection between the window and the broker ended. `(this window replaced it)` means the window did it itself. Anything else came from the broker or the operating system; `the peer closed the connection` is the broker, and the line after it says why.
- **`reattach started: last seq 120345 (the broker connection ended on its own)`**, then **`reattached: replay from seq … (the broker holds … to …); the broker (any window) closed a consumer as paced (its socket did not drain) 2 s earlier`** or **`… as fallen behind its retained lines …`**, then **`reattach finished in 840 ms after 1 attempt: last seq … to …, 17 lines received, phase live`**. *Paced* means the window did not read what the broker sent for 10 seconds, so the broker ended the connection at once instead of waiting minutes. *Any window* is literal: the broker keeps one record for all windows, so the close can have been another window's. *Fallen behind* means the broker's memory of recent output moved past what the window had read, so the window had to reattach. `reattach failed after …` is the end of its attempts: the Chat shows a Reconnect action.
- **`reattach attempt 2 failed after 45012 ms (the broker did not complete the attach within 45000 ms); trying again in 500 ms`** One attempt to reconnect to the broker did not finish; the window tries again after the delay. The reason in brackets names which step did not answer: the broker's handshake (`the broker did not complete the handshake within 10000ms`, with `(this process's event loop had been blocked for … ms)` when the window itself did not run), the reconnect (`the broker did not reconnect within 30000ms`) or the attach request (cut at 45 seconds). Once the attempts have taken two minutes in all (an attempt under way finishes first; the steps after the attach request keep their own deadlines, the longest being the child's 120-second ready wait) the reattach ends in **`reattach failed after … ms and … attempts: attach-failed (<reason>)`**: the Chat shows its failure with a Reconnect action, and slower automatic retries continue. A reattach no longer waits for ever on "Connecting to the session…"; a Chat that still does, with no line like these in the log, is a bug to report. **`the first attach failed: attach-failed (<reason>)`** is the same for the attach when a Chat starts.
- **`the broker's lines in between are gone: the transcript was re-read from the session file (last entry …)`** The broker had dropped output the window had not yet read (see *fallen behind* above, or a long stall of the window itself), so the window rebuilt the conversation from the session file instead of asking OMP for everything it missed, and then asked OMP only for what the file did not yet hold. Nothing is lost; the Chat repaints once.
- **`the link has delivered nothing for 5400 ms while prompt waits for its answer (5100 ms); last seq …; read 311 frames in 40 reads (… bytes from the socket, … unread), busy 220 ms, slowest read 40 ms and frame 9 ms, … bytes unsent`** A command has waited 5 seconds and nothing came. The traffic figures are the measurement: a large *busy* time or *slowest frame* means the window was slow to process what arrived; *unread* counts bytes the socket had received and the window had not yet taken; *unsent* counts bytes the window had not yet written to the broker. The window then asks the broker itself for its status (a request OMP never sees). If the broker answers (`the broker answered a status request in 3 ms: the link carries traffic, so the stall is OMP holding the command`) the connection is fine and OMP is busy: nothing is shown. If the broker does not answer (`the broker did not answer a status request within 15000 ms: the broker or the link is stalled`), or has not answered within 2 seconds, the Chat shows *OMP is not answering through the connection. Waiting a moment, then reconnecting on its own.* The window never replaces the connection because of that question alone: a broker that holds unsent data for 10 seconds ends the connection itself, and a connection that stays silent otherwise is replaced by the watchdog after 45 seconds of work or 90 seconds idle (plus its 15-second probe). Any line arriving ends the stall.
- **`OMP is working but has sent nothing for 5400 ms; last seq …`** OMP is busy without output (a long tool, a background wait), one line per silence. Nothing is wrong by itself; the traffic figures are there for when it is.
- **`the answer to prompt has not come for 31000 ms, but frames are still arriving`** Frames are arriving, so the link is not stalled: the answer is queued behind a long one, usually the whole conversation sent after a reload.
- **`OMP has not answered get_state for 2100 ms, but lines keep arriving (last seq …, 40 since the attach): the tab is shown live and read-only until it does`**, then **`OMP answered get_state 48000 ms after it was asked: the session is confirmed`**. After a reconnect OMP answers the state request in the order of its output, so while it streams heavily the answer can come a minute or more late. The Chat shows the conversation as it streams, with "Waiting for OMP to confirm this session; sending is paused until it does." in the composer, and sends, Stop and the tools wait for the answer. If it does not come within five minutes (or the lines stop for 30 seconds) the Chat shows the failure with Reconnect and Restart, as before.
- **`frames resumed after 7400 ms without one`** The stall ended and the notice is gone.
- **`the answer to prompt <id> did not come, but the session file holds the message (entry …): treated as delivered, transcript read from the file`** A message whose answer was missing for 30 seconds is on disk, so it reached OMP and is not sent again. Until the stream is back the Chat reads the conversation from the session file every two seconds. A message that is not in the file is reported as before: *may not have been delivered*.
- **`a check of rows saved on another branch is served from the session file (44 MiB), not by get_entries`** Once per session. In a session file of 8 MiB or more, the check that a pending row was saved on another branch reads the file and does not ask OMP for the whole transcript through the broker.
- **`event loop blocked for 41200 ms (… process CPU 39800 ms …): no marked Desk operation was running; metered Desk work in that time: broker socket read 120 times, 31000 ms in all, longest 640 ms; chat output delivery …`** The window's extension host (shared by every extension) did not run its timers for that long. If *metered Desk work* is present, its totals say how much of the stall was OMP Desk reading and delivering chat output (`broker socket read` includes the `chat output delivery` it caused, so read each name alone); a total far below the stall means the time went elsewhere, in another extension or in VS Code. With nothing metered, the line says that no Desk work was running. A stall of this size also makes the broker end the window's connection as *paced*, which the lines above then show.

The broker also writes a log of its own, one file per Chat, in the `logs` folder of OMP Desk's storage. It has `rpc consumer paced <ms>: …` while a window does not drain, and `rpc consumer summary: …` when a window disconnects: lines and bytes sent, the time spent sending, the slowest send, and how often the broker found a window below its pacing bound again (*resumed below the bound*) or with nothing queued although no drain had been reported (*missed drains*). Include these lines with the `tab` they are about when you [report a bug](https://github.com/hmmvot/omp-desk/issues/new/choose).

## The native module is blocked or missing

OMP Desk answers its Windows questions inside VS Code's extension host instead of starting PowerShell: whether another OMP holds a session, when a process started, and who owns and may read the folders it keeps its private state in. It does that through one prebuilt file, `koffi.node`, from the open-source [koffi](https://koffi.dev) foreign-function library (version 3.3.3, MIT). The file is shipped unmodified, pinned by its SHA-256, and koffi does not code-sign its binaries, so it is **not Authenticode-signed**. Neither is node-pty's `conpty.node`, which Terminals already depend on.

An organization that only allows signed code (AppLocker or Windows Defender Application Control, WDAC), or a security product that quarantines unknown DLLs, can refuse to load it. There is **no fallback**: OMP Desk would rather not start a session than start one it cannot check. While the module is unavailable:

- **Do not work:** New Session, Resume, and re-attaching a running Chat after a reload; the Sessions view cannot tell whether another OMP holds a session.
- **Still work:** the Sessions view and **Resume Session** still list your saved sessions, and a stopped session still opens, read-only, in its tab; the rest of VS Code is untouched.

Desk shows one message per window with the cause where Windows names it (policy block, missing or quarantined file, a stage that timed out, anything else) and three buttons: **Copy diagnostics**, **Open troubleshooting** (this section) and **Reload Window**, which stages and loads the module again once you have fixed the cause. The exact error is always in the **OMP Desk** output channel. A Windows that shows its errors in another language can make Desk report the cause as "not recognized"; the error text in the log and in the diagnostics is still the one to give your administrator.

### What to ask your administrator

Allow the file in both places it is loaded from. The extension folder copy is loaded by a short staging step at the start of every window; the staged copy is the one every window and session process then loads:

| Where | Path |
| --- | --- |
| Installed with the extension | `%USERPROFILE%\.vscode\extensions\hmmvot.omp-desk-<version>\out\native\koffi.node` |
| Staged copy in VS Code's global storage | `%APPDATA%\Code\User\globalStorage\hmmvot.omp-desk\runtime\<sha256>\koffi.node` |

(`Code - Insiders` and a custom `--user-data-dir` or `--extensions-dir` change the first part of the paths; **Copy diagnostics** has the exact ones.)

- **AppLocker (DLL rules must be enforced).** Add an *Allow* DLL rule with the condition **File hash**, pointing the rule wizard at the file, or from PowerShell: `Get-AppLockerFileInformation -Path "<path>" | New-AppLockerPolicy -RuleType Hash -User Everyone -Xml`. The rule applies to the file's contents, so one rule covers both locations. A **path** rule also works, but it trusts everything a user can write into those folders: use the wildcard `%USERPROFILE%\.vscode\extensions\hmmvot.omp-desk-*\out\native\koffi.node` and `%APPDATA%\Code\User\globalStorage\hmmvot.omp-desk\runtime\*\koffi.node` only if a hash rule is not possible.
- **WDAC.** Add a file rule at the **Hash** level for the file to your policy (for example `New-CIPolicyRule -DriverFilePath "<path>" -Level Hash`), or an allow rule by path if your policy format supports it.
- **Check that it is the file Desk ships.** `Get-FileHash -Algorithm SHA256 "<path>"` prints the file's SHA-256, which must equal the **Shipped SHA-256** line of **Copy diagnostics** (and the staged copy's name). The hash a policy tool computes for a program file is calculated over its executable image and can differ from this value, so let the tool compute it from the file rather than typing in the `Get-FileHash` value.
- **Antivirus.** Restore `koffi.node` from quarantine (in Windows Security: **Protection history**, then **Restore**) and add an exclusion for the extension folder `%USERPROFILE%\.vscode\extensions\hmmvot.omp-desk-*` and for `%APPDATA%\Code\User\globalStorage\hmmvot.omp-desk\runtime`. A product that holds the file for a long scan on first sight shows up as a stage that timed out: **Reload Window** after the scan.

**Updates.** The path of the extension folder changes with every OMP Desk version, so use the wildcard form there or re-add it. The file's hash changes only when OMP Desk moves to a different koffi version (the [changelog](../../CHANGELOG.md) says so), and differs between the x64 and arm64 builds; a hash rule written for one koffi version stops matching after such an update, and the message above returns until the rule is updated. Check **Copy diagnostics** after an update that shows it.

## Another Windows account can reach OMP Desk's folders

The message reads like this (the account and the folder are yours):

> The native module (koffi.node) did not load: another Windows account, `PC\OtherUser`, has full control of `C:\Users\<account>\AppData\Roaming\Code\User\globalStorage\<publisher.extension>`, so it could replace the module that runs as `PC\<account>`. Remove that account's access to the folder, or run VS Code as the account you are signed in to Windows with, then choose **Reload Window**.

**Why OMP Desk refuses.** OMP Desk starts programs from copies it keeps in VS Code's global storage (the native module, helpers, the broker). It runs them only when the account that runs VS Code, `SYSTEM` and the Administrators (the group, and any account Windows lists in it, see below) are the only ones who can replace those files, replace a folder on the way to them, or change who may do so. An account that could swap one of them could run its own code as you. The refusal is the check working; it cannot be switched off, and there is nothing to allow-list. Because the check cannot pass, the module stays unavailable and the same things stop working as in [The native module is blocked or missing](#the-native-module-is-blocked-or-missing): New Session, Resume and re-attaching a running Chat; saved sessions are still listed.

**An administrator account does not trigger it any more.** Up to OMP Desk 0.4.14 the message also appeared when you are signed in to Windows as an administrator, VS Code runs as another (standard) account, and your administrator account has an entry on that account's profile folder ([issue #1](https://github.com/hmmvot/omp-desk/issues/1)): the check trusted the Administrators *group* but not a single administrator *account* with full control. From the release after 0.4.14, an account that Windows itself lists as a member of the local Administrators group is trusted the same way as the group, because an administrator can elevate and reach everything the group reaches anyway. The membership is read from Windows by account SID (`NetLocalGroupGetMembers`), never guessed from a name, and kept for as long as the window lives: if you add or remove an account in the Administrators group, choose **Reload Window** for OMP Desk to see it. The rule still refuses every other account, including a standard user with an entry on the folder, a group such as `Users` and any account whose membership Windows cannot confirm. That includes an administrator who is a member only through another group (for example a domain group such as `Domain Admins` that is itself a member of Administrators, or a local group nested inside it): the rule reads direct members only and does not guess, so remove that account's entry or use the other ways below.

Typical ways to get here are an access entry added to the profile folder (to make it reachable from another account, for instance), a folder copied, restored or moved together with its permissions, and VS Code running as a different Windows account than the one you are signed in to Windows with. The message has one of three forms:

- *has full control of / modify access to / delete or permission-changing access to `<folder>`, so it could replace the module* is an entry on the folder itself or on a folder on the way to it. Only an entry that lets the account replace or re-permission counts; read-only entries on a parent such as `C:\Users` are fine.
- *has read access to `<path>`, where the module that runs as `<account>` is kept* is an entry on OMP Desk's own folders, which only you, `SYSTEM`, the Administrators and the accounts in that group may open.
- *`<path>` is owned by another Windows account* is an owner other than you, `SYSTEM`, the Administrators or an account in that group, who can change the folder's permissions whatever its entries say.

**See which entries there are.** In a Command Prompt or PowerShell of the account that runs VS Code:

```powershell
whoami /user
```

prints the account VS Code runs as and its SID (`S-1-5-21-…`). **Copy diagnostics** in the message has the folder (`Folder:`), the other account (`Other account:`), what it may do (`Its access:`), whether the entry is inherited (`Entry:`) and who VS Code runs as (`VS Code runs as:`). To list every folder on the way to the module, set `$p` to the folder the message names:

```powershell
$p = "C:\Users\<account>\AppData\Roaming\Code\User\globalStorage\<publisher.extension>"
while ($p) { icacls $p; $p = Split-Path $p -Parent }
```

An entry reads `PC\OtherUser:(OI)(CI)(F)` for full control (`(M)` is modify, `(RX)` is read and execute). `(I)` at the start of the flags means the entry is **inherited** from the folder above; without it the entry is set on that folder itself.

**Remove an entry that is set on the folder itself.** From a prompt of the account that owns the folder, or an elevated one when it answers "Access is denied":

```powershell
icacls "C:\Users\<account>\AppData\Roaming\Code\User\globalStorage\<publisher.extension>" /remove:g "PC\OtherUser"
```

`/remove:g` removes only what was granted to that account, on that folder. Then choose **Reload Window**; OMP Desk stages and verifies the module again.

**An inherited entry** cannot be removed where you see it: it comes from a folder above. Walk up with the loop above to the first folder whose entry for that account has no `(I)`, and remove it there with the same `icacls … /remove:g` command. If that folder is one you must not change (a whole shared profile, say), use the second or third way under **VS Code run as a different user** below. Do not turn inheritance off on a system folder to get rid of an entry.

**If the folder is owned by another account**, run VS Code as that account, or from an elevated prompt give it back: `icacls "<folder>" /setowner "PC\<account>"`.

**VS Code run as a different user.** The message names the accounts as the VS Code that shows it sees them: the module "runs as" the account that runs VS Code, and the other account is whichever one holds the entry, which can be the account you are signed in to Windows with. If you start VS Code as another account (**Shift** + right-click, **Run as different user**, or `runas /user:…`), its data and OMP Desk's folders are in that account's profile, and an entry there for the signed-in account lets that account replace what the other one runs, which is what the check refuses. Either:

- run VS Code as the account you are signed in to Windows with, so that its own profile is used, or

## My sessions and folders disappeared

If VS Code removed OMP Desk's storage folder (for example after a failed reinstall of the extension), OMP Desk restores the sessions, the folders and the reconnect records of running sessions on the next start from a private copy it keeps in `%LOCALAPPDATA%\omp-desk\recovery\<key>`, shows one notice with the age of the copy, and writes the restore to the **OMP Desk** log. If no usable copy exists, it says so once instead of starting silently empty, and names what it still sees (open editors for sessions that are gone, remembered sessions, running OMP processes with no record).

- **OMP processes still run but have no row.** They appear in the Sessions view (Terminals group) as *Unmanaged*. Desk cannot reconnect to them (their token was in the lost record); use **Kill** on the row to end one.
- **A restore is not wanted.** To reset OMP Desk completely, close every VS Code window, then delete both its storage folder and the recovery folder (`%LOCALAPPDATA%\omp-desk\recovery`).
- **Restoring older sessions by hand.** The recovery folder holds the previous copies of `catalog.json`. Close every window, copy the one you want over `<globalStorage>\hmmvot.omp-desk\catalog\v1\catalog.json` and start VS Code.
