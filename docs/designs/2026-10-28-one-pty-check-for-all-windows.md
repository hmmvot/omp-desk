# One PTY runtime check for all windows, and the Bun check warmed at activation

## Problem

After an extension update every window that reloads stages the same broker tree and then runs the same self-check, each in its own process, at the same moment. The retained logs of one update show four windows that each logged `PTY runtime proved itself` for the same tree within one second of each other, with self-checks of 8.9 s, 10.1 s, 11.1 s and 16.0 s (`ready in` 22.0–23.4 s); the earlier update of the 2026-10-23 design measured self-checks past their 15 s deadline in every window, with 36–78 s until the runtime was admitted. The check proves properties of the staged tree, the executable and the operating system build (ADR-0032); none of them differs between the windows, so four checks answer one question, and each makes the other three slower, which is how a check that takes 4 s alone ends at 9–16 s and, on a slower machine, past its deadline: an inconclusive answer, a provisional admission and a repeated check 20 s later in every window.

The Chat's own check, the Bun plan's pipe-only self-check of `bun.exe` (ADR-0074), has the same shape and one more problem: it first runs when the first Chat of a window starts, in the middle of the start, so the start waits for it. The 2026-10-23 design left "start it at activation" for later.

## Goals and Non-goals

- Goals: (a) a window starts the Bun plan's pipe-only check in the background at activation, without delaying activation, the first paint or the restore, so the first Chat finds it done; (b) windows that need the same check (the same tree, executable file and operating system build) run it once between them: the first runs it, the others take its result, a crashed or hung first window is recovered from, and a window never waits unboundedly.
- Non-goals: a faster check, a different deadline, caching a failure as a success, staging (the access verification and hashing that precede every check and remain per window), the restore's pipe work and the helper processes' scheduling ([ADR-0084](../decisions/0084-run-helper-processes-through-one-per-window-scheduler-with-cross-window-slots.md), another change), any change of what the stored proof contains.

## Current State

`ensurePtyRuntime` (`src/host/pty-runtime.ts`) stages and verifies the tree, builds the proof key from every input the answer depends on (`ptyProofKey`: tree digest, runtime version, the executable's path, size and modification time, its versions when it is this process's own, platform, architecture, OS release, `pipeOnly`), reads the proof stored under that key (`readPtyProof`: reused when it is under 24 h old and equal in every field), and otherwise runs the self-check (`runSelfCheck`, a child with a deadline per phase), storing only a *proven* answer (`writePtyProof`, atomic). An inconclusive answer admits the launch provisionally and is not stored (ADR-0032 amendment 2026-10-12); `PtyRuntimeProof` repeats it once, 20 s later, with a 90 s deadline. So a stored proof already is the durable, key-exact result that windows share; what is missing is that windows which find no proof all run the check, each at the same time.

The Bun plan's check is the same `ensurePtyRuntime` with `pipeOnly: true` and `nodePath` the `bun.exe` of the launch, run by `PtyBrokerClient.chooseChatRuntime` for a Chat launch only (`proveBunRuntime` wraps it, see the 2026-10-23 design). The OMP launch is resolved per launch (`resolveOmpBinary`: an `omp --version` probe), and a window already shares one such resolution among its other callers (`executableFor`).

Cross-window mechanisms that exist: the slot lock `acquirePtySlotLock` (a lock file created exclusively, its holder's process id checked for liveness, polled with a bound), the window registry, the proof store, the claims directory. None of them is keyed by a check.

## Proposed Design

### (b) A cross-window single-flight around the self-check

New module `src/host/pty-proof-flight.ts`, used by `ensurePtyRuntime` between the proof read and the self-check, when the key is known:

1. The **key** is the proof key, named by `ptyProofKeyName(key)` (the hash the proof file already carries). Every field of the key therefore separates flights: a window with another tree, another `bun.exe` file (path, size, time), another OS build, the pipe-only or the full check, never waits for another's.
2. The **result** is the stored proof, not a new record. The check is run by `attempt()`, which writes the proof **before** the lock is released. A window that finds the lock held polls the stored proof (250 ms) and takes it when it appears, reporting it as a reused proof (`reusedProof`, with `flight.via: "stored"` and the time waited). The in-process cache keeps the stored proof's file and time with the runtime, so a launch that relied on a proof a window's warm-up (or an earlier call) read from the store can still withdraw exactly that file when the launch contradicts it (the 2026-10-13 rule of ADR-0032, which the warm-up would otherwise have silently ended for every window that warmed up).
3. The **lock** is the file `<globalStorage>/runtime/pty-flight/<name>.lock`, in a directory beside, not inside, `pty-proof/`. It is created whole in one step (a temporary file linked to the name, so no reader sees half a record) and holds the holder's id, process id and the time its attempt can last at most (`2 × deadline + 30 s host bound + 5 s`). A lock is **stale** when its process id is not alive, when its time is past although the id is alive (a reused or hung process), or when its content is corrupt; a stale lock is taken over after a second read that confirms it is the same lock. A lock that cannot be read at this moment (a rename in flight) is a live holder's and is waited for, never removed.
4. A **wait is bounded** by `2 × deadline + 5 s` (35 s for the default 15 s, 185 s for the extended re-check). When it runs out, and when the lock directory cannot be used at all, the window runs its **own check without the lock**, as every window did before.
5. A check that ends **without a proof** (inconclusive, or broken with an observed fault) leaves an **outcome** next to the lock before the lock is released: the kind, the detail and the deadline it ran under. A window that waited for exactly that holder, and asked for no more time than the holder had, takes the outcome as its own answer (a provisional admission, or a refusal, with the holder's detail and a note that another window's check was the source) instead of repeating a check that just ended the same way on the same machine. Without this, the windows behind a check that ran out of time would each run one in turn, or concurrently after their wait, and the incident would only move. The outcome is never a success, is never stored as a proof, and is never read by a window that did not wait for that attempt: a window that starts later runs its own check. A window whose deadline is longer (the 90 s extended re-check) never takes a shorter check's outcome.
6. A **failure is not cached as success**: a proof is written only by the check that proved; the outcome file is a different file, in a different directory, with another reader.

The lock is an optimisation, not a mutual exclusion the answer depends on: two windows that both find a stale lock may both take it over and run two checks, which costs one duplicate check and nothing else (the proof write is atomic and equal). This is also why the lock needs no fencing token.

`PtyRuntimeReadiness.flight` records how the answer came about (`stored`, `shared`, `owner` after a wait, `local` after a timeout) and whether a holder waited for ran in another process, and the proof's log lines carry it (`…; waited 3120 ms for another window's check that was running and took its proof`; `this window's own` when the holder was this window's warm-up), so the Output log of an update's windows shows who ran the check.

Staging stays per window and before the flight: every window still re-hashes its copies and verifies the access rules, exactly as before the proof is looked at.

### (a) A warm-up of the Bun plan's check at activation

`startChatRuntimeWarmup` (`src/host/chat-runtime-warmup.ts`), called at the end of `activate`, hands its work to a later turn of the event loop (an unreferenced zero-delay timer), so activation, the first paint and the restore do not wait for it, and every way it can end is a log line, not a rejection. It resolves the OMP launch through the window's one shared resolution (`sharedOmpBinary`, the single-flight `executableFor` already had) and calls `PtyBrokerClient.warmChatRuntime(binary)`, which judges what a launch judges up to the check (the setting, the platform, the launcher kind, the file, a hold) and then runs the same `proveBunRuntime` as `chooseChatRuntime`. It reads no trust, records no hold and no fallback, starts no broker: a warm-up that ran out of time costs the next launch nothing it would not have paid, and a launch that starts while the warm-up runs finds the lock held by its own window and takes the proof (or the outcome) when it lands, so the check is not repeated inside a window either. The proof it leaves is the ordinary one: in the process (`provedRuntimes`) and in the store, so a window that starts later, in the same hour or the next, finds it. A window with no bun-shim OMP (a standalone `omp.exe`), the setting `vscode`, or a non-Windows-x64 host does nothing.

## Alternatives

- **A single-flight only for the proof file, no outcome.** Simpler; but the windows behind an inconclusive check then run one after the other (each past its wait) or all at once (after a timeout): the incident of this design, in a different order. Rejected.
- **Cache an inconclusive or broken outcome for a time (a negative cache).** It would also serve windows that start after the attempt ended; but a refusal that was caused by a transient load would then be served to a window that could succeed, which is the harm ADR-0032's amendment of 2026-10-12 removed. Only the windows that waited for that attempt take it.
- **One check run by a designated window (election through the window registry).** The registry's liveness is heartbeat-based and slower than a lock file's process-id check, and a designated window that never starts a check would leave the others waiting.
- **A named mutex or Windows API lock.** It would need the native module before it is verified, and the check runs before the native proof exists for some paths. A lock file with a process-id check is what `acquirePtySlotLock` already trusts.
- **Warm-up after the startup restore, like the full proof.** The restore is where a Chat that needs a fresh broker starts; a warm-up after it does not help that start. A warm-up before the first view paints would delay it. A later turn of the event loop after `activate` returns is the earliest that delays nothing.
- **Warm-up without resolving the OMP launch** (reading the shim and the `bun.exe` beside it directly). The resolution is what a launch uses and is shared in a window; a second, partial one would drift from it.

## Risks and Open Questions

- **The warm-up adds one `omp --version` probe and one staging pass per window, at the moment the machine is busiest.** The probe is the one the first launch pays anyway (a launch resolves the OMP itself; the warm-up shares its resolution with the window's other readers, not with a launch, so a Chat started right after activation resolves once more; for a bun shim the release comes from the package manifest and no child starts); the staging pass is the one the full proof's background start (after the restore) already pays. On a window with no Bun-shim OMP the probe is the only cost. A stored proof (under 24 h) reduces the check to a read.
- **A window waits behind a check it could have run itself.** Bounded as above; the wait is for a check that is already running on the same machine, which a second concurrent check would only slow. A hung holder is recovered after its declared time at the latest.
- **The outcome of a refusal is taken by the windows that waited.** A refusal is an observed fault of this tree, executable and operating system under this account; it is the same fault in every window. Its wording says it came from another window's check.
- **A process id alive but not the holder** (reuse after a crash) delays a waiting window until the lock's time is up (at most the wait bound) and then the window checks for itself.
- **The files left behind** (an outcome after an inconclusive check, a lock after a crash, and the temporary file of a crash between its write and its link) are small and named by the key; the first two are never read without the matching holder and are removed or replaced by the next check of the key; the temporary file is never read at all. The proof files already accumulate the same way (ADR-0032); nothing prunes any of them.
- **Security.** The flight directory sits below `runtime/`, whose access rules staging establishes before anything is written, like `pty-proof/`; a file there can make a window wait for a bounded time or take an inconclusive or broken outcome, never a proof, because proofs are read only from the proof store and a proof file is still checked against its key.
- Not measured on the installed build with several real windows (see Rollout).

## Rollout and Verification

1. `pty-proof-flight.ts`, `ensurePtyRuntime`'s use of it, `PtyRuntimeReadiness.flight`, the log suffix, `warmChatRuntime`, `chat-runtime-warmup.ts`, the `activate` call and `sharedOmpBinary` in `src/extension.ts`.
2. Tests (`src/host/pty-proof-flight.test.ts`, `chat-runtime-warmup.test.ts`, the warm-up cases of `pty-client-bun.test.ts`): concurrent windows run one check and the others reuse it; a dead holder, a lock past its time and a corrupt lock are taken over; a live holder is waited for and a wait that runs out runs a local check; a different key never waits; an inconclusive or broken check is shared only with windows that waited for it, never stored as a proof, and not taken by a window with a longer deadline; a throwing check lets go of the lock; the warm-up returns before it resolves or checks anything and ends every failure in a log line; a refused warm-up holds nothing.
3. A simulation with the real `ensurePtyRuntime`, the real proof store and lock files and a modelled check (alone 400 ms, concurrent checks sharing the machine, a 1000 ms deadline): before (no single-flight, `waitMs: 0`) 5 windows ran 5 checks and none was proven; after, 1 check ran and all 5 were proven. The model is a model: its times include about 300 ms of staging and the contention rule is assumed, not measured.
4. Installed check (after an update with several windows): the Output logs of the windows show one `PTY runtime proved itself` or `Bun runtime pre-check ahead of the first Chat: … proved` line and `waited … for another window's check that was running and took its proof` in the others; the first Chat of a window after a reload finds the pipe-only proof in the store (`Bun runtime pre-check … reused`), and its `runtime check` phase carries no pipe-only check.

## Architecture Review

- Reviewer: reviewer (a separate agent that did not write this design or the code), against the source, the tests and the earlier amendments of ADR-0032 and ADR-0074.
- Outcome: one pass, **accept with changes**. The lock protocol (creation by linking a temporary file, takeover after a confirming second read, holder-guarded release, a live holder losing its lock only after the time its check can last), the outcome rule, the wait arithmetic and the access-rule claim were checked against the source and found sound. One must-fix and three should-fix items: (M1) the stored proof a warm-up read was cached in process without the file it came from, so a launch that relied on it and failed could no longer withdraw it (the in-process cache now keeps the stored proof's file and time with the runtime; a test names it); (S1) a wait for this window's own warm-up was logged as another window's check (the note carries whether any holder waited for ran in another process, and the wording follows it); (S2) tests for the withdrawal path above and for a lock entry that cannot be read as a file (added); (S3) the warm-up and the launch each kept a copy of the "is this file held" rule (one helper now). Nits applied: the lock is a file and `pty-flight/` the directory, the OMP resolution is shared with the window's other readers and not with a launch, the leftover temporary file of a crash is named, and the warm-up's timing uses the client's clock. The confirmation of these changes is recorded below.
- Confirmation: the same reviewer re-read the changes against the source: the provenance fix, the `foreign` wording, the two new tests, the one hold rule and the clock were confirmed, and no production regression was found from keeping the stored proof's file in the in-process cache (the only other caller, the window's full proof, never starts from a cached entry; a proof a window computed itself is still never withdrawn). It found one existing assertion that encoded the old cache behaviour and two stale texts (a log quotation and two comments); all three were corrected. Accepted.
- Notes: the numbers of the simulation in Rollout are a model, not a measurement; nothing here was run in an installed window with several real windows.
