# Chat lists OMP's background jobs, links to them and cancels them through OMP's own `/jobs kill`

## Problem

OMP starts background work on the model's behalf (`bash` and `eval` with `async`, `task` spawns) and keeps a turn open while it runs. The terminal UI lists those jobs and cancels them (`/jobs`, `/jobs kill <id>`, the jobs sheet). Chat shows only a working row that says `Waiting for background job…`, so a user cannot see what is running, how long it has run, or stop it short of Stop-ing the whole session. A job's own tool card says `running in background as bg_7` forever, because the card is written once when the job starts. The transcript also names jobs as `proc://bg_30` (a `read` card, `wait` cards, assistant prose), and none of those is a link.

## Goals and Non-goals

- Goals: (1) a third HUD row, **Jobs**, beside TODO and Agents, with a one-line summary and an expandable list with a Cancel per job and Cancel all; (2) the working row's `Waiting for background job…` becomes a control that opens that row; (3) the tool card that started a job shows a live status chip and, while the job runs, a Cancel button; (4) `proc://<id>` in tool cards and Markdown links to that job in the Jobs row.
- Non-goals: listing jobs OMP never showed this transcript (see Risks); starting, pausing or reading a job's output from the row (a `proc://` click only reveals); services (`proc://<name>` of a `bash` service launch, `proc://<id>/mode`), which are not async jobs; a new RPC command (OMP has none for jobs); session reset code (`session.ts` is not touched).

## Current State

Verified on the installed OMP 18.11.1:

- RPC has no job list, job event or cancel command. `get_state.hasPendingAsyncWork` is the only job fact; Desk keeps it as `model.state.hasPendingAsyncWork` and `model.asyncPaused`. It is owner-scoped and also counts queued deliveries and `yieldQueue` items, and it excludes delivery-suppressed or watched running jobs (`agent-session.ts:3038-3053`; `job-manager.ts:1060`). So `pending` can be true with no running job.
- `readBackgroundJobs` (`src/chat/background-wait.ts`) infers running jobs from the transcript for the working row: a start result carries `details.async = { state: "running", jobId, type }` (`bash.ts:790`, `eval.ts:744`, `task/index.ts:1112`), a `job`/`wait` poll lists `details.jobs[] = { id, type, status, label }`, and a delivered result is a custom `async-result` message with `details.jobs[] = { jobId, type, status, label, durationMs }` (`async-job-delivery.ts:131`).
- A **cancelled** job delivers nothing (`job-manager.ts:416-431`; `:489` is the promote path). A transcript-only reader would show a cancelled job as running for ever.
- **A job id does not identify one job.** `bg_N` is monotonic only within one job manager (`job-manager.ts:277,845-850`) and each OMP process has a new manager (`sdk.ts:2218`), so after a Resume or restart ids start again at `bg_1`. A transcript can hold two different jobs named `bg_1`, and `/jobs kill bg_1` reaches only the one the current process owns.
- OMP does tell its own UI how every job ends: after the call returned, the job keeps emitting `tool_execution_update` frames whose `partialResult.details.async.state` is `running`, then `completed`, `failed` or `cancelled` (`bash.ts:880,915,924`; `eval.ts:621`; the terminal UI settles the call's card on it, `event-controller.ts:1980`, and `acp-event-mapper.ts:753` does the same). Desk's reducer treats such a frame as progress of an active tool, so it re-creates an `ActiveTool` that nothing reads for a finished call. For `task`, the frame state is per **call**, not per job: it stays `running` until every spawn settled, then `failed` or `completed`, never `cancelled`, and `jobId` names only the first spawn (`task/index.ts:1095-1113,1133-1137`).
- `/jobs`, `/jobs full`, `/jobs kill <id>` and `/jobs kill all` are a builtin with a text `handle` (`builtin-session.ts:322-379`; it declares a `kill` subcommand, `:328-331`). In RPC mode a `prompt` runs a builtin before it queues anything, whatever `streamingBehavior` says (`rpc-mode.ts:1803`), and the builtin answers with a `command_output` frame. If no builtin with a handler matches (`acp-builtins.ts:64-66`) or an extension `input` hook rewrites the text, the text goes to `session.prompt` instead (`rpc-mode.ts:1838-1850`): the model gets the literal `/jobs kill bg_1` as a message, and the ack reports `agentInvoked`, which the page sees as `accepted`, not `explained`. `handleJobsKillCommand` (`builtin-session.ts:80`) calls `session.cancelAsyncJob(id)` with the same id that `details.async.jobId` and `details.jobs[].id` carry (`manager.register` returns it: `bash.ts:848`; `getJob(id)`, `agent-session.ts:2990`), and answers `Cancelled background job <id>.`, `Cancelled N background job(s).`, `No running background job with id "<id>".`, `No running background jobs to cancel.`, `Could not cancel background job <id>.` or `Async background jobs are unavailable in this session.`. The id is echoed after `sanitizeText` and truncated to 60 characters (`builtin-session.ts:107`). `kill` uses the owner-scoped `getAsyncJobSnapshot` (`builtin-session.ts:90`; `agent-session.ts:2891-2897`), so `kill all` reaches the jobs OMP owns for this session, not subagent-owned jobs that `/jobs` itself lists (`getAsyncJobTree`).
- Chat already sends any text, builtins included, as `omp:chat-prompt` (a `prompt` with `streamingBehavior: steer`, so it also works during a turn); the page gets `accepted | explained | refused | unconfirmed` per request id. The builtin's `command_output` reaches the model as an ephemeral transcript row (`kind: "command_output"`, id `event:<seq>`). The host's `/context` capture already correlates a reply by its text (`session.ts:2380-2384`).
- A dropped `tool_execution_update` frame is never made up: `droppedFrameAffectsState("tool_execution_update")` is `false` (`frame-notices.ts:56-63`) and job frames are not in the session file. The terminal bash frame carries the full output and is the likeliest to be too large for the connection.
- `ChatClient.sendPrompt` (`#sendPrompt`) cancels a deferred `/clear` and arms the identity check (`session.ts:974-975`), whatever the text.
- `proc://` grammar (`proc-protocol.ts:38`): `proc://`, `proc://<id>`, `proc://<id>/kill` (a write that cancels), `proc://<id>/mode` (services). It names jobs, running agents and services alike.

## Proposed Design

### Job knowledge: `src/chat/background-jobs.ts`

A pure module replaces `readBackgroundJobs`; `background-wait.ts` keeps `backgroundWaitOf` and reads from it.

- `scanJobs(entries, frames, gone)` returns one `JobRecord { id, type, label, state, startedAt, endedAt, durationMs, callId, live, gone }` per job id, from four sources: start results (`details.async`, label from the call's `i` or `command`, `startedAt` the result's timestamp), polls and cancel results (`details.jobs[]`, `details.cancelled[]`, `details.proc.cancelled[]`), `async-result` deliveries, and the live **job frames**. A state is monotonic within one job: `running` never overrides `completed`, `failed` or `cancelled`.
- **One record per latest start.** Ids restart per OMP process, so the **latest start of an id wins**: an earlier job with the same id is replaced, never merged, and a poll or delivery attaches to the latest earlier start of its id in transcript order. A record is `live` when this OMP process reported it through a frame. A start result or frame whose `callId` differs from the record's **replaces that record, including a record with no `callId`** (a poll or delivery of an earlier process's id with no start in the loaded window). Only a live running job gets a Cancel (per job); a job known only from the transcript (an older process, or the loaded window) is listed without Cancel and is never offered as a target of `/jobs kill <id>`, which would reach a different job of the same id.
- **Job frames.** `ChatModel.jobFrames` (a `Map<jobId, { state, type, callId, at }>`, the newest 200) is fed by `tool_execution_update` frames whose `partialResult.details.async` has a string `jobId` and a known `state` and `type`, **and by the start result at `tool_execution_end`**, so a job is `live` from its start even when no update frame ever arrives. `withJobFrame` keeps the same Map, and the same `at`, while the state and call are unchanged, so a stream of `running` frames does not change identity. The map rides in the snapshot as an optional array (like `asyncPaused`), so a page attached later sees it; `session.ts` is not touched: a new OMP process is a new model, whose map starts empty, and the reducer's handling of the frame as tool progress is unchanged. A job that only a frame names (started before the loaded window) is listed with its id as label.
- **Task frames are call-level evidence.** A `task` frame states the call, not a spawn, and `jobId` names the primary spawn only. The primary is `live` from its start result or first `running` frame (Cancel is offered); a `running` frame ends nothing. An aggregate terminal frame (`completed` or `failed`) settles the primary. OMP never sends `cancelled` for a task. A primary that ended while siblings still run keeps showing running until a Cancel is answered `No running background job…`, which the `gone` tombstone retires; the end of the other task jobs comes from deliveries and polls. `incomplete` is true while a task job is listed.
- **`gone` tombstone.** When OMP answers `No running background job with id "<id>"`, the page records `id -> callId` of the record that was cancelled in `JobsUi`; `scanJobs` turns exactly that job (id and call) from `running` into `completed` with `gone: true` (shown as `ended`, as nothing says how it ended). A later job with the same id has another call and is not touched. This also clears a row whose end frame was dropped.
- `jobsViewOf(model, gone)` returns `{ shown, pending, running, byId, incomplete }`. `pending` is OMP's flag (`asyncPaused` or `state.hasPendingAsyncWork`); it is owner-scoped and can include queued deliveries, so it is worded as *pending*, not *running*. The row is **shown** while the conversation is live and either `pending` or the session is not settled and the transcript shows a running job; once OMP reports nothing pending and the session is settled, a transcript job that never got an end (cancelled outside the transcript) is not shown. The page keeps the previous view object when `sameJobsView` says nothing a consumer draws changed.
- **Cost.** The transcript scan is cached per `entries` array (a `WeakMap`), so a stream of bash preview frames does not rescan it; only the frame merge runs per model change.
- **Incomplete list, said honestly.** The list is a lower bound and an upper bound at once (jobs older than the loaded transcript, task spawns beyond the first of a call, cancels the transcript never saw). `incomplete` is true when older history is not loaded or a task job is listed; the collapsed summary then reads `at least N background jobs`. The expanded list ends with one line: `Listed from this chat's transcript and OMP's live events; a job it never showed may be missing. Cancel all stops the jobs OMP owns for this session.` (`JOBS_NOTE`; it is also the tooltip). When OMP reports pending work and no job can be named, the summary is `Background work is pending · no job is named in this chat`, with no Cancel per job and Cancel all kept. A **dropped** job frame is unrecoverable (Risks); the row can then show a finished job as running until the `gone` tombstone or an end the transcript carries clears it.

### The Jobs row

`HudDock` renders `TodoHud`, `RunningAgents` and a new `JobsHud` in one stack under one height cap. `hudSectionLines(height, visible, expanded)` is called with the Jobs row counted, **including a row forced visible by a focus, a pending request or an outcome** when nothing is pending; the row's own fixed extra lines (the note, a feedback line) are subtracted from its content rows by `jobsWindow(rows, lines, extra)` in `src/chat/jobs-hud.ts`, which keeps at least one job and a `+N more` line that opens nothing. The note and the feedback are each **one ellipsised line** (full text as the tooltip), so no line wraps and the fixed line height the cap assumes holds. The note is dropped only when it does not fit (when the lines are fewer than the rows shown, plus the `+N more` line, plus the feedback or missing line, plus one); a job is never dropped for it. The feedback line is reserved only while feedback exists. No scroll region.

- Collapsed (`HudHeader`, icon `server-process`): `2 background jobs · bash: npm run dev · 3m` (count, the newest job's type and label, its age, ticking while shown). No second status chip.
- Expanded: one line per running job, newest first: type badge, label, age, **Cancel** (only for a live running job; the other lines have none). Under the list: a feedback line (`role="status"`, with Dismiss), then the note. Header action: **Cancel all**.
- **Cancel** sends `/jobs kill <id>` and Cancel all sends `/jobs kill all` through `ChatClient.sendPrompt`. **Cancel all is a two-step inline confirm**: the first click turns the button into `Confirm cancel all` (Escape or leaving the button disarms it), the second sends; its title states that it stops the jobs OMP owns for this session. The id is sent only if it is a job id (`^[A-Za-z0-9_][A-Za-z0-9_.:-]{0,127}$`) and not `all`; otherwise nothing is sent. While a request is open its button shows `Cancelling…` and every Cancel is disabled.
- **Guard.** Cancel is enabled only when OMP's command list for the session contains `jobs` with a `kill` subcommand (`jobsCancelBlocked`) and the conversation is writable; otherwise the buttons are disabled with the reason as their title (`OMP did not list a /jobs kill command for this session.`). Without that the text would reach the model as a message (Current State). A guarded send can still reach the model (a hook rewriting the text, a list that is stale): an ack that is not `explained` is reported as `Not cancelled: OMP took /jobs kill as a message for the model, not as a command.`, never as a cancel; the text may then already have reached the model, which the row does not hide.
- **Outcome.** The page reads the reply from the model: it records the set of ephemeral ids present before the send, awaits the result, then (for `explained`) takes the first `command_output` ephemeral item **not in that set whose text is OMP's answer to this very command** (`isJobsKillReply`: the sentence names the id, anchored (a `.` or `"` follows it, unless the id is longer than 50 characters, when the 50-character prefix is compared, within OMP's 60-character echo), or is one of the fixed `all` sentences or the `unavailable` sentence), waiting up to 2 s for it (the frame is posted before the result, so the wait is a safeguard). Correlation is by sentence and by id set, never by `seq`, so another command's output, another page's cancel or a re-baselined `seq` is not read as this reply. `classifyJobsReply` maps OMP's sentences to `cancelled`, `gone` (`OMP has no running job with this id`; its wording does not claim the job finished), `failed` (`Could not cancel…`, unavailable) or `unknown` (shown verbatim, never as success); no matching reply is `silent`. `refused` and `unconfirmed` show Desk's fixed sentences (`Not cancelled: <reason>`, `OMP did not confirm the cancel; the job may still be running.`). A refusal or failure stays until dismissed or the next action; `cancelled` and `gone` clear after 6 s. A successful cancel removes the job from the list when its `cancelled` job frame arrives; the feedback line does not claim more than OMP said. A `gone` answer for a job id records the tombstone above.
- **Same path as a typed message.** A Cancel send is an ordinary `sendPrompt`, so it also cancels a pending deferred `/clear` and arms the identity check, as typing a message would; this is documented in `jobs-ui.ts`, not special-cased.
- **Transcript.** The reply stays in the transcript through the existing command-output path (`Command output: Cancelled background job bg_1.`): one short row per user action, a useful record, not noisy, and suppressing it would need a new correlation the protocol lacks.
- State shared by the row, the working row, the cards and the links lives in `JobsUi` (`src/webview/lib/jobs-ui.ts`, one per page, built beside `ChatClient`, exposed through a React context with the view and the cancel guard): the open target, the last outcome, the `gone` tombstones and a **focus request** `{ id | null, nonce }`.

### The working row

`WorkingStatus` renders the waiting text as a `<button class="omp-working-status-text omp-working-status-link">` when it is a background wait, with the same visible text. Click calls `jobsUi.focus(id)` (the job's id when exactly one is named, else none). The live region is **only** the `.omp-sr-only[role=status]` span that carries the announcement; the button sits outside it, so a named control is not re-announced inside an atomic region. The permanent final row keeps its height.

### Tool-card chip and Cancel

For a `bash`, `eval` or `task` result whose `details.async` names a job, the head shows a chip from the job record: `running · 3m` (blue, ticking), `done · 3m`, `failed · 3m`, `cancelled`, `ended` (`omp-job-chip--<state>`, with `data-job-id` and `data-job-state`). A job that is `running` with no end evidence and nothing pending (`!view.shown`) shows **no chip**, so an old card never ticks `running · 4320m`. While the job runs and is live, the card carries a **Cancel** icon button as a sibling of the head (a head is itself a button, so nothing nests), absolutely placed at the head's right edge, named `Cancel background job <id>`; it shares `JobsUi` pending state and the cancel guard with the row, and is absent when Cancel is not offered for that job. The head reserves the padding for the Cancel in both variants (a `button` and the `div` head of a card with nothing to expand). The chip text and button are absent when the page has no `JobsUi` (the detail tabs).

### `proc://` links

`src/shared/proc-links.ts` parses `proc://`, `proc://<id>`, `proc://<id>/kill` and `proc://<id>/mode` (id by the job-id pattern above). A link **never acts**: it calls `jobsUi.focus(id)`, which expands the Jobs row (forcing it visible, even with nothing pending, until the user collapses it), scrolls to and highlights the job's line; a job that is not running is shown as a dimmed line with its last known state and time (`bg_3 · bash · done · 2m`). An id the chat's list does not hold says `no such job in this chat's list (an agent is in the Agents row)`, since `proc://<agent id>` also names a running agent. `proc://<id>/kill` is parsed so it reveals the job and nothing more: a model-written `[Cancel](proc://x/kill)` is a link that shows the row, never an action, and Cancel stays a button the user presses. The page resolves it itself, so unlike `agent://` there is no host proof. Applied in: a read or edit card's target (`ToolTargetText`), the wait card's job names (head target and `JobRows`), Markdown inline code spans, bare text and `[label](proc://…)` links, following the rules of `internal-links` (the existing `parseInternalLink` keeps rejecting `proc://`).

## Alternatives

- **Parse `/jobs` output for an authoritative list.** Rejected: its format is a human report (`[id] type (status) — duration`, fenced) with no stability promise, it would add a transcript row per refresh, and OMP's UI itself works from events. The honest-lower-bound wording stays.
- **A local acknowledgement instead of job frames** (mark a job cancelled when OMP's reply says so). Rejected as the only mechanism: it misses cancels by the model or by a typed `/jobs kill`, and it cannot say how a job ended. The reply text is used for feedback, and for the `gone` tombstone only.
- **A dedicated `omp:chat-jobs-cancel` message and host capture of the reply** (like `/context`). Rejected: a new message, parser, bridge allow-list entry and a host request registry for one sentence; matching OMP's expected sentence for the id among the new ephemeral rows is enough and keeps the reply in the transcript.
- **Hide the `command_output` row.** Rejected, see Transcript.
- **Nested buttons in the card head, or a Cancel only in the expanded body.** Rejected: invalid markup; the body is closed for most cards.
- **A new detail tab for jobs.** Not asked for; the row is where TODO and Agents already live.
- **Key records by id only.** Rejected: ids restart per OMP process, which would show a ghost job with a Cancel that kills an unrelated job.

## Risks and Open Questions

- The list can miss a job or keep one OMP has already dropped; every surface says so (summary, note, tooltip) and Cancel all is defined by OMP, not by the list, and reaches only what OMP owns for this session (not subagent-owned jobs).
- A job frame sent while no page is attached is lost to the page but not to the host's model, which the snapshot restores; a host restart loses frames, and a job cancelled meanwhile shows as running until OMP reports nothing pending. A frame **dropped** by OMP (too large for the connection, the terminal bash frame being the likeliest) is never made up from the session file, so its job can stay `running` for as long as another job keeps `pending` true; a Cancel that OMP answers with `No running background job` retires it (tombstone), and nothing else does.
- `pending` can be true with nothing running (a queued delivery); Cancel all then answers `No running background jobs to cancel.`
- `kill <id>` for a task job cancels the subagent job (`cancelAsyncJob`); the Agents row follows from OMP's own events. A primary that ended while its siblings run stays running in the list until a Cancel answers `No running background job` (tombstone), because the frame is per call.
- OMP could change the reply sentences; an unrecognised reply is shown verbatim as `unknown`, never as success, and the guard on `/jobs` with a `kill` subcommand keeps the command from reaching the model on an OMP that lacks it (ADR-0011: no version gate).
- A late job frame still creates an `ActiveTool` in the reducer (unchanged); it is cleared by the existing `agent_end`/settle rules.

## Amendment 2026-10-19: agents are not jobs in the row

A background `task` is an agent, which the Agents row already lists, so the Jobs row showed it twice. `JobsView.running` now holds `bash` and `eval` jobs only; task jobs stay in `byId` for their cards' chips. `agentsRunning` says an agent runs: pending work with no job named draws no Jobs row then (OMP's flag may be the agent's alone), and Cancel all (`/jobs kill all`, which also stops agents) is not offered. `incomplete` no longer counts a running task, since the jobs a task starts are agents too; it is true only while older history is not loaded. This supersedes the task parts of the incomplete-list rule above.

## Amendment 2026-10-19 (later): no row while any call executes

`agentsRunning` was too narrow: the user saw the yellow warning while a Python `eval` call of the current turn was still running (its job id not yet known) and the two jobs it awaited had settled. The rule is now: pending work that no job names draws **no Jobs row** while anything in the transcript is executing, that is, any tool call of the current turn that has started and not ended (`ChatModel.activeTools`: bash, eval, task, any other) or an agent job (`JobsView.agentsRunning`); `JobsView.toolsRunning` carries the first. The yellow `Background work is pending · no job is named in this chat` warning remains only when OMP reports pending work, no job is named and nothing executes. A row with a named running job is unchanged. Cancel all stays hidden exactly when an agent runs, as before (`agentsRunning`), and is not tied to `toolsRunning`. `JobsSource` gains `activeTools` (only its size is read), and the page's view memo depends on whether any call is running. This supersedes the "Background work is pending … Cancel all kept" sentence of the incomplete-list rule and the `agentsRunning` sentence of the previous amendment.
