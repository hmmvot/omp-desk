# Windows desktop notifications for sessions waiting for the user

## Problem

The extension currently raises an in-VS Code information message for unseen Chat turn activity. The user needs a Windows desktop toast when a top-level agent finishes and waits for a prompt, or blocks on a question/approval mid-turn, with a click returning to that session.

## Goals and Non-goals

- Windows OS toasts, not a VS Code notification fallback; `omp.desktopNotifications` defaults to true and can disable them.
- Notify a top-level turn becoming idle, including a turn-stopping error, but not a user abort, subagent completion, intermediate tool cycle or automatic continuation.
- Notify each structured user-wait event once per session. Record suppressed events too: looking away later must not resurrect them.
- Suppress only when the window is focused and that session's visible editor is active.
- Title is the session title. Body is the folder name plus `Finished — waiting for your input` or `Asks: <question first line>`. Forward no raw error, tool arguments/options/prefill, answers, credentials or full filesystem paths.
- Clicking uses protocol activation and reveals that session without starting, stopping, switching mode or submitting work.
- No new native dependency or OMP/private API change. The maintainer withholds commit and primary installation for this package; they are not claimed as performed. Non-Windows delivery is a logged no-op.
- No GUI control without the maintainer's explicit relayed permission. Reading Windows notification history is permitted verification, separate from GUI control.

## State before this package

`src/host/notifications.ts` contains a transition ledger and injected VS Code information-message delivery. `src/extension.ts` projects its host-owned RPC model and records snapshot baselines. Pending RPC select/confirm/input/editor dialogs have stable request IDs. Existing suppression only tests visible plus focused, not the active editor. No URI handler exists.

Native uses authenticated `nativeState` polling every 750ms. Its current schema has settled/session/title facts but no causal turn or question observations. Installed OMP is 18.4.4; its actual package manifest, public extension types and lifecycle paths were inspected. Public `agent_end.willContinue` identifies automatic continuations. Some terminal errors skip `session_stop`, and registering that hook changes settle behavior: this package must not register it.

On this machine `Get-StartApps` identifies registered `Microsoft.VisualStudioCode`. A short-lived Windows PowerShell WinRT probe raised a real protocol toast; `ToastNotificationManager.History.GetHistory('Microsoft.VisualStudioCode')` returned its exact tag/group/XML. The probe removed only its own entry. This validates the delivery identity, not finished product behavior. The UTF-8-without-BOM probe file exposed Windows PowerShell's legacy file decoding; production will use UTF-16LE encoded static script and explicit UTF-8 stdin rather than script-file text decoding.

## Proposed Design

### Observed events and suppression

Keep the existing host-side ledger, replacing the old notification API/action vocabulary completely. Key it by the conversation identity used by SessionIndex. Chat completion requires `settled` false→true, no pending UI request, and a fresh non-aborted prompt result or assistant outcome. Clear both fresh fields at `agent_start` and snapshots. Installed RPC emits a prompt result once per accepted ticket, not for each autonomous continuation; its frame writer also removes already-streamed messages from `agent_end`. Therefore record the enum from live assistant `message_end`; an unstreamed final assistant in `agent_end` can override it, including the exception-path abort veto. Never infer freshness from historical transcript rows. Defer a settle with neither fresh signal; intermediate `agent_end` is not completion. RPC select/confirm/input/editor request-ID transitions earn one wait toast, carrying only their display title's first line. Snapshot/reconnect baselines earn no historical completion. Disabled or visibly watched events are consumed, not queued for later notification.

The [Sessions startup and work-status design](2026-10-04-sessions-startup-and-work-status.md#shared-activity-truth) amends completion gating: retain a fresh, non-aborted causal candidate across asynchronous pause, but notify only after authoritative SDK idle with all jobs and result deliveries drained. A new start or abort cancels it; readback alone and historical baselines never create one. Ask notifications remain independent and immediate.

For native, use a fresh public `agent_end` as a provisional completion candidate, including `willContinue:true` under the amended Sessions rule, never `session_stop`. Record only the live assistant `message_end` outcome enum since the current `agent_start`; full `agent_end.messages` may veto an exception-path abort or confirm that fresh outcome, but cannot establish freshness. Consume aborted silently. Publish once only after a later authenticated SDK observation reports idle with all jobs and deliveries drained; a new `agent_start` or abort cancels the candidate. Hooks are adapter-closure state, not module-global, gated by main-agent TUI context and stamped with its current session ID. Apply entries only to the row matching the observed native session; silently baseline the destination after a native switch. A cancelled self-continuation that never starts is indistinguishable from a drained asynchronous pause; the canonical design documents that limit.

Correlate built-in ask start/end and tool approval requested/resolved by tool-call ID and wait kind, only inside an active main run. Notify only waits still pending across a poll boundary, after consuming all entries in the response; synchronously rejected asks cannot notify. A new run or non-continuing end clears stale waits, so an aborted pending ask cannot notify or obstruct the next completion. Carry only sanitized first-line `questions[0].question` or fixed approval wording, not other tool inputs, options or approval details. Observation can lag by roughly 750ms; a rich ask dialog can fail after its start.

The adapter has a fixed 32-entry monotonic ring. Each stamped identity/tool-call ID is at most 128 UTF-16 units; questions are at most 200 Unicode code points. A new `nativeActivity` method returns its epoch, oldest sequence, entries and existing native-state facts computed in the same synchronous observation. A first/new-epoch read is a silent baseline; a replay gap drops pending candidates and never notifies historical events. The bounded response remains well below the 256KiB frame ceiling; the ring is not lossless across a gap. Keep protocol version 3 and every existing method's request/result shape unchanged. Only positive `activity: true` capability recorded by this extension when launching the new module permits this method: never probe older staged runtimes, whose missing capability means no native toasts but unchanged controls. This amends [ADR-0006](../decisions/0006-host-generated-key-peer-verified-pipe.md).

**Native limits:** only the built-in ask tool and tool approval gate in the main TUI session are observable waits. Plan-mode plan approval (after an abort), dialogs from extension tools/commands/hooks, generic `ctx.ui.select/confirm/input/editor/custom`, user-initiated slash-command dialogs and waits starting after settle are unobservable. Do not interpose on SDK objects or parse PTY text. Unknown/unavailable outcome cannot prove a non-aborted completion.

### Windows delivery and activation

A focused notification module builds XML-escaped display text/attributes. Strip XML-invalid controls, C1 and bidi controls, repair lone surrogates, and bound the first line by Unicode code point (title 120/body 200). Untitled sessions use fixed fallback text; tag/group are bounded ASCII. A constant PowerShell script is encoded UTF-16LE into `-EncodedCommand`; event data travels through raw stdin decoded with strict UTF-8, never interpolated into executable source or shell arguments. Use the system PowerShell path, `-NoProfile -NonInteractive`, `windowsHide`, `shell:false`, discarded stdout/stderr, closed stdin and a 10 s kill deadline. Submit with the proved `Microsoft.VisualStudioCode` AUMID only for Stable's `vscode` scheme; unproved product variants are a fixed-log no-op. Failures produce a fixed log, never a VS Code notification fallback or sensitive diagnostic.

At toast time, construct the owning window's `vscode://hmmvot.omp-desk/reveal?session=<encoded identity>` and pass it through `vscode.env.asExternalUri`. Serialize its unmodified result with `toString(true)` before XML attribute escaping: the default serializer aggressively encodes query separators, hiding the session and VS Code-added routing parameters from ordinary protocol URL query consumers. Do not cache or rebuild the external URI. Synchronously register `UriHandler` at activation and add `onUri`; validate path/identity while ignoring VS Code-added query parameters. Public routing sends URIs to the topmost window and cannot guarantee the original window or a handle-less webview. The maintainer accepted this limit: reveal the exact retained indexed panel with `panel.reveal(panel.viewColumn, false)`; otherwise select/reveal the indexed Sessions row only, or write a fixed log if unavailable. Revalidate row presence after asynchronous tree lookup. Surviving tree rows and folders retain their element instances across title, state and selection changes; only a completed current revision updates presentation and membership. Never open, attach, resume, launch or mutate a session as fallback.

## Alternatives

- VS Code information messages: the path being replaced, not desktop notifications.
- Native notifier module: adds an unnecessary native dependency and packaging burden.
- Interpolated PowerShell text or command-line event content: unsafe and exposes content in process arguments.
- Dedicated AUMID installer/shortcut: unnecessary on the verified machine; registered VS Code identity already works.
- Native PTY text parsing/UI-method monkey patching: unreliable or intrusive; use public causally identified events and disclose unsupported generic waits.

## Risks and Open Questions

- OS notification policy/focus assist can prevent presentation; successful API submission is not proof, so verify the real tagged notification history.
- Exact original-window/profile foregrounding and handle-less surviving-tab activation are not guaranteed by the public API. The maintainer accepted this disclosed routing limit and its non-mutating Sessions-row fallback; permitted isolated-window observation remains distinct from a multi-profile guarantee.
- Native completion follows the amended Sessions design's fresh provisional-end plus authenticated SDK idle/all-work-drained rule; no stop hook is registered. A cancelled self-continuation that never starts cannot be distinguished.
- Previous digest-staged native modules lack the new capability: retain their controls, never probe the new method or infer abort/error from busy/idle.
- Display question/title text persists in Windows notification history and can appear on the lock screen, subject to Windows settings. Hidden payloads/capabilities are never forwarded.
- EDR/ASR policy may reject PowerShell encoded commands; do not bypass OS policy or silently use another notification surface.
