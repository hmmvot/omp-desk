# Immediate Sessions rows and truthful work status

## Problem

The user observes Sessions rows about ten seconds after window startup and an initial `Cannot resolve tree item` error from automatic active-session reveal. Rows also fail to distinguish a paused main agent with background work from a genuinely idle session; a finish toast must not claim completion while subagents/jobs are still active.

## Goals and Non-goals

- Publish registered folders and indexed rows from the persisted profile catalog immediately after catalog hydration, without waiting for process, broker, ownership, native control or session-file title reads. Fill live facts independently per row; unresolved observations say Checking.
- Show icon plus description/tooltip for Working, Waiting for subagents, Needs your answer, Waiting for you, and existing stopped/not-running states. A structured ask outranks work; a question-mark heuristic is not an actionable ask.
- A finish toast is earned only when the main agent has settled and no background work remains. Ask/approval notifications remain immediate, with existing replay/dedup/visibility suppression.
- Preserve catalog/index identity and all action/claim/shutdown/exact-writer admission gates. Display observations never authorize lifecycle actions.
- No OMP/private API changes, control of the maintainer's window, primary installation or commit. Only the expressly permitted isolated profile/window may be recreated and exercised; leave it running.

## Current State

The profile catalog and SessionIndex hydrate synchronously during construction, before `activate` registers `SessionTreeProvider`. Preserve the existing legacy-import → catalog-adoption → asynchronous-restore order and command readiness barrier. The provider's initial projection nevertheless serially awaits each session-file header and `launcherOwnershipFacts`, which can perform process/broker probes, before returning any folders/rows. Provider-side construction is not VS Code's root/parent publication: automatic reveal can race a root refresh or another fetch of the same parent, canceling the fetch that reveal needs.

Chat already receives public `agent_end.isTerminal`, `yielded` and `awaitingAsyncWork` metadata plus the same subagent roster/progress that feeds the AGENTS HUD. The reducer had discarded the asynchronous pause flags. OMP explicitly defines `isTerminal:false` as a scheduling pause before async delivery resumes the main session, not completion. Task roster membership alone does not cover background bash/eval or pending delivery.

Native's authenticated `nativeActivity` journal already has main-TUI ask/approval and causal completion events. Its synchronous SDK state computes true settled from `isIdle`, pending messages and the async-job snapshot's running/queued/delivering/pending-delivery fields. `nativeState` is TUI-only; it must not be broadened into an RPC endpoint. The journal currently exposes only aggregate settled, so main-busy versus background-only work cannot be distinguished.

## Proposed Design

### Catalog-first tree and reveal

Keep synchronous persisted-catalog hydration and the existing complete catalog/import barrier unchanged. The first tree projection uses only current membership, persisted title/ordinal, and synchronous local runtime/activity facts. The source separates pure local facts from asynchronous ownership enrichment. No process probe or session-header read is awaited or invoked on that first projection path.

After publishing membership, schedule bounded independent row enrichments. Keep folder/row instances and a per-tab observation cache across root rebuilds. Each row has one in-flight ownership observation and at most one dirty rerun; its identity includes session file, draft/owner identity, generation, host PID/transport and local runtime slot. Removed/rebound rows cannot receive stale results. Local running/launching/stopping/activity facts are always merged fresh. Activity updates do not invalidate ownership; focus, visibility, catalog and lifecycle changes can mark it stale while retaining the last observation. Never-observed rows show Checking. Header enrichment has a separate file/title identity.

Refresh roots only for membership/folder changes, folders only for ordering-class changes, and individual rows for activity/enrichment. Automatic reveal waits until both roots and the target folder's children have actually been served at the current projection revision, not merely constructed by `itemFor`. Root/target-folder refreshes rearm the request. Coalesce to the latest active tab, honor saved collapsed folders and visibility, and never introduce timer retries or warning suppression.

The manifest also explicitly activates on `onView:omp.sessions`, retaining existing activation events. The Chat UI owner makes that manifest edit alongside its presentation setting.

### Shared activity truth

The extension-integration owner owns the expressly released model/RPC/activity slice; the Chat UI owner retains the display-turn completion-clock and footer contract. Public `get_state.hasPendingAsyncWork` and `get_state.isSettled` are authoritative at attach/resync and during an asynchronous pause. Main working and structured pending requests remain separate. A nonterminal end cannot complete a display turn or expose completed prompt status while work remains. Task roster membership covers presentation but not all background bash/eval or pending delivery; authoritative idle overrides a stale roster. Read back on a paused subagent's terminal transition and with a bounded cadence only when paused with an empty roster, so no-wake drains are observable without polling ordinary idle sessions.

Sessions derives structured ask → Working → Waiting for subagents → true idle. Preserve existing `question`/`waiting` action-state identifiers and add background/checking states with explicit action, icon, label, tooltip and sort behavior. Checking is unresolved ownership rather than permission to forget, delete or invoke live-only actions. Unread reply information stays supplementary and never overrides work; a trailing question mark alone is not Needs your answer. Unsettled activity with unavailable work detail shows Running rather than a guessed Waiting for you.

The notification ledger requires true settle **and** no main/background work before consuming a fresh finish candidate. Retain a fresh, non-aborted causal main-completion candidate across asynchronous pause; authoritative public readback proving idle earns exactly one finish toast even without a wake event or final `agent_end`. New main work, wake/continuation and user abort cancel that held candidate; historical/reattach baselines never create one. Requests remain independent and immediate. Sample visibility/settings suppression at true idle, preserve suppression until a late prompt result arrives, and retain existing once-only rules.

For native, use an explicit recorded capability to request the additive `nativeActivity({work:true})` response. Only that request receives nullable `work:{working,backgroundWork}`, computed from the same synchronous public-SDK snapshot as settled. Original kind-only requests retain their original four-key response; omitted `work` stays omitted during parsing/signing. Do not change control version, `nativeState`'s original eight-key contract or its TUI mode gate. Older staged hosts have explicitly unavailable detail. Expose the native ledger's pending structured request, including a consumed-but-still-pending wait, rather than maintaining a second ask reducer. The installed native hook collapses async pause and ordinary continuation into `willContinue:true`, dropping `yielded`/`awaitingAsyncWork`. The maintainer approved retaining a fresh non-aborted end as provisional, notifying once only after authenticated SDK idle and all jobs/deliveries drain; a new `agent_start` or abort cancels it. Observe once in the native ledger and deliver via the notifier without a second ledger observation.

### Exact Terminal limits

A current native journal with supported SDK idle/job APIs can distinguish the main turn from running async jobs or pending result delivery. The row uses Waiting for subagents as the user-facing category for subagents, tasks and other background jobs; it does not invent child names/counts. Older staged journals or unavailable SDK observations cannot distinguish these: a proven settled session can show Waiting for you; otherwise it shows Running with unavailable-detail wording, not a guessed main Working or finish toast.

Structured native asks are observable only for built-in ask and tool approval in the main TUI context. Reattach, new epoch and replay gaps baseline silently for completions, but a dialog that opened after the last turn boundary and never closed in the host's bounded journal is recovered as pending state for the verified row (a host-reported settled session recovers nothing). A recovered ask shows Needs your answer over Working and is announced once per watch, subject to the usual suppression; this covers a window reload or control reconnect while the TUI is already waiting. A dialog that has already scrolled out of the 32-entry ring, plus generic extension/custom dialogs, plan approval, slash-command UI and waits after settle remain unobservable. Do not parse PTY text or interpose on SDK UI objects.

The native hook cannot distinguish a cancelled self-continuation that never starts from an asynchronous pause that drains without a wake. The provisional-completion rule deliberately uses the later authenticated SDK idle boundary, not an inferred async-only event. Freshness still requires a newly observed assistant end; state readback or historical messages alone never earn a finish.

## Alternatives

- Await every live probe before drawing: rejected; display membership does not require ownership evidence.
- Treat `agent_end` or the subagent roster alone as completion: rejected; public nonterminal metadata and async-delivery semantics explicitly contradict it.
- Change native shutdown/state mode gates or add an OMP-private RPC API: rejected; existing public event/SDK observations suffice.
- Retry startup reveal on a timer or suppress its error: rejected; root-publication ordering must be correct.

## Presentation amendment (2026-10-08)

The activity precedence and notification-completion gates above are unchanged. True idle and fresh non-running sessions now say Idle, not Waiting for you; unread replies say Unread reply and structured questions retain Needs your answer. Saved stopped rows still say Stopped. Session and folder tooltips contain at most three plain lines (name, state, locale-relative activity), plus one actionable instruction where needed. Technical identity, paths and activity facts move to the row's Copy Diagnostics context-menu action. User-facing stopped-session details say Resume to continue, matching Chat's action. Pin, Unpin, Add Folder and successful Stop rely on their visible state update rather than an additional success notification.

The persistent extension status bar is removed rather than repaired to follow editor focus: its model/thinking readback duplicated Chat's authoritative editor-local footer, and its Terminal variant only repeated the active mode. This eliminates both the first-live-tab mismatch and permanent no-live-session text without adding another model/status surface. Terminal keeps OMP's native model information. Host-control commands and their real error messages remain available independently.
