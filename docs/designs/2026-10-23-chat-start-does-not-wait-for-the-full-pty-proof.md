# A Chat start does not wait for the full PTY runtime proof it never uses

## Problem

A session start (a restored draft, `kind: resume`) right after a window reload (the reload that follows an extension update) took 109 s until Chat was live. The start-timeline line of the OMP Desk log (`window timing: … start timeline`) split it as: 21.7 s in the lap `runtime proof` (Desk waiting, before anything was started), 17.7 s in the phase `runtime check` (the Bun runtime check and the access read of the broker's runtime), then `omp spawned` at 41.8 s, and 67 s more inside OMP until `omp ready` (OMP's own part is reported separately and is not changed here). The ADR-0068 settings barrier, which sits in the same lap, was free: the window's log has no `settings: the move … is still running` warning.

The 21.7 s are the wait of `LocalLauncher` on `brokerClient()`, which is `PtyReadinessGate.client()`, which awaits the **full** PTY runtime proof (`PtyBrokerClient.ready()`: staging, access pass and the console-child self-check that terminals need). On that machine the self-check outlives its 15 s deadline after every extension update: the log shows `PTY runtime admitted unproven after 36.0–77.6 s … did not finish within the self-check deadline of 15 s` on each of the three reloads after an update seen in the retained logs (30.4–88.6 s over all retained logs; the repeated check then takes 12.1–33.4 s). Every window that reloads runs it at the same time. A start made while it runs waits for the remainder.

[ADR-0074](../decisions/0074-run-chat-brokers-on-the-sessions-own-bun-runtime-with-code-exe-as-fallback.md) states the intent: "the full PTY self-check … is no longer a prerequisite for starting a Chat on Bun, so a Chat's first start does not wait for it when the pipe-only proof is cached". The Bun plan (`PtyBrokerClient.chooseChatRuntime`) stages and proves its own tree (`ensurePtyRuntime({ pipeOnly: true })`), and the `Code.exe` fallback asks for the full proof itself (`startBrokerOn` without a Bun plan awaits `this.ready()`). Only the launcher's up-front `await brokerClient()` (added on 2026-10-13, before ADR-0074) still makes every launch, a Chat included, wait for the proof of a different runtime and a different capability. The ADR's promise is conditional ("when the pipe-only proof is cached"); the start after an update is outside it, which is why that start is what this design addresses.

## Goals and Non-goals

- Goals: a Chat (`rpc`) start takes no wait for the full PTY runtime proof; the proof is still started in the background as today; the `Code.exe` fallback of a Chat, and every terminal, folder shell and Stats launch, wait for the proof they need; the first-launch settings-move barrier (ADR-0068) is kept for every launch.
- Non-goals: making the pipe-only proof or the access read faster or prewarmed (the 17.7 s `runtime check` of the same start; a separate design), serialising the self-check across windows, the OMP-side startup (`omp ready`) and the helper `omp` processes a reload starts (`models --json`, provider usage), the proof's 15 s deadline.

## Current State

`src/runtime/local-launcher.ts`: one `await this.#deps.brokerClient()` for every launch kind, then `timeline.lap("runtime proof")`; `null` means "The extension-owned PTY broker is not available in this build". `src/extension.ts` wires it to `brokerClient()`: `legacySettingsSettled(s)` (ADR-0068, bounded) and then `PtyReadinessGate.client()`. The gate also has `attachClient()` (`PtyBrokerClient.attachIdentity()`: this build's tree digest and runtime version, nothing staged, no proof), which every re-adoption uses.

`PtyBrokerClient.launchRpc` → `launchSlot` → `startBroker` → `startBrokerOn`: with a Bun plan the runtime is `plan.runtime` (its own pipe-only proof and access read, run together with the trust read), then `verifyPtyRuntime`; without one, `startBrokerOn(null)` awaits `this.ready()` and refuses with the readiness reason when the runtime is not ready. So every broker start is already gated inside the client by the proof of the runtime it starts on (ADR-0032); the launcher's wait is a second, earlier gate on the other runtime. A new launch always mints a new slot, so `launchSlot`'s recorded-slot branch (the other `this.ready()` call) is not reached by it.

## Proposed Design

A gate method and a launcher dependency, plus one rule in the Bun plan's pipe-only check (below, "What keeps an overlap from costing the Bun runtime"):

- `PtyReadinessGate.chatLaunchClient()` (`src/host/pty-readiness.ts`) = `(await attachClient()) ?? (await client())`, documented with its invariant: every broker start is gated inside `PtyBrokerClient.startBrokerOn` by the proof of the runtime it starts on, so a launch that can take the Bun plan needs neither the full proof nor its provisional admission to receive the client. The first branch answers as soon as this build's own tree digest is known (one small bounded read in a packaged install, none when a restore already latched it); when it cannot, the old gate is asked and its failure message and back-off are unchanged.
- `src/extension.ts`: `chatBrokerClient()` = the ADR-0068 settings barrier, then `gate.chatLaunchClient()`. Composing the two existing launcher dependencies (`attachBrokerClient() ?? brokerClient()`) would skip the barrier whenever the attach answers, so the composition lives in the gate method and the barrier in the wrapper.
- `LocalLauncherDeps.chatBrokerClient`; `LocalLauncher.launch` uses it for `request.transport !== "native"` and `brokerClient` otherwise. The launcher knows only the transport; whether the Bun plan is eligible is decided later, inside the client.
- Unchanged: the background start of the full proof after the startup restore (`void s.ptyGate?.client()`), so a terminal's first open still finds it ready, and everything the full proof gates inside the client.

**What the timeline reads afterwards.** The `runtime proof` lap is the wait for the client the launch kind needs: for a Chat, a few milliseconds; for a terminal, the full proof as before. For a Chat that falls back to `Code.exe`, the wait for the full proof moves into the broker's `runtime check` phase (`proofStartedAt` is taken before `await this.ready()` in `startBrokerOn`), later in the sequence than before (after the document, the slot reservation, the OMP resolution and the launcher probe); a refusal then carries the readiness reason without the launcher's prefix, and the gate's 2 s failure back-off no longer applies to that path. When both the attach check and the full check fail, the failure is logged twice (once per check).

## Alternatives

- **Make the full proof faster or raise its deadline.** The check is the console-child proof terminals need (ADR-0032); a Chat on Bun does not use it, so speeding it up helps the wrong consumer, and a longer deadline only lengthens the wait of the launches that do need it.
- **Start the Bun plan's pipe-only proof at activation too.** Also useful (it is the 17.7 s that remains after this change on a build seen for the first time), but it adds startup work at the moment the machine is busiest (a reload of every window), and the OMP binary it needs is resolved per launch. Left for its own design once this change shows what remains.
- **Replace `brokerClient` for every consumer by `attachClient`.** A terminal's `launch` really does need the proof; only the Chat path is changed.
- **Make `gate.client()` itself not wait when a Bun plan is likely.** The gate does not know the launch kind.

## Risks and Open Questions

- **Overlap of the two self-checks on a cold build.** A Chat start on a build seen for the first time (the digest in the proof key changed, so neither stored proof applies), or after the stored proofs expired (24 h), now runs the Bun plan's pipe-only self-check while the full self-check is still running; before, the two ran one after the other. Both run a pipe child under the same 15 s deadline, on a machine that is already slow at that moment (the incident), so the pipe-only check can run out where, alone, it would not. Without a rule, a Chat would then fall back to `Code.exe` and that `bun.exe` would be held off for 10 minutes (ADR-0074, decision 3), trading the runtime the ADR exists to give for a wait the fallback pays anyway. The rule below keeps that from happening; how often the second check also runs out (and is then judged by the ordinary rules) is not measured.
- **What keeps an overlap from costing the Bun runtime.** `proveBunRuntime` (`src/host/pty-bun-proof.ts`) wraps the pipe-only check: when its answer is inconclusive (`ready && !proven`) and this window's first full probe was running at the start or at the end of it (`PtyRuntimeProof.probing()`, read-only), the answer is not acted on: the check waits for that probe (`PtyRuntimeProof.settled()`, which never starts one) and runs once more, and the second answer is judged by today's rules, except that a second inconclusive answer falls back for that launch without the 10-minute hold (it may itself have been contended, for instance by the full proof's own repeated check that starts 20 s after a provisional admission, which `probing()` does not show). A refusal (a fault was seen) and a proof are never re-checked; an inconclusive answer with no full probe running is judged at once, and so is one whose overlap fell entirely inside the check (neither sample sees it). Rejected: a longer deadline for the pipe-only check (turns a timeout into a refusal), starting it at activation (more work when the machine is busiest), waiting for the repeated check too (up to 90 s the fallback would not pay). ADR-0074 carries the amendment. The wait is the one the fallback would have had, so the start is not longer than it was; when the plan still falls back, its time is part of the `bun attempt` phase (not covered by a test). Tested at the seam (`pty-bun-proof.test.ts`, `pty-runtime-proof.test.ts`); the client wiring is covered by the existing Bun start tests and type checking, not by a test that overlaps the two checks; an untrusted `bun.exe` also waits for and repeats the check, which cannot change its outcome.
- When the full proof is refused (a fault held for `PTY_FAULT_HOLD_MS`) a Chat used to be refused up front with the readiness reason; now a Chat with an eligible Bun plan starts, because it does not use the proof that failed, and a fallback Chat gets the held fault reason from the client. This was established by reading the client (`startBrokerOn`, `PtyRuntimeProof.ready`), not by a test: `PtyBrokerClient` builds its proof internally and offers no seam to put it into a fault hold. The pipe-only self-check runs the same staged entry and loads the same addon, so a tree broken in what a Chat broker uses is refused by it too when it runs; when a stored pipe-only proof (same digest and Bun file stamp, less than a day old) skips the check, a fault shows up as a `start` refusal at the Bun spawn, which holds that `bun.exe` off until its stamp changes, and the fallback then reports the fault. A fault hold on the full proof could not cause that hold before.
- `attachClient()` is `null` while the tree digest cannot be read; the fallback to `client()` keeps that case as it was.

## Rollout and Verification

1. `PtyReadinessGate.chatLaunchClient()`, `chatBrokerClient` in `src/extension.ts`, `LocalLauncherDeps.chatBrokerClient`, the launcher's use of it. Comments that this makes wrong are corrected: `local-launcher.ts` (the lap comment), `pending-steps.ts` (the `runtime proof` step), `extension.ts` (`brokerClient` "used by every path that launches"; `attachBrokerClient` and `attachClient` described as "for re-adopting"; the background-proof comment "so the first launch finds it ready"), `pty-readiness.ts` (the `attachClient` doc).
2. Tests. `src/host/pty-readiness.test.ts`: `chatLaunchClient()` answers at once while the full check is still pending, and waits for the full check only when the attach check cannot answer; it does not latch the provisional state. `src/runtime/local-launcher.test.ts`: a Chat launch asks `chatBrokerClient` and not `brokerClient`; a native launch asks `brokerClient` and not `chatBrokerClient`; a `null` from `chatBrokerClient` is the same refusal as before. No existing test pins that a Bun start leaves the full proof alone (the Bun-start cases of `src/host/pty-client-bun.test.ts` need a Bun install and do not look at the proof's log lines): the one added to `pty-client-bun.test.ts` asserts that after a Bun start the proof logged no `proved itself`, `admitted unproven` or `proof reused` line.
3. Documentation: `docs/architecture.md` (the paragraph that follows the PTY proof paragraph states which launch waits for which proof, and what the `runtime proof` lap means per kind), the troubleshooting guide (the lap is the wait for the client the start needs; no step name changes), CHANGELOG.
4. Installed check (after an update and a reload): a New Session's timeline line shows a `runtime proof` lap of milliseconds, **and** its `Chat broker runtime:` line names Bun, not `Chat broker runtime: VS Code (Code.exe), because the pipe-only self-check on … did not finish in time`. It counts only when the session was started while the window's first full probe was still running (its `PTY runtime admitted unproven` or `proved itself` line comes after the session command).
