# A session that continued in a newer file is the same session: follow the chain, move the row, show one session

## Problem

OMP 18.13 can move a running session to a new file. Resuming the old file then opens the newer one, so the file and the id OMP reports are not the ones Desk asked for, and Desk's identity check ends the attach:

- `--session <old>` of a session that has a continuation fails `identity-mismatch` (Chat), or `session-mismatch` in the host-control handshake (Terminal). Resume of such a session is broken.
- A process that moves while a tab is attached reports another file and id on the next `get_state`: the tab fails `identity-diverged` and becomes read-only; after Reload Window the same mismatch fails the reattach.
- History lists the old file and its continuation as two sessions, and opening both creates two rows for one conversation.

## Goals and Non-goals

- Goals: a verified continuation is accepted wherever Desk compares the file and id OMP serves with the ones it recorded; the catalog row follows the conversation to the newest file (one row, same tab, same editor, same claim discipline); History lists one session per chain; any change that is not a verified continuation stays a divergence.
- Non-goals: merging two rows that already exist for one chain; resuming an older copy on purpose; choosing between live branches the way OMP does (OMP's choice is accepted whenever it descends from the requested file); relocated files (`/move`) and files OMP replaced (below); re-binding a committed bridge document; any change to how Desk starts OMP; Rewind, Fork and Clear semantics.

## OMP facts (installed 18.13.3, `@oh-my-pi/pi-coding-agent`; paths are inside its `src/`)

- **When a continuation is created.** Only when a session cannot keep writing its own file: `#moveOffSessionFile(reason)` (`session/session-manager.ts:1279-1317`) with `reason` `open-elsewhere` (another live omp process owns the file's claim; 1494, 1658, 1790), `contested` (a writer without the lease kept changing the file; 1243) or `replaced` (the file no longer reads as this session's journal; 1233, 1251, 1257). Not compaction, size, branch or `/new`. The notice type is `SessionPersistenceNotice {reason, from, to}` (847-861).
- **Header.** The new file is `<fileSafeTimestamp>_<newId>.jsonl` in the same directory; its header has a **new session id** (`mintSessionId()`, 1283), `parentSession` and `continuationOf`, both the old session id (1300-1301), written before the carried fields because the listing reads only 4 KB (1286; `session/session-entries.ts:41-74`, `continuationOf` 56-62). The old file is left untouched; nothing durable exists in the new file until the next flush (1271-1272), and artifacts are copied in the background (1312).
- **Resolution.** `--session` is `--resume`'s path form: `createSessionManager` calls `findSessionContinuation(sessionArg)` and opens `continuation.session.path` (`main.ts:1307-1328`); an id resolves through `resolveResumeTarget` (1332-1351). `findSessionContinuation` (`session/session-listing.ts:892-951`) scans only files of the same directory whose generated name is later than the root's creation, follows `continuationOf` through any number of hops, follows a link only when the continuation holds the newest turn of the copy it continues, and picks the copy with the newest turn, keeping the requested file on a tie. The result is always a descendant of the requested file (or the requested file). Its `replaced` rule (900-903) applies to an id resume that matched a file name, and to a path whose file no longer reads as a session; a path whose file reads as another session resumes as that session. `--continue`/RPC `open_session` use `findRecentSessionContinuation` (1035-1101), which may also pick an ancestor or another branch; Desk uses neither. The chain walk of OMP is unbounded and finds a parent by any file name (1108-1121).
- **What OMP reports.** `get_state` reports the resolved file and its own id: a different file and a **different id**; the id does not stay the same across the chain. A process that moves while running reports the new pair from the move on.
- **Measured** with the installed OMP in an isolated agent dir (mock model): process A on file F0 (id I0); process B started with `--session F0` while A held it reports F0/I0, and after its first write reports F1/I1 with header `{id: I1, parentSession: I0, continuationOf: I0}`; a later `--session F0` reports F1/I1 at start; a process on F1 and a second `--session F0` give F2/I2 with `continuationOf: I1`; then `--session F0` reports F2/I2 (two hops).
- **A relocation is not a continuation.** `/move` renames the file into another directory under the same name and id (`session-manager.ts:2616`, `previousSessionFiles` 2688); the id does not change and the same-directory rule refuses it.

## Current State

Chat: `RpcSession.#identityMismatch` (`src/host/rpc/session.ts`) compares the reported file with the bound one and the id with the bound one; the only accepted id change is a `/clear`-style provider rotation inside the same file (ADR-0059). Terminal: the control handshake compares the host's file with the launch expectation (`session-mismatch`), and `LocalNativeWatch` treats any other reported file as `/resume` or `/new` (a second row, the process handed to it). Catalog: no code replaces the file of a row that has one; `mergeSessionIndexRecords` settles only the run state field by field. `scanFolderHistory` lists every file. The header reader and the chain proof (`src/host/session-files.ts`, `src/host/session-chain.ts`) are the first part of this change and exist in the tree.

## Proposed Design

**One rule.** A file `T` is a continuation of a requested file `R` when walking back from `T` along `continuationOf` reaches `R`: each step reads the header of the current file, takes its `continuationOf` id, and finds the file of that id in the same directory (`*_<id>.jsonl`, or `R` itself when `R`'s header has that id); every header id must equal the id its link and its name claim; a repeated id (a cycle), a missing file, another directory, an unreadable header, a missing link, or two files holding the id refuse. The walk stops after 64 links: a Desk cap that fails closed, not an OMP property. The ambiguity test only counts files with a generated name, stricter than OMP's lookup and safe. The proof carries `{fromFile, toFile, fromId, toId, hops}` and is computed from the files, never from what OMP reports (`src/host/session-chain.ts`). OMP's reported id must equal `toId`, and the reported file must carry OMP's generated name for that id (`<time>_<id>.jsonl`), which also keeps an unrelated file from costing any file read.

**Accepting it** (every place that compares OMP's file or id with the recorded one):

1. *Chat* (`RpcSession`): before the check at the first attach and every resync, after a prompt and in the `get_state` response path, a reported file that differs from the bound one is proved against it; an in-flight move whose new file does not exist yet waits a bounded 2 s (OMP publishes the new file with the move's first flush). On success the session rebinds file, id and its header id, reopens its history reader on the new file, awaits the catalog acceptance below, and the page learns the new id from the next state; if the catalog refuses, the tab fails `identity-diverged` as before. Without a proof the check is exactly as before.
2. *Terminal*: the host-control handshake proves the host's file against the expected one instead of refusing, and `LocalNativeWatch` proves a changed file against the row's before treating it as `/resume`; a proven continuation takes the same catalog acceptance and then the same-row path (id, title, committed document). A refusal falls through to the existing handover handling.
3. *Catalog* (`SessionIndex.acceptContinuation`, under the tab's lifecycle, through `LocalIdentity.bindContinuation`): re-proves the chain, requires the row to still record the old file and the old id, requires this window to run the row, refuses when another row of this window owns the new file or its claim is held by another live holder, takes the claim of the new file (same owner generation and holder as the old one) **before** the write, and writes one compare-and-swap catalog transaction like a provider identity (ADR-0059) that sets `sessionFile`, `sessionId`, `host.sessionId` and `sessionDir` and refuses when the committed record has another row on the new file or another host or file for this row. After the write it gives up the old claim. Failure paths: a refused or failed write gives the new claim back and leaves the row untouched; a refused release of the old claim is logged and both claims stay, and the old one is swept as an orphan claim once no row names it and its holder is gone. No new row is created; the tab, editor binding and title stay. Recording the same continuation twice is a no-op.
4. *Merge*: `mergeSessionIndexRecords` settles `sessionFile`, `sessionId` and `sessionDir` together under the same field-conditional rule as the run state: a window that did not change them keeps the committed ones, so a stale window's later title, unread or activity write cannot take the old file back.
5. `SessionIndex.rowOfChain(file)` names the row that holds a file's conversation in another file of its chain (and `null` for a file with a row of its own). `trackSession` stays exact-file. The History Resume uses `rowOfChain` before it registers a discovered file, and accepts a row that is the chain's, so a stale picker entry opens the conversation's row instead of creating a second one.

**One session per chain in History.** `scanFolderHistory` groups the candidates of one pass by `continuationOf` (`groupChains`) and hides a member that exactly one other file continues (it is superseded: OMP opens the newer file whichever member is named). The head of a chain (nobody continues it) stays listed. A chain with an indexed candidate keeps the user's own row, with its tab, and hides the discovered members instead (unless the family diverged). A parent that two files continue is a diverged family, which OMP accepts and states itself; every member of such a family that is not superseded stays listed, so no branch becomes unreachable, and an indexed row is never hidden. A chain that would be hidden whole (a cycle) keeps its member with the newest modification time. The rule is structural; modification time only breaks that last tie, so it cannot hide a copy OMP would resume. A candidate whose header cannot be read or whose file is gone is never hidden; hidden files are not reported as issues. An indexed row shows the title and time of its own file until it follows the conversation at its next resume.

**Unchanged.** Provider-id rotation inside one file (ADR-0059) still needs the explicit rotation window; a different file that is no proven continuation, an id that differs from the proven one, a cycle, a forged `continuationOf`, a relocated file, a file OMP replaced and a continuation that belongs to another row all stay `identity-mismatch`/`identity-diverged`/`session-mismatch`. Restart (ADR-0050) recovers an identity failure whose row file still carries the durable id; for a relocation, a `replaced` file and a stale committed bridge binding it refuses, and the way out is to Forget the row and open the new file. The Stop fences compare two live reports of OMP, so a move between their two reads still ends a Stop with its existing "still finishing work, or the session changed" refusal; the next Stop captures the new pair.

**The bridge document is not re-bound.** A committed bridge document names the file and id it was committed against and is write-once by design (ADR-0023): after an in-flight continuation its route stays authenticated standby until the editor is re-created (Reload Window, reopening the editor; Stop and Resume mints no new document and does not clear it), and ADR-0050's Restart, which compares the committed binding with the row, refuses until then with its existing message. The panel route of a live page is not affected. A first attach, or an editor created or restored after the acceptance, commits its document against the new pair.

## Alternatives

- **Resolve to the chain head before launching and pass that file.** Exact for a launch (OMP does not follow a file nobody continues), but it does not cover a move while attached or a reattach after Reload Window, so the accept rule would still be needed. Rejected as a second mechanism.
- **Trust OMP's report when the id looks plausible.** No evidence on disk; widens ADR-0059's refused broad acceptance. Rejected.
- **Keep one row per file and link them.** Two rows for one conversation in Sessions, two claims, two editors; the opposite of the goal.
- **Hide old files in the scanner by name or time only.** Cannot tell a continuation from an unrelated later session; the header link is the evidence.
- **Re-prepare the bridge document and re-render the page on an in-flight acceptance.** Reloads the page in the middle of a turn to fix a route that only a surviving page after an extension-host restart uses. Rejected; the limitation above is disclosed.

## Risks and Open Questions

- The proof is as strong as the files: a same-user writer can forge a header, and the same user's session directory is already trusted input for every identity check Desk makes.
- A row for the old file and a row for the new one that both exist (opened separately before this change) are not merged; the attach of the old one is refused with its reason and Forget resolves it.
- The in-flight acceptance needs the new file's header; OMP publishes it with the move's first flush, so a process that reports the new file and no header for 2 s fails `identity-diverged` as today.
- Delete acts on the row's own file. After the row is deleted the older members of its chain stay hidden by the superseded rule, so they cannot be deleted from History; removing them needs a claim per member (ADR-0027) and is not done.
- The bridge limitation above, and the unrebound claim of an old file whose holder lives on (the owning window), are accepted.

## Rollout and Verification

Chain proof and header parsing (chain of 1 and 2 hops, forged and unrelated links, cycle, id mismatch, missing file, other directory, ambiguity), catalog acceptance and merge, Chat, Terminal and History, each with focused tests; then a real continuation made with the installed OMP in an isolated hidden VS Code window (scenario `test/e2e/scenarios/75-session-continuation.spec.ts`): a second `omp --session <file>` process moves off the file a Chat holds, Close and Resume of the row and Reload Window attach without `identity-mismatch`, the row follows the newer file and Sessions shows one row. The same scenario run against a VSIX of the commit before this change fails with `identity-mismatch` at the Resume.
