# Link inline code symbols in Chat through VS Code's workspace symbol providers

## Problem

The Chat prompt asks the model to write each code symbol as a Markdown link to its definition line (`` [`App.start`](src/app.ts:12) ``). The model does this for most symbols, but a long answer still leaves many plain inline-code symbols (`Session`, `SessionData.Load`, `SessionStoreBase<T>`, `ISessionStoreRestriction`, `[Tracked]`), because it did not see their definition line or simply did not link them. VS Code already knows where most of these are defined: every language extension that implements a workspace symbol provider (C# Dev Kit/Roslyn, TypeScript, Python, Go, ...) answers `vscode.executeWorkspaceSymbolProvider`. Desk can use that to link a symbol whenever the provider reports one matching definition, whatever the model wrote. The decision to do this in the host window is [ADR-0058](../decisions/0058-resolve-chat-code-symbols-in-the-host-window-through-workspace-symbol-providers.md).

## Goals and Non-goals

- Goals:
  - An inline code span in **assistant reply text** that is not already a link or a path, and looks like a code symbol (`Name`, `A.B`, `Name()`, `Name<T>`, `[Name]`), renders as a code-path link when the provider reports exactly one matching definition inside the session's folders. The link looks and acts like the existing code-path links: underlined code, a click opens the file at the definition's line and column, Ctrl+Click reveals it in the Explorer, Ctrl+Shift+Click shows it in File Explorer, the same right-click menu.
  - Never block rendering or streaming; bounded work per document, per window and per provider.
  - A setting, `omp.linkCodeSymbols` (default on), turns it off.
  - The model-facing `code-links` prompt rule is improved so the model links more symbols itself; the host resolution is the safety net.
- Non-goals:
  - No guessing: an unknown symbol stays plain code, and a symbol with several different definitions never links to one of them (it links to the workspace symbol search, see Ambiguous symbols). No ranking picks "the best" overload, partial declaration or same-named member. (One maintainer-approved exception: a bare capitalized name prefers type-like declarations over members, see Matching.)
  - No links into library or metadata documents, or into files outside the session's folders. A vendored library whose sources are inside those folders is not told apart from the project's own code.
  - User messages, tool rows, notices, thinking blocks, code blocks and link labels are unchanged. Only a whole inline code span of assistant reply text is a candidate, wherever it stands in that text, including inside bold, italic and strike-through (maintainer decision, 2026-10-10, once emphasis rendered code spans).
  - No new language service, no parsing of source files by Desk, no index of our own, nothing given to the agent (the language tools of the agent stay native OMP `lsp`, [ADR-0013](../decisions/0013-authenticated-reverse-rpc-for-vscode-language-providers.md)).
  - Unsaved edits: a symbol added in an unsaved buffer is seen by a provider but not by this feature's invalidation until a save, a file-system change or the cache lifetime passes.

## Current State

- Page: `Markdown.tsx` renders a code span through `codeSpan`: a span that is one path becomes `<code><FileLink/></code>`; `FileLink` asks the host to validate the path (`omp:terminal-link-validate`, `ChatFileLinks`, a per-document `ValidationCache`) and wraps the characters in an anchor (`omp-file-link`) once the host proves it; a click posts `omp:terminal-link-open`, which the host re-resolves against the session cwd.
- A Markdown link with a path destination (`` [`Name`](src/a.ts:12) ``) is the same anchor around the code, once the file exists.
- Host: `handleTerminalLink` (`src/host/terminal-links.ts`) answers validate/open from `extension.ts`'s `handleTerminalGuestMessage`, over the panel route and over the authenticated bridge (`terminal-link-*` operations, stream class), so a surviving page works after an extension-host restart. The open path accepts any existing absolute local file; it is not a workspace sandbox.
- Nothing asks a language provider anything today.

## Proposed Design

### Candidates (shared pure module `src/webview/code-symbols.ts`; page and host both run it)

`parseCodeSymbol(content)` normalizes one inline-code span and returns `{ segments, name, last, attribute, call }` or `null`. Alphabet: ASCII identifiers `[A-Za-z_$][A-Za-z0-9_$]*` only; a span with a non-ASCII letter is not a candidate. Order of steps:

1. Trim. Reject spans longer than 120 characters, or containing a backtick or a control character.
2. If the whole span is `[...]`, remove the brackets (`attribute`). If it then ends in a balanced `(...)`, remove that one argument list (`call`); argument contents are not interpreted, so `[Tracked(typeof(X))]` is `Tracked`.
3. Remove every balanced `<...>` group, whose inside may hold only type-argument characters (letters, digits, `_ $ . , ? * & :`, spaces, brackets); an unbalanced or otherwise filled group rejects the span (`a<b`, `Foo<a+b>`).
4. Remove trailing `[]` and `?` suffixes.
5. What remains must be one to four identifiers joined by `.`; anything else (space, operator, quote, path separator, `::`, `->`, `;`) rejects the span.
6. Reject: a last segment shorter than three characters (so `A.B` and `x.y.zz` are not candidates); a first segment that is `this`, `base`, `self`, `super` or `cls`; any segment that is a keyword or keyword-like type name (one constant list, case-sensitive: `string` is one, `String` is not).
7. A bare name made only of lowercase letters and digits (`main`, `json`, `sha256`) is prose and a candidate only with a call suffix (`parse()`). A name with a capital, `_` or `$`, and every dotted name, is a candidate. The call flag has no other effect on matching: it never selects an overload or a constructor.

The span's raw content is what the page sends, so the host runs the same function again.

### Order against path links

A span that already looks like a path (`isFileLinkCandidate`) keeps its file link. `A.Bcd` is also path-shaped (`.Bcd` looks like an extension), so a candidate that is also a path first waits for the host to prove or refuse the path (the existing validation) and asks about the symbol only when the path is refused. The symbol request is never sent for a proven path.

### Eligibility

Only assistant reply text opts in: `AssistantContentView` provides a React context (`SymbolLinksEligibleContext`) that the assistant text blocks read, and the thinking disclosure turns off again. User text, tool rows, notices, detail tabs and the rest of the transcript render exactly as before; file links keep working everywhere they do today.

### Wire protocol (new pair in the terminal-link family, same plumbing)

- Page to host `omp:terminal-link-symbols { requestId, tokens: string[] }`: 1 to 16 tokens, each 1 to 120 characters without control characters; the exact key set is enforced.
- Host to page `omp:terminal-link-symbol-resolution { requestId, disabled?, results: [{ token, status: "found" | "none" | "unavailable" | "pending", target? }] }`: one result per admitted token, `target` only with `found`, a link target of the existing grammar (`path:line:column`; relative to the session cwd inside it, absolute otherwise; the bare path when the provider gave no position). The page matches a result to its request by `requestId` and to a token by its text, and treats a token missing from the answer as `unavailable`; an answer for an unknown request is ignored.
- Integration surface (each is one small additive entry, all in the existing terminal-link seam): both message parsers and unions (`messages.ts`), the browser's `bridgeOperation` mapping, the host's presentation admission (`TERMINAL_PANEL_TYPES`, the Chat panel guard that lets link requests through in either mode), the bridge's stream-operation class and `BRIDGE_OPERATIONS` allow-list, the `handleTerminalGuestMessage` case with the same document/session/cwd currency check as validate/open, and the reply through `pushTerminalTo`. A bridge request that fails parsing or the route state is refused as for any other link request. No mutation slot is taken.
- A click is not new: the anchor posts the existing `omp:terminal-link-open` with the returned target; the host re-resolves it against the session cwd, requires an existing file, and opens it. The symbol exchange adds no opening authority; a forged resolution can produce only a link the existing open path would accept anyway.

### Host resolution (`src/host/symbol-links.ts`, pure and tested without VS Code)

`SymbolLinkResolver` takes a `SymbolSource` (`query(text): Promise<SymbolEntry[] | null>`; `null` for an error or timeout) and answers one candidate at a time.

**Adapter contract.** The VS Code adapter (`extension.ts`) calls only `vscode.executeWorkspaceSymbolProvider` with a candidate's name and keeps at most 1001 entries of the answer before converting any (one past the 1000 examined marks a cut answer). `symbolEntry` converts each `SymbolInformation`: only a `file`-scheme URI has a path (a metadata or library document gets no path and can never be inside a session folder); a name or container too long to keep (over 256/2048 characters) is never cut into another identity: it is rewritten to what matching reads of it (the bare name and generic arity of a name; the enclosing-type alternatives and identity of a container, verified by reading the result again), and only a container that cannot be rewritten within the limit makes the entry `opaque` (name and kind kept, no container, never matched); an opaque entry named like the symbol could be the hidden rival of a unique match (or the match itself), so the lookup is `none` (plain text, final) unless an ambiguity was already seen, and an opaque entry of another name or outside the folders is no rival (amended 2026-10-18, see Readiness and parking: every oversize entry used to make the lookup `unavailable`); line and column are validated finite integers converted once to one-based; a location without a range, or an empty range at 0:0 that a provider substitutes for one it did not resolve, has no position, and the link then opens the file without a line (a click goes to the top of the file; a definition line is never invented).

**Scope.** Allowed files are those inside the session cwd or inside an open workspace folder that contains the cwd (a session started in a subfolder still links to the rest of its project). Containment is lexical, component-wise and case-insensitive (Windows); symlinks and junctions are not resolved. "No libraries" therefore means: no external or metadata locations.

**Steps.**

1. Cache lookup keyed by (session folder, canonical name, attribute flag), then in-flight sharing.
2. Query the provider for the **last segment** of the name. When a dotted name finds nothing, query the full dotted text once more, because a provider may understand a qualified query that the bare name's ranked list does not reach.
3. Keep entries inside the allowed folders.
4. Match: the entry's name with parameter and generic lists removed equals the last segment exactly and case-sensitively (an attribute candidate also matches `NameAttribute`, on a type only). For a dotted name, the entry's container (generic arguments removed, split on `.`/`:`) must end with the preceding segments, compared exactly; an entry without a container never matches a dotted name. The C# language server (Roslyn, behind the C# and C# Dev Kit extensions) gives a localized display text as its container, never a namespace: `in SessionIndex (project omp-vscode (net8.0))` for a member (`в SessionIndex (проект omp-vscode (net8.0))` in a Russian window), `in Outer.Inner (project …)` for a nested type, `project omp-vscode (net8.0)` or `Store.cs - omp-vscode (net8.0)` for a top-level type. A container with a trailing group that holds a space or a nested group is read this way: the words before the group (outside generic argument lists) are the alternatives for the enclosing type path, because the position of the localized `in` differs between languages, and the group (the project) stays part of the container identity for grouping. Other containers are compared as written. An inherited member (declared in a base type) therefore does not match its derived type's name.
5. Kind matrix (`vscode.SymbolKind`):

| Kind | Bare name | Dotted name | Attribute |
|---|---|---|---|
| Class, Interface, Struct, Enum | match | match | match |
| Namespace, Module | match | match | no |
| Method, Function, Constructor, Property, Field, Variable, Constant, EnumMember, Event | match | match | no |
| File, Package, String, Number, Boolean, Array, Object, Key, Null, Operator, TypeParameter | never | never | never |

   Maintainer-approved exception: for a *bare capitalized* name, when at least one type-like entry matches, only the type-like entries are counted (so a class `Session` is not made ambiguous by a property `Session` elsewhere, and a constructor is not a rival of its class). Everything else is counted as it is.
6. Distinct declaration locations (path, line, column; path compared case-insensitively) are counted, keeping the first report of one location. Entries without a position carry no identity: each counts as its own declaration (two unresolved overloads in one file are two). The locations are then grouped into symbols (maintainer decision, 2026-10-10, after a C# solution left partial classes and overloaded methods plain): the partial parts of one type (same name, generic arity and container; a `.cs` type with no container, as in the global namespace, counts too, a container-less type of another language never does) and the overloads of one member (same container, same name, both method-like or both of the same kind) are one symbol. **One symbol: found**, opened at the type's own file (`Desk.cs` for `Desk`), else at the first location by path and line (a positioned location before an unpositioned one). Several symbols (same-named types in different containers, a method and a property, an interface and its implementation) are ambiguous (the page links them to the symbol search, with the number of symbols as `definitions`), unless exactly one of them lies inside the session's own cwd, which is then the one (the roots may be wider than the cwd). A dotted qualifier narrows through the container match above. Zero: none.
7. A query that throws is `unavailable`; an invalidated lookup, a query that times out or is refused, or an empty answer from a provider that has not yet answered any symbol, is `pending` (see Readiness and parking); an empty answer after readiness is none. `unavailable` ("no reliable target yet"; it makes no claim about the provider's health, because an empty list is also a valid answer for a name that matches nothing): never cached. The same holds when the qualified second query of step 2 fails: the lookup is `unavailable`, not a miss. The adapter keeps only the entries that could be a declaration of the symbol's last segment (exact name, parameter and generic lists ignored however long the whole name is, or its `Attribute` form) before converting, so fuzzy neighbours (`DeskManager` for `Desk`, or a generated formatter's method with a hundred-parameter signature) never crowd exact entries out of the 1000-entry bound. An answer Desk still had to cut (more than 1000 candidates) can show an ambiguity among the entries it examined (none), but never a unique match (`unavailable`), because the second declaration may lie in the part it discarded. An answer with no entry at all is `pending` until the provider is ready (a language server still loading) and none after; an answer of unrelated entries only is none.

**Guarantee and its limit.** *Found* means: among the entries the provider returned for the exact name, inside the allowed folders, exactly one matches. A workspace symbol search is a relaxed, ranked search whose providers may cap their results, not an exhaustive declaration index. The design relies on providers ranking exact name matches first, which the API does not promise, so a hidden second declaration is possible for a very common name in a very large workspace. This residual risk is accepted by the maintainer's brief ("link only when exactly one definition remains"; provider caps are to be reported as a limit) and is disclosed in the README and the architecture document. Desk's own 1000-entry cut is different: it is known to Desk, and a cut answer never yields a unique match.

**Bounds.**

- Window-wide limiter: at most 4 provider calls are in flight; a slot is released only when the provider's own call settles, never at the timeout, so a hung provider keeps its slot instead of letting invocations pile up. Beyond the 4 slots, at most 64 queries may wait, each at most one query timeout; a query that finds the line full is refused at once (`pending`, log `parked (queue)`), and one whose wait expires is dropped from the line, so no request state outlives a hung provider.
- Each query gives up (logically) after 8 s (a large solution's Roslyn can need seconds for a workspace symbol query). A lookup issues at most two queries and starts none after its generation was invalidated or after 15 s. A batch is answered within 15 s (the page waits 20 s) with whatever settled; the rest is `pending` (it was not answered, so it is no try of the page) while it may still finish into the cache.
- The page's own limits (16 tokens per request, 2 requests in flight, a 64-token budget) are courtesy, not security: the host enforces its own admission as above, works on at most 8 batches at once (panel and bridge routes together; a ninth is answered `pending` at once and asked again with the queue-drain signal) and `parseSymbolLinksRequest` bounds every request (16 tokens of at most 120 characters, measured on the raw token like the page's parser). One batch looks up its tokens four at a time, so no batch fills the provider's line (2026-10-18).
- Cache: at most 1024 entries; found for 60 s, none for 15 s.

**Fencing.** Each lookup captures the resolver's generation. Any file-system change under the workspace folders (a lazily created `FileSystemWatcher("**/*")`), saved or renamed document and workspace-folder change bumps the generation, clears the cache and the in-flight table; a lookup of an older generation starts no further query (a query waiting for a slot checks the generation when its turn comes, and one dispatched is not used), returns `unavailable` and caches nothing; a call of the new generation never joins an old lookup. A batch captures the generation too: if it moved before the reply, every token is answered `unavailable`, so an answer buffered before a file change is never delivered. After the provider answers, the handler re-reads the setting and the allowed folders: a setting turned off yields `none` with `disabled`, a changed folder set yields `unavailable`; a replaced document, session or cwd yields no reply (the existing `isCurrent` check).

**Setting.** `omp.linkCodeSymbols` is read on each request and again after the provider answers; off means `disabled: true`, `none` for every token, and the page stops asking for 30 s. There is no configuration listener: the page learns of a change with its next request, and spans re-rendered meanwhile show plain code.

### Page (`src/webview/lib/chat-symbol-links.ts`, `FileLinks.tsx`)

`ChatSymbolLinks` is one per Chat document, created beside `ChatFileLinks` by `FileLinksProvider`. It batches unique tokens (a 40 ms window; at most 16 per request; at most 2 requests in flight; a 15 s timeout per request), caches answers (found 30 s, answered none 10 s), and retries an `unavailable` token twice, after 5 s and then after 20 s (a language server that is still loading). Admission is one budget: at most 64 tokens may be unsettled at once, whether queued, in flight or waiting for their retry; beyond it a token stays plain and uncached and is asked again when its span next renders. The budget is per document, not per message. After the retry the token is recorded as none for 60 s: a per-token cache entry, so remounts and new batches inside that minute do not restart the cycle (clearing the whole cache at its 1024-entry bound also clears cooldowns; the bound makes that a best-effort limit). Request ids are document-wide (like the terminal-link client's), and an answer is first matched to a live request, so an answer meant for another client of the same page, a late one or a made-up id changes nothing, not even the disabled state. A disabled answer settles queued tokens and cancels waiting retries. A code span component asks only after the span has been on screen once (`IntersectionObserver`, so history that was never scrolled into view does not query) and after the existing 200 ms settle that keeps a streaming reply quiet; before the answer arrives the code is exactly what Markdown produced, so text, selection and copy are unchanged. Answers are not polled: a span keeps the link it shows while its answer is expired, and the next render of the span asks again (a streaming update, a remount); while the host has the feature off, spans render as plain code. A stale link is harmless because the click re-validates through the open path (file existence, not that the symbol is still on that line).

### Prompt

The `code-links` rule is reworded (still one imperative rule under 280 characters): link every mention, tables and lists included; use the definition line seen in a read or search; when only the file is known, link the file; plain code only for symbols the model did not locate; never guess a line; no extra tool calls to find lines. The effect is measured by repeating one question before and after (see Verification).

### Readiness and parking (maintainer decision, 2026-10-10)

Observed in a real C# solution: while C# Dev Kit loaded 63 projects the provider answered no symbols, history rendered at once, and every visible token spent its retries; later a long reply overflowed the provider queue. Neither is a verdict about the symbol, so neither is final:

- **Readiness (per window).** Until some workspace-symbol query of the window returns at least one entry (any entry, exact or fuzzy; the provider's `total` before Desk's name filter), an empty answer means "not ready": the lookup is `pending` (log `parked (not ready)`), not unavailable and not none. A canary query (the name of a recently parked token, at most 8 remembered) probes with delays of 2 s doubling to 30 s for ten minutes; the first answer with an entry marks the provider ready, logs `code symbols: provider ready after N s, re-running M parked` and sends the retry signal. After readiness an empty answer is a real `none`. A change of the workspace folders resets readiness. Parked state is a bounded set of keys (1024) and at most 8 names, nothing is held per token.
- **Queue.** A full waiting line and a query timeout are `pending` too (log `parked (queue)`, `parked (timeout)`); when the provider's slots are all free again after such a refusal, the host sends the retry signal (at most one per 3 s, log `code symbols: provider queue drained, asking parked tokens again`).
- **Wire.** `pending` is a result status; `omp:terminal-link-symbols-retry` (host to page, no fields) goes to every page that has asked (a bounded set of slot ids, pruned when the slot is gone) over the same panel and bridge routes.
- **Page.** A `pending` token is not cached and is not asked again by re-rendering until the signal (or one minute); the signal forgets the parking and the cooldown of tokens that exhausted their retries and notifies every mounted span, so the spans without an answer ask again, visible ones only (the `IntersectionObserver` gate and the 64-token budget are unchanged). A page budget overflow notifies once when half of the budget is free again. No state is added per message.
- **Warm-up (maintainer report, 2026-10-17; amends Readiness and Fencing).** After a Reload with a Unity project, `SessionService.Dispose` stayed plain although Ctrl+N (the same `SymbolLinkResolver` lookup) opened it later. The host log (info level, window 3, installed `6f2a43d`) had `link lookup gave up: code symbol "SessionService.Dispose" had no answer in 3 tries over 2 s (provider not ready x2, invalidated x1)` 5 s after activation, and in window 2 four names `in 3 tries over 27 s (invalidated x2, provider not ready x1)`; nothing asked again once Roslyn was ready. Findings. (1) The counter of that line counted resolver lookups, not the page's tries: a lookup is one ask of any client, and the page re-asks without its 5 s / 25 s schedule when a new `ChatSymbolLinks` is made (`FileLinksProvider` makes one, with no memory of parked tokens, whenever the transport or the session's `cwd` changes) or another Chat page asks on its own, so three lookups fit in 2 s. [INFERENCE: the log is at info and has no per-ask lines, so which asker made them is not observed; the host now logs each batch (slot, request id, token count, then the statuses) at debug.] A `pending` answer never used the page's tries (it parks until the signal or a minute); an `unavailable` answer did, and one reporter name collects every client's lookups. (2) An invalidated lookup was `unavailable`, so the page used a try on it and rested for a minute after the third; and the ready transition sent no signal when no token had been parked as "not ready" (the parked set is also emptied by a workspace-folder reset), so a span whose tries went to invalidations was never asked again. This is what window 2's `invalidated x2` shows. (3) The invalidation sources in the code are the `**/*` watcher events that survive the gate (the gate knows only the folder's own `files.exclude` and `search.exclude`), a saved document, and a workspace-folder change. [INFERENCE: which of them fired in the reporter's windows is not in the info log; Roslyn's and Unity's files under `obj/`, `Library/` or generated `.csproj` files are candidates unless the user's excludes hide them.] The gate's debug line now names the first file of a burst, and an invalidation that dropped lookups under way is one info line (at most one per ten seconds) naming its source, so the next report carries the evidence.
  - **Rule.** A lookup that the provider could not answer yet (`parked (not ready)`) or that an invalidation dropped (`parked (invalidated)`, and the batch's "files changed while the batch ran", "invalidated while the batch ran" and "workspace folders changed") is `pending`: it waits for the retry signal and uses none of the page's tries. The give-up report no longer counts these reasons, so the info line is for real failures (timeout, no answer, error), which keep their three tries. A full line (`queue full`) joined the waiting reasons on 2026-10-18, below; a batch deadline and the batch cap no longer give up at all.
  - **Signals, bounded.** The retry signal goes (a) once when the provider becomes ready (at info: `code symbols: provider ready after N s, re-running M parked`, or `asking the pages that wait`) whenever any lookup ended pending since the last signal, not only when a token was parked as "not ready"; (b) once the queue has drained, at most one per 3 s (as before); (c) once after lookups were dropped by changes, `settleMs` (1 s) after the last change, at the latest 10 s after the first lost lookup, and not sooner than the backoff after the previous signal: 3 s, doubling with each signal that lost lookups caused without any lookup answering in between, up to a minute (an answer, or readiness, starts again). Every signal serves everything that was due; the page clears its parking and the unanswered rest of every token and notifies its mounted spans, so spans scrolled back into view ask again as they mount.
  - **Page.** A request sent before a signal that is answered `pending` is asked again at once (the signal went out before the page parked the token and would not repeat); the next signal lets it go again, so the repeats follow the host's rate. A readiness probe that never succeeds ends after ten minutes with one info line.
- **Loading provider, a full line and unreadable entries (maintainer report, 2026-10-18; amends Bounds, Readiness and parking, and the adapter contract).** In the installed `2c751a5`, whole replies had no links after a Reload that restored three Chat tabs while the C# provider (Roslyn, a Unity project) loaded for about three minutes (`provider ready after 183 s` in the other window). The host log had 109 `link lookup gave up` lines in two minutes; their reasons were `queue full` 49 times, `unmatchable entry` 92 times and `timeout` 12 times (a line lists every reason of its name's tries, so the counts exceed the lines), and file references like `X.cs:270` stayed plain as well. Before the Reload, in a quiet window, a type name and `Type.Member` names had given up with `unmatchable entry` alone. Two separate causes.
  - **Oversize entries poisoned every lookup of a name.** `symbolEntry` marked an entry that had a name over 256 or a container over 512 characters unmatchable (kind `-1`), and any such entry inside the folders made the whole lookup `unavailable: unmatchable entry`: never cached, three tries, a give-up line, again after a minute. Ctrl+N on such a type lists several declarations, a generic sibling and many source-generated partial files, and the cause was taken to be a serialization generator's formatter showing whole signatures as method names (`Deserialize(ref GeneratedReader reader, scoped ref ...)`), so that one generated entry hid every lookup of the name for as long as the provider listed it. **Captured shapes (2026-10-19).** The reporter's entries were not kept, so the C# extension's own language server (ms-dotnettools.csharp 2.160.4, `Microsoft.CodeAnalysis.LanguageServer`, driven over stdio) was asked `workspace/symbol` for a scratch project with an incremental source generator (a generated second part of a partial type, a formatter class with nested generic types of 40 type parameters per level). What it answers: **names are always bare** (`SessionService`, also for `SessionService<T>`; `Deserialize` with no parameter list; no type arguments), so a name over 256 characters was not seen and the name rule below is defensive; **containers are not bare**: a member's is `in Type (project P (net10.0))` and the type's own text carries its type parameters, so the container of a member of a nested generic type was 725 characters with one 40-parameter level and 1121 with two (over the 512 the adapter allowed, which is the poisoning seen; the 2048 limit was not reached); a top-level type's container is the *file of that part* (`Session.cs - P (net10.0)`, `SessionService.Generated.g.cs - P (net10.0)`) or `project P (net10.0)` when it has none; a document the compiler generates only in memory has a `roslyn-source-generated://<guid>/<hint>.g.cs?...` URI (about 400 characters) with no path in the adapter, so it is never inside the folders and cannot poison, and only generated files on disk (a Unity project that commits or emits `*.g.cs`) are in scope. The captured shapes, with names changed, are the fixtures of `src/host/symbol-links.test.ts`. **A second finding, fixed:** because a part's container names its file, the parts of one partial type in different files had different declaration keys and the type was `ambiguous` rather than one symbol; the key now drops the file (`Session.cs - P` and `SessionService.Generated.g.cs - P` read as `P`). A generic sibling in the same file is still indistinguishable from another part (names are bare, the arity is not visible) and is treated as one. **Rule.** An entry's name and container are not cut but *read*: (1) a name longer than 256 is replaced by exactly what matching reads of it, its bare name (parameter and generic lists removed) plus its generic arity, so a method with a hundred parameters is the method it names; a bare name over 256 characters equals no token (a token has at most 120) and stays cut, matching nothing; the adapter's pre-filter reads the bare name of the whole name too, so these fuzzy neighbours no longer crowd the exact entries out of the 1000-entry bound. (2) A container longer than 2048 is rewritten to the shortest text that `containerInfo` reads identically (the same enclosing-type alternatives and identity: `in SessionService<TArgument, ...> (project P (net8.0))` is `in SessionService (project P (net8.0))`), verified by reading the result again; when no such text fits, the entry keeps its name and kind, has an empty container and `opaque: true`: it matches nothing. (3) An opaque entry inside the folders that is *named like the symbol* (a linkable kind, the exact name, or the attribute form on a type) could be the symbol's other declaration or a rival, which nobody can tell: the name is not linked, and an ambiguity already seen stays an ambiguity. An opaque entry of another name, or outside the folders, is no rival. The verdict is `none` (log `none (unmatchable entry)`), a final answer: plain text without a retry, cached 15 s, no give-up line; it was `unavailable` and burned the page's tries. It never links a declaration that could be the wrong one.
  - **A refused lookup is a wait, and the work is bounded.** After the Reload three pages (hundreds of tokens) asked at once; each page sends 2 requests of 16 tokens in flight, and the host started every token of a request at once, so up to 96 lookups met 4 slots and a line of 64: the rest were refused `queue full`. The resolver already answered such a lookup `pending` (the page parks it without using a retry), but the give-up reporter counted it as a failed try (`996fccd` listed `provider not ready` and `invalidated` as waiting reasons and left `queue full` out), and a batch deadline or the batch cap answered `unavailable`, which does use the page's tries. The file-name side had the same fault: a full search line (2 slots, 32 waiting) was `unavailable`. **Rule.** (1) `queue full` is a waiting reason like `provider not ready`: no try, no give-up line. (2) A batch has its share: its tokens are looked up a few at a time (the resolver's slot count, 4), in the page's order, so a request of 16 never fills the line and the batches of several pages take turns through one first-in first-out line (at most 8 batches x 4 waiting lookups, within the line of 64); tokens a batch did not get to by its 15 s deadline are `pending`, not `unavailable`, and a ninth batch is answered `pending` at once: neither was tried. Both ask the pages again through the queue-drain signal (`batchDeferred`). (3) A file-name lookup that finds the search line full is `unavailable` with `waiting`, which the batch answers `pending`; when the line has emptied after refusing lookups the file resolver calls `onDrained` and the symbol resolver sends the retry signal (at the usual rate, whatever its own provider is doing). (4) A provider that has answered nothing, has let a call time out and holds every slot with calls still unanswered is loading and not answering: a further lookup waits as `parked (not ready)` without taking a place in the line, so a provider that does not answer is asked by its four slots and the canary probe only; the ready signal serves the rest. (5) The page asks what is on screen first: a span in the viewport when its settle timer fires sends its token with `onScreen`, which goes ahead of the queue's tokens that are not (a token already queued is promoted) and is admitted up to twice the 64-token budget; the others keep the budget. The page's retry and parking rules are unchanged.
  - **Evidence of the fix.** `src/host/link-warmup.test.ts` wires the real page client, host handler and resolver for three pages of 100 symbols each against a provider that holds its calls until it is loaded: before the change the log carried give-up lines for refused lookups; now none, the provider is asked by its four slots only while loading, and every token of every page becomes a link after it is ready.

### Ambiguous symbols (maintainer decision, 2026-10-10)

The user wants coverage: a token whose lookup finds several different definitions inside the session's folders (distinct symbols after the partial and overload grouping, and not narrowed to one by the cwd) is still a link, but never to a guessed location:

- **Wire.** The result is `{ token, status: "ambiguous", definitions: N }` (N is the number of distinct symbols, at least 2, at most 100000; `definitions` only with `ambiguous`). It is cached like `found` (60 s on the host, 30 s on the page); a later `found` replaces it when the answer changes.
- **Click.** The page posts the existing `omp:terminal-link-open` with `target` the symbol's own text and `search: true` (open only; the validate form refuses the key). The host re-parses the text with `parseCodeSymbol` (a non-symbol is refused with a notice, nothing runs) and executes the one fixed command `workbench.action.quickOpen` with the argument `#<last segment>`, in the window that owns the chat (the `handleTerminalLink` host, current-document checked). The webview never names a command. Ctrl+Click and Ctrl+Shift+Click do the same: there is no single file to reveal.
- **Query.** The last segment (`Run` for `Twin.Run()`), because every symbol provider accepts it and it lists every same-named symbol with its container, while a dotted query is not understood by all providers (TypeScript's does not) and a dead search would be worse than a broader list. The user chooses among the definitions the name has, which may include same-named symbols the page's qualifier excluded.
- **Look.** A span with class `omp-symbol-search` inside the code: link colour like other symbol links, underlined dotted rather than solid, title "N definitions — click to choose". It has no file context menu (no `data-vscode-context`) because there is no file target.
- `none`, `pending` and `unavailable` stay plain. The safety rule "never link a guessed definition" holds: the link goes to a search the user drives, not to a definition.

### Bare file names (maintainer decision, 2026-10-11)

A span such as `session-index.ts:849` stays plain today: it looks like a path, the host proves it only against the session cwd, and the file lives in a subfolder. VS Code knows where the file is (its file search), so a span that is a bare file name is looked up there and becomes a link when the lookup is unambiguous. This is a second *source* for the same exchange, not a second protocol: the page asks the same `omp:terminal-link-symbols` question about the same token, and the answers use the same statuses.

- **Candidates** (`parseBareFileName(content)`, shared pure module `src/webview/code-symbols.ts`, run by page and host): one segment of letters, digits and `_ . + @ ~ $ -` (no path separator, space, colon or glob character, so a name is never a pattern and the lookup needs no escaping), at most 100 characters, starting with a letter, a digit, `_` or `.` (a leading `@` is a file mention, which keeps its own rendering); a non-empty stem and an extension of one to ten characters that starts with a letter and is either all lowercase or all uppercase (digits allowed): `session-index.ts`, `index.ts`, `Makefile.am`, `README.MD`, `foo.d.ts`, `.eslintrc.json`. `Foo.Bar` (mixed case) is a symbol, never a file name; `1.2.3`, `v1.0`, `e.g.` are not file names either. The name may be followed by a position: `:849`, `:849:5`, `:L849`, `:849-860` (the start), `#L849`, or the MSBuild forms `(849)` and `(849,5)`; lines and columns are one to seven digits and at least 1. Anything else (`src/a.cs`, a drive path, `a.cs:x`, a trailing sentence dot) is not a bare file name; paths keep the existing cwd validation. Padding is trimmed and the raw length is bounded like a symbol's.
- **Order.** (1) A span that already looks like a path keeps waiting for the cwd validation (`session-index.ts:849` does, `session-index.ts(849)` does not look like a path), and the host is asked again only when that is refused; on the page the cwd match therefore always wins. (2) The host answers a file-name token from the file lookup first. (3) A token that is also a symbol (`Twin.run`, `Settings.json`) is looked up as a symbol only when the file lookup says `none` and no file change happened since the batch began; `found` and `ambiguous` of the file lookup are the answer, and `unavailable` stays `unavailable` (no guessing past an uncertain lookup).
- **Page rendering.** `codeSpan` sends a symbol or a bare file name to `CodeSymbolSpan`. Where nothing links (user text, tool rows, thinking, no link context, or no answer) a file name that is not a symbol renders exactly as before through the span's own file-reference detection (`plain`), so only assistant text changes.
- **Host lookup** (`src/host/file-name-links.ts`, pure and tested without VS Code; `FileNameLinkResolver` takes a `FileNameSource`, `find(name, folders, signal): Promise<{ paths, truncated } | null>`). Scope is the symbol scope (`symbolRoots`: the session cwd, any open workspace folder that contains it, and any open workspace folder inside it, which adds no path to the scope but is searched with its own excludes; containment lexical, Windows rules). Steps: (a) the file named exactly that inside the cwd (`stat`; the host repeats the cwd check because the `(849)` form skips the page's) is the answer, whatever else exists, so a name that exists relative to the cwd keeps its cwd match; (b) otherwise `vscode.workspace.findFiles` once per workspace folder (a folder inside another too, since the outer folder's own `files.exclude` may hide it; a file found twice counts once) with the pattern `**/<name>` (every letter written `[xX]` because Windows file names are case-insensitive: `Session-Index.ts` links to `session-index.ts`), the exclude glob built from that folder's `files.exclude` and `search.exclude` settings (entries set to `true`; conditional entries are ignored), at most 100 results per root and a cancellation token that fires after 5 s; (c) results are kept only if a `file` location, inside the scope, whose basename equals the name case-insensitively; paths are compared and deduplicated case-insensitively. No result: `none`. One: `found`. Several, exactly one of them inside the cwd: that one (the cwd narrows, as for symbols); otherwise `ambiguous` with the number of files. **A search that stopped at its result limit is never trusted for uniqueness:** it never gives `found` and never narrows to the cwd (a second cwd match may be beyond the limit); with two or more files it is a choice (the number is then a lower bound), with fewer it is `unavailable`. The direct cwd `stat` stays authoritative.
- **Target.** The link target grammar of symbols: relative to the cwd inside it, absolute elsewhere, `:line` or `:line:column` after the path when the span carried a position. The click is the existing open request; the host re-resolves it against the session cwd and opens at the line.
- **Several files** (decision: link, not plain). The wish for coverage is the same as for ambiguous symbols, and a name that is in two folders (`index.ts`, `Settings.cs`) is still useful as a link that lets the user choose, while plain text would hide that the file exists. Nothing is guessed: the user picks. The choice is a QuickPick of exactly the matching files rather than Go to File prefilled with the name, which fuzzy-matches unrelated files and cannot honour the `:line`; its count is the number of files the title promises. **Wire** (end to end): the result is `{ token, status: "ambiguous", definitions: N, files: true }` (`files` only with `ambiguous`; `parseSymbolLinksResolution` accepts it only there, the host result construction and the page's waiter, cache and `SymbolLink` carry it, and the anchor words the title "N files — click to choose"); the click posts `omp:terminal-link-open` with `search: "file"` (`search` is now `true | "file"`, only on an open) and the file-name span as `target`. Both parsers sit in the existing terminal-link seam, so the panel and bridge routes and the operation allow-lists need no new entry. **Host click** (`handleTerminalLink`): the span is parsed again with `parseBareFileName` (anything else is refused with a notice and nothing is searched); the host's own lookup runs again (the page's answer is never trusted and a file may have moved) through `host.lookupFileName`; none or unavailable is a notice; one file opens at once; several go to `host.pickFile` (QuickPick, label the file name, description its folder relative to the cwd or the workspace folder that holds it, matching on the description too). The document and session currency is checked after the lookup and after the pick (the picker may stay open while the document is replaced: a replaced document opens nothing). After the pick the host looks the name up again (the scope is derived afresh, and a workspace-folder change has dropped the cache), requires the chosen path to be among those files, and checks that it is still an existing file before `host.openFile` opens it at the span's position (top of the file without one). The webview names no path and no command.
- **Bounds.** Never in the render path: the page asks only after a span has been on screen and its text settled (200 ms), as for symbols, and a streaming reply waits for nothing. Window-wide at most 2 pieces of file I/O in flight (the cwd `stat` and the `findFiles` search share the limiter), a slot released only when the call settles; at most 32 lookups wait, each at most the 5 s; a lookup that finds the line full is `unavailable` with `waiting` at once, which the batch answers `pending` (it was not tried; since 2026-10-18 the line's drain asks the pages again). A lookup whose `stat` or search times out or fails is remembered as `unavailable` for 30 s (the page's two retries within that time are answered at once without more I/O; the page then rests as for any unanswered token) and starts no further step. A line-full refusal and an invalidated lookup are not remembered. Cache of 512 entries: found 60 s, none 15 s, same shape as the symbol cache. A batch keeps its 15 s deadline.
- **Fencing** (amended 2026-10-13 and 2026-10-17, see the last bullets of this section). `SymbolLinkResolver.invalidate()` (a file created, deleted or renamed, a workspace folder change) invalidates symbol answers and file-name answers; `invalidateContent()` (a change or save of a file's contents, which can move a definition but not make a file exist or vanish) invalidates symbol answers only. A symbol lookup started before an invalidation is `pending` (log `parked (invalidated)`; it was `unavailable` until 2026-10-17) and caches nothing, and every settled symbol-based token of a batch whose generation moved is `pending` too. A file lookup is fenced by its own generation instead (below); a file token whose lookup was dropped by a change to the set of files is `pending` as well.
- **Setting.** The file-name lookup is part of `omp.linkCodeSymbols` (one switch for "Desk looks things up for inline code"); off means the same `disabled` answer. The setting's description names both.
- **Path tails and busy repositories (maintainer reports, 2026-10-13).** Two ways a file that Go to File finds stayed plain in a large Unity repository. (1) `host/session-index.ts:579` has a directory part, so it is a path that the page proves only against the session's cwd, and it is not a bare name, so the host never looked for it: the grammar now accepts the trailing part of a path (`parseBareFileName` keeps `name` and a `/`-joined `directory`; no leading separator, drive, `~`, `.` or `..` segment, no space or glob character), the lookup is by reference (`host/session-index.ts`), the glob is `**/[hH]ost/[sS]ession-index.ts` per folder, a hit must end with the whole directory names (`nohost/session-index.ts` does not match), and one, several, none and the cwd rule behave as for a bare name. (2) The `**/*` watcher fired for every change of a file anywhere in the window, and each firing dropped file lookups under way as `unavailable: invalidated`; the page asks again after 5 s and 20 s and then stays quiet for a minute, so while an agent or Unity was writing files the span never linked (the host log showed the three attempts of one span, then silence). Now a change or save of contents does not touch file answers at all, and a file lookup that was running when files were created, deleted or renamed is not discarded: each file it found is checked with `stat` and the answer is delivered uncached when files remain, `unavailable` when none does (never `none`, since a file may have appeared meanwhile). A lookup waiting for a search slot is not dropped either: it searches after the change, so its answer is current. The batch fence applies only to results that needed a symbol lookup. Files that `files.exclude` hides (the Unity project's settings hide `*.meta`, `*.asset`, `*.prefab`, `*.unity`, `*.mat`, `*.dll`) remain unlinked by design, as in Go to File; this amendment was not independently reviewed.
- **Inner workspace folders (maintainer report, 2026-10-16).** A reply naming `Settings.cs:143` stayed plain although Go to File found the file in a Unity project that was open as a second workspace folder, below the repository root the session ran in. The repository root's `files.exclude` hides the project folder, and `symbolRoots` kept only the cwd and the folders that contain it, so the search never reached the project folder and the lookup was `none`. The earlier rule "a folder inside another is searched too" held for the search adapter, but the host never passed such a folder. `symbolRoots` now also returns the open workspace folders inside the cwd; they are no new scope (the cwd contains them) and each is searched with its own `files.exclude` and `search.exclude`. A file both searches find is still one match, so uniqueness and the cwd narrowing are unchanged.
- **Watcher churn and giving up silently (maintainer report, 2026-10-17; amends Fencing).** With a Unity project open, a file-name link (`Session.cs:1353`) and a symbol link (`Session.Copy`) stayed plain although both resolve when asked. A 75 s read-only watch of such a repository, idle, saw eight create/delete events (`.git`, `Temp/`, `Library/`); each one called `invalidate()`, which drops lookups under way as `unavailable: invalidated`, and the page's two retries (5 s, 25 s) and then its minute of rest fit inside such a stream. [INFERENCE: no debug log of the reporter's window exists; this is the mechanism the code shows, not an observed lookup.] Two changes. (1) `FileEventGate` (`src/host/link-watch.ts`) sits between the `**/*` watcher and the resolver. An event is ignored when no lookup's answer can depend on it: its path has a `.git` segment, or every workspace folder that holds the path hides it with that folder's own `files.exclude` / `search.exclude` (the patterns come from `folderExcludeSettings`, the code `workspaceFileNameSource` passes to `findFiles`, and a pattern matching the path or any directory above it hides it). A path that a second, outer folder holds and does not hide is not ignored (that folder's search still returns it). The glob matcher knows `**`, `*`, `?`, `[a-z]`, `[!a-z]` and `{a,b}`; a pattern it does not understand hides nothing, so an event is dropped only when that is certain. Patterns are read once per folder and again after a `files.exclude` / `search.exclude` change or a workspace-folder change. The events that remain are coalesced: one invalidation 250 ms after the last event of a burst, at the latest 2 s after its first (so an endless stream cannot hold invalidation off); a burst with any create, delete or rename is `invalidate()`, one of contents only is `invalidateContent()`. Saves and workspace-folder changes are not delayed. A cached answer therefore stays for up to that long after a change; a click re-checks the file, as before. A lookup under way is still dropped by an invalidation that does arrive: whether an event can affect that one lookup is not cheap to decide, so the semantics are unchanged. (2) Giving up is visible at the default Info level (`src/host/link-give-up.ts`). A name (a code symbol, a file reference, or a token a batch left unanswered) whose lookups end without an answer three times in a row (the first ask and the page's two retries) is reported once, with how long it took and the reasons seen (`invalidated`, `timeout`, `provider not ready`, `queue full`, `error`, `no-answer`, `truncated`, `lookup budget`, `too many batches at once (capped)`, `batch deadline`, `workspace folders changed`, `files changed while the batch ran`), and not again for five minutes; an answer in between starts the count again. The per-lookup lines stay at Debug.
- **Cost.** A span like `obj.run` is a file-name shape and a symbol, so it costs one cached, bounded file search before the symbol query. The one-case extension rule keeps ordinary members (`Foo.Bar`) out.
- **Authority.** The exchange opens nothing new. The lookup runs on host-parsed text, with a pattern from the restricted alphabet, inside folders the host derives from the session; a found target goes through the existing open path; the QuickPick lists only what the host's own lookup returned and the host re-checks the chosen file.

### Per-message reminder (maintainer decision, 2026-10-11)

The system-prompt rules (`file-links`, `code-links`) are followed less reliably deep into a long conversation. A second, per-message reminder reinforces both in one text (`LINK_REMINDER`, 343 characters): files and folders as paths in inline code, code symbols as links.

- **Mechanism.** The host-control `-e` module's `context` handler (OMP's extension `context` event; it runs on every provider request with a deep copy of the messages and returns the messages to send) inserts one `{ role: "user", synthetic: true, attribution: "agent", content: LINK_REMINDER }` message right after every user prompt (`role: "user"`, not `synthetic`, not a history rewrite), unless that message already follows it. The prompt is the same object as before. Nothing is persisted: the session file, Chat and a resumed session never contain the reminder. Same gating as the system prompt: `ctx.mode === "rpc"` and `ctx.agent.kind === "main"`; a subagent, the native TUI and every other mode send their messages untouched. The reminder takes its prompt's timestamp and the text is fixed, so request bytes are identical from one request to the next.
- **Why a separate message.** `emitContext` gives each cloned message its history index, and after the handlers it marks every message that differs from its stored form as per-call; the Anthropic provider never anchors a cache breakpoint on or before the first per-call message. Appending the text to the prompt made the prompt per-call, so a fresh session's first request had no breakpoint behind the system prompt and billed about 11–12k tokens uncached. Inserted messages leave every original message unmarked (alignment is by the carried index, not the position), so only the reminders are per-call and the breakpoint sits on the real prompt.
- **Setting.** `omp.linkReminder` (default off) is read when Desk launches the session and handed to the module as `OMP_VSCODE_LINK_REMINDER` (`1` or `0`); anything but `1` registers no `context` handler. Like other launch values it applies to sessions started or resumed afterwards. The system-prompt rules stay as they are.
- **Variants measured** (installed OMP 18.8.5, claude-opus-5-5, headless `--mode rpc` with the module, a four-file TypeScript fixture with the question "explain this small project ... Twin ... no SessionRoutine", 8 to 16 runs each, run in parallel on the same day; mentions counted with `parseCodeSymbol` over the final reply):

| Variant | runs | linked symbols | plain symbols | plain share | request 1 (input / cache read / cache write) |
|---|---|---|---|---|---|
| no reminder | 8 | 81 | 87 | 52% | 4 / 28557 / 0 (warm) |
| appended to the prompt (the first implementation) | 8 | 101 | 63 | 38% | 11.5k–12.1k / 17169 / 0 |
| persisted custom message (`before_agent_start` `message`) | 8 | 104 | 68 | 40% | 2 / 28557 / 125 (writes it) |
| inserted developer message | 16 | 181 | 140 | 44% | 127 / 28557 / 0 |
| inserted synthetic user message (chosen) | 16 | 212 | 93 | 30% | 127 / 28557 / 0 |
| chosen, final code | 3 | 37 | 17 | 31% | 127 / 17169 / ~11.9k (a fresh cache) |

  File and folder mentions were inline-code paths in every run with and without the reminder (59–63 per 8 runs, 0 bare, 4 once): the question already makes the model name files, and `file-links` already works, so the fixture shows no change for paths. The differences between variants are within run-to-run noise except the appended and inserted-user variants against none; the developer role gave no better rate than appending, the user role the best. Cost: the reminder is about 123 tokens; it follows the breakpoint, so each prompt's first request bills it uncached once (about 120 tokens) and the next request writes it. Over a three-prompt session every request after the first read 29–30k tokens from cache. The persisted variant caches normally but stores the message in every session file and needs Chat to hide its `customType`; the inserted variant stores nothing.

### Internal OMP URLs (maintainer request, 2026-10-17)

A reply names the agents and files of its own session by OMP's internal URLs (`` `agent://DocsReview` ``). They were plain text. This amendment makes four of OMP's schemes links, through the same exchange and the same authority model as file links.

- **Evidence (installed OMP 18.11.1, `src/` of `@oh-my-pi/pi-coding-agent`).** `internal-urls/agent-protocol.ts` resolves `agent://<id>` to `<artifactsDir>/<id>.md` (a nested agent is the dotted id, `Parent.Child`; a `/json-path` suffix selects a value in the output); `registry-helpers.ts` derives the artifacts directory from the session file (the transcript path without `.jsonl`; a nested subagent's files sit in its parent's directory, `<artifactsDir>/Parent/Parent.Child.md`); `history-protocol.ts` names a subagent's transcript by the same id; `artifact-protocol.ts` resolves `artifact://<n>` to the numbered tool-output file; `local-protocol.ts` roots `local://` at `<artifactsDir>/local`; the TUI's own linkable set (`hyperlink-targets.ts`) is `agent artifact history local memory omp rule skill`. No RPC resolves an internal URL (`host-uris.ts` is the reverse direction, OMP asking the host), and `get_subagent_messages` resolves only ids of OMP's subagent registry, which a switched session clears. Desk therefore reads OMP's published layout itself, as it already does for `omp-artifact:`.
- **Candidates (`src/shared/internal-links.ts`, run by page and host).** `parseInternalLink(text)` accepts a whole text that is `agent://<id>`, `history://<id>`, `artifact://<digits>` or `local://<path>`: an id is `[A-Za-z0-9_-]+` joined by dots for a nested agent, at most 256 characters; `agent://` and `history://` may carry a `/json-path` suffix, which opening ignores; a `local://` path has at most 16 segments of letters, digits and `_ @ + ~ % - .`, percent-escapes decoded, and is refused when a segment is `.`, `..`, or holds a Windows-forbidden character, a separator or a drive colon. `detectInternalLinks(text)` finds them in prose (not after a word character, so `xagent://` is not one; the link ends where its grammar ends, so sentence punctuation is prose). The canonical target (`agent://Id`, no suffix) is what the page asks about and what a click sends back.
- **Page.** The existing seams: `textLinks` and `plain` in `Markdown.tsx` for prose, `codeSpan` for a whole inline-code span (checked before the path and symbol rules), and a Markdown link's destination. They render `InternalLink` (`FileLinks.tsx`), which asks `omp:terminal-link-validate` and wraps the characters in an anchor only once the host answers valid, so an unresolved URL is plain text, never a dead link. A click posts `omp:terminal-link-open` with the canonical target and the existing `action` (`os` for `Ctrl+Shift+Click`), without `folders`. There is no new message and no new field.
- **Host (`src/host/internal-links.ts`, tested without VS Code).** `extension.ts` routes a request whose target `parseInternalLink` accepts to `handleInternalLink` before `handleTerminalLink`, with the same document/session currency check. It re-parses the target and resolves it against this conversation only:
  - `agent://<id>`: the detail tab when the live Chat session's roster holds the id (`RpcSession.subagentKnown`, the rule the child-transcript read already uses); otherwise the agent's output `<id>.md` as a read-only document of the `omp-session-file:` scheme (`src/wiring/session-file-documents.ts`) when it exists; otherwise the detail tab when a held task result names the agent (`"reference"`); otherwise nothing.
  - `history://<id>`: the detail tab for an agent the live session knows; nothing otherwise (a stopped agent's transcript file is not a document Desk shows).
  - `artifact://<n>`: the existing `omp-artifact:` document through `findArtifact`.
  - `local://<path>`: `<artifactsDir>/local/<path>` as an `omp-session-file:` document.
  - `Ctrl+Shift+Click` shows the file in File Explorer (`revealInOs`); a detail tab has no file, so it opens plain; other modifiers are a plain open. An unresolved activation shows a notice naming what was missing.
- **Authority.** The page never names a path. The artifacts directory comes from the conversation's session file on the host. `host/session-file-lookup.ts` accepts only a grammar-valid id or path, builds the path itself, takes only a regular file that `lstat` does not report as a link and whose real path is inside the real directory it looked in, reads a bounded size, and the `omp-session-file:` provider re-runs the same lookup on every read, as `omp-artifact:` does. A forged validation reply could create only a link the open path would then refuse.
- **Not done, and why.** `skill://` (OMP resolves it from the skills active in its process; there is no RPC, and Desk only knows a path from a read result), `memory://`, `rule://`, `omp://` (virtual documents or discovery inside OMP, no RPC), `pr://` and `issue://` (remote content through `gh`; Desk would have to run it), a bare `history://` (an index), `history://current/full`, `/json-path` extraction (the suffix is ignored; the whole output opens), and `:N` line selectors. They stay plain text.

### Namespaces, inherited members and Ctrl+N (maintainer request, 2026-10-17)

- **Why `Ctrl+N` found nothing for `Type.Member`.** `ompDesk.searchSymbolFromChat` sent `#Type.Member` to Quick Open. In VS Code 1.142 (`workbench.desktop.main.js`, the `#` quick access's `doGetSymbolPicks`) the whole query text is given to the workspace symbol providers, but each returned symbol is then scored with the fuzzy matcher against its bare `name` only (`Member`), so a query with a dot never scores and every result is dropped. A query with a space (`Member Type`) is split: the first word goes to the providers and the rest is matched against the container and path shown in the row. The chat links never had this problem because they ask the provider for the last segment and match the container themselves.
- **`Ctrl+N` now asks the same lookup as a link** (`src/host/symbol-search.ts`, `SymbolLinkResolver.find`). A selection that parses as a qualified symbol (two or more segments) is looked up in the folders of the front Chat's session (the same scope as a link). One definition opens at its position (through the ordinary file opener); several are chosen from in a Quick Pick (name, container, file and line); none, or a lookup that cannot answer (provider not ready, failed, timed out), falls back to Quick Open with `#<last segment>`, which lists every definition of the name as a click on an ambiguous link does. An unqualified selection, and text that is not a code symbol, go to Quick Open as typed, as before; an empty selection still opens the empty symbol search. The lookup shares the resolver's provider slots, timeouts and invalidation, and caches nothing (a search is a deliberate one-off, and a stale answer would be worse than a second provider call).
- **Namespaces before the type.** `parseCodeSymbol` accepts up to four segments of any spelling, and up to eight when everything before the last two segments starts with an uppercase letter (a namespace path such as `OmpDesk.Core.Catalog.Profile.Load`). In matching, a qualifier that no entry's container ends with is retried with leading PascalCase segments dropped, always keeping the segment next to the member: `OmpDesk.Core.Catalog.Profile.Load` is looked up as written, then as `Core.Catalog.Profile.Load`, `Catalog.Profile.Load` and `Profile.Load`. A provider that names no namespaces (Roslyn: `in Catalog.Profile`) matches a shortened form. A shortened qualifier applies only to a container with fewer segments than the one written, so a container that carries its own namespaces (`OmpDesk.Sessions.SessionData`) still contradicts a wrong namespace, and a lower-case segment is never dropped.
- **Inherited members (evidence).** A member declared in a base class is reported with the base class as its container, so `Derived.Member` finds no entry whose container ends in `Derived`. VS Code has a type hierarchy API (`vscode.prepareTypeHierarchy`, `vscode.provideSupertypes`), and the C# language server serves it: in the installed C# extension 2.160.4 (Roslyn language server), the server initializes with `typeHierarchyProvider: true`; run read-only and standalone (no VS Code window) on a throwaway C# file, `textDocument/prepareTypeHierarchy` at a class name returned an item for the class (name, kind Class, namespace in `detail`, its file and ranges), and `typeHierarchy/supertypes` returned the direct base class instantiated as written (`RecordBase<string, Profile>`) with the file and range of that base type's declaration. The type hierarchy items carry no members: a member is still found by the workspace symbol search.
- **Inherited members (rule).** Only for a qualified name whose direct container match found nothing, and only when the provider offers a type hierarchy: the qualifier's type is looked up (one more workspace symbol query for the type's name; the entries must be type-like, not enums, with a position, inside the folders, and exactly one definition), its position is prepared, and its supertypes are asked level by level (breadth first, at most 8 levels and 24 supertype calls, inside the lookup's time budget; every call has the slots and the per-call timeout of a symbol query). A member entry counts when its container's own name is the bare name of a type of the chain (`RecordBase<TValue, TSelf>` is the type the hierarchy calls `RecordBase<string, Profile>`), narrowed by the type's declaration range when several types of that name exist. The nearest level that declares the member decides, so an override is found where it is written; one definition at that level is the link, several are ambiguous as ever. A hierarchy that is too deep or too wide, that fails or that does not answer is a lookup that could not decide (`unavailable` or `pending`, never cached), not a miss. Without a type hierarchy, or when the type is not unique, the member stays unresolved: there is no guess from the member's name alone, because a wrong link is worse than plain code.
- **Not verified here.** The C# behavior was verified against the language server alone; no VS Code window with a C# project was available to this work, so the end-to-end link in a window is covered by unit tests with Roslyn-shaped entries and fake hierarchies.

## Alternatives

- **Resolve in the OMP process.** OMP has its own `lsp` tool, but the Chat page is rendered by the host window, not by OMP, and ADR-0013 rejected a reverse bridge from OMP to VS Code's providers. Resolution here serves only the transcript's links and returns nothing to OMP.
- **`vscode.executeDefinitionProvider` from a document position.** There is no document position for a span in a chat reply; it would need a synthetic source file.
- **Own index (ripgrep for `class Name`).** Language-specific, wrong for partial classes and overloads, and duplicates what the language server already knows.
- **Picking one result when ambiguous (most members, first path).** Explicitly rejected by the maintainer: a wrong link is worse than plain code. An ambiguous symbol links to the symbol search instead (Ambiguous symbols).
- **Treating a possibly capped result as unavailable.** Rejected: the cap cannot be observed through the API (a full list and a short list are indistinguishable from "that is everything"), so a threshold would also disable the common, correct case of a unique class in a large project. The limit is disclosed instead.
- **A new message family outside `terminal-link-*`.** The terminal-link exchange already has the panel and bridge plumbing, the document-currency checks and the cwd binding; a sibling message reuses all of it. The cost is the explicit integration list above.

## Risks and Open Questions

- Provider caps and ranking (see Guarantee and its limit). A common member name (`Start`) in a large C# project can have its other declarations cut off; most such names are ambiguous in practice and then also link nothing.
- Generics and overloads: `Foo<T>` and `Foo` are two types in C#; a provider that strips type arguments reports both as `Foo`: ambiguous, correctly. A generic method with overloads is ambiguous. A dotted `Type.Member` whose member is inherited resolves through the provider's type hierarchy where the provider has one (Inherited members), and to nothing otherwise.
- A TypeScript server starts lazily; until a TypeScript or JavaScript file is open it may answer no workspace symbols (an unknown name then costs one extra query, five seconds later).
- Providers that return `SymbolInformation` locations without a range cannot give a definition line; the link opens the file at its top.
- C# was not available in the isolated test environment; its behavior rests on the provider contract and on unit tests with Roslyn-shaped entries.
