# Build OMP Desk from native-session MVP to comparison-level UX

> Ownership rules follow [ADR-0039](../decisions/0039-refuse-only-on-a-verified-live-writer-the-extension-owns.md): unknown sessions/claims are unowned, verified legacy writers are Running with one-step stop-and-continue, and no explicit release state remains. Native capability/security integrity is unaffected.

> Amended by [ADR-0038](../decisions/0038-host-chat-over-rpc-ui-on-a-broker-pipe-child.md) and its [RPC-UI chat and Sessions design](2026-09-29-rpc-ui-chat-and-sessions.md): the Collab guest, Agents Hub, raw recorder and Chat | Terminal rows of this design are replaced by an `omp --mode rpc-ui` chat; remaining rows are unaffected.
> Narrowed by the implemented [compact-footer design](2026-10-01-compact-chat-footer.md): model/thinking remain as lazy host-readback pickers; notices, header, configuration/settings/tool inventory and usage panels are removed. Native provider login is command-only. Older settings/usage observations and rows below are historical at their original baseline, not current product surfaces.

## Problem

There is no extension implementation yet. Users need a GUI for ordinary OMP work, durable session discovery/restoration, and a switch to the **same live native OMP TUI process** in VS Code's integrated terminal. They also want a product functionally comparable to an established VS Code extension for the Pi agent (Pi Code 0.73.0, referred to below as the comparison extension), while using OMP as the authoritative runtime rather than copying Pi SDK internals. The primary correctness risk is opening two writers for one session or losing an interactive request during GUI/terminal/reload transitions.

## Goals and Non-goals

- **First deliverable:** a GUI-first chat attached as a full-control guest to an OMP host launched in a hidden native terminal; safe local relay; streamed transcript, tools, `ask`/approval, Agent Hub, model/thinking controls, and session history/restoration. The user can reveal the original TUI during an active turn without starting a second OMP process.
- **End deliverable:** user-visible VS Code capabilities comparable with the current (not retired desktop) features of the comparison extension, as listed in its README, contributed commands/settings and documentation index: launcher/editor tabs, settings/auth, tool and model controls, attachments and mentions, diffs/undo/checkpoints, queue/steer/Plan/ToDo, Hub/subagents, LSP/MCP/Claude inputs, diagnostics, usage and notifications, packaging. Use native OMP equivalents when their semantics match; implement missing VS Code affordances rather than silently dropping a comparison feature.
- The first MVP runs against the user's currently installed, already authenticated OMP. No numeric runtime release is pinned: the extension uses the `omp` that `PATH` resolves, launched PID-safely as a single process, with the launcher-directory file treated as a fallback so a stale launcher cannot win over the current installation, and compatibility is repaired when an error surfaces ([ADR-0011](../decisions/0011-use-installed-omp-without-version-gate.md)). The user explicitly accepts that an OMP update can break the extension until it is repaired. The extension never installs, bundles, downloads or upgrades an agent; the build keeps `@oh-my-pi/pi-wire` at a fixed version purely as the reproducible protocol grammar the guest is compiled against. GUI onboarding and a complete schema-driven settings editor come after its functional core; these and comparison-level settings/auth still belong to the end deliverable.
- The comparison extension is UI/UX evidence, not an OMP runtime API or source to import wholesale. Its retired Electron host is not a current VS Code parity target. Pi-specific model patch tables, package-install commands, and provider branding are not copied verbatim; equivalent OMP-backed user behavior is the target.
- No hosted Collab relay, terminal screen scraping, simulated TUI, concurrent writer, automatic approval, or claim that restored history implies survival of the former process.

## Current State

At acceptance time only documentation existed in this repository; the extension implementation now exists under `src/` and is described as implemented source in [Current architecture](../architecture.md), which does not imply that this design's acceptance gates have run. [ADR-0002](../decisions/0002-local-collab-gui-native-omp.md) selects a loopback Collab guest with native TUI host. OMP Collab documents a browser guest, writable prompt/Hub/UI responses, a local *development* relay, and private host discovery (`docs/collab.md:68-86,124-163,172-184` in the OMP repository). The OMP extension API exposes host model/thinking controls and read-only session history (`packages/coding-agent/src/extensibility/extensions/types.ts:1434-1464,428-452`). VS Code supports initially hidden terminals but does not promise restoring hidden terminals when a workspace reopens. Citations to OMP sources below were read in the OMP source checkout as it stood at acceptance (the 18.2.11 baseline); since [ADR-0011](../decisions/0011-use-installed-omp-without-version-gate.md) targets whichever OMP release the user has installed, those paths, line ranges and surfaces must be re-read in that installed package before they are relied on. None of the combined Webview, relay, ownership, or approval flows has yet been proven end to end. Launcher resolution already follows the no-pin policy in this design — `PATH` first, launcher directory last, `omp --version` as a diagnostic only — while [ADR-0011](../decisions/0011-use-installed-omp-without-version-gate.md) is accepted after its corrective re-review, which is a design decision only.

## Proposed Design

### Ownership and runtime boundaries

- **VS Code extension host:** creates/reveals a native OMP terminal, coordinates a relay sidecar whose endpoint survives extension-host reload, keeps a per-workspace index of session file + normalized working directory + profile/session directory + UI tab identity, and owns sidebar/editor panel restoration. It resolves the `omp` the user currently has installed, treats `PATH` as authoritative over a stale launcher in the official launcher directory, launches it PID-safely as a single process, and pins the wire package the guest is compiled against rather than bundling a second agent; no numeric runtime release is pinned ([ADR-0011](../decisions/0011-use-installed-omp-without-version-gate.md)). It does not infer OMP process identity from a persistent PID alone.
- **OMP host:** launched once per active session in its original interactive mode with a per-run config overlay selecting the local relay and full-control Collab autostart. Its session file/tree, agent, tools, model, approvals, and Agent Hub remain authoritative. An explicitly loaded narrow host extension handles operations unavailable to Collab guests (model/thinking and any proven missing host action), bound to the process/session generation; it does not replace the native TUI.
- **Relay:** a supervised local WebSocket sidecar for the existing encrypted Collab wire, bound explicitly to loopback. The host, guest, and VS Code extension can reconnect to the **same stable endpoint** across extension-host reload; record its rendezvous under restricted local state, health-check before reuse, and stop it after a bounded idle period once no hosts remain. Review and harden the source-available development relay semantics; it is not itself a production dependency. It serves no public UI or external fallback. Avoid logging or persisting write-capability links. Confirm readiness before launching a host configured with its URL. If a live host loses this endpoint, reconcile or explicitly rotate its room before replacing the relay; opening an unrelated ephemeral port does not reconnect that host.
- **GUI:** a VS Code editor Webview based on the existing Collab browser guest behavior/protocol, not a second OMP process. Its link is delivered only to the intended panel in memory, via an extension-owned typed message boundary. Browser WebCrypto, CSP, resource URIs and WebSocket connectivity must be proven in the actual Webview before choosing whether to adapt Collab Web components or embed its static bundle. The sidebar owns new/open/history/Hub entry points. Unknown OMP tools get a generic event card; optional specialized renderers do not block progress.
- **Host-only controls:** use a separately authenticated local host-extension channel for model/thinking; require a read-back from the *host*, not guest-local `/settings`. Show a credential-redacted read-only configuration snapshot scoped to the same profile/cwd/overlay. Later extend from OMP machine-readable metadata for settings editing; do not clone a fixed OMP schema into the Webview.

### Session identity and transitions

The per-session state is `saved` (file materialized, no known host), `claiming`, `starting`, `live` (host instance + room generation, GUI guest optional, terminal hidden or shown), `reconciling`, or `failed`. An imported OMP-history file retains its provenance but follows those same interactive states; the subsequent [interactive history design](2026-09-25-interactive-history-resume.md) replaces this design's former read-only restriction. Terminal visibility is not a new session. Do not use `--continue`; resume by exact file path with the matching profile/cwd/session directory. New unsaved empty chats are UI drafts until OMP materializes a file. A stream/interrupted turn must not be presented as safely replayable work.

Before opening or resuming a host, atomically acquire an exclusive local claim keyed by canonical session path, or a reserved extension session ID before any file exists. The claim records two identities: a random owner generation, which identifies the session as this workspace's own across reloads, and a per-extension-host holder lease that is never persisted and is what excludes a second window, because two windows read the same persisted row and present the same generation; the claim is released only after the host is confirmed stopped by that same holder and generation, and another live holder of the same generation is a conflict, not a takeover. When a draft first materializes a path, acquire its canonical-path claim **before** releasing the draft claim; any collision remains a conflict while the original host stays alive. On collision, check the live terminal, authenticated OMP registry, and recorded owner; neither an old timestamp nor a missing registry row proves a running host is gone, and a launch that matched no room is never declared absent however its pid ends. Unknown ownership remains a visible conflict, never a second writer. Ownership exclusion is extension-scoped: the claim and its holder lease keep this extension's own windows apart, and an external OMP process can be neither observed nor excluded. The user decided on 2026-09-24 to accept that as a known limitation rather than solve it — the extension guarantees only that it does not start a second writer, and avoiding two OMP processes over one session is the user's responsibility — so no per-action confirmation or veto is added, and the accepted consequence is that extension-only evidence cannot prove no foreign writer exists: a session this extension judges free may still be written by such a process, so resuming it or deleting it can collide with it, including a deletion that removes a file the foreign process is actively writing. This coordinates extension windows only; an externally launched OMP process is not under its lock and is not detected or reconciled by it at all — the user accepted that on 2026-09-24 as the limitation recorded above, with responsibility for not running concurrent copies on the user, so the design does not promise detection it cannot perform.

On Webview reload, authenticate a new guest to the **existing** live room generation and rebuild from the host snapshot. On window reload/restart, recover the atomic claim and stable relay first, then reconcile extension-known terminals and OMP's authenticated local Collab registry; only after proving no extension-owned writer remains may the extension take a new claim and start `omp --resume <exact path>`. This applies to imported OMP-history files as well as extension-created files under [ADR-0018](../decisions/0018-resume-imported-history-under-extension-claims.md): the former read-only-only restriction in this design was superseded. An external OMP process may still write that file; excluding it is the user's responsibility. Persist a launch-pending attempt before spawning any new host so a crash between spawn and recorded outcome cannot masquerade as no earlier extension writer. Missing or ambiguous extension owner identity remains a surfaced conflict, never grounds for a second extension writer. Room generations rotate on OMP session switches; stale links/approval responses/host-control commands are rejected. Persist pointers and UI metadata, not relay control links or credentials. A closed panel need not kill an active native terminal; explicit close/stop semantics must account for running tools before shutdown.

For parity with the comparison extension, each chat editor panel owns one tab identity and draft/attachment state. Restoring multiple panels is independent: a failed restore does not discard successful ones, duplicate claims of the same writable OMP session are rejected, and the active tab is recovered deterministically. File change tracking and workspace undo must remain separate from OMP conversation rewind; never overwrite unrelated user edits based on a transcript-only checkpoint.

### Parity tracks after the first deliverable

1. **Conversation UX:** queue/follow-up/steer mapping to OMP's authoritative queue; images/file attachments and workspace `@` suggestions; skills and available commands; per-session Plan Mode and native ToDo projection; rename, history deletion, and multi-tab editing. OMP's native tool catalogue may be shown and active names deliberately copied, but GUI per-chat selection, transfer/Paste and project defaults are **unavailable under OMP's native contract as verified so far**: [ADR-0009](../decisions/0009-read-only-native-tools-until-atomic-selection.md) and [ADR-0008](../decisions/0008-native-tool-selection-at-session-start.md) recorded that evidence against 18.2.11 and have not been re-verified against the release currently installed, and the user there rejected the unsafe live and inexact startup alternatives. Preserve OMP state rather than create a competing agent queue or task store; deleting a history entry must reconcile any live host and associated diagnostics first.
2. **Safety/reversibility:** observe OMP file mutations, show inline and VS Code native diffs, then add per-file Undo/Redo and checkpoint restoration with file preimage and user-edit conflict checks. OMP transcript rewind alone does not prove filesystem rollback. Exclude duplicate writers among this extension's windows/processes; independent OMP processes remain outside its guarantee.
3. **Native integrations:** model/auth/settings management including GUI onboarding and safe secret scope; bundled web search/content fetching and MCP access through OMP's existing tools/configuration where equivalent. Claude resources are **not ported**: the user decided on 2026-09-24 that installed 18.3.0's own capability discovery — context files (`CLAUDE.md` alongside `AGENTS.md`/`GEMINI.md`), skills, plugins/extensions, MCP servers and agents, with the `claude` provider as an opt-in foreign source — remains the owner, and that the extension ships no Claude adapter, resource inventory or capability-endpoint UI; adding either would need a new user decision. VS Code language-provider tools are **native OMP `lsp` only** (user decision, 2026-09-24): the proposed bridge that would have queried VS Code's own providers over authenticated reverse RPC was rejected, its source was removed in a clean cutover, and no second language route exists today. The user reopened the bridge on 2026-09-24 as **planned future work**, not as a current capability: it stays unimplemented while that work is planned, and building it requires a revised security design closing the three findings recorded against the removed code (a shared mutable workspace root that let one native session read another session's editor data; out-of-root workspace-symbol content reaching normalized results; and removing a workspace folder not revoking an existing attachment), explicit consent with Collab disclosure of the editor data a query would return, independent security review, and real-window acceptance; Agent Hub/subagent status, partial results and worktree review without replacing OMP task semantics.
   The read-only [active-session Tools view](2026-10-08-active-session-tools-view.md) (user decision, 2026-10-08) narrowly amends the no-inventory restriction: it presents OMP-reported skill commands and tool descriptors without taking over discovery, importing resources, managing endpoints or changing tool selection.
4. **Diagnostics and polish:** raw unredacted recording and viewer only with explicit opt-in, bounded retention and deletion; context/timing/cost and provider-account usage with provenance; startup/performance diagnostics and prewarm only when they provide a real measured benefit; cache controls when OMP exposes them; notifications, appearance and keyboard UX. Bundle and install a VSIX without depending on the OMP source checkout or any comparison-extension sources at runtime.

Each comparison feature must receive a verified result: OMP-native equivalent, extension implementation, or a documented unsupported dependency that is resolved before declaring functional comparison. Provider-specific numbers are not fabricated. The packaging boundary must exclude credentials, local control links, development-only files and any comparison-extension sources.

## Alternatives

- The accepted [ADR-0002](../decisions/0002-local-collab-gui-native-omp.md) compares hosted Collab and a custom GUI bridge. `rpc-ui` plus a pseudo-terminal cannot display the native TUI of the same process. `--resume` creates another process and is restoration, not a live switch.
- Copying the comparison extension wholesale retains its Pi SDK runtime ownership and session format and conflicts with OMP's native host. Only bounded UI behaviors/components may be adapted where license and protocol permit.

## Risks and Open Questions

- Webview WebCrypto/CSP and localhost WebSocket access, bundling the browser guest, local relay binding and control-link leakage are unproven. The development relay gives a localhost URL but does not explicitly bind its server to loopback and does not serve static UI. A relay restarted on a different endpoint does not revive an existing native OMP host; the stable sidecar and atomic session claim must be tested through extension-host reload.
- OMP Collab wire and browser client are internal packages rather than a stable extension SDK. [ADR-0011](../decisions/0011-use-installed-omp-without-version-gate.md) (superseded only for imported-history behavior by [ADR-0018](../decisions/0018-resume-imported-history-under-extension-claims.md)) retains the no-numeric-gate runtime policy: the guest uses a fixed `@oh-my-pi/pi-wire` grammar, consumes metadata-only `welcome` plus ordered `snapshot-chunk` frames and answers `ui-request`/`ui-request-end` with `ui-response`. Matching `hello` protocol **numbers** do not prove behavioral compatibility; mismatches must surface visibly and be repaired. Native APIs, catalogue, hooks, launcher/PID and registry fields require verification against the installed OMP release; OMP 18.3.0 deprecated the model-facing `hub` tool in favor of `wait`/`write`/`proc://`, while Collab agent frames remain. Native guest permissions cover `select`/`editor` but not every extension `input` path; unsupported prompts require explicit safe handling.
- OMP host-control API covers model/thinking but a secure channel, exact applied settings/provenance, concurrent sessions and live-owner reconciliation remain to be designed and verified. No user-data migration should run before a proven session mapping.
- [ADR-0004](../decisions/0004-best-effort-host-model-transitions.md) records the user's explicit acceptance of a race between GUI model/thinking changes and a simultaneous native OMP session transition. Implement these host controls with the stock OMP extension API, pre-dispatch stale checks and actual post-call readback; do not modify OMP core or claim atomicity across the transition. The IPC secret, idempotence and session single-writer gates remain strict.
- Planned, not implemented: the VS Code language-provider bridge. The user reopened it on 2026-09-24 as future work after rejecting its first implementation, whose source was removed. Enabling it is gated on a revised security design that closes the three findings the independent security review recorded against that code — LSP-01, one process-wide adapter rebound to each newly attached host, so a request from a still-attached session resolved against another session's workspace root and could return that session's editor data; LSP-02, workspace-symbol results whose location fell outside the authorized root still contributing name, kind and container to normalized results; and LSP-03, removing a workspace folder without any workspace-folder listener, so an attached host kept querying a folder the window no longer contains — plus explicit consent with Collab disclosure of returned editor data, independent security review, and real-window acceptance before it is enabled. [ADR-0013](../decisions/0013-authenticated-reverse-rpc-for-vscode-language-providers.md) and the [bridge design](2026-09-24-vscode-language-provider-bridge.md) stay `rejected` history; the current release remains native `lsp` only.
- Comparison parity includes Pi-specific subscription metrics and extensions. Prefer an accurately labelled OMP equivalent; missing provider APIs may require additional OMP contracts, not fake values.

## Rollout and Verification

User delegated technical decisions and requested full orchestration. Use medium coherent batches, no manual pause at a green boundary. Coverage-first (no mandatory RED phase). One separate architect reviews this design before implementation; fixed final security/session review after implementation. Each green phase is verified and committed with a focused commit; subagents edit disjoint packages and skip build/test/lint/format. Every gate below runs against the OMP release currently installed for the user ([ADR-0011](../decisions/0011-use-installed-omp-without-version-gate.md)); recorded evidence must name the release it was gathered against, because evidence from a different release does not transfer silently.

1. **Feasibility gate:** build the smallest experimental VS Code extension shell, host adapter and Webview needed to demonstrate actual native OMP in a hidden VS Code terminal, explicitly loopback-bound relay, browser guest in a Webview, one streamed prompt, `ask` and tool approval resolved in GUI, Hub observation/action, and reveal of the same live host during a turn and pending dialog. Verify one settlement, cancellation and stale/duplicate response rejection, room-generation rotation, atomic owner conflict/no second writer, and no external relay connection. Prove host model **and thinking** changes, read back the host-scoped credential-redacted settings, and reject host-control commands against an obsolete session. Reload the extension host while OMP stays live and reconnect to the same relay endpoint; crash the relay while a host is live and confirm recovery on the same endpoint or an explicit blocked state with no replacement writer. If the gate fails, repair the same local design or record a new ADR rather than substituting hosted Collab or TUI emulation.
2. **MVP infrastructure:** turn the successful bounded experiment into production extension/package scaffolding, typed host-Webview messages, supervised relay, host-only controls, session index/owner reconciliation and serializer. Run typecheck/build and targeted ownership/protocol checks; restart/reload actual VS Code, preserving successful sessions, drafts and single writer.
3. **MVP UX:** launcher/editor panels, chat/progress/tool/approval/Hub/model/basic settings UI. Smoke the installed VSIX in an isolated VS Code profile on Windows, including hidden-to-shown TUI while streaming and restoration after full restart. Screen inspection uses only the user's scoped permission for this test VS Code window.
4. **Comparison-level UX and safety:** implement the parity tracks above in disjoint subpackages; after each coherent slice run affected targeted checks and a changed-path smoke. Add permanent tests only for observable lifecycle, safety, concurrency and error boundaries that could plausibly regress. Keep the comparison behavior matrix live until every current user-facing feature is accounted for.
5. **Final acceptance:** build/typecheck, targeted tests, full suite once, VSIX contents/install smoke, real GUI+terminal scenario, session restart and safety/Hub parity. Independent reviewer evaluates a fixed final diff for correctness/security. Resolve material findings and rerun affected gates; update implemented architecture and mark this design implemented only after evidence.

The test matrix covers: relay room/write-link isolation, loopback and reload reconnect; response once/cancel/stale generation; atomic cross-window claim, session owner conflict and per-panel partial restore; queued prompt/steer settlement; model/thinking host readback and secret redaction; file undo user-edit conflicts; subagent lifecycle and worktree ownership; Webview accessibility/visible interactive state; and packaging without development secrets. No test is added merely to mirror implementation wiring.

## Architecture Review

- Reviewer: architect
- Outcome: reviewed; accepted after resolving material ownership, relay-lifetime, feasibility-gate and parity-inventory findings.
- Notes: The independent architect required an atomic cross-window claim before host launch; a stable relay across reload; the complete ADR-0002 feasibility predicates; and explicit comparison parity for web/content tools, startup/performance, history deletion, raw viewer and tool-selection transfer/defaults. These constraints are now recorded above. Acceptance is a design decision, not successful runtime evidence.

Subsequent accepted decisions ADR-0008 and ADR-0009 supersede the earlier proposed mutation and preset tracks and were recorded against OMP 18.2.11; [ADR-0010](../decisions/0010-use-verified-installed-omp-1830.md) proposed pinning a single exact release but was replaced before adoption by [ADR-0011](../decisions/0011-use-installed-omp-without-version-gate.md), which runs whichever OMP is installed, so their native prerequisites remain unsupported until they are re-verified against the release actually in use rather than silently counted as implemented.
