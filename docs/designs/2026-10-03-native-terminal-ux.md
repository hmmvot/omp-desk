# Stable native terminal interaction and editor-owned session actions

## Problem

The installed extension duplicates Chat/Terminal mode and normal live status above the content, loses terminal scrollback on health checks, equates input ownership with DOM focus, lacks reliable editor reactivation focus and multiline input, and does not reliably expose native completion desktop notifications. The maintainer requests all nine repairs and isolated installed-window proof; no primary installation or commit is authorized.

## Goals and Non-goals

- Remove both managed-session header rows in Chat and Terminal. Show the opposite-mode action in the active OMP editor title navigation and Copy Screen in its overflow. Keep only abnormal state notices in the pane.
- Preserve configured terminal/editor font priority, then common and installed Nerd Font families and the existing Codicon symbol face, without changing user font configuration.
- Keep healthy probes and ordinary focus changes non-destructive: preserve scrollback, selection and user scroll position; follow output only when already at the bottom.
- Paint the fitted-grid remainder with terminal background, hide native scrollbar chrome and retain the custom auto-hiding scrollbar.
- Send the multiline sequence actually supported by installed OMP for Shift+Enter.
- Keep authorized ownership independent of DOM focus, retaining generation and writer fencing. Restore focus on actual editor activation and mode entry without timer-driven focus stealing.
- Establish the native completion failure from real causal observations, fix its source, and prove desktop toasts with an inactive tab and an unfocused isolated window.
- Do not change lifecycle/mode replacement semantics, invent private OMP APIs, touch the user's normal window/profile, change a real user workspace, commit, or install in the primary profile. Separate folder-shell header affordances remain unchanged.

## Baseline and Implementation State

Before this package, ten-second/focus attach probes reset xterm and blur released ownership; a fixed initial focus signal missed later editor activation, and raw font updates discarded fallbacks. The maintainer's independent installed-window acceptance retained the header/title, glyph, automatic tab-focus, multiline, 25-second scroll-preservation and native-toast repairs, but found a black strip below the status line. Diagnostic10 identified the bundled xterm viewport's literal black paint extending 12 pixels below the fitted rows despite correct theme tokens. The shared viewport now inherits the terminal background. Final12 passed typecheck, the full suite (1188 passed, one skipped), build, VSIX packaging and exact isolated installation; Final15 then proved the correction on the same live native TUI with whole-pane and 3x bottom captures. No lifecycle, authentication, fitting or OMP-owned alternate-screen policy changed.

## Applied Design

### Editor actions and copy

One actual active OMP editor resolver supplies title context and title/Stop/focus handlers, including splits. Explicit Switch to Chat/Terminal commands reuse the existing gated mode switch and its refusal reason. Copy Screen is a host-user-command-triggered, single-use superseding request with a deadline, fenced to the current panel/document, native mode and renderer stream generation. Controlling and passive panes and acknowledged bridge read replies are admitted without mutation authority. The UTF-8 serialized reply envelope is capped at 240 KiB; oversized copies are refused with fixed feedback, never silently truncated. The host writes the VS Code clipboard and reports transient success. The managed header is removed; the folder-shell header remains.

### Stable transport and ownership

Initial attach and actual discontinuity/gap recovery obtain snapshots. The existing opaque generation becomes a fresh random identity for each pipeline, not a stable PTY process token; broker identity stays unchanged. A separate probe carries generation and consumed sequence. Mismatch or an impossible higher sequence obtains recovery; normal in-flight output does not. Otherwise ordered status lets the page detect a real gap without advancing across missing bytes. Status/ownership frames preserve pending recovery; explicit snapshot-follows/failed/status outcomes distinguish recovery answers. New attached streams are adopted only by snapshot-follows state, with reset deferred to the snapshot. Probe timeouts disable stale input without claiming disconnection; host loss is established by the authenticated bridge, and focus no longer attaches. Broker owner/disconnect events are authoritative; claims are never optimistic and newer owner observations fence delayed claim results. Eligible unowned acquisition uses takeover=false; explicit real focus intent alone allows takeover. Blur retains ownership; hidden/read-only/disconnected owners are released. Input/resize eligibility excludes DOM focus; seen/notification attention still require actual focus.

Panel acknowledgement is idempotent at the host dispatcher: a valid repeated ACK retains authority but does not re-publish the same status offer. The first ACK still publishes readiness, new generations still fence old writers, and the guest may repeat an ACK after a lost delivery. This removes the observed offer/ACK feedback storm without discarding status refreshes or changing bridge-connection acknowledgement.

### Closed-editor reopening

Closing an editor retires its document and bridge credentials but leaves the managed runtime, native watch, Chat conversation and running intent intact. A replacement editor has a new immutable slot. When the retained conversation record moves to it, only the old terminal presentation is disposed; binding the new panel registers a fresh pipeline/frontend against the same live native handle. This also covers a runtime restored before its previously closed editor is reopened. Chat reattaches its retained conversation to the new page without restarting the RPC session.

Native OMP can allocate a session path before writing a zero-turn transcript. Repeated observations of the same pending runtime/file/session identity do not restart binding or refresh the launcher; the existing retry promotes the file when it materializes and is claimable. This prevents idle native polling from starving an asynchronous Sessions projection that is checking a closed Chat writer. Changed binding failures remain diagnostic.

Concurrent Sessions/Open checks of the same exact Chat writer share one in-flight authenticated RPC proof rather than exhausting the broker's bounded client slots while awaiting kernel identity. Sharing is fenced by the client, slot, full recorded broker/child identity and kernel reader; completed or failed proofs are never cached. Native proof behavior and the existing positive-ownership policy are unchanged.

An unanswered terminal attach/probe is a response timeout, not proof that the extension host disconnected. The pane keeps its copyable screen, disables stale input and shows a response warning. The host-connection-lost message requires an established authenticated bridge connection to have dropped; reconnecting it clears that condition independently of terminal responses.

### Rendering and input

Compose one font stack for initial appearance and subsequent settings messages: configured terminal/editor family first, common Nerd/symbol faces, installed Nerd Font families, existing Codicon, then monospace. Installed-family discovery is bounded and cached without user configuration changes. Existing Codicon covers U+EC19 without a new font/dependency. Paint the remainder with resolved terminal background and hide native scrollbar chrome while retaining xterm's custom auto-hiding scrollbar. Managed native panes send OMP's modified Shift+Enter encoding (`ESC [ 13 ; 2 u`), suppressing the default submit byte; folder shells remain unchanged. Host activation tokens latch before app mounting and are emitted on actual activation/mode entry/readiness. Consume once with renderer/native/document-focus guards, or on next focus while pending; hidden/blur clears pending intent. Repeated models and probes never focus. A genuine click conveys takeover intent even when the terminal textarea already has DOM focus.

The xterm viewport is absolutely inset through the available terminal height, while its rendered row grid ends at a whole-cell boundary. Its bundled black background must inherit the themed `.xterm` background so the uncovered remainder matches the terminal in both native and folder-shell panes; fitting, row geometry and theme resolution remain unchanged.

### Clickable local file references (2026-10-04)

Native and folder-shell panes share xterm's OSC 8 handler and a plain-path provider.
Relative paths resolve against the host's current session/folder cwd; absolute Windows
paths and `:line[:column]` suffixes are supported. Wrapped links use terminal cell
coordinates, including wide-character prefixes. Plain paths become hover links only
after a host stat proves an existing regular file. Activation revalidates the file and
opens it with `vscode.open` (`preview:false` plus a zero-based selection; see below).
Hover retains xterm's underline and pointer; this webview uses plain click with a
“Click to open” hint instead of duplicating VS Code's configurable modifier handling.

#### Link stability and binary targets (2026-10-06)

Two installed-window defects shared this feature. (1) Hovering a path in the TUI's
inline code flipped the cursor between pointer and I-beam and a click did nothing: xterm
drops and re-queries the hovered link whenever its rows repaint, which a live TUI does
continuously, and each re-query waited for a host `stat` round trip, so the link was
absent for part of every frame. The provider now keeps a per-pane validation cache keyed
by the exact link text (a pane has one host-owned cwd; hits live 30 s, misses 5 s so a
file the agent has just written becomes clickable), shares one in-flight request per
text, answers a fully cached row synchronously, and retries a row that repainted while
its first stats were in flight. (2) `showTextDocument` rejects images, PDFs and other
binaries and the rejection was swallowed. The host opens every file through
`vscode.open` (new, non-preview tab; text keeps its line/column, viewers ignore the
selection) and an activation that cannot complete shows a short VS Code warning
(`terminal link: …` in the extension log). Detection now also accepts `~/` and `~\`
(expanded to the user's home by the host), stops drive paths at `:` and `)`, strips
trailing `:`, and no longer treats an in-word apostrophe as an opening quote.

Installed OMP's `pi-tui/src/render/hyperlink.ts` emits `file://` outside VS Code and
`vscode://file/<encoded-path>:line[:col]` when `VSCODE_PID`/terminal identity selects
VS Code. The maintainer approved decoding only that exact file authority into the same validated
local-file open, never launching the URI. Other custom schemes, remote file authorities,
UNC paths, directories and missing files are refused. HTTP(S) continues through the
existing extension-owned browser confirmation. The PTY environment is unchanged:
OMP's `off/auto/always`, `NO_COLOR` and explicit hyperlink opt-out remain authoritative.
Native/shell output cannot execute commands, choose cwd or navigate the webview.

Focused regression feedback covers detection, cwd/absolute resolution, real OMP's
encoded location URI, host rejection and correlated open targets. Owned Chromium
observed actual plain-path and OSC 8 mouse clicks reaching host disk validation at
lines/columns 2:3 and 3:2, plus underline, pointer and missing-path refusal
(the headless result and screenshot are not kept in the repository).
Combined-VSIX installed-window proof is recorded separately after the coordinated freeze.

**Accepted snapshot limit.** The broker's existing xterm SerializeAddon omits OSC 8
targets from an attach/reopen snapshot. This package deliberately does not change
the broker. A real headless serialization probe produced only underlined `Here`,
not its `file:///C:/owned/proof.ts` target. After reopening, OMP references whose
visible labels contain a resolvable path (including compact Read paths and normal
path/position text) remain clickable through the validated text provider. An
arbitrary or abbreviated label that does not contain a resolvable path cannot
recover its snapshot-only OSC 8 target. Newly arriving live OMP output retains OSC 8
activation normally. The maintainer explicitly accepted this limit on 2026-10-04.

### Selection copy (2026-10-05)

Field defect: select text in a native OMP tab and press Ctrl+C, and the TUI's input editor cleared. The pane forwarded `^C` to the PTY on every Ctrl+C. By source reading (not observed before the repair), the text still reached the clipboard through an unrelated path: VS Code forwards the keydown to the workbench, which copies in the webview, and xterm's own `copy` handler writes its selection. The copy and the interrupt both happened.

Native and folder-shell panes now match the VS Code integrated terminal (`terminal-keys.ts`, `terminal-renderer.ts`). A key handler on the shared xterm renderer classifies each keydown:

- Ctrl+C or Ctrl+Insert with a non-empty xterm selection copies it, clears the selection and sends nothing to the PTY.
- Ctrl+C with no selection is `^C` in a folder shell. **In a native OMP session it was `^C` too, which the 2026-10-06 rule below withdraws: a native session never sends Ctrl+C.**
- Ctrl+Shift+C always belongs to the pane: it copies the selection, and with nothing selected it still sends no byte.
- Ctrl+V, Ctrl+Shift+V and Shift+Insert are not classified and keep the browser paste event path. Shift+Enter handling is unchanged.

A letter key is matched by its Latin `key` and otherwise by the physical `KeyC`, so a Cyrillic layout behaves the same. A consumed chord also suppresses its keypress/keyup, so the already-cleared selection cannot turn the release into a plain `^C`. The handler stops propagation so the workbench never also sees the key; this matters most for Ctrl+Shift+C, which the workbench binds to open an external terminal.

The write is made by the Webview in response to the user's keystroke (`terminal-clipboard.ts`): `navigator.clipboard.writeText`, then the legacy `copy` command (which makes xterm put its own selection on the clipboard) if the former is refused. No new host message is needed: the screen-copy request/reply path stays only for the whole-screen command, whose trigger is not a keystroke in the page. The selection is cleared only after a write succeeded; a refusal keeps it and shows the existing copy note. Copying works while the pane is read-only (stopped or passive), since it does not use stdin.

Mouse reporting: if the TUI enables mouse tracking, xterm sends mouse events to it and a plain drag selects nothing; Shift+drag forces a local selection, which these chords then copy. Without a selection nothing changes for the TUI's own mouse handling.

Evidence (2026-10-05). Focused: `terminal-keys.test.ts` 4/4 for the chord classification; two real-Chromium regressions in `chat-ui.test.ts` (chat and shell documents) select a row by mouse drag, press Ctrl+C and observe one clipboard write and no terminal-input message, press it again and observe exactly `\u0003`, then Ctrl+Shift+C with nothing selected (no new input) and a paste event (reaches the PTY). Installed isolated proof against the shared VSIX (bundle hashes recorded by the final executor), real native OMP 18.4.x TUI in session №1 with `my unsent draft stays` in the OMP input and the clipboard pre-set to a sentinel: a mouse-selected `Write a 500-line poem abo` plus Ctrl+C left exactly that text on the OS clipboard (read with `Get-Clipboard`), cleared the highlight and left the draft intact; Ctrl+C with no selection cleared the draft as OMP defines and left the clipboard untouched; with `draft two` typed, Ctrl+Shift+C and nothing selected kept the draft and clipboard, and a real Ctrl+V (CDP `paste` command) appended the clipboard text exactly once. The plain xterm drag selected locally, so this OMP build does not enable mouse reporting. Screenshots were image-inspected; they are not kept in the repository. The iso window had been minimized, which makes the webview `hidden` and strips input ownership (readOnly textarea); it was restored without activation for the proof.

### Ctrl+C never interrupts a native OMP session (2026-10-06)

User rule, verbatim: “never treat Ctrl+C as an interrupt while OMP is running”. After the selection-copy repair above, Ctrl+C still cleared the OMP input editor whenever nothing was selected, because that repair deliberately kept `^C` for the no-selection case (the VS Code integrated terminal's rule, right for a shell, wrong for a session the user wants never interrupted).

**Why `^C` still got through (by source reading and real-Chromium regressions, not guessed).**

1. The no-selection path was designed to forward it: `terminalCopyChord` returned `null` for Ctrl+C unless `hasSelection()` was true, and xterm then encoded `^C` from `keyCode` 67.
2. The native OMP TUI does not take the selection away from xterm. Installed OMP enables mouse tracking only for fullscreen overlays and the opt-in `tui.mouse` setting (default `false`; `packages/tui/src/tui.ts`, `settings-schema.ts`), and it has no selection or OSC 52 copy in its normal chat view. A plain mouse drag in a default session therefore makes an xterm selection and `hasSelection()` is true. When tracking is on (a fullscreen overlay, or `tui.mouse`), a plain drag becomes mouse reports for the TUI and xterm has no selection, so Ctrl+C had nothing to copy and fell through to `^C`.
3. xterm clears a selection on any user input, on a row-count resize and on a trimmed scrollback or buffer switch (`SelectionService`), not on output, so ordinary OMP redraws do not drop it. A Russian layout reaches the handler: its `key` is the Cyrillic letter U+0441 but `code` is `KeyC` and `keyCode` 67, and the classification already followed `code`.

**Applied behavior** (`terminal-keys.ts`, `terminal-renderer.ts`, `TerminalPane.tsx`). The renderer takes `ctrlCInterrupts`, true only for a folder shell (`ShellView`), false for every managed session.

- Native session, Ctrl+C (or Ctrl+Shift+C) with a selection copies it and consumes the key; without a selection it is consumed and does nothing: no byte, no clipboard write, no workbench binding. The match is the Latin letter `c` or, when `key` is not a Latin letter, `code === "KeyC"`, so a Russian layout (`key` `U+0441`/`U+0421` (Cyrillic es)) behaves identically. Dvorak follows the letter: the key that types `c` copies, the one at the physical C position (which types `j`) does not.
- Ctrl+Alt+C and Cmd+C are not chords (AltGr and the macOS copy key stay with the browser), so the second line of defence applies: `withoutInterrupt` drops any input event that is exactly `^C` or `ESC ^C` and strips a literal `^C` from pasted text before it is sent. Nothing else in the renderer (`onData`, IME composition, paste) can emit `\x03` to a managed session. xterm 6.0.0 has no Kitty keyboard encoding, so `OMP` enabling it does not change Ctrl+C to a CSI-u sequence.
- A folder shell keeps the standard semantics: a selection copies, no selection sends `^C`, Ctrl+Shift+C always copies. Shells need the interrupt.
- The OMP TUI's mouse capture: Shift+drag forces an xterm selection while tracking is on (xterm's own override, unchanged), and Ctrl+C then copies it. There is no OMP-side selection to forward: OMP has no selection or copy request in its normal chat view, and the renderer still deliberately handles no OSC 52 (a program must not write the clipboard). A selection a fullscreen OMP overlay paints itself cannot be read back by the pane; with tracking on, use Shift+drag.

Regressions (all real Chromium in `chat-ui.test.ts`, plus `terminal-keys.test.ts`): native session with no selection sends no byte and writes no clipboard for Latin and Russian (`U+0441`, `KeyC`) Ctrl+C and Ctrl+Shift+C; a drag copies and still sends nothing; a second press after the copy still sends nothing; a pasted `^C` is stripped from a native paste only; with mouse tracking enabled a plain drag selects nothing and sends nothing, and Shift+drag then Ctrl+C copies. The real folder-shell document (`ShellView`) sends exactly `\u0003` for each no-selection Ctrl+C in both layouts and still copies a selection.

Evidence (2026-10-06). Focused: `terminal-keys.test.ts` 10/10; `chat-ui.test.ts` 69/69 including the two Ctrl+C regressions (native session and the real `ShellView` document). Installed isolated proof against the final shared VSIX (installed `media/guest.js` sha256 `8020c2e8…6354d8`, `media/shell.js` `15938a5f…610302`), real native OMP 18.6.0 TUI in the session “Run one task subagent”, driven through CDP (real key and mouse events to the page, clipboard read with `Get-Clipboard`, clipboard pre-set to a sentinel): with `DRAFT-KEEP-ME ABC` typed into the OMP input, Ctrl+C, Ctrl+C on a Russian layout (key `U+0441`, code `KeyC`), Russian-layout Ctrl+Shift+C and Ctrl+Shift+C with nothing selected left the draft and the sentinel untouched; a mouse drag over a localized waiting-for-subagent status line then Ctrl+C left exactly that text on the clipboard, cleared the highlight and kept the draft; a drag over `main don` then Russian-layout Ctrl+C copied it with the draft intact. With OMP then working (a 45-second bash command running, status “Working”), `WORKING-DRAFT` plus Latin and Russian Ctrl+C kept the draft and the command ran to completion (`tcc done`, 48.7 s turn), so nothing interrupted it. Screenshots were image-inspected; they are not kept in the repository. Not exercised live: OMP mouse tracking (the user's OMP config has no `tui.mouse`, so it keeps its default `false`); that path is covered by the Chromium regression above.

### Wide-character cursor alignment (2026-10-06)

Field defect: after pasting `⌚` (U+231A) into the OMP input in a terminal tab, the visible cursor sat one cell to the right of where text was inserted; the offset disappeared once the text wrapped onto the next row.

**Root cause (source-read and reproduced against the real xterm.js classes).** The OMP TUI measures widths with `Bun.stringWidth` (`visibleWidth`, `packages/tui/src/utils.ts`) and the native `unicode-width`-based engine (`crates/pi-natives/src/text.rs`): Unicode 11+ tables, where `⌚` and every default-emoji-presentation or East-Asian-Wide code point is two cells. xterm.js 6.0.0 starts on its Unicode 6 table, which counts `⌚` and `😀` as one cell. The TUI lays out the row and parks the hardware cursor by its own column count, so the emulator's cell advance and the TUI's disagree by one column per such character; a wrapped row is re-addressed absolutely, which hides the error.

**Applied behavior.** The Webview renderer (`terminal-renderer.ts`, shared by native and folder-shell panes) and the broker's headless mirror (`broker/pty-screen.ts`) both load `@xterm/addon-unicode11` (exact pin `0.9.0`, MIT) and set `unicode.activeVersion = "11"` through one function (`webview/lib/terminal-unicode.ts`), with `allowProposedApi: true` on the renderer's terminal because xterm.js gates the `unicode` API. Both emulators must use the same table: a reattach snapshot is serialized by the mirror and replayed by the renderer, and different tables would place the same cells differently from the live stream.

**Addon choice.** `@xterm/addon-unicode-graphemes` 0.4.0 (experimental; providers `15` and `15-graphemes`) was measured against `Bun.stringWidth` and rejected: it sizes supplementary-plane wide emoji (`😀`, `🚀`, `👍`) as one cell, which the TUI sizes as two. `addon-unicode11` matched the TUI for CJK, `⌚⌛⏳`, `✅` and supplementary-plane emoji. **Residual, accepted and not claimed fixed:** sequences only a grapheme-cluster model can size still differ — a text symbol promoted by U+FE0F (`⚠️`, `❤️`, keycaps: TUI two cells, xterm one), ZWJ families (TUI two, xterm six) and skin-tone modifiers (TUI two, xterm four). Fixing them needs a grapheme-aware provider whose wide-emoji table is correct; none of the published addons is, and `packages/tui/src` does not use terminal mode 2027.

Regressions (`terminal-unicode.test.ts`, `broker/pty-screen.test.ts`, `chat-ui.test.ts`): the real `@xterm/xterm` and `@xterm/headless` terminals receive TUI-style output (clear, home, prompt, text, CSI `G`) for `⌚`, `⌛⏳`, `✅`, `😀`, CJK, mixed text and ASCII; cursor `x` must equal the TUI's count, the next character must sit at the cursor and a typed character must overwrite exactly it. One assertion documents that the default table puts the cursor a column early. The mirror test checks the live snapshot cursor and replays the serialization into a fresh Unicode 11 terminal. Two real-Chromium cases (chat and shell documents, the compiled renderer) send `> ⌚😀你x` plus CSI `9G` and require the rendered cursor cell to hold `x`, then live output to replace exactly that `x`.

### Stale lines and a misplaced cursor after reveal or reattach (2026-10-06)

Field defect (user's main window, after installing the Unicode 11 build and Reload Window): a native OMP tab showed its working-status line (a localized "waiting for the search result" message) three times, the extra copies frozen at earlier shimmer frames, and the hardware cursor one row below the `❯` prompt.

**Hypotheses, each tested.**

1. *Broker version skew* — the user's brokers were started by an earlier build (tree `ca753fa9`, process start 2026-10-05; the main log shows `Reattached exact process`) and mirror with Unicode 6. **Not the cause.** Real ConPTY recordings of OMP (animated status, nerd-font glyphs, emoji) were replayed through a Unicode 6 `PtyScreenModel`, serialized and restored in a Unicode 11 renderer: the restored screen and cursor equalled the truth. The spinner glyph is U+F12B7 (Private Use Area-B), one cell in both tables.
2. *Trimmed snapshot off by a row* — `fitTerminalSnapshot` was checked on 24 real trimmed snapshots: screen, cursor row/column and attributes restore identically. A regression now defends it (`keeps the cursor on the row it was on`).
3. *Snapshot/live ordering* — the real `PtyScreenModel` + `TerminalPipeline` + reducer were driven with six random attach points during animation: every trial equals the truth. The seq cut is sound.
4. *Glyph width disagreement* — see 1; none for the spinner glyph.

**Root cause (observed in the isolated window with the previous build, against a broker of an older, Unicode-6 tree).** `TerminalPane.apply` rendered the xterm at the pane's grid only when the pane did *not* own input. A reattached or revealed pane first paints the restored screen at the host's grid (it is not yet the owner), then receives ownership; the host resizes the PTY to the pane's own fit, but the renderer stayed at the host's grid and nothing re-fitted it (the container did not change size, so `ResizeObserver` stayed silent). OMP drew for the new grid (29 rows) while xterm still showed the old one (46 rows): OMP's relative cursor moves and its erase of the previous frame landed on the wrong rows, leaving stale loader rows and a cursor one row off. Reproduced before the fix: working turn → switch to another tab → toggle the bottom panel (Ctrl+J) → switch back: DOM `rowCount` 46 versus fit 29, stale rows below the prompt. A plain Reload Window with an unchanged layout did not reproduce it, because both grids already agreed.

**Fix.** The pane now renders at `state.grid` for the owner as well (`renderer.renderAt(state.grid)`), so the emulator follows the PTY grid it asked for. Two further guarantees:

- *Repaint after restore.* After a restored screen is delivered to a visible owner of a native OMP pane, the host nudges the PTY one column narrower and back (`TerminalPipeline` option `redrawAfterRestore`, set only for `managed-omp` sessions). The resize reaches OMP as the ordinary resize path (`tui.ts` repaints the viewport on `SIGWINCH`; ConPTY gives it no cursor-position report, so it re-anchors itself), which makes OMP redraw its whole screen so its renderer state matches the emulator. Exactly one nudge per restore; a pane that is not yet the owner waits and nudges once when it becomes visible owner; passive readers and failed restores never nudge. Folder shells are never nudged: a shell does not redraw on a size change and the nudge would only reflow its prompt. OMP's reset-display key (`app.display.reset`) was not used: it discards scrollback.
- *Broker of another build.* The broker owns the PTY, so it cannot hand its terminal to a newer process, and restarting it would end the user's OMP process. A surviving broker of an older build is therefore detected (`PtyHandle.buildMatches`, the broker's tree digest against this build's), kept, and named in the native attach reason (`Its PTY broker was started by another build of this extension`); the repaint above refreshes whatever its mirror would otherwise misplace. `PTY_PROTOCOL_VERSION` and `PTY_RUNTIME_VERSION` are unchanged. An older broker keeps mirroring with its own Unicode table until its session is stopped and restarted; no action is required for correct rendering.
- *On-demand repaint.* `OMP: Redraw Terminal` (Ctrl+Alt+Shift+R) calls `TerminalPipeline.redrawNow()`, the same shrink-and-regrow, for the visible input owner of a native OMP pane only; each request is one repaint. Shells, hidden panels and non-owner panes get `false` and a visible warning. The chord is swallowed by the xterm key handler (without stopping propagation, so the workbench still runs the command) and is not an OMP default; Ctrl+Shift+L is not used because xterm encodes it as `^L`, which OMP binds to live mode.
- *A repaint must use the grid the PTY has, never the fit a page named at attach.* The first on-demand repaint in the installed isolated window corrupted a working session (duplicated status and footer rows, prompt missing, cursor off). A byte tap in the broker showed why: the host resized the PTY to the grid the page had *attached* at (131x44) while the page's xterm had since refitted to 131x46, so OMP drew for 44 rows and the emulator showed 46: the original defect. An earlier change recorded every owner fit in `Frontend.wanted`, which still left the attach-time value in force for the repaint that follows a restore (see the reload and restore items below), so `wanted` is gone: the nudge is made on the grid the broker reports at that moment (130x46 then 131x46) inside a serialized grid write. Regression: `terminal-pipeline.test.ts` "never resizes the program to the fit a page named when it attached".
- *Reload storm: one settled fit, one serialized grid.* Taps on the host, the broker and the page across `Developer: Reload Window` in the isolated window (131x46, a streaming session) showed the PTY going 46 -> 44 -> 45 -> 46 within 60 ms of every reattach: the revived editor is laid out over several frames, so the fit sent with `omp:terminal-attach` (44 rows) and the fits the pane measured next (45, then 46) differ by a row or two; the host's repaint resized the PTY to the stale attach-time fit (the `wanted` branch above) and the page then reported each intermediate fit as it was measured. Every value is a real SIGWINCH to OMP, whose resize handling is a multi-step anchor protocol (`tui.ts` coalesced resize burst, cursor-position probe, height shrink then regrow pulling rows back out of scrollback) and which assumes the terminal answers it for one geometry at a time; a burst that shrinks and regrows within milliseconds is the case its own comments call unsound without a cursor-position reply. The transient is observed (the frame is painted at 44 and 45 rows before the settled 46, frames captured every ~120 ms); the persistent off-by-one row reported from the main window was **not** reproduced in the isolated window, where the final screen and cursor were right after every reload, so it is attributed to this burst by mechanism, not by capture. Three changes remove the burst. (1) `TerminalPane` reports the owner's fit only once it has held still for 120 ms (`RESIZE_SETTLE_MS`), and forgets what it reported whenever it is not the owner or asks for a screen again, so a pane that regains input always restates its fit instead of trusting a grid another owner may have changed. (2) `TerminalPipeline` runs page resizes and the repaint nudge through one queue, and the nudge reads the broker's grid inside it, so a resize that lands between the two halves of a nudge is never undone by the regrow. (3) A resize to the grid the broker already has sends nothing, so a page that restates its fit does not wake the program. Regressions: `terminal-pipeline.test.ts` (a resize in the middle of a repaint wins; a restated grid sends nothing; the attach-time fit is never applied), `chat-ui.test.ts` (the fit is reported once, after it settles, and again after input is regained; the headless fixture itself measures the attach-time fit a row short of the settled one).
- *Cursor one column short after a restore.* A native tab restored while it was hidden and revealed later showed its cursor on the first column after the `❯` prompt arrow instead of the second, and it stayed there until the program next moved it (typing one character and Backspace put it right; verified in the isolated window, `cc` 1 against 2 in the live tab beside it). A tap on the page's writes showed the restored snapshot ending in `\e[2A\e[129D`: `SerializeAddon` (0.14) returns the cursor with relative moves counted from the end of the last row, and OMP's footer fills that row's whole width, which leaves the emulator in the pending-wrap state where xterm.js's cursor-backward first steps onto the last column and then moves, so the cursor lands one column left of the serializer's intent. No OMP output reached the pane after the restore in the capture (an idle prompt has nothing to repaint), so nothing corrected it. `placeSnapshotCursor` (`terminal-pipeline.ts`, applied where the native writer adapter builds the snapshot in `native-terminal.ts`) appends an absolute `CUP` from the mirror's own cursor after everything the serializer wrote; it needs no change to the broker, so a surviving older broker is covered too. Regression: `terminal-pipeline.test.ts` "restores the cursor to its column when the last row fills the width (pending wrap)" (the raw serialization lands at column 1, the placed one at column 2), and the two `extension-lifecycle.test.ts` snapshot-byte assertions.
- *Duplicated screens after a busy or hidden page.* xterm.js accepts `write()` bytes at once but parses them later, in slices; a minimized window throttles its timers to about one slice a second, so the page can hold a large backlog it has accepted and not parsed. The pane's `reset()` (a restored screen) and `resize()` (a refit) ran synchronously, ahead of that backlog: the old bytes were then parsed onto the freshly reset screen and the restored snapshot landed after them, so the whole screen appeared twice (headless xterm reproduces it exactly: `terminal-ordered-surface.test.ts`). The same happened to a screen restored twice within milliseconds (the host answered a fresh native start with two attaches 7 ms apart, observed in a host tap, and the installed isolated window showed the OMP banner, prompt and footer twice), and a refit parsed bytes OMP drew for one grid at another. `OrderedTerminalSurface` (`src/webview/lib/terminal-ordered-surface.ts`) now holds a reset or resize until every earlier byte has been parsed and holds later bytes until it is applied; it is a pass-through when nothing is pending. `fitToContainer` also refuses a zero-sized (hidden or collapsed) container instead of fitting it to the smallest legal grid. A real minimize of the isolated window during streaming produced no resize, attach or resnapshot at the host (host tap), so the minimize itself is not what duplicates lines; the unordered reset/resize is what turns any restore that meets a backlog into a duplicate.
- *Where the remaining live defects come from (follow-up evidence).* Real OMP (18.6) was recorded in node-pty ConPTY (bundled `conpty.dll`, as the broker spawns it) at 200x45 and 200x30 with OMP's own debug paint stream, and OMP's raw stdout (before ConPTY) was captured with a preload hook. Replaying the raw stdout and the ConPTY output into the same headless xterm (Unicode 11) gave identical screens, so neither ConPTY nor this extension's mirror, snapshot or webview changes what OMP writes. A blank run of about a dozen rows before an Ask card is already in OMP's raw stdout and in its own viewport paint (`packages/tui/src/tui.ts` `#renderProviderFrame` and `chrome/transcript-container.ts` viewport allocator). "Ask tool was cancelled by the user" at column 0 is a row OMP paints itself (`packages/coding-agent/src/tools/ask.ts`, `ToolAbortError`), not a stray stderr write. Duplicated loader/footer rows and tails of blocks overwritten by the next block were not reproduced offline (no resize, reattach or CPR battery produced them), so they are not claimed as fixed; `OMP: Redraw Terminal` is the honest on-demand repaint for them.

Regressions: `terminal-pipeline.test.ts` (cut keeps the cursor row; exactly one nudge per reattach of the owning page, sent after the screen; hidden page waits; a real grid change replaces the nudge; passive/failed/disabled never nudge), `chat-ui.test.ts` (an owner pane's renderer follows its fit after a screen restored at the host's grid), `pty-client.test.ts` (a broker of another tree digest is detected, adopted and left running).

### Native completion

The maintainer supplied field evidence: a fresh native host failed host-control connection about nineteen seconds after launch and emitted no desktop decisions, while Chat worked. Native readiness now waits up to sixty seconds for the exact recorded PID/process generation/key/runtime (Chat retains its fifteen-second deadline), cancels stale-runtime work and single-flights launch/recovery. The native watch retries absent/closed control later and records availability and native completion-signal capability. Re-adopted older children retain their recorded activity capability: unsupported journal APIs are not probed and signals are never fabricated. Top-level/continuation/abort, baseline, same-session and active-focused exclusions remain. Canonical isolated proof observed the same native process become controllable after 23.9 seconds, real inactive-editor and window-unfocused WinRT toasts, and a suppressed focused turn consistent with foreground/editor/DOM samples bracketing the decision.

## Alternatives

- Removing liveness probes would conceal extension-host loss; use non-destructive probes instead.
- Replaying a snapshot on every focus/probe destroys terminal-local state; reserve snapshots for recovery.
- Keeping the duplicated webview switcher conflicts with the requested native editor title UX.
- Focus-only input permission confuses browser focus with exclusive writer ownership; explicit eligible-owner retention keeps the fencing without the false read-only state.
- Cache-busting bundles is not justified by the previously observed raw-CDP served-resource artifact. The maintainer accepted that observation as a harness artifact; no bundle cache-busting change is included.

## Risks and Open Questions

Canonical isolated evidence proves slow native readiness, symbol fallback without a font override, non-destructive idle probes, title/copy targeting, multiline input, blur ownership, automatic mode-entry/tab-reactivation focus and inactive/unfocused native toasts. Native alternate-screen scrolling is OMP-owned; its return-to-tail after a new user prompt has not been attributed to extension output handling. Normal-buffer viewport preservation is covered by a real xterm consumer. The residual low-rate route offers have not been correlated to a producer; they do not establish another ACK loop. Two earlier sent decisions remain unobserved at their decision instant; later focused suppression has bounded before/after samples, not instant measurements. A second same-terminal frontend was not reachable through supported UI. Clipboard replies remain current-document-bound, and shared transport repairs retain folder-shell lifecycle/grace semantics. Final12's automatic reload left the alive native process unattached; its historical classification cause remains unproven. Fresh public broker/kernel/pinned/reconciler proofs established current attachability, and one subsequent supported guarded reload restored the same process in Final15. This is observed recovery, not a claimed restore-defect repair or a new retry policy.
