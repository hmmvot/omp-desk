# Context view

## Problem

The Chat footer shows one number about a conversation's context: a ring with the percentage, and a popover with tokens, window, session cost and the Compact and Shake buttons. It does not say what fills the window (system prompt, tools, skills, files, messages), which AGENTS and rule files OMP put into the prompt, what the last compaction did, or whether auto-compaction is on. The same information exists in OMP's TUI (`/context`, `/session`) but is invisible in Desk, and nothing in the OMP Desk side bar describes the session the user is working in. The user asked for a **Context** view in the OMP Desk container for the selected session.

## Goals and Non-goals

- A **Context** tree view in the OMP Desk container for the *active session*, selected by the same rule as the Skills, Tools, MCP and Extensions views: the focused Chat editor, else the last-focused one; an empty state otherwise.
- Show only what installed OMP reports (verified below). The header uses the numbers the Chat popover uses, from the same source, with the same normalization, formatting and thresholds.
- Token breakdown by category on the user's request, message and billed-token statistics of the retained context, the maintenance state and the compaction and clear history of the session file, and the context files OMP put in the prompt, each openable.
- Compact and Shake as view-title actions for the *viewed* session, reusing the Chat's existing `runChatAction` flow (mode pickers, instructions prompt, refusal text).
- Reads only while the view is visible, event-driven from the session, never on a timer; the automatic reads are read-only commands that write nothing to the session and add nothing to the conversation.
- Non-goals: any estimate, projection or token count OMP does not report (no local tokenizer, no per-file token count, no "cost of this turn"); a second discovery of rules or skills (the Skills view and OMP own that); changing OMP, Desk's `-e` host-control module or the host-control protocol; a Terminal-mode context (no surface exposes it); editing context files; an automatic or background breakdown (see Alternatives); a new setting.

## Current State

What installed OMP 18.8.5 reports about a running session (read from the installed package source and probed against a real `omp --mode rpc-ui` child with a local stub provider; every fact below was observed or is read from the cited source):

| `autoCompactionEnabled` | RPC `get_state` | Desk's Chat state does not keep it today; this design reads it per deep read only. |

| Token breakdown by category: System prompt, System tools, System context, Skills, Messages, Auto-compact buffer, Free (plus an optional Snapcompact estimate) | builtin slash command `/context` | Not an RPC command and not in `get_state` or `get_session_stats`. In RPC mode the builtin answers with one `command_output` frame (`{type, text}`, no request id), ahead of the acknowledgement (`{agentInvoked:false}`), emits no `prompt_result`, and writes nothing to the session file. The text is `Context window: N tokens (P% used)` (a rounded percentage, no exact used-token figure) followed by lines `  <label>  [bar] P%  N tokens`; a zero category is omitted; `messages` is clamped at zero. If the breakdown helper throws, OMP prints a minimal `Context / Window: N / Used: M` form. **Extension input handlers run before builtin dispatch** (`rpc-mode.ts`), so a handler can rewrite or handle `/context`; an unhandled idle text reaches the model. |

Entries of every branch are in the file. |

Existing Desk pieces reused: the editor-recency selection of `toolsTarget` (`extension.ts`, `SessionToolsTarget`), `RpcSession.subscribe` outputs and its `model.state` (the footer's own source), the streaming journal loop of `session-cost.ts`, `runChatAction` for Compact and Shake, the inventory views' open-file command `omp.inventory.open`, the tree-view registration pattern (`registerInventoryViews`), and the webview formatters `contextTokenLabel`, `sessionCostLabel` and `fmtPercent` plus the popover's percent normalization (clamped to 0–100) and thresholds (warning from 70 %, critical above 90 %).

## Proposed Design

### The view

One tree view `omp.context` named **Context**, collapsed by default, after Extensions. Its description is the session title. When there is nothing to show it displays a single message instead of rows:

- no editor selected: "Open an OMP Chat to see its context.";
- the selected editor is a Terminal: "This session is open as a Terminal. OMP reports its context only to a Chat editor.";
- the session is not running (stopped, view-only, passive in another window, starting, failed): "This session is not running, so OMP reports no context."

Otherwise it shows these groups, in this order. Every row is plain text with a plain-text tooltip; nothing is rendered as Markdown or as a command link.

1. **Context window** (expanded). *Model* (`name`, description `provider · window`). *Used*: the popover's normalization (a finite percentage clamped to 0–100), `fmtPercent` used and `contextTokenLabel(tokens) / contextTokenLabel(window) tokens`, with the popover's thresholds as a themed icon colour (≥ 70 % warning, > 90 % critical); a missing percentage reads "Usage unavailable" and is never computed from the token counts, exactly as the popover. These rows come from `model.state`, the same object the popover reads, so they match it at every instant. The Used row carries inline Compact and Shake buttons.
2. **Breakdown** (expanded). Before the first request, one row **Read breakdown** (tooltip: it runs OMP's `/context` in this conversation as if typed, and the report also appears in the Chat). After it: one row per category line of OMP's report (label as OMP prints it, `Auto-compact buffer` written out; `N tokens · P % of window` with the share computed from the report's own window; Auto-compact buffer and Free muted as reserved or empty space), any line the parser does not recognise as a verbatim muted note, and a **Read again** row. The group description is `as of <time>`, plus `; usage has changed since` when the live token figure differs from the figure `model.state` showed when the report arrived (no cause is claimed: a model, settings or turn change can all move it). The report is never rewritten to fit.
3. **This context window** (expanded). Messages (`N · U user · A assistant · R tool results`), tool calls, billed tokens (`input · output`, with cache read/write and reasoning only when non-zero), premium requests when non-zero. The group tooltip says these are OMP's `get_session_stats` for the messages OMP currently keeps, and that billed input counts every call's whole prompt, so it is not the context size.
4. **Maintenance** (expanded). *Auto-compaction* on or off (`get_state`, absent when not reported) and *Pass in progress* or *Last pass seen* (`model.maintenance`: action, reason, status). The tooltip states that Shake leaves no record in the session file, so only a pass this window saw is listed.
5. **Session file** (expanded). *Session cost* (the whole-journal figure the popover shows, hidden when zero as there), *Compactions* (count), *Last compaction* (relative time; tooltip with the ISO time, `method`, `tokensBefore → tokensAfter`, the pass's `warning`), *Last clear boundary* (time or "none recorded"). The tooltip states the scope: every branch of the file, abandoned branches included, as OMP's cost figure counts; and that a clear boundary is written before the live reset completes, so it does not prove the clear finished (the Chat's own warning for an unconfirmed clear stays authoritative).
6. **Context files** (expanded when non-empty). One row per `<file path>` of the prompt's `<repo-rules>` block: file name, description = folder and the character count of the content in the prompt (OMP reports no per-file tokens), tooltip = full path. A second row kind lists `<dir-context>` paths ("read on demand", muted). The tooltip says the rows are **paths extracted from OMP's rendered prompt**, not an authenticated list of loaded files (OMP exports none, and prompt text can itself contain the markers). A click opens the file through `omp.inventory.open` (absolute Windows path only, preview editor), the same command the inventory views use. When the prompt lists none the group is omitted; when the prompt was not read it is omitted.

### Actions

View title: **Refresh**, **Read Breakdown**, **Compact…** and **Shake…** (`omp.refreshContext`, `omp.context.readBreakdown`, `omp.context.compact`, `omp.context.shake`). The last three are enabled when the viewed session is a live Chat (context key `omp.context.canMaintain`) and act on the *viewed* tab, not the focused editor, so clicking the side bar cannot redirect them. Compact and Shake call the extension's existing `runChatAction(context, index, tabId, "compact" | "shake")` (pickers, instruction prompt, refusals and the maintenance outcome notice are the Chat footer's own). The palette commands `omp.compactConversation` and `omp.shakeConversation` keep acting on the active Chat editor and are unchanged.

### Where each number comes from, and refresh policy

`src/host/context/` holds the pure projection and parsers and a controller; `src/views/context-tree.ts` the tree provider; `src/host/context-wiring.ts` exports `registerContextView(context, deps)` (the one registration entry). `extension.ts` supplies `target(): ContextTarget | null` (built from `toolsTarget`, so the selection rule is the inventory views' own rule by construction, plus the tab id and the `RpcSession`), a `log`, and the compact/shake runner. `SessionToolsTarget` gains the `tabId` its builder already has.

The controller reads **only while the view is visible** and never on a timer of its own. It has two automatic tiers and one explicit request.

- **Live header, no I/O.** It subscribes to the target session's outputs (`RpcSession.subscribe`) while visible. Every `model` output is reduced to a small signature (model, usage tokens/window/percent, working, async pause, compacting, maintenance); only a changed signature republishes the tree, so streaming deltas cost one comparison each. A `snapshot` output (a new epoch: reconnect, rewind, a replaced conversation) makes the controller re-evaluate the selection, whose generation includes the session epoch, file and id; an `identity` output (`/clear`, `/new`, a verified resume) drops the deep read and the breakdown at once.
- **Deep read, read-only, at most once per settle.** `RpcSession.readContext()` is one fresh `get_state` (folded into the Chat model like any state read, plus the auto-compaction flag and the prompt's context files), one `get_session_stats`, and a streaming scan of the session file (the `readJournalCost` loop, extended to count `compaction` and `reset_boundary` entries too: one scan convention, no second pass). Only read commands are sent: nothing is written to the session or the conversation. It runs when the view becomes visible, when the target or its identity changes, on Refresh, and after the signature shows the session idle and changed (the working-to-idle transition, a new usage figure, a finished pass), debounced by 750 ms. It does not start while a turn, a compaction or a pass is in progress. The controller fences every result with two counters: an *attachment* (advances on hide, selection change and a session starting or stopping; it also fences the subscription and the debounce timer) and a *revision* (advances with every attachment and also when a turn begins or the identity changes under the same attachment). A read or report that started under an older value is discarded **whole**, even if it resolves while the session is idle again, because its sources were not read at one moment of one conversation (a read-only source is not an atomic one); the controller then asks again once idle. Fences use these counters and the target's `key` and `generation`, never the identity of the `ContextTarget` object, which `extension.ts` rebuilds on every call; hiding the view forgets the selection and everything read, so showing it again re-attaches and reads from nothing. At most one deep read is in flight per selection, with one queued. `readContext()` is identity-checked like `readSessionCost` (live, identity-verified, same epoch/file/id throughout, and `get_session_stats` must name the same session id and file). `get_state` is a prerequisite of the whole read (it verifies the binding); once it passed, stats, journal and prompt files each fail independently; the stats and session-file groups say so when their part failed and the files group is omitted.
- **Explicit breakdown request.** `RpcSession.requestContextReport()` sends `prompt "/context"` with an internal id, exactly as the user typing it would be sent, and reads the report from the first `command_output` frame whose text begins with a known report prefix while the request waits; OMP's output carries no request id, so this is the first report *observed while the request waits*, not a proven answer to it (a late report of an earlier request that gave up, or a report the user typed in the same milliseconds, is equally valid text and is not kept for a later request when none waits). It does **not** consume the frame: the report renders in the Chat as the notice OMP command output always is, replays like any other notice after a reload, and nothing is hidden. It is refused while a turn, async pause, compaction, pass, rewind, clear or reconnect is in flight (`#controlRefusal` plus the same busy facts `maintain()` uses) and when the session's command catalogue lacks an entry named `context` whose source is `builtin` (a same-named extension command or template would not print the report). The request is an operation object retained from admission until its result is returned, through the acknowledgement and the grace wait; while it exists `#controlRefusal` answers "busy", so a second request, `maintain()`, a rewind, a clear, a queue edit and any prompt are refused for its short lifetime. The other order is covered too: the request is refused while a user prompt, steer or follow-up is written and not yet acknowledged (OMP awaits its input hooks before it acknowledges, an interval the model does not show), and a user prompt rechecks the fence after its asynchronous preparation, before it writes. Model and thinking choices made meanwhile are held and applied when the request releases its fence. The request records the native epoch, session file and id it started under, and the input-claim generation; if any of them changed (a lost and regained claim keeps the epoch, file and id but not the generation) or the session closed while it waited, it returns a refusal, publishes nothing and sends no abort. The time and the usage figure of the report are sampled in the frame handler at the instant the report arrives, not when the acknowledgement does. If the text did not run as a command (`agentInvoked` is not `false`: an input handler rewrote it) the turn that started is aborted as navigation does and the request reports "OMP did not run /context as a command". A report that never arrives within the short grace after the acknowledgement answers "OMP did not report its context breakdown". A user-typed `/context` that lands in the same milliseconds is an equally valid report and may be the one read. The breakdown is **not** refreshed automatically: it is the report of that moment, labelled as such; a new epoch or `identity` output drops it.

Because the automatic reads are read-only commands, none of the races of a write exist for them (maintenance, rewind, clear, input ownership); the request is a write like a typed command and uses the host's existing admission for one.

Cost, stated completely. A deep read costs one `get_state` (OMP serializes the whole system prompt and every tool schema; Desk already requests this for the Tools view), one `get_session_stats`, and one pass over the whole session file (the footer's cost read does the same independently, so the two cost figures are separate samples of the same journal). Each is bounded by the settle gate and the 750 ms debounce; none touches the live header, which stays I/O-free. The explicit request is one builtin (it runs OMP's snapcompact-savings planner only when the user has enabled it in OMP).

### Parsing and projection (pure, tested)

- `parseSessionStats(data)`: non-negative integers for counts and tokens; a finite non-negative number for `premiumRequests` (fractional multipliers are legitimate); anything else yields `null` for the whole set.
- `parseContextReport(text)`: strips ANSI, reads `Context window: N tokens (P% used)`, then every line matching `^  (label)  [bar…] … N tokens$`. Labels are kept as printed; unknown lines become bounded notes. A text that does not start with a known prefix is not a report. `Context usage is unavailable…` yields an explicit "OMP reports no usage" state; the minimal fallback form yields one `Used` row.
- `extractContextFiles(systemPrompt)`: reads the `<repo-rules>` section's `<file path="…">` blocks sequentially, a block ending at the first `\n</file>\n` followed by `<file path="` or `</repo-rules>`; keeps absolute Windows or UNC paths without control characters (≤ 1 024 chars, ≤ 64 files, ≤ 4 MB of prompt scanned) with the content length; reads `<dir-context>` `- path` lines the same way. The result is a list of unauthenticated references (see above), shown as such. It does not read the files.
- `readJournalFacts(file)`: one streaming pass over the lines of the session file yielding the whole-journal cost (as today) and, for lines starting `{"type":"compaction"` or `{"type":"reset_boundary"` (a line begins with its entry type, so message text never matches), the count and the latest of each. A torn final line is skipped. `readJournalCost` stays a thin wrapper.
- `projectContext(inputs)`: pure; builds the groups above from live facts, the last deep read and the last breakdown; owns every sentence, threshold and icon choice.

## Alternatives

- **Automatic breakdown by a background internal `/context`** (the first version of this design): the report is OMP's own, but the transport is a write-class command. Extension input handlers run before builtin dispatch, so a handler can rewrite it into a model turn or run side effects every time a view becomes visible; the `command_output` frame has no request id, so a silent capture is a prefix guess that can mis-attribute across a timeout, a second reader or a maintenance pass, and a hidden report left in the broker ring replays as a notice after a host reload. Suppressing every report-looking output would also hide the reports users type. Rejected for the explicit request above.
- **Add a context message to Desk's `-e` host-control module**: it has `ctx.getContextUsage()` (tokens, window, percent) but no breakdown or category API; amends ADR-0003/0006/0009 for a display feature. Rejected.
- **Staged Bun worker importing `computeSessionContextBreakdown`** (the inventory approach): it computes from a fresh, session-less settings load, so it would describe a hypothetical session, not the running one. Rejected.
- **Local estimate** (tokenizer, character counts) for categories and per-file sizes: numbers OMP does not provide. Rejected.
- **Parse the transcript or the session file for usage**: reproduces `get_state`'s anchored estimate badly. Rejected; the file is read only for spend and boundaries.
- **Poll while visible**: wasteful and noisy; the session already emits every change. Rejected.
- **Compact/Shake via the palette commands**: those act on the *active* Chat editor; with focus in the side bar they could target another session or none. Rejected for tab-bound calls of the same flow.
- **A per-category mini-chart (stacked bar)**: a tree cannot draw it; a webview view would duplicate the formatting stack. Deferred, not rejected.

## Risks and Open Questions

- The `/context` text is OMP's human report, not an API. A reworded label degrades to a verbatim row; a changed header or prefix degrades to "OMP did not report its context breakdown" while the other groups still show. The contract test runs the real installed OMP when present and fails loudly on drift.
- The report is a moment's snapshot; the view says so and never refreshes it by itself. The price of that honesty is one click (and one notice in the Chat) per reading.
- Context files are references taken from prompt text; a file that contains OMP's own block markers can produce a false or missing row. Paths are bounded and absolute and only open a file the user could open anyway; the group says what the rows are.
- A `reset_boundary` and a `compaction` on an abandoned branch are counted; the labels say "recorded" and "any branch".
- A subagent's context is not shown; only the main session's.
- `autoCompactionEnabled` changes only at a deep read (it is not part of the Chat state); a toggle made in the TUI shows after the next settle or Refresh.

## Rollout and Verification

1. Parsers and projection with tests (stats incl. fractional premium, report variants and drift, prompt files incl. hostile content, journal boundaries, thresholds and percent clamping, empty/unknown states, freshness wording, signature).
2. `RpcSession` with the fake channel: the deep read's three independent parts and identity/epoch refusals; the explicit request (report read while the frame still renders, busy and fence refusals, missing builtin, fall-through aborts the turn, no report, a foreign `command_output` ignored, a report that arrives before a delayed acknowledgement keeping the request in flight against a second request, `maintain()` and `clear()`, an acknowledgement after the session closed sending no abort, time and usage sampled at the frame, a same-named extension command refused, an old report not kept for the next request).
3. Controller (the extension's target factory returns a new equivalent object per call, as in production): visibility gating and hide→show re-attachment, no read while working, a read overtaken by a whole turn is discarded though it resolves idle, one read per settle, queued refresh, syncs and title changes that keep following the session, fencing by key/generation, tab switch, `identity` and `snapshot` outputs, a report arriving after an identity change, explicit request outcomes and notices.
4. Contract test against the installed OMP (when present): the `/context` report parses to the categories, `get_state` carries `systemPrompt` with the context files and `autoCompactionEnabled`, `get_session_stats` has the stats fields.
5. Live check in an isolated minimized VS Code window with an isolated OMP agent directory and a local stub provider: the view follows the selected Chat; the header equals the popover's; it changes after a turn; Read Breakdown, Compact and Shake from the view run; a context file opens; no notice appears from any automatic read.
