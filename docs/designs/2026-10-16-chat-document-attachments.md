# Attach documents to a Chat message: the file's text goes into the message

Second revision, 2026-10-16. The first revision (accepted after an independent review) sent a document as an `@path` mention that OMP expands, and put a file with no path into the draft as a fenced block. The maintainer replaced that: **"A file should go into the draft the same way whether it has a path or not. The file's content is inserted when the message is sent. By default the content is collapsed, so it doesn't clutter the chat."** Decisions 12 to 24 record what that means and what the review of this revision added; they supersede decisions 2, 3, 4 and 6 where they conflict (the superseded ones stay in the list, struck through). *Current State* is kept as background. The independent architecture review of this revision (accepted with changes, all resolved in the text) is recorded in *Architecture Review*, before the record of the first revision. Nothing is implemented.

## Problem

The maintainer's request, first form: "Draw them like screenshots (a chip with a preview), but send them to OMP as a path to the file." Second form (above): one draft form for every file, the content inlined at send, collapsed in the transcript.

Today the composer accepts images only. Attaching `notes.md` shows `notes.md: unsupported format (text/markdown) — attach PNG, JPEG, GIF, or WebP.` (`src/webview/lib/attachments.ts:154-163`). The only ways to give OMP a file are typing an `@` mention by hand, or the "Add File to Session" command, which inserts a `@path` line from an editor (`docs/designs/2026-10-07-add-editor-context-to-session.md:26-34`). Neither gives the draft a visible attachment: no chip, no ✕, nothing that tells the user the file was understood. And `@path` has limits the maintainer does not accept: OMP expands a mention only in a prompt it receives while idle, and only the first 3000 lines or 50 KiB (*Current State* 3).

This design adds **document attachments**: any text file the user attaches, however it arrives, becomes a chip in the composer's attachment strip like a screenshot and a one-unit marker in the draft, and **its whole text is put into the message when the message is sent**. The transcript shows each file as a collapsed row that opens to its content.

The hard part is not the chip. A browser `File` (an `<input>`, a paste, a drag out of Windows Explorer) has no filesystem path, while a file the host can see by path is read by the host, not the page. One rule makes them one thing: **the draft holds a marker and a chip; the text is attached to the message at send, from wherever it lives**: the host reads a file that has a path, and the page holds the text of one that has none. Nothing is written to disk, and OMP, its `@` grammar and the prompt wire grammar (one string and images) are unchanged.

## Goals and Non-goals

- Goals:
  - A text file attached by the attach button, a paste, a drag from Windows Explorer or a drag from VS Code's Explorer or an editor tab shows in the strip as the same chip (file-type icon, name, size, ✕) and in the draft as the same one-unit marker `[File #N: name]`, which Undo, Backspace and ✕ treat like `[Image #N]`.
  - On send the file's **whole text** is part of the message the model receives, in an idle prompt, a steer and a follow-up alike. Nothing is truncated; the limit is the composer's 200 000-character message bound.
  - OMP stores the sent message as one user message. After a reload, a rewind or a resume the transcript draws each file as a collapsed row that expands to the highlighted content, and a restored draft gets its chips back.
  - A file that is not text (a PDF, a zip, a binary) is refused the same way with or without a path, with a sentence. An image stays an image.
  - Images keep working exactly as today, including images dropped by path.
- Non-goals:
  - Sending a path instead of text for a binary, a very large file or a folder: a possible follow-up (*Alternatives* 2).
  - Truncating or summarising a file (decision 14).
  - Writing a copy of a file anywhere; guessing a path from a name.
  - Changing OMP or the prompt wire grammar.
  - Folders (decision 5), remote and virtual file systems, and other platforms than the Windows host the drop path already requires (`src/host/dropped-images.ts:16,47`).
  - A content preview in the chip: it shows an icon and a name; the content is shown in the transcript after the send.

The text rules stay: UTF-8, line endings normalised, no control characters. **Unsaved editor changes are not used (the author's choice, within this decision): the saved file is what is sent**, the same file OMP's `@` mention would read; the host tells the page when an editor holds unsaved changes and the page says so after the send. (*Proposed Design* 2 and 5.)
14. **The whole file is sent; the message bound is the limit (Main's decision).** A file is never truncated. One file is bounded by the composer's 200 000-character message limit, and the whole message, with every inlined file, must fit in it. Over it, the attach or the send is refused, naming the file and its size. The 20 000-character limit of the first revision's no-path rule is dropped: it existed only because a no-path file went into the draft as text, which no longer happens. (*Proposed Design* 1 and 5.)
15. **Non-text documents are refused the same way with or without a path (Main's decision).** A PDF, a zip or any file that is not UTF-8 text is refused with "not a text file". Images stay images. A path reference for a binary is a possible follow-up, not part of this design. (*Proposed Design* 1.)
16. **Wire form: one `<file>` block per file after the user's text (the author's choice, within Main's four requirements).** `<file path="docs/plan.md" n="1" chars="1234">` … `</file>`; the marker `[File #N: name]` in the text is the short reference to block `N`. It mirrors the tag OMP gives the model for an expanded `@file`, is plain text in OMP's TUI, is parsed back from history by counting characters (so content containing `</file>` is safe), and anything that does not parse exactly is plain prose. (*Proposed Design* 4.)
17. **The transcript draws each file as a collapsed row (Main's decision).** A sent user message shows its text as today and, below it, one row per file (icon, name, line count and size) that expands to the content with code highlighting; also after a reload from history. (*Proposed Design* 6.)
18. **Restores give the chips back (Main's decision).** Rewind, queue edit, the ↑/↓ and Ctrl+R history, the recovery of an uncertain original and the draft hand-off restore a sent message by parsing its blocks: the text goes into the draft and each block becomes a chip that holds its content. (*Proposed Design* 7.)
19. **The draft hand-off carries the held text of files (Main's decision).** It carries the held content of files beside the draft text, within the bound of decision 24. (*Proposed Design* 7.)
20. **The host reads only what it attached (the author's choice).** The page never names a path to read; the host mints an opaque `ref` per attached path per tab and the send-time read takes refs. That guarantees three things: no path travels in a hand-off; a stale or unknown ref fails instead of reading something else; and a network (UNC) path is opened only when the user chose it in the host's dialog, because the registry records each entry's origin and the read enforces the drop rule again. It is **not** a defence against a compromised page: the page can already name any local file in `omp:attach-uris`, and under this design the host then returns its text at send, where before it returned only images (the webview runs only Desk's own bundle). (*Proposed Design* 2.)
21. **Ctrl+R history remembers a message with files by reference (the author's choice, amended by Main).** The host's cross-session prompt history (VS Code's global state, 200 entries, 20 000 characters each) stores the prompt with every file block reduced to its reference: the absolute path for a file that has one, the bare name for one that has none, and no content (`omitted="true"`, *Proposed Design* 4). A recall gives a path chip that the host re-validates and re-reads at send, and a note for a no-path file, whose text was not remembered. In-chat ↑/↓ and the "This conversation" list of Ctrl+R read the session's own transcript, have no length bound and restore the full text. "Not remembered" was rejected: the reduced form parses unambiguously (an explicit attribute with `chars="0"`) and dropping the message would lose the user's prose. (*Proposed Design* 7.)
22. ~~**A skill token in a file's text refuses the send (agreed by Main; review finding M1).**~~ **Superseded by decision 25.** The finding stands (OMP turns the whole message into a skill invocation when a whitespace-delimited `/skill:<installed name>` appears anywhere in a `prompt`, a file's text included, and cuts the token out), but the answer is no longer a refusal: Desk escapes the sigil in the file's text (decision 25). What stays: a skill invoked from the user's own text may carry files, so a leading `/skill:x` is not refused with the other slash commands, and the transcript's skill card draws the rows. (*Proposed Design* 4, 5 and 6.)
23. **The fallback route: accept its limits with true sentences (agreed by Main; finding M3).** On the bridge route (after an extension host restart) files with a path cannot be attached or read (the attach, pick and read messages are panel-only) and a message is bounded by the 256 KiB frame: about 37 000 non-Latin to about 230 000 ASCII characters. The attach button is disabled with a reason, a send the route cannot carry is refused with the existing exact `canCarry` sentence, and chunked requests or bridge file operations are a separate later design. (*Proposed Design* 1, 2 and 5.)
24. **The hand-off bound is on the whole capture (agreed by Main; amends decision 10; finding M4).** Restores (queue edit, rewind, recall, Alt+↑) can push a draft past 200 000 characters without the attach-time check, and a refused capture loses the draft. The hand-off therefore carries any draft the page holds: the **sum** of the text, the held file texts and the recoverable texts is bounded by `MAX_DRAFT_HANDOFF_CHARS = 2 000 000`, in memory and never truncated; 200 000 characters stays the **send** limit. (*Proposed Design* 7, *Rollout* 8.)
25. **Escape the text of an attached file with an invisible character (maintainer, via Main, 2026-10-16; supersedes decision 22's refusal and the accepted `^model`, `+N` and `@` exposures of *Risks*).** At send Desk inserts U+200B (ZERO WIDTH SPACE) inside each attached file's text, immediately before every sigil OMP would act on, using OMP's own boundary rules (verified in the installed 18.11.1): `@` at the start of the text or after `\s ( [ { < " '` or a backtick (`FILE_MENTION_REGEX`, `isMentionBoundary`, `P/utils/file-mentions.ts:33-41`); `^model` as `MODEL_MENTION_RE` (`pi-tui/src/prompt/model-mention-syntax.ts:9`); `+N` as `TURN_BUDGET` (`P/modes/turn-budget.ts:13`); `/skill:` as `SKILL_TOKEN_RE` (`pi-tui/src/prompt/skill-tokens.ts:8`). Every boundary `@` is escaped, whether or not the path exists (no filesystem check), and the start of every line of the file is a boundary in the whole message. **Scope:** only the text of attached files; the user's own typed or pasted text is not escaped and its tokens keep working. **Reversible:** Desk removes exactly the U+200B characters it inserted when it draws a row and its expanded content, on copy, and when a block is restored into a held chip (rewind, queue edit, ↑/↓, Ctrl+R, hand-off); the encoding is decodable from the stored text alone and unambiguous for a file that already holds U+200B. The block's `chars` counts the **escaped** text, the characters that are in the stored message, so parsing by count stays exact. The `/skill:` refusal is removed; the slash-command rule for a draft whose own text starts with `/` stays. The rule, its proof and the measurement are *Proposed Design* 4a.

### 2. How an image chip works

- **The draft string is the single source of truth.** An image is attached exactly while its marker `[Image #N, WxH]` is in the text (`Composer.tsx:25-27`, grammar `image-references.ts:23,40-42`). A marker whose number is unknown is ordinary text (`image-references.ts:44-47`).
- **Insertion.** `addFiles` reserves bytes, reads, numbers each image from `nextNumberRef`, publishes the images and calls `insertReferences`, which splices the markers at the caret with a space on each side through the surface so Undo covers it (`Composer.tsx:615-631,676-684`).
- **Rendering.** In the surface a marker is a non-editable inline `span.omp-chip` whose text is the marker (`draft-dom.ts:6-9,71-73,91-93`); Backspace/Delete remove it whole (`image-references.ts:90-110`). Below the field `ul.omp-attachments` lists one `li.omp-attachment` per image with the `data:` thumbnail, `#N`, name, size and a **×** (`Composer.tsx:1539-1566`).
- **Removal and undo.** The × deletes the marker(s) as one undo step (`removeImage`, `Composer.tsx:689-704`); an image whose marker is gone stays in memory only for Undo and is pruned against the budget (`image-references.ts:176-193`, `Composer.tsx:680-681`).
- **Limits.** 5 MiB per image, 10 MiB and 8 images per prompt (`chat-messages.ts:81-101`), checked before reading (`sizeRejection`, `attachments.ts:100-109`) and again at send (`Composer.tsx:851-854`). The grammar's budget sits under the broker's 16 MiB stdin line (`attachments.ts:15-24`, `chat-messages.ts:92-95`). The type is decided by magic bytes, never by the declared type (`sniffImageMimeType`, `attachments.ts:122-123`).
- **Send.** `compactForSend` drops images with no marker and renumbers the surviving markers 1..K because the wire pairs the Nth marker with the Nth image (`image-references.ts:158-174`, `Composer.tsx:826-830`). The message is `{requestId, text, images?}`; `ChatImageWire` is the only attachment shape (`chat-messages.ts:352-373`, parse `:1197-1212,1258-1269`). The RPC line is `{type:"prompt", message: text, images?, streamingBehavior}` with the text unchanged (`src/host/rpc/session.ts:934-982`); `RpcCommand` has no path or file field (`src/host/rpc/rpc.ts:118-122,136-169`).
- **Draft hand-off to a replacement editor.** The capture carries `text` and an attachment **count** only; images cannot be carried and the page tells the user to reattach them (`messages.ts:418-428`, `Composer.tsx:958-1007`, `guest-dispatcher.ts:360-361`). The carried text is capped at `MAX_DRAFT_TEXT_LENGTH = 8192` (`messages.ts:385`); a capture over it is answered `captured:false` (`messages.ts:418-428`, `App.tsx:87-90`). A view switch or an editor replacement then warns "could not be captured … not preserved" and goes ahead, so the **whole draft is lost**; Restart is refused with "Wait for pending image reads or edits to finish", which names the wrong cause (`guest-dispatcher.ts:355-358`, `extension.ts:4200,4351-4354`, `editor-panels.ts:679,806`). Decision 10 raises the cap to 200 000 and *Rollout* 8 corrects the sentence.
- **Rewind, queue restore, prompt history.** Text always survives (`rewindDraft`, `chat/rewind.ts:248-260`; `chat-runtime.ts:894-916`); images may not (`prompt-history.ts:25-33`, `extension.ts:5791-5808`).

### 3. How a path reaches OMP today, and what OMP does with it

> **Background only.** The first revision relied on this section for its wire (`@path`). The current design sends no `@path`, so the idle-versus-steer difference below no longer matters. What still matters is in section 6: OMP scans the **whole** text of an idle prompt for `@` mentions, `/skill:` tokens and `+500k`, which now includes the text of the attached files (*Risks*).

`@path` is the product's reference format. "Add File to Session" and the chat `@` completion produce it:

- `mentionPath(fsPath, cwd)` writes forward slashes, makes the path relative when it is strictly under the session cwd (case-insensitive on win32) and otherwise leaves it absolute with the drive letter (`src/host/file-mentions.ts:150-161`). `mentionTokenForPath` quotes when the path has whitespace, `@`, a quote, a backtick, or a leading or trailing bracket/punctuation, as `@"…"`, or `@'…'` when the path holds `"` and no `'` (`messages.ts:1574,1604-1607`). `formatReference` refuses a control character or both quote kinds (`src/wiring/editor-context.ts:92-98`).
- The session cwd is known to the host (`extension.ts:1115`, `guest-dispatcher.ts:600,623`) and to the page as `ChatHeader.cwd` (`chat-messages.ts:600-607`); `Composer.tsx` does not read it (grep `\.cwd` finds nothing).
- The transcript already turns `@path` in a sent message into a file link (`src/webview/lib/chat-file-links.ts:19-20`).

Verified in the installed OMP 18.11.1 (`P/`):

- **An idle `prompt` expands `@` mentions.** `#promptWithMessage` runs `extractFileMentions(expandedText)` and `generateFileMentionMessages(..., this.sessionManager.getCwd(), …)` and pushes the contents as separate `fileMention` messages after the user message (`P/session/agent-session.ts:8007-8018`; `#promptWithMessage` is reached only from the idle branch of `#dispatchPrompt`, `:7561`). The user text is not rewritten. Syntax: `FILE_MENTION_REGEX = /@(?:"([^"]+)"|'([^']+)'|([^\s@]+))/g`; a mention counts at index 0 or after whitespace or `( [ { < " ' \`` (`P/utils/file-mentions.ts:33-36,44-47`). A bare token loses leading `` `"'([{< `` and trailing `)]}>.,;:!?"'\``; a quoted one is only trimmed (`:34-35,49-55,179`). There is no line-range syntax (`:57-72`).
- **Path resolution.** `resolveMentionPath` → `resolveReadPath(filePath, cwd)` (`:57-72`) → `resolveToCwd`: absolute paths are used as they are, relative ones are resolved against the session cwd (`P/tools/path-utils.ts:320-332`); `file://` and `~` are expanded and `/c/…` is mapped to `C:\…` on win32 (`:116-130,167-175`). A path that does not exist (stat throws) is dropped and its token stays prose (`:61-67`). A UNC path is absolute under win32 `path.isAbsolute` `[INFERENCE, not exercised]`.
- **What is injected.** A text file up to 5 MiB, not binary, is read whole and head-truncated to 3000 lines or 50 KiB; larger or binary files are skipped with a visible `(skipped auto-read: too large|binary file, …)` entry; a directory is listed (500 entries); an image is attached as an image block (`P/utils/file-mentions.ts:41,74-105,107-165,192-334`, `pi-tui/src/tools/streaming-output.ts:11,13`, `pi-utils/src/binary.ts:33-47`). The model sees `<file path="…">…</file>` per file (`P/session/messages.ts:1086-1124`).
- **`steer`, `follow_up` and a `prompt` OMP receives while it is streaming do not expand mentions.** They go to `#queueUserMessage`, which calls no `extractFileMentions` (`P/session/agent-session.ts:7416-7441,8312-8341,8402-8520`; `P/modes/rpc/rpc-mode.ts:1780-1787`; the only two callers of the expansion are `:8008,8010`, both inside `#promptWithMessage`, whose callers are the idle branch `:7561` and `:4886,7732,8646`, none of which carries composer text). Every Desk `prompt` carries `streamingBehavior` (`request.streamingBehavior ?? "steer"`, `src/host/rpc/session.ts:960`), so what happens depends on OMP's own `isStreaming` when the prompt **arrives**, not on the page's `working`: an auto-continue or a hidden next turn that starts in between makes the prompt a queued one with no expansion. The model then sees the literal `@path` and must `read` it. The older design (`2026-10-07-add-editor-context-to-session.md:79`) and a comment at `src/extension.ts:6109-6110` already record this.
- **A plain absolute path with no `@`** is ordinary user text; no code in this flow treats it specially `[INFERENCE: only the prompt-path pre-processors were read]`.

### 4. Is there a downstream cap on the number of images?

The maintainer asked this before removing the count limit. Read in the installed OMP 18.11.1 (`P/` as above; `[INFERENCE]` where a grep, not a full read, is the evidence).

- **OMP's prompt and RPC do not count.** `prompt`, `steer` and `follow_up` take `images?: ImageContent[]` (`P/modes/rpc/rpc-types.ts:40-42`); the idle path and the queue append all of them to the user message (`P/session/agent-session.ts:7466-7469`, `:8459-8462`). A grep of `P/modes/rpc/` and `agent-session.ts` for an image-count constant finds none `[INFERENCE: grep, not a full read]`. The only size rule found there is `MAX_IMAGE_INPUT_BYTES = 20 MiB`, for an image *loaded from a path* (`pi-tui/src/chat/image-loading.ts:4`); the panel's 5 MiB is stricter.
- **The providers' caps are enforced by OMP at send time, per request, over the whole conversation, and non-fatally.** `clampProviderContextImages` counts every image in the context except the model's own output, drops the **oldest** ones past `providerImageBudget(model)` and writes `[image omitted: provider image limit]` where a message loses all its images (`P/session/provider-image-budget.ts:22-25,40-50,110-140`). A provider's own "too many images" rejection is recognised and handled by the recovery path (`P/session/session-maintenance.ts:223-251,2862-2866`). The budget is the catalog's `official-image-count-budget` while the request reaches the official endpoint, else `image-count-budget`, else a **floor of 5** (`snapcompact/src/snapcompact.ts:577-588`, `pi-catalog/src/compat/request-size.ts:34-38`).
- **The catalogued values** (`pi-catalog/src/compat/rules/providers/*.kdl`): Anthropic 90, and 600 on its official endpoint, 100 for models with a 200k window (`anthropic.kdl:85-100`); Amazon Bedrock 90; OpenRouter 90; OpenAI 200; OpenAI Codex 200, 2000 official; Google, Gemini CLI and Vertex 200; xAI 60; Cursor 60, 20 for some models; Google Antigravity 60, 20 for some; Umans 10; every host with no entry 5.
- **So the panel's 8 (`chat-messages.ts:85`) matches none of them.** It is below every catalogued value but one and above the floor of 5 that a custom or local host gets, so a draft of 6 to 8 images can already lose its oldest images silently today. No downstream value is a fixed number the panel could copy: the cap is per request, per model, counted over the history, and enforced by dropping, never by refusing.
- **The panel's own hard-coded 8s** are separate from OMP and are the ones that must change with the limit: `MAX_CHAT_IMAGES` and its parse test (`chat-messages.ts:85,1199`), `MAX_DROP_URIS = MAX_CHAT_IMAGES` for the drop request, the reply and the page's URI read (`messages.ts:252,1243,1418`, `Composer.tsx:781`), `MAX_RESTORED_IMAGES` for a dequeued message (`src/host/rpc/session.ts:331,339,484`), and the literal `8` that clips a rewound draft's images (`src/host/chat-runtime.ts:896`, test `chat-runtime.test.ts:1189`). The tests `chat-messages.test.ts:239,259-264` and `messages.test.ts:195` pin them.
- **The one fixed downstream bound is the broker's 16 MiB stdin line** (`pty-protocol.ts:144`, `rpc-handle.ts:147`). The byte budget is sized under it: 10 MiB is 13 981 016 base64 characters, a worst-case 200 000-character text is about 1 200 000 bytes of escapes, and 16 MiB is 16 777 216, which leaves about 1 596 000 bytes of which the test requires 512 KiB (`chat-messages.ts:92-95`, `chat-messages.test.ts:258-268`). Each image also costs about 50 bytes of JSON (`{"type":"image","data":"…","mimeType":"image/webp"},`), so without a count the line would overflow at roughly 20 000 images `[INFERENCE: computed from the numbers above, not exercised]`. The byte budget alone does not prevent that: a 1×1 PNG is about 70 bytes.

Conclusion: **no downstream cap justifies a panel cap of 8 or of any other number, and none of them refuses; OMP drops the oldest images and says so in the request.** Removing the count is safe for correctness, but it exposes one silent effect (the model may see fewer images than the draft shows; decision 8 leaves it unannounced) and needs a finite parser bound for the broker line (decision 9).

### 6. What inlining depends on

Rewind and branch return the user text unchanged. `[INFERENCE: two scout reads; slice 0 reads a real session file]`

## Proposed Design

### 1. One draft form; the entry points

Every document, however it arrives, gets the same chip in the strip, the same atomic marker in the draft and the same tile. Only where its text lives until the send differs:

| Entry point | Path | Where the text is until the send |
| --- | --- | --- |
| **Attach button** | **New host dialog**: the page posts `omp:pick-files {requestId}`; the host calls `showOpenDialog({canSelectMany:true, canSelectFolders:false, defaultUri: session cwd, openLabel:"Attach"})` and answers with the same reply as a drop, **always**: the host wraps the dialog in `try/finally`, and a cancelled or failed dialog answers an empty reply, which also settles the request. The page arms **no timeout** for a pick (a native dialog left open for more than 10 s is ordinary). The pick counts in the `reading` counter as a drop does. A path on a network share is accepted (decision 11). The `<input type="file">` is removed (decision 1). | In the file. The host read it once, to validate it (*Proposed Design* 2); it reads it again at send. |
| **Drag from VS Code's Explorer or an editor tab** | `file:` URIs, sent by the existing `omp:attach-uris`. | Same. |
| **Paste of an OS file** | None. | In the page: the `File` is read whole when it is attached and its text is held in memory. |
| **Drag from Windows Explorer** (with Shift) | None. | Same as a paste. |

An **image** from any entry point stays an image: a `File` is classified **first**, by its first bytes (`file.slice(0, 16)`, `sniffImageMimeType`), before `sizeRejection`, so a 6 MiB `.pdf` is never told it "exceeds the 5.0 MB limit per image" (`attachments.ts:100-109`); an image dropped by path is still read by the host and sent as an image, as today. A file whose magic bytes name an image format Desk does not take (BMP, TIFF, HEIC) keeps today's format sentence (`unsupportedReason`, `attachments.ts:154-163`) and is not called "not a text file".

A **non-image `File`** is first checked on a bounded prefix: the text rule (*Proposed Design* 2) runs on its first 64 KiB (an incomplete trailing UTF-8 sequence ignored), so a binary of any size is refused as "not a text file"; the host sniffs the type **before** today's per-image size check (`dropped-images.ts:68-75`) for the same reason. A file that passes is read whole, but only after a size check on the file itself: above `MAX_DOCUMENT_BYTES = 600 003` (3 bytes per UTF-8 character of 200 000 characters, plus a BOM) it is refused unread. The bytes go through the one text rule, shared by page and host. The refusals, each naming the file, are:

- `plan.pdf is not a text file (its bytes are not UTF-8).` / `… (it contains control characters).` The same sentences with or without a path (decision 15).
- `big.md is 312 004 characters; one message carries at most 200 000.` (for a file above the byte bound, its size in bytes or MB instead of characters.)
- `Adding big.md (150 000 characters) would take the draft over 200 000 characters.` The attach also refuses when the draft's text plus the known characters of every document, held or linked, plus the new file would pass the limit. It is a courtesy check (the send is the authority, *Proposed Design* 5); it keeps the draft below the size the hand-off carries (decision 19).
- `docs: a folder cannot be attached; attach the files in it.` (decision 5)

An empty file is a valid document (`0 B`). A file with no path is never matched to a path by its name, looked up in recent files or copied to disk; `File.path` is not used even if a future Electron exposes it, so the host is the only path source. `[INFERENCE]` Slice 0 measures what each entry point delivers in the installed VS Code, so this table is a measurement and not a guess.

A second attach of the same **linked** file (the same `ref`, *Proposed Design* 2) is reported as `notes.md is already attached.`. A file with no path has no identity and is never a duplicate.

A pick has no timeout, so the page settles it when its route changes or the host link is lost: `reading` returns to zero, and the draft can be sent and captured again; the host answers an empty reply when it still can. On the fallback route (decision 23) the attach button is disabled with `Attaching files needs the editor's connection to the extension host; reload the window.`, and a drop of file URIs says the same instead of today's "paste the image or use the attach button" (`Composer.tsx:750-753`).

### 2. The host: attach, read at send

**The text rule** lives in one pure module for page and host, `src/shared/text-file.ts`: `decodeTextFile(bytes)` decodes with `new TextDecoder("utf-8", { fatal: true })`, drops a leading U+FEFF, normalises line endings to `\n` (`normalizeLineEndings`, `draft-text.ts`; a lone `\r` is a line ending) and refuses a result that holds a control character other than tab and newline (`DRAFT_CONTROL_CHARACTER`, `messages.ts:394`, moved there and exported). It returns the text or one of the two reasons above. There is no extension or MIME rule: a file is text because its bytes are, so `Makefile`, `.foo` and a renamed `.png` that is not an image are decided by content (an SVG is an XML text file and a document).

**Attach.** `readDroppedImages` (`dropped-images.ts`) is generalised to `readAttachedFiles(paths, cwd, tab)`. For each distinct path it applies the existing refusals (scheme, host for a relayed URI, drive, not a file, changed while read; a folder gets its sentence) and classifies by magic bytes: an image follows today's size rules and is returned as an image; anything else is **read whole** (the byte bound above, then the text rule and the 200 000-character bound), and becomes a `document` item **without its content**. The reply keeps the input's order, which keeps image and file markers of one drop in drop order:

```
omp:attached-files { requestId, items: AttachedItem[], refusals: string[] }
AttachedItem = { kind: "image", name, mimeType, data } | { kind: "document", name, ref, bytes, chars }
```

`omp:attach-uris` and `omp:pick-files` share it. `ref` is **opaque** (decision 20). The host owns a registry per tab, held by the guest dispatcher and dropped with the tab (a host restart loses it): `ref → { absolute path, origin: "dialog" | "drop" }`, and an inverse keyed by `comparablePosix` (`file-mentions.ts:140-143`), so a path attached twice, in any casing, returns the same `ref` (the page's duplicate test). At the guard's 1 000 entries the **least recently used** entry is evicted, not refused (the guard is not a user limit, decision 9); a draft whose chip lost its entry fails at send with `attach it again`. The read enforces the drop rule again for an entry of origin `drop`, so a network path is opened only when the user chose it in the dialog. The page never sees, formats or resolves a path. Parse limits in `messages.ts` beside `:1275`: `name` 1–255 characters without control characters, `ref` a short identifier, `bytes` and `chars` non-negative safe integers, `items` and `refusals` bounded by `MAX_ATTACH_ITEMS` (*Proposed Design* 9), each refusal 400 characters, and the base64 total over `image` items only. The dispatcher keeps its rule: the answer goes only to the panel that asked and never to a replaced one (`guest-dispatcher.ts:612-620`), and the dialog is not shown to a replaced panel.

**Read at send.**

```
omp:read-files  { requestId, files: [{ number, ref }], budget }
omp:files-read  { requestId, files: [{ number, label, content, dirty }],
                  failures: [{ number, name, reason }] }
```

The host reads the files in order. For each `ref` it requires the registry entry (`that file is no longer known; attach it again`), then `stat` (missing: `plan.md no longer exists`; not a regular file), a size at most `MAX_DOCUMENT_BYTES`, the whole read and the text rule again; the file may have changed since the attach, so it is validated again, and a failure is a failure in `failures`, not a refusal of the whole request. The running sum of characters may not pass `budget` (the page's remaining room, so the host stops early; reason `over the message limit`). `label` is `mentionPath(absolute, cwd)` raw, with no quoting (`file-mentions.ts:150-161`): relative with forward slashes inside the session's cwd, absolute with the drive letter outside it, and **absolute when the session has no cwd yet**. `dirty` is true when an open editor holds the same path with unsaved changes (`vscode.workspace.textDocuments`); the **saved file** is what is sent (decision 13). The reply goes only to the asking panel, as above. The request timeout is 10 s plus 1 s per file, and its sentence says `reading the files took too long`, not that the host did not answer.

Any failure refuses the whole send; nothing partial is sent. `omp:check-paths` is not needed and is not added.

**Fallback route and host restart (decision 23).** On the bridge route the panel-only messages are not sent (`post` returns `false`), and after a host restart the registry is empty. A draft with a linked file it cannot read there is refused at send at once, with `plan.md cannot be read over this connection; reload the window and attach it again.`; held files and text still send, bounded by the exact `canCarry` check (*Proposed Design* 5).

### 3. The marker, the chip and the strip

- **Marker.** `[File #N: name.md]`. `N` comes from its own counter (documents are not paired with wire positions the way images are, so they are not renumbered at send). The name is the file's base name with `[` and `]` replaced by `(` and `)` and control characters by a space, clipped at 60 code points (`markerName`), so the marker has one grammar: ``\[File #([1-9]\d*): ([^\]\n]+)\]``. As for images, a marker of an unknown number is ordinary text (`image-references.ts:44-47`), so a hand-typed `[File #1: x]` stays prose. Unlike an image marker, which counts with any tail, a file marker is the **reference of a block** (*Proposed Design* 4), so it counts only when its **whole label equals that document's own label**: a pasted `[File #1: other.md]` is prose (the finder's known-test takes the label as well as the number, not `isKnown(kind, number)` alone). Quote capture neutralises `[File #N` in quoted text as it does `[Image #N` (`neutraliseImageMarkers`, `quote-draft.ts:32-33`); a restore brings in text whose markers are orphans (no document of that number in the draft), and an orphan marker is prose by the rule above, so a restore needs no neutralisation.
- **One reference finder, five invariants (ADR-0077).** `findImageReferences`, `referencedNumbers`, `snapSelection`, `deletionRange` and `repairDamagedReferences` (`image-references.ts:48-141`) become reference-kind-aware: a span has `kind: "image" | "file"`. (1) The finder returns **one start-sorted, non-overlapping span list** from one combined regex scanned leftmost-first, because the image tail `(?:,[^\]\n]*)?` can swallow a file marker (`[Image #1, x [File #2: a.md]`), and `lineSpecs` walks the spans in order (`draft-dom.ts:62-66`); a test pins that case. (2) `isKnown(kind, number)`: the number spaces are separate, and the image-only consumers stay image-only: `activeImages`, the image renumbering of `compactForSend`, `pruneInactive` and the restore counter bump (`Composer.tsx:997-1001`). (3) `lineKey` includes `kind` (`draft-dom.ts:72-74`), so a chip of the other kind at the same offsets and number cannot keep a stale DOM node. (4) A file chip keeps `CHIP_CLASS` plus a modifier class (`data-kind="file"`), so `isChip` and the caret mapping still treat it as atomic; it has a file icon and `aria-label="File #N, name.md"`, not `role="img"`. (5) `snapSelection`, `deletionRange` and `repairDamagedReferences` stay purely geometric. The string stays the source of truth.
- **Insertion** reuses `insertReferences` (`Composer.tsx:615-631`) with the file markers; the ordered `items` of one reply give image and file markers in drop order.
- **The strip.** `ul.omp-attachments` (`Composer.tsx:1539-1566`) gets `aria-label="attachments"`; a document's `li.omp-attachment` has the same layout with a **tile** in place of the thumbnail: a codicon chosen by the file's extension (`markdown`, `file-code`, default `file`) with the extension in capitals, `#N`, the name, the size and a ✕ that calls the same removal (`removeImage` becomes `removeAttachment`, one undo step, `:689-704`). The tooltip of a linked file is `read from disk when sent` (the page holds no path), of a held file with a label (a restored one) the label, and of a held file without one `no path: the text is held in the draft`. No file text is shown. The strip scrolls (`max-height` with overflow).
- **State.** `DraftDocument = {number, name, source}` in `documentsRef`, with the lifecycle of `imagesRef`: published with the markers, retained after marker deletion only for Undo, cleared on send. `source` is `{kind:"linked", ref, bytes, chars}` or `{kind:"held", content, label: string | null, bytes}`; `label` is the path text of a document restored from a sent message (*Proposed Design* 7), `null` for a file that never had a path. A held document's text is memory the draft owns: the sum of the documents retained only for Undo is capped at 200 000 characters, oldest pruned, like images (`image-references.ts:176-193`).
- **Controls.** The attach button's label and tooltip become `Attach files` and `Attach a file or an image. You can also paste an image or a file, drag one here with Shift, or drag a file from VS Code's Explorer.` (`Composer.tsx:1415-1416`). It stays disabled while reading; the picker and a drop share the `reading` counter, but only a drop has the 10 s request timeout.

### 4. The wire form: the file block

The prompt wire is **unchanged**: `{requestId, text, images?}`. The text is the user's text, followed by one block per attached file:

```
Summarise [File #1: plan.md] and compare with [File #2: notes.md]

<file path="docs/plan.md" n="1" chars="1204">
…the 1204 characters of the file, line endings \n…
</file>

<file name="notes.md" n="2" chars="87">
…
</file>
```

- **Grammar.** Header: `<file ` then `path=` (a file with a path: its label) or `name=` (a file with none: its name), the value a JSON string; ` n="N" chars="C">` and a newline. Content: exactly `C` UTF-16 code units (`content.length`). Footer: a newline and `</file>`. Blocks are separated by one blank line, the first is separated from the text by one blank line, and the last ends the message. An empty file is `chars="0">` and two newlines. It is the tag OMP uses for its own expanded `@file` (*Current State* 6) with two more attributes, so the model and OMP's TUI see familiar, readable text.
- **Compose and split** are one pure module, `src/shared/file-blocks.ts` (`composeFileBlocks(prose, docs)`, `splitFileBlocks(text)`). The page composes at send; the host never sees blocks except as part of a user's text it relays. The `[File #N: name]` marker **stays** in the text: it is the short reference to block `N`. Numbers in one message ascend and are not renumbered.
- **Parsing back is by count, never by searching for the closing tag.** `splitFileBlocks` finds each candidate start (a blank line, then `<file ` with a well-formed header) in order and tries to read a **chain**: header, exactly `C` units, `\n</file>`, then either the end of the text or `\n\n` and the next header. A chain is accepted only if it ends exactly at the end of the text, its numbers strictly ascend, there are at most `MAX_ATTACH_ITEMS` blocks, and the text before it contains, for each block, the marker `[File #N: markerName(name)]`. The first candidate that yields an accepted chain wins. Reachability (does the walk from this position reach the end of the text) is memoised per position, so parsing is linear; the semantic checks (ascending numbers, markers) run per candidate and are never memoised, so a forged block that chains into a real one cannot hide the real chain. A block's name is its `name=` value, or the last segment of its `path=` label (split on `/` and `\`). A header may carry `omitted="true"` after `chars`, only with `chars="0"`: the reduced form the host's Ctrl+R history stores (decision 21); the page never composes one. So a file that contains `</file>`, a whole block or a header is read correctly (its content is skipped by count), and the text of a plain message is returned unchanged when nothing parses.
- **When it does not parse, it is prose.** A message that does not end in a valid chain (typed or pasted text that looks like a block; a block whose length OMP's `^model` rewrite changed; a message from another client) is shown and restored as the text it is. Nothing is lost and no text is ever dropped. Typed text that does form a valid chain is the user's own text drawn as a file row: it shows nothing that was not sent, and the model reads the same bytes either way (a `^model` token, which OMP acts on wherever it stands, is the exception and an accepted exposure, *Risks*).
- **What OMP does with it.** On a `prompt` OMP scans the whole text (*Current State* 6): an `@src/a.ts` makes an idle OMP read that file, `^model` registers a delegation agent and is rewritten in the stored text, `+500k` sets a turn budget and `/skill:<installed name>` turns the whole message into a skill invocation. **Decision 25 removes all four for a file's text:** Desk escapes each sigil with U+200B (*Proposed Design* 4a), so OMP sees none of them and the stored text keeps its length. A text that starts with `/` is a slash command to OMP: a draft that carries files and starts with `/` is refused (`A message that starts with / is a command and cannot carry files.`) unless it starts with `/skill:<installed name>`, a skill invocation, which may carry files; the installed names are the `skill:` commands of `snapshot.commands`.

### 4a. Escaping a file's text (decision 25)

`src/shared/file-blocks.ts` owns it beside compose and split: `escapeFileText(text)` and `unescapeFileText(text)`; `composeFileBlocks` escapes each document's content and writes `chars` for the escaped text, `splitFileBlocks` counts the escaped text and returns the original content. Nothing else sees the escape: the chip, the held text, the hand-off and the Ctrl+R reduced form carry the original.

- **Sites.** Scan the text for the four sigil characters. A position `j` is a **site** when (a) its sigil pattern holds at `j`, tested on the text itself with a sticky regex: for `@`, nothing more (a bare `@`, because OMP's token grammar is not evaluated: every `@` that follows a boundary is escaped); for `^`, `\^[^\s^]+(?=\s|$)`; for `+`, `\+\d+(?:\.\d+)?[km]?!?(?=\s|$)` with the `i` flag; for `/`, `\/skill:[^\s/]+(?:\/[^\s/]+)?(?=\s|$)`; and (b) the **boundary** holds before the maximal run of U+200B that ends at `j`: that run starts at index `i`, and either `i = 0` or the character before `i` matches the sigil's boundary: ``/[\s([{<"'`]/`` for `@`, `\s` for the other three. The start of the file's text is a boundary because the block opens after a newline, and the end of the text satisfies `(?=\s|$)` because the block closes with a newline.
- **Escape.** Insert one U+200B at `i` for every site, counting the run: a site with `k` existing U+200B before the sigil ends with `k + 1`. Existing U+200B characters that precede a boundary sigil are therefore escaped too (the maintainer's suggestion), which is what makes the inverse unambiguous: in the original text such a site is shadowed (the character before the sigil is U+200B, which is neither `\s` nor a boundary character, so OMP would not act), and the stored text still has one more U+200B than the original.
- **Unescape.** Find the same sites in the stored text (the lookahead tests read characters that escaping never changes, and the inserted U+200B stands after a boundary character, never inside a token or between a token and its terminator) and remove one U+200B from the run of each. A run of length 0 is not a site of the stored text. `unescape(escape(t)) = t` for every string, including one with a run of U+200B, with CRLF, with a sigil at the start of the text or of a line and after a backtick; the property test generates such text and also checks that none of OMP's four patterns, copied from the installed source, matches `escape(t)` at a boundary.
- **Why U+200B is not whitespace.** JavaScript's `\s` does not include U+200B (it is a format character), so a U+200B between a boundary and a sigil breaks all four patterns at once, and `@` after it is not at a boundary. Measured below.
- **The header.** A label or a name is written as a JSON string. The same four sigils can follow a space inside a file name (`a @b.md`, `x ^y`, `n +5`, `s /skill:k`), where OMP would act on them in the header line, so a header's string value writes every `@`, `^` and `+`, and the slash of `/skill:`, as a `\uXXXX` escape: `JSON.parse` returns the original, the model sees a readable value, and no ZWSP is needed in a header. The marker `[File #N: name]` is part of the user's own text and is not escaped; a file named `@x.md` shows its marker with a boundary `@` in the user's text, an exposure the decision accepts because the marker is the user's text and the name is the file's own.
- **Size.** Escaping adds at most one character per site; the send length check (*Proposed Design* 5, step 6) measures the composed text, so a file of 200 000 characters made of `@ @ @ ` may pass the attach check and be refused at send with the figures.
- **Measured (slice 0, installed OMP 18.11.1, the real `omp --mode rpc`, a mock OpenAI server recording each request, 2026-10-16).** One idle `prompt` carrying `@probe.txt ^mock-model +500k /skill:probe-skill` on a line of its own acted on all four: the skill ran (the message became a `skill-prompt` custom entry and the model received the skill text), the token was cut out, and an `<file path="probe.txt">` block followed. The same line with U+200B before each sigil, sent as an idle `prompt` and as a `steer` during a running turn, was stored verbatim in the session file (the U+200B bytes unchanged), reached the model verbatim in the request, and none of the four acted: no skill entry, no file read, no mention rewrite. So OMP does not normalise U+200B away.

### 6. The transcript: one collapsed row per file

- The text of a **user** message (the `references` flag of `MessageContentView`, which is shared with assistant content, `MessageContent.tsx:62-72`) passes through a memoised `splitFileBlocks` in the text case (`:54-55,73`) before it is drawn; so does the prompt of a skill card (`userSkill(…).prompt`, decision 22), whose rows go under its header. ### 7. Restore, history and the hand-off

`draftFromSentText(text)` (page, pure over `splitFileBlocks`) turns a sent text into a draft: the prose and, for each block, a **held** document (`content`; `label` from a `path=` block, `null` from a `name=` block; `name` as in the marker), with the markers kept and the counter moved past them. Joining a non-empty draft renumbers the restored markers and block numbers to continue the draft's own, in one pass. A restored document composes back at the next send as `path=label` when it has a label and `name=` when it has none.

### 9. Counts: what changes when the limit goes (decision 7)

The user-facing rule becomes the byte budgets alone for images (5 MiB per image, 10 MiB per prompt, `chat-messages.ts:86-101`; `sizeRejection`, `attachments.ts:100-109`). Documents have no count (the guard of decision 9 aside) and no byte budget of their own: their bound is the 200 000-character message limit (decision 14, *Proposed Design* 1 and 5).

- **Constants.** `MAX_CHAT_IMAGES` (`chat-messages.ts:85`) is removed as a rule. Everything listed in *Current State* 4 that read it or a literal 8 follows: the image parse, the drop request and reply, the page's URI read, `MAX_RESTORED_IMAGES` and the rewind clip. Each is replaced by the **parser guard** `MAX_ATTACH_ITEMS = 1000` (decision 9), which is a bound on array length for the parser and the broker line, not a rule the user is told about. The guard is complete only with four more sites: (a) `droppedFileUris` silently stops at `limit` (`attachments.ts:203-209`), which would lose item 1001 onward without a word; it reads `limit + 1` and refuses the whole drop; (b) a `canSelectMany` dialog result is checked against the guard in the host before any read; (c) the guard is enforced **when attaching**, across several drops, picks and pastes into one draft, so the prompt parse never rejects a send `[INFERENCE: what the page shows for a rejected omp:chat-prompt was not read]`; (d) the reply's `refusals` bound becomes `MAX_ATTACH_ITEMS`. A restored or rewound message keeps every image **within the per-prompt base64 budget**: a set over it is reported dropped as a whole (`parseImages`, `chat-messages.ts:1198-1224`), and `imagesDropped` / `unavailableImages` count what is truly unavailable (a `blob:` reference, `rewind.ts:248-260`) or over the budget. A drop or draft above the guard is refused with `at most 1000 files can be attached at once`.
- **The base64 bound** `MAX_CHAT_IMAGES_BASE64_CHARS = ceil(10 MiB / 3) * 4` (`chat-messages.ts:101`) is a sum of per-image figures, and each image rounds up to a multiple of 4 characters, so a full budget of many small images exceeds it by up to 4 characters an image. The page would accept a draft the parser then refuses. The bound becomes `ceil(BYTES / 3) * 4 + 4 * MAX_ATTACH_ITEMS`, and a test fills the budget with the most images the guard allows.
- **The line budget** `chat-messages.test.ts:258-268` is rewritten for the guard: the worst case is a full byte budget carried by `MAX_ATTACH_ITEMS` images plus a worst-case text, and it must stay under `PTY_RPC_MAX_WRITE_BYTES` with the same 512 KiB to spare. With a guard of 1 000 the images add about 50 KB.
- **Cost per image in the page.** Each image is decoded once for its size (`decodedSize`, `attachments.ts:129-139`) and shown as a `data:` thumbnail (`Composer.tsx:1544`); the 10 MiB budget bounds the memory, and the strip scrolls (*Proposed Design* 3).
- **What the user sees for a draft the model cannot fully take.** OMP drops the oldest images of the request (*Current State* 4). By decision 8 the composer does not say so.

## Alternatives

1. **`@path` as the wire (the first revision).** One reference format and a short message, but OMP expands a mention only on an idle prompt and only the first 3000 lines or 50 KiB, so a steer or a long file reaches the model as a name; and a file with no path needs a different form. Rejected by the maintainer (decision 13). It remains the natural form for a binary or a very large file, a possible follow-up that decisions 4 and 15 leave open.
2. **A plain absolute path with no `@`.** The model must call `read`; nothing is injected. Loses the content in the message and the collapsed row. Rejected with 1.
3. **Copy pathless files into the workspace, `.omp/` or a temp folder and send that path.** Writes user data to disk without being asked, needs a lifetime and a cleanup, and a copy in the workspace can end up in a commit. Rejected; an explicit "Save a copy" remains a possible later request.
4. **Keep the browser `<input type="file">` and add a second button for the host dialog.** Two buttons for one verb. Rejected by decision 1.
5. **A structured `documents` field on the prompt wire** instead of text blocks. `RpcCommand` has no such field (`src/host/rpc/rpc.ts:118-122,136-169`) and OMP persists only text and images, so a field would be lost on reload, rewind and resume, and would need an OMP change. Rejected: the text is the single source of truth, as for the quote feature.
6. **A Markdown fence as the wire** (a `lang title=name` fence around the content). Collides with fences inside the content (the fence length must be computed), and is no more readable than OMP's own tag. Rejected.
7. **Read a linked file's text when it is attached and hold it, as for a no-path file.** Simpler (one source), but the model would see a stale file after an edit, and a large file would sit in the page. Rejected by decision 13.
8. **Send an open editor's unsaved text.** What the user sees is what is sent, but the host would have to trust a buffer OMP's `read` would not see, and the content would differ from the file the model can open by its label. Not chosen (decision 13); the unsaved note is the compromise. Cheap to change: the host's read is the one place.
9. **Truncate or summarise a large file** as OMP does for a mention. Rejected by decision 14.

## Risks and Open Questions

- **OMP acts on sigils in text.** `/skill:`, `^model`, `+N` and, on an idle prompt, `@path` are read from the **whole** text of a `prompt`, a file's text included (*Current State* 6). Decision 25 escapes them in a file's text with U+200B (*Proposed Design* 4a), measured to stop all four on an idle prompt and a steer. What stays: the user's own typed or pasted text is not escaped, so its tokens work as before; the marker of a file whose name has a boundary sigil is in the user's text; an installed extension's `input` handler may rewrite or swallow the text of any of the three (*Current State* 6), after which the message parses as prose or not at all; and `</file>` inside a file's text looks like a closed block to the model, as with OMP's own `@file`. A model or a tool that copies the file's text back copies the invisible character with it, which is harmless to text and visible only to a byte comparison.
- **A large file costs context.** Nothing is truncated, so a 200 000-character file puts about that many characters of text in one message; the chip shows the size, the refusals name the limit, and OMP's own context-overflow handling answers a conversation that is too large.
- **Entry-point behaviour is partly inferred.** What a paste and an Explorer drag deliver in this webview was not measured. Slice 0 measures it; the table in *Proposed Design* 1 is amended with the maintainer's agreement, never silently.
- **The fallback route has narrower limits** (decision 23): no linked files, and a message bounded by the 256 KiB frame (about 37 000 non-Latin to 230 000 ASCII characters), refused with a true sentence. The normal editor panel has no such limit `[INFERENCE: postMessage]`. This is a limit of the transport below the maintainer's 200 000; chunking the request or adding bridge file operations is a separate design.
- **Queue and history bounds.** A queued message above 128 KiB of JSON is not listed or editable (it still sends). Ctrl+R remembers messages by reference only, up to 20 000 characters of reduced text (decision 21). Both are stated in the guide.
- **The send reads the saved file.** An editor with unsaved changes sends the older text and says so after the send (decision 13). Reading the live buffer is a one-place change if the maintainer prefers it (*Alternatives* 8).
- **A held file's text is memory the page owns and the hand-off copies.** Bounded: the courtesy check at attach, the cap on the retained-for-Undo set, and the 2 000 000-character bound of the capture (decision 24); a held restore can exceed the send limit, and the send then refuses with the figures.
- **A restored document is not re-read.** A rewind restores what was sent; if the user then edits the file on disk, the restored chip still carries the old text, which is what a rewind means.
- **The reference finder is shared with the image chip.** Its existing tests (`image-references.test.ts`, `chat-ui.test.ts`) must stay green unchanged.
- **Registry loss and eviction.** A linked document whose host registry entry is gone (a host restart, a tab reopened while a hand-off carried it, or an eviction at 1 000 entries) fails the send with `attach it again`; nothing is lost silently.
- **Link rendering is bounded** (`chat-file-links.ts:13`, 64 references; the bare form stops at brackets). Cosmetic, for the prose only.

### Open questions

None for the maintainer: decisions 22 to 24 were resolved with Main on the review's findings; decision 25 is the maintainer's; the review is in *Architecture Review*.
