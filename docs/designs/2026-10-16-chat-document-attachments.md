# Attach documents to a Chat message as paths

Revised 2026-10-16: the maintainer's answers to questions 1 to 8 of the drafts, Main's decision on question 9 and Main's decisions on the two items the architecture review reserved (10, 11) are in *Decisions*; no question is open. Decision 3 (a file with no path goes into the draft as text, or is refused) is *Proposed Design* 9. The independent architecture review (accepted with changes, all resolved in the text) is recorded at the end.

## Problem

The maintainer's request: "Draw them like screenshots (a chip with a preview), but send them to OMP as a path to the file."

Today the composer accepts images only. Attaching `notes.md` shows `notes.md: unsupported format (text/markdown) — attach PNG, JPEG, GIF, or WebP.` (`src/webview/lib/attachments.ts:154-163`). The only ways to give OMP a file are typing an `@` mention by hand or the "Add File to Session" command, which inserts a `@path` line from an editor (`docs/designs/2026-10-07-add-editor-context-to-session.md:26-34`). Neither gives the draft a visible attachment: no chip, no ✕, no preview, and nothing that tells the user the file was understood.

This design adds **document attachments**: any non-image file the user attaches becomes a chip in the composer's attachment strip, exactly like a screenshot, and is sent to OMP as a reference to the file's path, not as bytes.

The hard part is not the chip. A browser `File` (from an `<input>`, a paste, or a drag out of Windows Explorer) has no filesystem path, and a path is the whole point. Section 1 of *Current State* lists, per entry point, whether a real absolute path exists at all; the design takes a path only from places that have one and refuses the rest with a sentence. It never writes a copy of a file anywhere.

## Goals and Non-goals

- Goals:
  - A non-image file attached through the attach button or dropped from VS Code's Explorer or an editor tab shows in the strip as a chip (file-type icon, name, size, ✕), and as a one-unit marker in the draft that Undo, Backspace and ✕ treat like `[Image #N]`.
  - On send, the file reaches OMP as a path: an `@` mention in the message text, in the form the product already uses for "Add File to Session" (relative to the session's cwd when inside it, absolute otherwise). No file bytes ride the prompt.
  - A file that has **no path** (a paste, a drag out of Windows Explorer) is never lost silently: a text file of at most 20 000 characters goes into the draft as a fenced code block of its content, and anything else is refused with one sentence that names the two routes that have a path. No silent copy, no guess from a file name, nothing written to disk.
  - Images keep working exactly as today, including images dropped by path (they are still sent as images).
- Non-goals:
  - Sending a document's bytes or text inline when it **has** a path (a different feature; see *Alternatives*). The one text-in-the-draft case, a text file with no path, is the user's own draft text (decision 3, *Proposed Design* 9), not an attachment.
  - Writing a copy of a pathless file into the workspace, the session folder or a temp folder (decision 3 chose text-or-refusal instead).
  - Changing how OMP reads `@` mentions, or any change to the prompt wire grammar beyond what *Proposed Design* lists.
  - Folders (decision 5), remote and virtual file systems, and other platforms than the Windows host the drop path already requires (`src/host/dropped-images.ts:16,47`).
  - A content preview or a document viewer. The chip shows an icon and a name; no file content is read into the page (decision 6).

## Decisions (maintainer, 2026-10-16)

Answers to the open questions of the drafts. They are inputs, not proposals; the sections below say how each is realised. Decision 9 is Main's, on a parser and line bound, and is marked as such.

1. **Button: one host dialog for everything.** The attach button opens VS Code's file dialog (`showOpenDialog`, in the host) for images and documents alike. An image picked there comes back as an image; the browser `<input type="file">` is removed. (*Proposed Design* 1.)
2. **Format: `@path`.** A document is sent as an `@` mention in the message text, in the product's existing reference form. (*Proposed Design* 4.)
3. **A file with no path: its text, or a refusal.** A text file (UTF-8 decodable, no NUL, a known text type or extension) of at most 20 000 characters goes into the draft as a fenced code block of its content, the info string taken from its extension and the fence `max(3, L + 1)` backticks long, as for quotes. Every other file with no path is refused with a sentence naming the two routes that do have a path. A text file over 20 000 characters is refused, with its size. (*Proposed Design* 9.)
4. **A file that is gone at send: refuse.** The send is refused with a message naming the file, and the draft is kept. (*Proposed Design* 4.)
5. **Folders: refuse for now.** (*Proposed Design* 7.)
6. **Preview: icon and name only.** No file content is read into the page. (*Proposed Design* 3.)
7. **Count: no limit for documents, and none for images either.** Only the byte budgets stay for images (5 MiB per image, 10 MiB per prompt). The maintainer asked first for the downstream facts: they are in *Current State* 4 and the change is *Proposed Design* 8.
8. **No note about provider image caps.** The composer says nothing about how many images a provider takes; OMP alone drops the oldest images of a request (*Current State* 4).
9. **A structural guard of 1 000 items (Main's decision, 2026-10-16).** `MAX_ATTACH_ITEMS = 1000` bounds the length of every attachment array in the grammar. It is a bound on the parser and on the broker's 16 MiB line, not a user-facing limit, and the user is not expected to meet it. (*Proposed Design* 8.)
10. **The draft hand-off carries anything the composer can send (Main's decision, 2026-10-16, review finding H).** `MAX_DRAFT_TEXT_LENGTH` is raised from 8192 to `MAX_CHAT_TEXT_LENGTH` (200 000). Today a capture over 8192 characters is answered `captured:false`, and a view switch or editor replacement then loses the whole draft; a 20 000-character text block or quote, or mentions that grow a draft, would always hit it. The change amends ADR-0050's bounded hand-off (the amendment is written in that ADR) and is a separate small slice that may land first (*Rollout* 8).
11. **UNC and network paths are accepted from a host dialog (Main's decision, 2026-10-16, review finding F).** The user chose the file in a host-owned dialog, so the "Windows authenticates to a share by itself" reason for refusing a host-bearing URI does not apply. A URI relayed from a page drop is still refused. (*Proposed Design* 1 and 7.)

### 2. How an image chip works

- **The draft string is the single source of truth.** An image is attached exactly while its marker `[Image #N, WxH]` is in the text (`Composer.tsx:25-27`, grammar `image-references.ts:23,40-42`). A marker whose number is unknown is ordinary text (`image-references.ts:44-47`).
- **Insertion.** `addFiles` reserves bytes, reads, numbers each image from `nextNumberRef`, publishes the images and calls `insertReferences`, which splices the markers at the caret with a space on each side through the surface so Undo covers it (`Composer.tsx:615-631,676-684`).
- **Rendering.** In the surface a marker is a non-editable inline `span.omp-chip` whose text is the marker (`draft-dom.ts:6-9,71-73,91-93`); Backspace/Delete remove it whole (`image-references.ts:90-110`). Below the field `ul.omp-attachments` lists one `li.omp-attachment` per image with the `data:` thumbnail, `#N`, name, size and a **×** (`Composer.tsx:1539-1566`).
- **Removal and undo.** The × deletes the marker(s) as one undo step (`removeImage`, `Composer.tsx:689-704`); an image whose marker is gone stays in memory only for Undo and is pruned against the budget (`image-references.ts:176-193`, `Composer.tsx:680-681`).
- **Limits.** 5 MiB per image, 10 MiB and 8 images per prompt (`chat-messages.ts:81-101`), checked before reading (`sizeRejection`, `attachments.ts:100-109`) and again at send (`Composer.tsx:851-854`). The grammar's budget sits under the broker's 16 MiB stdin line (`attachments.ts:15-24`, `chat-messages.ts:92-95`). The type is decided by magic bytes, never by the declared type (`sniffImageMimeType`, `attachments.ts:122-123`).
- **Send.** `compactForSend` drops images with no marker and renumbers the surviving markers 1..K because the wire pairs the Nth marker with the Nth image (`image-references.ts:158-174`, `Composer.tsx:826-830`). The message is `{requestId, text, images?}`; `ChatImageWire` is the only attachment shape (`chat-messages.ts:352-373`, parse `:1197-1212,1258-1269`). The RPC line is `{type:"prompt", message: text, images?, streamingBehavior}` with the text unchanged (`src/host/rpc/session.ts:934-982`); `RpcCommand` has no path or file field (`src/host/rpc/rpc.ts:118-122,136-169`).
- **Draft hand-off to a replacement editor.** The capture carries `text` and an attachment **count** only; images cannot be carried and the page tells the user to reattach them (`messages.ts:418-428`, `Composer.tsx:958-1007`, `guest-dispatcher.ts:360-361`). The carried text is capped at `MAX_DRAFT_TEXT_LENGTH = 8192` (`messages.ts:385`); a capture over it is answered `captured:false` (`messages.ts:418-428`, `App.tsx:87-90`). A view switch or an editor replacement then warns "could not be captured … not preserved" and goes ahead, so the **whole draft is lost**; Restart is refused with "Wait for pending image reads or edits to finish", which names the wrong cause (`guest-dispatcher.ts:355-358`, `extension.ts:4200,4351-4354`, `editor-panels.ts:679,806`). Decision 10 raises the cap to 200 000 and *Rollout* 8 corrects the sentence.
- **Rewind, queue restore, prompt history.** Text always survives (`rewindDraft`, `chat/rewind.ts:248-260`; `chat-runtime.ts:894-916`); images may not (`prompt-history.ts:25-33`, `extension.ts:5791-5808`).

### 3. How a path reaches OMP today, and what OMP does with it

`@path` is the product's reference format. "Add File to Session" and the chat `@` completion produce it:

- `mentionPath(fsPath, cwd)` writes forward slashes, makes the path relative when it is strictly under the session cwd (case-insensitive on win32) and otherwise leaves it absolute with the drive letter (`src/host/file-mentions.ts:150-161`). `mentionTokenForPath` quotes when the path has whitespace, `@`, a quote, a backtick, or a leading or trailing bracket/punctuation, as `@"…"`, or `@'…'` when the path holds `"` and no `'` (`messages.ts:1574,1604-1607`). `formatReference` refuses a control character or both quote kinds (`src/wiring/editor-context.ts:92-98`).
- The session cwd is known to the host (`extension.ts:1115`, `guest-dispatcher.ts:600,623`) and to the page as `ChatHeader.cwd` (`chat-messages.ts:600-607`); `Composer.tsx` does not read it (grep `\.cwd` finds nothing).
- The transcript already turns `@path` in a sent message into a file link (`src/webview/lib/chat-file-links.ts:19-20`).

Verified in the installed OMP 18.11.1 (`P/`):

- **An idle `prompt` expands `@` mentions.** `#promptWithMessage` runs `extractFileMentions(expandedText)` and `generateFileMentionMessages(..., this.sessionManager.getCwd(), …)` and pushes the contents as separate `fileMention` messages after the user message (`P/session/agent-session.ts:8007-8018`; `#promptWithMessage` is reached only from the idle branch of `#dispatchPrompt`, `:7561`). The user text is not rewritten. Syntax: `FILE_MENTION_REGEX = /@(?:"([^"]+)"|'([^']+)'|([^\s@]+))/g`; a mention counts at index 0 or after whitespace or `( [ { < " ' \`` (`P/utils/file-mentions.ts:33-36,44-47`). A bare token loses leading `` `"'([{< `` and trailing `)]}>.,;:!?"'\``; a quoted one is only trimmed (`:34-35,49-55,179`). There is no line-range syntax (`:57-72`).
- **Path resolution.** `resolveMentionPath` → `resolveReadPath(filePath, cwd)` (`:57-72`) → `resolveToCwd`: absolute paths are used as they are, relative ones are resolved against the session cwd (`P/tools/path-utils.ts:320-332`); `file://` and `~` are expanded and `/c/…` is mapped to `C:\…` on win32 (`:116-130,167-175`). A path that does not exist (stat throws) is dropped and its token stays prose (`:61-67`). A UNC path is absolute under win32 `path.isAbsolute` `[INFERENCE, not exercised]`.
- **What is injected.** A text file up to 5 MiB, not binary, is read whole and head-truncated to 3000 lines or 50 KiB; larger or binary files are skipped with a visible `(skipped auto-read: too large|binary file, …)` entry; a directory is listed (500 entries); an image is attached as an image block (`P/utils/file-mentions.ts:41,74-105,107-165,192-334`, `pi-tui/src/tools/streaming-output.ts:11,13`, `pi-utils/src/binary.ts:33-47`). The model sees `<file path="…">…</file>` per file (`P/session/messages.ts:1086-1124`).
- **`steer`, `follow_up` and a `prompt` OMP receives while it is streaming do not expand mentions.** They go to `#queueUserMessage`, which calls no `extractFileMentions` (`P/session/agent-session.ts:7416-7441,8312-8341,8402-8520`; `P/modes/rpc/rpc-mode.ts:1780-1787`; the only two callers of the expansion are `:8008,8010`, both inside `#promptWithMessage`, whose callers are the idle branch `:7561` and `:4886,7732,8646`, none of which carries composer text). Every Desk `prompt` carries `streamingBehavior` (`request.streamingBehavior ?? "steer"`, `src/host/rpc/session.ts:960`), so what happens depends on OMP's own `isStreaming` when the prompt **arrives**, not on the page's `working`: an auto-continue or a hidden next turn that starts in between makes the prompt a queued one with no expansion. The model then sees the literal `@path` and must `read` it. The older design (`2026-10-07-add-editor-context-to-session.md:79`) and a comment at `src/extension.ts:6109-6110` already record this.
- **A plain absolute path with no `@`** is ordinary user text; no code in this flow treats it specially `[INFERENCE: only the prompt-path pre-processors were read]`.

### 4. Is there a downstream cap on the number of images?

The maintainer asked this before removing the count limit. Read in the installed OMP 18.11.1 (`P/` as above; `[INFERENCE]` where a grep, not a full read, is the evidence).

- **OMP's prompt and RPC do not count.** `prompt`, `steer` and `follow_up` take `images?: ImageContent[]` (`P/modes/rpc/rpc-types.ts:40-42`); the idle path and the queue append all of them to the user message (`P/session/agent-session.ts:7466-7469`, `:8459-8462`). A grep of `P/modes/rpc/` and `agent-session.ts` for an image-count constant finds none `[INFERENCE: grep, not a full read]`. The only size rule found there is `MAX_IMAGE_INPUT_BYTES = 20 MiB`, for an image *loaded from a path* (`pi-tui/src/chat/image-loading.ts:4`); the panel's 5 MiB is stricter.
- **The providers' caps are enforced by OMP at send time, per request, over the whole conversation, and non-fatally.** `clampProviderContextImages` counts every image in the context except the model's own output, drops the **oldest** ones past `providerImageBudget(model)` and writes `[image omitted: provider image limit]` where a message loses all its images (`P/session/provider-image-budget.ts:22-25,40-50,110-140`). A provider's own "too many images" rejection is recognised and handled by the recovery path (`P/session/session-maintenance.ts:223-251,2862-2866`). The budget is the catalog's `official-image-count-budget` while the request reaches the official endpoint, else `image-count-budget`, else a **floor of 5** (`snapcompact/src/snapcompact.ts:577-588`, `pi-catalog/src/compat/request-size.ts:34-38`).
- **The catalogued values** (`pi-catalog/src/compat/rules/providers/*.kdl`): Anthropic 90, and 600 on its official endpoint, 100 for models with a 200k window (`anthropic.kdl:85-100`); Amazon Bedrock 90; OpenRouter 90; OpenAI 200; OpenAI Codex 200, 2000 official; Google, Gemini CLI and Vertex 200; xAI 60; Cursor 60, 20 for some models; Google Antigravity 60, 20 for some; Umans 10; every host with no entry 5.
- **So the panel's 8 (`chat-messages.ts:85`) matches none of them.** It is below every catalogued value but one and above the floor of 5 that a custom or local host gets, so a draft of 6 to 8 images can already lose its oldest images silently today. No downstream value is a fixed number the panel could copy: the cap is per request, per model, counted over the history, and enforced by dropping, never by refusing.
- **The panel's own hard-coded 8s** are separate from OMP and are the ones that must change with the limit: `MAX_CHAT_IMAGES` and its parse test (`chat-messages.ts:85,1199`), `MAX_DROP_URIS = MAX_CHAT_IMAGES` for the drop request, the reply and the page's URI read (`messages.ts:252,1243,1418`, `Composer.tsx:781`), `MAX_RESTORED_IMAGES` for a dequeued message (`src/host/rpc/session.ts:331,339,484`), and the literal `8` that clips a rewound draft's images (`src/host/chat-runtime.ts:896`, test `chat-runtime.test.ts:1189`). The tests `chat-messages.test.ts:239,259-264` and `messages.test.ts:195` pin them.
- **The one fixed downstream bound is the broker's 16 MiB stdin line** (`pty-protocol.ts:144`, `rpc-handle.ts:147`). The byte budget is sized under it: 10 MiB is 13 981 016 base64 characters, a worst-case 200 000-character text is about 1 200 000 bytes of escapes, and 16 MiB is 16 777 216, which leaves about 1 596 000 bytes of which the test requires 512 KiB (`chat-messages.ts:92-95`, `chat-messages.test.ts:258-268`). Each image also costs about 50 bytes of JSON (`{"type":"image","data":"…","mimeType":"image/webp"},`), so without a count the line would overflow at roughly 20 000 images `[INFERENCE: computed from the numbers above, not exercised]`. The byte budget alone does not prevent that: a 1×1 PNG is about 70 bytes.

Conclusion: **no downstream cap justifies a panel cap of 8 or of any other number, and none of them refuses; OMP drops the oldest images and says so in the request.** Removing the count is safe for correctness, but it exposes one silent effect (the model may see fewer images than the draft shows; decision 8 leaves it unannounced) and needs a finite parser bound for the broker line (decision 9).

## Proposed Design

### 1. One path source: the host

A document is attached only when the **host** holds its path. Two entry points can supply one, so the page never invents one:

| Entry point | Path source | Behaviour |
| --- | --- | --- |
| **Attach button** | **New host dialog**: the page posts `omp:pick-files {requestId}`; the host calls `showOpenDialog({canSelectMany:true, canSelectFolders:false, defaultUri: session cwd, openLabel:"Attach"})` and answers with the same reply as a drop, **always**: the host wraps the dialog in `try/finally` and a cancelled or failed dialog answers an empty reply, which also settles the request. The page arms **no timeout** for a pick: a native dialog left open for more than 10 s is ordinary, and a timeout would throw the user's later pick away. The pick still counts in the `reading` counter, as a drop does (a capture is unavailable while a request is in flight, ADR-0050, and the dialog is window-modal anyway). | Real path. Images picked here are read by the host like a drop and come back as images; everything else comes back as a document. A file on a network share (`\\server\share\…`) is accepted: the user chose it in a host-owned dialog (decision 11). The `<input type="file">` is removed (decision 1). |
| **Drag from VS Code's Explorer / editor tab** | The `file:` URIs already sent by `omp:attach-uris`. | Real path. Non-images are no longer refused: they come back as documents. |
| **Paste of an OS file** | None. | A `File` with no path: an image attaches as today; a text file goes into the draft as its text; anything else is refused. All three are *Proposed Design* 9 (decision 3). |
| **Drag from Windows Explorer** (with Shift) | None. | Same as a paste. |

A `File` the page holds is classified **before** `sizeRejection`: the first bytes decide image or not (`file.slice(0, 16)`, `sniffImageMimeType`), and a non-image goes to the text rule of *Proposed Design* 9. Today `sizeRejection` runs first and would tell a 6 MiB `.pdf` that it "exceeds the 5.0 MB limit per image" (`attachments.ts:100-109`); a file that is not an image must not get an image sentence. The old `unsupportedReason` format list (`:154-163`) stays only for a mislabeled image.

A pathless file is never matched to a path by name, never looked up in recent files, and never copied to disk. `File.path` is not used even if a future Electron exposes it; the host is the only path source, so the rule has one place to live. `[INFERENCE]` Slice 0 measures what each entry point delivers in the installed VS Code, so the table above is a measurement, not a guess.

### 2. The host reply carries documents

One request path, one ordered reply. `omp:attach-uris` and `omp:pick-files` share a reply, which keeps the order of the drop (or of the dialog's result), so image and file markers of one drop are placed in that order:

```
omp:attached-files { requestId, items: AttachedItem[], refusals: string[] }
AttachedItem  = { kind: "image", name, mimeType, data } | { kind: "document", name, mention, key, bytes }
```

- `readDroppedImages` (`dropped-images.ts`) is generalised to `readAttachedFiles(paths, cwd)`. For each distinct path it applies the existing refusals (scheme, host for a relayed URI, drive, not-a-file, changed while read; a folder gets its own sentence, decision 5) and then **classifies by magic bytes**: an image follows today's size rules and becomes an `image` item; anything else becomes a `document` item. Items come back in the order of the input. The classification reads only the header `sniffImageMimeType` needs (at most 4 KiB), and for a document those bytes never leave the host. Empty files are a valid document (`0 B`); the image rule "the file is empty" stays for images only.
- `mention` is the finished `@` token, computed by the host with the session cwd (`hostedCwd(tabId)`, `guest-dispatcher.ts:600`): `mentionTokenForPath(mentionPath(absolute, cwd))`, refused with a sentence when the path has a control character or both quote kinds (the same `formatReference` rule, `editor-context.ts:92-98`; the function is exported rather than copied). With **no session cwd yet** the host does not stay silent (`omp:complete-files` does, `guest-dispatcher.ts:603-604`): it formats with an empty cwd, which gives an absolute mention (`mentionPath(path, "")`, `file-mentions.ts:153`). The invariant is that **the page never formats or resolves a path**; it is not that the path is secret: a file outside the cwd has an absolute mention anyway (`file-mentions.ts:150-163`). `key` is the host's `comparablePosix` of the absolute path (`file-mentions.ts:140-143`, no second normalisation); the page compares it and never shows it.
- **No content crosses to the page for a document** (decision 6): `name`, `mention`, `key` and `bytes` (from `stat`, for the size shown on the chip) are all it gets. `kind` is only the discriminator; there is no `preview` member.
- Parse limits in `messages.ts` beside `:1275`: `name` 1–255 characters without control characters (as `MAX_ATTACHED_NAME_LENGTH`), `mention` ≤ 2200 characters without control characters, `key` ≤ 2200 characters, `bytes` a non-negative safe integer. `items.length` and `refusals.length` are bounded by `MAX_ATTACH_ITEMS` (*Proposed Design* 8; the reply's `refusals` bound is today `MAX_DROP_URIS`); each refusal keeps its 400-character bound. The base64 total is checked over `image` items only.
- The dispatcher keeps its rule: the answer goes only to the panel that asked, and never a replaced one (`guest-dispatcher.ts:612-620`). `omp:pick-files` is answered the same way; the dialog is not shown to a replaced panel, and the answer is sent from the `finally` of the dialog call.

### 3. The marker, the chip and the strip

- **Marker.** `[File #N: name.md]`. `N` comes from its own counter (documents are not paired with wire positions the way images are, so they are not renumbered); the name has `[` and `]` replaced by `(` and `)` and is clipped at 60 characters so the marker has one grammar: ``\[File #([1-9]\d*): ([^\]\n]+)\]``. As for images, a marker of an unknown number is ordinary text (`image-references.ts:44-47`), so a hand-typed `[File #1: x]` stays prose. Unlike an image marker, which counts with any tail, a file marker is **replaced** on send, so it counts only when its **whole label equals that document's own label**: a pasted or quoted `[File #1: other.md]` is prose, never a chip for document 1 sent under the wrong name. Quote capture and the no-path text block neutralise `[File #N` as they do `[Image #N` (`neutraliseImageMarkers`, `quote-draft.ts:32-33`).
- **One reference finder, five invariants (ADR-0077).** `findImageReferences`, `referencedNumbers`, `snapSelection`, `deletionRange` and `repairDamagedReferences` (`image-references.ts:48-141`) become reference-kind-aware: a span has `kind: "image" | "file"`. (1) The finder returns **one start-sorted, non-overlapping span list** from one combined regex scanned leftmost-first, because the image tail `(?:,[^\]\n]*)?` can swallow a file marker (`[Image #1, x [File #2: a.md]`), and `lineSpecs` walks the spans in order (`draft-dom.ts:62-66`); a test pins that case. (2) `isKnown(kind, number)`: the image and file number spaces are separate, and the image-only consumers stay image-only: `activeImages`, the image renumbering of `compactForSend`, `pruneInactive` and the restore counter bump (`Composer.tsx:997-1001`). (3) `lineKey` includes `kind` (`draft-dom.ts:72-74`), so a chip of the other kind at the same offsets and number cannot keep a stale DOM node. (4) A file chip keeps `CHIP_CLASS` plus a modifier class (`data-kind="file"`), so `isChip` and the caret mapping still treat it as atomic; it has a file icon and `aria-label="File #N, name.md"`, not `role="img"`. (5) `snapSelection`, `deletionRange` and `repairDamagedReferences` stay purely geometric and need no change. The string stays the source of truth.
- **Insertion** reuses `insertReferences` (`Composer.tsx:615-631`) with the file markers; the ordered `items` of one reply give image and file markers in drop order.
- **The strip.** `ul.omp-attachments` (`Composer.tsx:1539-1566`) gets `aria-label="attachments"`; a document's `li.omp-attachment` has the same layout with a **tile** in place of the thumbnail (decision 6):
  - a codicon chosen by the file's extension (`markdown`, `file-code`, `file-pdf`, `file-zip`, `file-binary`, default `file`) with the extension in capitals; no file content is shown;
  - `#N`, the name, the size, and a ✕ that calls the same removal (`removeImage` becomes `removeAttachment`, deleting the marker as one undo step, `:689-704`).
  The tooltip of a document says how OMP reads it: `OMP reads up to 3000 lines or 50 KiB of a text file into the prompt; a larger or binary file is only named.` A file over 5 MiB shows that sentence as a visible note on the chip, not only as a tooltip (OMP skips it at `P/utils/file-mentions.ts:289`). Nothing blocks the attach: the model can still open the file by its path. The strip scrolls (a `max-height` with overflow) so a draft of many attachments does not push the field off the panel.
- **State.** `DraftImage` has a sibling `DraftDocument = {number, name, mention, key, bytes}` in `documentsRef` with the same lifecycle as `imagesRef`: published with the markers, retained after marker deletion only for Undo, cleared on send. A document carries no bytes, so it is exempt from `MAX_DRAFT_BYTES` and the pruning budget (`image-references.ts:176-193`), and it has no count cap (decision 7).
- **Duplicates.** A second attach of the same file is not added: it is reported as `notes.md is already attached.` The comparison is the host's `comparablePosix` key (case-insensitive on win32), carried as an opaque `key` in the reply that the page compares and never shows. The same path as an image and as a document is allowed (different kinds). The host also de-duplicates inside one reply (`new Set(uris)`, `dropped-images.ts:55-58`).
- **Controls.** The attach button's label and tooltip become `Attach files` and `Attach a file or an image. You can also paste an image, drag one here with Shift, or drag a file from VS Code's Explorer.` (`Composer.tsx:1415-1416`). It stays disabled while reading (`:1414`); the picker and a drop share the existing `reading` counter, but only a **drop** has the 10 s request timeout (`:728-753`); a pick has none (*Proposed Design* 1).

### 4. What is sent

The prompt wire is **unchanged**: `{requestId, text, images?}` (`chat-messages.ts:354-373`, `session.ts:934-982`). The documents are text.

`compactForSend` (`image-references.ts:163-174`) is rewritten as **one walk over the combined span list** of the finder, and the substituted text is never scanned again. Images get their renumbered labels, files get their `mention`; markers of deleted attachments disappear, and so do their documents. Substituting mentions first and then running the image renumbering pass would corrupt a path that contains `[Image #1]` (a Windows file name may: `@"docs/[Image #1].md"`), so the order is part of the contract. A token needs a boundary OMP accepts (index 0, whitespace or an opening bracket/quote, `P/utils/file-mentions.ts:44-47`): if the character before the marker is none of those, one space is inserted. After the marker the **whole run** of non-whitespace, non-`@` characters that follows is read, because OMP's bare token takes `[^\s@]+` and strips punctuation only at its **end** (`:33,35,49-55`): a space is inserted unless that run is entirely OMP's trailing punctuation (the characters `) ] } > . , ; : ! ? " '` and the backtick). So `[File #1: a.md],x` is sent as `@a.md ,x`, never as `@a.md,x`, which OMP would read as the path `a.md,x` and drop as prose, while `[File #1: a.md].` is sent as `@a.md.`. Example: `Summarise [File #1: plan.md] for [File #2: a b.md]` is sent as `Summarise @docs/plan.md for @"docs/a b.md"`. The hand-off (*Proposed Design* 5) uses the same function, so a carried draft sends identically.

- **Idle prompt.** OMP expands every mention: the model receives each text file as a `<file>` block (head-truncated to 3000 lines or 50 KiB), a skip notice for a binary or over-5 MiB file, and the path as typed. See *Current State* 3.
- **While OMP is streaming when the prompt arrives** (`steer`, `follow_up`, a `prompt` queued by `streamingBehavior`): the model receives the literal `@docs/plan.md` and reads the file itself. Which of the two happens is decided by OMP's own state when the prompt arrives (*Current State* 3), not by the page's `client.getSnapshot().working` (`Composer.tsx:861-873`), which is unchanged; no second format is invented.
- **Transcript.** The sent message holds `@docs/plan.md`, which `chat-file-links.ts:19-20` already draws as a file link that opens the file.
- **Failure: a file that is gone (decision 4).** When the draft holds a live document, the page asks the host (`omp:check-paths`, one request, answered only to the asking panel, with the existing request timeout) whether the files **OMP will actually read** still exist. The request carries the **mentions**, not keys: the host resolves each unquoted token against the *current* `hostedCwd` the way OMP's `resolveToCwd` does (`P/tools/path-utils.ts:320-332`) and requires `isFile()`, so a cwd that changed since the attach is checked correctly. A missing file refuses the send with `plan.md no longer exists; remove it to send.`, the draft and every chip stay, and nothing is sent. A host that does not answer refuses the send with the existing "the extension host did not answer" kind of sentence: a send never goes out on an unverified path. A file removed after the check is OMP's case (the token left as prose, `P/utils/file-mentions.ts:61-67`), documented and accepted.
- **Where the check sits in `send()`.** All guards are evaluated once before any await (`Composer.tsx:835`); `running` is read, and `sendingRef` and `pendingOriginalRef` are set, just before the RPC await (`:861-868`); a capture includes the pending original (`:963-964`). The order is therefore: (1) compact once (the single walk above) and check the 200 000-character bound; (2) set `sendingRef` and `setSending(true)` **before** awaiting the check, so a second Enter and `runCommand` (`:944`) are blocked; (3) the check is **not** counted in `reading`, because a capture during the check would then be refused (`:959`) and a view switch would lose the draft; (4) `pendingOriginalRef` is **not** set during the check; (5) after the check, re-test `captureRef.current !== null || !canPrompt` and, if either holds, abort without sending: the capture already carries the draft intact; (6) only then read `client.getSnapshot().working` and set `pendingOriginalRef`. Edits made during the check are kept by the existing revision guard (`:891`); what is sent is the text frozen at Enter, as today.
- **The text bound is the real limit for documents.** With no count cap, the substituted text must still fit `MAX_CHAT_TEXT_LENGTH = 200 000` (`chat-messages.ts:81`); the page checks it before sending and refuses with `the message would be N characters; one message may carry 200 000`, keeping the draft. A mention is at most about 2 200 characters, so this bites at roughly a hundred long paths, not before. The 900-character bound (`messages.ts:354`) concerns `omp:insert-text` only and is not affected.

### 5. Draft hand-off, restore and history

- **Hand-off.** The capture's `text` replaces every live file marker by its `mention` (the function of *Proposed Design* 4) before the capture is frozen, so a document is not lost when the editor is replaced: it arrives as a plain `@path` the user can still send. `attachments` stays the image count (`Composer.tsx:965`); the "N image(s) could not be carried" sentence (`guest-dispatcher.ts:360-361`) is unchanged because no document is dropped. The cap is `MAX_DRAFT_TEXT_LENGTH`, raised to 200 000 by decision 10, so the substituted text (mentions of up to 2 200 characters each) and a 20 000-character text block are carried; before the change a capture over 8192 lost the whole draft on a view switch (*Current State* 2), and the claim that a document survives a replacement would have been false past 8192.
- **Rewind, queue edit, ↑/↓ history.** These carry the sent text, which already holds `@path` (`chat-runtime.ts:894-916`, `prompt-history.ts:25-33`). A restored message keeps working as a mention; it is not a chip again. This is stated in the guide.

### 6. What does not change

- An image dropped from VS Code's Explorer by path is **still sent as an image**: the host reads the bytes and `files` carries them, as today. Sending an image's path instead would put it under OMP's mention rule, which does not apply to `steer` and `follow_up` (*Current State* 3), and would stop the model seeing the image in those two cases. A drop of one image and one `.md` gives one image chip and one document chip.
- The prompt wire grammar, the per-prompt 5 MiB / 10 MiB image budget, `omp:attach-uris` request shape, the host's local-drive-only rule (`dropped-images.ts:16,47`), and the UNC refusal.

### 7. Paths

| Case | Rule |
| --- | --- |
| Inside the session cwd | Relative with forward slashes: `docs/plan.md` (`mentionPath`, `file-mentions.ts:150-161`). OMP resolves against the session cwd (`P/tools/path-utils.ts:320-332`). Case-insensitive prefix test on win32; the file's own casing is kept. |
| Outside the cwd, or empty cwd | Absolute, forward slashes, drive letter kept: `@D:/Other/b.ts`. |
| Spaces, quotes, brackets, Unicode | `mentionTokenForPath` quotes them (`messages.ts:1574,1604-1607`). Unicode letters are fine in a bare token; every `\s`-class character, including Unicode spaces, makes OMP split a bare token, and `MENTION_NEEDS_QUOTES` tests the same `\s`, so such a path is quoted too (`P/utils/file-mentions.ts:33`). |
| Both quote kinds, or a control character | Refused with a sentence; nothing attached (`editor-context.ts:92-98`). |
| UNC and `file://host/share` | A URI **relayed from a page drop** is refused with the existing sentence (`dropped-images.ts:32-48`): Windows would authenticate to the share by itself the moment the host stats it. A path **chosen in the host's own dialog** (`showOpenDialog`) is accepted, including `\\server\share\…`: the user picked it there (decision 11), and without this an image picked from a share, which the browser input accepts today, would regress. The refusal sentence for a drop must not talk about dropping when the path came from the dialog. A mapped drive letter looks local and is accepted. `[INFERENCE: a UNC path is absolute under win32 path.isAbsolute (P/tools/path-utils.ts), not exercised]` |
| Symlink | Followed by the host's `stat` (`dropped-images.ts`) and by OMP; the reference names the link, not the target. |
| `vscode-remote:`, `untitled:`, `vscode-userdata:` | Refused: not `file:` (`dropped-images.ts:32-48`). With `extensionKind: ui` (`package.json:47-49`) the host cannot open a remote file, so the sentence is true. |
| Deleted or moved before send | The send-time check refuses the send and keeps the draft (decision 4, *Proposed Design* 4). |
| Folder | Refused with `<name>: a folder cannot be attached; attach the files in it.` (decision 5). |
| Path changed under the cwd later | The mention is relative to the session cwd, which is fixed for a session (`hostedCwd`, `extension.ts:1115`); a resumed session keeps its cwd `[INFERENCE: not re-verified]`. |

### 8. Counts: what changes when the limit goes (decision 7)

The user-facing rule becomes the byte budgets alone (5 MiB per image, 10 MiB per prompt, `chat-messages.ts:86-101`; `sizeRejection`, `attachments.ts:100-109`). Documents have no count and no byte budget.

- **Constants.** `MAX_CHAT_IMAGES` (`chat-messages.ts:85`) is removed as a rule. Everything listed in *Current State* 4 that read it or a literal 8 follows: the image parse, the drop request and reply, the page's URI read, `MAX_RESTORED_IMAGES` and the rewind clip. Each is replaced by the **parser guard** `MAX_ATTACH_ITEMS = 1000` (decision 9), which is a bound on array length for the parser and the broker line, not a rule the user is told about. The guard is complete only with four more sites: (a) `droppedFileUris` silently stops at `limit` (`attachments.ts:203-209`), which would lose item 1001 onward without a word; it reads `limit + 1` and refuses the whole drop; (b) a `canSelectMany` dialog result is checked against the guard in the host before any read; (c) the guard is enforced **when attaching**, across several drops, picks and pastes into one draft, so the prompt parse never rejects a send `[INFERENCE: what the page shows for a rejected omp:chat-prompt was not read]`; (d) the reply's `refusals` bound becomes `MAX_ATTACH_ITEMS`. A restored or rewound message keeps every image **within the per-prompt base64 budget**: a set over it is reported dropped as a whole (`parseImages`, `chat-messages.ts:1198-1224`), and `imagesDropped` / `unavailableImages` count what is truly unavailable (a `blob:` reference, `rewind.ts:248-260`) or over the budget. A drop or draft above the guard is refused with `at most 1000 files can be attached at once`.
- **The base64 bound** `MAX_CHAT_IMAGES_BASE64_CHARS = ceil(10 MiB / 3) * 4` (`chat-messages.ts:101`) is a sum of per-image figures, and each image rounds up to a multiple of 4 characters, so a full budget of many small images exceeds it by up to 4 characters an image. The page would accept a draft the parser then refuses. The bound becomes `ceil(BYTES / 3) * 4 + 4 * MAX_ATTACH_ITEMS`, and a test fills the budget with the most images the guard allows.
- **The line budget** `chat-messages.test.ts:258-268` is rewritten for the guard: the worst case is a full byte budget carried by `MAX_ATTACH_ITEMS` images plus a worst-case text, and it must stay under `PTY_RPC_MAX_WRITE_BYTES` with the same 512 KiB to spare. With a guard of 1 000 the images add about 50 KB.
- **Cost per image in the page.** Each image is decoded once for its size (`decodedSize`, `attachments.ts:129-139`) and shown as a `data:` thumbnail (`Composer.tsx:1544`); the 10 MiB budget bounds the memory, and the strip scrolls (*Proposed Design* 3).
- **What the user sees for a draft the model cannot fully take.** OMP drops the oldest images of the request (*Current State* 4). By decision 8 the composer does not say so.

### 9. A file with no path: its text, or a refusal (decision 3)

Only a `File` the page holds without a path reaches this rule: a paste and a Shift-drag from Windows Explorer. A file the host picked or the Explorer named by `file:` URI has a path and is always a document, text or not (*Proposed Design* 1 and 2).

For each such `File`, in this order:

1. **An image** (`sniffImageMimeType` of its first bytes) follows today's image path, size rules included.
2. **Known text type or extension.** The file qualifies when `languageForPath(file.name)` is not `null` (the file-name table, then the extension against the fence languages, `code-languages.ts:404-427`), or its extension is in a short list of plain-text extensions that are not code languages (`txt`, `text`, `log`, `csv`, `tsv`, `rst`, `tex`, `diff`, `patch`, `env`, `conf`, `cfg`, `properties`), or its declared `file.type` is `text/*` or one of `application/json`, `application/xml`, `application/javascript`, `application/x-yaml`, `application/yaml`, `application/toml`, `application/x-sh`, `application/sql`, `image/svg+xml`. The declared type can only add, never veto: the browser derives it from the extension, and `[INFERENCE: Chromium's table reports .ts as video/mp2t; not exercised]`. Anything else is refused as `not a known text file`. The lists live in one page module, `src/webview/lib/text-attachments.ts`.
3. **Size, without reading.** An empty file is refused (`the file is empty`). A file over **80 000 bytes** is refused with its size and is not read. The bound is loose and safe: a UTF-16 code unit never takes more than 3 bytes of UTF-8, so a file of at most 20 000 characters has at most 60 000 bytes of content, plus a 3-byte BOM and CRLF line endings (about 60 005 bytes in the tight case); 80 000 only has to be above that.
4. **UTF-8 text.** The bytes are decoded with `new TextDecoder("utf-8", { fatal: true })` and a leading U+FEFF is dropped; a failure is refused as `its contents are not UTF-8 text` (UTF-16 and every legacy code page fail here). Line endings are normalised to `\n` (`normalizeLineEndings`, `draft-text.ts`). The draft's own control-character rule then applies: NUL and every control character but tab and newline refuse the file as `its contents are not text` (`DRAFT_CONTROL_CHARACTER`, `messages.ts:394`, exported for this; it is the rule a draft must already satisfy to be handed off, `messages.ts:397-399`).
5. **Length.** The decoded content, minus one trailing newline, counted in the characters `MAX_CHAT_TEXT_LENGTH` counts (UTF-16 code units), may be at most **20 000**. Over it the file is refused with the count: `big.md is 31 204 characters; a file with no path can be put into the draft only as text of at most 20 000 characters.` plus the routes sentence below. Nothing is truncated.
6. **The block.** The file becomes a fenced block: an opening line of the fence and the info string, the content, a closing line of the fence. The info string is `languageForPath(file.name)`, else the extension when it matches `[a-z0-9+#_-]+`, else empty (an opening fence's info string may not contain a backtick, `code-fence.ts:29`). The fence is `max(3, L + 1)` backticks, where `L` is the longest backtick run at the start of any content line after its leading whitespace (`longestFenceRun`, now in `code-fence.ts` and shared with quote capture: it is a closing fence for the draft's grammar and the transcript's, the same reasoning as for quotes, `2026-10-15-quote-chat-selection.md` section 3). **Every occurrence** of `[Image #N…]` or `[File #N…]` in the content (the pattern is global) is neutralised to `[image #N…]` / `[file #N…]` as quote capture does, so it cannot pair with an attachment of the new draft (`image-references.ts:23`).
7. **Placement.** Through `placeQuote` renamed `placeBlock` (`quote-draft.ts:64-72`): at the end of the draft after a blank line, an unclosed fence of the draft closed first, the caret on the line after the block, refused when the draft would pass `MAX_CHAT_TEXT_LENGTH` (`the draft would be over 200 000 characters`, the file named). Several files of one paste are one insertion, in order, one undo step (`replaceInSurface`, `Composer.tsx:152`); a file that does not fit is refused alone and the others still go in.
8. **Feedback.** A status line under the composer, not an error: `notes.md was put into the draft as text: it has no path OMP can open.`

There is **no chip, no marker and no strip entry** for this text: it is ordinary draft text in a code band (ADR-0077), edited, undone or deleted like any text, and it is sent as the user's message text. It is not counted as an attachment in the hand-off.

Every other file is refused with one sentence of the form `<name>: <reason>. A file with no path can go into the draft only as text. Attach it with the paperclip, or drag it from VS Code's Explorer, so it is sent as a path.`, where the reason is `not a known text file`, `the file is empty`, `its contents are not UTF-8 text`, `its contents are not text`, or the size sentence of step 3 or 5. Nothing is written anywhere.

Consequences stated once:

- OMP scans the user text of an idle prompt for `@` mentions (*Current State* 3). A text file that contains `@src/a.ts` makes OMP read that file. A quote and any pasted text have the same exposure; it is accepted.
- A block of 20 000 characters is carried by the draft hand-off since decision 10 raised `MAX_DRAFT_TEXT_LENGTH` to 200 000; at the old 8192 a capture was refused and the draft lost on a view switch (*Current State* 2). The same holds for a 20 000-character quote.
- The file's name is not in the draft: the info string carries only the language. A name line above the block was considered and left out because the maintainer specified the block alone (*Alternatives* 7).

## Alternatives

1. **Inline the file's text into the prompt.** Simple and works for `steer` and `follow_up`, but for a file **with** a path it is not what the maintainer asked ("send them … as a path"), spends tokens on every attach, needs its own size rules, and cannot carry a binary. Rejected for files with a path; decision 3 adopts it, as draft text, for a text file that has none.
2. **A plain absolute path with no `@`.** The model must call `read`, so nothing is injected, and the transcript's link detection still finds a path. It avoids the 3000-line / 50 KiB injection a large file would cause, but loses OMP's own mention behaviour, the relative-path form and the product's single reference format, and on an idle prompt costs a tool turn. Rejected by decision 2.
3. **Copy pathless files into the workspace, `.omp/` or a temp folder and send that path.** Makes paste and an Explorer drag work, but writes user data to disk without the user asking, needs a lifetime and a cleanup, and a copy in the workspace can end up in a commit. The maintainer chose text-or-refusal instead (decision 3); an explicit "Save a copy" button remains a possible later request.
4. **Keep the browser `<input type="file">` and add a second "attach file" button.** The picker would still give no path; the second button would be the host dialog. Two buttons for one verb. Rejected by decision 1.
5. **Add a `documents` field to the prompt wire** so the host, not the page, writes the mention. The host would need to splice text into the user's sentence; `text` would stop being what the user sees. Rejected: the text is the single source of truth, as for the quote feature (`2026-10-15-quote-chat-selection.md`).
6. **Resolve the path in the page from `File.path`, a recent-files list or a search by name.** `File.path` is not available `[INFERENCE]`; guessing by name is wrong whenever two files share a name. Rejected.
7. **A file-name line above the text block** (`notes.md:`), so the model sees the name. Not chosen: decision 3 specifies the block alone, and the info string cannot carry the name without extra tokens that the composer's own grammar and the guide would then have to describe as a second convention. Cheap to add later.

## Risks and Open Questions

- **Entry-point behaviour is partly inferred.** What a paste and an Explorer drag deliver inside this webview (no `File.path`; `codefiles` not read) was not measured here. Slice 0 measures it; if an entry point does give a real path, the table in *Proposed Design* 1 is amended with the maintainer's agreement, never silently.
- **`@` expansion is OMP behaviour, not ours.** An idle prompt inlines up to 50 KiB / 3000 lines per file, and documents have no count cap (decision 7): a hundred attached text files can put 5 MB of context in one message. The chip says so for one file (tooltip and over-5 MiB note); nothing blocks it, and OMP's own context-overflow handling is what answers a draft that is too large. `[INFERENCE]` A later OMP could change the mention grammar; the existing mention features have the same exposure.
- **`steer` and `follow_up` do not expand.** The user cannot tell from the chip whether the model got the file or only its name. Mitigated by the guide and the tooltip, not by a second format.
- **The attach button moves from a browser input to a host dialog.** Its tests in `chat-ui.test.ts` that drive `onFilesPicked` are rewritten, and the page needs the host connection for the button (as a drop from VS Code's Explorer already does, `Composer.tsx:749-752`); with no connection the button says so. A native dialog is not driven in automation `[INFERENCE: Playwright over CDP cannot drive native file dialogs]`; it is covered by the recording stub (`src/wiring/vscode-recording-stub.ts:237`) and a manual check.
- **The reference finder is shared with the image chip.** Generalising `image-references.ts` touches atomic-chip editing that ADR-0077 relies on; its existing tests (`image-references.test.ts`, `chat-ui.test.ts`) must stay green unchanged.
- **No file content reaches the page for a document** (decision 6). The host reads the first bytes of a file only to tell an image from a document, and for a document they stay in the host; the page gets a name, a size and the `@` token. An image's bytes reach the page as they do today.
- **A mention whose file vanishes between check and send.** The check is a best effort and OMP then treats the token as prose (`P/utils/file-mentions.ts:61-67`); this is documented and accepted.
- **A text block in the draft is large and editable.** Up to 20 000 characters and several files of them can fill the draft; it is the user's text, so it is editable, and the 200 000-character bound refuses the one that does not fit. The status line says what happened.
- **The text rule is a guess about the user's intent.** A UTF-8 file with an unknown extension (`.foo`) is refused though it is text; the maintainer's rule asked for a known type or extension. Extending the lists is one edit in `text-attachments.ts`.
- **`@` tokens inside a pasted text file** make OMP read those files on an idle prompt, as any pasted text does.
- **Link rendering is bounded.** The transcript links only the first 64 file references in one text (`chat-file-links.ts:13`), and the bare form of the mention pattern stops at `()[]{}` though OMP accepts them (`:19`). A message with very many documents, or a bare path containing brackets, shows partial links. Cosmetic; the guide says so.
