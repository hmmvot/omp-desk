# Extension host module structure: layers with a checked import direction, one window state, wiring modules cut out of `extension.ts`, and shared file primitives

## Problem

The extension host grew by feature, and its module structure no longer says where a change belongs or what it may touch:

- `src/extension.ts` is 14,408 lines. It declares about 70 mutable module globals (`let` bindings, `Map`s, `Set`s, `WeakMap`s; `src/extension.ts:544-860` and later) that any of its several hundred functions may read or write, and its only test, `src/extension-lifecycle.test.ts`, reaches them by appending an `export const harness = {...}` block to a copy of the source before bundling it (`src/extension-lifecycle.test.ts:141-149`, 69 internal functions listed) and by assigning the globals from the test (`setWindowRegistry` assigns `windowRegistry`, `setActivationContext` assigns `activationContext`, `notificationTree` assigns four launcher globals, `policy` reassigns `reconciler`, `launcher`, `openPanel` and `brokerProvenanceFor`; `:159-160,233,244-253`). A new feature cannot be tested without extending that harness, and nothing bounds what a function in `extension.ts` depends on.
- There is no stated import direction. The host process imports page code: 11 runtime and 7 type-only edges from `src/host/**`, `src/broker/**` and `src/chat/**` into `src/webview/**` and `src/views/**` (for example `src/broker/pty-screen.ts:53` → `src/webview/lib/terminal-unicode.ts`, `src/host/rpc/session.ts:85` → `src/webview/lib/transcript-window.ts`, `src/host/chat-runtime.ts:34` → `src/webview/chat-messages.ts`), and the page imports host code (`src/webview/lib/chat-client.ts` → `src/host/rpc/protocol.ts`, `src/webview/lib/activity.ts` → `src/host/notification-text.ts`, `src/webview/desk-settings/page-state.ts` → `src/host/desk-settings/model.ts`). The edges are harmless today because the imported modules are pure, but nothing stops a `document` reference from entering `src/webview/lib/*` and breaking the host bundle at runtime, and a reader cannot tell a contract from a page helper by its path. Five import cycles are closed through `import type` (`src/chat/transcript.ts:4` ↔ `src/chat/model.ts`, `src/host/symbol-links.ts:4` ↔ `src/host/file-name-links.ts:4-5`, among others).
- `src/host/session-index.ts` is 4,710 lines: the `SessionIndex` class (`:1658-4226`) with, before and after it, pure session-file readers (`readSessionFileHeader`, `readSessionFileActivity`, `parseSessionFileHeader`, cwd and identity helpers, `:1068-1426`), the ownership-verdict contracts and policy (`OwnerVerdict`, `OwnerReconciler`, `acceptOwnerAbsenceEvidence`, `launcherOwnershipFacts`, `:421-722`) and the snapshot/merge internals of the catalog (`:4228-4710`). The Sessions view, the lifecycle and the host import all three kinds from one module.
- Atomic file publication exists in ten forms. `src/host/atomic-file.ts` (`replaceFileAtomic`, `renameReplacing`: exclusive `wx` temp file, nine rename tries with waits summing to 2,170 ms) serves the window registry, the window requests and the profile catalog's rename; `src/host/file-operation-retry.ts` (`retryWindowsFileOperation`: Windows-only `EPERM`/`EBUSY`/`EACCES`, seven attempts, waits summing to 1,075 ms) serves six bespoke writers (`src/host/session-claim.ts:573-588`, `src/host/bridge-records.ts:579-588`, `src/host/control-protocol.ts:1211-1222`, `src/host/native-file-observation-storage.ts:349-370`, `src/host/session-lifecycle.ts:395-418`, `src/omp/config-transaction.ts:69-99`) that differ in exclusive creation (three of six use `wx`), `fsync` (two of ten), temp naming and cleanup; `src/runtime-assets.ts` and `src/host/pty-registry.ts` publish by hard link without retry. `docs/architecture.md:301` describes "one bounded retry helper … exhaust after seven attempts", which is true of one of the two helpers.

The seven performance fixes of 2026-10-12 touched `extension.ts`, `session-index.ts` and `session-tree.ts` again; each change had to be located by reading, not by structure. This design makes the structure carry that information and makes it checked.

## Goals and Non-goals

- Goals:
  - A stated, checked import direction between source layers, so that host and broker code never depends on page or tree-view code and the page never depends on host code; the check runs with `npm run typecheck` and fails the build on a violation or an import cycle.
  - Message contracts and pure helpers both sides use live where their path says so: `src/protocol/` and `src/shared/`.
  - All mutable per-window state of `extension.ts` in one explicit, typed object created at activation, so a reader can see what the window holds and a test can build one without assigning module bindings.
  - The four largest cohesive regions of `extension.ts` become wiring modules with explicit dependencies and their own tests, following the existing `src/host/process-wiring.ts` pattern; the lifecycle harness lists fewer internals after each extraction, never more.
  - `session-index.ts` split along its three concerns, with the class unchanged in behaviour.
  - One atomic-write primitive with one retry policy, used by every writer that replaces a file.
  - No behaviour change: every existing test passes unchanged except for import paths and for harness entries that an extraction makes unnecessary.
- Non-goals:
  - Reducing `extension.ts` to a composition root in one step; after this design it still holds the lifecycle, the launch and restore paths and the native editor paths. Further extractions follow the same pattern as separate work.
  - Changing any wire protocol, file format, retry bound or user-visible behaviour.
  - A dependency-analysis dependency (dependency-cruiser, madge, eslint): the check is one script in `scripts/` with no new package.
  - Reorganising `src/broker/` or `src/omp/` internally.

## Proposed Design

### 1. Layers and the import rule

Source directories become layers with one allowed direction. A module may import from its own layer and from the layers listed; nothing else.

| Layer | May import | Content |
| --- | --- | --- |
| `src/shared/` | nothing in `src/` | Pure helpers with no runtime dependency on Node, DOM, React or `vscode`: `format`, `relative-age`, `terminal-unicode`, `terminal-links`, `code-symbols`, `selection-query`, `footer-metadata`, `panel-identity`, `context-indicator`, `guards`, `notification-text`, and whatever else the check reports as needed by two sides. |
| `src/chat/` | `shared` | The chat model and reducer both sides run. `transcript-window` moves here (it imports `chat/transcript`). |
| `src/protocol/` | `chat`, `shared` | Message contracts and their parsers: `messages.ts` (guest ↔ host), `chat-messages.ts`, `settings-messages.ts` (today `src/webview/settings/messages.ts`), `desk-settings.ts` (today `src/host/desk-settings/protocol.ts` and the pure part of `model.ts`), `rpc.ts` (today `src/host/rpc/protocol.ts`: OMP's RPC frames, used by the page's chat client), `control.ts` (the host-control frames `messages.ts` references as a type today), `detail-target.ts`, `activity.ts`. A contract that today names a host type (`src/webview/settings/messages.ts:1-3` imports `host/omp-settings-core` and `host/settings-pick-items` as types) gets that type moved into the protocol module or into `shared`; the host then imports it from there. |
| `src/host/`, `src/broker/`, `src/omp/` | `protocol`, `chat`, `shared`, each other as today | Process-side code. Never `views`, `webview`, `wiring`. |
| `src/views/` | `host`, `protocol`, `chat`, `shared` | VS Code tree providers and their row models. Never `webview`. |
| `src/webview/` | `protocol`, `chat`, `shared` | The pages. Never `host`, `views`, `broker`, `omp`. |
| `src/wiring/` | `host`, `views`, `protocol`, `chat`, `shared` | Modules that connect host services to VS Code surfaces: the three existing `*-wiring.ts` (moved from `src/host/`, which today import `src/views/`), `src/host/editor-context.ts` and `src/host/predecessor-import.ts` (they import `src/views/`), and the four modules of §3. |
| `src/extension.ts` | everything | The composition root, and the only file allowed directly under `src/`. The other root modules move to their layer: `guards.ts` to `shared`; `bridge-protocol.ts` and `bridge-fragments.ts` (host and page both import them) to `protocol`; `bridge-identity.ts` and `runtime-assets.ts` (host importers only; `runtime-assets.ts` imports `host/private-storage.ts`) to `host`; their tests with them. |

`scripts/check-imports.mjs` (Node, no dependency) walks `src/**/*.ts` and `src/**/*.tsx`, reads every static `import`/`export … from` specifier including `import type`, resolves relative specifiers to files, maps each file to its layer by its first path segment under `src/` (a file directly under `src/` other than `extension.ts` is itself a violation), and fails with one line per violation (`src/host/x.ts:12 imports src/webview/y.ts: host may not import webview`). It also runs a depth-first search over the resolved graph and fails on any cycle, runtime or type-only, printing the cycle. Test files (`*.test.ts`, `*.test.tsx`), the test stubs (`src/views/vscode-test-stub.ts` and siblings) and `test/**` are exempt from the layer rule, not from the cycle rule. `npm run typecheck` becomes `tsc -p tsconfig.json && tsc -p test/e2e/tsconfig.json && node scripts/check-imports.mjs`; CI already runs `typecheck`. The script's own test (`scripts/check-imports.test.mjs`, run by `npm test` through a widened glob or a second `node --test` argument) feeds it a fixture tree with one layer violation, one root-file violation, one re-export-only cycle and one runtime cycle, and asserts the messages. A prototype of the walk run on the tree today, with the matrix above and the root modules still in place, reports 123 edges (65 of them the root modules) and exactly five cycles.

The move list is whatever the script reports after the layers exist, resolved in this order: the root modules; the six pure helpers to `src/shared/`; the contracts to `src/protocol/`; `transcript-window` to `src/chat/`; the wiring modules to `src/wiring/`; then the remaining edges one by one by moving the imported pure module to the lowest layer both importers may see (the prototype names them: `webview/lib/activity.ts` with `host/notification-text.ts`, `webview/detail-target.ts`, `webview/panel-identity.ts`, `webview/footer-metadata.ts`, `webview/lib/context-indicator.ts`, `host/rpc/protocol.ts`, `host/desk-settings/model.ts` and `protocol.ts`, `host/omp-settings-core.ts` and `host/settings-pick-items.ts` for the settings page, `host/control-protocol.ts`'s frame types for `messages.ts`). Import paths are rewritten with the extension-bearing form the repository uses (`./x.ts`); esbuild entry points (`esbuild.mjs:31-138`) are unchanged because they name entry files, not these modules; the three tests that register an extensionless-import hook (`src/views/session-tree.test.ts:48-66`, `src/views/inventory-tree.test.ts`, `src/views/multi-window.test.ts`) keep working because the hook resolves by directory, not by layer. `src/omp/` runs inside the OMP process under Bun's Node-compatible APIs, so it may keep importing Node-using host modules (`src/omp/host-control.ts:101-105` imports `host/control-protocol.ts`); only `vscode` is out of its reach, and no `src/omp/` production import pulls it in today.

The five cycles the prototype found are removed by moving the shared type or value to a leaf module. Four are closed through `import type`: `chat/model.ts` → `webview/lib/transcript-window.ts` → `chat/transcript.ts` → `chat/model.ts` (`src/chat/transcript.ts:4`; a `chat/pending.ts` holds `ActiveTool` and `PendingRow`); `host/pty-client.ts` → `host/pty-shell.ts` → `host/pty-client.ts` (`src/host/pty-shell.ts:32`; `PtyLaunchSpec` moves to `host/pty-protocol.ts` or a `host/pty-launch.ts` leaf); `host/file-name-links.ts` → `host/symbol-links.ts` → `host/file-name-links.ts` (`src/host/file-name-links.ts:4-5`, `src/host/symbol-links.ts:4`; a `host/link-scope.ts` holds `isInside`, `SymbolScope`, `SymbolOutcome`, `FileLookup`, `FileNameLinkResolver`); `webview/components/tool-renderers.tsx` → `debug-tool-renderers.tsx` → `tool-renderers.tsx` (`src/webview/components/debug-tool-renderers.tsx:6`; `ToolRenderContext` and `ToolSemanticView` move to a `tool-render-types.ts` leaf). One is a runtime cycle between two React components, `ChildTranscript.tsx:12` ↔ `Transcript.tsx:41`, which works today only because both are hoisted function declarations; `Transcript` takes the child renderer as a prop (or through a context) so that `ChildTranscript` imports `Transcript` and not the reverse.

### 2. `WindowState`

`src/extension.ts` declares one `interface WindowState` and one `function createWindowState(context: vscode.ExtensionContext): WindowState`. Every mutable module binding that holds per-window data moves into it as a field, grouped and documented by concern (the scout's grouping, `.omp/workspace/tmp/arch/extension-state.md`): session index and claims (`reconciler`, `indexForBridge` …), window registry and routing (`windowRegistry`, `windowFocusedAt`, `windowRequestWatch`, `pendingLaunchWatch`, `resolveAgentRoots`, `requestSelections`), editor panels and bridge (`tabs`, `bridgeWorkspace`, `bridgeStore`, `bridgeEndpoints`, `pendingBridgeEndpoints`, `bridgeSerializerTypes`, `bridgeLiveEditors`, `outcomes`, `openingTabs`, `sessionPanelColumns`, `stoppingTabs`, `readyDocuments`, `panelBindWaiters`, `pendingSessionViewChanges`), guest dispatch (`composerPopupTabs`), PTY and broker (`ptyClient`, `ptyGate`, `brokerSlots`, `editorSlots`, `shellSlots`, `shellEditors`), views (`inventoryViews`, `contextView`, `sessionProcesses`, `launcherProvider`, `launcherView`, `launcherRevealInFlight`, `launcherRevealRequested`, `launcherSelectedPath`, `launcherExpandFor`, `launcherFolders`), providers and models (`defaultProviderModelsAvailable`, `defaultProviderModelsRead`, `defaultProviderModelsDirty`, `sessionModelReads`, `sessionModelRefreshOwed`, `providerLoginTerminal`, `providerLoginOpening`), lifecycle (`activationContext`, `startupRestore`, `startupRestorePending`, `bridgeHostGeneration`, `editorEventSequence`, `nextLauncherRuntimeId`), conversations (`chat`, `detailTabs`, `turnActivities`, `editorRecency`, `turnNotifier`, `replacingConversations`), and the caches (`stagedEntries`, `stagedLeaseHelper`, `unityProjects`, `olderBuildNoticed`, `launcherRuntimeIds`, `brokerWatches`, `nativeObservations`).

`activate` calls `createWindowState(context)` once and stores it in the one remaining module binding, `let window: WindowState | undefined` (`undefined` before activation and after `deactivate`); every function that used a global reads `window.<field>` through a `state()` accessor that throws when no state is installed, which is the invariant the scattered `activationContext === undefined` checks express today. `deactivate` disposes through the object and clears the binding. Nothing else about the functions changes in this step.

The rewrite is done by deletion, not by substitution: the module bindings are removed and `WindowState` is declared, after which `tsc` reports every reference that resolved to a deleted binding, and each is changed to `state().<field>` by hand or by a scope-aware codemod (`ast_edit`), one binding at a time. A local variable or parameter that shadows a global name (`tabs` and `chat` at `src/extension.ts:6241-6252`, among others) keeps resolving to the local and is reported by nothing, which is correct: it never referred to the global. A blind textual rename is not used.

The harness in `src/extension-lifecycle.test.ts` calls internals without `activate` (`reset` builds the fixtures, `:141-253`), so it installs the state itself: the `ACCESS` block exports `installWindow(state: WindowState)`, and `reset` calls it with `createWindowState(fixtureContext)` (both names are in the bundled copy only, like the harness itself). The harness then sets fields on `harness.window()` (`harness.window().windowRegistry = registry`) instead of assigning module bindings; `setWindowRegistry`, `setPackageDrift`, `setActivationContext`, `setResolveAgentRoots`, `notificationTree` and the assignments inside `policy`, `desktopEnvironment`, `shellContext` and `shellFixture` go away. The four *function declarations* the harness reassigns (`openPanel` at `src/extension.ts:5973`, `ensureBridgeEndpoint` at `:7422`, `brokerProvenanceFor` at `:3121`, `launcher` at `:4312`; the bundled copy can assign a function declaration) are not state: they stay as they are in this step and become injected dependencies of the modules that own them in §3 (`openPanel` and `ensureBridgeEndpoint` in EditorPanels and BridgeHost, `brokerProvenanceFor` in SessionActions, `launcher` in the launch path), after which the harness reassigns no module binding.

### 3. Wiring modules cut out of `extension.ts`

Each region below becomes `src/wiring/<name>.ts` exporting `interface <Name>Deps`, `interface <Name>` (the handle) and `register<Name>(deps: <Name>Deps): <Name>`, like `registerSessionProcesses`. A region is its function list; the line ranges locate it today and are not a contract. The module owns a `WindowState` field only when every reference to it is inside the region (checked by `grep` at cut time); a field that other regions read stays in `WindowState` and the module reads it through `deps`, until those readers call a handle method, at which point the field moves. The module is tested through its interface with fake deps in `src/wiring/<name>.test.ts`. `extension.ts` keeps one call per module and the functions outside the region call the handle. The regions, in the order they are cut (each cut shrinks the next one's dependencies):

### 4. `session-index.ts` split

### 5. One atomic-write primitive

`src/host/atomic-file.ts` becomes the one module for replacing a file's content and for retrying a file operation: `replaceFileAtomic(target, content, options?)` with `options.sync` (fsync the file before the rename; the catalog and the native-file-observation store ask for it), `options.mode` (`0o600` for the records that set it today), `options.backoff` (see below), and a temp file `<target>.<pid>.<uuid>.tmp` created with `wx` next to the target, removed on every exit path; `retryFileOperation(operation, backoff)` (today `retryWindowsFileOperation` in `src/host/file-operation-retry.ts`), which `renameReplacing` and the two non-replacement callers use (`SessionIndex.restore`'s three-attempt claim admission at `src/host/session-index.ts:2633-2642`, and `src/omp/config-transaction.ts:7`). The retry budgets stay what they are, named: `RENAME_BACKOFF_MS` (`[10, 20, 40, 80, 160, 320, 640, 800]`, nine tries, the registry, requests and catalog) and `FILE_OPERATION_BACKOFF_MS` (`[25, 50, 100, 200, 250, 250]`, seven tries, every caller of `retryWindowsFileOperation` today), each writer keeping the budget it runs under now, so that no launch admission or record write waits longer or shorter than before; unifying the two budgets is a separate decision with its own measurement. `src/host/file-operation-retry.ts` is deleted and its tests fold into `atomic-file.test.ts`, which also gains a test of the whole replace (exclusive temp, cleanup on failure, content on success, the requested backoff honoured). The six bespoke replacement writers of the Problem section call `replaceFileAtomic`; `src/host/pty-registry.ts` and `src/runtime-assets.ts` keep their hard-link publication (it is a different operation: create-if-absent with a conflict answer, not replace) but take the temp-file naming and cleanup from the same module through an exported `stageBeside(target, content)` helper. `docs/architecture.md:301` is corrected to name the one module and both budgets.

## Alternatives

- **An import linter package** (dependency-cruiser, eslint-plugin-import). Rejected: a new build dependency and configuration dialect for a rule that fits in one short script; the script is also runnable by `node --test`.
- **Keep the pure helpers in `src/webview/lib/` and whitelist them.** Rejected: a whitelist is a list of exceptions that grows; the path should say what the module is.
- **A class `Window` with methods instead of a state object plus free functions.** Rejected for this step: it would rewrite every function signature at once; the state object is the smallest change that makes the state explicit, and §3 moves the functions in bounded groups.
- **Extract the seams first and gather the globals afterwards.** Rejected: each extraction would have to invent its own way to reach the globals it does not own; with `WindowState` first, every extraction takes slices of one object through its `Deps`.
- **Cut `extension.ts` by file size (every N lines) or by one agent per region in parallel.** Rejected: the regions share the one file; parallel writers on `extension.ts` cannot be serialised by ownership, and the harness must keep passing between cuts.
- **Keep two helper modules and document the difference.** Rejected: two modules are what let six writers drift in exclusivity, `fsync` and cleanup. **Unify the two retry budgets** in the same step: rejected by the independent review, because the seven-try budget bounds a launch admission (`SessionIndex.restore`) and a longer wait there is a behaviour change this design promises not to make; one module keeps both budgets under their names, and merging them is a separate decision with a measurement.
- **Also fsync the parent directory after every rename.** Not adopted: no writer does it today, the files are small records whose loss on power failure is tolerated by their readers (leases expire, claims are re-verified), and the cost is one more system call per write on every path; it can be an option later.

## Risks and Open Questions

- **The `WindowState` rewrite touches most of `extension.ts`** (every reference to about 70 names). Mitigation: it proceeds by deleting bindings and following the compiler, one binding per step, so a shadowing local is never touched; the lifecycle test exercises the paths; it is one commit on its own, before any extraction.
- **An extraction changes a function's reach.** A function moved into a module can no longer reach a global it used implicitly. Mitigation: the compiler reports it; the dep is added explicitly; the design treats a long `Deps` list as information, not failure. A region whose `Deps` would exceed about twenty members is cut smaller.
- **Test timing.** Harness cases that rely on reaching into two regions at once (open a session, then inspect bridge state) may need the module handles instead; such a case moves to the module whose behaviour it asserts.
- **`src/omp/` runs inside the OMP process** under Bun's Node-compatible APIs and imports Node-using `src/host/` modules; the layer rule keeps that, and the check must not force `src/omp/` to go through `protocol`. Open: whether `src/omp/` should become its own layer below `host` later; not in scope.
- **Cycle check false positives** on type-only self-references through re-exports. Mitigation: the script resolves `export … from` like an import and the test fixture covers it.
- **Exemptions.** Test files are exempt from the layer rule so that a host test can use a page parser as a fixture, and remain subject to the cycle rule; the independent review kept the exemption.

## Rollout and Verification

Sequence, each step a commit with `npm run typecheck`, the affected tests and the full `npm test` green (the full run is bounded by the real-broker suites, about three minutes; it runs once per step, not per edit):
