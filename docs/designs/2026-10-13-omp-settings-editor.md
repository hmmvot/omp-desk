# A full editor for OMP's own settings, global and project

## Problem

`/settings` is OMP's terminal settings menu. It exists only in OMP's TUI (`slash-commands/builtin-modes.ts`, `showSettingsSelector`); RPC has no settings commands. A Desk user in Chat who types `/settings` is told it is a terminal command and is sent to the Models editor, which covers model roles, fallback chains and agents (about 14 of roughly 550 settings). Everything else (appearance, thinking and sampling, retries, approvals, compaction, memory, editing and LSP, shell, tools, tasks, providers) needs a terminal, and nothing in Desk can write the project layer (`.omp/config.yml` of a folder) for any of it.

## Goals and Non-goals

- Goals:
  - Edit what the terminal `/settings` shows (the same tabs, groups, labels, descriptions, controls and visibility rules), in a Desk editor tab, writing the **global** layer (`<agent dir>/config.yml`) and the **project** layer (`<folder>/.omp/config.yml`), one chosen layer per change.
  - Show, per setting, the value in each layer, the value OMP uses and the layer it comes from (default, global, project, runtime, overlay, environment), the environment variable in play, and whether OMP hides the setting under its own visibility condition.
  - Reset removes a layer's value, so the other layer or the default shows through, as OMP's own `unset` does.
  - Open from the Chat composer's `/settings`, the palette command `ompDesk.openOmpSettings` and the Sessions title menu.
  - Fail closed: an installed OMP whose schema has a shape this build does not recognise is refused with a clear message (no version number gates it, ADR-0011); credentials are never read into the page; every refusal names its reason and writes nothing.
- Non-goals:
  - Credentials and tokens (set in a terminal), the plugins tab, theme and status-line live preview, and settings OMP itself does not show in its panel.
  - Editing records and free-form lists (they open the YAML file at their key).
  - Changing a running session's settings through RPC (OMP has none), or claiming which settings apply live.
  - The final visual design: the page is plain and functional, and its presentation is separated so a later pass replaces it.

## Current State

- ADR-0048 and the Models and Agents editors write 14 setting paths through a staged Bun worker (`src/omp/settings-worker.ts`) that imports the selected OMP's own sources, and through `writeConfig` (`src/omp/config-transaction.ts`): OMP's native file lock, re-read under the lock, targeted-key merge with conflict check, staged fsync and atomic replace, no unlink, exclusive first creation. ADR-0061 reuses the same transaction for the inventory toggles.
- `slash-registry.ts` maps the TUI-only builtin `settings` to the Models editor; `nativeSettingsCommand` intercepts `/models` and `/agents` before anything is sent.
- OMP 18.10.3 (installed, sources verified): `config/all-settings.ts` `orderedSettings()` lists 550 registry handles; 414 carry panel metadata (`ui`); `config/registry.ts` `lookup(id)` and the `Setting` handle give `type`, `default`, `enumValues`, `ui`, `isCredential`, `envName`/`envFallback`/`envValue()`, `layered(scope)`, `get(scope)`, `provenance(scope)`, `accepts`, `assertWritable` and `definition.normalize`; `pi-tui/overlays/settings-defs.ts` exports `SETTING_TABS`, `TAB_METADATA`, `TAB_LEADS`, `TAB_GROUPS` and `getSettingsForTab(entries, tab)`, which is the mapping from a setting to the terminal's control (`boolean`, `enum`, `submenu`, `text`, `multiselect`, `providerLimits`) and hides numbers and lists that have no option list. `config/settings-ui.ts` `createSettingsHost()` builds the entries (with an environment note in the description) and holds the visibility `CONDITIONS` table, which is module-private and evaluated against the writable global `Settings` singleton.
- `Settings.loadReadOnly({ cwd, agentDir })` loads the layers with OMP's in-memory key migration but without the legacy `settings.json` and agent.db migrations, without agent.db and without writing or quarantine files, and answers `getGlobalSettings()`, `getProjectSettings()` and `getProvenance(setting)`. The project layer of OMP is the merge of every project settings file the capability loader finds (`.omp/config.yml`, `.omp/settings.json`, `.claude/settings.json`, …); `.omp/config.yml` is the native one.
- `omp config get|set|reset` is OMP's CLI over the same registry; `set` writes the global layer.

## Proposed Design

### Pieces

| Piece | File | Role |
| --- | --- | --- |
| Schema projection | `src/omp/config-schema.ts` | Pure: turns duck-typed OMP registry handles, tab definitions and layers into the bounded JSON of `ConfigSnapshot`; version range; shape assertion; baseline projection. |
| Visibility rules | `src/omp/config-conditions.ts` | OMP's 13 condition names over a read-only reader; unknown name is a result, not a guess. |
| Worker | `src/omp/config-settings-worker.ts` | Bun, staged and verified like the other workers. Actions `read` and `write`. Imports OMP's sources, never initializes OMP's writable singleton. |
| Controller | `src/host/omp-config-controller.ts` | VS Code free: parses page actions, one operation at a time, request-id dedupe, scope rule, write then fresh read, outcome sentence, open-at-key. Ports for worker, post, file open, scope pick. |
| Panel host | `src/host/omp-config-editor.ts` | `OmpConfigEditors`: one webview panel per profile and scope, serializer for restore, staging of the worker, QuickPick scope control, palette command. |
| Protocol | `src/protocol/omp-config-model.ts` | Shared DTOs and the pure sentences. |
| Page | `src/webview/omp-settings/` | `main.tsx` (state and bridge), `model.ts` (pure filter, badges, list edits), `components/` (thin presentation), `styles.ts`. |

### Schema extraction

The worker imports `config/all-settings.ts`, `config/registry.ts`, `config/settings.ts`, `discovery/index.ts` (so the project layer finds its capability providers, as the inventory worker does) from the selected OMP package and `pi-tui/src/overlays/settings-defs.ts` from its sibling package, by file URL, as the other workers do. It builds the same entries as `createSettingsHost()` (without predicates), asks OMP's own `getSettingsForTab` for the definitions, and projects each one into a `ConfigEntry`: id, tab, group, label, description (with OMP's environment note), warning, type, control (boolean, enum with options, number chosen from OMP's listed choices, text, multiselect with options and `ordered`), default, the value of each layer, the effective value and its source, the environment variable (`present`, `active`, `fallback`), the visibility result, and `writable` per layer. A real snapshot of the installed OMP is about 270 KB and takes about 0.8 s to produce.

- **Layer values.** Global comes from `Settings.getGlobalSettings()` (OMP's migrated global layer). Project comes from the folder's own `.omp/config.yml`, parsed as the file holds it, because that is the file a project write targets. OMP merges every project settings file in discovery order and the last file that sets a key wins (verified in 18.10.3: `.omp/settings.json` < `.omp/config.yml` < `.claude/settings.json` and the other foreign files), so the worker asks OMP's own settings capability for the files and names, per entry, the last project file that sets it when that is not `.omp/config.yml` (`projectOther: { file, shadows }`; `shadows` is true when `.omp/config.yml` sets the key too, so a project write has no effect). A folder that is the home directory, and the global scope, have no project layer: OMP never treats home as a project, and the worker then runs from the agent directory and reads no project file.
- **Effective value and source.** `Setting.layered()` (the value from the layers alone, never an environment value) with `Setting.provenance()` (`env` first, then `runtime`, `overlay`, `project`, `global`, `default`) and `Settings.getProvenance()` for the layer behind the value when an environment variable wins. When a variable overrides, the page shows the layers' values and an "overrides" badge; the variable's value is never read into the page, as OMP's own panel does not show it either.
- **Visibility.** OMP's conditions are re-evaluated by `config-conditions.ts` over a reader built on `Setting.get` and `Setting.provenance` of the read-only load. A condition that depends on the terminal (`hasImageProtocol`, `nativeRendering`) leaves the entry visible with OMP's note, because a Desk page cannot know the terminal; `macOS` is `process.platform === "darwin"`. An entry whose condition is false is in the snapshot with `visible: false`, is hidden everywhere, search included (OMP's panel drops it before it builds the search corpus), and is refused on write. An unknown condition name makes that entry read-only (`condition-unknown`), not hidden and not guessed.
- **Unknown or complex kinds.** The control mapping is OMP's. Records, JSON lists, `providerLimits` and any definition whose control or option shape this build does not recognise become read-only entries with an "Open `<layer>` YAML at this key" action. Strings whose choices OMP fills at run time (themes, composer shape) are read-only too (`runtime-options`). The 26 numbers that carry panel metadata but no option list (OMP's panel hides them) are editable with a typed number: `{ kind: "numeric", integer }`, a finite number, whole when the setting's default is a whole number (all 26 count lines, milliseconds, hours or seconds); OMP's registry declares no bounds. `parseNumericInput` is the one rule, applied by the page before it sends and again by the worker, which also runs OMP's `assertWritable`, so an invalid value is never written. Over-long values (more than 4096 characters or 256 items) are read-only (`oversize`) and never sent. Layer values of complex entries are a one-line summary ("mapping, 3 entries"), never contents.
- **Bounded.** The projection reads only the registry; values are capped, option lists are capped at 256, the worker's stdout is capped at 8 MiB by `runSettingsWorker`.

### Secrets

An entry whose handle has `isCredential` (explicit `credential` or legacy `ui.secret`), or whose definition is a masked text, is projected as `readOnly.reason = "secret"`: no control, no default, no effective value, layers carry only `state` (`set` or `unset`), and the note names the terminal command (`omp config set <id> <value>`). Environment values are never read into the output for any entry. The write baselines the host keeps are a projection of registered, non-credential setting paths only, so a credential does not sit in the extension host's memory either. The write path refuses a credential by the same projection, and the unedited credential in the YAML is carried through the write untouched. The raw layer values never leave the worker, so only the page-bound snapshot and the baselines need the guarantee, and both are tested against a planted value.

### Writes

`set` and `reset` actions carry one setting id and one layer. The host controller validates shapes, refuses a project write when the scope has no project layer (global scope, home folder), turns an empty text save into a Reset as OMP's panel does (it removes the key rather than pinning an empty string), refuses to open a credential at its key, and passes `{ action: "write", scope, changes, baseline }` to the worker with the layer's baseline from its last read. The worker re-projects the snapshot and refuses, with a sentence that names the setting and the reason, unless: the id is in OMP's panel, the entry is not read-only, OMP's condition is true, the layer is writable, the value is one the control offers (a listed choice for enums and listed numbers, a number that passes `parseNumericInput` for a numeric control, text of at most 4096 characters, a duplicate-free subset of the listed members for lists), `definition.normalize` accepts it, and OMP's own `assertWritable` accepts the merged value. Then `writeConfig` runs under OMP's file lock exactly as ADR-0048 specifies: unrelated and unknown keys are retained, an overlapping change to the edited key since the read refuses ("changed outside the editor"), a changed target, malformed YAML or a lost file refuses, an edit that changes nothing never rewrites the file or strips its comments, a missing file is created exclusively. Reset deletes the key and prunes the mappings it emptied, which is what OMP's `unset` does (`mergeConfigEdits` gains a `pruneEmpty` option; the Models and Agents editors keep their shape). The global layer is written from OMP's migrated global layer reread under the lock, as ADR-0048 already specifies; the project file is written as the file holds it. After every write the host reads again and answers with one sentence: what was saved to which layer and what OMP now uses and from where, so a project value that shadows a global write, or an overriding variable, is visible in the very result.

### Version coupling

OMP internals change between releases. There is no numeric version gate: ADR-0011 runs the installed OMP without one and keeps verification per release, so the shape checks are the gate. Every imported module and every handle member the projection uses is checked (`assertSchemaShape`), including the members that decide secrecy (`isCredential`, `definition.credential`, `ui.secret`, each a boolean or absent) and the provenance words (an unknown one is a drifted schema, not "default"); a failed import, a missing export or a malformed handle ends in one refusal ("a shape this version of OMP Desk does not recognise, so nothing was read or changed"), with no native error text. A setting is secret when any of the three markers says so. Per-setting drift (a new control kind, a new condition name, an option list that does not fit the setting) degrades that setting to read-only, not the editor. The snapshot reports the OMP version and whether it is the verified one (`VERIFIED_OMP_VERSION`, 18.10.3); another release is read through the same checks and the page says it was not verified with it. Three tests pin the coupling: a committed recording of the registry and panel definitions (`src/omp/fixtures/omp-schema.json`) that the projection is tested on without OMP installed; a live test that records the installed OMP again and fails when it differs (rerun with `UPDATE_OMP_SCHEMA_FIXTURE=1` after reviewing the change); and a live probe that compares the editor's visibility rules with OMP's own predicates, evaluated by `createSettingsHost()` over an in-memory `Settings.init`, across sweeps of the inputs. Adopting a release as verified is a deliberate change that follows those tests passing on it.

### Applying changes

OMP records no per-setting liveness, so the editor makes no per-setting claim. Facts verified in the installed source: `rpc`, `rpc-ui` and interactive processes call `settingsInstance.startWatching()` (`main.ts`), which reloads `config.yml`, the project settings files and `--config` overlays after a debounce, and effects (theme, redaction, request limits) re-apply when a value changes; a setting a consumer reads once at construction takes effect in the next session. The page says this once, in its footer. The Models editor's explicit "apply to this session" for the default model and thinking level is unchanged; `/settings` does not change the running session's model.

### Entry points

- `nativeSettingsCommand` recognises a bare `/settings` (case-insensitive, nothing after it) in prompt, steer and follow-up and opens the editor on that Chat's folder and profile without sending anything; with arguments it reaches the terminal-only guidance, whose action is now `omp-settings` (it was `models-settings`) and opens the same editor. The slash completion lists `/settings` among Desk's commands. `/models` and `/agents` are unchanged.
- `ompDesk.openOmpSettings` (palette, category OMP Desk) opens on the active session's folder, else the first workspace folder, else the global scope.
- The Sessions title menu shows it as the first entry of the settings group, before Models and Agents.
- One editor per OMP profile and scope; the header's scope control picks the folder (QuickPick of the folders Sessions shows, or a folder dialog) and a layer switch picks Global or Project; panels restore across reload through a serializer and a bounded list of stored contexts, as the Models and Agents panels do.

### Page

Plain and functional: a header (OMP version, profile, layer switch, scope, Reload, Open config), a filter box, the ten tabs OMP lists with counts, OMP's groups as headings, and one row per setting: label, id, description, OMP's warning, the visibility note, badges (layer values, "in effect: …", "project: other file", "$VAR overrides"), the control for the chosen layer (checkbox, select, text with Save, checklist with order and Save/Discard) showing the layer's own value or the value in force marked inherited, and Reset. Read-only rows show their note and, except credentials, "Open `<layer>` YAML at this key". A status line reports each result; a footer carries the apply note. Presentation components take plain props and import no host code; `model.ts` holds all logic that needs no React; `styles.ts` is one replaceable stylesheet, so the approved visual design replaces `components/`, `styles.ts` and the layout of `main.tsx` without touching the data and protocol layer.

## Alternatives

- **Extend the Models and Agents worker.** Its read path starts credential snapshots, a model registry and an agent loader, none of which this editor needs; a separate worker keeps the heavy one unchanged. The transaction is shared.
- **Hand-written settings list.** Duplicates 414 definitions and drifts at once; rejected for OMP's own registry and panel mapping.
- **Host the TUI `/settings`.** Violates the native-editor choice of ADR-0048.
- **`Settings.init` and OMP's setters.** Gives OMP's validation and visibility predicates for free but opens an effect-binding, process-wide singleton (persisting, with background saves, migrations and file watchers, unless it is the in-memory variant, which the live probe uses) inside an editor transaction; ADR-0048 already rejected setter-based writes. The editor takes OMP's `assertWritable` and `normalize` per setting instead and repeats the 13 visibility rules, pinned by a live comparison with OMP's own.
- **One layer implied per setting** (as the TUI writes global only). Rejected: the project layer is the point of the feature; each change names its layer.
- **Free list input.** OMP's own panel offers lists only as membership; the editor offers the same. Numbers with a listed set are offered as that set, and the 26 without one take a validated number (decision of the user: a finite number, whole when the default is, since the registry declares no bounds).
- **Show environment values.** OMP's panel deliberately does not; neither does the editor.

## Risks and Open Questions

- Settings OMP's panel hides stay config-file only (136 settings without panel metadata, 8 lists without choices), reached by Open config, except the 26 numbers that carry panel metadata but no choices: the user decided they are editable with a validated number, so the editor shows slightly more than the terminal `/settings`.
- The editor writes `<folder>/.omp/config.yml` while OMP merges several project files; a value another file supplies can shadow it. The row names the winning file (`.claude/settings.json overrides`, or `project: .omp/settings.json`), and the result sentence says so when a project write is shadowed, because OMP merges foreign files over `.omp/config.yml`.
- Rewriting the global file from OMP's migrated layer removes YAML comments and applies OMP's legacy-key migration to the file, as ADR-0048 already accepts for the Models editor. The project file is rewritten from its own content and loses its comments the same way.
- OMP's visibility rules are repeated, not imported; a new OMP rule is read-only until the table learns it, and the live comparison fails first.
- The project layer is read for the folder the editor is bound to; a nested `.omp` in a subfolder of a session's cwd is not consulted, and neither is one above it: OMP's settings read only `<cwd>/.omp` and the other project files of `<cwd>`, with no walk up to ancestors.
- Environment as seen by the extension host can differ from the user's terminal.
- The first project write creates `<folder>/.omp/config.yml`. OMP loads AGENTS.md, RULES.md and SYSTEM.md from the *nearest non-empty* `.omp` between the folder and the repository root, so in a subfolder of a repository whose root `.omp` holds those files the new file would stop them loading for sessions in that folder. The worker detects this before the first creation (`ancestorContextDir`) and refuses with a sentence naming the effect and the ancestor, and the page shows the same notice; the user can create the file by hand. Not detected: a folder that already has a non-empty `.omp`, which changes nothing.
- A legacy spelling in a file (`task.eager: true`) shows as "not recognised here (OMP may migrate it)", because OMP migrates some; resetting the new key leaves the legacy key in force.
- Writing `defaultThinkingLevel` or `modelRoleStorage` to the project layer overlaps the Models editor, which keeps them global-only (ADR-0048); `modelRoleStorage: project` enables ADR-0048's project role writes. This editor exposes what OMP's panel lists (plus the 26 typed numbers below).
- A `/settings` interception runs before ADR-0052's advertised-name rule, as `/models` and `/agents` already do: an extension command named `settings` cannot be reached from Chat.
- Reading a credential's YAML line: opening a file in VS Code shows its whole content, and the page refuses an open-at-key for a credential row; the retained state (snapshot, baselines) never holds a credential value. A refused value forwards up to 300 characters of OMP's own validation text for the edited, non-credential setting.
- The sweeps that pin the 13 visibility rules do not exercise the project branch of `contextFilesExtraNotProject` or environment inputs.
- Open for the visual pass: layer switch placement, per-row layer selector versus page switch, search scope across tabs, density, and whether hidden-by-condition rows deserve a toggle.

## Architecture Review

- Reviewer: architect (independent, 2026-10-13), two passes against the working tree and the OMP 18.10.3 sources.
- Outcome: accepted after changes. The first pass verified the approach (schema from OMP's own registry and `getSettingsForTab`, layers from `Settings.loadReadOnly`, writes through the locked transaction), the counts (550 settings, 414 with panel metadata, 26 numbers and 8 lists without choices, 13 conditions, 10 tabs, 8 credentials), the reset-prunes-parents rule and the layering, and found four material issues, all fixed: (M1) the numeric version gate contradicted ADR-0011, so it was removed and the runtime shape checks are the gate; (M2) credential classification was not covered by the shape check, so `isCredential`, `definition.credential` and `ui.secret` are all checked and any one marks a secret, and an unknown provenance word is a shape refusal; (M3) project-file precedence was modelled backwards (a foreign project file overrides `.omp/config.yml`), so the worker reads OMP's own settings capability and names the winning file; (M4) the first project write could stop an ancestor's AGENTS.md, RULES.md and SYSTEM.md loading, so it is refused with the reason (the author's decision; confirmation was the alternative). Its minor findings were applied: empty text is a Reset, an inherited control shows the layer below, legacy keys are labelled "not recognised here", the home folder and the global scope have no project layer, a credential row cannot be opened at its key, the conditions rationale is corrected, and ADR-0048 and ADR-0052 carry amendment notes. The second pass confirmed those fixes and found two more, both fixed: the ancestor check refused a folder that is the repository root (it now returns nothing there), and the README and CHANGELOG still claimed a version range. The user's later decisions (26 typed numbers, hidden entries hidden in search, the S1 layout with a Global / Project / Effective switch) are recorded in this document.
