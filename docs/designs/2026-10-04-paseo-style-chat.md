# Paseo-style Chat with OMP-native semantics

## Problem

Chat currently gives routine tool output the same visual weight as prose: bordered cards, bounded body previews and a separate intent line. The existing 100-card recent window limits initial paint, but loading older history can grow the mounted DOM indefinitely. Scroll following is inferred from geometry alone. Adopt Paseo's quiet transcript and composer, without replacing our OMP-specific renderers, host-owned reducer or process ownership.

All four implementation slices are implemented and the coordinated isolated installed-window acceptance is complete, with methods and residual limits recorded below. The companion [HTML mockup](assets/2026-10-04-paseo-style-chat-mockup.html) and [PNG](assets/2026-10-04-paseo-style-chat-mockup.png) remain authored illustrative data, not an installed screenshot. A completed turn followed by the next live turn illustrates finished and running states in separate turns.

## Goals and Non-goals

- Flat, one-line tools with inline disclosure; unboxed assistant Markdown; collapsed reasoning; Copy/duration/time beneath finished replies.
- `omp.toolCallDetail`: `overview` (default) or `detailed`, plus an always-discoverable in-chat toggle. Overview aggregates each consecutive eligible run, shows failures, expands to individual semantic rows and exposes live edits while they are being written.
- Grapheme-safe paced text and user-intent-aware bottom anchoring with a round jump-to-latest control.
- Semantic advisor cards, hidden-message exclusion, source-guaranteed skill attribution, chronological goal/retry/fallback rows, and a dynamic slash picker.
- Visible-window DOM virtualization with measured heights and anchor preservation, building on the existing history/window/reconciliation contracts.
- All production colors derive from VS Code CSS variables; accessible operation at narrow widths, high contrast and reduced motion.
- **Non-goals:** host tools/MCP bridge, native Terminal, broker/process/session-claim architecture, lifecycle slash functionality, arbitrary raw details archives, voice input, a changes sidebar and new OMP APIs.

### Density and in-chat toggle

Declare application-scoped enum `omp.toolCallDetail` with only `overview` and `detailed`, default **overview**. The implementation assignment fixed **global persistence for all open chats**, superseding the original resource-scoped proposal. Place a compact Tools control in the composer toolbar beside the model and thinking pickers (moved there on 2026-10-06 from chat-only chrome at the top of the chat column; see the composer-toolbar follow-ups below). It is not an editor-title action; Chat/Terminal switch and native Copy Screen keep their existing ownership. The control remains available at narrow widths (as an icon) and in read-only/passive Chat because it changes presentation only; absent from Terminal.

Selecting a value sends an enum-only preference request to the extension host, which writes `ConfigurationTarget.Global` and broadcasts effective readback to every applicable panel/bridge Chat route. No optimistic persistent state; failure retains the prior value with inline feedback. Settings/menu edits converge on the same value instantly in both directions. Toggle preserves draft, focus, native selection, manual call/group disclosure and source-row viewport anchor; no OMP command, writer lease or mode transition. There is no tab-local density override.

### Overview grouping algorithm

1. Run after chronological positioning, hidden filtering, mutable TODO/Wait replacement and call/result pairing, **before** viewport mounting. Canonical calls retain `callId` and every live/pending/durable alias. Use existing window ownership semantics so a result-only row represents its call once when the call is outside admitted history; remove the orphan representation when its owner arrives. Density never merges durable entries.
2. Scan canonical visible items oldest-first. Start/append a run for each eligible tool. Flush at every visible non-tool: user, prose, reasoning, advisor/custom, retry/goal/fallback, compaction/reset, notices and user execution. Hidden `display:false` items do not introduce visual boundaries. All ask/approval/question forms are **excluded and flush the run**, including a routed `xd://` write whose effective renderer is ask. Every other settled call is eligible: task (subagent spawn), wait, IRC writes and unknown or extension tools join the adjacent run like any read or edit (2026-10-07: Task, Wait and IRC rows used to break the summary into several one-row groups). A **running or queued** task or wait is the one live exception: it keeps its own plain row, so its live face is on screen, and it joins the run once it settles; the group key is retained across that change by rule 3. A failed call joins and shows in the run's failure count. Approval cards are never displaced by a summary. Tools before and after an ask are separate runs even when the live ask's only actionable copy is docked. **A group exists only for a run of two or more calls.** A run with exactly one tool call is a singleton: the projection emits the ordinary flat tool row (no summary header, no nesting) with its own disclosure, failure/warning tone, running spinner and live-edit following. The singleton still reserves its run key (see rule 3), so a live run that grows from one to two calls becomes a group under the same key, with source-alias anchors, detached scroll position and a focused row preserved (the presentation wraps tool rows identically whether flat or grouped, so a focused call keeps its DOM). A run that shrinks to one call becomes a plain row again. Detailed mode is unaffected.
3. Initially allocate a namespaced key `run:<conversation>:<epoch>:<firstCallId>:<allocationCounter>`; counter guarantees uniqueness against live **and redirected** prior keys. Orphan placement also includes its result-entry placement identity, never only the owner's call id. Individual disclosures use separate `call:` keys. Do **not** recompute run identity from today's first visible member. Reconcile previous/new runs by surviving member/source aliases, preserving a run key while any of its members remains; if preceding history merges runs, retain the earliest chronological prior key and redirect the others. On split, only the earliest overlapping descendant retains that key; new descendants get fresh keys. Superseded TODO/Wait and retry-suppressed removals cannot transfer state to an unrelated run. When an orphan's calling card arrives, remove that representation and map its source anchor to the owner, but never transfer the orphan run key/disclosure to the owner's earlier run. Pending→durable aliases refer to one call ownership position, not a new call. Retain call/result aliases for anchor lookup, not indiscriminate run-state inheritance. Rejoin maps surviving keys by conversation/source identity rather than forcing a new epoch to discard reading state.
4. Summary categories come from the OMP renderer's effective semantic family, not substring matching: local edit/apply_patch/ast_edit and file write → edit/write; Bash/Python tool execution → command; file read → read; grep/ast_grep/find/glob/web_search → search; task → agent (“Spawned 2 agents”, counting the tasks of each call); wait → wait (“Waited for 2 jobs”, counting distinct settled job names across calls, and “1 wait” for a wait that reports none); a write to an `agent://` address → message (“Sent 1 message”); remaining → named/other tool calls. Routed writes to agents/process/config/devices are not counted as edited files. Distinct file paths count once **within each category/run**, using existing cwd-relative normalization and authoritative per-file targets; do not lowercase case-sensitive remote paths or guess filesystem equivalence. Command/search counts are calls. If targets are unavailable use “1 edit”/“1 read”, not “1 file”. Multi-file edits count proven files. For unsuccessful operations use attempted language, e.g. “Read 3 files · 1 failed” has tooltip “3 file-read attempts”; do not claim a failed write succeeded (“Attempted to spawn 1 agent”, “Attempted to send 1 message”).
5. Order summary parts consistently: edits/writes, commands, reads, searches, agents, waits, messages, other; omit zero categories and pluralize. Completed example: **Edited 1 file, ran 2 commands, read 3 files, 1 search, spawned 1 agent, waited for 1 job, 1 tool call**. Running example: **Editing 1 file, running 2 commands, reading 3 files** (counts of known calls/targets so far, not future estimates), spinner and textual Running. Any failed call/native error tone adds **N failed**; skipped/cancelled stay neutral, not failures. Attached warning diagnostics add a warning count without counting as failures. A run is running if any member is streaming arguments/queued/running, regardless of coarse agent state. Terminal outcome settles the member; turn completion must not fabricate success for missing results.
6. Summary click opens individual rows in chronological order, initially closed except remembered disclosures/live edits. Group members and individual detail bodies grow in the normal outer transcript flow: no nested vertical scroll regions, height caps, inner latest pin or inner window/controller. Expanded members are separate rows in the outer measured virtualizer, so giant runs remain DOM-bounded with one scroll owner. Native focus/selection retains affected rows and detail DOM until release. Long source/output/diff bodies initially render up to 200 head lines plus 20 tail lines, with in-flow **Show N more lines** and **Show all** controls; complete canonical output remains intact. Wide code may scroll horizontally only. This supersedes the original inner-scroller requirement following the user's 2026-10-05 correction.
7. Detailed mode bypasses summary projection and shows individual flat tool rows. Both modes share body renderers, status, live editing and error semantics. Remove obsolete read-group outer layout/tests/styles, not a compatibility export.
8. **A row with nothing to disclose is one static line (both densities).** When a settled, successful tool call's expanded details would carry no substantive content, the row is not expandable: no chevron, no empty body box, no repeated intent paragraph. Currently this applies exactly to Bash with an empty (`(no output)`) result and Read of an empty file, in both cases with exit code 0 (or none) and no error, timeout, background/service state, diagnostics, late diagnostics, non-text attachments, truncation or artifact notice. The line is `✓ Bash sleep 5 · <intent> · no output`; the intent and “no output” are muted, truncate with ellipsis, and the full text is in the row title. A running or queued call stays expandable, and output arriving later (or an error/non-zero exit) restores the normal disclosure. Other families keep their bodies, which already carry content (diffs, source, “No matches found” notes, job rows, arguments).

### Live-edit expansion rule

A file-edit/write with available actual diff or in-flight written content is **automatically expanded while its arguments are streaming or its execution is queued/running**. OMP tool-call argument growth, partial results and stream previews are data, not success. The existing renderers consume `editDiffPreview`, `files`/`perFileDiffPreview`, fallback text and write content; no second diff synthesizer or host file reader is introduced. A write's available content can show as source rather than inventing a diff. With no usable content show a flat “preparing edit…” row, not an empty/fake diff.

In overview the run remains **one logical group**, but active edits are a presentation exception: completed ordinary members appear only in its summary; live edit surfaces render immediately below that summary at their chronological member positions. When the group is expanded each live edit appears once in the individual list, not again outside it. Interleaved ordinary calls stay in summary until expanded. No later live edit reorders earlier non-tool boundaries. When an edit ends (success/error/skipped), remove automatic expansion and include it in the closed group; failure remains visible in the summary count. User-open individual disclosure is remembered inside an open group, but does not force the group open after automatic expansion ends. If focus/selection is inside an ending edit, defer its DOM removal until focus leaves and announce completion; outer anchor preservation prevents jumps. Live-edit/detail regions are bounded, latest-pinned during updates except active selection/focus. This rule applies equally in detailed mode.

### Reply footer and truthful timing; no Fork

Add one footer below the last visible prose/image segment of a finished assistant reply, not after each text block or intermediate `toolUse` response. A reply host contains source ids for canonical assistant text segments and completion status; copy reads canonical plain Markdown text in chronological order, excluding thinking, tools, hidden messages and advisor/event content. Native image-only replies explain when no text can be copied rather than copy an opaque payload. Flush paced text before exposing finished Copy. Clipboard failure is reported; Copy Screen is unaffected.

Define a **live** display turn as one agent invocation ending at terminal yield/settle, not every provider response. Carry per-turn start, member source ids and confirmed terminal completion in the shared projection/snapshot; existing `working`/`settled`/lastAgentOutcome are scalar live facts, not historical per-entry completion records. Retries, automatic continuation and async resumed work do not prematurely finalize it. Intermediate `toolUse` responses have no footer. Live steer/follow-up injection does not reset an ongoing invocation's timing.

**Durable fallback rule:** a visible user-role message or a guaranteed user-attributed visible skill-prompt starts a history display turn. Agent-attributed custom messages (advisor, async-result, IRC and autoload skills) never start/split one. Between adjacent initiators, host one footer at the last visible text/image-bearing assistant entry with `stopReason !== "toolUse"`; absence of such a candidate means no reply footer. The newest live interval remains unfinished until actual terminal settle and no working/resumed work; the newest stopped/view-only interval may expose its terminal candidate without starting OMP. Historical entries do not encode whether a user message was steer/follow-up: each initiator starts a display interval, explicitly a history grouping rather than a claim of a new engine invocation. Its duration is labeled **user→reply** and uses that initiator's timestamp and candidate completedAt; it is not misrepresented as an exact engine-turn duration. A window missing its initiator cannot infer the interval or duration; preserve candidate source metadata and resolve when earlier history is admitted. Copy hosts collect canonical prose only from the applicable live turn/history interval.

Timing source is verified OMP: `packages/ai/src/types.ts:1080-1084` defines timestamp (epoch ms), **duration as request duration**, and optional `completedAt` wall-clock completion. Derive prompt-to-reply duration only when an attributable turn-start timestamp and final `completedAt` exist and ordering is sane; carry observed live start/completion into page snapshots, not page-open time. For imported history use a proven user-turn initiator and final response; if history window truncates its initiator, wait for earlier data or show “duration unavailable”. If only request duration exists, show **response 2.4s** with tooltip “final model request”, never mislabel total turn duration. Use completedAt for local end time; if absent, label timestamp as **started 14:32**, not finished time. Invalid/negative/nonfinite data is unavailable, not zero. No sums of overlapping provider/tool timers or fake estimates.

**No Fork control in this design.** OMP really has `branch {entryId}` and `get_branch_messages` (`modes/rpc/rpc-types.ts:79-81,329-335`; `rpc-mode.ts:568-571,1555-1557`). The latter lists **user messages**, and branch changes the managed session/clears registry; this is not Paseo's assistant-cursor fork into a newly claim-owned conversation. Our contract forbids identity changes (`src/host/rpc/protocol.ts:246-265`; architecture Editor ownership). There is no verified safe per-assistant-turn fork route within approved scope, so omit the button entirely, not disable a fake control. A new owned-fork feature would require a separate lifecycle design.

### Scroll and streaming policy

**Outer controller:** two modes `following` and `detached`; separately track tagged programmatic writes and actual user input evidence. Initial conversation opens at latest after history readiness and measurable layout. Upward wheel or PageUp/Home/upward navigation detaches immediately before compositor movement or measurement can repin, including inside the 40px bottom proximity. Touch, scrollbar drag and middle-button autoscroll detach on actual movement. Input in composer/menu must not count. Scroll events alone never signify intent (resize, browser anchoring, spacer correction and our scrollTop writes also emit them). A user scrolling downward back within the existing 40px bottom proximity may rearm following. Explicit jump-to-latest always rearms and scrolls after layout; user interrupt cancels its pending correction. Following writes pause during active user scroll intent; detached geometry compensation still preserves source anchors. No unbounded animation/retry loop. All live tool content follows through this outer controller.

During following, content growth, image load, disclosure, composer/HUD resize and virtualizer estimates settle against bottom in a coalesced frame. During detached reading preserve first visible stable source id plus viewport offset; append, edit completion and group expansion cannot steal scroll. Load older captures that same anchor before request and resolves aliases after prepend. Same-conversation authoritative reconnect preserves anchor/disclosures where ids survive instead of current unconditional tail force (`Transcript.tsx:205-219`); actual conversation/branch replacement resets. If anchored source disappears, use nearest surviving predecessor/successor by source order, announce reset and never create a phantom anchor. Round 36px jump button above dock appears only detached/not at latest; accessible name “Jump to latest”, new-activity indicator is count-only, not raw hidden text. End key in transcript can request latest; no global key override while editing.

**Text reveal:** keep full canonical text in reducer; page renders a paced prefix only for append-only growth of a mounted live text/reasoning slot. Adapt Paseo `text-reveal.ts:19-29,36-61,65-97,130-147`: rAF, max 60Hz commits, 150ms backlog horizon, elapsed clamped 250ms, monotonic boundary. `Intl.Segmenter` grapheme segmentation plus hold trailing uncertain cluster during growth (ZWJ emoji/combining mark/regional indicator may extend across arrivals). Segment stable suffix, cache boundaries rather than repeatedly parsing entire completed text. If segmenter absent, reveal whole arrivals without pacing, never UTF-16 character stepping. Historical hydration/replay/remounts reveal whole existing text; no replay animation. Message-id/content-slot change, replacement/non-prefix edit resets to authoritative text. Completion/error/abort flushes immediately. Reduced-motion and screen-reader optimized presentation bypass pacing; hidden page pauses frame scheduling and shows full current text on return, never delayed backlog. Do not pace tool diffs or ask controls.

Native selection copies the visible DOM prefix; per-turn Copy appears only after completion and uses full canonical prose. Do not continuously replace selected Markdown DOM: flush the slot when a user begins selecting, then defer append DOM changes until selection is released. Throttle polite working/completed announcements, never announce every token; expanding reasoning exposes only unredacted available content. Preserve Markdown parser/security, bound frame work and measure changed slot only. Reveal changes feed the same layout/anchor controller, not independent scroll effects.

### Virtualization and history

Keep disk-first paging and exact source/call ownership, but explicitly migrate admission cost: **100 is a density-independent canonical-card/page budget, not the mounted-DOM bound**. Host cannot depend on each page's overview/detailed preference. Each visible non-tool canonical card and each individually owned tool costs one; hidden/internal entries and an orphan result already owned in that admitted window cost zero. This deliberately admits fewer calls/earlier prose in read-heavy 100-card pages than today's one-cost ReadToolGroup; earlier content remains available through unchanged paging, and overview must not secretly change host coverage. A multi-orphan `results` container remains an ownership bookkeeping kind only: emit each unmatched call as an individual canonical tool card, never recreate `reads`. Update history-reader tail/loadOlder and its tests alongside shared window consumers. Split host loaded history, admitted canonical ownership and mounted viewport rows. Exposing older history does not pin every later row in DOM; no canonical data is dropped because a closed overview run costs one presentation row.

Project density across admitted chronological cards first; build prefix-height estimates for those presentation rows. Render only visible range plus approximately one viewport overscan above/below with top/bottom spacer blocks. Keep focused/selected rows and their controlling group summaries mounted as bounded exceptions until interaction ends, so Escape from a distant closed member still collapses the group and returns focus to its summary. Live ask controls stay docked, not virtualized. Use ResizeObserver measurements keyed by conversation/source id, content revision, width bucket, density and expansion mode; invalidate width/typography/theme/font changes and subgroup/layout changes. Unmeasured estimates: tool/reasoning/closed overview ~32px, user/prose estimated from line/Markdown length and width, image reserves declared aspect ratio when available, cards use conservative semantic estimate. These are layout estimates, never user-facing timing/count facts. Hidden rows estimate zero and do not mount.

Preserve source id + intra-row offset before every projection/height/window change; compensate height differences **above** the anchor only when detached, else bottom-anchor controller owns correction. Disable browser overflow anchoring on managed virtualized spacers to avoid double correction. Batch measurement updates once per frame. Expanding/collapsing a group uses constituent source aliases to map anchors; the expanded summary owns its own run identity rather than stealing its members' anchors. Completing live edit maps its removed surface to the group/individual source. Giant expanded runs flatten into the same outer measured visible-range policy; never mount thousands of children inside one virtualized outer row. Individual native output uses bounded head/tail disclosure in flow rather than nested scrollers.

Initial tail still uses orphan-result ownership under the canonical cost above. Fetch/reveal older cards with existing earlier-message control; keep request deduplication, timeout rearming, branch reset and source reconciliation. Spacers represent only loaded/admitted history; unknown disk history is explicit Load earlier, not guessed height. Browser find cannot search unmounted text: disclose this limit; no hidden full DOM. Existing supported full-history retrieval/export remains available.

**Accessible paged view:** Overview/Detailed stay the only density values; paged history is not a third density level and has no in-chat control. With host readback `editor.accessibilitySupport === "on"` the transcript uses paged view; `"auto"` is not a reliable detection signal and defaults to normal virtualization. Configuration changes update the mode live. (Until 2026-10-06 the Tools menu also carried a page-local **Paged history (screen-reader friendly)** override checkbox; the 2026-10-06 composer-toolbar change removed it so the VS Code setting is the only switch.) Paged view bypasses pacing and preserves the draft and source anchor on entry, uses 100 canonical-card admission pages with Previous/Next controls and no scroll-triggered unmount of the current reading page. `extension.ts`/`messages.ts` forward the explicit value through the same guarded presentation exchange; no new setting or automatic screen-reader heuristic. Expanded groups share that outer canonical page budget; there are no separate inner tool pages. Both modes preserve focused/selected rows and semantic source identities. Screen-reader speech acceptance remains distinct from keyboard/accessibility-tree proof.

In paged view, the last page follows live appends while retaining its 100-card bound; earlier pages never auto-advance and show a count-only New activity control to reach the last page. Focused/selected rows defer page replacement until interaction ends, as in virtualized mode.

## Alternatives

- **Copy Paseo app/provider wholesale:** rejected; RN DOM mismatch, foreign tool schema, direct child lifetime and MCP features conflict with approved scope and ADR-0038.
- **CSS-only restyle:** insufficient; cannot reliably implement grouped call identity, streaming edit exceptions, live command metadata or virtualized anchors.
- **Only keep read grouping:** fails the requested all-tool overview density. Replace it cleanly rather than nesting read groups inside overview.
- **Third editor-title action for density:** rejected in favor of chat-only chrome, preserving title-space priority for Chat/Terminal and Copy Screen.
- **Use request duration as turn duration / add disabled Fork:** rejected because unsupported semantics mislead users.
- **Always mount loaded rows for browser find:** rejected for default large-history behavior; accessible explicit paging retains read stability without a hidden full DOM.

## Risks and Open Questions

Risks: late result pairing and source-id aliases across pagination; merged/truncated groups losing expansion; auto-collapse removing focused edits; Markdown pacing reshaping selection; giant groups or native output defeating virtualization/disclosure bounds; width/font changes invalidating heights; reconnect forced-tail regressions; command metadata readback racing pushed replacements; custom schema variants losing content; theme contrast; missing historical start/end timing. Mitigations and boundary tests below are required, not excuses for falling back to boxed/growing DOM behavior. No RPC-supported assumption implies every installed version emits optional fields; absence stays explicit.

User decisions (2026-10-04) on the former open questions:

1. **Density toggle persists globally** to `omp.toolCallDetail`, shared by all chat tabs and restarts. The implementation assignment explicitly narrows the original effective-scope proposal to global persistence. No per-tab temporary override.
2. **Legacy skill history** (no `details.prompt`): show the user-attributed label **“Invoked /skill:name · args”**, marked as reconstructed, with the expanded skill text available as a collapsed disclosure under it. Exact original text is never fabricated; agent/autoload skills never appear as user turns.
3. **Unknown timing is shown explicitly** as unavailable; request-only timing stays labeled as response timing.
4. **No Fork** under current lifecycle scope. A real new-session owned fork may be proposed separately; a fake or destructive current-session branch is not an option.
5. **Accessible explicit paging and the loaded-window browser-find limit are accepted** as designed. Global history search is separate scope.

### Composer, saved-image and tool-header follow-ups (2026-10-05)

**Saved images after resume.** OMP never writes pasted or tool image bytes inline into the session JSONL: it persists `{"type":"image","data":"blob:sha256:<64 hex>","mimeType":…}` and keeps the bytes in the content-addressed store `<agent dir>/blobs/<hash>` (OMP `session/blob-store.ts`; its own loader swaps the reference back to base64 on resume). `HistoryReader` used to forward the reference verbatim, so the page built `data:image/png;base64,blob:sha256:…`, which the browser cannot decode; live-sent images worked because a running OMP still holds the base64. `history-blobs.ts` now resolves canonical references beside the nearest `sessions/` ancestor of the file (XDG and subagent layouts included) before parsing each row; only a 64-hex hash is ever turned into a path, one blob is capped at 16 MiB and one read at 64 MiB. Overflow menus and QuickPicks that live in the host are not webview layers. Disclosure `<details>` rows (thinking, summaries, child transcripts) are content, not popovers, and keep their own behavior. Layers that name an `owner` report through `composer-overlay`, whose owner type gained `"menu"`, so the host's Escape-to-stop keybinding stays disarmed while any of them is open.

**Numbered image references, the TUI's convention.** The OMP TUI (`packages/tui` `prompt/composer-attachments.ts`, `coding-agent` `input-controller.ts`) marks each pasted image inline as `[Image #N, WxH]` (`[Image #N]` when the size cannot be decoded), sends the images in the same request (the RPC `prompt`/`steer`/`follow_up` `images` array goes straight to `session.prompt(text, {images})`, identical to the TUI submit path) and pairs the Nth marker with the Nth image by position (`getImageAttachments` labels them `Image #N`/`attachment://N`). Behavior copied exactly: numbers are sequential per draft and **stable while editing** (deleting #2 never renumbers #3; the next attachment takes the next unused number); a marker is **atomic**; an image whose marker was deleted is **not sent**; on submit the surviving markers are **renumbered densely 1..K in number order** (`compactImageMarkers`) because the wire mapping is positional. The extension reproduces the same grammar in `src/webview/lib/image-references.ts` (pure, unit-tested) and the TUI's own regular expression, so the agent sees the same text in Chat as in the terminal and a resumed native history renders the same markers.

*Composer.* The editor stays the native `<textarea>` — IME, Enter/Alt+Enter/Shift+Enter, slash and `@` pickers, text paste, draft hand-off across reload, the autosize and every existing test selector keep working. Markers are plain text in the draft, painted as chips by a click-through mirror layer behind the transparent textarea (`.omp-textarea-mirror`; `<mark>` backgrounds only, so text metrics are identical and no second copy of the text is visible). Atomicity is enforced in three layers: (1) the caret and selection edges never rest inside a marker — native `selectionchange`, pointer release and keyboard movement snap them to the nearest edge in the direction of travel, so one Arrow key crosses a marker and Shift+Arrow selects it whole; (2) a native `beforeinput` interception turns a Backspace/Delete (character or word-wise) that touches a marker, and any deletion that cuts into one, into removal of the whole marker through `document.execCommand("delete")`, which keeps the browser's own undo stack; (3) a safety net in `onChange` repairs any edit that still damaged a marker by removing it whole. Attach, paste and drop insert at the caret (`execCommand("insertText")`, one space of separation where needed); an insertion waiting on an IME composition is deferred until `compositionend`.

*Single source of truth and Undo.* The text decides which attachments exist: an image is attached exactly while its marker is present. Deleting a marker therefore removes the attachment, the thumbnail's × removes the marker(s), and — because the deletion went through the editing command stack — **Ctrl+Z restores the marker and the attachment together, Ctrl+Shift+Z removes both again**; the two can never desync. A deleted image's bytes are retained only so Undo can bring it back, are released oldest-first whenever the retained total would exceed the per-prompt budget, and never count toward it while unreferenced. A marker whose number is not an image of this draft (for example text restored after a reload, where attachments cannot travel — already disclosed) is ordinary text: not atomic, not painted, not sent as a reference. The next draft after a send starts again at #1.

*Transcript.* A user message resolves each `[Image #N, WxH]` marker to its Nth image block: a reference chip (`Image #N`, focuses and scrolls to the thumbnail) and every thumbnail is captioned `#N`. The reference works only inside user messages (`UserImageReferencesContext`), so the same text in assistant prose or tool output, or a marker with no matching image, renders unchanged. Composer thumbnails carry the same `#N` badge and accessible names.

### Amendment (2026-10-07): clickable file references

Chat text and tool rows link file references through the Terminal mode's own detector, validation cache and host open path rather than a second convention: a candidate stays plain text until the host's existing `omp:terminal-link-validate` pair proves a regular file (relative paths resolve against the session cwd), and a plain click posts `omp:terminal-link-open`, which the host re-resolves, re-stats and opens non-preview at the line or column. Detection never edits the rendered text (the characters are wrapped, not replaced), fenced code blocks stay text, and a page without the Chat's provider (detail tabs) renders nothing differently. The installed OMP's own TUI links only through OSC 8 on tool paths and model-authored Markdown links, so bare paths, inline code and `@` mentions are linked here exactly as VS Code's terminal text detection links them in Terminal mode.
