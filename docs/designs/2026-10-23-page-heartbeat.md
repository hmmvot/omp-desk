# A frozen Chat page is diagnosable from the log: a visible page's heartbeat, its recent events and its long tasks reach the host

## Problem

A Chat tab froze: its page's main thread was stuck while the extension host ran normally, the clocks on the page stopped at one instant, and VS Code wrote `CodeWindow: detected unresponsive` only minutes later. Nothing in the OMP Desk log said that a page had stopped, when, or what it had been doing, so the freeze could not be told from a host problem or tied to a cause. The host cannot see a stuck page: it posts to it and hears nothing back either way, and a quiet page is normal.

## Goals and Non-goals

- Goals: the log shows, at Info, when a *visible* Chat page has been silent for 10 seconds, what the page last reported it was doing, and how long the silence lasted once the page answers again; it shows every task of 1 second or more that the page measured, with the browser's attribution; a hidden page, a hidden panel, a replaced document, a paused host and a reloaded page are never reported as a freeze; the report is cheap (constant work per event, at most two posts a second, one timer while visible), carries no message text, and is validated by the existing guest vocabulary against closed vocabularies (ADR-0017's rule for owned diagnostic surfaces).
- Non-goals: unfreezing or reloading a stuck page; a user-visible notice; diagnosing a stall of the extension host (`src/host/loop-lag.ts` does that); detail tabs (read-only pages with no editor slot); a page on the bridge route (see Risks); a general page performance profile.

## Current State

The page posts focus traces (`omp:focus-trace`, debug) and the host logs `loop-lag` stalls of its own. Nothing watches the page's liveness. `retainContextWhenHidden` is on for every Chat panel, so a hidden tab's page keeps running and the browser throttles its timers; a minimised window also hides the page (`document.visibilityState`), and measured on an owned Chromium a page hidden for several minutes ran its timers tens of seconds apart.

## Proposed Design

**One message, `omp:page-health`** (`src/protocol/page-health.ts`, part of the guest vocabulary, panel route only): `reason` (`beat`, `events`, `visibility`, `long-task`), a per-document counter `seq`, `visible`, `lateMs` (how overdue the page's pending beat is at the time of the report), the page's last events and, for `long-task`, the task. Every string is from a vocabulary the parser enforces, so the message cannot carry prose, a path, an element's id or a URL whatever the page sends: an event kind is one of eight local kinds (`render`, `key`, `pointer`, `input`, `paste`, `drop`, `visible`, `hidden`), `rx:other` or `rx:omp:<lowercase-and-dashes>` (the type of a host message); a long task's `name` and `container` are the platform's fixed values (the page sends `unknown` for anything else); a script is an invoker (the browser's invoker type, then for a listener its tag and `on…` handler, for a callback or promise its plain name, nothing for a script), a file name with a character position, and a function identifier, each `-` when it has no such shape. The ring holds at most 12 entries, a long task at most three scripts; a field the page invents is dropped and a wrong shape drops the message. No message type was added in the host-to-page direction and `GUEST_PROTOCOL_VERSION` is unchanged: additive page-to-host messages (`omp:focus-trace`, `omp:chat-magic-keywords-read`) were added without a bump, an older page sends none, and an older host ignores it as an unrecognised message (a package change on disk withholds new documents from an older host in any case).

**Page** (`src/webview/lib/page-health.ts`, installed by `boot()` for session documents, inside a `try` so a diagnostic never stops the page from mounting):
- A beat every 2 s from a `setTimeout` chain while `document.visibilityState` is `visible`. A hidden page stops the beat timer, sends one `visibility` report, and starts again with one when it is visible; throttled timers of a hidden page therefore cannot look like a freeze. Host messages and redraws still run in a hidden page: they are remembered in the ring and not posted.
- `lateMs` is on every report the time by which the pending beat is overdue (0 while it is not due or the page is hidden). After a freeze, queued input and host messages run before the overdue timer, so the first report out is usually an `events` report, and it carries the length of the freeze.
- A ring of the last 12 events as runs of one kind: `rx:<host message type>` (a tap in the transport, called before any listener handles the message and guarded, so it cannot stop a message), `render` (one effect per commit of the conversation view), and the kind of an input (never which key, where or what text), plus `visible` and `hidden`. An event is reported at once, from inside its own handler and before the work it announces, when the last report is at least 500 ms old: a freeze sends nothing afterwards, so what the host can quote is what was posted before it. At most two posts a second while events flow, one per 2 s otherwise. Work per event is a counter update and a comparison.
- A `PerformanceObserver` for `longtask` and one for `long-animation-frame` (the browser lists the supported types; a missing one is skipped). A task of 1 s or more is reported 100 ms after it was seen, joined with the long animation frame that overlaps it: the browser's `name` and container and up to three scripts. The browser calls the observers only for tasks of 50 ms and more. A task that Chromium's DevTools protocol itself runs (an `evaluate`) is not measured as a long task; a task of the page's own (a timer, an event handler) is.

**Host** (`src/host/page-health.ts`, wired in `registerPanelLifecycle`, so every editor's page is covered, active or not):
- `PageStallDetector` (pure, fake-clock tested) keeps the last report and the moment silence is measured from. A page is held to the threshold of 10 s only while the host sees its document in a visible panel **and** either its last report said it was visible **or** the host has seen the user leave and come back (the window not focused, or the tab not in front, at some check since that report, and both now): a page that is shown to the user after that and has not said it is visible again is stuck. That covers a page that froze after reporting itself hidden and is then shown, and it leaves alone a page whose hidden report came while the user was in the window (a tab in a minimised window of its own). The clock restarts at the moment these conditions hold again. A gap above 6 s between two host checks means the host itself did not run (blocked, or the machine slept): the clock restarts, and a stall in progress is marked so its end says the host paused meanwhile. A report whose `seq` did not increase is a page that reloaded in place; it ends a stall with a remark.
- The wiring passes `visible()` as "this very document, the one that reported, is the panel's current document and the panel is visible", and the document itself as a token, so a document the host replaces in the same panel (a mode switch, an explanation page that loads no bundle) or a superseded panel is a new page and never a silent one; and `windowFocused()` as `vscode.window.state.focused && panel.active`. Only documents of kind `guest` are watched.
- `PageHealthMonitor` keeps one detector per editor slot, panel and document, one interval timer (2 s, `unref`ed, on a monotonic clock) that runs only while a page is watched, and logs at Info, with the tab as `tab <id>`: the stall (`no report from the Chat page has reached the host for 10 s while it was visible`, the last report's number, age and visibility, its events oldest first with their age), the end of a stall that was logged (`reports again after 47 s without a report`, how overdue the page's own timer was when that is a second or more, or that a page which had reported itself hidden cannot say, and the host-pause and reload remarks), the close or replacement of a page with a logged stall (`was closed after 15 s without a report`) and every long task (duration, name, scripts, events). Silence is not proof of a stuck page, since a report also rides the window's renderer, so the lines say that no report arrived and the figure of the page's own overdue timer tells the two apart. Lines are bounded by the host whatever a page sends, and a page cannot reset a bound by restarting its counter: a bound belongs to the document the host loaded. One long task a second and 50 per page, 20 stalls per page (the end and close lines follow only a stall that was logged), then one line that says the rest are not logged for that document.

## Alternatives

- **A host ping the page must answer.** A stuck page cannot answer either, so it adds a host-to-page message, a version question and a second round trip for the same information. The page's own beat is the proof of life, and the host's visibility fact is already local.
- **A page-side watchdog in a Worker.** A worker keeps running while the main thread is stuck, but it cannot reach `acquireVsCodeApi`; the report would have to go through the stuck thread, or through a loopback channel with its own authentication and CSP entry. More machinery than the silence the host already sees.
- **Log every beat at debug.** Flooding for no information: only a stall and its end matter. The detector keeps the last report in memory.
- **A long-animation-frame-only attribution.** Only recent Chromium reports it; `longtask` stays the trigger and the frame is optional detail.
- **Carry the report on the bridge route.** A bridge request is a sealed frame for an operation the restarted host serves without a panel; a stall check needs the panel's visibility, which that host does not have. A page on the bridge route is the case after a host-only restart, not the one that was observed.
- **Reload the stuck page automatically.** Not asked, and it would discard a draft the page may still be able to save once it answers.
- **Ask whether the panel's last `postMessage` settled** to tell a stuck page from a held-up renderer. Possible, but whether that settlement is the renderer's acknowledgement is not established here; the page's own overdue-timer figure answers the same question without relying on it.

## Risks and Open Questions

- The events of the last 500 ms before a freeze can be missing from the quoted ring (the report is rate limited); the stall line names the last report's own age.
- Whether Chromium throttles the timers of an iframe that VS Code hides with CSS while its page stays visible (`visibilityState`) is inferred, not measured. The host does not hold a hidden panel to the threshold and starts a full 10 s from the moment it sees the panel visible again, so a throttle of once a second at worst does not read as a freeze. [INFERENCE: a longer throttle would log a stall and its end after the tab is shown.] If hiding a retained panel leaves `visibilityState` at `visible`, a hidden tab keeps posting its beat (one small message every 2 s) and the host leaves it out of the judgement; that is the cost.
- Two limits of the document identity: the host reads the panel's current document when a report arrives, so a report in flight from the outgoing document can be credited to the incoming one (a protocol field echoing a document token would close that and is not justified for a rare race); and a replaced document that never reports leaves the old entry until its panel is disposed.
- Whether an occluded or minimised VS Code window flips `visibilityState` in its Electron is not verified here. If it does not, a window the user cannot see is held to the threshold as long as its page is visible by its own last report and the host sees the panel visible, so a page that froze there is reported; a page that merely sits in a throttled hidden window is not at fault if its timers are throttled by no more than a second, as for a hidden tab above.
- A page stopped on a breakpoint of an attached debugger is reported as stalled; that is true.
- The reports need the panel route; the bridge route and detail tabs are not covered. A page that shares the workbench renderer's main thread and not just its channel could not be told apart by this design from a stuck workbench; the overdue-timer figure is the evidence for the difference.

## Rollout and Verification

One change: protocol module and parser, page module and transport tap, host module and wiring, guide (troubleshooting: what the lines mean), architecture paragraph, changelog and the `docs/README.md` map. Verified by unit tests (parser with closed vocabularies, the detector with a fake clock including hidden, focused-window, paused-host and reload cases, the monitor's lines, closing and bounds, the page heartbeat and the long-task join with a fake clock, the attribution shapes with the browser's invoker forms), by a page test in owned headless Chromium (a busy task of the page yields a long-task report whose ring holds the host message type and the input kind but not the key, a late beat, a hidden page that stops posting, and every report the browser made passes the host's parser), by `npm run typecheck`, and by the installed build (a Chat tab's reports reach the log).

## Architecture Review

- Reviewer: architect (independent agent)
- Outcome: first pass accepted with changes (two material findings, five should-fix, seven nits); confirmation pass accepted with changes (no material finding; the armed rule for a page that reported itself hidden, the overdue figure taken before a visibility change, a per-document identity token with host-owned bounds, and nits); final pass accepted with changes (one material documentation finding: the architecture paragraph and the module header still stated the earlier watch rule; corrected, together with the guide's order of a script's fields)
- Notes: the material findings (a page that froze after reporting itself hidden and is then shown was never watched; a document replaced inside the same panel was charged as a silent page) and the should-fix items (the page's overdue-timer figure on every report, wording that silence is not proof of a stuck page, closed vocabularies instead of a character filter, a guarded and removable transport tap, a line when a stalled page is closed) and the nits (monotonic host clock, bounded stall lines, per-document budgets, cost wording, the ADR-0017 note, a `guest` document check) were applied to this design and the code. The confirmation pass's findings (R1 to R3) are described in Proposed Design above. Two minor limits the final pass named are accepted: a stalled page whose document is replaced by one that never reports stays in the monitor until its panel closes, so its end line says `was closed` with the silence up to that moment; and a report still in flight from an outgoing document can be credited to the incoming one when it arrives after the swap (at worst one extra stall line next to the start-failure warning).
