# Quote selected Chat text into the draft

Revised 2026-10-16: the maintainer's answers to the first draft's open questions are in *Decisions*; an independent review of the atomic-block variant of decision 3 led the maintainer to choose an editable band instead (*Architecture Review*). The one remaining open question (the line after a quote) was answered the same day, option B, and is decision 8. The same day the maintainer asked for the quote key to work in a text editor too; that is decision 9 and the *Addendum* at the end of *Proposed Design*.

## Problem

The maintainer's use case: "I read the agent's reply in the Chat, select some text, press Quote, and it lands in the draft, visibly as a quote. I write my comment under it. I repeat this several times and then send one message."

Today there is no way to do that with one gesture. The only paths are copy and paste (the transcript has no `copy` handler of its own, so the clipboard gets the *rendered* text: no code fences, no links, no list markers), or "Add Selection to Session", which inserts one `@path [lines a-b]` line from an *editor* selection and refuses newlines and anything over 900 characters (`src/protocol/messages.ts:354`, `src/webview/lib/insert-text.ts:36-41`). The composer is a `contenteditable` surface rendered from a Markdown string with a band for fenced code ([composer surface design](2026-10-15-composer-contenteditable-surface.md), ADR-0077), which makes a visible quote band natural. The transcript's Markdown renderer, however, renders a quote as inline text only, so a quoted code block would show up broken in the user's own sent message (Current State 2). Two existing transcript defects sit on the path of this feature and are fixed with it: a parser hang on some list-like lines and a fence grammar that disagrees with the composer's (Section 5).

## Goals and Non-goals

- Goals:
  - One gesture quotes the selected text of an assistant reply, a user message or thinking into the draft of the Chat the selection is in, as Markdown blockquote lines (`> `), faithful to the source Markdown of exactly the selection (code fences, links, lists, emphasis), and never silently lossy.
  - The draft shows the quote as a band, the way a fenced block shows as a band: the `> ` prefix stays visible, the text stays editable, and the string stays the single source of truth (ADR-0077). A ✕ removes a whole quote as one undo step.
  - Several quotes interleaved with comments in one draft, in reading order: every quote lands at the end of the draft and the caret is left on a new line after it.
  - A keyboard path and a screen-reader-usable path; one new host protocol member (a panel action).
  - The sent message renders back in the transcript as a quote, including a quoted code block, list or nested quote.
- Non-goals:
  - Quoting from the editor, the Terminal pane, the Sessions views, tool output, tool rows, the dock (queued messages, TODO and Agents rows, the ask dialog) or the TODO/Agents detail tabs.
  - Rich-text paste, attribution lines ("Assistant said:"), a quote that links back to its message, or a structured attachment: OMP receives one string.
  - Changing how OMP reads `@` mentions or slash commands.
  - Any change to ADR-0077: a quote is a per-line property of the rendering, exactly like the code band.

## Decisions (maintainer, 2026-10-16)

Answers to the seven open questions of the first draft, and the choice made after the review. They are inputs, not proposals; sections below say how each is realised.

1. **Trigger.** A contributed command with the key **`Alt+Q`** and a context-menu item. *Changed 2026-10-16 by the maintainer:* the floating Quote button and the per-message Quote buttons that the first answer asked for are not built; the key and the menu item are the only triggers. (Section 1 records how `Alt+Q` was checked.)
2. **Capture.** The source Markdown of exactly the selection, with the plain-text fallback and a notice.
3. **Composer.** An **editable band with a visible `> ` prefix**, following the fenced-band precedent, **plus a ✕ that removes the whole quote as one undo step**. (The first answer was a non-editable atomic block; after the independent review the maintainer chose the band. No ADR-0077 amendment.)
4. **Scope.** Assistant replies, user messages and thinking only. Tool output is not quotable.
5. **Transcript.** Parse the content of a quote as nested blocks for **all** messages (Section 5 lists the rendering this changes and the tests that pin it).
6. **Insertion.** **Always at the end of the draft**, after a line break, with focus moved to the composer and the caret on the new line after the quote. No caret snapping and no retained-caret logic (Section 2 gives the exact separators).
7. **Limit.** Refuse a selection over 20 000 characters, with its size in the message.
8. **The line after a quote (option B).** After an inserted quote comes **one line break only**, and the caret sits on the very next line, so the user writes the comment straight under the quote. The reasons: the transcript renderer ends a quote at the first line without `>` (there is no lazy continuation, `Markdown.tsx` quote branch), so the user's own sent message shows the quote and then the comment as separate blocks; and the raw text the model reads marks every quoted line with `>`. Slice 2 (nested quote blocks) keeps this property: a following non-`>` line still ends the quote in the transcript, and a test pins it. To a CommonMark parser the comment under the quote is a lazy continuation of the quote's last paragraph; this was weighed and accepted (Risks).
9. **The quote key works in a text editor (maintainer, 2026-10-16).** `Alt+Q` with a selection in a text editor quotes it into a Chat session's draft: "the quote then holds a link to the file and the start of the quote, plus the selected text". A separate command **Quote Selection to Session**; the target rule of Add Selection to Session; a first line with the location as inline code (never an `@` mention), then the text as a fenced block for code and as plain quote lines for Markdown and plain text; each multi-cursor selection its own quote. The *Addendum* gives the details and the tests.

   *Addendum (2026-10-16, the maintainer's request, Main's rule): no picker when a Chat is visible.* "Don't show this if a session tab is open and visible in the same window. Here the quote must go into the visible composer." When at least one Chat session view of **this window** is visible on screen, the quote goes straight into that composer, with no picker. A view counts when its webview panel reports `visible` (the front tab of its group, in any editor group); a tab hidden behind another tab does not. Desk has no sidebar or bottom-panel Chat view, so editor panels are all there is. Several visible Chats: the one focused last, by the recency the picker already orders by (`EditorRecency`, touched when a panel becomes active); one no recency knows ranks after the ones it knows, then by title. A visible Terminal-mode session does not count (no composer). A Chat that is not `live` (stopped, so choosing it would first start it, or still starting, or waiting for an answer) does not count either: the picker keeps deciding for those, as it already leaves out a starting or waiting row. A Chat whose process runs but whose page is still mounting counts: the existing hold (`deliverInsertion` waits for the page's ready report, the page holds a quote until a composer mounts) delivers it. With no visible Chat the picker is shown as before. The focus rule is unchanged: the quote lands at the end of the draft and the composer takes the focus. **Add Selection to Session is not changed.** The rule is `visibleQuoteTarget` in `src/wiring/editor-context.ts`, checked by unit tests and by `41-editor-quote-selection.spec.ts` (a Chat in the left group, the file in the right one, no picker).

10. **The quote key works in a diff editor, with the file, the lines and the version (maintainer, 2026-10-18).** "Support quoting from the diff view, with the file and the lines." A selection in either side of any diff editor quotes its text with the file and the line range **of that side's document**; a side that is a Git version says which one. The *Amendment (2026-10-18)* at the end gives the evidence and the format.

11. **With nothing selected, the quote key in a diff editor quotes the whole hunk under the caret (maintainer, 2026-10-19).** In an inline diff, and on either side of a side-by-side diff, with the caret on a changed line `Alt+Q` (and the editor menu entry) quotes the hunk: a `diff` block with its unchanged context, under a location that names both sides. With no change under the caret the caret-line reference stays; a selection quotes the selection. The *Amendment (2026-10-19)* gives the format, the diff and what differs from VS Code's own hunks.

12. **The quote key works in VS Code's Markdown preview, with the document's name (maintainer, 2026-10-20).** `Alt+Q` (and **Quote Selection to Session**) in the built-in Markdown preview quotes the selected *rendered* text, not the source, under the document's path (no line numbers). The *Amendment (2026-10-20)* gives how the selection is read and the document identified.

### 2. The Markdown pipeline and whether source is available per block

- The renderer is project-owned and renders straight to React nodes; there is no AST and no node carries `position` or `data-*` source information (`Markdown.tsx:313-464`, DOM output at `:466-472`).
- The only offsets are `MarkdownParse.starts`, the first line of each *top-level* block (`Markdown.tsx:299-304`, pushed at `:344`). They live in a `useMemo`/`useRef` inside the component and are not reachable from the DOM. Every top-level block pushes exactly one start and one root element, so the Nth child of `div.omp-md` is block N. List items re-parse their dedented bodies through `parseBlocks`, which discards `starts` (`Markdown.tsx:280,291-293`); table rows and quote lines have no offsets.
- The source string of a message lives only in the `text` prop of `Markdown`, in the `source` prop of `CodeBlock`/`MermaidBlock` (also the Copy button's closure, `CodeBlock.tsx:25`) and in the card closure. `Transcript.tsx:202-205` already reads the source of a *user* message (`messageText(message.content)`) for the hover Copy button, and `ReplyFooter.tsx:15-16` has the whole reply text (`reply.text`, built in `src/chat/reply-turns.ts:62-73`).
- Rendered text is not source text: `**x**`, `_x_`, `~~x~~` markers, code-span backticks, heading `#`, link syntax (collapsed to the label), table pipes and the separator row, and list markers are all dropped (`Markdown.tsx:115-142,368-375,405-437,279-286`); a soft newline inside a paragraph becomes `<br>` (`Markdown.tsx:152-159`). So `Selection.toString()` cannot be turned back into Markdown without the source.
- `PacedMarkdown` hands `Markdown` the *revealed* prefix, not the canonical text, and stops painting while the selection touches its slot (`PacedMarkdown.tsx:39-47,63`): while a reply streams and is selected, the DOM lags the canonical text. A source map must therefore come from the parse that produced the DOM, never from the model.
- A reply's row id and element can change while its text stays the same: the streaming card is `live:<streamId>` (`src/chat/transcript.ts:195`), and a message that ended live before its entry is durable is held as a pending row `live:<messageId>` and reconciled to the durable entry by role and timestamp (`src/chat/model.ts:10-13`). That a selection survives such a remount is `[INFERENCE]` and is to be measured.
- **Quotes in the transcript today.** `QUOTE = /^\s*>\s?(.*)$/` (`Markdown.tsx:43`); consecutive matching lines become one `<blockquote>` whose content is `renderLines(quoted)`, inline tokens separated by `<br>` (`Markdown.tsx:383-395`, `:152-159`); the quote ends at the first line that does not match (no lazy continuation). **Fences, lists, headings and nested `>` inside a quote are not parsed as blocks**: `> ```ts` renders as literal backticks and the code lines as plain wrapped text without monospace or indentation. The blockquote style is `styles.ts:424-430` (3 px bar, muted text, High Contrast border). `markdown.test.ts` has no test that renders a quote's shape.
- **A parser hang** (found by the review, which bundled and ran the current `Markdown.tsx`; the cause is read here in code). The paragraph interrupts on `UNORDERED_ITEM = /^\s*[-*+]\s+/` and `ORDERED_ITEM = /^\s*\d+[.)]\s+/` (`Markdown.tsx:38-39,451-452`), but the list branch is entered only when `listItem` accepts the line, and `LIST_ITEM` is stricter: `[ \t]+` after the marker and `\d{1,9}` (`Markdown.tsx:41,212-214,397`). A line both regexes match and `listItem` rejects (`1234567890. x`, a no-break space or an ideographic space after the marker, `-\u00a0x`, `*\u3000x`) skips the list branch, then the paragraph loop breaks on its first line without consuming it (`Markdown.tsx:443-458`), so the outer loop pushes an empty `<p>` forever. The review reproduced out-of-memory on `"1234567890. x"`, `"\u00a0- x"`, `"-\u00a0x"` and `"*\u3000x"`; `"> 1234567890. x"` returns today because quote content is not block-parsed, and would hang after the nested-quote change of Section 5.
- **Two fence grammars.** The composer follows CommonMark: an opening run of three or more backticks, an info string without backticks, and a closing line of *at least as many* backticks (`code-fence.ts:29-30,46`). The transcript opens on `^\s*```(\S*)\s*$` and closes on exactly three backticks (`Markdown.tsx:37,351`): a four-backtick fence opens with the info string `` ` `` and ends at the first three-backtick line or at the end of the message, and an info string with a space (`` ```ts title=x ``) is not a fence at all.

### 3. How the composer stores and renders its draft

- The model is one Markdown string; the field is a `div[contenteditable]` with one `div.omp-line` per line, and the DOM text of a line *is* the model text, image chips included (`src/webview/lib/draft-dom.ts:26-57,74-109`; ADR-0077 and the design above, sections 1 and 6).
- Band lines come from `findFencedBlocks` (`src/webview/lib/code-fence.ts:29-56`: an unclosed block runs to the end) through `lineSpecs`, which sets `code` and `fence` on each line (`draft-dom.ts:36-57`); `buildLine` turns that into `omp-line--code`/`omp-line--fence` (`draft-dom.ts:74-92`). The band is CSS on each line (`src/webview/styles.ts:704-712`, forced colours at `:711`). `LineRenderer` re-renders incrementally by line signature and updates a line in place only when `code` and `fence` are unchanged (`draft-dom.ts:59-61,316-373`).
- Keys: `Composer.onPromptKeyDown` handles `Enter`/`Tab`/`Shift+Tab` inside a fenced block (`Composer.tsx:1229-1245`, edits from `code-fence.ts:89-170`), completions are off in a block (`Composer.tsx:416-418,448`), **`Enter` and `Alt+Enter` send everywhere else, including on any prose line** (`Composer.tsx:154-157,1295-1298`); `Shift+Enter` is the native line break, turned into a model `\n` by `beforeinput` (`draft-surface.ts:473-497`). History recall on the arrow keys needs an empty or recalled draft (`src/chat/prompt-history.ts:40-43`).
- Undo is the page-owned stack of `{text, anchor, focus}` snapshots (`draft-history.ts:8-14`); `surface.apply({from, to, insert, selection}, kind)` and `replaceRange` are one undoable step each (`draft-surface.ts:361-381`).
- The draft hand-off captures the draft with `read`, which freezes the surface and sets `captureRef`, and `release` thaws it and **runs the work deferred meanwhile in the same editor** (`Composer.tsx:948-975`); when the host replaces the editor the replacement page receives only text (`DraftHandoffContent`: `text`, an attachment count and recoverable records, `src/protocol/messages.ts:408-412`). Work deferred behind a capture that ends in a replacement therefore never runs. `freeze()` refuses every mutation until `thaw()` (`draft-surface.ts:326-337`).
- Inserting text from outside the field has two precedents. Add Selection to Session splices at the caret with `spaceInsertion` through `replaceInSurface`, deferred while a capture is held or an IME composition is open (`Composer.tsx:143-146,1001-1022`, `insert-text.ts:36-41`). A recalled or restored queued message is **appended after a blank line** (`src/webview/lib/queue-restore.ts:133-134`: `${draft.text}\n\n${queued}`). The thumbnail ✕ removes an image's markers as one undo step, deferred during a composition (`Composer.tsx:677`).
- Send: `compactForSend`, then `.trim()` of the text (`Composer.tsx:816-817`), then `client.sendPrompt(draft, images)` (`Composer.tsx:857-861`). A draft of only a quote is sendable (`canSubmit` needs non-blank text, `Composer.tsx:420`).

### 4. What OMP receives and how the transcript shows it

- `omp:chat-prompt` carries the string, parsed as text of at most `MAX_CHAT_TEXT_LENGTH = 200_000` and kept verbatim (`src/protocol/chat-messages.ts:81,1258-1268`); `RpcSession.prompt` sends `{type: "prompt", message: request.text, …}` after `classifySlashInput` (`src/host/rpc/session.ts:924-945`). No Markdown processing happens anywhere on the way; a blockquote reaches the model as the literal `> …` lines. Only two things change the text: the trim, and the renumbering of `[Image #N]` markers that belong to attached images (`src/webview/lib/image-references.ts:164-172`, marker grammar `:22-56`). A draft starting with `/` is a slash command (`session.ts:926,937`).
- OMP expands `@path` mentions inside `AgentSession.prompt` for a prompt sent while the session is idle; a mention counts after whitespace or an opening bracket/quote, and a token that names no existing file is prose ([add-editor-context design](2026-10-07-add-editor-context-to-session.md), lines 30-32 and 79).
- After the send the user message is stored as is (`src/chat/messages.ts:166-174`) and rendered by the `Markdown` component above: a `> ` quote shows as a blockquote, inline content only. "Copy message" copies the source (`Transcript.tsx:202-205`).

## Proposed Design

### 0. Shape

````
select text in an assistant reply, a user message or thinking
   └─ trigger: Alt+Q command / context-menu item
        └─ page: Range → Markdown source of exactly the selection (or a rendered-text fallback + notice)
             └─ composer: append the quote at the END of the draft (separator rule, Section 2); focus the composer
                  └─ the draft shows a quote band (editable `> ` lines) with a ✕; the caret is on the new line after it
                       └─ the user writes the comment; repeat; send: the trimmed draft string → OMP; the transcript renders it as a quote
````

Everything is page-local (webview layer). The host's only part is the keybinding/menu command, which posts one new panel action. No new reply message and no selection text cross the bridge.

### 1. Trigger

Both triggers call one page function (`quoteSelectionIntoDraft`), so neither can do what the other cannot. The maintainer decided on 2026-10-16 against a floating button and per-message buttons (decision 1), so there are two triggers; the text below that described them is gone.

1. **A contributed command and keybinding** `ompDesk.quoteChatSelection`: title "Quote Selection", category "OMP Desk", `enablement: ompDesk.sessionMode == chat`, palette-visible, key **`Alt+Q`** with the chat-only `when` (`activeWebviewPanelId =~ /^omp[.]session/ && ompDesk.sessionMode == chat`). The host handler is `postChatPanelAction("quote-selection")`; the new `"quote-selection"` member of `GuestPanelAction` is run by the composer's `providePanelActions` map, which the compiler forces to be complete. With no quotable selection the page says so in the status line (Section 7).
2. **A context-menu item** "Quote Selection" in `webview/context`. The transcript root carries `data-vscode-context='{"ompChatText":true}'` and the item's `when` is `webviewId =~ /^omp[.]session/ && ompChatText`; the item is always offered on the transcript and answers "Select text in the conversation first" when nothing is selected, because the context object is read when the menu opens. A link span keeps its own `webviewSection`. *Measured in a real window:* VS Code merges the keys, and the item appears on text, on a paragraph and on the transcript background (e2e scenario 38).

**How `Alt+Q` was checked** (decision 1). Reading and searching only; no window was started, and the review confirmed the bundle search independently:

- *This extension.* `package.json` contributes no `alt+q`: the keys with Alt are `ctrl+alt+q` (Go to Session, `:1515`), `ctrl+alt+n`, `ctrl+alt+r`, `alt+r` (`:1561`) and `alt+shift+k` (`:1602`). Nothing in `src/webview` handles an `Alt`+letter chord: every `altKey` use is `Alt+Enter`, `Alt+ArrowUp/Down`, `Alt+click` or a modifier guard (`Composer.tsx:1233,1278,1297`, `AskDialog.tsx:239`, `ChatFooter.tsx:149,154`, `Rewind.tsx:45`, `settings/common.tsx:134`), type-to-focus ignores Alt chords (`type-to-focus.ts:43`), and the composer's undo handler requires Ctrl or Meta (`draft-surface.ts:525`). In Terminal mode the page forwards only `Ctrl|Meta`+`Alt` chords to the workbench (`terminal-keys.ts:66-69`), so `Alt+Q` reaches the PTY there, and the command's `when` is Chat-only anyway.
- *VS Code's defaults, installed 1.142.* The workbench registers default keybindings as numbers (`KeyMod.Alt` 512 plus `KeyCode.KeyQ` 47 = **559**). Searching `workbench.desktop.main.js` for `primary|win|mac|linux|secondary` followed by `559` finds nothing. The same search finds `primary:568` twice (512 + `KeyZ` 56, Alt+Z, Toggle Word Wrap), which shows the method sees such registrations. A search for the string `alt+q`, in every built-in extension's `package.json` and in all files under `out/`, finds nothing. Webview focus adds no keys: the webview forwards unhandled keydowns to the workbench keybinding service (`did-keydown` in `out/vs/workbench/contrib/webview/browser/pre/index.html`, Platform facts of the [composer design](2026-10-15-composer-contenteditable-surface.md)).

### 2. Insertion: always at the end of the draft

No caret snapping and no retained-caret logic (decision 6). `placeQuote(text, quoteMarkdown)` (pure, `src/webview/lib/quote-draft.ts`) returns the one edit `{from: text.length, to: text.length, insert}` and the selection `{anchor: end, focus: end}` where `end` is the new length.

A quote is the string `Q + "\n"`, where `Q` is the quote's lines each prefixed `> ` (a bare `>` for an empty line): the quote lines and **one line break** (decision 8). After a quote the caret is on the new line that follows, so the comment is written directly under the quote. `insert = prefix + Q + "\n"`, with `prefix` decided by the end of the draft:

| The draft | `prefix` | Result (`·` marks the caret) |
| --- | --- | --- |
| empty (`""`) | `""` | `> q\n·` |
| ends with text, no line break (`foo`, also `foo  `) | `"\n\n"` | `foo\n\n> q\n·` |
| ends with a whitespace-only last line (`foo\n  `) | `"\n\n"` | `foo\n  \n\n> q\n·`: the spaces are kept, so one more blank line appears |
| ends with one line break (`foo\n`) | `"\n"` | `foo\n\n> q\n·` |
| ends with two or more line breaks (`foo\n\n`, also a draft that is only `\n\n`) | `""` | `foo\n\n> q\n·`: the quote starts on the empty last line |
| ends with a quote and its line break (`> a\n`, the caret on the empty line under it): two quotes in a row | `"\n"` | `> a\n\n> q\n·`: **a blank line separates the two quotes**, so they stay two runs with two ✕ buttons (one line break only would join them into one run); the blank line is the empty line the caret was on plus the one the prefix adds |
| ends with a quote, no line break (`> a`) | `"\n\n"` | `> a\n\n> q\n·` |
| ends inside an unclosed fenced block (`` ```ts\nfoo `` or `` ```ts\nfoo\n ``) | `"\n"` (only when the draft does not end with `\n`) + the closing fence of the block's own length + `"\n\n"` | `` ```ts\nfoo\n```\n\n> q\n· `` in both cases: a quote never lands inside code |

The separator between two quotes follows from the one rule below (the number of line breaks at the end of the draft); a comment written between two quotes (`> a\ncomment\n`) is separated from the next quote by the same blank line (`> a\ncomment\n\n> q\n·`).

Rules:

1. `prefix` depends only on the number `n` of `\n` at the very end of the draft: `""` for an empty draft, otherwise `"\n".repeat(max(0, 2 - n))`; the unclosed-fence row is the only other case, and it reuses the closing-fence supply of `newlineEdit` (`code-fence.ts:89-103`). Existing blank lines are never removed. The closing fence is as long as the opening one, which both grammars close (Section 5 aligns the transcript to the composer's length rule). The blank line before a quote is what splits two quote runs and sets the quote off from the text above it; the line after it is only the one line break.
2. The edit is applied with `surface.apply(edit, "replace")`: one undo step, caret at the end (`draft-surface.ts:361-376`), the surface scrolls the caret into view. Then `surface.focus()`; its retained selection is the end, so nothing guesses a caret.
3. **A held draft capture refuses the quote; it is never deferred.** While the hand-off holds the draft (`captureRef` set, `captureLocked`, `Composer.tsx:948-975`) the quote is refused with a visible notice ("Your draft is being moved to a new editor; quote again in a moment"). A deferral, as Add Selection to Session uses, runs only in the same editor on `release`; when the capture ends in a replacement the waiting work never runs and the quote would be lost silently. An open IME composition does defer: `deferredRef` is flushed at the settle in the same editor (`Composer.tsx:1020`), and a capture cannot start inside a composition (`read` refuses first).
4. When the field is not mounted (the ask dialog replaces it, `Composer.tsx:1447`) or the session cannot take a prompt, the quote is refused with a notice, not held: the user is looking at the transcript and would be surprised by text arriving later.
5. A draft whose length plus the insertion would exceed `MAX_CHAT_TEXT_LENGTH` (`chat-messages.ts:81`) refuses the quote with a notice (the page does not enforce that bound on send today; the host parser rejects the message, `chat-messages.ts:1261`).

### 3. Captured format: the source Markdown of exactly the selection

Decision 2: source Markdown, mapped from the DOM, never `innerText`. The page keeps the *parse that produced the DOM*:

- `Markdown` takes a `quotable` prop, set only by the three kinds of decision 4 (assistant text and thinking blocks in `ContentBlock`, the user case in `NativeMessage`; child transcripts inside agent rows render the same views and are quotable, tool output and notices are not). A quotable instance registers, after commit (a layout effect), its parse in a page-local `WeakMap<HTMLElement, RegisteredMarkdown>` keyed by its `div.omp-md` root: the exact `text` it rendered (the revealed prefix for a paced reply, so the map is consistent with the DOM by construction) and per-leaf records. No source text is written into the DOM.
- The renderer stamps every **leaf block element** it already creates (`p` or the tight-list `span`, headings, list items, table rows, the quote's block children, the code block's wrapper, the `hr`) with `data-md-leaf="n"`, and the registry holds, for leaf *n*, its **source line range and, for each of its source lines, the number of leading characters the parse stripped before the leaf's own text** (the `\s*>\s?` of a quote, which varies per line, the list marker and dedent of an item, `Markdown.tsx:43,196-208,262-267`). Lines alone are not enough for an exact slice inside a quoted or listed line, since the column where the text starts differs per line. Top-level blocks have `MarkdownParse.starts` (`Markdown.tsx:299-304`) plus the next start; list items, table rows and quote children need the line index and prefix lengths that `parseList`, the table branch and the quote branch already know (`Markdown.tsx:232-293,383-395,405-437`) threaded in as a base offset next to `keyPrefix`, instead of discarded when the dedented body is re-parsed (`Markdown.tsx:280,291-293`). Inside a quote, nested line *j* is source line `quoteStart + j` (each quoted line strips only its own prefix), so the line base is trivial there. Streaming reuse of earlier blocks is unaffected: a reused block's records do not change when the text only appends (`Markdown.tsx:313-329`).
- `quote-capture.ts` (new; its pure parts testable without a DOM) takes a `Range` and:
  1. Refuses a collapsed or whitespace-only range, a range with an endpoint outside the transcript region, a range touching an editable field, and a range that touches no registered `div.omp-md`.
  2. Walks the registered `div.omp-md` the range crosses in document order. Everything else the range crosses (tool rows, `pre` output, notices, buttons, `.omp-sr-only` text) contributes nothing.
  3. For a `div.omp-md`, clips the range to each leaf block and slices the **source lines** of the leaf, taking the first and last leaf by text offset and the leaves between them whole, using the recorded prefix lengths to turn a text offset into a column of the source line. Within a leaf the rendered-to-source offset map comes from the same inline tokenizer the renderer uses (`INLINE_TOKEN`, `Markdown.tsx:33-34`): **a token (emphasis, code span, link, autolink) is carried as source only when the selection covers its whole visible text; a token the selection cuts contributes its selected visible text unchanged**. A list item or heading keeps its marker only when the selection starts at the item's visible start; a table is cut to what the selection touches (the cell's own text for a selection inside one cell; otherwise the header, the separator and the touched rows, narrowed to the touched columns; whole rows when the selection starts or ends outside the table: *Amendment: table selections*, 2026-10-17, which replaces the earlier "header, separator and the touched rows"); a `<br>` is a newline. A leaf inside a quote is sliced from the original source lines, `>` prefixes included, so it re-enters the draft as a nested quote.
  4. A code block is sliced by the text of its `code` element, which equals the source exactly (`CodeBlock.tsx:17-23`): the selected lines, re-fenced with the original info string (`code[data-language]`) and a fence of `max(3, L + 1)` backticks, where `L` is the longest backtick run at the start of any line of the slice **counted after that line's leading whitespace** (both grammars accept a fence line with leading blanks, `code-fence.ts:29-30`, `Markdown.tsx:351`, so an indented run of backticks closes a fence and has to be counted). Once Section 5.2 aligns the length rule, a fence of `L + 1` is closed by its own synthetic closing line and by nothing inside the slice. The closing fence is synthetic when the block is only partly selected. A drawn mermaid diagram contributes nothing; its Source view is a code block.
  5. Joins the slices of distinct surfaces with an empty line, then prefixes: `> ` before each non-empty line, a bare `>` for an empty one (no trailing space). Source that already contains `>` lines becomes `> > …`.
  6. **Neutralises image markers:** `[Image #N…]` is rewritten `[image #N…]`. The marker grammar and the transcript's `INLINE_TOKEN` are case-sensitive (`image-references.ts:23`, `Markdown.tsx:34`), so a quoted marker neither pairs with an image attached to the new draft (the Nth marker is the Nth image on the wire) nor renders in the sent message as a button that points at the wrong image.
- **Degradation, never failure.** If a surface is not registered, a leaf has no record, or the offset map disagrees with the DOM text of its leaf (the visible text of the mapped slice, rendered through the same tokenizer, is compared with the Range's own text; a wrong column therefore falls back instead of producing a wrong quote), that surface falls back to its *rendered* text from the Range, wrapped as plain quote lines. The user still gets a quote and the status line says "Quoted as plain text", so the loss is not silent.
- **Limit (decision 7).** The captured Markdown, before prefixing, is refused over 20 000 characters (the bound that decides which prompts the history keeps, `extension.ts:5787`), with the size in the message: "That selection is 31 482 characters; Quote takes at most 20 000." Truncating would put an invented ellipsis into the model's context. The limit is one named constant.

### 4. The composer: an editable quote band

A quote is plain text in the draft, shown as a band on its lines, exactly as a fenced block is. No change to ADR-0077: the band is a property of each line (surface design, section 1), and the model, the offsets, the IME window, the undo stack, the freeze, the hand-off, copy and paste are untouched.

**What is a quote line.** A line outside every top-level fenced block that matches `^ {0,3}>` (CommonMark's indentation, as `code-fence.ts:4-7` says of fences; the transcript's own `QUOTE` is looser, `^\s*>`, so a line indented four or more spaces and starting with `>` shows no band but still renders as a quote after the send: harmless and noted). A **quote run** is consecutive quote lines; a blank line ends it, which is where both the transcript renderer and CommonMark end a quote. A top-level fence takes precedence, and a quote line can never open one (`OPENING` demands the fence at the line start, `code-fence.ts:29`), so `findFencedBlocks`, `blockContaining` and every fence key rule are unchanged. A line the user types as `> hello` is a quote line too, and gets the band: the band shows how the line will read in the transcript and to the model.

**Nested fences.** Inside a run, the content after each line's prefix is scanned with the same `OPENING`/`CLOSING` grammar; those lines also get the code treatment (`omp-line--code` font, no separate band), so a quoted code block is monospace inside the quote band. A nested fence is not an editing zone: no code keys inside it, `Enter` just continues the prefix even on an empty line (a blank line in code is code, so the exit by an empty line is off there), and `Shift+Tab` is the way out.

**Rendering.** A pure `findQuoteRuns(text, fenced)` (new `src/webview/lib/quote-lines.ts`) yields the runs and the per-line flags. `lineSpecs` (`draft-dom.ts:36-57`) gains `quote` (and `quoteCode`, the nested fence lines); `buildLine` adds `omp-line--quote` (`draft-dom.ts:74-92`); `lineKey` includes both (`draft-dom.ts:59-61`) and `LineRenderer`'s in-place text update requires them unchanged, as it does for `code` and `fence` (`draft-dom.ts:356-357`), so typing `>` at a line start rebuilds just that line and nothing else. CSS next to `styles.ts:704-712`: the left bar and muted colour of the transcript blockquote (`styles.ts:424-430`: 3 px bar from the foreground at 28 %, `--omp-muted` text, `--vscode-contrastBorder` in High Contrast), a faint tint over the surface width by the negative-margin trick of the code band, and a `forced-colors` rule like `styles.ts:711`. The `> ` stays **visible as ordinary text** in the muted colour, as the fence lines stay visible in the code band (`styles.ts:707`). Meaning is not colour alone: the `>` characters are there.

**Keys.** Pure `quote-edits.ts` returns `TextEdit`s that the composer applies through `applyBlockEdit`, like `code-fence.ts`. They run in `onPromptKeyDown` only when no composition is active and no capture is held, before the send rule:

- **The prefix of a quote line** is its leading run `^ {0,3}>(?:[ \t]?>)*[ \t]?`: up to three blanks, one `>` per nesting level, each optionally followed by one blank, so `> a` has the prefix `> `, `  > a` has `  > `, `> > a` has `> > `, `>a` has `>`. The prefix is read from the line itself (nothing is stored). The rules below read **plain keys**: never with Ctrl or Meta (so `Ctrl+Enter` sends, and `Ctrl+Backspace`, `Ctrl+Delete` and `Shift+Delete` (cut) keep their native meaning), with Shift only for `Shift+Enter` and `Shift+Tab`, with Alt only for `Alt+Enter`.
- **The keys follow the code block's** (decision 2026-10-16; the maintainer: "there is no hotkey to leave a quote; it needs keys like the code block"). This replaces the first revision's "`Enter` sends, as on every prose line" with `Shift+Enter` as the line break: in a quote `Enter` is a line break and `Ctrl+Enter` sends, exactly as in a fenced block.
- **`Enter`, `Shift+Enter` and `Alt+Enter` on a quote line** are a line break and never a send. With the selection start at or after the end of the prefix they replace the selection by `\n` plus that line's whole prefix, so a nested line `> > a|b` becomes `> > a` and `> > b` and the next line stays at the same depth. Shift and Alt are the same key as plain `Enter` (the choice for `Shift+Enter` was: the same as `Enter`, or a soft continuation; the same keeps the hint short and matches the block, where `Alt+Enter`, a follow-up send elsewhere, is also a newline and a follow-up is `Ctrl+Alt+Enter`). With the selection start strictly inside the prefix the key inserts a plain `\n` (the native line break, never a send): splitting a prefix leaves a line that is no longer in the quote, which is the user's choice there. **On an empty quote line** (only its prefix and blanks, the caret collapsed and after the prefix) `Enter` lets go of **one level** and keeps the caret on the line: `> |` becomes an empty line, `> > |` becomes `> |`. Two Enters leave a quote, as in common Markdown editors, and a nested quote leaves one level per Enter, like `Backspace`. This exit is off on a line of a fenced block nested in the quote, where a blank line is code: `Enter` keeps the prefix there and `Shift+Tab` is the way out.
- **`Ctrl+Enter` and `Meta+Enter` send** from a quote line by the ordinary send rule; they are not ours.
- **`Shift+Tab` leaves the quote**, the analogue of the block's "outdent, or leave when there is nothing to outdent", **one level per press**. On a line with text it inserts a new line **after the line** and puts the caret on it, so the text and the lines under it do not move: from `> a|b` the new line is empty and plain (the caret on it), from `> > a|b` it is `> `, one level out. On an empty quote line it removes one level of the line's own prefix in place (the same edit as `Enter` there, and also inside a nested fence). With a selection it acts on the line where the selection starts. With the selection start inside the prefix, or with another modifier, it is the browser's (the focus moves back), and plain `Tab` still moves the focus. Why one level and not "leave completely": from depth 3 the user who wants to continue the outer quote would have to retype two levels, and `Backspace` already removes one level at a time; why after the line and not at the caret: the key says "I am done with this quote", not "split here", which `Enter` does.
- **`Backspace`** with a collapsed caret directly after the prefix removes **one nesting level** in one step: `> > |` becomes `> |`, and `> |` becomes `|` (the prefix and its indentation go), instead of leaving a lone `>` that is still a quote line. **`Delete`** with a collapsed caret at the end of a quote line whose next line is a quote line removes the line break **and the next line's whole prefix**, so the two lines join as text.
- **Paste and drop** (decision 2026-10-16, after the report "pasting several lines after `>` adds only the first line to the quote"). Plain text with a line break pasted (or dropped, or inserted by a multi-character `insertText`: they share `DraftSurface.#insert`) at or after the end of a quote line's prefix **stays in the quote**: the first pasted line lands at the caret, and every later line gets **the whole prefix of the line the selection starts on** (`> > `, `  > `, `>`), so one paste is one `surface.apply` and one undo step. Pure `quotePasteEdit` in `quote-edits.ts` reads the prefix with the same grammar as the keys above. The edge cases:
  - **Line endings** CRLF and a lone CR are line breaks, as for every paste.
  - **A pasted line that already is a quote line** (it starts with the prefix grammar) is left as it is, and a pasted block whose *first* line is one, pasted with only the prefix before the caret, **replaces the line's own prefix**, so `> a` / `> b` pasted after `> ` gives `> a` and `> b`, not `> > a` and `> > b`. Why not always prefix: a quote the user copies from the draft or from a message and pastes into a quote is the usual case, and nesting every line of it one level deeper is never what the user meant (Backspace removes a level, but only one line at a time); a user who wants a nested quote types `> ` once. The price is that a pasted line that starts with `>` for another reason (a shell redirect in pasted code) stays at its own depth instead of getting the prefix; the user sees it and can add the prefix.
  - **An empty pasted line** becomes the bare prefix without its trailing blank, as the capture does (`>`, `> >`); the **last** pasted line, where the caret lands, keeps the full prefix, so a paste that ends with a line break leaves the caret on an ordinary empty quote line (`> |`), as `Enter` does.
  - **A fenced block nested in the quote** is quote lines: the paste keeps the prefix. A **top-level** fenced block is code, never a quote line, so a paste there is a plain paste.
  - **The caret in the prefix, or at column 0 before the `>`**: a normal paste (the prefix cannot be split without leaving a line that is not in the quote), as `Enter` does. A paste without a line break is always the plain insert, whatever the line.
  - **A selection that spans quote and non-quote lines** uses the prefix of the line **where the selection starts** (it replaces the rest, and the text after the selection joins the last pasted line, as typing over it would); a selection that starts outside a quote is a normal paste. The alternative, a normal paste whenever the selection leaves the quote, would make the result depend on where the selection ends, which the user does not see as clearly as where it starts.
  - **Drop** goes through the same `#insert`, at the offset under the pointer, so it follows the same rule.
- **Completions** are off while the caret is in a quote line, like in a block: `completionsEnabled` also requires no quote line at the caret (`Composer.tsx:416-418,448`), so no `/` or `@` popup opens over text the agent wrote. `Tab` outside a fenced block still moves the focus.
- **Hint.** The hint row under the composer that shows the code keys while the caret is in a block (`Composer.tsx:1531-1532,1567`) shows the quote keys while the caret is in a quote line, in the block's wording: "Quote · Ctrl+Enter: send · Enter: new line · Shift+Tab: leave the quote" (`Backspace` at the start of a line still removes a level but is not in the hint). It stays the field's `aria-describedby`.

**The ✕.** Each quote run has a **Remove quote** button that removes the whole quote as one undo step.

- It is a real `button` outside the field, in a sibling overlay container of the composer's input row (`position: absolute; inset: 0; pointer-events: none; overflow: hidden`), the button itself `pointer-events: auto`. **It never covers text or the scrollbar:** the band's CSS gives each quote line an inline-start gutter of the button's width (`padding-inline-start` on the line, which changes no model offset because it adds no text), the bar is at the gutter's left edge, and the button sits in the gutter beside the run's first visible line, so a click aimed at the text cannot hit it and wrapping inside a quote line shrinks by the gutter only. The field's markup is unchanged and nothing is written into it: the overlay only *reads* line rectangles through a small `surface.lineRect(index)` (the surface owns the line elements), so an IME composition is never disturbed. The overlay is recomputed from the draft text (`findQuoteRuns`, memoised like `blocks`, `Composer.tsx:417`) and rectangles are re-read after each edit, on the field's `scroll`, and on a `ResizeObserver` of the field. A run scrolled out of the field's visible area has no button.
- Its name is "Remove quote: «first words of the quote»", so several quotes are told apart. It is a **Tab stop** after the field, so a keyboard user reaches it without selecting text. A click must keep the field's focus and selection: the button calls `preventDefault()` in `onMouseDown`, as the suggestion list does (`Composer.tsx:1551`); `pointerdown` is not used because that the focus change can be stopped there was not verified. The owned-Chromium test measures `document.activeElement` and the selection after a click.
- A click removes the run `[start, end)` plus the one line break right after it (the break the Quote action added; none when the run ends the draft), as one `surface.apply({from: start, to: end + k, insert: ""}, "replace")` with `k` of 0 or 1, and puts the caret at `start`; one `Ctrl+Z` brings it back. The blank line the Quote action put *before* the quote is not removed: it is the user's own paragraph break as much as the quote's. While an IME composition is open the click is deferred (`deferredRef`), like the thumbnail ✕ (`Composer.tsx:677`); while a capture is held the button is disabled, like every other mutation.
- **After a removal the field has the focus, with the caret at `start`** (`surface.focus()` after the `apply`; fix of 2026-10-16, "`Ctrl+Z` does not undo the deletion of a quote"). The page's undo is the field's own `keydown` handler, so `Ctrl+Z` reaches it only while the field has the focus. A press on the button keeps the focus where it was (`preventDefault` on `mousedown`), which is the page body when the user had clicked elsewhere, and a keyboard activation leaves the focus on a button the removal then unmounts; either way the key went nowhere. Every other way a quote goes (selecting its lines and `Backspace` or `Delete`, `Backspace` taking prefix levels, the key rules above) happens in the field and was already one undo step each; the owned-Chromium test covers all of them, each followed by `Ctrl+Z`.
- Text that the user edited into the quote since it was inserted is part of the run and goes with it; a comment typed directly under the quote is **not** part of the run (it does not start with `>`); a quote the user has split by a blank line is two runs with two ✕ buttons.

### 5. The transcript

#### 5.1 Slice 0: fix the list-like-line parser hang (before or with everything else)

The cause is the mismatch of Current State 2. The fix has two parts, both in `parseBlockRange` (`Markdown.tsx:332-464`):

1. **The paragraph loop consumes its first line unconditionally.** It breaks only when `paragraph.length > 0` and the line opens another block, and it interrupts on `listItem(paragraphLine) !== null` (the one definition of a list item, `Markdown.tsx:212-223`) instead of `UNORDERED_ITEM` and `ORDERED_ITEM`; the two looser regexes (`Markdown.tsx:38-39`, used only at `:451-452`) are deleted. A line that is list-like but not a list item (`1234567890. x`, a no-break or ideographic space after the marker) is then paragraph text, which is what CommonMark does with more than nine digits and what no renderer should hang on.
2. **A progress invariant.** Every iteration of the outer loop consumes at least one line; an iteration that did not advance `index` consumes one line as paragraph text. It makes the parser total even for a rule that is wrong in some other way.

Regression tests (`src/webview/markdown.test.ts`, no browser): `parseMarkdown` of `"1234567890. x"`, `"\u00a0- x"`, `"-\u00a0x"`, `"*\u3000x"`, `"> 1234567890. x"` and `"- \u00a0x"` each returns promptly with exactly one block holding the original text; a bounded property over the 17 symbols `- * + > # | \` 1 0 . ) space tab NBSP U+3000 x`: every string of length up to four (about 88 000 small parses) plus a seeded sample of 2 000 strings of length up to twelve (a fixed seed in the test) and a short list of two-line combinations, asserting that the parse terminates with at most as many blocks as lines. Longer exhaustive lengths are deliberately not used: length six alone is 24 million parses. This slice has no dependency on the feature and can ship alone.

#### 5.2 Slice 1: the same fence length and info rules in the composer and the transcript

The composer follows CommonMark: open on a run of three or more backticks with an info string without backticks, close on a line of at least as many (`code-fence.ts:29-30,46`). The transcript opens on three backticks followed by one token and closes on exactly three (`Markdown.tsx:37,351`), so a reply that wraps a fence in a four-backtick fence (a common way to show a fence) renders broken today, and a quote or a draft that does the same renders broken after the send.

**Decision: align the transcript to the composer's length rule**, and keep the capture rule of Section 3 (`max(3, L + 1)` backticks). Why not only change the capture to write three backticks unless the content has a bare fence line: that would leave every four-backtick fence in assistant replies wrong, which is the same defect, and a quote's fences would depend on the renderer's quirk. The change, for **all messages** (`FENCE` at `Markdown.tsx:37`, its uses at `:266,:346,:447`, the closing test at `:351`):

- Open on `^\s*(`{3,})([^`]*)$`, the language being the first token of the info string; keep the transcript's leading-whitespace tolerance.
- Close on `^\s*(`{3,})\s*$` with a run **at least as long as the opening run**. An unclosed fence still runs to the end.

**Indentation stays different, on purpose.** The composer accepts at most three blanks before a fence (`code-fence.ts:29-30`), the transcript any amount of whitespace, because list-item bodies are re-parsed after a dedent that keeps the extra columns (`Markdown.tsx:197-208,265`); capping the transcript would break fences nested in lists. So the two grammars agree on run length and info string, not on indentation: a draft line of four or more blanks followed by backticks is prose in the composer (no band, and `placeQuote` does not see an unclosed block) and a fence in the transcript after the send. The capture never writes such a line (its fences start at the line start after `> `); a user can type one, and then the missing band already shows that the composer reads it as text. This is documented, not worked around.

What changes for existing text: a four-or-more-backtick fence now opens with its real info string and closes on its own length (a three-backtick line inside it is content); an info string with spaces (`` ```ts title=x ``) now opens a fence (language `ts`) instead of being a paragraph, as in the composer. Three-backtick fences are unchanged. Tests: `markdown.test.ts` (`code fences inside items survive` at `:125` and the `STREAMED` corpus at `:313-339` stay green; new cases: a four-backtick fence holding a three-backtick fence and a bare three-backtick line, an info string with a space, a closing run longer than the opening, an unclosed four-backtick fence streamed prefix by prefix).

#### 5.3 Slice 2: a quote's content is nested blocks (decision 5)

The quote branch of `parseBlockRange` (`Markdown.tsx:383-395`) collects the quoted lines as today (stopping at the first line that is not a quote line, so a comment directly below a quote is a separate paragraph) and, instead of `renderLines(quoted)`, renders `parseBlocks(quoted.join("\n"))`, the way list items re-parse their dedented bodies (`Markdown.tsx:280,291-293`). It applies to **every** message that goes through `Markdown`, including assistant replies, thinking, user messages, summaries and tool prose. `parseBlockRange` gains parameters for what the quote needs (today it has `tight` and `keyPrefix`): a `quoted` flag that makes a `mermaid` fence a plain `CodeBlock` (the fence branch builds a `MermaidBlock` unconditionally today, `Markdown.tsx:357-361`) and a `depth` that caps nesting; margin resets are CSS.

**This stop is a requirement, not a detail (decision 8).** The Quote action leaves the comment on the line directly under the quote, so the quote branch must keep ending at the first line that has no `>`: no lazy continuation is added, and a test pins that `> q\ncomment` renders a `<blockquote>` followed by a separate `<p>`, with and without a nested fence or list in the quote.

**Rendering that changes** (today → after):

| Quoted source | Today | After |
| --- | --- | --- |
| `> text` (one or several lines) | `<blockquote>` with inline content and `<br>` | `<blockquote><p>…</p></blockquote>`: the same inline content inside a paragraph |
| `>` or an empty quoted line between lines | an extra `<br>` | a paragraph break: two paragraphs |
| `> ```ts … > ``` ` | literal backticks and unformatted lines | a `CodeBlock` with highlighting and its Copy button |
| `> - a` / `> 1. a` | literal `- a` text | a list (`ul`/`ol`) |
| `> # h`, `> ---`, a table | literal | a heading, a rule, a table |
| `> > text` | literal `> text` inside the quote | a nested `<blockquote>` |
| `> ```mermaid` in an assistant reply | literal | a plain `CodeBlock`, not a drawn diagram |
| `> 1234567890. x` and other list-like lines | inline text | a paragraph (after Section 5.1; it would hang without it) |

Guards: nesting depth is capped at eight (deeper `>` stays literal text); a quote's blocks are parsed from its own lines only, so the streaming reuse of finished blocks (`Markdown.tsx:313-329`) is unchanged (the quote is still one top-level block with one `starts` entry); CSS resets the first and last child margin inside `.omp-md blockquote` so a one-paragraph quote keeps today's height (`.omp-md p` has `margin: 8px 0`, `styles.ts:348`); the High Contrast bar is unchanged (`styles.ts:430`).

**Tests that pin the existing behaviour and what each needs:**

No test renders a quote's DOM shape today; the table above becomes new tests (a quote with a fence, a list, a heading, a nested `>`, a bare `>`, a quote directly followed by a paragraph, depth cap, mermaid in a quote, a streamed prefix of a quote with a fence).

The draft string, trimmed, byte for byte as ADR-0077 states (`Composer.tsx:816-817`, `session.ts:939-944`). The comment follows its quote on the next line and a blank line precedes each quote after the first; a draft with two quotes and two comments is:

> The migration runs inside the lock and releases it on error.
>
> ```ts
> await withLock(path, () => migrate(db));
> ```
Why not release it after the commit? The retry path needs the lock.

````

Confirmed by reading, not by running: the quote reaches OMP as `message` unchanged (Current State 4), and the transcript shows the user's message through the same `Markdown` component, so after Section 5 it renders as a quote with a nested code block. `[INFERENCE]` what the model makes of a quote versus plain text is not something this design can verify.

Two OMP behaviours on a quote's content are inherited, not introduced, and documented rather than worked around: an `@token` in a quoted reply that names an existing file is expanded as a mention when the prompt is sent while idle (`2026-10-07-add-editor-context-to-session.md:30-32,79`); the TUI-only emoticon expansion is not reached by Chat. A draft that is only a quote is sendable (it is non-blank).

### 7. Accessibility and the keyboard path

- **Selecting without a mouse.** The per-message Quote buttons were the Tab-reachable path; with them gone (decision 1, 2026-10-16) the keyboard path is to select text and press `Alt+Q` (rebindable in the Keyboard Shortcuts editor, also from the palette). *Measured in the owned Chromium (`chat-ui.test.ts`):* `Shift+Arrow` extends a selection that already exists in the transcript, but a collapsed caret placed in transcript text is **not** extended by `Shift+Arrow`, because the transcript is not editable and caret browsing is off, so a selection cannot be started from the keyboard alone. **This is an accessibility gap**: a keyboard-only user cannot quote. The maintainer accepted it on 2026-10-16 and declined a keyboard-only alternative (a "Quote last reply" command on its own key). A screen reader's own selection commands, and `F7` caret browsing, are not measured here `[INFERENCE]`.
- **Feedback** is one visually hidden `role="status"` line (the pattern of the composer's suggestion count, composer design section 7) plus one visible line in the composer's hint row for a few seconds: "Quoted N lines into the draft", "Quoted as plain text", "Select text in the conversation first", "This session cannot take a message", "Your draft is being moved to a new editor; quote again in a moment", "That selection is N characters; Quote takes at most 20 000". Focus moves to the composer with the caret on the line after the quote, so a screen reader announces the field.
- **The band is text.** A screen reader reads every quote line as it will be sent, `>` included; there is nothing hidden or atomic to explore. The band is visible in High Contrast and forced colours (`styles.ts:430,711` precedents). The hint names the quote keys while the caret is in a quote line.
- **Removing a quote by keyboard:** Tab to the "Remove quote: …" button after the field and press `Enter` or `Space`, or select the lines and delete them; `Ctrl+Z` restores it. The ✕ is also a pointer affordance.

## Alternatives

1. **Rendered plain text (`Selection.toString()`) prefixed with `> `.** Smallest change, no renderer work. Rejected as the default: it drops code fences, link URLs, emphasis and list markers (Current State 2), so quoting a code snippet from a reply, the commonest case, produces text the model reads as prose. Kept as the per-surface fallback.
2. **Whole-block snapping** (quote every top-level source block the selection touches). Exact Markdown with no inline mapping. Rejected by the maintainer (decision 2): the selection is quoted exactly. It remains the floor if the inline mapping proves too fragile in a slice.
3. **A non-editable atomic quote block** (the maintainer's first answer to decision 3). Designed in the first revision of this document as a row element covering several lines, with a known-quote set, select-then-delete and an ADR-0077 amendment. The independent review rejected that shape (caret before a block sits on the root, which the surface forbids and which is unmeasured; about fifteen offset and render functions change and missing one corrupts the model on read-back; its rules hold only for cancelable input; the known-quote set is page state lost on hand-off and triggered by typed text; a screen reader cannot read inside it) and the maintainer chose the band. A per-line atom variant (each quote line an editable line holding one non-editable span, as chips) would keep one element per line and shrink the amendment, but it shares the page state, the edit-rule and screen-reader costs and was not prototyped.
4. **A hidden `> ` prefix on editable lines.** The prefix would be an atomic non-text element on each line; more edge cases than the visible prefix and a worse screen-reader story, for no gain.
5. **Recognising a quote band by anything but its text** (a registry of inserted quotes). Rejected: the band is a function of the string alone, so the hand-off, history recall, Rewind and Undo need no new state.
6. **Send-time normalisation** (insert the blank line CommonMark needs after a quote, trim trailing `>`). Rejected: ADR-0077 makes the sent string the stored string, byte for byte; the insertion decides the shape instead.
7. **Host-side capture** (a menu command receives the selection from the page over `omp:selection-request`). Rejected: that reply keeps one line of at most 200 characters (`selection-query.ts:9-47`), and a page-local action avoids a new reply message.
8. **A prompt-level attachment** (the quote as a structured context field). Rejected: OMP's `prompt` takes a string (`session.ts:939-944`) and the maintainer wants the quote visible in the draft.
9. **No floating button, command and menu only.** Chosen by the maintainer on 2026-10-16 (decision 1 changed); the first draft's "press Quote" and the per-message buttons are dropped.
10. **Deferring a quote behind a held capture** (the Add Selection to Session pattern). Rejected: it runs only in the same editor, so a quote would vanish when the capture ends in a replacement (Section 2, rule 3).

## Risks and Open Questions

- **Inline offset mapping is the highest-risk piece of capture.** The tokenizer and the renderer must not drift; the leaf-level consistency check with the plain-text fallback bounds the damage (a visible "Quoted as plain text", never a wrong quote), and a property test guards it, including partial selections inside a quoted list item.
- **Nested quote blocks change every message with `>` lines** (assistant replies too): paragraph margins, list rendering and code blocks inside quotes; the table in Section 5.3 lists them, and a look at real replies belongs in the smoke. The fence-grammar alignment (5.2) changes four-backtick fences and info strings with spaces in every message.
- **A quote is editable text.** Editing can trim it, split it or glue a comment to it; the visible `>` prefix, the key rules and the ✕ make the intended shape the easy one, nothing enforces it.
- **The comment is a lazy continuation for a CommonMark parser.** The Quote action leaves no blank line between the quote and the comment (decision 8): in CommonMark `> q\ncomment` is one quoted paragraph. The transcript renderer here ends the quote at the first non-`>` line, so the user sees what they meant; the model reads raw text in which every quoted line has `>` and the comment has none. Accepted by the maintainer; the cost is that a Markdown preview of the sent text elsewhere would show the comment inside the quote.
- **The ✕ overlay reads rectangles of a field it does not own.** It never writes into the field, but its positions go stale between an edit and the next measurement; it is recomputed after each edit, scroll and resize, and the owned-Chromium test drives all three.
- **Context-menu merging.** The behaviour of `data-vscode-context` keys on nested elements and of a right-click on a selection in the webview is read second-hand from the VS Code documentation, not measured; the end-to-end check proves it in a real window, and the menu item is the first thing dropped if it does not hold.
- **Selection survival across the streaming-to-saved row change** (`live:` ids, Current State 2) is inferred, not measured; the worst case is a vanished button.
- **`@` mentions in quoted text** are expanded by OMP on an idle send and cost an extra file read (inherited, documented, not mitigated).
- **Assistive technology** behaviour for the ✕ buttons and the status line is unverified and goes on the same manual list as the composer's. A selection cannot be started from the keyboard alone (Section 7).
- No question is open: the maintainer decided the one that remained (decision 8).

## Addendum (2026-10-16): quoting an editor selection (decision 9)

The maintainer asked: "the quote hotkey should work for files, not only the Chat; the quote then holds a link to the file and the start of the quote, plus the selected text." Main decided the shape the same day; the choices below are the implementer's within it. It changes none of decisions 1 to 8 for a Chat quote.

- **Command and key.** A second command, `ompDesk.quoteEditorSelection`, titled **Quote Selection to Session** (palette category "OMP Desk"), bound to `Alt+Q` when `editorTextFocus && editorHasSelection`, and a context-menu item in `editor/context` under the same `when`, group `9_omp@3`. It is a separate command rather than a second `when` of `ompDesk.quoteChatSelection` because the two do different things (the Chat command reads the page's own selection through `providePanelActions`; this one reads the active editor and asks which session) and a palette title "Quote Selection" would otherwise mean two things. The two keybindings cannot both match: a Chat webview is never `editorTextFocus`.
- **Target.** The target rule of **Add Selection to Session** (`pickSendTarget`): a QuickPick of the sessions of this window, most recently focused first and preselected, then a new session next to the file. Two differences, both because the payload is Markdown for the Chat composer: **terminal sessions are not offered**, and a new session is started as a Chat (`openTab` with a requested mode). With no Chat session and no folder the warning says so and nothing is started. The page receives `omp:insert-quote` and places the quote exactly as a Chat quote is placed (Section 2): at the end of the draft, one line break after it, the caret on the next line, the focus in the composer, one undo step, refused while the draft is held for a hand-off. A page that has not announced itself yet holds the quote until its composer mounts (`offerQuote`, as `omp:insert-text` is held).
- **Format.** The first line of a quote is the location as **inline code**: `path:line` for one line, `path:start-end` for a range. The path is written as the mention helpers write it (`mentionPath`: relative to the session's cwd when inside it, else absolute with forward slashes). It is **not** an `@` mention: an idle OMP expands a mention into the whole file, which would defeat a quote of three lines. The transcript draws a code span that is one path as a file link, so the sent message links to the file; *measured in a real window* (spec 41): after a send, the location `quote-sample.ts:2-3` in the user's quote is an `omp-file-link` with that target. The lines of the range are the lines the text is on: a selection that ends at column 0 of a line does not count that line, and the line break it leaves is dropped.
  - A **code file** puts the text in a fenced block: the info string is `languageForPath(fileName)`, else the editor's own language id when it is a language the composer knows, else none; the fence is `max(3, L + 1)` backticks (`fenceFor`, shared with the capture). Every line, fences included, is prefixed `> `.
  - A **Markdown or plain-text document** (the editor's language id `markdown` or `plaintext`, or a `.md` name) is quoted as plain quote lines with no fence, after an empty `>` line under the location so the location is not glued to the first paragraph.
  - A document with **no file path** (untitled, another scheme) is quoted without a location line.
  - Example, lines 42 to 50 of `src/app.ts`:

    ```
    > `src/app.ts:42-50`
    > ```ts
    > const x = 1;
    > ```
    ```
- **Several selections (multi-cursor).** Every non-empty selection is its own quote, in document order, without repeats, separated by a blank line so each keeps its own ✕; all are placed as one insertion, one undo step. At most 64 selections.
- **Limits and refusals.** The same 20 000 characters as a Chat quote, counted over the selected text of every selection (the constant and the sentence moved to `src/shared/quote-limit.ts` so the host and the page share them). The host refuses an over-long selection, a control character other than tab and line feed, a path a message cannot carry and too many selections **before** the session picker; the page checks the limit again. An empty selection answers "Select some text first."
- **Unsaved text.** The quote holds the text as it is in the editor now; the location is the saved file's. The status bar and the picker say so for a dirty document.
- **Protocol.** `omp:insert-quote { quotes: { location: string | null, fileName, languageId, text }[] }` (host to page), parsed with the bounds the host composes within (`MAX_EDITOR_QUOTES`, `MAX_QUOTE_LOCATION_LENGTH`, a total over 20 000 characters refused). The page, not the host, writes the Markdown (`editor-quote.ts`), because the quote band, the fence rules and the `> ` prefix are page code.
- **Tests.** `editor-context.test.ts` (ranges, relative versus absolute path, CRLF, the column-0 end, order and repeats, no-path document, size, control character, too many selections), `editor-quote.test.ts` (info string, fence length, Markdown without a fence, a backtick in the path), `messages.test.ts` (the boundary), `insert-text.test.ts` (held until a composer mounts, chat pages only), `quote-draft.test.ts` (several quotes in one placement), the Chromium test of `omp:insert-quote` in `chat-ui.test.ts`, `contributions.test.ts` (the key, its `when`, the menu entry) and the end-to-end scenario `41-editor-quote-selection.spec.ts`.
- **Known limit.** A 20 000-character quote is above the draft hand-off cap of 8192 characters today, so a view switch with such a draft loses it; [ADR-0050](../decisions/0050-retain-uncertain-input-and-confirm-exact-file-restart.md) is amended to raise the cap to the composer's send limit (attachments design, *Rollout* 8), which also removes this limit for Chat quotes.

## Amendment (2026-10-17): table selections

The maintainer selected the text of one cell of a table in a reply (the bold first-column cell of a row) and pressed `Alt+Q`; the quote held the header, the separator and the whole row with every cell. That was the rule of Section 3, step 3 and the edge-case table ("header, separator and the touched rows, so the quote is a valid table"), chosen for validity, and the maintainer does not want it. Main decided the rule below on 2026-10-17; it replaces that sentence and nothing else of Section 3. Everything not named here (tokens, quote prefixes, the plain-text fallback, the limit) is unchanged.

- **A selection inside one cell** quotes the selected text of that cell alone, by the rules of a paragraph: a token (emphasis, code span, link) the selection covers whole keeps its source, so a whole `**Всё — параметры**` stays bold source, and a token it cuts gives its selected shown text. No header, no separator, no pipes. A pipe the cell wrote as `\|` is a plain `|` here, because the cell now stands alone in a line of prose.
- **A selection across cells of one row, or across rows** keeps a valid table: the header, the separator and the touched rows, cut to the columns between the **start cell** (the first cell the selection has text in, in reading order) and the **end cell** (the last), `min(column)..max(column)` of the two. A selection from cell (r1, c1) to cell (r2, c2) is therefore the rectangle of rows r1..r2 and columns between c1 and c2, and a start cell to the right of the end cell gives the same columns. The two edge cells are cut to the selected text (the start cell from the selection point to its end, the end cell from its start to the selection point; whole when covered whole, so a token covered whole stays source); every other cell of the rectangle, and every separator cell (`:---:` alignment included), is carried as written. A cut cell is written back with `\` and `|` escaped, so the row still has the cells it had; an uncut cell keeps its own escapes. The header is cut to the same columns, and its own cell is cut like any edge cell when the selection starts or ends in it. A selection that touches two rows in one column is still a table (one column, two rows); only a selection with text in **one** cell is the single-cell rule.
- **A selection that starts before the table with text in front of it, or ends after it with text behind it** keeps today's whole-row behaviour for the rows inside, with every column. Decided so: the part outside the table names no cell, so "the cell at the edge of the range" has no meaning for it, and cutting only the table's columns while quoting whole paragraphs around it would leave a quote that reads as a different table from the one on screen. Whole rows are the same quote the user would get by selecting the table's rows themselves. A range that merely ends at the start of the next block (a triple click in a cell ends in the next cell or paragraph) does not reach outside: only text counts.
- **Where the cells come from.** A table row is still one leaf. The row element's children are its cells (the Nth `td`/`th` is column N, since the renderer draws every row with the header's column count), and the page asks the DOM which of them the Range has text in and how much of each (`quote-selection.ts`, the same measure as a paragraph; a cell the range only reaches the start of has no text in it and does not count). The pure half takes the cells of the row's source line from `splitTableCells` (`markdown-table.ts`, the function the renderer draws a row with, which now also returns each cell as written), so a cell's offsets cannot drift from what is drawn. A cell whose tokens do not render back to the text the selection covers degrades: a single cell to its shown text ("Quoted as plain text"), a narrowed table to the whole rows.
- **Tests.** `quote-capture.test.ts` (one cell, whole and cut tokens, a header cell, a quoted table, `\|`; two cells of a row; the rectangle across rows including a start cell right of the end cell; whole rows from outside; the property test over every range of every cell of three tables) and `chat-ui.test.ts` (the same in a real Chromium selection, including the triple-click overshoot into the next cell).

## Amendment (2026-10-18): quoting from a diff editor (decision 10)

**Status of this amendment: accepted** (2026-10-18), by the review recorded in *Architecture Review*, last entry. The rest of this document keeps its status.

The maintainer asked: "support quoting from the diff view, with the file and the lines." Before this change the host gave a location only to a `file:` document (`fsPath = scheme === "file" ? uri.fsPath : null`), so a side of a diff that is a Git version was quoted as bare text.

### What happened before, per case (VS Code 1.142, a hidden window)

Measured with the OMP Desk log (the `activeTextEditor` and `visibleTextEditors` URIs at the command) and the Chat draft, the Chat visible in the left group so that nothing is asked. Cases (a) and (b) were measured on the build before this change; (c) to (e) were read in the first run of the new build, where the document and its scheme are the same, so what the old code did follows from its one rule above (stated, not measured).

| Case | Alt+Q and the right-click menu | `activeTextEditor` | The quote before |
| --- | --- | --- | --- |
| (a) Source Control diff of a changed file (left `git:`, right `file:`) | **Fire on both sides**; the menu of each side has **Quote Selection to Session** and Add Selection to Session. | The side that has the focus: the left is `git:/…/diff-app.ts?{"path":…,"ref":"~"}`, the right `file:///…/diff-app.ts`; both are in `visibleTextEditors`. | Right: with `diff-repo/diff-app.ts:3-4`. **Left: the text and no location.** |
| (b) staged diff (HEAD against the index, both `git:`) | Fire on both sides. | Left `ref: "HEAD"`, right `ref: ""` (the index). | Both: text, **no location**. |
| (c) a commit's changes (the multi-file diff editor) | Fire on both sides of the embedded diff. | The focused embedded side, a `git:` URI whose `ref` is the full hash of the parent (left) or of the commit (right). | Both: text, no location. |
| (d) a diff shown inline | Fire for the added and unchanged lines (one editor). **Not for deleted lines**, see below. | The one modified editor. | As (a) and (b) for the lines the editor selects. |
| (e) two plain files (Compare Active File With) | Fire on both sides. | `file:` of that side's file. | Both sides with their own file's location. Nothing was missing. |

What the Git extension writes (read from its bundle in VS Code 1.142): a `git:` document is `{scheme: "git", path: <file>, query: JSON {"path": <absolute fsPath>, "ref": <ref>}}`. The ref is `HEAD`, a hash or a branch; `""` (the index); `~` (**the index when the file has index changes, else HEAD**, decided when the document is read); `~1`, `~2`, `~3` (the stages of a merge conflict, read as `:N`); or any other commit-ish. `git.viewCommit` opens `_workbench.openMultiDiffEditor` with a `git:` document per side whose ref is the full hash of the parent and of the commit.

VS Code switches a diff to the inline view by itself when its editor is narrow (`diffEditor.useInlineViewWhenSpaceIsLimited`); with the Chat in the left group and the file in the right one, a diff **usually is inline**, which is why case (d) matters most.

### Decision

The command quotes the active editor, and the side of a diff that has the focus is the `activeTextEditor`, so the key and the menu already reached every side the editor can select in. What changes is the location.

- **A `file:` side** is `path:42` or `path:42-50` of that document, as before: in a diff, the lines of the working file.
- **A `git:` side** is the same path (the query's `path`, relative to the session's folder when inside it, as for any file) and the lines of **that version's text**, then ` @ ` and the version: `src/app.ts:3-4 @ HEAD (3f2a9c1)`.

| Ref | Version written | How it is found |
| --- | --- | --- |
| `""` | `index` | nothing to ask |
| `~` | `index` when the file is among the repository's `state.indexChanges`, else as `HEAD` | the Git extension's own rule, asked through its API |
| `~1` `~2` `~3` (also `:1` `:2` `:3`) | `merge base (index :1)`, `ours (index :2)`, `theirs (index :3)` | nothing to ask |
| a hash of 7 to 64 hex digits | its first 7 digits, `3f2a9c1` | nothing to ask |
| `HEAD`, a branch, a tag, `HEAD~1`, `stash@{0}` | `HEAD (3f2a9c1)`, `main (3f2a9c1)` | `repository.getCommit(ref)` through the Git extension's API, **bounded to 3 s**; the name alone when it does not answer |
| anything else (a space, a backtick, over 100 characters), a `~` whose side cannot be told, no repository, a submodule's entry (`submoduleOf`) | **no location**: the text is quoted as before | a location that cannot say which version it is would mislead |

- **Why this shape.** `@ <version>` after the lines reads as "these lines, at that version", adds no line to the quote, keeps the `path:lines` prefix the agent already knows, and is actionable: `git show HEAD:src/app.ts` and `git show 3f2a9c1:src/app.ts` give the file the lines belong to, and `index` is `git show :src/app.ts`. The hash is the short form git prints; a symbolic ref is shown with the commit it named when the key was pressed, because `HEAD` moves. The staged side is `index` and not a hash, because the index has no commit.
- **Not a file link.** The page draws an inline-code span that is one path as a link that opens the file on disk at those lines, and for a Git version those are other lines. *Measured with the page's own detector:* `src/app.ts:42-50 @ HEAD (3f2a9c1)` still contains the file reference `src/app.ts:42-50`. A shared grammar (`src/shared/quote-location.ts`: `quoteLocationText`, `isRevisionLocation`) is used by the host to write the location and by the page (`Markdown.tsx` `codeSpan`): a whole code span of the form `…:N[-M] @ <version>` is plain code, wherever it came from.
- **Protocol.** `omp:insert-quote` keeps its shape: `location` is the finished string, and its bound grows by ` @ ` and `MAX_QUOTE_VERSION_LENGTH` (128). The page's Markdown writer is untouched; `fileName` is the base name of the path and `languageId` the document's, so a `git:` side is fenced with the file's language.
- **Other schemes** keep today's behaviour, text without a location. The only other scheme whose path is recoverable is `git`; notebook cells, `output:`, `untitled:` and virtual file systems are not guessed.
- **Where the code lives.** `src/wiring/quote-revision.ts` (no `vscode` import: the URI parse and the words for a version, with the Git lookups passed in), `src/wiring/quote-source.ts` (asks the Git extension) and `src/wiring/git-api.ts` (the Git extension's API and its activation, shared with `src/wiring/commit-links.ts`). `quoteEditorSelectionToSession` calls `quoteSourceOf`; the Git extension is asked only for a `git:` document.
- **A submodule's entry is not a version of a file.** The Git extension opens a submodule resource of Source Control as a `git:` document whose query also has `submoduleOf` and whose ref is `index` or `wt`; its text is a *diff* of the submodule (`diffIndexWithHEAD`, `diffWithHEAD`, read from the bundle of VS Code 1.142), not the file's text at a version. Such a document has no location (`parseGitDocumentUri` refuses a query with `submoduleOf`), as an unusual ref does.
- **`@` is not a mention here.** OMP reads `@path` (an `@` that starts a word and is followed by a path) as a mention of a file. In the location the `@` stands between spaces, and the grammar only ever writes that form (` @ `), so nothing in a location can be read as a mention. A different separator would have to keep that property.

### What does not work, and why

- **Deleted lines of an inline diff** (case d) are not editor text, so there is no editor selection and no key: `editorHasSelection` is false. Evidence (hidden window, asserted by the spec): a triple click on the deleted line gives a page selection with its text, and `Alt+Q` produces no quote and no picker. In the side-by-side view the same lines are selectable on the left, which is where to quote them. No workaround: a quote from the page's selection would be another command, and a deleted line's number is not in the DOM.
- **`git.viewCommit` itself could not be started in the hidden window**: a keybinding passes one argument, and a `command:` link in a Markdown preview was clicked and opened nothing. The multi-file diff editor was opened with `_workbench.openMultiDiffEditor`, the command `git.viewCommit` runs, with the `git:` documents it builds (full hashes of the parent and of the commit), from the Git extension's source. That is the same documents in the same editor, and not a proof of the `git.viewCommit` entry point.
- **A moved HEAD.** A symbolic ref is resolved when the key is pressed. A diff opened before a commit shows the old text until the Git extension refreshes it, and the location names the new commit meanwhile; a hash side (a commit's changes) cannot drift.

### Tests

`quote-revision.test.ts` (the URI parse including a submodule's entry; index, `~` both ways, merge stages, hashes, branches and tags with and without an answer, refusals), `editor-context.test.ts` (the location per version, every selection, the bounds), `quote-location.test.ts` (the grammar), `markdown.test.ts` (a revision location is plain code and the file's location still links), `messages.test.ts` (the boundary) and, in a hidden window, `43-diff-quote-selection.spec.ts`: key and menu on both sides of (a), (b), (c) and (e), the `~` side of a file that is staged and then changed again (`@ index`, the one lookup the Git extension's `state.indexChanges` answers), the inline view and its deleted-line limit (the key finds nothing to quote; the spec does not drive the context menu there), and the sent location as plain code.

## Amendment (2026-10-19): the hunk under the caret in a diff editor (decision 11)

**Status of this amendment: accepted** (2026-10-19), by the review recorded in *Architecture Review*, last entry. The rest of this document keeps its status.

The maintainer decided: in an inline diff, `Alt+Q` (and the editor menu entry) with no selection and the caret on a changed line quotes the whole hunk that line belongs to, as a `diff` block with the removed lines after `-`, the added lines after `+` and up to three unchanged lines each side; the location names both sides; it also works in a side-by-side diff on either side; with no change under the caret the caret-line reference stays. A selection keeps its behaviour (decisions 9 and 10). Decision 3 of [the chat keys design](2026-10-18-chat-keys-and-empty-state.md) (the caret-line reference) is the fall-back, not replaced.

### Decision

- **Trigger.** The command has no non-empty selection and the active editor is a side of a diff. The side's diff is found from the tab, not from the editor: the visible tab of **the editor's own group** (its `viewColumn`; the active group when VS Code gives none, as for an editor embedded in the multi-file diff editor) whose input is a `TabInputTextDiff`, or, for the multi-file diff editor of a commit, holds one in its `textDiffs` (the typings of VS Code 1.110 lack `TabInputTextMultiDiff`; the property is read structurally and the hidden-window scenario proves it on 1.142). Another group's diff is never looked at: a plain editor of the same file beside a diff is not a side of it (the scenario drives that). The other document is read with `openTextDocument`, which the diff editor has already loaded. In an inline diff the one editor is the modified side and the original document is found the same way.
- **No API for hunks.** `vscode.diff` is a command that opens an editor; no API returns what the editor drew. The repository had no line diff (searched for Myers, LCS and the like). `src/shared/line-diff.ts` computes the blocks from the two texts: common head and tail cut off, then Myers' O(ND) algorithm, the blocks being the maximal runs of changed lines (deletions and insertions together). Bounds: `MAX_DIFF_LINES` (20 000 lines of a side after the cut) and `MAX_EDIT_DISTANCE` (1 000 inserted plus deleted lines); beyond either there are no hunks and the command takes its caret-line reference. Line ends are normalised; the empty line after a final line break is not a line.
- **Which line.** The hunk is the block that has the caret's line among its changed lines **on the caret's side**: for a block that only deletes there is none on the modified side, so a caret there keeps the line reference (decision 3 of the chat keys design); the original side of a side-by-side diff has those lines. In an inline diff the removed lines are drawn in view zones and cannot hold the caret, so such a block cannot be quoted there; the guide says to use the side-by-side view.
- **The text.** A `diff` fence: the unchanged lines before (at most 3, never a line of the neighbouring block, fewer at the start of the file), `-` and the removed lines, `+` and the added lines, the unchanged lines after (at most 3). Context rows start with a space, as in `diff -u`. No `@@` header: the location names the lines. The quote is the ordinary `omp:insert-quote` message with `fileName: ""` and `languageId: "diff"`, so the page's writer, unchanged, fences it as `diff`; its size is the quote's own limit (20 000 characters, refused with the size).
- **The location.** Both sides on one line, as one code span, the modified side first: `src/app.ts:1-7 was src/app.ts:1-5 @ HEAD (3f2a9c1)`; each side is written by the rule of decision 10 (its own path relative to the session's folder, its own `@ version`: `index`, `HEAD (3f2a9c1)`, `3f2a9c1`, none for the file on disk), so a renamed file, a staged side and a commit's two hashes are all named. The ranges are the hunk's lines on each side, context included. A side with no path, or with no line in the hunk, is left out and the location is the other side's alone; with neither, the quote has no location. The grammar is `hunkLocationText` in `src/shared/quote-location.ts`; `" was "` has a space on both sides, so it is as little an `@` mention as `" @ "` is.
- **Not a link.** The page makes a code span that holds a file reference a link to the file on disk; a hunk location holds two, one of them of another version. `isHunkLocation` (same module, same grammar, bounded to 8 192 characters) joins `isRevisionLocation` in `Markdown.tsx` `codeSpan`: such a span is plain code. Measured with the page's own detector: `src/a.ts:9 was src/a.ts:3` linked the file twice before the rule.
- **Protocol.** The message keeps its shape. The bound of `location` is two sides and the separator (`MAX_QUOTE_LOCATION_LENGTH`); one side keeps the old bound (`MAX_QUOTE_SIDE_LOCATION_LENGTH`), which `quoteLocation` checks.
- **Unsaved edits.** The text is the documents' (what the user sees); the path of a `file:` side is the saved file's, as in decision 9.
- **Where the code lives.** `src/shared/line-diff.ts` (pure), `composeHunkQuote` in `src/wiring/editor-context.ts` (pure: the locations, the refusals), `src/wiring/quote-hunk.ts` (the tab input, the two documents, the caret), the `hunk` request kind of `quoteEditorSelectionToSession` in `src/extension.ts`.

### Not VS Code's hunks

The blocks are the minimal line edit script of the two texts. VS Code's diff editor uses another algorithm (an advanced one that also detects moved blocks), by default ignores whitespace at the ends of lines (`diffEditor.ignoreTrimWhitespace`) and may group neighbouring changes differently. So a hunk here can differ from what the editor draws: a change of only trailing whitespace is a hunk here and no change there, and two changes VS Code joins may be two hunks here. A file whose last line has no final line break is the same text here as one that has it, where the editor shows the missing break as a change; a caret on that line keeps the line reference. The quote says what these lines are (the text and the ranges are the documents'), not what the editor drew. There is no way to ask the editor, so this is a limit, not a choice.

### Tests

`line-diff.test.ts` (the blocks of 3 000 random small pairs against the longest common subsequence: valid and minimal; the bounds; the hunk text and its context at the ends and between blocks; the hunk under a line from either side; line ends), `quote-location.test.ts` (the hunk grammar), `editor-context.test.ts` (`composeHunkQuote`: both sides, a renamed file, a staged side, a side left out, the refusals and the bound), `markdown.test.ts` (a hunk location is plain code; failing without the rule) and, in a hidden window, `43-diff-quote-selection.spec.ts`: with nothing selected, `Alt+Q` on both sides of a Source Control diff of a changed file and of a staged file, of a commit's changes in the multi-file diff editor and of two plain files; the editor menu on both sides of the changed file's diff and on the modified side in the inline view; in the inline view the caret on the added line of a change that replaced one line by three gives the whole hunk, removed line included; and the caret-line reference when the caret is on an unchanged line, in both views. Not driven: a renamed file (only `composeHunkQuote` covers it), a side of a block that only removes lines, a pair beyond the bounds of the diff, and the menu in the staged, commit and plain-file diffs.

## Amendment (2026-10-20): the Markdown preview (decision 12)

All of this was measured on VS Code 1.142.0 in a hidden test window (`scripts/test-vscode.ps1`, driven over CDP).

### Getting the selection out of the preview

- The preview is the Markdown extension's webview. Its CSP is `connect-src ${cspSource}` only, so a `markdown.previewScripts` script cannot reach Desk's loopback servers, and the extension reads the preview's messages itself (`didClick`, `revealLine`, `openLink`, ...); hooking either would depend on that extension's internals, so neither is used.
- What is supported is what a user does: **Copy**. `vscode.commands.executeCommand("editor.action.clipboardCopyAction")` while the preview has the focus copies the webview's selection (the workbench copies from the focused webview). The host reads `vscode.env.clipboard`, then puts the previous **text** back (`src/wiring/preview-selection.ts`).
- A marker string is written to the clipboard before the copy: a clipboard that still holds the marker after 600 ms means the preview selected nothing (an empty selection), so an empty selection is told apart from a copy that left the old text.
- **Limit, documented rather than hidden:** only text is saved and restored. A clipboard that held an image or files (no text) is replaced by an empty string, and rich formats of a text copy (HTML, RTF) are lost. `vscode.env.clipboard` offers no more than text. The clipboard is touched only by the key press, for about the time a copy takes, and only for a preview.
- Measured: with `USER-CLIP-TEXT` on the clipboard, a selection in the preview quoted `quote. Second paragraph here.` and the clipboard still read `USER-CLIP-TEXT` afterwards; the same for an empty selection.

### Identifying the document

- The active tab of the active group is a `TabInputWebview` whose `viewType` is `mainThreadWebview-markdown.preview`; the context key `activeWebviewPanelId` is `markdown.preview` while it is focused. Both measured. A preview to the side and a locked preview are the same view type.
- The tab label is `[Preview] chat.md` (a locked preview: `Preview chat.md`; the words are localised), so only its ending, a space and the file's name, is relied on.
- The file is the one **open** Markdown document whose name ends the label; failing that, the one Markdown file of the **workspace** with that name (a locked preview of a closed document, measured with `README.md`). Two different files with that name (two `chat.md` open, or in the workspace) cannot be told apart, because the preview names no source path: the quote is then headed by the **name alone** (`chat.md`), never a guess. Measured with `docs/guide/chat.md` and `notes/chat.md` both open.

### Format and target

- The quote is the rendered text as quote lines, under the path as inline code, written by the quote's own path rule (relative to the target session's folder when inside it, else absolute): `> \`docs/guide/chat.md\``, `>`, `> quote. Second paragraph here.` Measured in the draft of a Chat.
- The target rule is the quote's (the visible Chat, else the picker, **New session** starts a Chat; no Chat and no folder: the existing warning).
- Nothing selected: the notice "Select some text in the preview first." and no picker, no quote (measured).

### Key

`Alt+Q` runs `ompDesk.quoteEditorSelection` under `activeWebviewPanelId == 'markdown.preview'`; no other `when` of the key widened. The command is always in the Command Palette and checks the active tab itself, so it also works from the palette while the preview is active. Tests: `src/wiring/preview-quote.test.ts` (label matching, location, refusals), the lifecycle harness (`extension-lifecycle.test.ts`: the copy command, the clipboard restored, the empty notice, no session, a foreign webview), `contributions.test.ts` (the binding).
