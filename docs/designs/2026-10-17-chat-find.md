# Find in Chat

Status: **accepted** after one independent architecture review (see Architecture Review); implemented in source, unreleased. The first installed-window check failed for the maintainer (Ctrl+F did nothing); see Amendment 2026-10-17 (real-window defect). Date: 2026-10-17. Requested by the maintainer: "Ctrl+F does not let me search the chat (nothing happens), and I thought we already did this."

Amends `2026-10-04-paseo-style-chat.md` (the "Browser find cannot search unmounted text: disclose this limit" line) and `2026-10-14-chat-tool-output.md` ("the browser's own find sees only the rows in the page").

## What existed

Nothing. No earlier design, backlog item or code searched the Chat. The two designs above only record that VS Code's find cannot see unmounted rows, and the paseo design rejected "always mount loaded rows for browser find". The panel is created without `enableFindWidget`, so VS Code binds no find key for it; the page's own key handling (type-to-focus ignores Ctrl chords, the composer handles only `Ctrl+Z`/`Ctrl+Y`) never took `Ctrl+F`, so the key did nothing.

## Decision

A page-owned find bar that searches the transcript model, not VS Code's find widget.

- The native widget searches mounted DOM only. The transcript is windowed and the Overview collapses tool groups, calls' output and thinking, so it would miss most of a long conversation; the earlier rejection of mounting every row for it still stands.
- `Ctrl+F` has two paths that end in the same `openFind`: the page's capture-phase `keydown` on `document` (works from the composer, in a view-only Chat and while the host restarts) and a contributed keybinding `ctrl+f` (`cmd+f` on macOS) for `ompDesk.findInChat` under the Chat-only `when` (see the amendment below; the first version had no keybinding). **Find in Chat** (`ompDesk.findInChat`) posts a `find-in-chat` panel action for the keybinding, the palette and the editor title menu.
- Searched: user message prose, assistant text and thinking, a tool call's title, target, intent and output text. Not searched: notices, summaries, custom messages, attached files' text, history before a `/clear`, rows not loaded (the bar says how many earlier messages), child agents' transcripts, and **the reply still being written**: it changes with every delta, so reading it per delta would cost a Markdown parse of the whole partial reply each time; it is searched once it is complete. The query is literal; `Alt+C` toggles case.
- The query is searched once typing pauses (150 ms); the field keeps the raw text meanwhile, `Enter` before the pause searches at once, and the status text follows the searched query, never a stale result under new text.
- The first match is the newest. `Enter`/`F3` next and `Shift+Enter`/`Shift+F3` previous wrap. `Esc` closes the bar from the field and from every button in it, and restores the focus. While focus is anywhere inside the open bar the page reports the `find` owner to `composer-overlay`, so the host's `Esc` stop-turn binding stays disarmed for that press and a running turn is never stopped by dismissing the bar. The previous and next buttons use `aria-disabled`, not `disabled`, so focus is never dropped to the page while they change state.
- A match is revealed by what the transcript already does for rewind and image anchors: pin the window (or set the page in paged history), open the overview run, the call and the thinking block (before the scroll, because the controller recaptures its anchor; the retry loop is capped by the same frame budget), then scroll the match line into view, never under the bar. Matches in mounted rows are painted with CSS Custom Highlights (repainting while output streams is throttled to one pass per 200 ms); a long tool output paints only the rows its card shows, and the match's row gets a marker. The shown-text cache is bounded by characters, and cleared when the bar closes.
- The input names the earlier-messages note with `aria-describedby` and carries `aria-keyshortcuts`.

## Amendment 2026-10-17 (real-window defect)

The maintainer's installed build (guest bundle identical to the tree of `6f2a43d`) did nothing on Ctrl+F. The Chromium tests had only ever sent `key: "f"`.

- **Measured in a hidden VS Code 1.142 window (e2e scenario `42-chat-find.spec.ts`, the real extension and webview):** Ctrl+F from the composer, from the transcript and with nothing focused all opened the bar; the webview host (`pre/index.html` `handleInnerKeydown`) calls `preventDefault` on find keys and forwards every key to the workbench *after* the page's own listeners, so the page's capture handler runs first, and `enableFindWidget` off leaves the workbench nothing to do with it. The palette command also worked. The same press with `key: "а"`, `code: "KeyF"`, `keyCode: 70` (what Chromium reports on a Russian layout; VS Code resolves keybindings from the physical key and still reads it as Ctrl+F) did **nothing**: the page tested `event.key.toLowerCase() === "f"`.
- **Cause:** the page handler matched the typed character, so it ignored the chord on a non-Latin layout. `Alt+C` (Match Case) had the same test. `[INFERENCE]` The maintainer's own layout at the time of the press was not observed; the measured failure is the only mechanism found that makes the page ignore a key the workbench forwards, and every other key of the Chat (Ctrl+N, Alt+Q, Ctrl+R, ...) is a contributed keybinding, which is the class of path known to work for them.
- **Fix:** (1) `isLetterKey` reads a Latin character as typed and any other script by the physical key (`KeyF`), used for Ctrl+F and Alt+C; (2) a contributed keybinding `ctrl+f`/`cmd+f` under `activeWebviewPanelId =~ /^omp[.]session/ && ompDesk.sessionMode == chat`, the one `when` of every Chat key, so VS Code resolves the key itself and the user can rebind or remove it; `contributions.test.ts` pins it as the only binding of the key.
- **Two arrivals, one press (decision):** the page handles the key first and VS Code forwards the same press to the keybinding, so `openFind` runs twice. The second run, and any Ctrl+F while the open bar's field already has the focus, changes nothing (it neither reselects nor seeds from a selection): the first design rejected a keybinding exactly because a second path would reselect the field under a typing reader. From anywhere else (the composer, the transcript, a bar button) Ctrl+F still moves the focus to the field and selects its text, as VS Code's own find does. The cost: Ctrl+F in the focused field does not select-all; `Ctrl+A` does.

## Limits

Output rows the card does not render (before **Show all**) are found and counted but only their row is marked. History not loaded is not searched; the global history search is a separate scope.

**Amendment: the current match's block stays open (maintainer decision after 0.4.7).** The first version opened a thinking block by script and left it closed after the row left and re-entered the mounted range, with only the row marker to show where the match was. Now the container of the **current** match (its thinking block, tool group or call output) is reopened whenever its row is back, from the same repaint that paints the highlight, unless the reader closed it by hand after the jump. A close is detected where it can only be the reader's: a `toggle` to closed on a thinking block of the current match's row (a click, `Esc` inside it, the thinking toggle), and a group or call key that was seen open and is not open now (only the find code opens those and nothing here closes them). That sets one flag for the match; it is cleared by the next jump to a match (`Enter`, `F3`, a new query) and a different match starts clear. Only the current match's own block is touched: the block of a thinking segment is picked by its position among the unit's thinking blocks, and the others are left as they are. The Chromium test jumps to a match in a collapsed thinking block and one in a collapsed call output, wheels the row out of the list and back (open), closes each by hand and does it again (still closed), then jumps again (open).

## Architecture Review

One independent review pass (`ChatFindReview`, a separate reviewer agent, 2026-10-17, of commit `bd9ee511`): **accept with changes**. It traced the model search through `MeasuredRows`, the window and page projections, source bindings, the overview projection, `NativeDisclosure` and the scroll controller's `reveal(sources, offset)` and found no wrong-result path. Findings and resolutions:

1. **Material: `Esc` was handled only by the field.** From a bar button `Esc` neither closed the bar nor kept the stop-turn key disarmed (`find` was reported only while the field had focus), so it could abort a running turn. Resolved: the handler is on the bar container (IME guard kept) and the owner is reported while focus is inside the bar; a Chromium test presses `Esc` on a focused bar button during a streaming turn.
2. **Material: the shown-text cache kept every prefix of a streaming reply and re-parsed the whole partial reply per delta.** Resolved: the streaming reply is not searched until complete (and its row carries no find id), the cache is bounded by characters and `clearFindCache` runs when the bar closes and on unmount; a unit test shows no prefix of a streaming reply is read.
3. **Material: every keystroke rescanned the conversation (`useDeferredValue` is not a debounce).** Resolved: a 150 ms settled-query state; the field keeps the raw value; `Enter` flushes.
4. **Material: the design had no status, review or map entry, and the amendment of the tool-output design was missing.** Resolved here, in `docs/README.md` and in `2026-10-14-chat-tool-output.md`.
5. Should-fix, all resolved: `aria-describedby` and `aria-keyshortcuts` on the field; the status text uses the searched query; mutation-driven repaints are throttled; the reveal offset is clamped below the bar; the disclosure retry loop has the frame cap. The thinking marker after a remount was first left as a limit, then resolved by the amendment above.
