# ADR-0011: Run the currently installed OMP without a runtime version gate

> Ownership clauses narrowed by [ADR-0039](0039-refuse-only-on-a-verified-live-writer-the-extension-owns.md): roomless/unknown ownership and retained unconfirmed claims no longer veto user actions or require release. Installed-runtime and capability integrity requirements remain. Earlier ownership amendments below are historical.

> Narrowly superseded by [ADR-0038](0038-host-chat-over-rpc-ui-on-a-broker-pipe-child.md): the "a roomless launch of ours is never declared absent" rule is replaced for rpc rows by broker/kernel identity evidence (legacy Collab-era rows keep it, except that an authenticated broker exit report counts), and the pinned pi-wire guest grammar goes away with Collab (`@oh-my-pi/pi-wire` remains for type-only `SessionEntry` use). This supersession takes effect only once ADR-0038 is accepted. The installed-OMP runtime policy, the absence of a version gate and invariants F1–F3 remain operative — F1 is met by binding `get_state` identity before any `set_model`.

> Superseded by [ADR-0018](0018-resume-imported-history-under-extension-claims.md): imported sessions now resume interactively under extension-scoped claims. The installed-OMP runtime policy, launcher/PID/guest compatibility rules and F1–F3 invariants below remain operative by reference. The read-only history rule and incident notes remain here as the original, historical rationale, not current behavior.
>
> Narrowed by [ADR-0033](0033-release-stale-ownership-of-an-unidentified-launch-explicitly.md), as narrowly amended by [ADR-0036](0036-release-an-unresolvable-launch-attempt-explicitly.md): an unresolvable recorded launch attempt — one that recorded no process id, no matched room, or a current `owner-unknown` reading — may have this extension's reservation released by an explicit user action, after a fresh best-effort target check, without that release establishing absence. The retained-unconfirmed-ownership rule and repair R1 below continue to govern every other case, including a launch whose writer is positively identified as live, a registered room, and a live broker-owned child.

## Context and Problem Statement

[ADR-0010](0010-use-verified-installed-omp-1830.md) proposed one exact OMP release — the installed 18.3.0 — as the only supported runtime. It was reviewed but never adopted, and the implementation briefly refused every launcher that reported a different version. On 2026-09-24 the user replaced that policy before adoption: the extension must not pin a numeric OMP release at all. It must run whichever `omp` the user currently has installed, be repaired when an incompatibility surfaces, and the user explicitly accepts the resulting update-regression risk — an OMP update may break the extension until it is fixed.

Two constraints from the earlier decisions survive and shape this one:

- **Process identity.** The process the extension starts must be the process whose PID OMP publishes in its local Collab registry, so the extension never launches a package-manager shim that spawns the real binary as a child, and it never infers identity from a stored PID. This is independent of any version question.
- **No runtime ownership.** The extension never installs, downloads, upgrades or bundles an agent, and never mutates the user's global package. That was already true under [ADR-0010](0010-use-verified-installed-omp-1830.md) and is unchanged here.

A third constraint is about evidence rather than policy. Its own independent review found that an equal `COLLAB_PROTO` number proves nothing about a guest's behavior ([ADR-0010](0010-use-verified-installed-omp-1830.md), finding F2), so a numeric gate was never a compatibility proof; it only converted an unverified combination into a refusal. Removing the gate neither raises nor lowers that evidence standard, but it does admit runtime/guest combinations the project has not verified, and that is the accepted compatibility risk of this decision. Runtime shape and capability checks stay mandatory wherever a usable signal exists; they are simply not a numeric release gate. Nothing here relaxes authentication, ownership, secret handling, permissions or approvals: this decision neither bypasses launcher and process-identity proof, the peer-verified host-control channel, single-writer session ownership or approval settlement, nor closes any open security gate of [ADR-0006](0006-host-generated-key-peer-verified-pipe.md).

## Considered Options

- **Run the currently installed `omp` with no numeric gate (chosen).** The user's current installation is authoritative; incompatibilities surface as errors and are repaired; the user accepts the regression risk.
- **Keep the exact-release gate of [ADR-0010](0010-use-verified-installed-omp-1830.md)**, i.e. refuse anything except 18.3.0. Replaced by the user's decision: it refuses the user's own updated runtime and makes every OMP release a source-plus-documentation change before the extension can start.
- **Accept a semver range or a known-good release matrix.** Still a numeric gate, so it still refuses an unlisted future release, and the project has no per-release compatibility evidence to populate a range with — the very gap finding F2 identified.
- **Feature-detect capabilities at runtime and refuse only what is provably missing.** Attractive in principle, but the contracts in play (wire grammar, Collab registry JSON, the in-process extension API) publish no capability declaration to probe. It remains a possible addition where a concrete signal exists; it is not the primary mechanism now.
- **Bundle or install a matching runtime.** Rejected as before: it duplicates the agent and contradicts the extension-only boundary.

## Decision Outcome

No numeric OMP runtime version is pinned, checked or refused. The extension launches the `omp` the user currently has installed, resolved through `PATH` and launched PID-safely: a direct executable is used as-is, and a recognised package-manager shim is resolved through to the runtime entry it forwards to, so the started process is the one OMP registers. The official launcher-directory file (`omp\omp.exe` under the user's local application data directory) is a fallback only when `PATH` offers no usable launcher: that file can be an older build, and a stale launcher must not win over the user's current installation. The extension still never installs, downloads, upgrades or bundles a runtime.

Two boundaries belong to this decision rather than to the version question. First, a successful `--version` and a PATH classification are **not** proof of process identity: an unrecognised wrapper that answers a version request and then spawns the real OMP as a child must not be treated as the registered process, the extension must not launch an unknown wrapper blindly, and it must not conclude that no writer exists merely because such a launched PID has exited. Unconfirmed writer ownership persists until a positive proof of absence. Second, launcher resolution belongs to a host, not to the extension-host process: a new native host re-resolves the user's current installation instead of reusing a launcher resolved earlier, while an already running host keeps its own executable for its CLI calls. A change to the external `PATH` environment may require a VS Code restart, and this decision does not promise automatic environment refresh.

Compatibility is reactive. When a native contract changes, the extension reports the failure rather than pretending success, and the project repairs it; the user explicitly accepted that an OMP update can break the extension in the meantime. Errors stay visible instead of being absorbed: a wire-protocol mismatch must surface (the host answers `hello` with a protocol-mismatch `error`, and that refusal must reach the user), and no code path silently negotiates or downgrades a contract.

The build keeps `@oh-my-pi/pi-wire` pinned at a fixed version, currently 18.3.0, but as a **reproducible protocol grammar for the compiled guest**, not as a runtime pin. That pin fixes what the shipped bundle is compiled against; it does not restrict which OMP the user may run. Its correct consequence is that when the installed host speaks a different protocol number, the mismatch is visible rather than masked.

Nothing in this decision asserts that an untested future release works. Documentation must speak of the release currently installed plus the evidence actually gathered, never of a supported-version matrix; a release that merely launched is not a verified release.

### Consequences

- Positive: the user's own installation is authoritative and an OMP update no longer requires a source or documentation change before the extension can be used.
- Positive: the guest bundle stays reproducible, and the failure of a stale bundle to match the host is reported instead of hidden behind a version string.
- Negative: an OMP release can break the extension until it is repaired. The user accepted this regression risk explicitly, and no compatibility matrix warns about it in advance.
- Negative: guarantees that the numeric gate insulated now rely entirely on their own mechanisms — launcher/PID identity, peer-verified host-control authentication, single-writer session ownership and fail-closed API checks must each stand without a version check in front of them.
- Constraint: no document may claim a release is supported because it starts, and no document may claim the reverse either. Verification evidence remains per-release and explicit. The installed-VSIX and actual VS Code Webview acceptance gates remain open regardless of this decision.

## Architecture Review

- Reviewer: architect, independent of the author (separate ADR-0011 review)
- Outcome: reviewed on 2026-09-24 with material findings F1–F3. F1, F2 and F3 are implemented in code with their invariants recorded below, and the revised choice the record turns on — the user's 2026-09-24 decision that an adopted history session is **always read-only** — was reviewed and approved with two required corrections, both repaired in source, after which the corrective re-review accepted the repaired text (both reviews are recorded below). The record is therefore **accepted** as a design decision: acceptance here is not runtime or security acceptance, and the installed-VSIX, Webview and remaining ownership gates stay open.
- Post-review incident (2026-09-24) — **this is why acceptance was deferred until the ownership rule was corrected**. The extension resumed an unmanaged session file taken from OMP's own history while an external, user-launched OMP process was live on that same file and published no Collab room; two writers then appended to one session file, and the extension-started writer had to be stopped by hand. An independent inspection of the installed 18.3.0 interactive-session code found no durable per-session live-owner signal to consult instead: installed OMP holds no lifetime lease on a session file — `--resume` loads the file without checking for another interactive process, ordinary appends take no lock that outlives the operation (its session storage does lock per operation and releases it when the operation finishes), and the only session-scoped lock is the short-lived publish lock (a stale gate file may remain without meaning anything) — so an external writer of the same file cannot be excluded. Extension claims coordinate only participants that honour them, which is why an adopted history session is shown read-only rather than resumed. The Collab registry is therefore not an incomplete fallback that could be completed — a native session hosted without Collab is simply invisible to it. F3's ownership rule (a matched room withdrawn together with the observed pid gone) has nothing to match against in exactly that case. The user resolved that question on 2026-09-24: an adopted (`unmanaged`) session is **always read-only**, so no confirmed-continue path is pursued and no durable ownership signal is needed to offer one. Nothing in this record may claim that read-only handling or any liveness probe proves that another writer is absent.
- Accepted limitation (user decision, 2026-09-24) — the foreign-roomless-writer case is **temporarily accepted, not solved**. What this record does guarantee is extension-scoped: the extension never starts two writers for one session; this extension's own windows exclude each other through the holder lease; an adopted (`unmanaged`) history row is never resumed, claimed or attached; and a roomless launch of ours is never declared absent, so it keeps its claim as a visible conflict. Explicitly out of scope: an external OMP process resuming a session file this extension created is not detectable by the extension — installed OMP publishes no durable per-session owner marker and such a launch publishes no Collab room — so the user takes responsibility for not running concurrent external copies of one session. No per-action confirmation, veto or external-process lease is added for this. The consequence is accepted explicitly rather than mitigated: absence is judged only from this extension's own recorded host — its matched room withdrawn and its observed process gone — so a foreign OMP process writing that file while publishing no room of its own stays invisible, and both a resume and `Delete Session` can collide with it, including a deletion that unlinks a file another process is actively writing.
- Notes: F1 (high) — **closed in code**. The reported defect was that a failure to read the session identity was conflated with a legitimately unmaterialised session, so a native API change could leave model/thinking mutation admissible without proof of the current session. The fix separates the two states: `HostControlFacts.sessionIdentityKnown` distinguishes a read that returned `null` (a genuinely unsaved session, still admissible) from an identity that could not be read, and `beginMutation` refuses with code `not-ready` before any request-id reservation or dispatch when identity is unknown. F2 (medium) — **closed in code**. The extension-host-lifetime launcher cache that pinned the first resolved path is gone: `resolveOmpBinary()` resolves on every call, so a replaced shim target or a newly earlier `PATH` entry is picked up at the next launch, while a running host keeps the command captured at its own launch for its later CLI calls. An external `PATH` change still requires a VS Code restart, and this record promises no automatic environment refresh. F3 (high) — **closed in code**, with a reconciliation half repaired after the independent revised-choice review: that review found reload reconciliation still answering `free` from a vanished pid alone (its finding R1), and the repair makes absence a single combined item — a recorded roomless launch stays owner-unknown however its pid ends, `reconcileOwner` answers `unknown` for it, and `absenceEvidenceForRecordedHost`/`acceptOwnerAbsenceEvidence` accept only an item that names both the previously matched room's withdrawal and the process exit. The earlier per-launch registry baseline and its `attemptLeftNoWriter` helper are deleted: a successfully read Collab registry with no room for the attempt no longer releases anything, because a child whose Collab start failed or was disabled publishes no room at all. A launch now returns `not-started` only when nothing was started at all (resolution, relay, overlay, session directory or terminal creation failed before a process could run); a launch whose process is live is `running`, with a missing matched room reported as a warning rather than a different state, and `unconfirmed` covers the case where a process may exist but its writer identity cannot be proven — so post-terminal failures can never return `not-started`, and `running` without a matched room establishes no writer identity and permits no later PID-only recovery — with the claim kept; a stop is `confirmed` only when the observed pid is gone **and** the room this extension matched to that host is withdrawn, so a host that never published a room keeps its claim as a visible conflict. The content scan is an admission rule rather than identity proof: it decides what may be started, and identity is the launched process's pid matching the room OMP publishes. It is memoized per file identity (path, size, mtime), so a replaced binary is re-scanned and no launcher choice is cached across launches. The corrective's owner reports non-canonical local evidence only — an isolated-file typecheck and a hermetic smoke suite exercising the admission, resolution and ownership paths — with no canonical runtime, VSIX or Webview verification; that smoke is not acceptance evidence for this record. The review's other points stand: the `--version`/PATH identity caveat, and the unproven support for Bun-specific `--define`/`--preload` arguments by arbitrary launchers. The reviewer ran no runtime, build or test checks.
- Revised-choice review (2026-09-24, independent of the author) — the reviewer approved the always-read-only policy and blocked acceptance on two corrections, both repaired in source since: **R1** (high) reload reconciliation still answered `free` from a vanished pid for a launch that had matched no room, so a roomless launcher's disappearance could permit a second launch — the repair keeps such a launch owner-unknown however its pid ends and makes absence a single combined item naming both the matched room's withdrawal and the process exit; **R2** (medium) ownership documentation invoked a native single-writer backstop that does not exist and an over-broad absence of locking — the backstop claim is dropped and the lock statement narrowed to the missing lifetime lease, because installed OMP does lock per operation. The reviewer also raised a non-blocking point that the read-only transcript is a bounded snapshot rather than a view that follows later writes, which the architecture now states. That review performed no runtime acceptance. **Corrective re-review** (same independent reviewer, 2026-09-24) returned **ACCEPT with no remaining material findings in the corrective scope**: R1 is closed by the combined `recorded-host-and-process-gone` evidence item whose proof requires both identities to match the recorded host, by reload reconciliation answering `unknown` for a roomless record, and by the shared predicate governing both restoration and deletion; R2 is closed by the narrowed ownership text in the session index and the claim module. The re-review also confirmed that unmanaged history still returns read-only before any claim, reconciliation or launch, that no unmanaged resume path was added, and it corrected one non-blocking wording issue in this record (the launch-status sentence) plus one source comment about snapshot freshness. Its verification was read-only inspection of source, documentation and tests: no runtime operation, build, test or formatter was run, and the roomless/reload runtime acceptance and the other security gates remain open.
- Recorded invariants (acceptance conditions): **F1** — model/thinking mutation is admissible only when the host can positively name the session it is serving; an unreadable identity reports `sessionIdentityKnown: false`, refuses `not-ready` before any reservation or dispatch, and surfaces `SESSION_IDENTITY_UNREADABLE` first in the snapshot's bounded read gaps, while a successfully read `null` stays admissible. **F2** — launcher resolution belongs to a host, not to the extension-host process: each launch re-resolves the user's current installation, a running host keeps its own executable, and a replaced binary is re-classified rather than served from a memoized choice. **F3** — a candidate is admitted only on its own content (OMP program markers plus an embedded JavaScript runtime; unknown executables, script launchers and non-bun package-manager shims are refused unstarted, and an absent launcher-directory file is simply absent); identity is the launched process's pid matching the room OMP publishes, never the file's name, path, content or reported version; and unconfirmed writer ownership persists until a positive proof of absence — a matched room withdrawn together with the observed pid gone, or a launch that strictly started nothing. A launch that recorded no matched room can never be declared absent however its pid ends, and the reconciler answers `unknown` for it rather than `free`. A consequence to keep visible: an OMP that dies before hosting now leaves its claim held as a conflict instead of releasing it.
