# ADR-0083: Take the Bun runtime of a bun shim launch only when its content is Bun

## Context and Problem Statement

A launch whose `OmpBinary.launcher` is `bun-shim` is `bun.exe <OMP entry> ...`: Desk spawns `bun.exe` itself and the process it observes must be the process OMP runs in. Host control checks that: the peer of the control pipe must be the launched pid (`pid-mismatch` in `src/host/control-client.ts`), and the broker records the same pid as the child ([ADR-0006](0006-host-generated-key-peer-verified-pipe.md), [ADR-0035](0035-distinguish-a-recorded-process-from-a-later-occupant-of-its-pid.md)).

The OMP shim file is classified by its content, but the `bun.exe` it runs on was taken **by name** (`bunRuntime` in `src/host/native-terminal.ts`): the `bun.exe` beside the shim, else the first on `PATH`, checked only for being a runnable file, with `bun` (no extension) accepted as a second name on Windows. A package manager can put a launcher of that name first: a shim `bun.exe` that hands its command line to the real Bun and waits for it. Desk would then start the launcher, OMP would run as a grandchild, the control pipe's server pid would not be the launched pid, and host control would fail the pid check with `pid-mismatch` on every launch, with no hint of the cause. The hole exists since 0.1.0; the review of [ADR-0075](0075-carry-bun-runtime-flags-by-launcher-kind-and-probe-before-using-an-environment-carrier.md) found it (finding R2) and deferred it to the maintainer backlog (2026-10-14). Scoop's and Chocolatey's shim folders are the backlog's examples; this change did not reproduce them with the real package managers (Scoop is not installed on the machine it was made on, and Chocolatey holds no Bun there), so the forwarding file is covered by a stand-in launcher (below).

The same principle already governs the OMP file itself: a file is OMP's program by what it contains (OMP's identity strings plus an embedded JavaScript engine), never by its name or by what `--version` prints, because a wrapper answers for the real program just as well. The Bun runtime was the one file in the launch not held to it.

Requirements: a clear refusal naming the launcher, or the correct use of the real Bun, instead of `pid-mismatch` on every launch; a cheap check, cached per file identity; in process where possible, since the project left PowerShell spawns ([ADR-0076](0076-call-win32-in-process-through-a-staged-koffi-module-instead-of-starting-powershell.md)) and the resolver reads a bun shim's release from its package manifest, so it starts no process for a shim except when that manifest gives no release (`bunShimRelease`; a start that a busy machine can delay past any limit).

## Considered Options

- **(a) Refuse a runtime found in a package manager's shim folder.** Decided by a folder name (`shims`, `chocolatey\bin`, ...). Cheap, but a guess: the same names hold real programs (`.bun` is Bun's own install folder, which the existing shim-location list for the OMP file must not apply to; mise's `shims` and Scoop's differ from `apps\...\current`), and an unknown manager's folder passes. It would be right for the cases it lists and silent for the rest.
- **(b) Drop the extensionless `bun` name on Windows.** Right as far as it goes (Bun's program file on Windows is `bun.exe`; a file with no extension is at best a script for another shell) but it does not touch a `bun.exe` that forwards. Taken, as a part.
- **(c) Run the candidate once and compare its `process.execPath` with the file** (the self-check of [ADR-0074](0074-run-chat-brokers-on-the-sessions-own-bun-runtime-with-code-exe-as-fallback.md)). The strongest proof, since the forwarder cannot answer for the real Bun without the answer naming the real Bun's path. But it would add one process start per candidate, before the entry is even known, to a path that starts none in the common case, brings the transient-timeout class of failures (a busy machine) into it, and needs its own cache and its own handling of a candidate that cannot run. ADR-0074 already does this for a Chat broker's runtime, after the fact.
- **(d) Judge the file by its content, in process: the file must carry Bun's JavaScript engine.** The rule that already tells OMP's compiled program from a launcher (`isOmpRuntimeProgram`), applied to the runtime: real Bun carries JavaScriptCore and Bun's own repository identity; a package manager's launcher is a small program holding a path. No process, one sequential read of the file, a verdict that is a property of those bytes and so cacheable by file identity.

## Decision Outcome

1. **A bun shim's runtime must be Bun itself, by content (d).** `bunRuntime` visits the `bun.exe` beside the shim, then every `PATH` entry in order, and takes the first that is a runnable file **and** carries one of the engine markers Desk already uses for the embedded runtime of OMP's program (`JavaScriptCore`, `oven-sh/bun`; `EMBEDDED_RUNTIME_MARKERS`). A runnable file that does not is skipped, not refused outright: the search goes on, so a forwarding launcher first on `PATH` never hides the real Bun behind it.
2. **The name list drops the extensionless `bun` on Windows (b)**, in the launch resolution and in `resolveBunRuntime` (the Bun that runs the helpers). `resolveBunRuntime` is otherwise unchanged: a helper's result is read through a pipe and does not depend on the pid, so a forwarding Bun still serves it; it is not held to the content rule.
3. **What the user sees.** With a real Bun behind a skipped launcher, the launch uses the real Bun and, once the launch candidate is accepted, the log gets one Info line per skipped file and window naming the launcher, the reason and the Bun used. With no real Bun anywhere, the OMP resolution is refused (`No usable OMP launcher was found. Tried: ...`, the existing refusal path of an unusable OMP) with the shim's line: `<omp shim> is a bun shim, but no bun runtime was found beside it in <dir> or on PATH: <launcher> is not Bun's own runtime (no JavaScript engine found in the file): a package manager's launcher that starts the real Bun as a second process, so the process Desk starts would not be the one that runs OMP. Put Bun's own bun.exe (installed with Bun's installer) on PATH.` The refusal is definitive (it records a reason and the search goes on to the next OMP candidate), as a missing runtime already was.
4. **Cost and cache.** The scan is one sequential read that stops at the first marker (the real Bun 1.4.0 of this machine, 89 MB, carries them from byte 65 million on: about 47 ms with the file in the system cache; a cold read was not measured separately). The verdict is kept per question and file identity (path, size, modification time) for the window, in the same map as the OMP-program verdict (`markerScans`), so a launch after the first reads nothing, a replaced file is read again, and a file that is busy or unreachable right now is a transient failure of the resolution, never a "not Bun" verdict (`rethrowIfTransientInspection`). The scan code is the OMP-program scan generalised to "one marker of every group", not a second copy.
5. **Chat brokers (ADR-0074) are unchanged.** `inspectBunLaunch` and the pipe-only check, with its `runtime-mismatch` comparison of `execPath`, stay as the second line for a broker's runtime; they now receive only a runtime the resolver already judged to be Bun's.

### Consequences

- Positive: the failure that every launch would show as `pid-mismatch` is a refusal that names the file, or is avoided by using the real Bun; no process is started and the cost is paid once per file; the OMP program and the Bun runtime are judged by one rule.
- Negative: a Bun build that stops carrying both markers (neither its engine name nor its repository identity) would be refused as "not Bun's own runtime" (with the file named and the rule stated, but with no override in settings); the OMP-program rule has the same exposure and has held since [ADR-0011](0011-use-installed-omp-without-version-gate.md)'s resolver. A forwarding launcher that itself embeds a JavaScript engine (a `bun build --compile` program that spawns the real Bun) would pass; none is known and ADR-0074's `execPath` comparison still catches it for a Chat broker. The first resolution after a window start reads about 65 MB of a real `bun.exe`.
- Not covered: a Terminal (native) session on a forwarder that passes the content rule is not detected before launch and ends as `pid-mismatch` as before; the control-pipe check remains the final guard.
- Evidence: unit tests in `src/host/native-terminal.test.ts` (a forwarding `bun.exe` is skipped and the real one behind it is used with one log line; a lone forwarder refuses with the reason; a Bun that carries the engine strings passes; a verdict is answered from memory for an unchanged identity and re-read for a changed one; the extensionless name is ignored on Windows). A smoke run with a stand-in forwarding executable (a copy of a small Windows system program named `bun.exe`) and this machine's real Bun 1.4.0 through the real resolution path: the forwarder was skipped and the real `bun.exe` used (49 ms the first resolution, 1 ms the second, file cached by the system), and with the forwarder alone the refusal above was produced. Not run: a real Scoop or Chocolatey shim, and a full session start behind one.

## Architecture Review

- Reviewer: reviewer agent (independent, one pass, run after the implementation and tests were in place)
- Outcome: accepted with changes; no material finding, the decision stands
- Notes: three should-fix items applied: the claim that a shim resolution starts no process is scoped to the common path (a package that gives no release is still asked with `--version`, so option (c) would add one start per candidate); the marker exposure is stated as one of two markers, not both; the Info line about a passed-over launcher is written only once the launch candidate is accepted (`resolveBunShim`), with a test. Three nits applied: the skip wording says the engine was not found in the file (a file that could not be read also lands there), the beside-the-shim test now places the Bun beside the shim (and a forwarder beside the shim is tested), and the cost figures are stated once with their cache condition. The reviewer also confirmed by search that no other place takes `bun.exe` by name for a launch: the remaining name lookups feed helpers that are read through a pipe.
