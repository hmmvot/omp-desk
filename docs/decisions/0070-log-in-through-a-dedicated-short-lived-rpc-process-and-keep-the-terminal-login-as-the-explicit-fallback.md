# ADR-0070: Log in to a provider through a dedicated short-lived `omp --mode rpc` process, and keep the terminal login as the explicit fallback

## Context and Problem Statement

**Log In to Provider** opens a visible `omp login` terminal and reads nothing back; there is no log out. VS Code should show the provider list, open the browser, read a pasted authorization code through a masked box and show progress with Cancel. OMP 18.10.3 exposes this over RPC (`get_login_providers`, `login`, `get_logout_accounts`, `logout`; `extension_ui_request` frames `open_url`, `notify`, `input`). The lasting choices: **which OMP process** serves the flow, how **Cancel** really ends it, how the **secret** is kept out of every owned surface (ADR-0017), and what the GUI does with the 60 of 83 providers that take an API key. See [the design](../designs/2026-10-13-gui-provider-login.md) for the evidence table.

Facts (OMP 18.10.3 sources and real runs): `login` is not in `BACKGROUND_COMMANDS`, so it occupies the session's serial command queue until it ends (up to 300 to 600 s); the RPC handler passes no abort signal to the login, so an RPC client cannot cancel it other than by ending the process; a pasted-code prompt answered empty is asked again; `omp --mode rpc` without a model exits at startup, with `--model <selector>` it runs without credentials; killing the resolved `bun.exe <entry>` process ends it (verified: no login process remained after a cancel; the desktop `omp.exe` shim is never spawned, the executable resolver returns the `bun.exe` and entry). OMP's end-of-input teardown (`rpc-mode.ts`) disposes its session and MCP connections, but while a login runs it waits for the login to finish (up to the 300 s callback timeout), so end of input does not end a login in progress.

## Considered Options

| Option | Verdict |
|---|---|
| **Dedicated short-lived `omp --mode rpc --no-session --no-ui … --model <selector>` per login or logout, over stdio pipes** | chosen |
| Use the active Chat's own RPC session | the login occupies that session's command queue for minutes (a Chat prompt, `get_state` or Stop would wait behind it); its `input` frame would surface as a Chat dialog; Cancel cannot end it without killing the Chat |
| A broker-owned `managed-rpc` child | adds a broker kind, a lease, an authentication route and a Sessions row for a process that lives seconds to minutes and owns nothing durable |
| A staged Bun worker over OMP's own auth modules (the ADR-0061/0071 pattern) | would give a real abort signal, an explicit pasted-code channel and API-key kinds read from the registry, but writes the credential store through private, unversioned modules (ADR-0011) |
| Keep the terminal flow and only improve its wording | the user still copies and pastes through a terminal; no log out |
| Classify API-key providers up front from OMP (hide them from the list) | the RPC does not say which providers take a key; a copied list would rot with every OMP release |
| Ask for API keys in the masked box too | the user decided keys are entered in terminal OMP; the box would also be asked for OMP's non-secret-flagged prompts of unknown meaning |

## Decision Outcome

1. **Process.** One `omp --mode rpc` per login or logout, spawned with the session's (or the palette's) executable, cwd and `OMP_PROFILE` (the helper the terminal login already used), flags `--no-session --no-ui --no-skills --no-rules --no-lsp --no-tools --no-title --model <gpt|claude|gemini>` (the next selector is tried only when the process ended before `ready`), extension discovery on (as `omp login`). An idle process (the flow settled, failed or was dismissed with no command in flight) is ended the way OMP expects: stdin is closed, OMP disposes its session and MCP connections and exits, and a process still running after 5 s is killed. A login that is waiting on the user or the browser has no abort in OMP, so Cancel, a dismissed masked box and window disposal kill it at once (so does Cancel while OMP is still starting or listing providers). The window guard is released after the process has exited. **Extensions and MCP servers are not switched off**: `--no-tools` only empties the tool list and OMP 18.10.3 has no switch for MCP, so the process starts the MCP servers the profile and the folder configure (`mcp.enableProjectConfig` defaults to on). OMP 18.10.3 has no flag, environment variable or setting override to skip MCP in RPC mode (checked: `cli/args.ts`, `sdk.ts` `enableMCP`, `mcp/loader.ts`), so Desk owns the cleanup: a kill is a **process-tree kill** (`runTaskkillTree`, Windows `taskkill /T /F`, the helper Kill already uses) issued before the plain kill, and stdin is not closed first, so an OMP that exits on end of input cannot leave before its tree is found. Observed with real OMP 18.10.3 and a scratch folder whose `.mcp.json` starts a trivial stdio MCP server that also spawns a detached grandchild: after a plain kill the detached grandchild survived; after Cancel during a login and after dispose, no OMP, MCP server or grandchild remained. (A plain kill alone already ends the direct MCP child: libuv and Bun put children in a kill-on-close job; the tree kill adds the descendants that detached.) **Residual**: the idle, graceful end relies on OMP's own MCP shutdown exactly as a normal `omp` exit does; a descendant an MCP server detached on purpose survives that path (observed: the detached grandchild survived a graceful close), as it does after any `omp` run. The process carries no prompt, session file or registry row.
2. **Cancel.** Cancel on the progress notification, a dismissed masked box and window disposal kill the process and resolve *cancelled* with no failure notice. A dismissed box cannot be answered with an empty string (OMP asks again until its 300 s timeout) and OMP has no abort, so ending the process is the only real cancel. The masked box closes itself when OMP reports it is exchanging the code (the browser callback won), so an Esc cannot kill a login that is completing.
3. **Browser.** The `open_url` `url` (validated as an http or https web link; anything else ends the login with a fixed sentence) is opened with `env.openExternal`; `launchUrl` is ignored (a loopback shortcut for terminals). When the browser cannot be opened the notice offers Copy Link.
4. **Secret.** A pasted authorization code or redirect URL is read by an `InputBox` with `password: true` and exists only as that result and the line written to the child's stdin. Logs and diagnostics receive fixed sentences, ids matching OMP's id grammar, the **origin** of the sign-in address and outcome names; they never receive a frame, OMP's error text, instructions, prompt text or account labels. Errors from OMP are classified (`refused`, `unknown-provider`, `failed`, `closed`) and never forwarded; stderr is drained and discarded. **What is shown on screen**: text OMP sends for the user to act on, bounded and with control characters replaced (the masked box's prompt and placeholder, `notify` progress lines, `instructions` such as a device code, which must be visible); and, for log out, the account label and detail OMP reports (they include an organisation name) in the modal and, with brackets replaced, in the final notice.
5. **API-key providers.** The GUI never asks for a key. A provider is recognised **when it asks**: any `input` prompt other than a pasted authorization code or redirect URL ends the login before anything is typed, with one fixed notice ("API-key providers: run `omp` in a terminal and use /login") and an **Open Terminal Login** action; so do the six providers OMP's RPC refuses ("not supported in RPC mode"). OMP sends the sign-in address first and a key prompt in the same tick, so the address is held for a 400 ms settle window (or until a pasted-code prompt) and a key provider's dashboard page is not opened for nothing. The picker lists every provider OMP marks `available` and ends with an **Other providers** item that opens the terminal login.
6. **Terminal login stays**, only as an explicit fallback (`Other providers`, the refusal and failure actions, a start failure); closing it still re-reads the models.
7. **Guard.** One window-local reservation (`providerAuthRun`) covers a login or logout from before its preflight until its process has exited; a second request is answered, not queued, and the outcome notices (decline, refusal, failure) are shown without the flow waiting for them, so a notice that hides itself never holds the guard or the OMP process; a request is also answered while a fallback login terminal of this window is open (a terminal and a GUI login of the same provider would compete for the same fixed callback ports). Window disposal aborts the flow. Chat's model picker, its footer and the bridge `provider-login` request start the flow and are answered at once, so a minutes-long sign-in never holds the Chat's model and thinking controls.
8. **Refresh.** OMP stores a credential before it refreshes the provider online, and removes one before its online refresh. So every login or logout that sent its command re-reads this window's model catalogues (default profile and every session) whatever its outcome, except a refusal, an unknown provider or an API-key decline, where nothing was stored; a closed login terminal still does the same. Other windows are not notified.
9. **Caller-supplied scope.** `ompDesk.loginProvider` resolves with the outcome (`signed-in`, `cancelled`, `terminal`, `declined`, `failed`, `busy`) and accepts an optional `{ providerId?, profile? }`: a profile the extension already knows (the default, or one of its indexed sessions') and a provider OMP lists as available. The directory is never taken from the caller, and any other profile or field is ignored, so another extension cannot start OMP in a directory of its choosing.
10. **Log out** is new (`ompDesk.logoutProvider`, palette and Sessions overflow menu): authenticated provider, stored account, modal confirmation, `logout`. A provider whose key comes from the environment or configuration explains where to remove it.

### Consequences

- Positive: no terminal copy and paste for the ten providers that use a browser sign-in, a real Cancel, a masked paste, a visible progress, log out from VS Code, no new broker kind or protocol message, no change to Chat's RPC session.
- Negative: 2 to 4 s startup measured on an empty scratch profile, longer with extensions or MCP servers (progress shown); a second `omp` process, with the MCP servers of the profile and folder, for the duration of the flow; a graceful end leaves a descendant an MCP server detached on purpose running (disclosed above; upstream could add a `--no-mcp` flag or a login abort); a provider's "signed in" mark also covers a key read from the environment or configuration, which log out then explains it cannot remove; two windows signing in to a provider with a fixed callback port at once fail the second one with the generic sentence; the sign-in address is opened from `url` strictly (Chat's own link opener uses `launchUrl ?? url`, the loopback shortcut meant for a clipped terminal); 60 of 83 listed providers are only recognised as API-key providers after picking them and send the user to the terminal; other windows learn of a new credential at their next availability read; the authorization-code prompt is recognised by OMP's wording and the 400 ms window rests on OMP 18.10.3's frame order, both failing safe into the terminal path; if no `gpt`/`claude`/`gemini` selector resolves, the flow cannot start (the terminal action is offered).
