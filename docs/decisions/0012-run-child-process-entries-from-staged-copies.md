# ADR-0012: Run Child-Process Entries From Content-Addressed Copies Outside the Install Folder

## Context and Problem Statement

Three packaged files are executed from inside the installed extension folder:

- `out/relay.js`, spawned detached by `src/relay/manager.ts` as the loopback Collab relay sidecar;
- `out/omp-host-control.mjs`, loaded into each native OMP TUI process through Bun `--preload` and `omp -e` ([ADR-0005](0005-preload-control-key-before-omp-startup.md), [ADR-0006](0006-host-generated-key-peer-verified-pipe.md));
- `out/verified-pipe.ps1`, run by the extension host per host-control connection.

Two observed defects follow from that placement. First, `code --install-extension <vsix> --force` cannot rename the extension folder while any process still references a file inside it, so reinstall fails with EPERM and tells the user to restart VS Code — restarting is exactly what the detached relay and the live native host are designed to survive. Second, a relay that outlives the extension host keeps running the code it was started from: after an update a window adopts the previous version's relay, because the rendezvous record identifies an endpoint, not a build.

Requirements: no long-lived child process may reference the installed extension folder; an updated extension must never adopt the previous build's relay, while a relay that a live OMP host is already using must not be killed; the installed OMP surface stays untouched; and the ADR-0006 property that the host-control module is not secret but not writable by other users must hold for wherever it runs from instead.

## Considered Options

- **Keep running from the install folder and tell the user to restart**: rejected. It preserves both defects, and the extension's own design deliberately keeps sessions alive across a reload.
- **Copy the entries to the system temporary directory**: rejected. `%TEMP%` is frequently shared, its ACLs are outside the extension's control, and a stale copy there has no owner to reclaim it.
- **Identify the relay by the extension's package version instead of its bytes**: rejected. A version string is metadata that can disagree with the code it labels, and it cannot distinguish two builds of one version (a development window and an installed one) that share global storage.
- **Reclaim copies of other digests when a delete succeeds**: rejected. A window that has not reloaded may still be starting a host from its own copy, an already running process may still read one, and a *successful* delete of some files says nothing about the rest of the tree; there is no proof of "unused" available to this process, so nothing is removed (outcome 6).
- **Content-addressed copies under extension global storage, with the digest as the relay's version identity**: selected. The copy path is derived from the file's own bytes, the write is atomic and hash-verified, the copy lives in the extension's own per-user directory whose access is verified, and the same digest answers "is this relay my build's?" without any extra protocol field to keep in sync.

## Decision Outcome

1. `src/runtime-assets.ts` stages each packaged entry at `<globalStorage>/runtime/<sha256>/<name>`: read the source bytes, hash them, write to a temporary sibling name, replace the whole path in one step, then read the copy back and re-hash it before it is handed out. An existing copy with the right bytes is reused; anything else at that path is replaced. A new copy is created with a hard link first, so a second staging of the same digest that races this one is an ordinary "already there" answer rather than a lost update — the replacement is the fallback for a path that holds different bytes or a filesystem that cannot hard-link. Nothing is removed first: another window may already have handed that path to a process, so the path must never be absent, and a path that cannot be replaced atomically is refused rather than deleted. `src/extension.ts` stages the three entries and passes the returned paths — never `context.asAbsolutePath(...)` — to the relay supervisor, the native launch and the control client, and re-verifies every copy on every use: a copy that no longer holds the bytes its digest names is staged again from the packaged file rather than executed. The relay supervisor and the control client each re-read and re-hash the bytes immediately before the spawn they are about to perform, and the digest the sidecar is told it runs is the one just computed. That is a *fresh reading*, not an atomic verify-then-execute: the path stays writable by this account, and the protection against another account substituting code is the access verification of outcome 5, not the hash alone.
2. The digest is the relay's version identity, and it also names the state that version owns. The sidecar receives it as `--script-hash` (mandatory; `parseRelaySidecarArgs` refuses a missing or malformed digest), reports it on `/healthz` and writes it into its rendezvous record. The rendezvous file and the startup mutex are keyed by the digest (`relay-sidecar.<sha256>.json`, `relay-sidecar.<sha256>.lock`), so two builds never overwrite each other's endpoint. `ensureRelay(storageDir, { path, sha256 })` adopts an endpoint only when the record it reads belongs to that digest *and* the live `/healthz` answer names the same instance, pid, url and digest — on the reload fast path, while waiting for the startup mutex, and inside it.
3. A relay of another digest is never adopted, never stopped and never re-bound: it keeps serving the hosts already bound to it, and it keeps its own record, so a window that later goes back to that build finds its endpoint again instead of starting a second relay for it. This build starts its own relay on a fresh port and publishes its own record. A record written by a build that did not key its state is never read at all, which is what makes the very first update after this change start its own relay.
4. The same digest rule applies when this version's record names a relay that is gone: that endpoint is re-bound as before, so a live host still retrying the old URL lands on this build's relay. Only an endpoint belonging to *another* build is abandoned, because taking it over would serve that host a different build's code. A record that sits in this version's own state file but names another digest is not adopted either; this build publishes over it without touching whatever it pointed at.
5. Access follows [ADR-0006](0006-host-generated-key-peer-verified-pipe.md): the staged paths are public (they appear in the command line of the processes that load them), but the copies are code that runs as this user and no other account may write them. The tree is verified *through the shared private storage convention* (`src/host/private-storage.ts`): this module describes the tree as a layout — the runtime directory and the digest directories it owns and may rewrite (non-recursively, and only before any copy is written, so the copies inherit the limit), every copy as a verified file (a file's own entries decide whether its bytes can be replaced, and a parent's entries never stand in for them), and **every ancestor** of the storage directory up to but excluding the OS-managed volume root as carriers, verified but never rewritten — the walk matters because a component with write access to a directory on that path can replace the next one and so the tree, while an ancestor that is shared *read-only* (measured: the volume's `Users` directory grants foreign principals `RX` only) is accepted. That convention refuses on a path that is not plain (a symbolic link or reparse point anywhere), on an owner beyond this account, SYSTEM, Administrators and TrustedInstaller (with the `CREATOR OWNER`, `OWNER RIGHTS` and `SELF` placeholders resolved against the verified owner), and on a carrier entry whose rights could replace or re-permission that component — an entry that can merely create or write *inside* a shared ancestor is tolerated, which is exactly what lets a read-only system directory stand on the path; on the components this module owns, the rule is the strict one and any foreign write refuses. Its owner read asks the exact source first (`Get-Acl`) and falls back to the directory listing (`cmd /c dir /q`, pattern-narrowed) for the paths that cannot answer, and a path neither read can prove is reported unreadable and refused rather than guessed — so a missing or blocked tool refuses the stage instead of being treated as an answer. On POSIX the mode bits count only while no extended access control list exists, and the marker printed by the system's own listing decides that: every path the store is reached through (`root`, `directories`, `verifiedDirectories`, `probeDirectory`, existing `verifiedFiles`, and every component up to but excluding the volume root) is read with that listing, and only a plain mode or a trailing `.` — an LSM security context without an access list, per GNU coreutils — is proof. Any other marker refuses: "the store path `<path>` shows the access marker '`<marker>`', which can stand for an extended access control list, so the mode alone does not prove access is limited to this account" — that covers `+` when it means an ACL, `?` when the list could not be read, `@` when extended attributes are present (Apple's `ls` prints `@` *instead of* `+`, so an attribute can hide an ACL), and `%` for a dataless file, which hides both. A listing that cannot be read at all refuses with "the extended access list of `<path>` could not be read" (with the tool's detail appended when the listing command itself failed). This is deliberately conservative rather than mask-aware: a POSIX ACL whose named entries the mask bounds refuses too, so this document claims no platform where such a listing can exist and no ACL is read, and it makes no platform-wide claim at all. The availability cost is stated rather than hidden: on macOS a path carrying extended attributes — the normal state of anything a download, a browser, a Finder tag or an archive touched — refuses, and on Linux a path carrying an ACL, or one whose ACL information cannot be read, refuses. On success the convention records that no path the store is reached through shows an access marker that could stand for an extended access control list. Accepting `.` rests on that documented GNU semantics rather than on a check of the context itself, and the shared module's owner flags it as a residual choice: refusing `.` as well is a one-line change there, at the price of a SELinux host losing the feature. That rule is entirely the shared module's; this module reads no mode, no ACL and no owner, passes no platform gate of its own, and needs no seam beyond the layout it already describes. Nothing that cannot be shown to be owner-only is used, up to and including the relay and the host-control channel not starting on that machine. The volume root itself is the explicit **platform trust anchor**: the walk stops there, and this decision does not claim protection against a principal with control of it — such a principal can compromise the machine, not merely this store. A machine whose tree sits under an ancestor that another account can write therefore loses those features by design; the tests that stage with the real tools therefore live in this account's profile rather than under the shared temporary directory, which is exactly such an ancestor here. Scope: this protects against another *user* writing the staged code, which is what the assigned contract requires; arbitrary code running as this same user is outside ADR-0006's threat model and is not defended against.
6. Nothing here removes another build's copies. No process can prove that another window — which may still be starting a host from its own copy — or an already running process does not need one, and deleting part of a tree proves nothing about the rest, so copies accumulate, one small directory per build, until a cleanup exists that carries that proof.

## Consequences

- Positive: `code --install-extension <vsix> --force` no longer has to wait for the relay or a native session, and an updated extension never runs the previous build's relay code.
- Positive: the relay's version is derived from the bytes that are actually running — re-checked immediately before each spawn — so a development window and an installed extension sharing one global-storage directory cannot adopt each other's relays, and a relay that was already serving hosts is still found when that build comes back.
- Positive: the fix keeps the extension's reload-survival design intact — a live native host keeps its relay.
- Positive: the staged code's write protection is a verified property of the tree, not an assumption about where VS Code puts global storage.
- Negative: during a version transition two relays run at once (one per build), each with its own state files, and the superseded one keeps its port until it ends on its own idle policy.
- Negative: the ancestor rule costs availability by design. A tree under a directory another account can write refuses the stage, so the relay and the host-control channel do not start there — measured here for the shared temporary directory (the temporary directory carries another account's modify right), which is why the tests that stage with the real tools use this account's profile instead.
- Negative: copies accumulate. Each build leaves roughly the bundle's size under `<globalStorage>/runtime/`, and nothing in this decision reclaims it.
- Negative: the copies must be readable for as long as the processes started from them run, so reclamation could never be based on this process's view of "in use" alone — the reason (6) is a deliberate non-goal here rather than a solved problem.
- Negative: an updated window cannot re-attach to a relay serving a live host from another build, so a guest joining through the new window's relay does not reach a host still bound to the old one until that host is restarted. This is the accepted cost of never running the previous build's code.
- Negative: `startRelayServer` and the sidecar CLI now require the script digest, so any hand-started relay must pass `--script-hash`.

## Verification Gates

- Staging: a copy is created under the source's digest outside the install folder; an identical stage reuses it; a tampered copy is replaced by an atomic path replacement; a path that cannot be replaced atomically (a directory in its place) is refused and left as it is; three stagings of one digest that race as its *first* publication publish one copy with no temporary file left — the case that found a real race in this package, where two publications of the same digest collided on Windows and the replacement failed with `EPERM`; it is closed by creating the path with a hard link first and treating an occupied path as an ordinary outcome, re-verified by repeated runs; a changed build stages its own copy and the previous one stays; a copy whose bytes change after staging is reported as not verified; a copy whose own entry lets another account write it is refused; a directory the tree is reachable through that another account can write is refused and never rewritten; a copy owned by another account, a copy missing from its directory's owner listing and an unreadable owner listing are each refused; a runtime directory that is a reparse point is refused; the real `icacls` and owner reads run against this machine's filesystem and the copy reads back (`node --test src/runtime-assets.test.ts`).
- Relay version rules: a matching-digest record is adopted; every build keeps its own state file, so another build's start neither hides nor replaces this one's endpoint and a later call still finds the relay this build already serves; a record that names another digest is refused; a record written by a build that did not key its state is never read; a relay of another digest is never adopted (`node --test src/relay/server.test.ts`).
- Control helper: the process-generation probe runs the staged helper, and both an unconfigured helper and one whose bytes no longer match its digest are refused with `helper-unavailable` (`node --test src/host/control-client.test.ts`).
- Process-level probe, run once with a throwaway script against the built relay bundle: the old shape (relay started with its entry and its working directory inside a fake install folder) reproduced the reported failure — renaming that folder failed with `EPERM` while the relay ran and succeeded once the process ended; the new shape's detached child reports `…\runtime\<sha256>\relay.js --storage-dir … --port 0 --idle-ms 30000 --script-hash <sha256>` as its real command line (read from `Win32_Process`), which contains no reference to the install folder, and the install folder renamed while that relay kept answering `/healthz`; with the staged copy then substituted, the next call — which had to spawn, the relay having been stopped — refused with `invalid-state` and left nothing listening.
- POSIX and ACL-capable filesystems: the rule and its evidence are the shared convention's (`src/host/private-storage.ts`), and this package runs no POSIX case because the development host is Windows. The landed rule classifies the listing's marker rather than pattern-matching it: only a plain mode or GNU's context-only `.` is proof of "no access list", while `+`, `@`, `%`, `?` or an unrecognised marker, and a listing that cannot be read or parses to no mode line, refuse the store — so the refusal names the marker (`the store path … shows the access marker '…', which can stand for an extended access control list …`) and the success path records that no path the store is reached through shows such a marker. The reading is taken from vendor sources rather than inferred: Apple's `ls` prints `@` for extended attributes *instead of* `+` for an ACL (and `%` for a dataless file, which hides both), while GNU coreutils prints `.` only when an LSM context exists without an ACL, `+` for an ACL and `?` when the list could not be read. The availability cost is fail-closed and stated in outcome 5: on macOS a path carrying extended attributes refuses, which ordinary downloads, Finder tags and unpacked archives produce. That module's suite carries the evidence this document cites: the marker cases over synthetic listings, and a POSIX-host acceptance case that is skipped on Windows and reports on a POSIX runner. This document therefore makes no platform-wide claim — it states the property the shared rule proves.
- Real-window gate observed on Windows in a secure isolated VS Code 1.139.0 profile with installed OMP 18.3.0: a new GUI session launched a native host (PID 129820) preloading the module from `globalStorage/hmmvot.omp-desk/runtime/<digest>/`, with detached relay PID 153800 also executing from that staged tree. Neither child command line referenced the installed extension directory. `code.cmd --install-extension omp-desk-0.0.1.vsix --force` reported successful installation while both processes ran; afterward both original PIDs remained alive, `omp collab` still reported the same connected host, and the GUI plus native terminal displayed the ongoing session and `READY` reply. This establishes the live reinstall gate for that VSIX; it does not simulate an upgrade to a different digest or certify separate recorder acceptance.
