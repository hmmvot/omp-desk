# ADR-0006: Generate the Host-Control Key in OMP and Verify the Pipe Peer PID

## Context and Problem Statement

[ADR-0003](0003-native-host-control-pipe.md) requires a fresh, secret per-host authentication key that survives extension-host reload, excludes substituted pipe servers and never appears in VS Code's public terminal options, argv, logs, child environments or Webview traffic. [ADR-0005](0005-preload-control-key-before-omp-startup.md) rejects both terminal-environment and plaintext `Terminal.sendText` delivery: other extensions can read creation options, and VS Code logs sendText arguments before the PTY write. The native OMP TUI must remain its own Bun process and entrypoint, without OMP core edits. The original ADR-0003 wording also treated arbitrary same-user processes as untrusted; Windows SecretStorage uses user-scoped protection and cannot meet that stronger claim.

A host-generated key can be encrypted to a launch-pinned recipient public key, but a same-user process can replace the ciphertext rendezvous and serve a fake pipe. Encryption alone cannot authenticate the sender. Verification of the pipe server's **kernel process identity on the very connection carrying the HMAC exchange** supplies that missing binding.

### Local threat boundary selected by the user

The user explicitly chose to **trust arbitrary code running as the same Windows user** for credential confidentiality. A malicious program or installed extension executing arbitrary code under that account can potentially decrypt that user's Windows SecretStorage values; it is **outside** this boundary, as is a debugger reading OMP memory. This does **not** authorize keys in documented public terminal creation options, argv, terminal text or debug logs, nor remove the fake-pipe/replay/single-writer checks. Such surfaces expose credentials without arbitrary compromise and must stay clean. A substituted endpoint without the legitimate key remains refused; no claim is made against a malicious same-user process that has extracted the key.

## Considered Options

- Retry environment or raw terminal-input bootstrap: rejected by [ADR-0005](0005-preload-control-key-before-omp-startup.md).
- Encrypt a host-generated key to a parent public key and trust the metadata file, pipe name or OMP registry PID: rejected. A same-user process can replace those values, supply a key of its own choosing and satisfy a fake HMAC exchange.
- Probe the pipe process ID in a separate connection, then open a regular Node socket: rejected; endpoint replacement between those connections is a TOCTOU gap.
- Connect and proxy the **same named-pipe handle** through a bounded Windows PowerShell 5.1 helper that calls `GetNamedPipeServerProcessId` before forwarding bytes: selected for the Windows target. It requires no OMP core edit or packaged native binary. A missing/locked-down PowerShell or failed PID check refuses host controls; there is no unsafe fallback.

## Decision Outcome

1. The VS Code extension generates a per-run RSA-OAEP-SHA256 recipient keypair and owner nonce, recording the private key in extension-scoped SecretStorage **before** launching the terminal, scoped to the atomic session claim. Only the public SPKI key (base64url DER) appears in terminal arguments. Launch Bun directly as `bun --define '__OMP_VSCODE_RECIPIENT_PUBLIC_KEY:"<public-key>"' --preload <packaged-host-module> <verified-installed-OMP-dist/cli.js> ... -e <same-packaged-host-module>` (Windows shell argument array, no shell). The preload's module lexical state captures this Bun-transpiled literal once; the OMP `-e` loader consumes that same canonical module instance. Do **not** copy or subsequently reread the recipient from mutable `process.env`. Other extensions' environment-variable collections may change ambient values, but cannot replace this public key through that mechanism. The actual installed CLI remains `Bun.main` and the native TUI's process entry; no secret is present in `TerminalOptions.env`, argv or stdin.
2. The narrow OMP `-e` extension generates a **fresh random 256-bit control key inside the OMP process** when it loads. It starts the existing authenticated named-pipe service; its rendezvous contains the public pipe name, pinned recipient-key fingerprint, owner/slot binding and RSA-OAEP ciphertext of the key. Never publish the plaintext, private key, Collab bearer link or credential-bearing configuration. Ambient OMP child environments inherit no host-control secret. Missing/malformed public-key binding or a non-shared preload module leaves host controls unavailable, never an unencrypted fallback.
3. The extension treats the rendezvous as attacker-controlled. It checks its owner claim, exact live terminal association, public recipient fingerprint and recorded process generation, decrypting only a **candidate** key in its process. The packaged Windows PowerShell helper opens the pipe once, verifies `GetNamedPipeServerProcessId` on the **same connected handle**, checks the expected PID plus independently recorded OS process-creation time while retaining a process handle for connection lifetime, and only then forwards bounded frames over private stdio. The parent completes [ADR-0003](0003-native-host-control-pipe.md)'s nonce/HMAC handshake on that verified connection, checking instance/session bindings. Fake ciphertext or a swapped pipe cannot satisfy both the kernel identity and the HMAC. An ambiguous host generation, missing expected process handle or unexpected PID reuse refuses service rather than re-pinning.
4. Persist the key **only after** the genuine host proves it on that connection. On extension-host reload, use the already proven key and recorded host generation, revalidate the existing terminal and claim, and reconnect with a **new** peer-verified handle and HMAC nonce pair. Never accept a new candidate key from a changed rendezvous for an already proven owner. Delete the key/private recipient key only after confirmed native host termination. Before enabling mutation, also repair the existing bounded in-memory request ledger: terminal outcome eviction currently erases request-ID reservation. Keep old IDs non-replayable for the process lifetime; if a bounded capacity is exhausted, fail closed rather than dispatching an evicted ID again. Host-scoped snapshot/readback, generation checks and [ADR-0004](0004-best-effort-host-model-transitions.md)'s narrowly accepted native transition race remain.

The PowerShell helper uses `Add-Type` for the documented `kernel32.dll` pipe-server PID and process-creation-time queries; it disables profile and interactive startup, emits no frame contents to PowerShell's formatting pipeline or logs, and must enforce the protocol's byte/frame limits and timeouts. Its verified per-connection acknowledgment (not a separately checked file) releases the parent to send HMAC frames. The helper owns the same pipe and process handles until the channel ends; EOF or helper exit is an unknown mutation result, never an automatic retry. Enterprise restrictions that block `Add-Type` fail visibly and do not fall back to an unchecked `net.Socket`. Other platforms need their own same-connection peer-credential mechanism; this is a Windows choice.

Initial Windows 11/PowerShell 5.1 probes proved `GetNamedPipeServerProcessId` on the same connected pipe handle and rejected an expected-PID mismatch before forwarding. A subsequent production-helper exercise proxied a 163,840-byte frame and rejected an incorrect PID and process generation. Bun 1.4.0 proved that the pinned public `--define` literal reached the extension-owned `--preload` module without replacing the native OMP CLI entry. An isolated real OMP 18.2.11 TUI then published its encrypted rendezvous under its own PID; the production peer-verified client authenticated that process, read its live model and thinking level, applied a thinking change with readback, and rejected the wrong generation. These are native-process and helper observations, **not** evidence from an installed VS Code profile, Webview, child environment or extension-host reload; those gates remain open.

### Consequences

- Positive: the reusable key never enters terminal creation options, startup environment, stdin, argv, native TUI buffer, child environments, relay or Webview. A replaced rendezvous without the genuine key cannot pass both kernel PID and HMAC authentication.
- Positive: OMP's published CLI remains `import.meta.main`; a public-only preload does not replace its native worker entry.
- Negative: a Windows PowerShell P/Invoke proxy, RSA-OAEP key lifecycle and process-generation proof require bounded framing, exact connection lifetime and SecretStorage cleanup. Enterprise PowerShell restrictions may visibly disable host controls.
- Negative: Windows user-scoped SecretStorage cannot isolate an arbitrary malicious process running as that same user; the user explicitly selected that local trust boundary. POSIX peer verification remains a separate parity requirement.

## Verification Gates

- Verify installed OMP provider/version, pinned preload/`-e` canonical module reuse, same terminal/registry PID and real native worker behavior; test attempted public-key environment-collection substitution does not change the lexical recipient.
- Test actual encrypted host key, wrong-recipient and forged-rendezvous rejection, fake pipe/wrong process generation, genuine PID+creation-time HMAC, lost reply/reconnect/result and old request ID after ledger capacity without a second mutation; prove model **and** thinking readback and obsolete-session refusal.
- Inspect an actual isolated VS Code profile/terminal metadata, logs, argv, Webview traffic and child shell/MCP/subagent environments for canary absence; reload extension host while OMP remains alive and reconnect to the **same** writer. Do not use desktop automation without renewed user permission.
- Review the fixed final diff and helper for byte-bounded framing, process handle lifetime, exit/timeout handling, argument quoting and cross-extension public API exposure. Keep host controls unavailable until these gates pass.

## Addendum 2026-10-06: one server per process, reattach by the proven key, rotation only by proof

**Status of this addendum: accepted** after an independent architecture review of the addendum and its implementation. The review confirmed the peer-proof and key invariant (pid and creation time on the connected handle before any frame, fresh client nonce in every MAC, record pid equal to the pinned pid for a rotation) and raised the session-binding exposure now recorded under Consequences, the inconclusive-examination rule in step 3, a per-candidate discovery timeout, and a shutdown-before-start race in the host; each is addressed. The decision above stays accepted and is narrowed only as described here (step 4, "never accept a new candidate key from a changed rendezvous").

### Problem

After Reload Window (and after an in-place extension update) native sessions that were running showed "host identity check failed (key-changed)" or "The native host has not published its control record yet", and their statuses and completion toasts stopped, although the OMP process and its PTY were healthy. Reproduced in the isolated window with the installed build: OMP binds the `-e` extension again for every in-process agent session, so each task subagent ran `hostControlExtension` in the same OMP process and started a **second control server** (new key, new pipe name with fresh entropy, new instance id). The rendezvous record is one file per slot and last-writer-wins, so it began to name the subagent's server; the original server stayed healthy on its own pipe and the extension's live channel never noticed. After a reload the extension compared the record's key with the key it had pinned and refused it as `key-changed`. When the subagent's server later stopped it removed the record it owned, leaving the slot with no record at all although the original server was alive (the "not published" state, which retried forever against a file that would never come back).

### Decision

1. **One control server per process and slot.** The host module keeps a process-wide claim per `(directory, slot)`; the first binding serves and later bindings in the same process (subagent sessions) stay inert: they mint no key, pipe or instance, register no hook and cannot stop the owner or overwrite or remove its record. The claim is released when the owner's server stops, so a later binding may serve the slot again.
2. **A key this launch already proved identifies the host without the record.** Reattaching dials every pipe that exists for the slot (`omp-vscode-control-<slot>-*`, at most 32 per attempt, the record's pipe first when it still exists; the listing is a discovery hint that proves nothing), each through the unchanged peer proof (pinned pid and creation time on the connected handle) and handshake, and accepts only a pipe whose server proves possession of the pinned key. A pipe served by another process or holding another key is skipped as conclusively not the pinned server; a pipe that cannot be examined (unreachable, timed out, refused, beyond the cap) makes the attempt inconclusive. The authenticated binding must still match the slot, the dialled pipe and endpoint, the pinned pid and the launch's session/cwd expectation. This recovers hosts launched by older builds whose record was overwritten or removed, without restarting OMP.
3. **A changed key in the record is accepted only as a rotation by the same proven process, after a conclusive absence of the pinned server.** It is considered only when step 2 examined every listed pipe and found none that proves the pinned key (an inconclusive examination rejects and is retried, it never falls through to a rotation), and only when the record names the pinned pid, is sealed to this launch's recipient key, the peer proof shows the pinned pid and creation time, and the host proves possession of the new key in the handshake. The caller then pins the new key. Any other changed key, a record for another pid, a pipe served by another process generation, or a host that cannot prove the key it published stays refused (`key-changed`, `pid-mismatch`, `generation-mismatch`, `key-mismatch`). The extension never re-pins a key for an unverified host.
4. **No sticky pending state.** With a pinned key a missing record is not startup lag: its wait is bounded to three seconds, the state reads as one line ("Host control lost: … Reload the session to restore them."), and failed native reattaches back off from 5 s to 60 s instead of re-dialling continuously. A first launch that never connected keeps the bounded startup wait with a one-line "Waiting for the native host to publish its control record" state.

### Why this keeps the security invariant

The original invariant was that a substituted record or pipe cannot make a different host trusted. It rests on two proofs that do not move: the kernel identity of the pipe server on the very connection that carries the HMAC exchange (pid plus creation time recorded at launch) and possession of a key the host generated and sealed to this launch's private recipient key. Re-pinning a key for the **same** kernel process is not a change of host: a same-user process that is not the OMP process cannot satisfy the peer proof, and one inside it is outside the boundary the user selected for this ADR. The earlier flat refusal also turned a harmless same-process republication into a permanent loss of control, which is the defect observed.

### Consequences

- Positive: Reload Window, in-place update and subagent-heavy sessions keep their statuses and toasts; sessions launched by builds before this change recover after the new build is installed and the window reloaded, provided their original server is still alive.
- Negative: a session whose original server is gone and whose record is gone has nothing to attach to; the one-line state says so and Reload (a managed restart that resumes the conversation) is the way out.
- Negative (residual, recorded by the independent review): servers inside one OMP process are not distinguishable by their native session — a native terminal pins no session file — so a rotation could in principle bind a subagent's server. Rotation is therefore considered only after every listed pipe of the slot answered conclusively and none held the pinned key (an unreachable, timed-out, refused or over-cap pipe makes the attempt inconclusive and it is retried later instead), which never happens while the original server of an older build is alive, because that server lives until the process exits. The same exposure exists on a new host only if its owner stops while the process continues and a subagent binding takes the slot over; the process-wide claim is released only on the owner's own `session_shutdown`.
- Negative: each unverifiable attempt spawns up to 32 PowerShell peer proofs (older hosts leak one server per finished subagent, and the original may be any of them); the backoff bounds that cost.

### Verification

Focused tests: rotation accepted for the same process and refused for a record naming another pid, a pipe served by another process generation, and a host that cannot prove the published key; reattach by the proven key when the record names a subagent's server or is absent; the host binds one server however many sessions bind the extension and serves again after its owner stops; a missing record is not sticky once the host answers. The isolated window ran the same artifact end to end (see [the architecture overview](../architecture.md)).
