# ADR-0071: Edit OMP's settings from its own registry in a staged worker, and write one layer at a time

## Context and Problem Statement

OMP's `/settings` is a terminal-only menu over about 414 settings in ten tabs; RPC has no settings commands. Desk covers 14 of them (model roles, chains, agents) in the Models and Agents editors (ADR-0048) and can write no project layer for anything else. The user wants the same settings in a Desk editor, writing the global and the project layer.

Constraints: OMP's schema belongs to OMP and changes between releases (the 18.10 registry has 550 handles, a tab and group layout, a control mapping and 13 visibility conditions); the installed OMP is imported from source by staged Bun workers, never bundled; a credential must not reach the page or the extension host's state; OMP's config files are written by other processes, so writes need the native lock and conflict detection; `config/settings-ui.ts` keeps its visibility table private and evaluates it over its `Settings` singleton; ADR-0011 runs the installed OMP without a version gate.

## Considered Options

- Hand-maintain the setting list in Desk: no coupling to OMP's internals, but it drifts at once and duplicates 414 definitions.
- Host OMP's TUI settings menu: violates ADR-0048's native-editor choice.
- Initialize OMP's `Settings` singleton in a worker and write through its setters: reuses OMP's validation, visibility and persistence, but starts background saves, migrations, effects and file watchers inside an editor transaction, and ADR-0048 rejected setter-based writes for the same reasons (an in-memory init avoids the persistence but not the process-wide state; it is used only by the live comparison probe).
- Import OMP's registry and panel definitions in a read-only staged worker, project them to bounded JSON, validate with OMP's own `assertWritable`/`normalize`, and write through the existing locked transaction; repeat the 13 visibility rules over a read-only reader and pin them against OMP's own predicates with a live test.

## Decision Outcome

Choose the last option. A second staged Bun worker, `config-settings-worker`, imports `config/all-settings.ts`, `config/registry.ts`, `config/settings.ts`, `discovery/index.ts` and `pi-tui/overlays/settings-defs.ts` of the selected OMP, builds the same entries as `createSettingsHost()` and takes the tab, group and control mapping from OMP's own `getSettingsForTab`. It never initializes the writable singleton; layers, provenance and environment come from `Settings.loadReadOnly` and the registry handles.

1. **Projection.** Each panel setting becomes one `ConfigEntry`: identity, tab, group, label, description with OMP's environment note, type, control (boolean, enum, number from OMP's listed choices, typed number for the 26 numbers OMP lists no choices for, text, multiselect), default, the value in the global and the project layer, the effective value and its source (default, global, project, runtime, overlay, env), the environment variable's presence and effect, the visibility result and whether each layer may be written. The project layer shown is the folder's own `.omp/config.yml`; OMP merges every project settings file and the last that sets a key wins, so the file that wins (`.claude/settings.json` over `.omp/config.yml` over `.omp/settings.json`) is named per entry (`projectOther`), including when `.omp/config.yml` also sets the key and is shadowed. An environment variable's value is never read into the output.
2. **Read-only kinds.** Credentials, records and free-form lists, strings with run-time choices, oversize values, an unknown control or option shape and an unknown visibility rule are shown read-only with a note and, except for credentials, an action that opens the layer's YAML at the key.
3. **Secrets.** A setting OMP marks as a credential has no value, default or effective value in the projection, only `set`/`unset` per layer; the host's write baselines hold registered non-credential paths only; the note points to `omp config set <id> <value>` in a terminal; an unedited credential in the YAML survives a write untouched.
4. **Writes.** One setting and one layer per request, through `writeConfig` under OMP's native lock (ADR-0048): reread under the lock, targeted-key merge with conflict check against the baseline, validate with OMP's `assertWritable` after `normalize`, staged fsync and atomic replace, exclusive first creation, no rewrite when nothing changes. Values must be ones the control offers; a typed number is a finite number, whole when the setting's default is, checked by one function in the page and again in the worker, plus OMP's `assertWritable`. An empty text save is a Reset, as in OMP's panel. The first creation of `.omp/config.yml` is refused when it would stop an ancestor's AGENTS.md, RULES.md or SYSTEM.md loading (OMP uses only the nearest non-empty `.omp`). The home folder and the global scope have no project layer. Reset removes the key and prunes the mappings it emptied, as OMP's `unset` does. Every refusal (unknown id, read-only kind, hidden by condition, unlisted value, no project folder, conflict, malformed or lost file, out-of-range OMP) names its reason and writes nothing. The outcome sentence is built from a fresh read and names the value and layer OMP now uses, so a shadowing layer or variable is visible.
5. **Version coupling.** No numeric version gate (ADR-0011). Runtime shape checks are the gate: a failed import, a missing export, a malformed handle, a missing or non-boolean credential marker or an unknown provenance word is one fail-closed refusal with no native error text, while drift in a single setting degrades only that setting to read-only. A setting is a credential when `isCredential`, `definition.credential` or `ui.secret` says so. The snapshot reports whether the installed release is the verified one (18.10.3), and the page says so. A committed recording of the schema, a live re-recording comparison and a live comparison of the visibility rules with OMP's own predicates detect drift; a release is adopted as verified after they pass on it.
6. **Applying.** The editor claims nothing per setting: OMP records no liveness; running RPC and interactive processes reload watched config files, and settings read once at startup apply to new sessions. One footer note says so.
7. **Entry points.** A bare `/settings` in Chat (intercepted like `/models` and `/agents`; with arguments the terminal-only guidance opens the same editor), `ompDesk.openOmpSettings`, and the Sessions title menu. One editor per profile and scope.

### Consequences

- Positive: the editor follows OMP's own tabs, groups, labels, controls and visibility without a Desk-maintained list; a new OMP setting appears with no Desk change; the project layer becomes editable; credentials cannot leak by construction; no OMP singleton, background save or watcher runs in an editor operation; the page's presentation is separate from the data and protocol layer.
- Negative: Desk now depends on four OMP source modules and the shape of the registry handle; the visibility table is repeated; an OMP release other than 18.10.3 is read through the shape checks alone until a verification pass adopts it; the editor needs Bun and importable OMP sources (compiled-only installs get a refusal); rewriting the global file applies OMP's migration and drops YAML comments, as ADR-0048 already accepts; settings OMP's own panel hides stay config-file only, except the 26 numbers with panel metadata and no listed choices, which take a validated typed number by the user's decision; the project layer written is `.omp/config.yml` while OMP merges several project files (a foreign file that wins is named, not editable); the first project write in a folder under an ancestor `.omp` with context files is refused.

## Architecture Review

- Reviewer: architect (independent, 2026-10-13), two passes against the working tree and the OMP 18.10.3 sources.
- Outcome: accepted after changes. The first pass verified the approach (schema from OMP's own registry and `getSettingsForTab`, layers from `Settings.loadReadOnly`, writes through the locked transaction), the counts (550 settings, 414 with panel metadata, 26 numbers and 8 lists without choices, 13 conditions, 10 tabs, 8 credentials), the reset-prunes-parents rule and the layering, and found four material issues, all fixed: (M1) the numeric version gate contradicted ADR-0011, so it was removed and the runtime shape checks are the gate; (M2) credential classification was not covered by the shape check, so `isCredential`, `definition.credential` and `ui.secret` are all checked and any one marks a secret, and an unknown provenance word is a shape refusal; (M3) project-file precedence was modelled backwards (a foreign project file overrides `.omp/config.yml`), so the worker reads OMP's own settings capability and names the winning file; (M4) the first project write could stop an ancestor's AGENTS.md, RULES.md and SYSTEM.md loading, so it is refused with the reason (the author's decision; confirmation was the alternative). Its minor findings were applied: empty text is a Reset, an inherited control shows the layer below, legacy keys are labelled "not recognised here", the home folder and the global scope have no project layer, a credential row cannot be opened at its key, the conditions rationale is corrected, and ADR-0048 and ADR-0052 carry amendment notes. The second pass confirmed those fixes and found two more, both fixed: the ancestor check refused a folder that is the repository root (it now returns nothing there), and the README and CHANGELOG still claimed a version range. The user's later decisions (26 typed numbers, hidden entries hidden in search, the S1 layout with a Global / Project / Effective switch) are recorded in this document.
