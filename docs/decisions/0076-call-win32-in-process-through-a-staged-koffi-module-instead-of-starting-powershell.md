# ADR-0076: Call Win32 in process through a staged koffi module instead of starting PowerShell

## Context and Problem Statement

Desk answers its Windows questions (a lease mutex, a process's creation time and descendants, the owner and access list of a path, the server of a pipe) by starting `powershell.exe`. Each answer is one Win32 call. On the maintainer's machine a PowerShell start costs 0.73–0.81 s wall and 1.2–1.6 s CPU (0.21 s the evening before), and Windows Defender spends about 2.1 s of CPU on each start; every reload showed the 5 s lease probe timing out in every window and restore steps of 13–42 s. Desk starts one PowerShell every 15 s per window with the Sessions view visible, and a chain of them at every restore and launch. The cost is per start and is set by the machine, not by the script. The [design](../designs/2026-10-15-native-windows-checks-without-powershell.md) has the inventory and the measurements.

Requirements: no PowerShell start on a recurring, restore or launch path (a folder shell's owner-watch helper is the one exception, kept as a follow-up); the same answers, refusals and fail-safe `unknown` verdicts as today's scripts; the staged, hashed, verified trust model of [ADR-0012](0012-run-child-process-entries-from-staged-copies.md); both `win32-x64` and `win32-arm64` in the VSIX, no download at run time; buildable on GitHub's `windows-latest` and locally without a C toolchain (the maintainer declined one for [ADR-0029](0029-report-uncontained-pty-tree-stop-as-unknown.md)).

## Considered Options

- **Keep PowerShell and start it less** (longer cache, fewer rows, a resident helper): lower load, but the restore path is a chain of mandatory starts and the first start of a resident helper is the same 0.8 s or more.
- **A native helper executable (C or Rust) that Desk stages and spawns:** 98 ms cold and 16 ms warm per start on this machine, crash-isolated, a natural fit for ADR-0012. Still one process creation per question (and whatever per-process cost the machine adds), and it needs an MSVC or Rust build for two architectures, ARM64 cross tools in CI, and a second review surface.
- **A Node-API addon written for Desk:** in process, only the needed calls, no third-party binary. Needs the same toolchain and per-architecture build, cannot be built or run for arm64 on this machine, and puts hand-written C in the extension host.
- **koffi, a prebuilt FFI addon, called from TypeScript:** in process (0.04 ms for the lease call, 1.1 ms for a nine-path ACL read, 9 ms for a process tree), no build step, both architectures prebuilt and integrity-pinned in the lockfile, loads in Node, Electron's Node and Bun. Third-party native code in the host, and a generic FFI primitive instead of a minimal one. Chosen.
- **`pwsh` 7:** 0.4 s, not installed by default; the helpers are written for 5.1.
- **Koffi, with the old PowerShell checks kept as a fallback for a machine where `koffi.node` cannot load** (considered at O9 and rejected by the maintainer, 2026-10-15, after weighing it against a visible error). It means two implementations of every check, a path that never runs on a healthy machine and so is never exercised, and a second security review of both. It would also not serve the machines it is meant for: an environment that enforces AppLocker or WDAC on DLLs usually enforces it on scripts too, and PowerShell then runs in Constrained Language Mode, which refuses `Add-Type` and P/Invoke (the removed `verified-pipe.ps1` depended on exactly that; that direct .NET type calls are restricted there as well is an inference, not verified). What is left is a security product that quarantines the file, and restoring it with an exclusion fixes that without a second implementation. A blocked module therefore stops launching and attaching with an explained error (decision 6).

## Decision Outcome

1. **Mechanism.** Desk ships `out/native/koffi.node` (one file per VSIX, the target's architecture, version 3.3.3 exactly) and calls `kernel32`, `advapi32` and `ntdll` through it from `src/host/win32-native.ts`, the only module that touches the FFI (`check-imports.mjs` enforces it). It uses the raw addon through `process.dlopen`; koffi's JavaScript wrapper is not shipped. The module binds a fixed table of function prototypes at load.
2. **Same answers, or stricter.** The module reproduces each script's contract, call by call (design, "Module"): `OpenMutexW(SYNCHRONIZE)` with `TryOpenExisting`'s mapping (`FILE_NOT_FOUND`, `PATH_NOT_FOUND`, `INVALID_NAME`, `INVALID_HANDLE` absent; `ACCESS_DENIED` held; else error); `OpenProcess(QUERY_LIMITED)` + `GetProcessTimes` for the FILETIME string (`INVALID_PARAMETER` and an exited process gone, any other failure unknown); one Toolhelp snapshot walked in memory for descendants; `GetNamedSecurityInfoW(OWNER|DACL)` with every allow and deny ACE (object and callback forms included) as raw mask and flag, a NULL DACL as an Everyone full-control entry, SIDs formatted from the binary form, the token SID from `GetTokenInformation`. Where the native reading differs from `GetAccessRules` it is stricter (an object ACE on a file is reported); an ACE type the module does not know refuses. The typed results are the ones `queryPtyProcessIdentity`, `queryPtyProcessTree`, `readStorageSecurity` and the lease probe already return, so no consumer changes meaning.
3. **Staged and verified like every loaded file.** `koffi.node` is copied to `<globalStorage>/runtime/<sha256>/koffi.node` by the existing content-addressed staging; each process re-reads and re-hashes the copy immediately before its one `dlopen` and checks the PE machine type first (the broker gets `--native` and `--native-sha256`, replacing `--helper` and `--helper-sha256`; the broker's `--self-check` and `--pipe-only` runs take the same pair, load the addon and read one creation time, and the stored runtime proof's key includes the addon digest). A loaded DLL is held open, so the extension host never loads it from the install folder (a `--force` reinstall must still succeed).
4. **Order of verification keeps ADR-0012's rule: nothing staged is loaded before the layout is verified.** Until the security read is native (slices 1 and 2), the existing PowerShell verification of the staged layout runs before the host loads the addon, exactly as for every staged helper today. When the security read becomes native (slice 3) the verifier is a short-lived child: Desk runs `Code.exe` as Node (`ELECTRON_RUN_AS_NODE`, as brokers already run) on a one-shot entry in the install folder, which loads the install folder's own `out/native/koffi.node` (the same trust root as `out/extension.js`; it holds no file for longer than the child lives), writes the staged copy of `koffi.node` itself (so ADR-0012's "rules before the first byte" pass has a reader), establishes the rules, verifies the layout with the native reads, and exits with the verdict, under the existing 20 s bound. Only after a pass does the extension host re-hash and load the staged copy; a refusal, a start failure or a timeout leaves the module unloaded (`win32Native()` resolves `null`, every reading `unknown`, staging refuses as it does today for a loose tree). The hash-to-`dlopen` gap that remains follows a verification that passed, so it is open only to principals the rule admits, the same gap every staged helper has (the Bun design, 2026-10-14, "usable only by principals the rule admits"). Costs one non-PowerShell process start per activation. A child that loaded the staged copy was considered and rejected: it protects nothing, because same-user code is inside ADR-0006's boundary, and loading before verifying lets a substituted DLL falsify its own verification.
5. **Bounded calls.** Calls that cannot wait on anything outside the process (open mutex, open process, process times, token) are synchronous. `GetNamedSecurityInfoW` and the process snapshot run on koffi's worker threads, which are libuv's shared pool, so Desk uses one lane: at most one such call in flight, the others queued, each request carrying a deadline after which its reading is `unknown` (which refuses, as today's 20 s read timeout does). A call past its deadline keeps the lane until it returns (a Win32 call cannot be cancelled), so later readings answer `unknown` at their own deadlines and Desk never starts a second pool call; releasing the lane on timeout would bring back the pool exhaustion this rule exists to prevent. No pool thread is held for the life of a connection. Account names (`LookupAccountSidW`) are not read on the admission path: a reading carries SIDs, and names are resolved only for the SIDs named in a refusal message, in the same lane under the same deadline, so a stalled lookup holds the lane too.
6. **Fail-safe, no PowerShell fallback.** A module that cannot be loaded (hash, architecture, `dlopen`, quarantine by security software) is one log line naming the cause, shown where the session fails to start and not only in the log. Every reading is then `unknown` and every private-storage verification refuses, so no session starts. There is no PowerShell fallback: it would keep the scripts, their staging and a second implementation of every check. Consequently an environment that blocks unsigned DLLs (neither shipped `koffi.node` is Authenticode-signed; node-pty's `conpty.node` is not either) stops Chat as well as Terminals, because the Bun broker now needs the creation-time reading. *Decided 2026-10-15 (the maintainer, O9):* a blocked or missing module stays fatal to launching and attaching, and the remedy is a message, not a fallback. When the one load settles as unavailable the window shows one message (`src/wiring/native-module-notice.ts`) that classifies the cause from the raw error where Windows names it (`src/host/native-module-failure.ts`: blocked by policy, `ERROR_ACCESS_DISABLED_BY_POLICY` 1260 or a code-integrity block such as 577; missing or quarantined, including 126, 225, 226, 1920 and `ENOENT`; a stage child that timed out; anything else, which a localized Windows message also falls into, the raw error being kept in the log and in the diagnostics), says plainly that New Session, Resume and re-attaching a running Chat do not work meanwhile and that saved sessions stay listed and a stopped one still opens read-only, and offers **Copy diagnostics** (shipped and staged paths, SHA-256, error and code, VS Code and Desk versions, architecture), **Open troubleshooting** (the README section that tells an administrator to allow the file by hash or path in both locations, or to restore it from quarantine) and **Reload Window**. The last is deliberately not an in-place retry: other readers of the window already hold the unavailable answer (the broker client's cached state-directory verdict, the window's claim without its creation time), so a module that appeared under them would leave those stale until the next reload anyway. A refused check names the cause in its detail instead of "the native module is unavailable". Signing `koffi.node` ourselves is a possible later way to make an application-control policy that trusts our publisher allow it without a hash rule; it is not planned and nothing here depends on it.
7. **One loader, awaited.** `win32Native()` is one shared promise started first thing in activation (before the first creation-time reading and before storage access); every reader awaits it, and `null` is only the settled "unavailable" answer, so no reader can race an unfinished load and file a claim without its creation time for the life of the window.
8. **Slices.** Lease probe and loader; process identity (including the control channel's generation read and the claim start time); owner and ACL reads (private storage, executable trust) with the verifier child; the peer proof (`CreateFileW` overlapped; the server pid read from that one handle and its creation time from the kernel; the verified handle is then given to libuv as a socket, so libuv's own overlapped I/O carries the frames and no pool thread is held per connection). *Amended 2026-10-15 at slice 4:* the first mechanism, completion by Windows thread-pool waits through koffi callbacks, is replaced by adopting the verified handle into libuv. The prototype (a real named pipe, under Node and under VS Code's own Electron) showed that `socket._handle.fd` is -1 for a connected Windows pipe and that `_open_osfhandle` from `ucrtbase` is invisible to libuv's own C runtime, so the descriptor comes from `uv_open_osfhandle`, which the host executable exports and koffi can bind, and `new net.Socket({ fd })` adopts it; nothing is read or written before the pid and creation time match, and a failed proof closes the handle unread. The bridge builds `\\.\pipe\<name>` itself and only from a name that matches `CONTROL_PIPE_NAME_RE` (the native call opens nothing but local pipes), the executable whose libuv is bound is the one the kernel names (`GetModuleFileNameW(NULL)`), and no process handle is kept for the connection. The obsolete scripts are deleted with the slice that obsoletes them. The owner-watch helper (per folder-shell broker; its readiness is awaited by the first attach of a folder shell), the WinRT toast and the one-time font discovery stay on PowerShell and are recorded as follow-ups; `icacls.exe` (a store's one-time rewrite) and `taskkill.exe` stay.
9. **Build.** `npm ci` provides the x64 addon; `scripts/native-assets.mjs` provides arm64 from the locked tarball and refuses on an integrity mismatch before writing. Neither needs a compiler. The build pins the expected SHA-256 of each architecture's `koffi.node` in the repository, so a version bump is a reviewed hash change, and the VSIX gate checks the PE machine type of the packaged addon automatically.
10. **Narrow amendments to accepted decisions.** This ADR amends, and the amended ADRs carry a banner pointing here: [ADR-0054](0054-verify-private-windows-storage-with-security-identifiers.md) (the module-free .NET reader and its rejected "native in-process reader" are replaced by the native reader above; its refusal semantics, SID rule and 20 s bound are kept), [ADR-0006](0006-host-generated-key-peer-verified-pipe.md) (the "no packaged native binary" reason; slice 4 replaces the helper; its gate is the real host-control handshake through the native bridge (`connectVerified` and `connectWithProvenKey` against `startHostControlServer`) and the same proof under VS Code's own Electron, both in `control-client.test.ts`), [ADR-0046](0046-probe-omp-session-lease-for-external-writers.md) (the probe is a native call, not a staged PowerShell helper), [ADR-0024](0024-own-omp-pty-for-in-tab-terminal.md) and [ADR-0074](0074-run-chat-brokers-on-the-sessions-own-bun-runtime-with-code-exe-as-fallback.md) ("a Chat broker on Bun loads no native module": it now loads `koffi.node`, hashed and checked by the self-check; both stored proofs, the full one and the pipe-only one, include the addon digest). ADR-0012's 2026-10-13 amendment, decision 4, is not amended.
11. **A warm start reuses the layout verification instead of spawning the verifier (amends decision 4, ADR-0054 and ADR-0012 for the native module only; the caching itself maintainer-approved 2026-10-15; the ancestor rule, the account and volume binding and the post-load read below came out of an independent review and are put to the maintainer by name).** Measured on the maintainer's machine at a reload of three windows, the verifier child costs 0.6–1.6 s, and every step after it that waits for the module (a claim, the state-directory check, a restore's first attach) pays a turn of a host event loop that other extensions keep busy for seconds; an admission of 3–5 s per tab was that wait. A process start on the critical path is the cost, not the verification. So the child, after its verification passes, records what it verified, and a later activation that finds the same state skips the child, loads the staged copy in one synchronous step, and judges the layout again natively before it shares the module. This is the separate review of the other-account boundary that [ADR-0012](0012-run-child-process-entries-from-staged-copies.md) (rejected options), [ADR-0054](0054-verify-private-windows-storage-with-security-identifiers.md) (rejected options) and the 2026-10-13 amendments of ADR-0035 and ADR-0032 reserved for cross-window verdict caching, for this one layout and nothing else: every other store is verified at every use as before.
    - **The record.** `<globalStorage>/native-proof/<sha256>.json`, named by the digest of the packaged `koffi.node`, written by the verifier child only after `stageRuntimeAssets` and the verification of the proof directory itself have passed, and only when the layout is on one local, fixed NTFS volume (`GetDriveTypeW` is `DRIVE_FIXED`, `GetVolumeInformationW` names `NTFS`, every path reports the same volume serial): a network share caches metadata for seconds and a redirected profile is realistic, and a file system without a volume-wide file id cannot show a replaced path. It holds the digest, the staged path, the time, the account that verified (the token SID the native read reports, and the user name and profile directory `os.userInfo()` reports), and for every path the verification covered (each ancestor the tree is reached through, up to but not including the volume root, which is ADR-0012's trust anchor; the runtime directory; the digest directory; the staged file) its kind, volume serial and file identifier as `lstat` reports them and, for the digest directory and the file, which hold the module and nothing else, also size and last-write and change times in nanoseconds. The chain is read right after the staging and again after the record is written; a record is kept only if nothing it names moved between the two. The proof directory is outside the chain, so writing a record changes nothing a record names; it is created and verified owner-only by the same convention as the runtime directory, before the record is written into it, and the record is verified as a file afterwards.
    - **The reuse.** In one synchronous step, with no await: read and hash the packaged file (the install folder is the same trust root as `out/extension.js`); `lstat` the proof directory and the record and require plain objects; read the record for that digest; require it to be well formed, to name the expected staged path, to have been written by the account this process runs as (user name and profile directory), to be at most 24 hours old and not from the future; `lstat` every named path and require it to be a plain directory or file (a link or a junction is refused) with the identical volume and file identifier (and, for the digest directory and the file, size and both times); read the staged bytes, require their digest, check the PE machine type; `dlopen`. Then, in the same synchronous step and before any reader can have the module, one synchronous native read (`readSecuritySync`, decision 12) takes the owner and access list of every path of the chain (about 2 ms), and `chainSecurityProblem` judges them by the verifier's own rules (`chainSecurityProblem`: every entry of an owned path names a permitted principal, no other account's entry on a carrier lets it replace or re-permission it, every path is owned by a permitted principal) and requires the token SID to be the recorded one. A refusal settles the load as unavailable with that cause, exactly as a refusal by the child does (decision 6). Any mismatch, any error and any missing piece before the `dlopen` means "no proof": the verifier child runs as in decision 4 and writes a fresh record. A failed `dlopen` after a matching proof is not retried from the proof; it takes the child's path, which reports the cause.
    - **What it relies on, and what it does not.** What the loader consumes is the path chain, and a chain in which every link is a plain object with the volume and file identifier it had is the chain that was verified: a replaced or redirected link has another identifier or is a link. The digest directory and the file also keep their times, so a change of their access rules, owner or entries changes a change time; setting a change time back needs write-attribute rights on the object, which only the owning account, administrators and the system have on those two paths (ADR-0006's boundary, the same one that lets them replace `out/extension.js`). The times of every other directory are deliberately not compared (measured on the maintainer's machine: VS Code's global storage directory gained or lost an entry within the previous half minute, the roaming profile folder within hours, and Desk itself adds a sibling to the runtime directory whenever it stages another asset, such as the first session after an update; a comparison that included them would almost never match). What that gives up is the earlier sign of an in-place change of an ancestor's owner or access list; the native read after the load closes it for the activation that loaded, so a carrier that became replaceable refuses in the same activation and not within 24 hours. What remains, and is stated as the residual: an account that such a change admitted could replace an ancestor inside the few milliseconds between the proof's `lstat` and the `dlopen` (decision 4 rejected loading before verifying for that reason, and carries the same gap from the hash to the `dlopen`), and the read after the load judges the state it then finds, so a substitution undone before that read is not seen. The staged bytes are still re-hashed before every load, so a substituted file fails the digest as before. The record's integrity rests on the owner-only rules of its directory, checked when the record is written; `verifiedAtMs` is self-reported, so whoever can write that directory could refresh the 24 hours, and forging a record gives nothing without a change made from inside the boundary, because an outsider cannot read the owned paths' identifiers and times. A different account on the same profile (an elevated process pointed at this user-data directory) finds a record it did not write and takes the child's path. The verified rules are established by the child on the first activation of a build, after any update that changes the packaged module, after 24 hours, and after anything that changed the digest directory or the file or replaced a directory above them. The access checks of the broker state directory, the broker executable and every other private store are unchanged: they run natively in the host at every use, and are cheap once the module is loaded.
    - **Cost.** About a dozen `lstat` calls, two sequential reads of 1.3 MB with a SHA-256, one `dlopen`, one batched native read: measured in a hidden window on an idle machine, the module is ready 26–30 ms after activation began (read 1, hash 1, `dlopen` 2, bind 1, verify 2) against 153–440 ms with the child, and the staging child no longer runs. A run that has no proof (first run of a build, a daily refresh, an account or volume change, a changed digest directory or file, a replaced ancestor; an entry another program adds to an ancestor is not a change) costs what decision 4 costs. The hit rate over real reloads is read from the activation log, which names the reason of every miss.

12. **A native security read of a verified local NTFS path is synchronous (a transport change of decision 5; no decision's content changes).** Decision 5 put every Win32 call that can wait on a network or a domain controller on the lane, one call at a time under a deadline, because libuv's pool is shared and a call cannot be cancelled. Measured on the maintainer's machine at a reload with three windows, that transport cost seconds for work that takes microseconds: the warm start's read of ten paths took 3.5–5.2 s (ten sequential pool jobs, each finished by a turn of an event loop that other extensions kept blocked for 1.1–1.2 s at a time), against 0.26–0.42 ms for the same ten calls made synchronously (4.7 ms through the lane, idle). The call cannot wait on anything when the path is on a local fixed NTFS volume, so for those paths the read is made on the calling thread: `Win32Native.readSecuritySync`, used (a) by the warm start's chain read, whose record exists only for such a volume and which asks again before reading, and (b) by `readVerifiedStorageSecurity`, which the storage verification calls for the paths it has just shown to be plain (no link or reparse point on the way), when `volumeOf` says every path's volume root is a fixed NTFS drive (remembered per root for the module's life). Any other volume (a network drive, a UNC path, another file system), and every other caller (`readStorageSecurity`, which makes no promise about the paths it is handed), keeps the lane and its deadline. The rules the reads are judged by are unchanged. A synchronous call blocks the host thread for as long as a local disk takes to answer, which the synchronous read, hash and `dlopen` of the module in the same step already do. The same rule makes the rest of the broker state directory's verification synchronous (`synchronousLocalPaths`): when every path it names is on a local fixed NTFS volume and every ancestor of each is an existing plain directory (checked outermost first with `lstat`, which never follows the component it asks about, so no call can be sent through a junction to a network path), its directory creation, the `lstat` and `realpath` of every store path, the listing of the record directory and the write probe (`open`, `write`, `fsync`, `read`, `rm`) are made on the calling thread, each as one synchronous call instead of one thread-pool job and one event-loop turn (about twenty-five of them, each a wait behind other extensions' work). The first ancestor that is missing, a link or not local sends the whole verification to the asynchronous path, which produces the refusal; a probe's own fake security reads keep the asynchronous path. The probe's `fsync` stays: it is part of what the probe proves, and a single flush of a 24-byte file on a local volume is the longest synchronous call here. The log line `broker state access` is now Info and names the parts of the verification (`mkdir`, `list`, `directories`, `plain`, `security`, `judge`, `probe`), so the rest of its time can be attributed.
13. **The same rule serves the session claims and the profile catalog (2026-10-15; the same transport change, no decision's content changes).** After decision 12 the reload's remaining seconds were the claims and the catalog: an asynchronous `stat` measured at startup took a median of 11–31 ms and up to 693 ms, a synchronous one 0 ms, and a claim take (about fifteen calls, two or three of them flushed writes) cost 0.2–5.4 s per row, a catalog commit and the activation read up to 4.7 s and 0.8 s. The calls of `session-claim.ts`, `atomic-file.ts` and `profile-catalog.ts` now go through `localFs(path)` (`src/host/local-fs.ts`): the asynchronous `fs/promises` calls, or, below a directory for which `synchronousLocalPaths` said yes at activation (the `session-claims` and catalog directories, one verdict), the same calls as synchronous steps wrapped in `async` functions, so the code, the order of the calls, the flags, the error codes and every wait are unchanged. A lock that has to wait (a claim's mutex directory, the catalog's lock file, a rename another process holds open) still sleeps on a timer between attempts; only a file call itself is synchronous. Without the native module, on a network or removable volume, or behind a link, the calls stay asynchronous. A flushed write blocks the host for as long as the disk takes to flush it; that cost is on the host's one thread, as decision 12's reads are.
14. **The digest of the packaged broker tree is recorded at build time and checked later (2026-10-15; a narrow relaxation of ADR-0012's rule that identity is the content, accepted by the maintainer's coordinator; no trust decision reads it).** A re-adoption needs this build's tree digest to say whether a surviving broker runs this build's runtime ([ADR-0024](0024-own-omp-pty-for-in-tab-terminal.md), [ADR-0035](0035-distinguish-a-recorded-process-from-a-later-occupant-of-its-pid.md); `PtyHandle.buildMatches`). The window used to hash the 24 files (2.9 MB, binaries among them) of `out/pty` and the native module at every activation, and on a loaded machine that took 1.9–2.3 s, the whole `broker client` step of every tab's reconcile, and the thread-pool jobs it queued delayed the next row's other file calls. **What the digest gates, and what it does not:** `buildMatches` decides the log text, the screen repaint, the "older build" label of Processes, and, in a launch into a slot that a live broker holds, whether that broker is adopted as this build's or the slot is reported occupied ("reported, never replaced and never adopted as this build's"). No trust decision reads it. A broker is authenticated by the token handshake (its MAC covers the broker's pid and creation time), its attestation, the protocol version and the runtime version, each checked on its own, and whether a broker may be stopped depends on the protocol and runtime versions only. **The relaxation:** [ADR-0012](0012-run-child-process-entries-from-staged-copies.md) rejected identifying a build by recorded metadata ("a version string is metadata that can disagree with the code it labels"), and a digest the build wrote into a file is also metadata. Until this window has hashed the installed tree, the identity it compares is that record. That window lasts from activation until the first of two events: the runtime proof finishes, after which the proof's own digest, hashed from the staged copies, takes precedence over the record (`attachIdentity` asks `provenAnswer` first), or, ten seconds after the startup restore is over, the check described below. In it a wrong record can only mislabel a surviving broker, or make a launch into a live slot report the slot occupied; it cannot authenticate, adopt as trusted, or stop anything. It is accepted because the record lies in the install folder, the trust root of `out/extension.js` (decision 11): whoever can edit it can edit the code the window runs. **The change:** `esbuild.mjs` writes `out/pty-tree.json` (`{ format, digest, files }`) after the tree and the native module are in place, with the algorithm of `hashRuntimeTree` (`scripts/pty-tree-digest.mjs`). The record lies outside the tree it describes; it is removed before a build writes its first output and written as the last step (`recordPtyTreeDigestAfter`), so a build that fails part-way, a watch build or an incomplete tree leaves none. The window reads it (one synchronous read of at most 4 KiB, decision 15) only when the extension passes `useBuildRecord`, which it does in a packaged install (`extensionMode` Production) and nowhere else: a development or test host, where `out/` is rebuilt in place, hashes the tree as before, and so does any other construction of the client. **The format is `omp-runtime-tree/v2`:** the files are ordered by code unit in the build script and in `hashRuntimeTree`. The first version sorted with `localeCompare`, which orders some names differently under `th`, `uz`, `om` and `haw` than under `en`, so a record built on a CI runner could differ from the hash on such a host and every surviving broker would read as another build; the digest also changes every later key built from it, so the first update after this decision stages and proves the runtime once, and a surviving broker staged under the previous format reads as another build once, even when its files are byte-identical. **The packaging gate:** `scripts/package-vsix.mjs` (`npm run vsix:*`, which the release runs) unpacks the VSIX it made and fails when `extension/out/pty-tree.json` is not the digest of the `out/pty` tree and native module that package carries (`scripts/verify-vsix-tree-record.mjs`), so a one-shot build that ran beside a watch build, files edited after the build or a packaging filter that dropped something cannot ship a record that describes other bytes. **The check, and what it covers:** once, 10 s after the startup restore is over, the window hashes the installed tree (two reads at a time) and compares it with the record; a difference is a warning in the log and the hash replaces the record's digest for every later attach, which is what every window used before this decision. A tree that cannot be read to be hashed leaves the record in use and is reported as `unchecked`, not as verified. The re-adoption at the restore is decided on the record, before the check runs: a correction changes later attaches only, and a handle adopted under the record keeps its classification; the warning says so. A build with no record hashes at activation as before. The staged runtime's own digest, the proof's key and the staging verification are unchanged: they hash every time. A cheaper check at activation (the recorded size of each file against a `stat`) was considered and left out; modification times are not usable for it, since a VSIX install may set them to the time it unpacks the files.
15. **The restore's own reads are synchronous on a verified local volume too (2026-10-15; the same transport change as decisions 12 and 13, no decision's content changes).** After decision 14 the `broker client` step of a reload fell from 1.9–2.3 s to 0.11–0.5 s and the wait came back one step later: `record`, the read of the tab's broker record, which took 18–39 ms before and 1.2–2.3 s now, while the restore ended at +3.4–4.9 s against +4.3–5.3 s, and every tab's `admission` waited 0.6 s on one `stat` of its session file in the first of two reloads. Nothing in those steps is slow by itself: `readPtyRecord` was one asynchronous `readFile`, which is four jobs of the host's file-system pool (open, `fstat`, read, close) each finished by a turn of the host's event loop, in every tab at once, and in the same reloads the loop was blocked for 1.2–1.3 s at a time by other extensions (`event loop blocked for 1337 ms`, process CPU 719 ms in 1437 ms) while an asynchronous `stat` took up to 545–851 ms and a synchronous one 0–16 ms. A wait that is queued behind other extensions' work lands in whichever asynchronous step comes first, so removing it from one step showed it in the next. The three file reads the restore makes before it talks to a broker are now synchronous steps when the volume is proved local: `readPtyRecord` and the read of `out/pty-tree.json` go through `localFs` (decision 13), and the `stat` of the session file in the restore's admission (`fileExists`) is its own `lstat`. **Roots.** The broker state directory joins the claims' and the catalog's in the activation verdict (the same storage root, one `synchronousLocalPaths` call); the extension's `out` folder has a verdict of its own, so that an extension folder behind a link turns off only its own read, and its target is the record file, so that `out` itself is checked. Both are Desk's own directories, and `localFs` matches them by prefix: `useSynchronousLocalFs` refuses a root that is a drive root or a share root. A recorded OMP session file is not Desk's: its folder is never made a root. `fileExists` asks `synchronousLocalPaths` about the file on every call, so every folder on the way (the session file's own folder included) must be a plain directory, and a folder replaced by a link is noticed by the next call; nothing but the volume of each drive root is remembered. A session file directly in a drive root, or one that is itself a link, keeps the asynchronous `stat`. **What the verdict now requires.** A drive-letter root (UNC, `\\?\`, `\\?\UNC\` and device paths are refused by their spelling, before any native call); `GetDriveTypeW` answering `DRIVE_FIXED`, and only then `GetVolumeInformationW` answering NTFS (the call can wait on a server or a device, so no other drive type reaches it); every ancestor a plain directory (`lstat`, not a link or junction), with the volume serial of the drive root, so a folder that has another volume mounted on it is not walked; the native module. Otherwise the calls stay asynchronous. **Bounds.** The record read opens the file, reads its size from the open file and refuses more than 64 KiB (a record is under 1 KiB; the file is then `invalid`), and the digest file more than 4 KiB (then no record), before reading either. Every read keeps its error codes, its order and its result (the tests compare the broker record and digest reads with their asynchronous answers). **What remains.** A synchronous call blocks the host's thread for as long as the disk takes: a small local read costs a millisecond or less, but a USB hard disk usually reports itself as a fixed drive, and one that has spun down blocks a synchronous `stat` or read for the spin-up, where an asynchronous one would have waited off the thread. The `GetDriveTypeW` and `GetVolumeInformationW` answers of a fixed disk are cached per drive root for the module's life. What stays asynchronous is what has to leave the process: the pipe `connect`, the `status` request, the attach `connect`; they wait for a turn of the loop and for the broker, and no file-call style changes that. The startup line `window timing: startup file-system turnaround …` now also lists the three slowest asynchronous samples with the moment each began (`slowest asynchronous stats: 851 ms at +1800 ms`), so the next reload shows whether a queue in the file pool or a busy loop held a step.

### Consequences

- Positive: no PowerShell start in steady state or on the restore and launch paths, except a folder shell's owner-watch helper; a lease probe, a creation-time reading and a security read cost microseconds to a millisecond instead of 0.7 s and more each, whatever else the machine is doing; no resident process; +1 MB per VSIX.
- Negative: one third-party native binary in the extension host, pinned by version and integrity; a generic FFI, so correctness rests on Desk's TypeScript decoding native memory (bounds-checked, tested against crafted blobs); a security product that blocks the DLL stops every session start, with a clear log line and no fallback; arm64 is packaged but not runnable on the development machine.
- Negative: one short-lived `Code.exe` (as Node) verifier start per activation once slice 3 lands; one more failure mode for Chat (an environment that blocks the unsigned DLL); a crash in decoding native memory now takes the extension host down, not a helper, and TypeScript over native memory is no safer than hand-written C, only reviewed and tested more easily.
- Negative: Desk's own Windows knowledge moves from readable scripts into TypeScript over struct layouts; the real-Windows tests (a held mutex, a real ACL, a real process tree, a real pipe) carry the proof that replaces "the script was the oracle".
- Negative: a window whose claims and catalog are on the synchronous path blocks the host's thread for the length of each flushed write; the startup line `window timing: startup file-system turnaround …` and the `window timing: restore tab …` pieces (`claim take`) are how a slow disk is told from a busy queue.
