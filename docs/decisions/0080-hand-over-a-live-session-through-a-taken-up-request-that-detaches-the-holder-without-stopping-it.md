# ADR-0080: Hand over a live session through a taken-up request that detaches the holder without stopping it

## Context and Problem Statement

A session is written by one window at a time; the window holds a claim (ADR-0039) and other windows may only switch to it (ADR-0056) or end its process (Stop, Kill: ADR-0060). A window that adopts a session whose old window closed, or any window that opened it first, keeps it even when another window, the one that has the session's folder open, wants it. The only way to move it is to end the process, losing the turn in progress and the background work.

The decision is how a live session can change windows without ending, and without a window overriding another's claim.

## Considered Options

- **A taken-up `handover` request; the holder detaches without stopping; the requester then opens it normally.** Reuses the audited request channel and the claim/attach proofs; the process is never touched. Cost: a new request kind, a new holder-side operation and a new index method.
- **The requester takes the claim over.** One step fewer, but a live holder would keep its broker connection and its runtime, and two windows would act as the writer. Contradicts ADR-0039.
- **Stop, then Resume in the requester.** No new mechanism; ends the process and its work.
- **Automatic move to the folder's window.** No user action; windows would contend for rows and move sessions users opened on purpose.
- **A new transport between windows.** Duplicates the registry and request channel.

## Decision Outcome

Option 1.

- A new request kind `handover` (`{ tabId, incarnation, binding }`, addressed to the claim holder's id) is **taken up** by an atomic rename before the holder acts, like `stop`, so a withdrawal and the holder cannot both win and "never seen" (an older build) is distinguishable from "being served". It is answered with the ordinary response; `RefusalReason` gains `not-holder`, `busy`, `terminal` and `unfinished` (a bare refusal means only that the handler failed).
- The holder refuses `stale-build` and a requester that is not another live registry window (a sanity filter, not authentication), then **takes the tab's lifecycle gate, holds it from its first recheck to its last recording, and re-reads under it**: it acts only for the exact run it holds (fresh claim read: holder id, owner generation, `sessionIncarnation`, a live driven host, the row still recording `runIntent: running` and the captured host, the named editor binding), only for a Chat (RPC) host, and only when no stop, close, restart, view switch or other transition is in flight; a failed recheck answers without touching the editor. Kill is not gated (ADR-0060), so a Kill that races the detach is not excluded; the under-gate recheck catches one already recorded.
- The detach is a gated `SessionRuntime` port member (`detach`, in the vscode-free `src/runtime/` layer). Under the hold: the conversation is dropped (the broker connection closes), the window's runtime record, its broker watch and its exit handling end (so nothing can record "OMP ended"), the host-control channel closes with its credentials kept, and a new `SessionIndex.detachLiveClaim`, bound to the exact incarnation and to `runIntent: running`, releases the claim and drops the live entry. After the release and outside the gate, the runtime renders the read-only view itself (a transcript read must not delay the release or hold the gate); the window only notifies, repaints and answers. It writes no `runIntent`, no host change and no `releasedAt`, so nothing in the shared record says the session ended or authorizes a relaunch.
- The broker clears the holder's input ownership only when it processes the unacknowledged close, and an attach does not retry a refused input claim; the adopter therefore retries the plain (non-takeover) input claim a bounded number of times, only from the attach path of a window that holds the session's claim, and re-registers host tools when it gains input; if the retry runs out the session is readable but not writable until that window reloads.
- The requester waits with the stop waiter's classification (not accepted, answered, `silent`), carries no focus plan, and then runs the ordinary open of the row (routing suppressed): admission takes the free claim and reconciles and re-adopts the broker exactly as a window reload does. A mid-turn move is allowed; the process is untouched. A working session is confirmed once on the requester.
- The holder's editor stays as a read-only view with a note; the adopter's controlling binding demotes it.
- A holder reload between the release and the adopter's claim re-adopts the session in the holder through its own restore; the adopter's open then ends as the ordinary conflict.
- Surfaces: the Sessions row menu on rows open in another window, the conflict notice, and the Command Palette.

### Consequences

- Positive: a live session, including one mid-turn, changes windows with no loss of the process; the user is no longer forced to Kill to move; ownership decisions stay where they were (claims and the adopter's admission); old-build holders are reported, not mistaken for slow ones.
- Negative: one more request kind and a holder-side teardown that must stay in step with the runtime's record (a new collaborator added to a window's runtime must be ended by the detach); a short window in which the holder has dropped its connection and not yet released its claim (a failed release leaves the holder with a read-only view and an ordinary open to reconnect); the work a holder's host-tool calls and unacknowledged prompts were doing at that instant fails, as in a reload; Terminal sessions are not movable; a forged request (the live-requester check is a sanity filter) can make a holder release a session it really holds and re-home its host tools, failing one in-flight call (the process is unaffected and the session can be reopened), which is recorded as the worst case for the kind.

### Amendments to other records

ADR-0056's and ADR-0057's lists of request kinds gain `handover` with a pointer here; ADR-0055 gains a note that a move changes the window that serves host tools mid-turn; ADR-0066's port gains `detach`.

### Amendment (2026-10-21): a session has a home window, and a restart returns it there

**Status: accepted after three independent review passes (see "Amendment Review (2026-10-21)" at the end). Design: [A restart returns a running session to its home window](../designs/2026-10-21-restart-returns-the-session-to-its-home-window.md).**

The holder of a Move keeps a read-only editor for the session (above). At the next VS Code start every window that VS Code restores an editor for restores that tab into its recovery cohort, races for the claim and elects its editor controlling, and a restored editor outside the cohort is opened by its own serializer path exactly as a click would. A moved session can therefore come back in the window it was moved away from. The exit message of an unrequested end also promises "restarts the next time VS Code starts", which holds only when some window restores an editor for the row.

- **Decision.** (1) The shared session row records `home`, the window URI (`file:` folder or saved workspace, compared by `windowUriIdentity`) of the window that last became its driver; `null` for a window with no URI and for rows written before this amendment, both meaning "no preference". It is written in the same persist as the host record at every place a window becomes the driver (launch, attach of a surviving host, re-attach of a live draft, native conversation transfer), from the window's URI read at write time. A stop, a close and a crash never clear it. (2) A window is *home* for a row when `home` is `null` or its identity equals the window's. At startup a restored editor of a `running` row for which the window is not home is **not** restored into the cohort and is **not** opened by the serializer path: it shows the saved history read-only with one fixed sentence (below), takes no claim and no controlling election. A row that is not `running`, and a row this window already runs a host for, are unchanged. A click that opens the session in this window is a launch or an attach and makes this window the home; Move to This Window re-homes a live session. (3) `exitOutcome` says "The session restarts when its window's editor is restored at the next VS Code start; Resume starts it now."
- **What does not change.** Claims, admission and process-generation evidence ([ADR-0039](0039-refuse-only-on-a-verified-live-writer-the-extension-owns.md)): a home never admits or refuses a launch and is not evidence of ownership; launch placement by folder ([ADR-0057](0057-start-a-session-in-the-window-that-suits-its-folder.md)); the registry and the request kinds; rows with no editor anywhere stay inert; the catalog version (the field is optional and per-row: [ADR-0034](0034-store-sessions-in-one-profile-catalog.md) run-state merge rules apply to it).
- **Mixed builds.** A build that does not know `home` drops it when it rewrites the row and restores by today's race; the next launch or attach by a build that knows it writes it again.
- **Consequences.** Positive: a moved session stays where the user put it across a full restart; the restart promise is true. Negative: one more field in the shared row; a window whose URI changed is no longer home until the user acts; a session whose home window is not restored is not relaunched by any other window (it was, by whichever window had an editor) until the user clicks it; two windows on the same folder are both home.
- **Alternatives rejected.** Rewording the exit message only (the race remains); a user setting (new surface); recording the home in the host record (cleared by every stop and crash, which is when a restart needs it); asking the home window through the registry (it does not survive a restart); choosing the window by the session's folder (a Move deliberately places a session in a window that may not have the folder, and launches are already placed by folder).
- **Review corrections.** The record that carries the field and its merge rule is [ADR-0034](0034-store-sessions-in-one-profile-catalog.md) (amended the same day): `home` is the fourth field of the run state `settleRunState` settles (the early return for a write that only clears the host of a run takes the committed home; a write that records a new attempt carries its own), so a stale window's unrelated write cannot carry an older home back and undo a Move; that amendment's "no field is added" is superseded for this one optional field. The window becomes the driver in several places (the launch and the attach of a surviving host and the re-attach of a verified live draft in `#openEntry`, and the native conversation transfer); a successor transport in the same editor does not change the driver. The URI is read from the window when the row is written, not from the claim holder's value frozen at activation. The home test lives in `inLocalRecoveryCohort`, so the cohort, the pending `restoring` fact and the gone-record sweep's `ownedHere` follow it, and `openRestoredTabIfUncovered` applies it too. A click on a session another window holds switches to that window (ADR-0056); only Move to This Window takes a live session and so re-homes it, and a click that opens the session in this window is a launch or an attach and so makes this window the home. The read-only sentence is fixed and claims only what is known ("This session belongs to another window. Use Sessions to switch to it, or Move to This Window."). Home is a URI, not a window: two windows that show the same folder or workspace are both home and the claim race still decides between them. **Trade-off:** a crashed `running` row used to be relaunched in whichever restored window had an editor for it; it is now relaunched only by its home window, so when the home window is not restored nobody relaunches it until the user opens it. ADR-0031 (a surviving managed host is re-adopted at startup by its home window) and ADR-0057 (placement across restarts follows the home) carry pointer notes. The exit texts that promise a relaunch (the exit log line, the comments of `recordKillIntent` and `session-kill.ts`, `docs/architecture.md`, the ADR-0034 and ADR-0060 amendments of 2026-10-21) are reworded to "when its home window is restored" with the implementation.
