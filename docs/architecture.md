# Current Architecture

This describes **implemented source**, not completion of the [accepted development design](designs/2026-09-24-omp-vscode-development.md). Chat runs over `omp --mode rpc-ui` ([ADR-0038](decisions/0038-host-chat-over-rpc-ui-on-a-broker-pipe-child.md)); [ADR-0040](decisions/0040-switch-one-editor-between-rpc-chat-and-native-pty.md) restores the unmodified native TUI as another mode of the same editor, with exact old-root exit before transport replacement. Collab, relay, room/link, raw recorder and the Collab-era Agents Hub remain deleted. Separate native Models/Agents settings editors implement the user-requested boundary change of 2026-10-08 without restoring that roster. Source/headless/native-command evidence is distinct from installed-window acceptance.

The implementation has five runtime boundaries:

- **VS Code extension host** (`src/extension.ts`, `src/host/chat-runtime.ts`, `src/host/native-session.ts`, `src/host/rpc-launch.ts`, `src/host/rpc-reconcile.ts`, `src/host/rpc/`, `src/host/pty-client.ts`, `src/views/`): owns the session index/claims, actual Chat or Terminal runtime, editor bindings, launcher, notifications and diagnostics. A Chat runtime holds an `RpcSession` whether or not an editor is open; Terminal holds the managed PTY and authenticated native state observer. It resolves installed OMP per launch without a version gate and starts neither transport directly from the extension host.
- **Detached broker** (`src/broker/pty-broker.ts`, `src/broker/rpc-child.ts`, `src/broker/rpc-ring.ts`): independently surviving authenticated loopback IPC per slot. Kinds are `managed-rpc` (Chat pipe child), `managed-omp` (native TUI PTY), `folder-shell` (separate shell) and `stats-dashboard` (standalone Stats PTY). The runtime/native addon are content-staged outside the installed extension ([ADR-0012](decisions/0012-run-child-process-entries-from-staged-copies.md), [ADR-0032](decisions/0032-prove-the-pty-runtime-with-a-console-child.md)).
- **Managed OMP process**: installed `omp --mode rpc-ui` for Chat or default interactive OMP for Terminal, one extension-owned writer per claimed conversation. `-e`/`--preload` loads process-bound authenticated host control.
- **Session Webview** (`src/webview/`, `src/chat/model.ts`): the same WebviewPanel and immutable editor slot E show the host-owned Chat projection or xterm TerminalPane. Mode navigation belongs to the active OMP editor title; Copy Screen is native Terminal's title overflow action. Neither managed view duplicates these controls or normal live/grid status inside the page ([ADR-0043](decisions/0043-place-session-mode-actions-in-editor-title.md)). Replacing the child renews the document credential, not the editor.
- **Folder-shell Webview** (`src/webview/shell/`): an xterm renderer over a folder shell PTY; a folder's Open Terminal creates a separate shell and recoverable slot, never a second managed OMP writer.
Visible terminal panes check a quiet host every ten seconds with a non-resetting status probe and a four-second response bound. Initial attach and actual stream discontinuities recover through snapshots, never ordinary focus. Silence disables input but preserves the copyable screen; folder shells name the folder's Reconnect Terminal action. This is liveness detection, not a shell bridge or editor-membership recovery protocol: a host-only restart cannot address the old shell page unless it still holds that panel. Reconnect uses attach-only runtime staging and retains the exact broker/slot. Open Terminal deliberately creates another shell; a host-less page close cannot be intercepted.

**Terminal presentation.** Native and folder-shell panes share resource-resolved VS Code terminal settings. The configured terminal family (editor fallback) stays first, followed by common and installed Nerd/symbol families, existing bundled Codicon and monospace. Bounded installed-family discovery does not modify user settings or add a font dependency. Configuration events update/refit existing instances without replacing screens; only the broker-authorized owner resizes. The fitted-grid remainder uses terminal background and native scrollbar chrome is hidden beneath xterm's auto-hiding scrollbar. Both terminal surfaces are headerless and use terminal editor icons, with a Starting status before the first ready state. Grid, input ownership and live shell-cleanup verdicts are display-only tooltip metadata; shell titles remain compact.

**Native start admission.** The host projects an explicit starting flag while a native editor's open or mode request admits a stopped session. Before a broker pipeline exists, attach/probe requests receive that lifecycle projection rather than an unavailable terminal frame. The page keeps Starting visible and hides stopped controls and stale warnings until the attempt completes. Explicit same-mode Terminal opens refresh the authenticated handle and frontend; an exited writer is reconciled before resuming, and an unreachable reopen is reported visibly without launching another writer.
The terminal pipeline belongs to one exact writer. A proved Close or natural process exit disposes it, so a retained editor's next start binds a fresh frontend instead of asking its stopped broker for a screen.

**Shell sizing and retirement.** The app wrapper's full-height flex rules live in the shared terminal stylesheet, so standalone shell documents use the same sizing chain and ResizeObserver refit as session documents. On an authenticated broker's confirmed child exit, the host removes the shell recovery record and broker-slot mapping, then requests authenticated shutdown with `requireStopped: true`, without sending a child stop or signalling a PID. The broker can retire even while its frontend remains attached, so the Processes row disappears on the next visible refresh. The editor keeps its final screen and exited state after broker shutdown; closing it stays silent. Successful Processes stops also retire the recovery record after confirmed child exit, even while the stopped broker is closing. None of this proves escaped descendant commands ended; live or unreachable shells retain their explicit Keep Running / Terminate decision.
An installed isolated-window check (2026-10-08) typed `exit` into a real folder shell and observed its visible Processes row disappear after 2.274 seconds, without Stop or Refresh. The retained editor showed exit code 0 with a copyable screen, and closing it produced no editor or native confirmation. The shell recovery catalog was empty, the exact broker had exited, and the owned test window left no running process. Typecheck and 102 targeted tests passed on that packaged baseline; this check does not prove descendant-tree emptiness or later unrelated changes.
Closing a live folder shell still asks **Keep Running / Terminate**; cancellation never authorizes a stop. Confirmed Terminate uses the authenticated broker to stop its child, requires child absence, then requests `shutdown(requireStopped: true)` before retiring the shell slot and mapping. A Windows `tree: unknown` / `verified: false` verdict describes descendant completeness, not a live shell or failed stop, and remains in Output without a warning after successful child exit and broker shutdown. Genuine stop/shutdown failures retain recovery metadata, warn with the Processes Stop action, and refresh the child facts without pretending the closed editor is still open.
Broker shutdown first waits until replies for previously accepted stop requests have been queued, including a stop refusal. A child-exit notification can start natural retirement while the explicit stop is still collecting its kernel verdict; that concurrent shutdown must not close the endpoint before the stop caller receives its correlated result. Read-only requests remain independent, and no tree or child-absence proof is promoted by this ordering.
The same window also serializes natural folder-shell metadata retirement and shutdown with the entire Processes Stop → shutdown sequence on the index's existing per-slot lifecycle gate. A confirmed explicit stop cancels its captured queued natural watcher before releasing that gate; its authenticated shutdown remains the authority, not a closed socket or broker absence. Ordinary editor teardown only unsubscribes future events and preserves retirement already queued for a confirmed natural exit. Session stop routes and read-only Processes observations keep their existing behavior.
Installed isolated acceptance also exercised editor-close Terminate on an idle shell and on a shell running `ping -t localhost`. Both produced truthful child-absent / tree-unknown diagnostics followed by authenticated broker shutdown, empty recovery mappings and an automatically disappearing Processes row without a warning or manual Stop/Refresh. The observed original shell and broker generations were absent; the ping process was absent in that case, not a general descendant-tree guarantee. Natural-exit screen retention and silent close still passed, with 110 targeted tests and typecheck on the same packaged snapshot. Cleanup left no owned test processes running.
A later frozen-snapshot isolated acceptance passed typecheck, build and 164 targeted tests, with 56 installed runtime/helper payload files matching the packaged build. Its real modern NodeService extension host armed the staged owner monitor against the independently read owning-main kernel generation. One actual Processes Stop with the shell editor open received the validated child-absent verdict and authenticated `requireStopped` shutdown acknowledgement, removed the row and recovery mappings, and retained the exited screen without a false warning. The acknowledgement was established by the guarded host success output and its authenticated helper response checks, not inferred from socket closure. A fresh shell from the same artifact then exited with code 0, retired automatically without Stop/Refresh, kept its copyable screen and closed silently. Cleanup reconciled all 20 observed owned process generations, the isolated window and its listener; no main-profile operation or PID signal was used. This establishes installed arming and these lifecycle paths, not real last-window grace expiry, cross-window concurrency or an empty descendant tree.

Live VS Code theme changes are observed on the renderer's ancestors. The shared renderer re-reads the palette and assigns `terminal.options.theme`, updating the host remainder background in the same callback without recreating xterm or changing fonts, grid, input ownership or screen contents. Its observer disconnects on disposal.

**Terminal cell widths.** The OMP TUI counts Unicode 11+ widths (`Bun.stringWidth`), so the Webview renderer and the broker's headless screen mirror both run xterm.js's Unicode 11 table (`@xterm/addon-unicode11`, `webview/lib/terminal-unicode.ts`); wide emoji and CJK therefore advance the cursor by the two cells the TUI addressed, in the live stream and in reattach snapshots. Grapheme-cluster sequences (VS16 symbols, ZWJ families, skin-tone modifiers) still differ; see the [native terminal design](designs/2026-10-03-native-terminal-ux.md).

**Terminal file links.** Native and folder-shell panes activate OSC 8 through the shared xterm handler and detect plain relative/absolute paths with a host-validated link provider (wrapped and wide cells preserved). Hover underlines with a pointer and a plain-click hint. The host resolves against the current session/folder cwd, rechecks existing regular local files at activation, and opens non-preview editor tabs at one-based line/column positions. Only `file:` and the narrowly decoded OMP `vscode://file` form map to local files; other custom schemes/network files are refused. HTTP(S) retains the extension-owned browser confirmation. Cwd, route and document authority remain host-owned; PTY environment is unchanged. Existing broker serialization omits OSC 8 targets on attach/reopen snapshots: visible resolvable OMP path labels (compact Read and path/position text) remain clickable via the plain provider, but arbitrary/abbreviated labels without a resolvable path cannot recover their snapshot-only target. New live output retains OSC 8 normally.

Terminal link opening goes through `vscode.open` (new non-preview tab; text at its line/column, images/PDFs/binaries in their viewer) and failed activations show a short warning. The link provider caches host validations per text (30 s hits, 5 s misses), answers cached rows synchronously and shares in-flight requests, so a repainting TUI cannot flicker or drop the hovered link; `~/` paths resolve against the user's home. See the [native terminal design](designs/2026-10-03-native-terminal-ux.md).

**Chat file links.** The Chat reuses the Terminal mode's detector, validation cache and host open path (one convention). `src/webview/lib/chat-file-links.ts` finds candidate references (`detectChatFileLinks`: the Terminal detector plus `@path [lines a-b]` mentions, a path-shaped filter, and Markdown destinations that are a path or `file:` URL); `ChatFileLinks` asks the host through the same `omp:terminal-link-validate` / `omp:terminal-link-open` pair, with `folders: true` so a folder is a valid target too, through the shared `ValidationCache` (30 s hits, 5 s misses, one request per target, at most eight in flight). Terminal links send no `folders` and stay files only. `FileLinks.tsx` wraps a reference in a focusable `role="link"` span only after the host proves an existing regular file or folder; text, selection and copy are never altered and nothing is linked without the page's provider (detail tabs have none). Linked: assistant and user Markdown prose, bold/italic/strike text, inline code spans, Markdown links, tool-row read/edit targets (a read's selector line, an edit's first changed line), section titles, grep/find line numbers and glob entries. Fenced code blocks stay text. The host accepts the pair in Chat mode too (panel and bridge routes), resolves against the session's cwd, and still refuses everything but an existing local file or folder; the position grammar is `:12`, `:12:3`, `:12-30`, `:L12`, `#L12`, `#L12-34`, `#L12C3` and `file:` fragments (the start of a range is revealed). Activation (`handleTerminalLink`, `src/host/terminal-links.ts`): a click or Enter opens a file in a non-preview tab; Ctrl+Click or Ctrl+Enter (`action: "reveal"`) only selects it in VS Code's Explorer, without opening it, through the workbench's `revealInExplorer` command, which shows the Explorer; Ctrl+Shift+Click (`action: "os"`) starts `explorer.exe /select,"<path>"` (`revealPathInOs`), opening the containing folder in File Explorer with the item selected; VS Code's `revealFileInOS` is not used because, while its Explorer list has focus, it reveals the Explorer's selection instead of its argument. A folder has no tab, so a plain or Ctrl click reveals it in the Explorer. The Explorer shows only paths inside an open workspace folder (`workspace.getWorkspaceFolder`); for anything else a warning points to Ctrl+Shift+Click. Extensions have no API to select an Explorer row without showing the Explorer, so revealing switches the side bar. The link's right-click menu offers the same three actions through VS Code's `webview/context` menu: the span carries `data-vscode-context` (`fileLinkMenuContext`: `webviewSection: "ompFileLink"` and the target), VS Code turns its keys into context keys for the menu's `when` clauses and passes the object with the panel's viewType as `webview` to `omp.fileLink.open` / `reveal` / `revealInOs`; `openFileLinkFromMenu` checks the object (`fileLinkMenuTarget`), finds the editor with that viewType and sends the same `omp:terminal-link-open` request a click sends. VS Code's own Cut/Copy/Paste stay below them. A web link's right-click menu (`webLinkMenuContext`, `webviewSection: "ompWebLink"`, in a Chat and in the TODO/Agents detail tabs) offers **Open in Editor** and **Open in Browser** (`omp.webLink.openInEditor` / `openInBrowser`); the command re-validates the URL with `webLinkUrl` (`webLinkMenuUrl`) and opens it through the same `openPageWebLink` a click uses, needing no editor lookup because a web link does not depend on the session's cwd. The Chat prompt's `file-links` rule (below) asks the model to write paths in the form this detector links. Verified against the installed OMP 18.6.3: its TUI links only through OSC 8 — `fileHyperlink` (`pi-tui/src/render/hyperlink.ts`: `vscode://file/<path>:<line>:<col>` in VS Code terminals, else a plain `file:` URI) on tool paths (read, edit, write, grep, find, ast-grep/ast-edit), skill and image chips and the status-line folder, and `resolveMarkdownLinkTargets` (`pi-coding-agent/src/internal-urls/hyperlink-targets.ts`) for model-authored Markdown links (relative to the session cwd, existing files or directories, `file:` URLs, `#`/`?` suffix kept). It does not link bare paths, inline code, fenced code or `@` mentions itself; those are linked here as the VS Code terminal's text detection links them in Terminal mode. Not supported: internal-URL schemes (`local://`, `agent://`, …), which the TUI resolves but the host open path refuses, and bare `file://` URLs in prose (the TUI does not link those either).

**Chat code-symbol links** (`src/webview/code-symbols.ts`, `src/host/symbol-links.ts`, `src/webview/lib/chat-symbol-links.ts`, `CodeSymbolSpan` in `FileLinks.tsx`; [design](designs/2026-10-10-code-symbol-links.md), [ADR-0058](decisions/0058-resolve-chat-code-symbols-in-the-host-window-through-workspace-symbol-providers.md)). An inline code span of **assistant reply text** (`SymbolLinksEligibleContext`, set by `AssistantContentView`, cleared in thinking) that is not a link and parses as a symbol (`parseCodeSymbol`: one to four ASCII identifiers joined by `.`, after removing generic arguments, `[]`/`?` suffixes, one call argument list and a whole-span `[Attribute]` wrapper; no keyword, no last name under three characters, no bare all-lowercase word unless called) is offered to the host once it has been on screen and after the 200 ms streaming settle. A span that is also path-shaped (`A.Bcd`) waits for the file validation to refuse it first. `ChatSymbolLinks` batches unique tokens (40 ms window, 16 per `omp:terminal-link-symbols` request, two requests in flight, 64 unsettled tokens in all, retries included; request ids are document-wide), caches answers (found 30 s, answered none 10 s) and retries an `unavailable` token after 5 s and again after 20 s, then rests it for 60 s. The host (`handleSymbolLinks` in the `handleTerminalGuestMessage` link case, both panel route and bridge stream operation `terminal-link-symbols`, same document/session/cwd currency check as validate/open) parses each token again and asks `SymbolLinkResolver`, whose `SymbolSource` is `vscode.executeWorkspaceSymbolProvider` converted by `symbolEntry` (only `file` URIs have a path; a location with no range has no position). It queries the last segment (and once more the full dotted text when a dotted name found nothing), keeps entries inside the session cwd or an open workspace folder that contains it, matches the exact name (`NameAttribute` too for an attribute; the entry's container must end with a dotted name's preceding segments) with a kind matrix, counts distinct declaration locations, groups them into symbols (the partial parts of a type and the overloads of a member in one container are one symbol, opened at the type's own file or the first location by path and line) and answers `found` only for one symbol (same-named types in different containers: `ambiguous` with the symbol count, unless exactly one lies inside the cwd; the page links an ambiguous token to the workspace symbol search through `omp:terminal-link-open` with `search: true`, which the host re-parses and runs as `workbench.action.quickOpen` with `#<last segment>`, never to a guessed definition; a bare capitalized name prefers type-like entries over members), logging one line per lookup (entry counts, matching locations, verdict, milliseconds). `unavailable` (an error, an invalidated lookup, an unmatchable entry, a cut answer) is never cached; `pending` (provider not ready: no query of the window has returned a symbol yet, so an empty answer is not a miss; or queue full or timeout) is no verdict and never cached either: the host probes a not-ready provider with a canary query (2 s doubling to 30 s, ten minutes), and when it becomes ready or its queue drains it sends `omp:terminal-link-symbols-retry` to every page that asked, whose spans without an answer then ask again. Window-wide bounds: four provider calls in flight, a slot released only when the provider's own call settles, 64 waiting queries that give up after the query timeout, overflow refused at once, 8 s per query, 15 s per batch, 1,024 cached answers (found 60 s, none 15 s); a generation counter, bumped by a file-system watcher, saves, renames and workspace-folder changes, fences cached, in-flight and queued work, and a batch whose generation moved answers every token `unavailable`. The reply carries `path:line:column` (relative to the cwd inside it) and a click is the ordinary `omp:terminal-link-open`, re-validated by the host. `omp.linkCodeSymbols` (default on) turns it off: the host answers `disabled` and the page stops asking for 30 s. Limit: a workspace symbol search is ranked and may be capped (providers may cap results), not an exhaustive index, so "exactly one" means one among the entries the provider returned, and an answer Desk itself cuts (over 1,000 entries) never gives a unique match; unsaved edits reach the provider but not the invalidation until a save.

**Chat prompt** (`src/omp/chat-prompt.ts`). Chat features that depend on how the model formats a reply say so in one short section appended to the system prompt: a fixed preamble ("The user reads your replies in OMP Desk, a chat panel in VS Code") and the list `CHAT_PROMPT_INJECTIONS`, one rule per feature (today `file-links`, and `code-links`, which asks the model to link every code symbol at each mention, tables and lists included, as a Markdown link to the definition line it has seen in a read or search, `` [`App.start`](src/app.ts:12) ``, or to the file alone when that is all it knows, `` [`Parser`](src/parse.ts) ``, to leave plain only a symbol it has not located, and never to guess a line or search just for one; `Markdown.tsx` renders inline code in a link label as code and links it once the host proves the file, the same path as any Markdown file link; a symbol the model leaves plain is the host's to link, see **Chat code-symbol links**). The `-e` host-control module calls `registerChatPrompt`, whose `before_agent_start` handler returns the system prompt with the section appended, only for an RPC main session (`ctx.mode === "rpc"`, `ctx.agent.kind === "main"`): the native TUI renders replies itself, and a subagent answers its parent. Like Rewind it needs only the module loaded with a non-absent bootstrap. The text is constant, so the provider's cache prefix stays stable. Every rule costs tokens on every request, so the module header sets the guideline for adding one (one imperative rule, an inline example instead of a description, nothing Markdown already implies, no runtime values) and `chat-prompt.test.ts` holds each rule to 280 characters and the section to 1,500. Observed with installed OMP 18.8.5 in `--mode rpc`: the model quoted the appended section and followed it.

**Chat web links.** Web links follow the same convention and request pair, without a validation round trip. `webLinkUrl` (`src/webview/terminal-links.ts`) accepts only an absolute `http:`/`https:` URL with a host and returns its normalized form; `detectWebLinks` (`src/webview/lib/chat-web-links.ts`) finds bare URLs in prose, starting only at a word boundary and stopping before trailing sentence punctuation and closing brackets the URL never opened (GitHub's autolink rule). `Markdown.tsx` links `[label](https://…)`, `<https://…>` autolinks and bare URLs (a bare URL is one inline token, so `_`/`*` inside it never start emphasis); inline and fenced code stay text, and any other destination (`javascript:`, `data:`, `command:`, `mailto:`, …) keeps its label and loses its URL. `WebLinks.tsx` renders a focusable `role="link"` span, never an `<a href>`, with the tooltip "Open in editor · Ctrl+Click to open in browser"; a click or Enter posts `omp:terminal-link-open` with `mode: "editor"`, Ctrl+Click or Ctrl+Enter with `mode: "external"`, and the handler prevents the default action and stops propagation so the page never navigates and Ctrl+Enter never reaches the Send keybinding. Its provider wraps both the session page and the TODO/Agents detail documents, so web links work in the transcript, tool output (web-search and GitHub sources included) and the detail tabs. The wire accepts `mode` only on an open request. The host re-validates with `webLinkUrl` before anything opens (`handleTerminalLink`, and `DetailTabs` for detail documents, which accept no other link request) and opens through `openWebLink` (`src/host/terminal-links.ts`): the built-in Simple Browser extension's `simpleBrowser.api.open` for an editor tab, and `vscode.env.openExternal` for the browser; only the origin is logged. In the installed VS Code 1.141 the Simple Browser command hands the URL to VS Code's integrated browser (an editor tab with its own address bar), and `openExternal` first shows VS Code's own "Do you want Code to open the external website?" prompt for a domain the user has not trusted. Terminal mode uses the same path: an OSC 8 `http(s)` link OMP draws (Markdown links and autolinks in replies, login and pull-request links) opens in an editor tab on a click and in the browser on Ctrl+Click, with the same tooltip; xterm has no plain-text URL detector here, so a URL OMP prints without OSC 8 is not a link in Terminal.

**Terminal streams and input.** Each pipeline has a fresh random presentation identity, distinct from the unchanged authenticated PTY identity. Healthy probes preserve output, selection and scrollback; ordered missing bytes or another presentation trigger explicit snapshot recovery. Only snapshot-follows adopts a new stream, and only the snapshot resets xterm. Bounded target-frontend buffering maps the broker's UTF-16 snapshot cut to dense output sequences so concurrent post-cut Unicode is not lost. Broker claim/owner events, not DOM focus, authorize input; visible eligible owners retain permission through blur, while hidden/passive/disposed panes release it. Genuine activation/click intent alone permits takeover, including an already-focused textarea click ([ADR-0044](decisions/0044-resynchronize-on-stream-discontinuity-and-retain-broker-ownership.md)). Native Shift+Enter sends OMP's multiline sequence. Single-use activation tokens restore keyboard focus on actual activation/document readiness/window-focus return, never model/probe ticks. Host clipboard copying admits stopped/passive screen reads but requires the latest current-document/generation-bound user nonce; oversized serialized replies refuse rather than truncate.

**Terminal screen restore.** The broker serializes up to about a million characters of screen and scrollback, but one `omp:terminal-snapshot` message carries at most 131,070 decoded bytes. A longer retained screen is trimmed by the host (`fitTerminalSnapshot`): whole oldest lines are dropped, attributes are reset at the cut and the visible rows, cursor and modes (or an alternate screen) are never cut, so a long session reattaches with its recent screen instead of failing. Output that outruns a reading triggers a fresh reading (three attempts) instead of an error; only a visible screen that alone exceeds one frame, or output that never lets a reading settle, shows the plain sentence "The earlier screen of this terminal … new output will still appear".

**Terminal repaint after restore.** A restored screen is replayed into an xterm that must show the grid the PTY really has: the owning pane renders at its own fit (a pane that has not yet been granted input first shows the host's grid, and is refitted once it owns), otherwise OMP's differential renderer draws for one grid while the emulator shows another, leaving stale status lines and a cursor one row off. After a snapshot reaches a visible owning native OMP pane, the host nudges the PTY one column narrower and back once (`TerminalPipeline` `redrawAfterRestore`, native `managed-omp` sessions only; shells are not nudged), so OMP repaints its whole screen from its own state. A surviving broker of an older build is detected and left running (it owns the PTY, and restarting it would end the OMP process); the repaint heals what its older mirror gets wrong. See the [native terminal design](designs/2026-10-03-native-terminal-ux.md).

**Terminal resize after reload.** A revived editor is laid out over several frames, so its first fit (the one sent with `omp:terminal-attach`) is a row or two off the settled one. The owning pane therefore reports its fit to the host only after it has held still (`RESIZE_SETTLE_MS`) and restates it whenever it regains input or asks for a screen again; the host never applies the attach-time fit, runs every grid write (page resizes and the repaint nudge) through one queue, nudges the grid the broker reports at that moment, and sends nothing for a resize to the grid the broker already has. Without this the PTY went 46 -> 44 -> 45 -> 46 rows within 60 ms of each reload and OMP repainted at every value. See the [native terminal design](designs/2026-10-03-native-terminal-ux.md).

Authority-fence changes publish terminal state immediately, independently of the queued broker ownership work. Even a fence that is set and lifted before that queue runs must produce the input-loss and restoration edges: the page clears its last-reported fit on loss and restates the settled grid on restoration. This prevents a resize refused during role reconciliation from remaining cached as delivered when the broker owner itself never changed. Read-only and hidden panes still render the host's grid and cannot resize it.

**Snapshot cursor.** The serialized screen is given an absolute cursor position (`placeSnapshotCursor`, from the mirror's own cursor) after everything the serializer wrote: `SerializeAddon` returns the cursor with relative moves, and after a full-width last row (OMP's footer) xterm.js's cursor-backward starts from the last column, so the restored cursor landed one column left of the prompt's until OMP next moved it.

**Redraw Terminal on demand.** `OMP: Redraw Terminal` (command palette, the editor title overflow beside **Copy screen**, and Ctrl+Alt+Shift+R / Cmd+Alt+Shift+R, a chord no OMP or VS Code default binds) runs the same one-column nudge for the active native OMP pane (`TerminalPipeline.redrawNow`). It is for the moments OMP's own differential renderer and the terminal disagree about rows for a reason outside this extension (the program's output itself overwrites earlier rows); the program repaints from its own state, nothing is hidden or rewritten, and a folder shell, a hidden pane or a pane that does not own input is refused with a message rather than nudged. The terminal swallows the chord so the program never receives it (Ctrl+Shift+L would reach OMP as `^L`, its live-mode key).

**Workbench keys from anywhere.** Ctrl+Shift+Q runs `omp.focusComposer` with no `when` clause: the active session editor, else the one showing in the chat group, else the index's active tab, is revived if VS Code has not handed its panel over yet, revealed with focus, and a Chat page gets the `focus-composer` panel action; with no session editor it opens the OMP Desk side bar (`workbench.view.extension.omp`). Inside a Chat, Ctrl+Shift+L keeps running the same command. Ctrl+Shift+M runs `omp.moveFileToNewWindow`, which takes every tab of the group next to the chat (`filesGroupColumn`: the active group without a session editor, else the leftmost one, never the file window's own group) into the file window: one auxiliary window, kept on top, that every file opened from a Chat link joins until it is closed (see the chat column below). It is a toggle: while that window exists, the command returns its tabs (`returnFilesFromWindow`) to the existing files group, else to a new group beside the chat group, and forgets the window. It replaces VS Code's default Ctrl+Shift+M (Problems), and Cycle Model has no default key. Between two extensions VS Code picks by load order, so a keymap extension binding the chord under `editorTextFocus` (IntelliJ IDEA Keybindings: Move Caret to Matching Brace) can win in text editors; only a user keybinding outranks it. `contributes.configurationDefaults` lists both commands in `terminal.integrated.commandsToSkipShell`, so the integrated terminal passes the keys to the workbench instead of the shell; a user value for that setting replaces the contributed default and must list the commands itself. A Terminal-mode pane claims both chords, and Ctrl+Alt+Q, like Redraw (`isTerminalWorkbenchChord`): they reach the workbench and are never encoded for the program, which would read them as Ctrl+Q (OMP's follow-up key on Windows) and Ctrl+M (a carriage return).

**Go to Session.** Ctrl+Alt+Q (`cmd+alt+q` on macOS) runs `omp.goToSession` from anywhere, with no `when` clause and listed in `commandsToSkipShell` like the other workbench keys. It shows a `showQuickPick` over `SessionTreeProvider.listedSessions()`: the rows the flat Sessions list is built from, in its order (`src/views/session-order.ts`), computed for either grouping, each with its folder name (`flatFolderLabels`) and the status text the row carries (including `Unread ·`). The key is `ctrl+alt+q` because Ctrl+Shift+Q already focuses the composer, no VS Code default and no IntelliJ IDEA Keybindings entry uses the chord, and it needs no `when` clause. On a layout whose AltGr is Ctrl+Alt the chord can type a character first (German AltGr+Q is `@`); rebind `omp.goToSession` there.

**Terminal writes, resets and resizes stay in arrival order.** xterm.js parses what it is given later and in slices; a hidden or minimized window can sit on a large unparsed backlog. The Webview's renderer therefore routes every write, screen reset and refit through `OrderedTerminalSurface` (`src/webview/lib/terminal-ordered-surface.ts`): a reset or resize waits for every earlier byte to be parsed and later bytes wait for it, so a restored screen replaces the old one instead of being parsed after it, and bytes drawn for one grid are never parsed at another. A hidden or zero-sized container is not fitted at all. See the [native terminal design](designs/2026-10-03-native-terminal-ux.md).

**Terminal selection copy.** Native and folder-shell xterm panes copy like the VS Code integrated terminal: Ctrl+C/Ctrl+Insert with a non-empty selection and Ctrl+Shift+C write it to the clipboard from the Webview on the user's keystroke, clear the selection after a successful write and never send `^C`. Without a selection Ctrl+C is the interrupt byte in a folder shell only; a native OMP session never sends Ctrl+C (the key is consumed on every layout, matched by letter or physical `KeyC`, and a stray `^C` in input is dropped). Paste stays on the browser paste event. See the [native terminal design](designs/2026-10-03-native-terminal-ux.md).

**Broker `managed-rpc` kind.** `PtyKind` is `"managed-rpc" | "managed-omp" | "folder-shell" | "stats-dashboard"`. `PTY_PROTOCOL_VERSION` and `PTY_RUNTIME_VERSION` were **not** bumped: the `rpc-*` frames are additive and gated by the record's kind (a `managed-rpc` broker refuses terminal-only frames and other brokers refuse `rpc-*` with `wrong-kind`), so a surviving Collab-era or folder-shell broker of the previous build stays reachable for probing, adoption and stop. `src/broker/rpc-child.ts` spawns the child with pipes (no node-pty and no screen model are loaded for this kind); the broker, not any client, negotiates rpc protocol 2 after the `ready` frame, swallows that response, and returns `ready` and the negotiated version on every attach. stdout is drained continuously into a sequence-numbered ring (`RpcLineRing`, 4 MiB / 2048 lines) whose retention is deliberately shallow: `message_update` frames are superseded per `messageId` and dropped at `message_end`, unanswered `extension_ui_request` dialogs are pinned until answered or cancelled, open `message_start`/`tool_execution_start` lines up to 64 KiB are pinned until their end frame, `response` and `rpc_chunk` frames are not retained (except a small `vsc:` response), and a `pinnedOverflow` flag is reported instead of ever evicting a dialog. The ring only lets a (re)attaching client rebuild the in-flight turn; it is not a durability store. Lines cross the authenticated link as base64 fragments (≤ 96 KiB raw), replay is paced by the connection's send-queue bound and only the input owner may write. `RpcHandle` (`src/host/rpc-handle.ts`, on the shared `BrokerHandle`) implements the `RpcChannel` port an `RpcSession` uses. **Stop** closes the child's stdin (OMP aborts the turn, persists it, appends `session_exit` and exits); a force stop kills the retained child handle, never a numeric pid, and its whole-tree result stays `unknown` unless proven (ADR-0029). The broker never auto-stops a `managed-rpc` child: an extension-host or VS Code restart leaves it running, and only a folder shell has an owner-exit grace.

**Autonomous Chat exits.** The managed-RPC pipe child strips terminal escape sequences across stderr chunks and retains only the last 4 KiB of UTF-8 plain text, draining both output pipes before publishing exit (under the existing finite drain deadline). Exited broker status optionally includes `stderrTail`; it is validated and survives attach, so a client that missed streamed `rpc-stderr` frames still gets the final diagnostic. The field is additive, absent on native Terminal children, and does not change launches or retry policy. `RpcHandle` suppresses autonomous-exit notification for its own requested Stop; `RpcSession` carries `{exitCode, stderr}` as an optional `exitReason` in Chat state and snapshots. The page renders it as text, not HTML, and the extension logs it to OMP Desk output. Other failures have no special action; user Stop/Close retains ordinary stopped presentation. Resume replaces the runtime and diagnostic in the same tab through existing launch admission.

**Launch.** `rpcOmpLaunchSpec` (`src/host/rpc-launch.ts`) builds Bun control flags, launcher prefix, `--mode rpc-ui --cwd <dir> --profile <explicit profile> [--session <exact file>] -e <host-control module>`. `nativeOmpLaunchSpec` (`src/host/native-session.ts`) uses the same resolver/bootstrap, without `--mode`, and `--resume <exact file>` for a native resume. **Same-editor mode replacement.** The profile default is read from `globalState` (`omp.session.defaultMode`, initially Chat) only when opening/creating a tab, including reopening a closed editor whose writer still runs. Ordinary Open/click on an existing tab reveals its actual mode; explicit Open in Chat/Terminal switches that tab. Restore chooses live host transport, saved slot mode, then default, independently of the current default when actual/saved mode is known. Attachment persists the actual transport mode to the durable editor binding rather than leaving a provisional default there. Stop/start actions operate on that actual transport. The lifecycle fences Chat mutations/UI responses and terminal input before inspecting state. It captures exact E/T/root/file/id/epoch under the per-row gate, releases the gate for busy consent, then revalidates. RPC uses fresh `isSettled` plus compaction and rechecks before stdin EOF. Native uses public idle/pending/async-job facts; unknown is busy. Guarded SDK abort/shutdown is not ConPTY close: accepted shutdown is irreversible and may be deferred, so timeout keeps Stopping and never schedules a successor. Both require matched broker exit plus exact creation-time absence before replacement; Windows tree emptiness is not claimed.

Content without a durable file is refused before stopping. Only a confirmed no-turn fileless draft may reset its session identity while preserving row/ordinal/editor/claim; missing durable rows never become empty. A successful replacement keeps the claim and run intent through a durably recorded successor mode/attempt; failure records stopped and releases. Bounded Chat draft text survives on the host until another Chat document is ready, never enters Terminal or saved editor state, and is discarded on dispose/conversation change; attachment loss is disclosed.

**Native autonomous identity.** `/resume`, `/new`, branch/tree and rollback remain unmodified and best effort. Authenticated current file/id observations may move the same E/root from A to B: claim B first, atomically publish row/binding/broker mapping, then release A. A stays stopped; a verified rival demotes only the newcomer. No idle/early event is called a settled identity witness. **`RpcSession` and history** (`src/host/rpc/session.ts`, `history-reader.ts`, `frames.ts`, `protocol.ts`). The session is a state machine `starting → attaching → resyncing → live` (and `stopped`, `failed(code)`) over an `RpcChannel`. Every attach first paints JSONL history through the shared density-independent 100-canonical-card admission rule; each visible non-tool and individually owned call costs one, hidden/internal entries and already-owned results cost zero. Older cards are read by byte range. Replay folds into a shadow model, identity is proved with `get_state`, and `get_entries {since: <disk cursor>}` supplies the durable delta before authoritative publication. Ended live rows retain aliases and unmatched/unsaved notices through durable reconciliation. Mutations retain exactly-once `vsc:` ids and lost-prompt reporting. Identity-changing slash builtins remain refused, including the installed lifecycle operations `wt` and `worktree` and their advertised aliases. One `get_available_commands` query follows verified live attach; a pushed `available_commands_update` advancing the catalogue revision supersedes an older query response. There are no keystroke queries or new discovery processes for stopped/passive history. Protocol mismatch retains disk history and fixed refusal codes. `readViewOnlySnapshot` never claims, launches or appends history.
History reads resolve OMP's externalized images (`blob:sha256:<hash>` references in the JSONL, bytes in `<agent dir>/blobs/`) through `src/host/rpc/history-blobs.ts` before the shared parser runs; an unresolved reference renders an explicit “Image not available in saved history” placeholder instead of a broken image.

**Leaf moves and branches (2026-10-09, [design](designs/2026-10-09-chat-rewind.md), [ADR-0051](decisions/0051-rewind-chat-in-place-through-a-desk-registered-omp-command.md)).** The active branch can move without an append from this host: OMP's own turn recovery, or a Rewind. `#reconcileEntries` therefore rebuilds the window at the live leaf when a `get_entries {since}` delta is empty but reports another `leafId`, or does not extend the known leaf (the parent of its branch root is not the model's leaf). `#rebuild(live)` refreshes the `HistoryReader` and takes `snapshot(rows, leafId)`, the tail window of the path to that leaf, only when the disk holds exactly what the process just reported (its last complete entry is the live `lastId` and the live leaf is indexed), because OMP's write queue can trail the process. Otherwise it looks once more after 150 ms (`REBUILD_RETRY_MS`), then falls back to a full `get_entries`, which `#applyFull` trims to the same tail window (`transcriptWindow`) with an older-row count. The cursor becomes the live `lastId`. `HistoryReader.loadOlder(beforeId)` walks the ancestors of `beforeId`, so paging up follows the active branch even when its leaf is not the file's last line. The model's `branches` (`computeBranchPoints` over the reader's index or the full read, with first-prompt previews from the reader) list only divergences the user made: an off-path subtree whose first message, past metadata and markers, is a user prompt. OMP's retry and checkpoint pruning leaves subtrees rooted at an assistant or tool-result message, which are not listed. A branch's switch target is its newest user, assistant or tool-result message. A point is anchored at the nearest message at or before the divergence on the path, because a rewind usually lands below OMP's `model_usage` bookkeeping, which Desk does not load; points sharing an anchor merge. A reattach replays the broker's ring, which can hold turns of a branch the user rewound away from; on the first unmatched reconcile pass of a settled session with branches, one full `get_entries` drops the pending rows saved off the active path (`dropPendingSavedElsewhere`) instead of flagging them *not yet saved*.

**In-place navigation** (`RpcSession.navigate`, `src/omp/navigate-command.ts`, `src/chat/rewind.ts`; ADR-0051). The `-e` host-control module calls `registerNavigateCommand`, which registers the extension command `omp-desk-navigate` at the first `session_start` whose `ctx.mode` is `rpc` (the native TUI loads the same module and lists nothing). It needs only that module loaded with a non-absent bootstrap, not the host-control pipe. `RpcSession.navigate` runs once per 32-hex `requestId`. `#navigationRefusal` first refuses on host-known state: a fence or turn, compaction, a dialog, queued input, an unsettled or async-paused session, an unconfirmed prompt or unreconciled pending row, a catalogue without the command at `source: "extension"`, a leaf other than `expectedLeafId` (past which only OMP's `model_usage` bookkeeping may follow, `leafReaches`), or a target that is not a durable user prompt (rewind), the Undo offer's `from` (`undoOffer`) or a listed branch tip (switch). The request then goes out as `/omp-desk-navigate <json>` (`encodeNavigateCommand`, a compare-and-swap of session id, expected leaf and target) through an ordinary `prompt` without `streamingBehavior`. Inside OMP, `runNavigateCommand` re-checks session, leaf (with the same `leafReaches` rule) and target, calls `navigateTree`, and appends one `custom` entry `omp-desk/navigation` `{v, requestId, kind, from, target, to, summarized, raced?}` whenever the leaf moved, taking `from` and `to` from OMP's `session_tree` event and flagging `raced` when they differ from what was checked or no event was observed. Refusals throw `omp-desk-navigate:<code>`, which OMP reports as an `extension_error` with `extensionPath` `command:omp-desk-navigate`. `#onFrame` keeps that command's `prompt_result` and coded errors out of the transcript; `agentInvoked: true` in its acknowledgement or result, or the command text echoed as a user message, means it reached the model, which is aborted. `#runReconcile` defers while the command runs; afterwards one re-sync runs through the same serializer, and the marker with this `requestId` on the durable active path (the leaf or an ancestor) is the only proof of success. The outcome carries `summarized`, `raced` and, for a rewind, the target prompt as a draft taken from the entry the host holds, with `blob:` images resolved. A command whose answer never came (30 s, 180 s when summarizing) or was lost leaves `#navigationFence`: every mutation is refused as busy until its late `prompt_result`, its marker on the path or the end of this `RpcSession` (process exit, or a reattach after a window reload), and the page is told `unconfirmed`. `ChatRuntime.navigate` answers `omp:chat-navigate-result` to the asking page, or, for **OMP: Rewind Conversation…** (`omp.rewindConversation`, no origin), to every writable route, refusing `not-owner` when there is none. Read-only, view-only and not-live routes are refused before the session is asked, and a draft too large for its route is resent without images, counted as unavailable. `/rewind` and `/branch` typed alone open the page's Rewind; with arguments they are refused with `REWIND_ARGUMENTS_SENTENCE`. Files are never restored; the page and the QuickPick name the files changed after the target, including the paths of OMP's hashline `edit` (`toolPresentation` reads its `[PATH#TAG]` headers and the result's `path`).

**Lost-connection recovery and package drift** (`src/host/rpc/session.ts`, `src/host/package-drift.ts`, `src/host/pty-ipc.ts`). A session never stays frozen on a connection that stopped delivering. A watchdog armed while `live` probes a silent connection with `get_state` (after 45 s of silence while a turn shows as working, 90 s while idle); a probe that times out replaces the connection through the ordinary reattach, and a probe that answers “idle” while the page shows working clears the stale working state (`recovery` output, reason `probe-timeout` / `stale-working`). A frame that cannot be folded, or a frame listener that throws in `pty-ipc` (which now closes the connection instead of abandoning the buffered lines behind it), schedules an authoritative resync/reattach (`frame-failure`). Entering `failed` clears working, async-paused and active-tool state, and a *recoverable* failure (`attach-failed`, `state-failed`, `ready-timeout`, `protocol-error`, `write-refused`; `isRecoverableRpcFailure`) is retried automatically with growing delays (3 s, 10 s, 30 s, then 60 s); the failed banner offers **Reconnect** (`omp:chat-reconnect` → `RpcSession.reconnect()`), which reattaches to the same process and proves identity again, and is refused for identity divergence or an exited process. Drafts live in the page and are untouched by any of this.

**Unanswered native dispatcher recovery.** `RpcSession.nativeStateUnanswered` remembers an unconfirmed state read for one native session; attach readiness and transcript events do not clear it, while a newer authoritative state answer does. A state-failed Chat notice offers Reconnect and explicit Restart, retaining the latter through same-native resynchronization. `omp:chat-restart` carries the native epoch and follows `ChatRuntime`'s lifecycle-event route. The host requires the controlling guest document, committed binding, positively owned runtime generation and exact saved header before and after consent. It uses authenticated force stop and matched broker/root-creation exit evidence without another native state or abort prerequisite, then reuses `SessionIndex.replaceHost` under the same claim and per-tab gate. No positive exit proof means no successor. Consent discloses uncertain admission, unsaved effects, image loss and independently surviving tools that can still modify files; ordinary Stop, Close and native Terminal behavior are unchanged ([ADR-0050](decisions/0050-retain-uncertain-input-and-confirm-exact-file-restart.md)).

`code --install-extension --force` of a same-version build replaces the installed folder in place under a running window. The host (loaded `out/extension.js`) keeps running its old code, but every *new* webview document, child entry or helper read loads the new files. `PackageDrift` (`src/host/package-drift.ts`) fingerprints the shipped entry bundles at activation and every 10 s; on a change it logs once, shows a warning with **Reload Window**, withholds a freshly built guest document from the old host (an already-loaded guest keeps working; mode switches show an “updated on disk” notice instead) and refuses to stage new child entries. Reload the window right after any in-place install.

**Host-owned conversations** (`src/host/chat-runtime.ts`). A conversation is `live` (an `RpcSession`), `view-only` (a stopped session's history, composer disabled, one explicit Open) or `legacy` (a row an earlier Collab build's host owns: a banner-only page with no composer and no transport). Pages are a separate axis: a page is one route (an editor's `postMessage` channel or its authenticated bridge) that receives the conversation's `omp:chat-*` messages, comes and goes without touching the conversation, and every replacement (view-only to live on Open, relaunch after Reload) uses a fresh epoch nonce so a surviving page accepts the new snapshot. A snapshot is chunked to the route's size ceiling; a route that refuses a size gets an authoritative re-send. The runtime reports model changes (turn activity, notifications), phase changes, identity and `open_url` to the extension; `open_url` becomes an extension-owned confirm naming the URL and is opened with `vscode.env.openExternal` only after an explicit click.
The bridge wire acknowledgement is available before the document's accepted-readiness callback attaches and resends the chat route; rejected acknowledgements restore the previous wire gate. A bridge acknowledgement is connection-scoped: losing that socket clears the document's bridge acknowledgement, so replacement authentication alone cannot publish readiness or lose the resend against an unacknowledged wire. The new connection's acknowledgement triggers the authoritative snapshot again, even after an interrupted first live snapshot; the document generation, sequence ledger and any panel acknowledgement survive. Headless coverage follows the actual Close, stopped-row Open, page Open and first host restart through this interruption. Installed-window verification remains separate. See the [surviving-page ordering invariant](designs/2026-09-29-rpc-ui-chat-and-sessions.md#3-webview-contract).

Large authoritative snapshots use ordered bridge backpressure, not a synchronous burst of encrypted-frame promises. The writer produces one sealed frame at a time and releases its plaintext byte reservation only after the socket write callback, under the unchanged 256 KiB frame and 1 MiB outbound queue ceilings. A stalled write closes after five seconds, independent of inbound heartbeats. The earliest admitted train finishes to preserve disk-first paint; only later wholly unsent trains are superseded, at their actual positions among live events. Every train ends with its epoch-bound display preferences. Large rows/DTOs use authenticated, sequenced fragment payloads; at most one bounded DTO is encoded/reassembled, with 128 MiB total, 128 KiB decoded parts and a 15-second absolute reassembly deadline. The guest discards partial data on refusal, route change or disconnect and exposes only complete DTOs. The panel path remains preferred where acknowledged, but an orphan has no guaranteed panel handle. Three early authenticated recovery failures (or repeated deterministic fragment refusals/timeouts) stop retries and explain Reload Window or copying the draft before reopening; neither OMP nor input is replayed. The [bounded snapshot design](designs/2026-10-09-bounded-bridge-snapshot-delivery.md) and ADR-0023 amendment were independently accepted; installed verification is recorded separately.
Before a bridge Chat page attaches or sends any snapshot, a sealed read-only `guest-version` announcement must prove guest protocol version 9 with fragment support on this exact authenticated connection and acknowledged route. Reoffer, disconnect or document replacement clears that proof. A fixed five-second post-ACK deadline cannot be extended by duplicate ACKs; missing, malformed, wrong-version or late proof gets one small existing unfragmented blocked chat-state with Reload Window guidance, no ChatRuntime attachment, no native call and no reconnect loop. The existing v8 page retains its transcript and composer-local draft.

Panel route ACKs are repeatable but quiescent: only the first valid current-generation ACK publishes the ready-status offer. Later ACKs retain route authority without another identical offer, preventing the panel offer/ACK feedback loop. Lost-ACK re-delivery and fresh-generation writer fences remain intact; this does not change connection-scoped bridge acknowledgement.

**Chat page** (`src/webview/main.tsx`, `chat-messages.ts`, `lib/chat-client.ts`, `App.tsx` and components). Epoch-bound shared snapshots feed chronological canonical cards, then density and measured visible-window projection. [Paseo-style Chat](designs/2026-10-04-paseo-style-chat.md) replaces read-only groups and collapsed body previews with flat, lazy individual details and Overview groups of two or more tool calls. `projectToolOverview` emits a group only for a run of at least two calls; a lone call is the ordinary flat row (it keeps its reserved run key, so growing to two calls becomes a group under the same key with anchors, scroll and focus preserved, and shrinking restores the plain row). A settled successful Bash/Read call whose expanded details would be empty (`(no output)`, no error, diagnostics or artifacts) renders as one static, non-expandable line with its muted intent and “no output”. Shared `tool-presentation.ts` owns route/category/error/live-edit semantics; only ask and approval cards are never grouped, and every other settled call (task, wait, IRC writes, unknown tools) joins the adjacent Overview group and is counted as agents, jobs, messages or tool calls in its summary, while a running or queued task or wait keeps its own live row until it settles. A Wait is one header line in both densities (job name, outcome and clock, or a count and a truncated name list; the full list is in the tooltip and the expanded body). An actual live file edit/write stays expanded until terminal outcome, then returns to its run unless native focus/selection holds the detail. Late diagnostics stay attached to their file tool; unmatched diagnostics and native notices remain boundaries. Advisor notes validate severity/nonempty content, keep blockers discoverable and fall back to actual message content. Only proven visible user-attributed skills become user rows; exact prompts remain exact, legacy labels are explicitly reconstructed and expanded content/images stay disclosed. Goal/retry/fallback rows preserve native chronology; hidden data is excluded before counting, grouping, copying or announcements.

**Wait row and running badge (2026-10-08).** `wait()` in `tool-renderers.tsx` decides from the data whether expanding adds anything the one-line face and tooltip lack: several entries (the header ellipsizes names), a job's result, error, extra label lines or output notices, cancelled rows, an IRC message body, or the text of a rowless result. When it adds nothing (a lone job with a plain label, a lone agent, an empty progress), `ToolCard` renders a plain non-interactive row (`omp-tool-head--static`: no chevron, no button, nothing focusable) whose tooltip still lists every job's name, type, status, clock, exit code and first label line. A failed wait, diagnostics or attachments always stay expandable. The live clock is the longest awaited job's duration, ticking locally, in the right-aligned `omp-tool-elapsed` slot and kept after settling. **Bottom anchoring and following (2026-10-06).** The bottom edge of the transcript viewport is the top edge of the composer dock, and the line a reader sees there stays fixed relative to it. Following pins the tail synchronously: `TranscriptScrollController` runs its pin from `ResizeObserver` callbacks (after layout, before paint) and from layout effects, so streaming growth and dock resizes are absorbed in the frame they appear in, never one `requestAnimationFrame` later. Detached anchors record the viewport height they were captured at and compensate when it changes, so a growing or shrinking dock (typing, paste, attachments, image tokens, the working chip, feedback lines, the ask card) moves the reading offset instead of the bottom line. Only upward input (upward wheel, PageUp/Home/ArrowUp) or a touch/scrollbar drag is intent to leave the tail; downward wheel, Space or End while following neither pauses the pin nor can detach, so jump-to-latest appears only when the controller is detached by the reader. Rows for assistant text keep their last measured height across revisions (`MeasuredRow.growing`) so a streaming reply never snaps back to a text-length estimate and churns mounts. The composer's `autosize` freezes the dock height while it measures, so no transient dock height is ever laid out and clamps the transcript.

**Queued messages (2026-10-07).** Chat lists OMP's own queue above the composer (`QueuedMessages`, in `.omp-dock`): the host reads `get_state.queuedMessages` and `queue_update` into `ChatLiteState.queuedMessages` (steering, then follow-up; no ids, so a message is named by its exact chip text). Remove and Edit send `omp:chat-queue-remove`; the host runs one `remove_queued_message` per item in order, stops at the first unconfirmed command, and answers only the asking page, by request id, with one `removed | gone | unknown | failed` entry per item and no message text. Edit appends the removed messages (and their images, renumbered) after the composer's draft and sends nothing; `gone` is reported as already sent or no longer queued, never dropped. OMP has no dequeue-all that leaves the run alone, so Edit all is a sequence of removals. See [Edit queued messages](designs/2026-10-07-edit-queued-messages.md).

**Stop, queue authority and TUI controls in Chat (2026-10-09, [ADR-0052](decisions/0052-answer-terminal-only-commands-and-restore-the-queue-on-stop.md)).** Guest protocol version 8: a page of an older build cannot receive the queue a Stop withdraws, so the host refuses it. Every Stop path sends `abort_and_restore_queue` once per request id (`RpcSession.abortAndRestore`). OMP withdraws the queue before it waits for the turn to stop, and the command waits behind any serial command, so its answer is awaited past the manual-compaction deadline rather than the ordinary 30-second command deadline. An OMP that answers `Unknown command: abort_and_restore_queue` gets a plain `abort`; its queue stays in OMP and in the dock. `ChatRuntime` answers only the stopping page with `omp:chat-abort-result`, carrying the withdrawn steering and follow-up messages, oldest first. The composer appends them to its draft and never sends them; entries past the host's cap of 64 and images it cannot hand back are flagged as truncated or dropped and reported. A queued steer therefore never runs as a new turn after Stop. Plain `abort` would let OMP's post-abort drain deliver it. The dock follows OMP's queue under one ordering rule. `RpcSession` counts `queue_update` frames and records the count on every command it writes. A `get_state` answer to a read sent before a later `queue_update` keeps the model's queue and applies the rest of the state; OMP 18.8.5 was observed writing such an answer after a `queue_update` that had already emptied the queue. A user `message_end` while the dock lists anything triggers a state readback, because OMP does not report every delivery of a live-steered message. **Send now** promotes a follow-up with `promote_queued_message` through the queue-request path (`purpose: "promote"`), and `Alt+↑` is an Edit of the newest queued message. Terminal-only builtins are classified from the installed OMP's registry, read by the staged `media/slash-registry.mjs` (`src/host/slash-registry.ts`); a new install root or version drops the previous list, and a failed read is not repeated for the same install. They are answered in the transcript with result `explained`, and a mapped Desk action runs. Compact, shake, model and thinking cycling, HTML export and share reach the host only as fixed `omp:chat-command` names; `runChatAction` asks for consent and chooses every argument. **Compact…** and **Shake…** (context popover, editor title menu, Command Palette) first ask for OMP's mode in a QuickPick: `/compact` `snapcompact` (preselected, no model call), `soft` or `remote` (these two then ask for optional focus instructions), and `/shake` `elide` (preselected, OMP's own default), `images` or `thinking`. OMP's RPC `compact` takes no mode and there is no RPC `shake`, so `RpcSession.maintain` sends the slash command as a `prompt` with an internal id and no `streamingBehavior`: OMP runs a builtin before any turn logic (a compaction during a turn aborts it and resumes it afterwards). A manual pass emits no maintenance event; observed with installed OMP 18.8.5, `/shake` reports one `command_output` line before its acknowledgement and `/compact` acknowledges at once and reports from the background (`Compaction complete…` / `Compaction failed: …`). The session therefore shows its own progress line from the send until that report, fails it on a `… failed` report or on an acknowledgement saying the text reached the model, and refuses a second pass meanwhile; the report itself still renders as the notice it always is. Retry re-sends `/retry` from the composer. `↑`/`↓` history is derived from the loaded user prompts (`lib/prompt-history.ts`), and `Ctrl+R` adds remembered prompts from other conversations (`globalState`). The thinking and tool-call defaults (`Ctrl+T`/`Ctrl+O`) are `globalState` values pushed with the display preferences (`lib/transcript-toggles.ts`). OMP extension widgets and info or warning notices render around the composer, and errors become VS Code error messages.

**Registry liveness rows (2026-10-09, [ADR-0053](decisions/0053-merge-a-desk-published-registry-liveness-signal-into-the-agents-row.md)).**

- **The gap.** OMP 18.8.5's RPC roster hears only task-executor monitors. A finished subagent that a parent's `write agent://` steers into another run therefore never appears in it. Its registry ref also stays `idle` while it works.
- **Publisher.** `registerAgentLiveness` (`src/omp/agent-liveness.ts`) runs in every binding of the `-e` host-control module.
  - Subagent bindings record their own `agent_start`, `turn_start`, `tool_execution_start` (tool and intent) and `agent_end` in a process-global store.
  - The first `rpc`-mode main binding subscribes to `AgentRegistry.global().onChange`. It publishes `{v, instance, seq, sessionId, agents[{id, agent, state, sessionFile?, tool?, intent?}]}` through its own `ctx.ui.setStatus("omp-desk.agent-liveness", …)`, with at most 32 agents and 16 KiB, shedding detail rather than skipping.
  - It coalesces at 150 ms for edges and 1 s for activity. It re-checks every 2 s only while an agent is live as `idle`, and repeats a non-empty set every 10 s. Nothing runs while no subagent is live.
- **Shared derivation.** `subagentLiveState` is also the rule for `hasLiveSubagents`. It counts `running` (not a stale accepted run), `idle` with queued messages, and `idle` with a streaming session whose own binding observed new work after `lifecycle.terminalAt`.
- **Host and page.**
  - `RpcSession` takes that status key out of the status line. `AgentLivenessGuard` (`src/chat/agent-liveness.ts`) accepts only the bound session id, with a newer `seq` per publisher `instance`. It keeps the newest list, re-applied after a resync reset unless the replay was truncated.
  - The shared reducer folds the accepted list as `agents_liveness` (`reduceAgentLiveness`, `src/chat/agents.ts`). RPC rows stay authoritative and are only annotated with `liveState`. Unlisted ids become `origin: "registry"` rows, running with the published activity and the remembered spawn identity. The next publication that omits a registry row removes it.
  - Any RPC frame for an id takes its row over. A terminal frame removes it, unless the newest publication reported the agent `idle`-live, in which case the row is kept as a registry row. `get_subagents` snapshots keep registry rows.
- **Installed check (2026-10-09).** In owned isolated windows with real OMP 18.8.5, a parent spawned a subagent that finished, then sent it a `sleep 45` follow-up (receipt "Delivered").
  - The pre-fix build showed no Agents row for the whole 45 s.
  - The fixed build showed "Agents 1 running · <id>: bash · Sleeping forty-five seconds" throughout, and removed the row within about a second of the subagent's final reply.

Reload requires an actual reattached runtime and preserves its mode.

It disconnects, forgets the conversation's broker mapping and clears its cached restore conflict; the broker's own record stays as recovery metadata. A shutdown refusal is disclosed without undoing the writer-gone proof.
A fresh fileless draft launch clears the previous draft host's session id before recording its new attempt, so the first current-runtime identity can be accepted and its file promoted. Existing-file resume IDs stay pinned; a confirmed not-started launch restores the prior draft identity. Current-runtime and differing-ID fences are unchanged.

An allocated native session path need not exist before the first assistant response. Repeated observations of the same runtime/file/session identity keep one pending promotion retry rather than restarting it or invalidating the Sessions projection. Materialization still requires the exact header and claim; a changed promotion failure remains diagnostic.

**Folder navigation and history query.** Folders are navigation only; they never change VS Code workspace roots or session ownership. Sessions shows one per-window list (`LauncherFolders`, `src/views/launcher-folders.ts`, [design](designs/2026-10-07-window-folders-and-other-window-state.md), [ADR-0045](decisions/0045-derive-window-folders-per-window-and-pin-with-identity-ids.md)): the folders VS Code has open in this window (local `file` roots, VS Code order, live on `onDidChangeWorkspaceFolders`, hidden by `omp.showWorkspaceFolders: false`), then the other **pinned** folders (the profile-wide `WorkspaceFolderRegistry`, catalog key `omp.workspaceFolders.v1`, stored order), then folders kept visible only by a session running or launching in this window. Entries are deduplicated by `folderIdentityKey`; a folder both open and pinned appears once with the pin icon. Window folders are never persisted. A folder's id is `windowFolderId(path)` (a hash of its identity key), and Pin stores the record under that id, so Pin and Unpin never change a row's identity or a folder command's argument; records from earlier builds keep their ids. Collapsed state is in the pinned record for pinned folders and in this window's workspace state (`omp.windowFolderCollapsed.v1`) for the others. Pin and Unpin replace the old Remove; Unpin is metadata-only and refused while a managed session of the folder runs or is launching here. Every consumer (New Session, Resume Session, Open Terminal, `folderArgument`, the Add Selection/File picker, the welcome context) reads this one list. On-demand Resume Session scans readable exact files and canonical indexed paths, deduplicates them and exposes the same exact-path Delete transaction regardless of provenance. Header/path integrity is revalidated; ownership uncertainty is not a refusal.

**Sessions state and actions.** Fresh positive ownership facts override cached availability for RPC, explicit native and legacy children. A verified rival-window holder has the `otherWindow` state and `multiple-windows` icon, with Stop available for the rival's recorded host. Open and a click offer navigation to the owning window rather than launching; the claim is re-read first, so a released claim opens normally. The state is an observation, not an authority; all launch paths still go through claim admission. It updates without a manual refresh when the other window opens or stops a session: `src/host/claim-watch.ts` watches the claims directory (`fs.watch`, non-recursive, not persistent, 150 ms debounce, spawns nothing), and changed claim names map only to affected rows for re-observation. A normal window close or crash releases no claim (children and claims outlive the extension host), so the row is rechecked on focus, visibility change or click. Processes uses the same displayed ownership state when it refreshes. Unowned records are Stopped/Draft. Native lifecycle reattaches rather than launching a process just to stop it, uses guarded SDK grace, and requires separate force consent when grace/control is unavailable. A missing transcript offers Forget. Stopped Chat paints history; stopped Terminal keeps an attachable broker screen or a recovery placeholder, never silently spawning.

Other-window rows retain a known run state (Running when finer activity is unavailable), followed by “in another window”. The opening notification and context menu provide Switch to Window. Claims carry an optional display-only owning-window URI, separate from all ownership evidence: the saved local workspace file, or the single local folder when there is no workspace file. Navigation rechecks the holder and calls `vscode.openFolder` with `forceNewWindow: false`; it never uses the session cwd as a proxy for window identity. Unsaved multi-root and older metadata-free claims are limited to manual Window-menu selection.

**Outside OMP writers.** A plain `omp` (typically in a terminal) that writes a session holds OMP's session ownership lease, a named Windows mutex, until it exits; the extension only *opens and closes* it read-only ([ADR-0046](decisions/0046-probe-omp-session-lease-for-external-writers.md), [design](designs/2026-10-07-external-omp-session-lease.md)). `src/host/omp-session-lease.ts` derives the name (`Global\omp-file-lock-` plus two XXH64 values of the lock path `<home>/<PI_CONFIG_DIR or .omp>/run/session-owners/<session id>.lock`, verified against OMP 18.6.3) and `ExternalLeaseObserver` serves all rows with one run of the staged `session-lease-probe.ps1` (cached 2 s; a `fresh` request waits for a newer probe, bounded at 5 s; an access-denied answer reads as held). `launcherOwnershipFacts` adds `externalOmp` only when no claim of another window, no live claim of this window and no verified broker writer can be the holder (their children hold leases too; a child none of these can verify is reported as external); `sessionItemState` shows **Open in another OMP process** (`externalOmp`, `terminal` icon) after `otherWindow`, `starting` and `restoring`. A click or Open on such a row re-probes and asks; every explicit attempt that can start a writer (`openTabOnce`: verb *resumed*, or a row whose run intent is not stopped) asks the same question through `confirmOpenAnyway`, and `openSession` reports whether it proceeded so Add to Session adds nothing after Cancel; history views of stopped rows never ask. Known limitation: a restored editor and the activation pass's automatic relaunch do not consult the lease. A failed probe, an unknown derivation or an unreadable header leaves rows as before and logs. The lease exists only after the other process has written the session.

**Session row context menu.** The menu is the `when` clauses in `package.json` evaluated over the row's `contextValue`, `ompSession.<forgettable|held>.<state>.<resumable|live-only>.<deletable|file-kept>.<materialized|fileless>.view-<chat|terminal|none>` (built in `src/views/session-tree.ts`; the `view-*` segment is the view this window's open editor shows, from `SessionLauncherFacts.viewMode`). It follows what each command does: **Open in Chat/Terminal** (`openSessionInMode`, verb *open*) launches, so only stopped and draft rows get it, while a live row's **Show in Chat/Terminal** (`omp.showSessionInChat/Terminal`, the same handler with verb *show*, hidden from the palette) reveals the existing editor, or reopens it when only the tab was closed, and is offered only for the view the open editor is not already showing (both when no editor is open or its view is unknown). `background` ("Waiting for subagents") is live everywhere `working` is. A folder node's `contextValue` is `ompWorkspaceFolder.[shells.]<collapsed|expanded>.<pinned|unpinned>`: Pin Folder is offered on unpinned folders (also inline) and Unpin Folder on pinned ones.

Sessions title navigation contains New Session; default-mode choices stay in overflow. An empty folder has a folder-scoped launch placeholder. Stopped and draft rows expose inline Open as well as their mode-specific menu actions, while existing single-click history and second-click resume behavior remains.

When a successful default-profile `omp models --json` read reports no available models, Sessions prepends one stable account-icon action, **Log in to a model provider to start**, which runs `omp.loginProvider`. The window caches this observation and refreshes asynchronously on activation, when an **omp login** terminal closes and when a Chat reports changed model availability. An unresolved OMP adds no row; activation never waits for discovery. The row is independent of folder/session membership and disappears once models are reported.

Rename of a live row not yet attached in this window reattaches its verified writer first (as Reload does) and renames through it. The Delete button retains writer-stop, exact-file, ownership and frozen-target checks; Cancel returns without a redundant notification.

**Sessions panel.** Persisted rows publish immediately as **Checking** while ownership/title enrichment proceeds, rather than waiting for the complete restore scan. Only current-revision publication updates retained row/folder identities; superseded reads cannot mutate the visible projection. Positive local/authenticated ownership remains distinct from activity. Rows distinguish **Working**, **Waiting for subagents** (including asynchronous jobs and undelivered results), **Needs your answer** only for structured dialogs, and **Idle** only at proven idle. Fresh non-running sessions also use Idle; stopped saved sessions remain Stopped. **Unread reply** is supplementary, not proof of idle. Requests appear immediately; completion waits for full background/result-delivery drain. Stopped single-click remains non-mutating, rapid second-click/Open launches through the existing gate, and running clicks reveal their editor. Profile default-mode selection never changes existing tabs. The [Sessions startup/work-status design](designs/2026-10-04-sessions-startup-and-work-status.md#implementation-evidence) records the accepted coordinated checks, package and installed proof and the earlier runtime observations: one paired first-leaf measurement of 10.673 → 2.853 seconds from recorded launch, and real asynchronous waiting with one completion only at true idle. These are bounded observations, not a latency distribution.

**Flat Sessions list, unread marker and selection pin.** `omp.sessionsGrouping` (`flat`, the default, or `folders`) is read by `SessionTreeProvider` through `SessionLauncherSource.grouping`; the title-bar commands `omp.showSessionsFlat`/`omp.showSessionsByFolder` only write the setting (and the `omp.sessionsFlat` context key picks which icon shows), and a configuration event refreshes the view, which then fires one root change. Both layouts are built from the same per-folder rows, so every row action, context value and state icon is unchanged. The flat list has one root-level row per session of the folders the grouped view would show (a row is listed once), labelled `folder · title` with folders of equal name widened by parent components (`flatFolderLabels`), and ends with a `New Session…` row whose command is plain `omp.newSession` with no argument: the existing folder QuickPick (or Add Folder flow) and `newSession` path are used, not forked. Empty with no folder at all, so the view's welcome content shows. Order (`src/views/session-order.ts`, pure): rows whose process is not stopped (`stopped`/`draft` are the stopped group) come first, unread before read, then by the conversation's last activity (`readSessionFileActivity`, falling back to the index's `lastActiveAt` for a file with no conversation), newest first, then newer ordinal; stopped rows follow by last activity alone. A reorder is a root change; a presentation change repaints the row. **Unread** reuses the two identities the index already persisted: `lastCompletedReplyId` (catalog, shared) and `lastSeenReplyId`, both in the shared catalog row (an earlier design kept the second in the window's workspace state, which a window that opened another folder lost, marking every finished session unread). `TurnNotifier` reports every earned event (a finished, not aborted, turn or a question), notice sent or suppressed, through `onEarned`; the native ledger does the same through its suppression callback. `recordSessionEvent` mints a fresh event identity (`src/host/session-unread.ts`) and, when the user is looking at the session (`isLookedAt`: the editor in front, visible, in the focused window; the notification-suppression notion without the `omp.desktopNotifications` switch), also marks it seen. `settleViewedSession` marks the front session seen on refresh, tab change and window focus. The row carries a `●` decoration badge (a `FileDecorationProvider` the provider exposes, keyed by an `omp-session:` `resourceUri`), `Unread · ` before its status and an `Unread reply` tooltip line in both layouts; a row another window or a plain `omp` runs is never shown unread here; reading a session in any window clears the mark in all of them. **Selection pin** (`src/views/session-selection.ts`, pure): while a session has an open editor in this window, `pinnedSessionTab` (the most recently focused session editor of `EditorRecency` whose row is shown) is what `revealActiveSession` selects, and `view.onDidChangeSelection` puts it back (`selectionRestore`) when the selection holds no session row; picking another session row is left alone and the selection follows once that editor is viewed. Reveals keep `focus: false`. VS Code limits: a TreeItem label cannot be styled and a long label truncates the description (observed: the description vanished), so the mark is a decoration badge, which stays visible; and a pinned row inside a folder the user collapsed cannot be selected without expanding it, so the grouped view leaves that selection alone.

New staged native hosts request-gate `nativeActivity({work:true})`; main/background work details come from one authenticated SDK state cut. Background work is the parent's async jobs and result deliveries **and** the live subagents of the OMP process: `hasLiveSubagents` (`src/omp/host-control.ts`) reads the process-global `AgentRegistry` through the injected SDK namespace (`pi.pi.AgentRegistry.global()`) and counts `sub` refs that are `running` (not an already accepted, no longer streaming run) or `idle` with messages queued for them; parked, aborted, advisor and main refs never count. A subagent revived from `parked` by an IRC message is in the registry but is neither a parent async job nor announced by a lifecycle frame, so without this a Terminal row showed Waiting for you and a Chat row settled while it ran. The Terminal path reads it inside `nativeActivity({work:true})`; a Chat (rpc-ui) child, which loads the same extension, answers the additive `subagentWork` control request (only to a child launched by a build that records the `subagents` capability), which the window polls every 3 s and merges through `withRegistrySubagentWork` into that tab's activity. Old hosts without that work detail remain Running unless idle is proved. Native end hooks strip async-specific claims: a fresh, non-aborted `willContinue` is provisional until authenticated SDK idle and every job/result delivery drain, and a new start/abort cancels it. A cancelled self-continuation that never starts is indistinguishable from an idle continuation gap; the maintainer explicitly accepted this hook-observation limit. Positive new-capability native background-work gating is covered by source/control-channel scenarios, not an installed long-running native case. Actual installed native detach/reattach was notification-silent; tagged WinRT history proves submission, not physical banner presentation. Same-artifact Chat and native/shell path-click receipts, restored fixture identities and retained shell-recovery/snapshot-link limits are recorded in the design.

Folder rows show the folder name followed by its cwd as a muted TreeItem description, middle-truncated to 40 characters while retaining root/drive and tail. Accessibility text includes the full path and session count. Session and folder tooltips are plain text with name, status and locale-relative last activity, plus one actionable line where needed. Last activity is the conversation's own: the `timestamp` of the last `message`, `custom_message`, `compaction` or `branch_summary` entry of the exact session file (`readSessionFileActivity`), read backwards from the tail only when an `fstat` on refresh shows the file changed; a folder shows its latest session's, and a fileless draft says No activity yet. File mtime is not used, because installed OMP also appends `session_exit`, model/thinking/service-tier and other bookkeeping entries and rewrites the title slot without a turn. The index's `lastActiveAt` is bookkeeping time (restore, reattach, conflict, failure, focus) that only recovers the focused tab; it keeps its persisted name for catalog compatibility and is never shown. The row context-menu **Copy Diagnostics** command copies the row's technical facts (including full paths, recorded identities and activity), using the existing capability redactor at the clipboard boundary.
Activity-signature transitions refresh Sessions directly, including dialog answer/cancel and work/wait changes; unchanged streaming text does not rebuild the tree. OMP queue facts stay count-only in Sessions; Chat lists the queued messages (see Queued messages). Background wait and continuation completion facts stay host-owned, not inferred from transcript wording.
The window-local launch/stop facts show **Starting/Stopping** while that operation is active. An unconfirmed attempt releases its lease and becomes saved/draft, never a stale-reservation state. Later actions probe current positive ownership anew.

**Restart recovery and row actions.** Activation attaches, before any launch, each recorded `managed-rpc` slot this window is responsible for through the read-only authenticated probe, so a running child is adopted and never respawned; only a row whose run intent is `running` and whose old writer is proved absent is relaunched with `--session <exact file>`, and a stopped-intent row stays stopped and opens view-only. Tree rows use internal `omp.clickSession` with an injected-clock recognizer; palette `omp.openSession` launches using the former Resume semantics and the obsolete `omp.resumeSession` alias is removed. It reuses an already-open view-only panel or surviving bridged editor. The row context menu is state-specific (table above); plain `omp.openSession` is no longer a menu entry because its default view is chosen through the two explicit entries. Close refuses before confirming when this window drives no transport for the row. See [ADR-0031](decisions/0031-reattach-a-surviving-managed-host-through-its-broker.md) and the [broker-aware restart recovery design](designs/2026-09-27-broker-aware-restart-recovery.md) for the surviving transport pinning.
A stopped session's explicit Resume request is allowed even though its editor holds no writer. It enters the same
claim-and-launch admission as the palette and row actions; passive editors still cannot mutate a running session.

**Resume from a stopped Chat.** The composer's Resume button shows in the `view-only` and `stopped` phases, and the host answers it in both: a history shown read-only, a session whose process exited (the live conversation object is still attached, in phase `stopped`) and one whose conversation was already released (the page keeps its last state). `ChatRuntime.handleMessage` raises `resume-requested` for each, and `resumeFromChat` (`extension.ts`) runs the row Open's path (`openTab` with the `resumed` verb → `index.restore` with `allowStoppedResume`), so ownership and claim checks, the one-writer rule and the exact-file launch are shared. Success replaces the conversation, so the page goes `stopped → starting → live` and its composer becomes writable. A refused or failed admission puts its reason on the page (banner; a conflict is also an error notification); a request that never reached the admission, or a Resume sent while the session is running or starting, is answered in the footer (`ChatRuntime.notify` / the fixed `CHAT_ALREADY_RUNNING_SENTENCE`). Nothing is silently ignored.

**Commands during a fresh editor's election.** A new editor is published passive until the index has durably recorded its control of the session, and its page can already be talking by then: the footer asks for the host's controls when it mounts, and a prompt may follow within seconds. Such a command is never dropped and never sent by an editor that does not control the session. The page messages that need authority (`omp:control-request` and the write commands of the chat vocabulary) wait, bounded to 15 s, for the election in flight on that slot (`dispatchSlotMessage`, `trackElection`, `awaitElection` in `extension.ts`) and are then routed on its outcome: delivered exactly once when the editor became the controller, otherwise refused visibly — the conversation tells the page the reason, and a control request is answered as unavailable with it. The role is published before the view mode is recorded, so recording the mode no longer extends the passive interval. Promotion asks the footer to read the host's controls again.

**Editor ownership.** VS Code owns open Webview panel membership and serializer revival; persisted identity is not a capability ([ADR-0019](decisions/0019-vscode-owns-omp-editor-persistence.md)). Closing a managed editor detaches without stopping its process. An editor is bound to one conversation for its slot; the tab is named for the session it shows (`sessionHeadline`, the same title the launcher row uses, plus the OMP icon) and corrected wherever a panel becomes a chat surface or Rename records a new stored title. Rename of a running session is rpc `set_session_name`, a stopped one rewrites its file. There is no native `/resume` or A→B switching in a chat process (`new_session`, `switch_session`, `branch` and `handoff` are not offered), so the slot-to-conversation binding changes only by the extension's own open/resume paths.

**Chat column.** With `omp.chatColumn` on (default), a session editor created by `openPanel` targets the editor group that already holds a session editor (the active group if it holds one, else the leftmost) by its exact column; with none, it opens in a new group beside the active one, or the active group of an empty editor area. `src/host/chat-layout.ts` then waits for the panel's view-state report, moves a new group `column - 1` steps left and locks the group while the session editor is still active. `arrangeSessionPanelGroup` (`extension.ts`) takes that column from the tab VS Code reports (`panel.viewColumn` keeps the requested column until a view-state event), because VS Code does not put an editor into an *empty* locked group even by exact column: after the last session editor of the chat group was closed (VS Code keeps the empty locked group), the reopened session lands in a new group on its right. It is then moved left from where it really is, and the emptied locked group, now on its right, is closed (`strayEmptyGroups`) instead of staying beside the chat. VS Code puts no editor into a locked group unless it is targeted by column (`ViewColumn.Active` included, verified on 1.141), so files from Chat links, the Explorer and Quick Open, Stats, Models/Agents, TODO/Agents details and folder shells open to its right without their own placement code. Restored editors keep the group and lock VS Code saved; the extension never re-locks a group the user unlocked except when it places another session editor there. With the setting off, session editors open in `ViewColumn.Active`.

**File window.** VS Code's Move Editor into New Window takes no arguments and opens a 1024x768 window (`createAuxiliaryEditorPart()` with no options; 1.141 remembers no size and has no setting for it). The first Ctrl+Shift+M of a group whose tabs are all *text* files (`TabInputText`, none untitled) therefore reopens the first file, with its selection, through the workbench's internal `_workbench.open` command, targeting `AUX_WINDOW_GROUP` (-3) with `auxiliary: { bounds }` (`FILE_WINDOW_SIZE`, 1600x1000; Chromium clamps a larger request to the screen); the public `vscode.open` drops the `auxiliary` option. The group's other files are then reopened into the new window's group in order (`vscode.open`, the active one last so it stays active) and the original tabs are closed; the file's document, so unsaved edits, stays shared. `workbench.action.enableWindowAlwaysOnTop` then acts on the focused, new window: the `alwaysOnTop` window option of the same call produced no topmost window on 1.141, and the command did, in the window's own title bar toggle and in the OS topmost flag. When any tab is not such a file (diff, viewer, custom editor, untitled file) the focused group is moved whole with `workbench.action.moveEditorGroupToNewWindow` (VS Code 1.141: `createAuxiliaryEditorPart()` then `mergeGroup` of the active group, no bounds, so a default-size window). Returning reopens each tab of the window's group by its input (`vscode.open`, `vscode.diff`, `vscode.openWith`) in the files group and closes it in the window, which VS Code closes once empty; a tab with no such input (untitled, webview, terminal) stays in the window, which stays remembered, and is reported. VS Code's `workbench.action.restoreEditorsToMainWindow` is not used: it merges the focused part's groups into the main part's active group (a no-op when run from the main window, the chat group when that is active) and touches every auxiliary window. Without a files group, the first tab is opened into the chat group by its exact column (VS Code accepts that for a locked group that holds editors; `ViewColumn.Beside` is relative to the focused window's active group, which is the file window's own when the key is pressed there, so it put the files back into the file window), which makes the main window's group active whichever window had the focus, and is then moved with `workbench.action.moveEditorToRightGroup` into a new group on the chat's right; the other tabs follow into that group. An auxiliary window's groups appear in `window.tabGroups` after the main window's, with ordinary view columns that shift when the main window gains or loses a group, so `src/host/file-window.ts` remembers the `TabGroup` object (one per group, its `viewColumn` kept current by VS Code) rather than a column; the window is gone when that object is no longer in `tabGroups.all`. `openTerminalFile` (Chat and Terminal file links) passes the file window's column to `vscode.open`; the Explorer and Quick Open cannot be redirected, but a locked chat group sends them to the most recently used unlocked group of any window, which is the file window once the main window has no file group of its own. The window is remembered by the extension host only: after a reload VS Code restores the window, but the next Ctrl+Shift+M opens another one.

Session naming uses the installed OMP title slot or session header, then the cached name, then a trimmed single-line first-user-prompt summary capped at about sixty characters, and finally the stable unnamed ordinal. An empty current title slot clears a legacy header name. Header identity reads remain prefix-bounded; an unnamed prompt beyond that prefix is found by streaming only through the first user entry. Imported/promoted titles feed the common Sessions, Processes and editor headline; authenticated live RPC name readback updates that cache and open detail titles without replacing their panels. User renames remain authoritative through OMP's own naming contract.
Reopening a still-running conversation gives its replacement editor a fresh immutable slot. When the current default matches the live mode, it retains the writer: moving retained state retires the old slot's terminal pipeline, the new panel binds a fresh frontend to the same native handle, native watches and run intent survive, and Chat resends its retained conversation. This also applies when startup restored the runtime before the closed editor was reopened. If the default differs, reopening uses the existing guarded mode replacement rather than bypassing shutdown, durable-content or one-writer checks. An unanswered terminal request disables stale input and reports response silence; only a lost established authenticated bridge connection produces the host-connection-lost message.
Before capturing transition facts, a switch joins the exact native runtime's already-pending authenticated-control attempt or the exact RPC session's memoized initial startup when it is still attaching/resyncing. This happens outside the lifecycle gate, which control publication itself needs. Completion revalidates editor/runtime/session/authority and the existing window-local open/view request sequence; a close, rebind or newer explicit selection supersedes the pending request, even when the newer choice keeps the current mode. No new retry is started, and genuinely unavailable or mismatched state still refuses replacement.

**Surviving-Webview bridge (implemented; installed acceptance observed for the rpc chat).** New editors use tab- and editor-specific view types and an identity-only persisted `{tabId, editorId}`; the serializer still restores editors after Reload Window. The host stamps such an editor's own `(tab, editor)` namespace into every document it builds, so the bounded *fallback* page a panel shows while it has no bridge endpoint saves the same version-2 state as the guest document and a page that never received the guest bundle cannot make its editor unrecognizable at the next restart. For an editor whose already-saved state is the version-1 `{tabId}` identity (an earlier build's fallback page, or a guest document with no bridge ticket), the serializer adopts it once — binding the editor exactly as a version-2 revival would, so its next document heals the state — only when the registered view type, the saved tab and the durable **controlling** binding all name the same `(tab, editor)` pair; a missing, passive, mismatched or foreign identity is still refused, and an unidentified editor persists nothing. A legacy generic editor is migrated lazily to one typed successor on first post-upgrade reload. `src/host/editor-coordinator.ts` elects one actual editor per indexed tab against VS Code TabGroups membership, not against stale index rows. `src/host/bridge-records.ts` and `src/host/bridge-endpoint.ts` provision a private per-editor document credential and an exclusive exact-port loopback listener (`src/host/bridge-listener.ts`), bound to the chat host's verified identity (owner generation, broker slot and generation, child pid and creation time, session id and file) before the secret is sent to the page. `src/webview/bridge.ts` and `src/webview/lib/bridge-client.ts` reconnect a surviving original document after Restart Extensions without replacing its chat client; the per-document route is acknowledged and fenced, while native mutations share an admission sequence across panel and bridge. A route's acknowledgement belongs to one wire connection: it is installed before readiness callbacks run and cleared when that connection ends, so a replacement connection's own acknowledgement triggers the authoritative snapshot resend. The new extension host reconstructs Sessions from actual editor membership and verified ownership. An orphan cannot be focused through a lost `WebviewPanel` handle; after a host-only restart the page names what stays unavailable until Reload Window (provider-account usage/settings refresh, provider login, `@` file completion, extension editor commands). Installed isolated windows (OMP 18.4.3) observed surviving pages dispatching and rendering prompts after repeated host-only restarts, including a session resumed from its view-only page, with model/thinking and Tools controls available. See [the reconnection design](designs/2026-09-25-reconnect-live-webviews-after-host-restart.md) and [ADR-0023](decisions/0023-reconnect-surviving-webviews-through-an-authenticated-bridge.md).

The rendered-document cache also keys on the embedded bridge document ID: upgrading a ticketless guest to a ticket-bearing document must actually reload its HTML. If the editor closes before its asynchronous endpoint bind finishes, its reservation is released synchronously and the late endpoint/records are forgotten; closing does not stop the native OMP process.

**Host-control reattach.** A host process serves one control server per slot: OMP binds the `-e` extension again for every in-process agent session (each task subagent), so the module keeps a process-wide claim and later bindings stay inert; earlier builds started a second server (new key, new random-suffix pipe) per subagent that overwrote or, on stop, removed the slot's last-writer-wins rendezvous record, which after Reload Window made the extension refuse the record as `key-changed` or wait for a record that never returned although the original server was healthy. **Staged runtime assets.** The helper and the host-control module a child process loads run from content-addressed copies staged under extension global storage rather than from the installed extension folder (as does the broker tree), so a reinstall can rename the installed folder while a session runs; the helper path and the digest of its bytes are configured by that staging, every copy is re-verified on every use (a helper whose bytes changed is refused before it is spawned), and an unconfigured helper refuses host control visibly ([ADR-0012](decisions/0012-run-child-process-entries-from-staged-copies.md)). Staging is not uniformly best-effort: where an asset is needed the stage is awaited and its failure surfaces (a host launch reports that the runtime entries could not be staged outside the installed folder), while the activation call is deliberately fire-and-forget so the helper path is configured before the process-generation probe used by the observation-history deletion proof, which re-awaits that same promise. The staged paths are not secret — they appear in the command line of the processes that load them — but the tree they live in is *verified*, not assumed: on Windows the access of the runtime directory, every digest directory, every copy, and every ancestor of the storage directory up to but excluding the OS-managed volume root must be limited to this account, SYSTEM, Administrators or TrustedInstaller — with the owner placeholders CREATOR OWNER, OWNER RIGHTS and SELF resolving to this account (the ancestor walk itself is derived by the shared private-storage convention from the layout root, not computed by the stager) — the copies and the directories that hold them with the strict rule, those carrier directories with the rule that no other principal may hold a right to replace the tree or change its permissions — a foreign principal that can only create or write inside them is tolerated, and so is a read-only shared ancestor — a directory this module owns that is not yet limited is rewritten non-recursively (a recursive `/T` rewrite leaves a file it reaches with no access entry at all), the owner of each of those paths is read and compared, and a symbolic link or reparse point is refused; on POSIX the mode bits and the owner count only while the listing shows no access marker, or GNU coreutils' context-only `.` (accepted on coreutils' documented meaning of that marker rather than on any check of the context itself): every path the store is reached through — the directories, every copy and the derived carrier walk — is read with the system's own listing, and the markers `+`, `@`, `%`, `?` or any unrecognised marker refuse the store, as does a listing whose mode cannot be read, so a macOS path carrying extended attributes or a Linux path with an ACL is refused rather than taken as proved. The cost is deliberate fail-closed rather than a narrow edge: on Apple's `ls` an attribute marker is printed instead of an ACL marker and accompanies the ordinary state of anything downloaded, tagged or unpacked, so such a chain makes the store unverifiable and the staged runtime unavailable on that machine. Anything unprovable refuses the stage, which is why a host launch can fail visibly on a machine whose storage directory is writable by another account. The volume root is the platform trust anchor: the walk stops there and the extension does not claim protection against a principal that controls it. This is protection against another *user* writing the staged code; arbitrary code running as this same user is outside ADR-0006's boundary and is not claimed against, and re-verifying a copy immediately before a spawn is a fresh reading rather than an atomic verify-then-execute.

**Packaging and platform.** OMP Desk targets Windows only: the broker depends on ConPTY through `node-pty`, and the host control, identity probes and desktop toasts run PowerShell and named pipes. One VSIX is built per target (`win32-x64`, `win32-arm64`); `OMP_DESK_TARGET` makes `esbuild.mjs` ship only that target's `node-pty` prebuilds, and `scripts/package-vsix.mjs` sets it for `npm run vsix:x64` and `npm run vsix:arm64`. The extension declares `extensionKind: ["ui"]` and no support for untrusted or virtual workspaces, because it starts local processes in a workspace folder. Release steps and Marketplace constraints are in [Publishing OMP Desk](publishing.md).

**Lifecycle and detail loading refinement (2026-10-08).** Session view requests project a pending context key so editor-title mode actions are disabled during a transition. Reversible admission fences are released on readback, gate-admission or publication failure; ten-second read/admission deadlines invalidate late queued requests. A shutdown that may already have been accepted retains its safety fence and offers the existing Stop/Force Stop recovery without automatically launching a replacement. Delete preflight errors produce visible failure feedback and bounded read-only inspection, while the destructive transaction remains exact-file and claim-protected. Single-agent detail tabs wait for the parent snapshot and first child read rather than treating missing initial data as proof the parent stopped.
