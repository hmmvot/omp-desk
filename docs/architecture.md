# Current Architecture

This describes **implemented source**, not completion of the [accepted development design](designs/2026-09-24-omp-vscode-development.md). Chat runs over `omp --mode rpc-ui` ([ADR-0038](decisions/0038-host-chat-over-rpc-ui-on-a-broker-pipe-child.md)); [ADR-0040](decisions/0040-switch-one-editor-between-rpc-chat-and-native-pty.md) restores the unmodified native TUI as another mode of the same editor, with exact old-root exit before transport replacement. Collab, relay, room/link, raw recorder and the Collab-era Agents Hub remain deleted. Separate native Models/Agents settings editors implement the user-requested boundary change of 2026-10-08 without restoring that roster. Source/headless/native-command evidence is distinct from installed-window acceptance.

The implementation has five runtime boundaries:

- **VS Code extension host** (`src/extension.ts`, `src/wiring/`, `src/host/chat-runtime.ts`, `src/host/native-session.ts`, `src/host/rpc-launch.ts`, `src/host/rpc-reconcile.ts`, `src/host/rpc/`, `src/host/pty-client.ts`, `src/views/`): owns the session index/claims, actual Chat or Terminal runtime, editor bindings, launcher, notifications and diagnostics. A Chat runtime holds an `RpcSession` whether or not an editor is open; Terminal holds the managed PTY and authenticated native state observer. It resolves installed OMP per launch without a version gate and starts neither transport directly from the extension host. The window's mutable state is one `WindowState` object that `activate` creates (`createWindowState`) and installs in the module's one `let` binding; functions reach it through `windowState()`, and `deactivate` disposes through it and leaves it installed. Six wiring modules hold the window's regions behind a `register…(deps)` handle stored on that object: `src/wiring/window-routing.ts` (the window registry, cross-window hand-over of sessions and launches, other windows' requests, the file window), `src/wiring/session-actions.ts` (the Sessions view's click, open, forget, stop, kill, delete and refresh), `src/wiring/guest-dispatcher.ts` (the `omp:*` page messages, chat commands, draft and selection handoffs, detail tabs), `src/wiring/editor-panels.ts` (creating, binding, rendering and placing the session editors), `src/wiring/bridge-host.ts` (the bridge endpoint, document provisioning, live-editor adoption and binding delivery) and `src/wiring/recent-sessions.ts` (the empty chat's recent sessions and the open of one of them, over the Sessions view's own rows and click). Each takes its dependencies as getters and callbacks, never `extension.ts`, and has its own test with fake dependencies.
- **Detached broker** (`src/broker/pty-broker.ts`, `src/broker/rpc-child.ts`, `src/broker/rpc-ring.ts`): independently surviving authenticated loopback IPC per slot. Kinds are `managed-rpc` (Chat pipe child), `managed-omp` (native TUI PTY), `folder-shell` (separate shell) and `stats-dashboard` (standalone Stats PTY). The runtime/native addon are content-staged outside the installed extension ([ADR-0012](decisions/0012-run-child-process-entries-from-staged-copies.md), [ADR-0032](decisions/0032-prove-the-pty-runtime-with-a-console-child.md)).
- **Managed OMP process**: installed `omp --mode rpc-ui` for Chat or default interactive OMP for Terminal, one extension-owned writer per claimed conversation. `-e`/`--preload` loads process-bound authenticated host control.
- **Session Webview** (`src/webview/`, `src/chat/model.ts`): the same WebviewPanel and immutable editor slot E show the host-owned Chat projection or xterm TerminalPane. Mode navigation belongs to the active session editor title; Copy Screen is native Terminal's title overflow action. Neither managed view duplicates these controls or normal live/grid status inside the page ([ADR-0043](decisions/0043-place-session-mode-actions-in-editor-title.md)). Replacing the child renews the document credential, not the editor.
- **Folder-shell Webview** (`src/webview/shell/`): an xterm renderer over a folder shell PTY; a folder's Open Terminal creates a separate shell and recoverable slot, never a second managed OMP writer.

**What ends a broker.** A broker is `process.execPath` of the extension host run with `ELECTRON_RUN_AS_NODE=1` (`src/host/pty-runtime.ts`), so its image is VS Code's own `Code.exe`; it survives window close, reload and a full quit of VS Code. The one outside force known to end it is VS Code's updater: "Restart to Update" runs Inno Updater, which waits 30 s for every `Code.exe` of the install to exit and then terminates the rest (observed 2026-10-13, VS Code 1.141.0 to 1.141.1: five session brokers and the stats broker among seven processes terminated; the OMP child of each ended with its broker, because an `rpc` child lives on the broker's pipe). The restored window therefore relaunches those sessions from their files. `src/wiring/updater-notice.ts` recognises it afterwards (the updater's temp log names the terminated pids; a broker descriptor with one of them) and tells the user once; nothing in Desk can keep a `Code.exe` alive through the updater, and a broker under another runtime would change the ABI the staged `node-pty` is checked against (ADR-0032), which is not decided here.

**Source layers** ([ADR-0065](decisions/0065-enforce-one-import-direction-between-source-layers.md), [design](designs/2026-10-12-extension-host-module-structure.md)). `src/` is divided into layers by directory, with one import direction: `src/shared/` (pure helpers, no `src/` imports), `src/chat/` (the reducer both sides run; may import `shared`), `src/protocol/` (message contracts and their parsers; `chat`, `shared`), `src/host/`, `src/broker/` and `src/omp/` (process-side code; `protocol`, `chat`, `shared` and each other), `src/views/` (tree providers; also `host`), `src/webview/` (the pages; `protocol`, `chat`, `shared` only, never `host`, `views`, `broker` or `omp`) `src/runtime/` (the `SessionRuntime` port and its in-process implementation, [ADR-0066](decisions/0066-extract-a-session-runtime-port-and-enforce-it-with-a-vscode-free-layer.md); `host`, `broker`, `omp` and below; no file under it may refer to `vscode`, directly or through any chain of non-test imports, and its port module `session-runtime.ts` imports only data-shape types from an allow-list) and `src/wiring/` (modules that connect host services to VS Code surfaces; `host`, `views`, `runtime` and below). Only `wiring` and `src/extension.ts` may import `runtime`. **Session runtime port.** A window opens, restores and re-attaches a conversation through `LocalSessionRuntime` (`open`, `restore`, `reattach`; and `replaceWriterHeld` inside a lease it already holds), not through the session index; launching and re-adopting a host is `LocalLauncher`, which reaches the window only through the `LauncherWindow` hooks in the order a launch runs them (retire the document, reserve the broker slot, launch, adopt, watch the broker, prepare the view, attach, record the run intent). What still bypasses the port, by name, is listed in the [design](designs/2026-10-13-session-runtime-port.md) §6. `src/extension.ts` may import every layer except `src/webview/` (it is the host bundle's entry, so page code may not enter through it either) and is the only file directly under `src/`. `import type` counts as an import, and any import cycle fails the check. `node scripts/check-imports.mjs` (run by `npm run typecheck`, tested by `scripts/check-imports.test.mjs`) reports one line per violation; test files (`*.test.ts`, `*.test.tsx`), test stubs and `test/**` are exempt from the layer rule but not from the cycle rule. The remedy for a violation is to move the imported module to the lowest layer both importers may see, never an exception.

**Contributed ids and the `ompDesk.` namespace** ([ADR-0068](decisions/0068-rename-contributed-ids-to-ompdesk-and-migrate-settings-at-activation.md), [design](designs/2026-10-13-extension-namespace.md)). Every id the manifest contributes — commands (category `OMP Desk`), settings, the container and views, context keys, keybindings and the `when` clauses that name them — is `ompDesk.<name>`; the bare `omp.` namespace is Oh My Pi's own. `omp.detail` and `omp.stats` have no serializer and became `ompDesk.detail` and `ompDesk.stats`. Not renamed, because VS Code persists or scopes them and no user or other extension sees them: the webview view types (`omp.session`, `omp.session.b2.<tab>.<editor>`, `omp.shellTerminal`, `omp.settings`, which also keep the `^omp[.]session` keybinding regex and the `onWebviewPanel:` events), every Memento, catalog record and SecretStorage key (`omp.sessionIndex.v1`, `omp.bridge.v1/…`, `omp.hostControl.*`, …), tree element ids, the status bar item id, the `omp:*` page messages and every name OMP itself reads. For the releases in which users still have old names in `settings.json` and `keybindings.json`: `src/wiring/legacy-settings.ts` moves the 13 old settings of the User and Workspace layers at the start of every activation (awaited at most 10 seconds before any setting is read; the old keys stay contributed, hidden and deprecated; no marker, so a value that reappears is moved too; read-only workspace files are not written; layers the new key cannot hold are left alone; one log line per key and layer), and `src/wiring/legacy-aliases.ts` keeps the 92 command ids published in 0.3.2 (and the generated view commands) registered, first in `activate`, uncontributed, as aliases that forward their arguments to the new commands and warn once per id, and publishes `sessionMode`, `streaming` and `composerPopupOpen` under their old context-key names too. All of it (aliases, mirror, old skip-shell ids, the migration and the hidden deprecated keys) is kept until 1.0.0 and removed in that release. A one-time notice (`ompDesk.renameNotice.v1`) tells a profile that ran an earlier release what moved; another extension's `omp.` names are never touched.

**Session runtime port, cuts 4 to 6.** `LocalSessionRuntime` also holds the stop verdict operations (ungated, the caller's lease and the recording stay in the window until cut 7 below), the services of the end of a process (`exit`: `rpcExited`, `nativeExited`, `endEnded`, `brokerLost`; `control`: host control; `identity`: conversation identity binding; `nativeWatch`: the native Terminal's watch and observed handover) and the conversation surface `conversations` (`ConversationPort`, over the `ChatRuntime` the runtime owns): page attach, `command`, `navigate`, `notify`, the view-only and legacy views and the value reads `stateOf`, `activityOf`, `promptsOf` and `rewindOf`, so the chat model never leaves the runtime. The window reacts through hooks run after the state they describe is committed.

**Session runtime port, cut 7.** Kill is `SessionRuntime.kill` (`LocalKill` in `src/runtime/local-kill.ts`: the identity probe, `taskkill`, and the recording that follows a proven kill); the window only builds the selection and shows the notices and refreshes (`KillWindow`). The gated `stop`, `stopRecorded`, `replaceWriter`, `beginTransition`/`endTransition` and `readTransitionFacts` are runtime operations that the compound flows (stop, delete, new session in place, view switch, Restart) call, and the runtime owns the per-conversation record (`RuntimeRecords`: process, control channel, fence, failure, native watch). The live Chat session never leaves the runtime: `conversations.incarnationOf` names it by a number that is never reused, `liveOf` reads its facts as a `LiveConversation` value, and the footer reads, model and thinking choices, Compact, Shake, export, Share, rename, the Context view's reads and subscription, the settings editor's apply and the view switch's pending join are operations keyed by `(conversation, incarnation)` that answer `stale` when the conversation holds another session. `LocalSessionRuntime` has no `sessionOf` and no `chat` member.

Visible terminal panes check a quiet host every ten seconds with a non-resetting status probe and a four-second response bound. Initial attach and actual stream discontinuities recover through snapshots, never ordinary focus. Silence disables input but preserves the copyable screen; folder shells name the folder's Reconnect Terminal action. This is liveness detection, not a shell bridge or editor-membership recovery protocol: a host-only restart cannot address the old shell page unless it still holds that panel. Reconnect uses attach-only runtime staging and retains the exact broker/slot. Open Terminal deliberately creates another shell; a host-less page close cannot be intercepted.

**Terminal presentation.** Native and folder-shell panes share resource-resolved VS Code terminal settings. The configured terminal family (editor fallback) stays first, followed by common and installed Nerd/symbol families, existing bundled Codicon and monospace. Bounded installed-family discovery does not modify user settings or add a font dependency. Configuration events update/refit existing instances without replacing screens; only the broker-authorized owner resizes. The fitted-grid remainder uses terminal background and native scrollbar chrome is hidden beneath xterm's auto-hiding scrollbar. Both terminal surfaces are headerless and use terminal editor icons, with a Starting status before the first ready state. Grid, input ownership and live shell-cleanup verdicts are display-only tooltip metadata; shell titles remain compact.

**Native start admission.** The host projects an explicit starting flag while a native editor's open or mode request admits a stopped session. Before a broker pipeline exists, attach/probe requests receive that lifecycle projection rather than an unavailable terminal frame. The page keeps Starting visible and hides stopped controls and stale warnings until the attempt completes. Explicit same-mode Terminal opens refresh the authenticated handle and frontend; an exited writer is reconciled before resuming, and an unreachable reopen is reported visibly without launching another writer.
The terminal pipeline belongs to one exact writer. A proved Close or natural process exit disposes it, so a retained editor's next start binds a fresh frontend instead of asking its stopped broker for a screen.

**Shell sizing and retirement.** The app wrapper's full-height flex rules live in the shared terminal stylesheet, so standalone shell documents use the same sizing chain and ResizeObserver refit as session documents. On an authenticated broker's confirmed child exit, the host removes the shell recovery record and broker-slot mapping, then requests authenticated shutdown with `requireStopped: true`, without sending a child stop or signalling a PID. The broker can retire even while its frontend remains attached, so the Processes row disappears on the next visible refresh. The editor keeps its final screen and exited state after broker shutdown; closing it stays silent. Successful Processes stops also retire the recovery record after confirmed child exit, even while the stopped broker is closing. None of this proves escaped descendant commands ended; live or unreachable shells retain their explicit Keep Running / Terminate decision.
An installed isolated-window check (2026-10-08) typed `exit` into a real folder shell and observed its visible Processes row disappear after 2.274 seconds, without Stop or Refresh. The retained editor showed exit code 0 with a copyable screen, and closing it produced no editor or native confirmation. The shell recovery catalog was empty, the exact broker had exited, and the owned test window left no running process. Typecheck and 102 targeted tests passed on that packaged baseline; this check does not prove descendant-tree emptiness or later unrelated changes.
Closing a live folder shell still asks **Keep Running / Terminate**; cancellation never authorizes a stop. Confirmed Terminate uses the authenticated broker to stop its child, requires child absence, then requests `shutdown(requireStopped: true)` before retiring the shell slot and mapping. A Windows `tree: unknown` / `verified: false` verdict describes descendant completeness, not a live shell or failed stop, and remains in Output without a warning after successful child exit and broker shutdown. Genuine stop/shutdown failures retain recovery metadata, warn with the Processes Stop action, and refresh the child facts without pretending the closed editor is still open.
Broker shutdown first waits until replies for previously accepted stop requests have been queued, including a stop refusal. A child-exit notification can start natural retirement while the explicit stop is still collecting its kernel verdict; that concurrent shutdown must not close the endpoint before the stop caller receives its correlated result. Read-only requests remain independent, and no tree or child-absence proof is promoted by this ordering.
The same window also serializes natural folder-shell metadata retirement and shutdown with the entire Processes Stop → shutdown sequence on the index's existing per-slot lifecycle gate. A confirmed explicit stop cancels its captured queued natural watcher before releasing that gate; its authenticated shutdown remains the authority, not a closed socket or broker absence. Ordinary editor teardown only unsubscribes future events and preserves retirement already queued for a confirmed natural exit. Session stop routes and read-only Processes observations keep their existing behavior.
Installed isolated acceptance also exercised editor-close Terminate on an idle shell and on a shell running `ping -t localhost`. Both produced truthful child-absent / tree-unknown diagnostics followed by authenticated broker shutdown, empty recovery mappings and an automatically disappearing Processes row without a warning or manual Stop/Refresh. The observed original shell and broker generations were absent; the ping process was absent in that case, not a general descendant-tree guarantee. Natural-exit screen retention and silent close still passed, with 110 targeted tests and typecheck on the same packaged snapshot. Cleanup left no owned test processes running.
A later frozen-snapshot isolated acceptance passed typecheck, build and 164 targeted tests, with 56 installed runtime/helper payload files matching the packaged build. Its real modern NodeService extension host armed the staged owner monitor against the independently read owning-main kernel generation. One actual Processes Stop with the shell editor open received the validated child-absent verdict and authenticated `requireStopped` shutdown acknowledgement, removed the row and recovery mappings, and retained the exited screen without a false warning. The acknowledgement was established by the guarded host success output and its authenticated helper response checks, not inferred from socket closure. A fresh shell from the same artifact then exited with code 0, retired automatically without Stop/Refresh, kept its copyable screen and closed silently. Cleanup reconciled all 20 observed owned process generations, the isolated window and its listener; no main-profile operation or PID signal was used. This establishes installed arming and these lifecycle paths, not real last-window grace expiry, cross-window concurrency or an empty descendant tree.

Live VS Code theme changes are observed on the renderer's ancestors. The shared renderer re-reads the palette and assigns `terminal.options.theme`, updating the host remainder background in the same callback without recreating xterm or changing fonts, grid, input ownership or screen contents. Its observer disconnects on disposal.

**Terminal cell widths.** The OMP TUI counts Unicode 11+ widths (`Bun.stringWidth`), so the Webview renderer and the broker's headless screen mirror both run xterm.js's Unicode 11 table (`@xterm/addon-unicode11`, `src/shared/terminal-unicode.ts`); wide emoji and CJK therefore advance the cursor by the two cells the TUI addressed, in the live stream and in reattach snapshots. Grapheme-cluster sequences (VS16 symbols, ZWJ families, skin-tone modifiers) still differ; see the [native terminal design](designs/2026-10-03-native-terminal-ux.md).

**Terminal file links.** Native and folder-shell panes activate OSC 8 through the shared xterm handler and detect plain relative/absolute paths with a host-validated link provider (wrapped and wide cells preserved). Hover underlines with a pointer and a plain-click hint. The host resolves against the current session/folder cwd, rechecks existing regular local files at activation, and opens non-preview editor tabs at one-based line/column positions. Only `file:` and the narrowly decoded OMP `vscode://file` form map to local files; other custom schemes/network files are refused. HTTP(S) retains the extension-owned browser confirmation. Cwd, route and document authority remain host-owned; PTY environment is unchanged. Existing broker serialization omits OSC 8 targets on attach/reopen snapshots: visible resolvable OMP path labels (compact Read and path/position text) remain clickable via the plain provider, but arbitrary/abbreviated labels without a resolvable path cannot recover their snapshot-only target. New live output retains OSC 8 normally.

Terminal link opening goes through `vscode.open` (new non-preview tab; text at its line/column, images/PDFs/binaries in their viewer) and failed activations show a short warning. The link provider caches host validations per text (30 s hits, 5 s misses), answers cached rows synchronously and shares in-flight requests, so a repainting TUI cannot flicker or drop the hovered link; `~/` paths resolve against the user's home. See the [native terminal design](designs/2026-10-03-native-terminal-ux.md).

**Chat file links.** The Chat reuses the Terminal mode's detector, validation cache and host open path (one convention). `src/webview/lib/chat-file-links.ts` finds candidate references (`detectChatFileLinks`: the Terminal detector plus `@path [lines a-b]` mentions, a path-shaped filter, and Markdown destinations that are a path or `file:` URL); `ChatFileLinks` asks the host through the same `omp:terminal-link-validate` / `omp:terminal-link-open` pair, with `folders: true` so a folder is a valid target too, through the shared `ValidationCache` (30 s hits, 5 s misses, one request per target, at most eight in flight). Terminal links send no `folders` and stay files only. `FileLinks.tsx` wraps a reference in a focusable `role="link"` span only after the host proves an existing regular file or folder; text, selection and copy are never altered and nothing is linked without the page's provider (detail tabs have none). Linked: assistant and user Markdown prose, bold/italic/strike text, inline code spans, Markdown links, tool-row read/edit targets (a read's selector line, an edit's first changed line), section titles, grep/find line numbers and glob entries. Fenced code blocks stay text. The host accepts the pair in Chat mode too (panel and bridge routes), resolves against the session's cwd, and still refuses everything but an existing local file or folder; the position grammar is `:12`, `:12:3`, `:12-30`, `:L12`, `#L12`, `#L12-34`, `#L12C3` and `file:` fragments (the start of a range is revealed). Activation (`handleTerminalLink`, `src/host/terminal-links.ts`): a click or Enter opens a file in a non-preview tab; Ctrl+Click or Ctrl+Enter (`action: "reveal"`) only selects it in VS Code's Explorer, without opening it, through the workbench's `revealInExplorer` command, which shows the Explorer; Ctrl+Shift+Click (`action: "os"`) starts `explorer.exe /select,"<path>"` (`revealPathInOs`), opening the containing folder in File Explorer with the item selected; VS Code's `revealFileInOS` is not used because, while its Explorer list has focus, it reveals the Explorer's selection instead of its argument. A folder has no tab, so a plain or Ctrl click reveals it in the Explorer. The Explorer shows only paths inside an open workspace folder (`workspace.getWorkspaceFolder`); for anything else a warning points to Ctrl+Shift+Click. Extensions have no API to select an Explorer row without showing the Explorer, so revealing switches the side bar. The link's right-click menu offers the same three actions through VS Code's `webview/context` menu: the span carries `data-vscode-context` (`fileLinkMenuContext`: `webviewSection: "ompFileLink"` and the target), VS Code turns its keys into context keys for the menu's `when` clauses and passes the object with the panel's viewType as `webview` to `ompDesk.fileLink.open` / `reveal` / `revealInOs`; `openFileLinkFromMenu` checks the object (`fileLinkMenuTarget`), finds the editor with that viewType and sends the same `omp:terminal-link-open` request a click sends. VS Code's own Cut/Copy/Paste stay below them. A web link's right-click menu (`webLinkMenuContext`, `webviewSection: "ompWebLink"`, in a Chat and in the TODO/Agents detail tabs) offers **Open in Editor** and **Open in Browser** (`ompDesk.webLink.openInEditor` / `openInBrowser`); the command re-validates the URL with `webLinkUrl` (`webLinkMenuUrl`) and opens it through the same `openPageWebLink` a click uses, needing no editor lookup because a web link does not depend on the session's cwd. The Chat prompt's `file-links` rule (below) asks the model to write paths in the form this detector links. Verified against the installed OMP 18.6.3: its TUI links only through OSC 8 — `fileHyperlink` (`pi-tui/src/render/hyperlink.ts`: `vscode://file/<path>:<line>:<col>` in VS Code terminals, else a plain `file:` URI) on tool paths (read, edit, write, grep, find, ast-grep/ast-edit), skill and image chips and the status-line folder, and `resolveMarkdownLinkTargets` (`pi-coding-agent/src/internal-urls/hyperlink-targets.ts`) for model-authored Markdown links (relative to the session cwd, existing files or directories, `file:` URLs, `#`/`?` suffix kept). It does not link bare paths, inline code, fenced code or `@` mentions itself; those are linked here as the VS Code terminal's text detection links them in Terminal mode. Not supported: internal-URL schemes (`local://`, `agent://`, …), which the TUI resolves but the host open path refuses, and bare `file://` URLs in prose (the TUI does not link those either).

**Chat code highlighting** (`src/chat/code-theme.ts`, `src/host/code-theme.ts`, `src/wiring/code-theme-wiring.ts`, `src/webview/lib/code-{theme-store,theme-style,highlight,tokens,languages}.ts`, `CodeBlock.tsx`; [design](designs/2026-10-13-chat-code-highlighting.md), [ADR-0067](decisions/0067-highlight-chat-code-with-highlightjs-and-host-resolved-theme-rules.md)). A Webview has no token colours, so the host resolves the TextMate rules of the colour themes that may be active (`workbench.colorTheme` and the preferred themes of the active kind, with their `include` chains and `editor.tokenColorCustomizations`; `vscode`-free core, thin wiring that re-resolves on settings, theme and extension changes) and `ChatRuntime` posts them as `omp:chat-code-theme` (at most three themes) from `attachPage` and `resend`, whether or not a conversation exists, and `refreshCodeThemes()` on change. The page picks the entry whose id is `data-vscode-theme-id` on `<body>` (plain code when none matches), tokenizes fenced code with highlight.js, names the tokens with TextMate scopes and colours them with a matcher modelled on `vscode-textmate`; tokenizing is cached by (language, text), runs one block per queued task after first paint, skips blocks over 10,000 characters or 400 lines, and waits for an unfinished fence to settle for 400 ms. Copy always gets the plain source. The page also sets `--omp-inline-code` from the theme's string colour for inline code (text on a 14 % tint of itself; High Contrast keeps the preformatted-text colours).

Fence languages (`code-languages.ts`, amendment of ADR-0067 on 2026-10-13): 43 canonical language ids, each with a TextMate root scope and suffix, keyword and built-in tables and a word strategy, and many aliases matched case-insensitively against the fence's first word (`languageId`): ts/tsx/js, json, python, cs, powershell, shell, html/xml, css, markdown, yaml, diff, rust, go, cpp, c, java, kotlin, swift, php, ruby, sql, dockerfile, toml, ini (`.editorconfig`), properties, makefile, scala, dart, r, perl, graphql, protobuf, haskell, elixir, objectivec, groovy (`gradle`), hcl (`tf`), nginx, lua, bat (`cmd`), gitignore (`.dockerignore`). highlight.js tokenizes all but two: `gitignore` and `hcl` have no highlight.js grammar and use small scanners (`code-mini-languages.ts`) that emit highlight.js's HTML shape, so one classifier names every token. Grammars are registered on first use (`engineFor`), so only the languages a conversation shows are compiled; `text`, `plaintext`, `txt`, `mermaid` and unknown ids stay plain.

Tool card code (`use-highlighted-runs.ts`, `CodeRuns.tsx`, `CodePreview`/`DiffPreview`/`TextPreview`/`MatchOutput` in `tool-renderer-primitives.tsx`, `ToolTargetText` in `FileLinks.tsx`; ADR-0067 amendment of 2026-10-13): the code a tool card shows goes through the same tokenizer, caps, cache, queue and settle delay as a fence; `useHighlightedRuns` is the one hook (a fence, a header command and every preview use it, so streaming behaves alike: plain first paint, colour after the text has stopped changing for 400 ms, coloured text stays coloured while new text arrives). A preview's language is `languageForPath(path)` (file name first: `Dockerfile`, `Makefile`, `.gitignore`; then the extension through the fence alias table; read selectors such as `:10-40` are ignored), and an unknown one stays plain. `useCodeLines` tokenizes the whole text when it is within 10,000 characters and 400 lines, so a construct opened above the visible lines keeps its colour; a longer text is tokenized from the visible window for as many lines as fit the caps and the rest is plain. A diff is read as two texts, the old file (context and `-` lines) and the new one (context and `+` lines), each tokenized whole, so the signs, numbers and added/removed row backgrounds stay the diff's own; a construct spanning two hunks is cut at the gap. Search match lines are tokenized as one text per file. The `bash` (shell), `python` and `powershell` tools' command in the card header is coloured as its language. Plain text nodes are not split when there is no colour, so selection and the tests that read them are unchanged.

**Chat code-symbol links** (`src/shared/code-symbols.ts`, `src/host/symbol-links.ts`, `src/webview/lib/chat-symbol-links.ts`, `CodeSymbolSpan` in `FileLinks.tsx`; [design](designs/2026-10-10-code-symbol-links.md), [ADR-0058](decisions/0058-resolve-chat-code-symbols-in-the-host-window-through-workspace-symbol-providers.md)). An inline code span of **assistant reply text** (`SymbolLinksEligibleContext`, set by `AssistantContentView`, cleared in thinking) that is not a link and parses as a symbol (`parseCodeSymbol`: one to four ASCII identifiers joined by `.`, after removing generic arguments, `[]`/`?` suffixes, one call argument list and a whole-span `[Attribute]` wrapper; no keyword, no last name under three characters, no bare all-lowercase word unless called) is offered to the host once it has been on screen and after the 200 ms streaming settle. A span that is also path-shaped (`A.Bcd`) waits for the file validation to refuse it first. `ChatSymbolLinks` batches unique tokens (40 ms window, 16 per `omp:terminal-link-symbols` request, two requests in flight, 64 unsettled tokens in all, retries included; request ids are document-wide), caches answers (found 30 s, answered none 10 s) and retries an `unavailable` token after 5 s and again after 20 s, then rests it for 60 s. The host (`handleSymbolLinks` in the `handleTerminalGuestMessage` link case, both panel route and bridge stream operation `terminal-link-symbols`, same document/session/cwd currency check as validate/open) parses each token again and asks `SymbolLinkResolver`, whose `SymbolSource` is `vscode.executeWorkspaceSymbolProvider` converted by `symbolEntry` (only `file` URIs have a path; a location with no range has no position). It queries the last segment (and once more the full dotted text when a dotted name found nothing), keeps entries inside the session cwd or an open workspace folder that contains it, matches the exact name (`NameAttribute` too for an attribute; the entry's container must end with a dotted name's preceding segments) with a kind matrix, counts distinct declaration locations, groups them into symbols (the partial parts of a type and the overloads of a member in one container are one symbol, opened at the type's own file or the first location by path and line) and answers `found` only for one symbol (same-named types in different containers: `ambiguous` with the symbol count, unless exactly one lies inside the cwd; the page links an ambiguous token to the workspace symbol search through `omp:terminal-link-open` with `search: true`, which the host re-parses and runs as `workbench.action.quickOpen` with `#<last segment>`, never to a guessed definition; a bare capitalized name prefers type-like entries over members), logging one line per lookup (entry counts, matching locations, verdict, milliseconds). `unavailable` (an error, an invalidated lookup, an unmatchable entry, a cut answer) is never cached; `pending` (provider not ready: no query of the window has returned a symbol yet, so an empty answer is not a miss; or queue full or timeout) is no verdict and never cached either: the host probes a not-ready provider with a canary query (2 s doubling to 30 s, ten minutes), and when it becomes ready or its queue drains it sends `omp:terminal-link-symbols-retry` to every page that asked, whose spans without an answer then ask again. Window-wide bounds: four provider calls in flight, a slot released only when the provider's own call settles, 64 waiting queries that give up after the query timeout, overflow refused at once, 8 s per query, 15 s per batch, 1,024 cached answers (found 60 s, none 15 s); a generation counter, bumped by a file-system watcher, saves, renames and workspace-folder changes, fences cached, in-flight and queued work, and a batch whose generation moved answers every token `unavailable`. The reply carries `path:line:column` (relative to the cwd inside it) and a click is the ordinary `omp:terminal-link-open`, re-validated by the host. `ompDesk.linkCodeSymbols` (default on) turns it off: the host answers `disabled` and the page stops asking for 30 s. Limit: a workspace symbol search is ranked and may be capped (providers may cap results), not an exhaustive index, so "exactly one" means one among the entries the provider returned, and an answer Desk itself cuts (over 1,000 entries) never gives a unique match; unsaved edits reach the provider but not the invalidation until a save.

Bare file names (`session-index.ts:849`, `session-index.ts(849)`) and the trailing part of a path (`host/session-index.ts:579`) use the same exchange from a second source: `parseBareFileName` (`src/shared/code-symbols.ts`: a name, optionally with the `/`-joined directories that end its path, never anchored by a leading separator, drive, `~`, `.` or `..`) is run by page and host; the host answers a file-name token from `FileNameLinkResolver` (`src/host/file-name-links.ts`: the cwd's own file first, else `vscode.workspace.findFiles` with the exact path tail, `files.exclude`/`search.exclude`, its own limiter of 2 searches, 5 s timeout and 512-entry cache) before the symbol lookup. The cache is dropped by `SymbolLinkResolver.invalidate()` (a file created, deleted or renamed, a workspace folder change); a change or save of a file's contents calls `invalidateContent()` instead, which leaves file answers alone, and a search that was running when files changed is not discarded: each file it found is `stat`ed again and the answer is returned uncached (`unavailable` when none remains). One file is a `found` target; several are `ambiguous` with `files: true`, and the click (`omp:terminal-link-open` with `search: "file"`) is re-parsed and re-searched by `handleTerminalLink`, which asks the host to show a QuickPick of exactly those files (`lookupFileName`, `pickFile`) and opens the chosen one at the span's line. **Chat prompt** (`src/omp/chat-prompt.ts`). Chat features that depend on how the model formats a reply say so in one short section appended to the system prompt: a fixed preamble ("The user reads your replies in OMP Desk, a chat panel in VS Code") and the list `CHAT_PROMPT_INJECTIONS`, one rule per feature (today `file-links`, and `code-links`, which asks the model to link every code symbol at each mention, tables and lists included, as a Markdown link to the definition line it has seen in a read or search, `` [`App.start`](src/app.ts:12) ``, or to the file alone when that is all it knows, `` [`Parser`](src/parse.ts) ``, to leave plain only a symbol it has not located, and never to guess a line or search just for one; `Markdown.tsx` renders inline code in a link label as code and links it once the host proves the file, the same path as any Markdown file link; a symbol the model leaves plain is the host's to link, see **Chat code-symbol links**). The `-e` host-control module calls `registerChatPrompt`, whose `before_agent_start` handler returns the system prompt with the section appended, only for an RPC main session (`ctx.mode === "rpc"`, `ctx.agent.kind === "main"`): the native TUI renders replies itself, and a subagent answers its parent. Like Rewind it needs only the module loaded with a non-absent bootstrap. The text is constant, so the provider's cache prefix stays stable. Every rule costs tokens on every request, so the module header sets the guideline for adding one (one imperative rule, an inline example instead of a description, nothing Markdown already implies, no runtime values) and `chat-prompt.test.ts` holds each rule to 280 characters and the section to 1,500. Observed with installed OMP 18.8.5 in `--mode rpc`: the model quoted the appended section and followed it. A second, per-message reminder (`LINK_REMINDER`, one paragraph of about 340 characters starting `[OMP Desk reminder]`: files and folders as paths in inline code, code symbols as links) follows every user prompt of each provider request, when `ompDesk.linkReminder` is on (default off): the module's `context` handler (the extension `context` event, emitted on every request with a copy of the messages) inserts a separate `role: "user"`, `synthetic` message with that text right after each prompt that is not itself synthetic or a history rewrite, unless one is already there. The prompt object is not touched. It reaches the model only: the session file and Chat never contain it. It is a separate message because OMP marks any message it finds rewritten for a request as per-call and the Anthropic provider never anchors a cache breakpoint on or before such a message: appending the text to the prompt cost an uncached first request (about 12k tokens in a fresh session), while an inserted message leaves the breakpoint on the real prompt. The text is the same for every prompt, so earlier requests' bytes never change. The setting reaches the module as `OMP_VSCODE_LINK_REMINDER` (`1`/`0`), set by `rpcOmpLaunchSpec` when the session starts or resumes; a change applies to sessions launched afterwards ([design](designs/2026-10-10-code-symbol-links.md)).

**Chat web links.** Web links follow the same convention and request pair, without a validation round trip. `webLinkUrl` (`src/shared/terminal-links.ts`) accepts only an absolute `http:`/`https:` URL with a host and returns its normalized form; `detectWebLinks` (`src/webview/lib/chat-web-links.ts`) finds bare URLs in prose, starting only at a word boundary and stopping before trailing sentence punctuation and closing brackets the URL never opened (GitHub's autolink rule). `Markdown.tsx` links `[label](https://…)`, `<https://…>` autolinks and bare URLs (a bare URL is one inline token, so `_`/`*` inside it never start emphasis); inline and fenced code stay text, and any other destination (`javascript:`, `data:`, `command:`, `mailto:`, …) keeps its label and loses its URL. `WebLinks.tsx` renders a focusable `role="link"` span, never an `<a href>`, with the tooltip "Open in editor · Ctrl+Click to open in browser"; a click or Enter posts `omp:terminal-link-open` with `mode: "editor"`, Ctrl+Click or Ctrl+Enter with `mode: "external"`, and the handler prevents the default action and stops propagation so the page never navigates and Ctrl+Enter never reaches the Send keybinding. Its provider wraps both the session page and the TODO/Agents detail documents, so web links work in the transcript, tool output (web-search and GitHub sources included) and the detail tabs. The wire accepts `mode` only on an open request. The host re-validates with `webLinkUrl` before anything opens (`handleTerminalLink`, and `DetailTabs` for detail documents, which accept no other link request) and opens through `openWebLink` (`src/host/terminal-links.ts`): the built-in Simple Browser extension's `simpleBrowser.api.open` for an editor tab, and `vscode.env.openExternal` for the browser; only the origin is logged. In the installed VS Code 1.141 the Simple Browser command hands the URL to VS Code's integrated browser (an editor tab with its own address bar), and `openExternal` first shows VS Code's own "Do you want Code to open the external website?" prompt for a domain the user has not trusted. Terminal mode uses the same path: an OSC 8 `http(s)` link OMP draws (Markdown links and autolinks in replies, login and pull-request links) opens in an editor tab on a click and in the browser on Ctrl+Click, with the same tooltip; xterm has no plain-text URL detector here, so a URL OMP prints without OSC 8 is not a link in Terminal.

**Terminal streams and input.** Each pipeline has a fresh random presentation identity, distinct from the unchanged authenticated PTY identity. Healthy probes preserve output, selection and scrollback; ordered missing bytes or another presentation trigger explicit snapshot recovery. Only snapshot-follows adopts a new stream, and only the snapshot resets xterm. Bounded target-frontend buffering maps the broker's UTF-16 snapshot cut to dense output sequences so concurrent post-cut Unicode is not lost. Broker claim/owner events, not DOM focus, authorize input; visible eligible owners retain permission through blur, while hidden/passive/disposed panes release it. Genuine activation/click intent alone permits takeover, including an already-focused textarea click ([ADR-0044](decisions/0044-resynchronize-on-stream-discontinuity-and-retain-broker-ownership.md)). Native Shift+Enter sends OMP's multiline sequence. Single-use activation tokens restore keyboard focus on actual activation/document readiness/window-focus return, never model/probe ticks. Host clipboard copying admits stopped/passive screen reads but requires the latest current-document/generation-bound user nonce; oversized serialized replies refuse rather than truncate.

**Terminal screen restore.** The broker serializes up to about a million characters of screen and scrollback, but one `omp:terminal-snapshot` message carries at most 131,070 decoded bytes. A longer retained screen is trimmed by the host (`fitTerminalSnapshot`): whole oldest lines are dropped, attributes are reset at the cut and the visible rows, cursor and modes (or an alternate screen) are never cut, so a long session reattaches with its recent screen instead of failing. Output that outruns a reading triggers a fresh reading (three attempts) instead of an error; only a visible screen that alone exceeds one frame, or output that never lets a reading settle, shows the plain sentence "The earlier screen of this terminal … new output will still appear".

**Terminal repaint after restore.** A restored screen is replayed into an xterm that must show the grid the PTY really has: the owning pane renders at its own fit (a pane that has not yet been granted input first shows the host's grid, and is refitted once it owns), otherwise OMP's differential renderer draws for one grid while the emulator shows another, leaving stale status lines and a cursor one row off. After a snapshot reaches a visible owning native OMP pane, the host nudges the PTY one column narrower and back once (`TerminalPipeline` `redrawAfterRestore`, native `managed-omp` sessions only; shells are not nudged), so OMP repaints its whole screen from its own state. A surviving broker of an older build is detected and left running (it owns the PTY, and restarting it would end the OMP process); the repaint heals what its older mirror gets wrong. See the [native terminal design](designs/2026-10-03-native-terminal-ux.md).

**Terminal resize after reload.** A revived editor is laid out over several frames, so its first fit (the one sent with `omp:terminal-attach`) is a row or two off the settled one. The owning pane therefore reports its fit to the host only after it has held still (`RESIZE_SETTLE_MS`) and restates it whenever it regains input or asks for a screen again; the host never applies the attach-time fit, runs every grid write (page resizes and the repaint nudge) through one queue, nudges the grid the broker reports at that moment, and sends nothing for a resize to the grid the broker already has. Without this the PTY went 46 -> 44 -> 45 -> 46 rows within 60 ms of each reload and OMP repainted at every value. See the [native terminal design](designs/2026-10-03-native-terminal-ux.md).

Authority-fence changes publish terminal state immediately, independently of the queued broker ownership work. Even a fence that is set and lifted before that queue runs must produce the input-loss and restoration edges: the page clears its last-reported fit on loss and restates the settled grid on restoration. This prevents a resize refused during role reconciliation from remaining cached as delivered when the broker owner itself never changed. Read-only and hidden panes still render the host's grid and cannot resize it.

**Snapshot cursor.** The serialized screen is given an absolute cursor position (`placeSnapshotCursor`, from the mirror's own cursor) after everything the serializer wrote: `SerializeAddon` returns the cursor with relative moves, and after a full-width last row (OMP's footer) xterm.js's cursor-backward starts from the last column, so the restored cursor landed one column left of the prompt's until OMP next moved it.

**Redraw Terminal on demand.** `OMP Desk: Redraw Terminal` (command palette, the editor title overflow beside **Copy screen**, and Ctrl+Alt+Shift+R / Cmd+Alt+Shift+R, a chord no OMP or VS Code default binds) runs the same one-column nudge for the active native OMP pane (`TerminalPipeline.redrawNow`). It is for the moments OMP's own differential renderer and the terminal disagree about rows for a reason outside this extension (the program's output itself overwrites earlier rows); the program repaints from its own state, nothing is hidden or rewritten, and a folder shell, a hidden pane or a pane that does not own input is refused with a message rather than nudged. The terminal swallows the chord so the program never receives it (Ctrl+Shift+L would reach OMP as `^L`, its live-mode key).

**Workbench keys from anywhere.** Ctrl+Shift+L runs `ompDesk.focusComposer` with no `when` clause: the active session editor, else the one showing in the chat group, else the index's active tab, is revived if VS Code has not handed its panel over yet, revealed with focus, and a Chat page gets the `focus-composer` panel action; with no session editor it opens the OMP Desk side bar (`workbench.view.extension.ompDesk`). (It replaced Ctrl+Shift+Q, which took the same command from anywhere; Ctrl+Shift+L is VS Code's Select All Occurrences of Find Match key, which the contributed binding takes over and a user keybinding can take back.) Ctrl+Shift+M runs `ompDesk.moveFileToNewWindow`, which takes every tab of the group next to the chat (`filesGroupColumn`: the active group without a session editor, else the leftmost one, never the file window's own group) into the file window: one auxiliary window, kept on top, that every file opened from a Chat link joins until it is closed (see the chat column below). It is a toggle: while that window exists, the command returns its tabs (`returnFilesFromWindow`) to the existing files group, else to a new group beside the chat group, and forgets the window. It replaces VS Code's default Ctrl+Shift+M (Problems), and Cycle Model has no default key. Between two extensions VS Code picks by load order, so a keymap extension binding the chord under `editorTextFocus` (IntelliJ IDEA Keybindings: Move Caret to Matching Brace) can win in text editors; only a user keybinding outranks it. `contributes.configurationDefaults` lists both commands in `terminal.integrated.commandsToSkipShell`, so the integrated terminal passes the keys to the workbench instead of the shell; a user value for that setting replaces the contributed default and must list the commands itself. A Terminal-mode pane claims both chords, and Ctrl+Alt+Q, like Redraw (`isTerminalWorkbenchChord`): they reach the workbench and are never encoded for the program, which would read them as Ctrl+L (a form feed) and Ctrl+M (a carriage return).

**Focus VS Code takes back from the page.** When a window gains the operating-system focus, VS Code's `WebviewEditor` focuses its active webview again: the workbench runs `contentWindow.focus()` on the webview's outer frame, and 50 ms later the webview host focuses the page's frame. Chromium empties the focused element of a frame that loses the focus that way, so a click into the Chat composer of an unfocused window used to leave the page focused with nothing focused in it. `restoreFocusTakenByHost` (`src/webview/lib/frame-focus.ts`, installed by the Chat page's `boot()`) remembers the element that lost focus when the window's `blur` follows in the same task with the body as `activeElement`, and focuses it again when the window's `focus` returns within 750 ms with nothing focused. The operating system deactivating the window keeps `activeElement` and a later return is outside the window, so neither is touched. Native Terminal mode has its own re-activation (`activateNativeEditor` on window focus). Reproduced in an owned headless Chromium with the same two-level frame nesting (`src/webview/frame-focus-ui.test.ts`) and observed in an isolated VS Code window by replaying the workbench's call; the real operating-system activation order was not observed.

**Focus a disabled composer cannot keep.** The Chat composer's textarea is `disabled` whenever the session is not `live` (`chatWritable`), and a session leaves `live` without the user doing anything: the watchdog's reattach after a silent or dropped connection, and the rebuild after a damaged frame, both pass through `attaching` or `resyncing`. A disabled field cannot hold the focus and the browser does not return it when the field is enabled again, so the user typed into nothing. `useHeldFocus` (`src/webview/lib/use-held-focus.ts`) lets the composer *hold* its place from the moment it gains focus until focus moves for another reason than being disabled (another element takes it, or a press lands on something while the field is disabled), and focuses it again when it is writable and nothing else has focus. The page also keeps an always-on focus trace (`src/webview/lib/focus-trace.ts`, installed by `boot()`): a ring of what it saw (focus moves, window focus and blur, the field disabled or removed, the caller of every `focus()` and `blur()`), posted once as `omp:focus-trace` (rate-limited to one a second and 30 a page) when the composer loses focus without a pointer press, Tab or Escape in the preceding 400 ms. The host writes it to the OMP Desk output as `tab <id>: focus: <reason> | -<age> <event> | …`; nothing acts on it. Typing needs no focus on the composer: `installTypeToFocus` (`src/webview/lib/type-to-focus.ts`, installed by `boot()`) listens for `keydown` on the document (bubble phase, trusted events nobody has `preventDefault`ed) and, when a printable character or a paste chord (Ctrl/Meta+V, Shift+Insert) arrives at something that is not editable, focuses the composer with the caret at the end of its draft so the browser's own handling of that same key lands the text there once. Space, Enter, Tab, Escape, navigation keys, other Ctrl/Meta/Alt chords, IME composition, the Rewind picker's focused bar and a composer that is absent (an ask is open), disabled or read-only are left alone.

**Go to Session.** Ctrl+Alt+Q (`cmd+alt+q` on macOS) runs `ompDesk.goToSession` from anywhere, with no `when` clause and listed in `commandsToSkipShell` like the other workbench keys. It shows a `showQuickPick` over `SessionTreeProvider.listedSessions()`: the rows the flat Sessions list is built from, in its order (`src/views/session-order.ts`), computed for either grouping, each with its folder name (`flatFolderLabels`) and the status text the row carries (including `Unread ·`). Picking a row runs `clickSession`, so it is exactly a click on that row (a stopped row opens its history, a second pick in a short interval resumes it); the last item, New Session…, runs `ompDesk.newSession` with no argument, as the view's New Session row does. The key is `ctrl+alt+q` because Ctrl+Shift+Q already focuses the composer, no VS Code default and no IntelliJ IDEA Keybindings entry uses the chord, and it needs no `when` clause. On a layout whose AltGr is Ctrl+Alt the chord can type a character first (German AltGr+Q is `@`); rebind `ompDesk.goToSession` there.

**Terminal writes, resets and resizes stay in arrival order.** xterm.js parses what it is given later and in slices; a hidden or minimized window can sit on a large unparsed backlog. A hidden or zero-sized container is not fitted at all. See the [native terminal design](designs/2026-10-03-native-terminal-ux.md).

Without a selection Ctrl+C is the interrupt byte in a folder shell only; a native OMP session never sends Ctrl+C (the key is consumed on every layout, matched by letter or physical `KeyC`, and a stray `^C` in input is dropped). Paste stays on the browser paste event. See the [native terminal design](designs/2026-10-03-native-terminal-ux.md).

**Broker `managed-rpc` kind.** `PtyKind` is `"managed-rpc" | "managed-omp" | "folder-shell" | "stats-dashboard"`. `PTY_PROTOCOL_VERSION` and `PTY_RUNTIME_VERSION` were **not** bumped: the `rpc-*` frames are additive and gated by the record's kind (a `managed-rpc` broker refuses terminal-only frames and other brokers refuse `rpc-*` with `wrong-kind`), so a surviving Collab-era or folder-shell broker of the previous build stays reachable for probing, adoption and stop. `src/broker/rpc-child.ts` spawns the child with pipes (no node-pty and no screen model are loaded for this kind); the broker, not any client, negotiates rpc protocol 2 after the `ready` frame, swallows that response, and returns `ready` and the negotiated version on every attach. stdout is drained continuously into a sequence-numbered ring (`RpcLineRing`, 4 MiB / 2048 lines) whose retention is deliberately shallow: `message_update` frames are superseded per `messageId` and dropped at `message_end`, unanswered `extension_ui_request` dialogs are pinned until answered or cancelled, open `message_start`/`tool_execution_start` lines up to 64 KiB are pinned until their end frame, `response` and `rpc_chunk` frames are not retained (except a small `vsc:` response), and a `pinnedOverflow` flag is reported instead of ever evicting a dialog. Transient `response`/`rpc_chunk` lines wait for attached cursors under their own 128 MiB budget per broker (2026-10-12), so a reattaching client's own `get_entries` answer no longer evicts the replay ahead of it; eviction still walks one oldest-first queue, and a cursor that loses an unsent line reattaches. The ring only lets a (re)attaching client rebuild the in-flight turn; it is not a durability store. Lines cross the authenticated link as base64 fragments (≤ 96 KiB raw), replay is paced by the connection's send-queue bound and only the input owner may write. `RpcHandle` (`src/host/rpc-handle.ts`, on the shared `BrokerHandle`) implements the `RpcChannel` port an `RpcSession` uses. **Stop** closes the child's stdin (OMP aborts the turn, persists it, appends `session_exit` and exits); a force stop kills the retained child handle, never a numeric pid, and its whole-tree result stays `unknown` unless proven (ADR-0029). The broker never auto-stops a `managed-rpc` child: an extension-host or VS Code restart leaves it running, and only a folder shell has an owner-exit grace.

**OMP resolution (2026-10-12 amendment, [ADR-0011](decisions/0011-use-installed-omp-without-version-gate.md)).** `resolveOmpBinary` (`src/host/native-terminal.ts`) walks PATH in order, then OMP's launcher directory as a last resort, and a candidate's failure is classified (`src/shared/omp-unavailable.ts`). A *definitive* refusal (missing file, not OMP's program, foreign launcher, probe exited non-zero) records its reason and tries the next candidate. A *transient* one (the `--version` probe did not finish within 15 s, spawning or inspecting the candidate failed for lack of resources or because the file was busy, the process was ended by a POSIX signal) stops resolution with an error that names the candidate; a busy machine never starts an older OMP than the one PATH selects, and the next launch is the retry (Windows reports an externally ended process only as an exit code, which stays definitive). The machine-scoped setting `ompDesk.executablePath` replaces the search: when set it is the only candidate and every refusal is an error, never a PATH fallback; its Settings row has a **Test** button that resolves the typed value without saving it. Every caller (launch, native terminal, CLI reads, Settings, Stats, rename, inventory) goes through this one resolver; the package source they read is the package that holds the selected launch's entry script, never a global location. The inventory's runtime resolver keeps its earlier Bun and package root only across a transient failure and drops them when the explicit path changes. When PATH offers a second distinct install, the OMP Desk output logs both paths and releases once per window.

**Same-editor mode replacement.** The profile default is read from `globalState` (`omp.session.defaultMode`, initially Chat) only when opening/creating a tab, including reopening a closed editor whose writer still runs. Ordinary Open/click on an existing tab reveals its actual mode; explicit Open in Chat/Terminal switches that tab. **`RpcSession` and history** (`src/host/rpc/session.ts`, `history-reader.ts`, `frames.ts`, `protocol.ts`). The session is a state machine `starting → attaching → resyncing → live` (and `stopped`, `failed(code)`) over an `RpcChannel`. Every attach first paints JSONL history through the shared density-independent 100-canonical-card admission rule; each visible non-tool and individually owned call costs one, hidden/internal entries and already-owned results cost zero. Older cards are read by byte range. Replay folds into a shadow model, identity is proved with `get_state`, and `get_entries {since: <disk cursor>}` supplies the durable delta before authoritative publication. Ended live rows retain aliases and unmatched/unsaved notices through durable reconciliation. Mutations retain exactly-once `vsc:` ids and lost-prompt reporting. Identity-changing slash builtins remain refused, including the installed lifecycle operations `wt` and `worktree` and their advertised aliases. One `get_available_commands` query follows verified live attach; a pushed `available_commands_update` advancing the catalogue revision supersedes an older query response. There are no keystroke queries or new discovery processes for stopped/passive history. Protocol mismatch retains disk history and fixed refusal codes. `readViewOnlySnapshot` never claims, launches or appends history.
History reads resolve OMP's externalized images (`blob:sha256:<hash>` references in the JSONL, bytes in `<agent dir>/blobs/`) through `src/host/rpc/history-blobs.ts` before the shared parser runs; an unresolved reference renders an explicit “Image not available in saved history” placeholder instead of a broken image.

**Streaming cost (2026-10-12).** OMP sends one `message_update` per token chunk and each carries the whole partial message. `RpcSession` passes on at most one per message every `MESSAGE_UPDATE_PACE_MS` (33 ms): the latest frame per message is kept, a pending frame is delivered before any other line so order is kept, the first frame after a pause goes out on the next timer turn, and a stop flushes what was pending so a partial reply is shown as far as it got. On the page, `Markdown` keeps the previous parse (`parseMarkdown(text, previous)`, `src/webview/components/Markdown.tsx`): when the text only appends to the previous text, every block that ends before the previous last line keeps its element and only the tail from the last block (or the one before it, which a new line can join) is parsed again; a 20 KB reply rendered at 400 growth steps went from 562 ms of parsing to 16 ms.

**Host tool channel (2026-10-11, [design](designs/2026-10-10-agent-debugger-tools.md) §1, [ADR-0055](decisions/0055-expose-vscode-capabilities-as-rpc-host-tools-run-by-the-owning-window.md)).** Desk can register VS Code capabilities with OMP as RPC host tools (`set_host_tools`) and run them in the window that holds the session's broker input. The broker advertises `hostToolRetention` in `rpc-attached`: its ring pins a `host_tool_call` line until the matching `host_tool_result` is written to OMP or a `host_tool_cancel` for it is seen, and reports `hostCallOverflow` when pinned calls pass soft limits (32 lines, 1 MiB) without evicting them. A broker without the capability gets no tools and one Chat notice that the session must be restarted. `RpcChannel` exposes live `inputOwned` with an `input-owner` change event. `src/host/tools/host-tool-calls.ts` is the per-`RpcSession` call ledger: calls execute only while the session has verified identity and holds input (re-checked before each side effect), a call not seen live by this session (an earlier attachment, or a reconnect replay) is answered with an error and never executed, an OMP cancel aborts the tool and writes nothing, a local cancellation or lost ownership still writes exactly one error result, and a written result is retried under its id until the broker accepts it. `src/host/tools/host-tool-registration.ts` serializes and coalesces registration after identity verification and again when the provider's tool set changes. `src/host/tools/host-tool.ts` is the contract tools implement; the debugger tools live under `src/host/debug/`.

**Leaf moves and branches (2026-10-09, [design](designs/2026-10-09-chat-rewind.md), [ADR-0051](decisions/0051-rewind-chat-in-place-through-a-desk-registered-omp-command.md)).** The active branch can move without an append from this host: OMP's own turn recovery, or a Rewind. `#reconcileEntries` therefore rebuilds the window at the live leaf when a `get_entries {since}` delta is empty but reports another `leafId`, or does not extend the known leaf (the parent of its branch root is not the model's leaf). `#rebuild(live)` refreshes the `HistoryReader` and takes `snapshot(rows, leafId)`, the tail window of the path to that leaf, only when the disk holds exactly what the process just reported (its last complete entry is the live `lastId` and the live leaf is indexed), because OMP's write queue can trail the process. Otherwise it looks once more after 150 ms (`REBUILD_RETRY_MS`), then falls back to a full `get_entries`, which `#applyFull` trims to the same tail window (`transcriptWindow`) with an older-row count. The cursor becomes the live `lastId`. `HistoryReader.loadOlder(beforeId)` walks the ancestors of `beforeId`, so paging up follows the active branch even when its leaf is not the file's last line. The model's `branches` (`computeBranchPoints` over the reader's index or the full read, with first-prompt previews from the reader) list only divergences the user made: an off-path subtree whose first message, past metadata and markers, is a user prompt. OMP's retry and checkpoint pruning leaves subtrees rooted at an assistant or tool-result message, which are not listed. A branch's switch target is its newest user, assistant or tool-result message. A point is anchored at the nearest message at or before the divergence on the path, because a rewind usually lands below OMP's `model_usage` bookkeeping, which Desk does not load; points sharing an anchor merge. A reattach replays the broker's ring, which can hold turns of a branch the user rewound away from; on the first unmatched reconcile pass of a settled session with branches, one full `get_entries` drops the pending rows saved off the active path (`dropPendingSavedElsewhere`) instead of flagging them *not yet saved*.

**In-place navigation** (`RpcSession.navigate`, `src/omp/navigate-command.ts`, `src/chat/rewind.ts`; ADR-0051). The `-e` host-control module calls `registerNavigateCommand`, which registers the extension command `omp-desk-navigate` at the first `session_start` whose `ctx.mode` is `rpc` (the native TUI loads the same module and lists nothing). It needs only that module loaded with a non-absent bootstrap, not the host-control pipe. `RpcSession.navigate` runs once per 32-hex `requestId`. `#navigationRefusal` first refuses on host-known state: a fence or turn, compaction, a dialog, queued input, an unsettled or async-paused session, an unconfirmed prompt or unreconciled pending row, a catalogue without the command at `source: "extension"`, a leaf other than `expectedLeafId` (past which only OMP's `model_usage` bookkeeping may follow, `leafReaches`), or a target that is not a durable user prompt (rewind), the Undo offer's `from` (`undoOffer`) or a listed branch tip (switch). The request then goes out as `/omp-desk-navigate <json>` (`encodeNavigateCommand`, a compare-and-swap of session id, expected leaf and target) through an ordinary `prompt` without `streamingBehavior`. Inside OMP, `runNavigateCommand` re-checks session, leaf (with the same `leafReaches` rule) and target, calls `navigateTree`, and appends one `custom` entry `omp-desk/navigation` `{v, requestId, kind, from, target, to, summarized, raced?}` whenever the leaf moved, taking `from` and `to` from OMP's `session_tree` event and flagging `raced` when they differ from what was checked or no event was observed. Refusals throw `omp-desk-navigate:<code>`, which OMP reports as an `extension_error` with `extensionPath` `command:omp-desk-navigate`. `#onFrame` keeps that command's `prompt_result` and coded errors out of the transcript; `agentInvoked: true` in its acknowledgement or result, or the command text echoed as a user message, means it reached the model, which is aborted. `#runReconcile` defers while the command runs; afterwards one re-sync runs through the same serializer, and the marker with this `requestId` on the durable active path (the leaf or an ancestor) is the only proof of success. The outcome carries `summarized`, `raced` and, for a rewind, the target prompt as a draft taken from the entry the host holds, with `blob:` images resolved. A command whose answer never came (30 s, 180 s when summarizing) or was lost leaves `#navigationFence`: every mutation is refused as busy until its late `prompt_result`, its marker on the path or the end of this `RpcSession` (process exit, or a reattach after a window reload), and the page is told `unconfirmed`. `ChatRuntime.navigate` answers `omp:chat-navigate-result` to the asking page, or, for **OMP Desk: Rewind Conversation…** (`ompDesk.rewindConversation`, no origin), to every writable route, refusing `not-owner` when there is none. Read-only, view-only and not-live routes are refused before the session is asked, and a draft too large for its route is resent without images, counted as unavailable. `/rewind` and `/branch` typed alone open the page's Rewind; with arguments they are refused with `REWIND_ARGUMENTS_SENTENCE`. Files are never restored; the page and the QuickPick name the files changed after the target, including the paths of OMP's hashline `edit` (`toolPresentation` reads its `[PATH#TAG]` headers and the result's `path`).

**In-place clear and Desk session commands** (`RpcSession.clear`, `src/omp/clear-command.ts`, `src/chat/clear.ts`, `src/chat/desk-commands.ts`; proposed ADR-0059, round 4 review pending). A latest-committed-row catalog transaction checks previous provider id, file, host/RPC generation and ownership. Tentative identity is confined to its desired snapshot, published only after commit; queued ordinary snapshots are captured at their serialized turn, preserving concurrent title/unread/other-tab edits without leaking a refused identity. A detected competing committed runtime remains authoritative in the shared row. Durable row/header identity serves liveness, bridge/navigation and stopped-file operations; provider identity serves host readback/reattach. **Named refusals and a deferred `/clear` (2026-10-13 amendment to ADR-0059).** `RpcSession.#clearBlock` names the first thing in the way: `busy` (a response streams, or compaction/another Desk operation runs: OMP's own sentence), `dialog`, `queued` (a message waits in OMP's queue), `jobs`, `unsettled` (OMP is finishing the interrupted turn), `unconfirmed-send` (a sent message is not reconciled yet). When the only reasons are the transient `queued`, `unsettled` and `unconfirmed-send`, the chat runtime passes `RpcSession.clear` a callback and the clear is deferred instead of refused: nothing is written to OMP, the page gets one notice, `model.clearPending` (reason, carried in snapshots and the `clear_pending` host frame, shown as a footer row) marks the wait, and `handleMessage` answers at once so the composer is not held. At most one clear waits per session (a second says so). Every model change re-checks the block; when it clears, the deferred clear calls the same `#clear` as an immediate one, so ADR-0059's fence, phases and confirmation are unchanged. It ends, without writing, when the user sends a message, starts another command (`/new`, `/delete`, `/fresh`, a rewind, compaction, a context report), the session stops or changes identity, or after 60 s, which shows the then-current precise refusal; an abort, a queue removal or a streaming turn that begins while it waits does not end it. A streaming response, an open dialog, jobs and the other refusals are never deferred.

Installed-OMP isolated no-model RPC evidence established that prepare/confirm return early no-data admission acknowledgements and finish later with correlated `agentInvoked:false/status:completed` results; Desk waits for those handler completions before advancing. Two repeated native sequences retained the exact file/durable id and prior journal history, rotated provider ids and wrote final markers. This is not installed-window or real-provider teardown evidence.

**Lost-connection recovery and package drift** (`src/host/rpc/session.ts`, `src/host/package-drift.ts`, `src/host/pty-ipc.ts`). A session never stays frozen on a connection that stopped delivering. A watchdog armed while `live` probes a silent connection with `get_state` (after 45 s of silence while a turn shows as working, 90 s while idle); a probe that times out replaces the connection through the ordinary reattach, and a probe that answers “idle” while the page shows working clears the stale working state (`recovery` output, reason `probe-timeout` / `stale-working`). A frame that cannot be folded, or a frame listener that throws in `pty-ipc` (which now closes the connection instead of abandoning the buffered lines behind it), schedules an authoritative resync/reattach (`frame-failure`). Entering `failed` clears working, async-paused and active-tool state, and a *recoverable* failure (`attach-failed`, `state-failed`, `ready-timeout`, `protocol-error`, `write-refused`; `isRecoverableRpcFailure`) is retried automatically with growing delays (3 s, 10 s, 30 s, then 60 s); the failed banner offers **Reconnect** (`omp:chat-reconnect` → `RpcSession.reconnect()`), which reattaches to the same process and proves identity again, and is refused for identity divergence or an exited process. Drafts live in the page and are untouched by any of this.

**Unanswered native dispatcher recovery.** `RpcSession.nativeStateUnanswered` remembers an unconfirmed state read for one native session; attach readiness and transcript events do not clear it, while a newer authoritative state answer does. A state-failed Chat notice offers Reconnect and explicit Restart, retaining the latter through same-native resynchronization. `omp:chat-restart` carries the native epoch and follows `ChatRuntime`'s lifecycle-event route. The host requires the controlling guest document, committed binding, positively owned runtime generation and exact saved header before and after consent. It uses authenticated force stop and matched broker/root-creation exit evidence without another native state or abort prerequisite, then reuses `SessionIndex.replaceHost` under the same claim and per-tab gate. No positive exit proof means no successor. Consent discloses uncertain admission, unsaved effects, image loss and independently surviving tools that can still modify files; ordinary Stop, Close and native Terminal behavior are unchanged ([ADR-0050](decisions/0050-retain-uncertain-input-and-confirm-exact-file-restart.md)).

**Restart after an identity failure (2026-10-13 amendment to [ADR-0050](decisions/0050-retain-uncertain-input-and-confirm-exact-file-restart.md)).** `RpcSession.restartOffered` adds a failed `identity-mismatch` or `identity-diverged` session to the unanswered-state case; `chatBanner` gives those codes a `restart` action (no Reconnect, which stays refused for both). `ChatRuntime` and `restartChat` gate on `restartOffered` with the checks above. A session that failed before it went live in this host has no committed bridge document, so `restartBinding` derives the same binding fields from the row and the runtime instead, before and after consent; a committed binding is used whenever one exists. The successor resumes the row's own file. Consent adds that the exact recorded process now reports another conversation or identity. `#identityMismatch` logs, per tab, the file and id OMP reported and the ones the tab expected.

`code --install-extension --force` of a same-version build replaces the installed folder in place under a running window. The host (loaded `out/extension.js`) keeps running its old code, but every *new* webview document, child entry or helper read loads the new files. `PackageDrift` (`src/host/package-drift.ts`) fingerprints the shipped entry bundles at activation and every 10 s; on a change it logs once, shows a warning with **Reload Window**, withholds a freshly built guest document from the old host (an already-loaded guest keeps working; mode switches show an “updated on disk” notice instead) and refuses to stage new child entries. Reload the window right after any in-place install.

**Host-owned conversations** (`src/host/chat-runtime.ts`). A conversation is `live` (an `RpcSession`), `view-only` (a stopped session's history, composer disabled, one explicit Open) or `legacy` (a row an earlier Collab build's host owns: a banner-only page with no composer and no transport). Pages are a separate axis: a page is one route (an editor's `postMessage` channel or its authenticated bridge) that receives the conversation's `omp:chat-*` messages, comes and goes without touching the conversation, and every replacement (view-only to live on Open, relaunch after Reload) uses a fresh epoch nonce so a surviving page accepts the new snapshot. A snapshot is chunked to the route's size ceiling; a route that refuses a size gets an authoritative re-send. The runtime reports model changes (turn activity, notifications), phase changes, identity and `open_url` to the extension; `open_url` becomes an extension-owned confirm naming the URL and is opened with `vscode.env.openExternal` only after an explicit click.
The bridge wire acknowledgement is available before the document's accepted-readiness callback attaches and resends the chat route; rejected acknowledgements restore the previous wire gate. A bridge acknowledgement is connection-scoped: losing that socket clears the document's bridge acknowledgement, so replacement authentication alone cannot publish readiness or lose the resend against an unacknowledged wire. The new connection's acknowledgement triggers the authoritative snapshot again, even after an interrupted first live snapshot; the document generation, sequence ledger and any panel acknowledgement survive. Headless coverage follows the actual Close, stopped-row Open, page Open and first host restart through this interruption. Installed-window verification remains separate. See the [surviving-page ordering invariant](designs/2026-09-29-rpc-ui-chat-and-sessions.md#3-webview-contract).

Large authoritative snapshots use ordered bridge backpressure, not a synchronous burst of encrypted-frame promises. The writer produces one sealed frame at a time and releases its plaintext byte reservation only after the socket write callback, under the unchanged 256 KiB frame and 1 MiB outbound queue ceilings. A stalled write closes after five seconds, independent of inbound heartbeats. The earliest admitted train finishes to preserve disk-first paint; only later wholly unsent trains are superseded, at their actual positions among live events. Every train ends with its epoch-bound display preferences. Large rows/DTOs use authenticated, sequenced fragment payloads; at most one bounded DTO is encoded/reassembled, with 128 MiB total, 128 KiB decoded parts and a 15-second absolute reassembly deadline. The guest discards partial data on refusal, route change or disconnect and exposes only complete DTOs. The panel path remains preferred where acknowledged, but an orphan has no guaranteed panel handle. Three early authenticated recovery failures (or repeated deterministic fragment refusals/timeouts) stop retries and explain Reload Window or copying the draft before reopening; neither OMP nor input is replayed. The [bounded snapshot design](designs/2026-10-09-bounded-bridge-snapshot-delivery.md) and ADR-0023 amendment were independently accepted; installed verification is recorded separately.
Before a bridge Chat page attaches or sends any snapshot, a sealed read-only `guest-version` announcement must prove guest protocol version 9 with fragment support on this exact authenticated connection and acknowledged route. Reoffer, disconnect or document replacement clears that proof. A fixed five-second post-ACK deadline cannot be extended by duplicate ACKs; missing, malformed, wrong-version or late proof gets one small existing unfragmented blocked chat-state with Reload Window guidance, no ChatRuntime attachment, no native call and no reconnect loop. The existing v8 page retains its transcript and composer-local draft.

Panel route ACKs are repeatable but quiescent: only the first valid current-generation ACK publishes the ready-status offer. Later ACKs retain route authority without another identical offer, preventing the panel offer/ACK feedback loop. Lost-ACK re-delivery and fresh-generation writer fences remain intact; this does not change connection-scoped bridge acknowledgement.

**Chat page** (`src/webview/main.tsx`, `chat-messages.ts`, `lib/chat-client.ts`, `App.tsx` and components). Epoch-bound shared snapshots feed chronological canonical cards, then density and measured visible-window projection. [Paseo-style Chat](designs/2026-10-04-paseo-style-chat.md) replaces read-only groups and collapsed body previews with flat, lazy individual details and Overview groups of two or more tool calls. `projectToolOverview` emits a group only for a run of at least two calls; a lone call is the ordinary flat row (it keeps its reserved run key, so growing to two calls becomes a group under the same key with anchors, scroll and focus preserved, and shrinking restores the plain row). A settled successful Bash/Read call whose expanded details would be empty (`(no output)`, no error, diagnostics or artifacts) renders as one static, non-expandable line with its muted intent and “no output”. Shared `tool-presentation.ts` owns route/category/error/live-edit semantics; only ask and approval cards are never grouped, and every other settled call (task, wait, IRC writes, unknown tools) joins the adjacent Overview group and is counted as agents, jobs, messages or tool calls in its summary, while a running or queued task or wait keeps its own live row until it settles. A Wait is one header line in both densities (job name, outcome and clock, or a count and a truncated name list; the full list is in the tooltip and the expanded body). An actual live file edit/write stays expanded until terminal outcome, then returns to its run unless native focus/selection holds the detail. Late diagnostics stay attached to their file tool; unmatched diagnostics and native notices remain boundaries. Advisor notes validate severity/nonempty content, keep blockers discoverable and fall back to actual message content. Only proven visible user-attributed skills become user rows; exact prompts remain exact, legacy labels are explicitly reconstructed and expanded content/images stay disclosed. Goal/retry/fallback rows preserve native chronology; hidden data is excluded before counting, grouping, copying or announcements.

**Wait row and running badge (2026-10-08).** `wait()` in `tool-renderers.tsx` decides from the data whether expanding adds anything the one-line face and tooltip lack: several entries (the header ellipsizes names), a job's result, error, extra label lines or output notices, cancelled rows, an IRC message body, or the text of a rowless result. When it adds nothing (a lone job with a plain label, a lone agent, an empty progress), `ToolCard` renders a plain non-interactive row (`omp-tool-head--static`: no chevron, no button, nothing focusable) whose tooltip still lists every job's name, type, status, clock, exit code and first label line. A failed wait, diagnostics or attachments always stay expandable. The live clock is the longest awaited job's duration, ticking locally, in the right-aligned `omp-tool-elapsed` slot and kept after settling. No tool row shows a `running` badge next to its spinner any more; `error` and `skipped` badges stay (a failed call that is still running keeps its error badge).

**Chat presentation and reading.** Application-scoped `ompDesk.toolCallDetail` defaults to Overview and is changed in Settings (the composer has no control for it); host readback of the setting updates every panel/bridge route live without an OMP mutation, including read-only chats. The look is derived from the theme: `--omp-muted` and `--omp-border` are `color-mix` of the foreground over the page (72 % and 18 %; the theme's own `descriptionForeground` and `contrastBorder` in High Contrast), so Light Modern really dims, and radii come from a three-step scale (`--omp-radius` 4 px for controls, `--omp-radius-card` 6 px for cards, `--omp-radius-composer` 10 px). A tool row is one 26 px line: a settled call shows no mark (its status stays in the head's sr-only `role="status"`), the name is regular and muted, the digest neutral, an edit shows `+N −N` in colour, a TODO call its operation and `done/total`, a Task `N agents: A, B` with the per-agent list as its tooltip. An empty conversation shows the folder, model, key hints and up to three recent sessions of the same folder: the page sends `omp:recent-sessions-request` (panel route only), the host answers `omp:recent-sessions` from the rows the Sessions view already lists and keeps that answer per editor document, and a click sends `omp:open-recent` with the answer's id and an ordinal, which the host resolves only against its last answer and opens through the Sessions click (`src/wiring/recent-sessions.ts`). An aborted reply is one muted line, a provider error one line, `Handed off` sans and muted, and the working row carries a spinner and a text shimmer that stop under reduced motion (and, for the shimmer, in High Contrast and forced colors). Manual disclosures, draft, source anchor, focused tool and native text selection survive both density directions. `TranscriptScrollController` is the sole vertical scroll writer for the outer transcript: upward wheel detaches immediately before measurement can repin, and programmatic geometry changes cannot rearm following. Source aliases preserve viewport offsets through prepend, grouping, measurements and same-conversation rejoin. `MeasuredRows` uses measured prefix heights, roughly one viewport overscan and bounded focus/selection islands; expanded giant runs flatten their members into this same outer window. Groups, individual detail bodies and read-only child content grow in transcript flow without inner vertical scrollers. Long source/output/diffs initially render 200 head lines and 20 tail lines with in-flow incremental/all-line disclosure; wide code retains horizontal scrolling. Live edits/output follow only through the outer controller. Typography, width, font and theme changes invalidate layout, not semantic data. The normal 100-card admission window can grow on explicit older-history reveal without growing mounted DOM. Paged history has no in-chat control: it is on exactly when VS Code's `editor.accessibilitySupport` reads `on` (`auto` keeps normal virtualization), bypasses pacing, and preserves 100-card earlier pages during append/prepend without separate inner tool pages. Latest-page replacement waits for active focus/selection release. Browser Find is explicitly limited to mounted history; there is no hidden full-history DOM.

Long lines never widen the transcript (2026-10-13). Inline code, file, symbol and web links, URLs, long words, headings and list items in Markdown wrap at the block's edge (`overflow-wrap: anywhere` on `.omp-md` and its inline code); a block that cannot wrap scrolls inside a block of its own: a fenced code block's `pre`, a diagram's frame, a tool card's `.omp-pre`, and a table through its `.omp-table-scroll` wrapper. Inline code and link text in Markdown carry a `<wbr>` after every `/` and `\` (and after `.`, `_`, `-` only inside a segment longer than 20 characters), inserted by `breakable` in `components/BreakPoints.tsx` from `lib/break-points.ts`, so a long path wraps at a separator and only a segment still too long breaks by the `anywhere` fallback; a `<wbr>` adds no character, so copying, selection, link targets and symbol lookups see the text as written. The transcript is `overflow-x: hidden` only as a last guard; `chat-ui.test.ts` (and `mermaid-ui.test.ts` for diagrams) assert at 360, 480 and 900 px that its `scrollWidth` never exceeds its `clientWidth`.

Detached reading never restores an anchor while wheel/touch/scrollbar intent is active; native compositor movement owns that interval, then the controller captures its settled position. Tool-call and content-slot aliases precede shared entry aliases so a multi-call reply cannot redirect an anchor to a sibling. A reading source remains a bounded mount exception when its old offset exceeds an invalidated height estimate. Mounted rows are synchronously remeasured after revision or layout-cache invalidation, even when their size is unchanged and `ResizeObserver` has no new notification. Only jump-to-latest or actual downward user movement to the bottom resumes following.

Explicit Latest or a manual arrival at the bottom overrides pre-existing held focus/selection while tail measurements settle. A new native body interaction may hold content again, and upward input still detaches immediately. Focused headers remain bounded DOM exceptions without pausing following; only body focus or native body selection holds live content.

**Bottom anchoring and following (2026-10-06).** The bottom edge of the transcript viewport is the top edge of the composer dock, and the line a reader sees there stays fixed relative to it. Following pins the tail synchronously: `TranscriptScrollController` runs its pin from `ResizeObserver` callbacks (after layout, before paint) and from layout effects, so streaming growth and dock resizes are absorbed in the frame they appear in, never one `requestAnimationFrame` later. Detached anchors record the viewport height they were captured at and compensate when it changes, so a growing or shrinking dock (typing, paste, attachments, image tokens, the working chip, feedback lines, the ask card) moves the reading offset instead of the bottom line. Only upward input (upward wheel, PageUp/Home/ArrowUp) or a touch/scrollbar drag is intent to leave the tail; downward wheel, Space or End while following neither pauses the pin nor can detach, so jump-to-latest appears only when the controller is detached by the reader. Rows for assistant text keep their last measured height across revisions (`MeasuredRow.growing`) so a streaming reply never snaps back to a text-length estimate and churns mounts. The composer's `autosize` freezes the dock height while it measures, so no transient dock height is ever laid out and clamps the transcript.

**Queued messages (2026-10-07).** Chat lists OMP's own queue above the composer (`QueuedMessages`, in `.omp-dock`): the host reads `get_state.queuedMessages` and `queue_update` into `ChatLiteState.queuedMessages` (steering, then follow-up; no ids, so a message is named by its exact chip text). Remove and Edit send `omp:chat-queue-remove`; the host runs one `remove_queued_message` per item in order, stops at the first unconfirmed command, and answers only the asking page, by request id, with one `removed | gone | unknown | failed` entry per item and no message text. Edit appends the removed messages (and their images, renumbered) after the composer's draft and sends nothing; `gone` is reported as already sent or no longer queued, never dropped. OMP has no dequeue-all that leaves the run alone, so Edit all is a sequence of removals. See [Edit queued messages](designs/2026-10-07-edit-queued-messages.md).

**Stop, queue authority and TUI controls in Chat (2026-10-09, [ADR-0052](decisions/0052-answer-terminal-only-commands-and-restore-the-queue-on-stop.md)).** Guest protocol version 8: a page of an older build cannot receive the queue a Stop withdraws, so the host refuses it. Every Stop path sends `abort_and_restore_queue` once per request id (`RpcSession.abortAndRestore`). OMP withdraws the queue before it waits for the turn to stop, and the command waits behind any serial command, so its answer is awaited past the manual-compaction deadline rather than the ordinary 30-second command deadline. An OMP that answers `Unknown command: abort_and_restore_queue` gets a plain `abort`; its queue stays in OMP and in the dock. `ChatRuntime` answers only the stopping page with `omp:chat-abort-result`, carrying the withdrawn steering and follow-up messages, oldest first. The composer appends them to its draft and never sends them; entries past the host's cap of 64 and images it cannot hand back are flagged as truncated or dropped and reported. A queued steer therefore never runs as a new turn after Stop. Plain `abort` would let OMP's post-abort drain deliver it. The dock follows OMP's queue under one ordering rule. `RpcSession` counts `queue_update` frames and records the count on every command it writes. A `get_state` answer to a read sent before a later `queue_update` keeps the model's queue and applies the rest of the state; OMP 18.8.5 was observed writing such an answer after a `queue_update` that had already emptied the queue. A user `message_end` while the dock lists anything triggers a state readback, because OMP does not report every delivery of a live-steered message. **Send now** promotes a follow-up with `promote_queued_message` through the queue-request path (`purpose: "promote"`), and `Alt+↑` is an Edit of the newest queued message. Terminal-only builtins are classified from the installed OMP's registry, read by the staged `media/slash-registry.mjs` (`src/host/slash-registry.ts`); a new install root or version drops the previous list, and a failed read is not repeated for the same install. They are answered in the transcript with result `explained`, and a mapped Desk action runs. Compact, shake, model and thinking cycling, HTML export and share reach the host only as fixed `omp:chat-command` names; `runChatAction` asks for consent and chooses every argument. **Compact…** and **Shake…** (context popover, editor title menu, Command Palette) first ask for OMP's mode in a QuickPick: `/compact` `snapcompact` (preselected, no model call), `soft` or `remote` (these two then ask for optional focus instructions), and `/shake` `elide` (preselected, OMP's own default), `images` or `thinking`. OMP's RPC `compact` takes no mode and there is no RPC `shake`, so `RpcSession.maintain` sends the slash command as a `prompt` with an internal id and no `streamingBehavior`: OMP runs a builtin before any turn logic (a compaction during a turn aborts it and resumes it afterwards). A manual pass emits no maintenance event; observed with installed OMP 18.8.5, `/shake` reports one `command_output` line before its acknowledgement and `/compact` acknowledges at once and reports from the background (`Compaction complete…` / `Compaction failed: …`). The session therefore shows its own progress line from the send until that report, fails it on a `… failed` report or on an acknowledgement saying the text reached the model, and refuses a second pass meanwhile; the report itself still renders as the notice it always is. Retry re-sends `/retry` from the composer. `↑`/`↓` history is derived from the loaded user prompts (`src/chat/prompt-history.ts`), and `Ctrl+R` adds remembered prompts from other conversations (`globalState`). The thinking and tool-call defaults (`Ctrl+T`/`Ctrl+O`) are `globalState` values pushed with the display preferences (`lib/transcript-toggles.ts`). OMP extension widgets and info or warning notices render around the composer, and errors become VS Code error messages.

**Tool display mode (2026-10-14).** The Chat has one global tool display mode of three values (`src/chat/tools-mode.ts`): `collapsed` (every Overview group closed), `groups` (every group open, every call in it one collapsed line) and `all` (groups open, calls expanded, the TUI's `Ctrl+O`). Two commands move between them from a Chat only: `ompDesk.toggleToolOutput` (`Ctrl+O`, Expand/Collapse All Tool Calls) and `ompDesk.toggleToolGroups` (`Ctrl+Shift+O`, Expand/Collapse Tool Groups), by `nextToolsMode`:

| From | `Ctrl+O` | `Ctrl+Shift+O` |
| --- | --- | --- |
| `collapsed` | `all` | `groups` |
| `groups` | `all` | `collapsed` |
| `all` | `collapsed` | `groups` |

`Ctrl+O` expands whatever is not fully expanded and collapses only from `all`; the groups key closes the groups from `groups` and lands on `groups` from anywhere else. `Ctrl+Shift+O` replaces VS Code's Go to Symbol in Editor only under the Chat `when` clause (the IntelliJ IDEA keymap binds neither it nor `Ctrl+O` outside Java editors; its `Ctrl+Alt+O`, Optimize imports, is why that key was not chosen, and `Ctrl+Alt` is AltGr on many layouts). The host keeps the mode in `globalState` under the key that always held the `Ctrl+O` boolean, `omp.chat.toolsExpanded`: `true` is `all` (what every earlier build stored), the string `"groups"` is `groups`, anything else `collapsed`; an older build reads `"groups"` as collapsed. It is pushed with the display preferences as `toolsMode`, so it survives reload and webview restore and applies to every Chat of the profile. In the page, `transcript-toggles.ts` keeps the mode and a generation; `Transcript` forgets every tool block's own state on a change (`clearToolDisclosures`) and reads the disclosure map through `withToolDefault`: an unset `run:` key (group) reads open in `groups` and `all`, an unset `call:` key reads open only in `all`. So a group that arrives later follows the mode, a group or call toggled by hand keeps its own state until the next key press, and the mode only changes the fold state; `ompDesk.toolCallDetail` still decides whether calls are grouped (Detailed has no groups, so `groups` looks like `collapsed` there).

**Text admission and original recovery.** `omp:chat-send-result` reports accepted, refused or unconfirmed admission to the submitting page, correlated by request id independently of later epoch reconciliation. Transport acknowledgement and eventual native `prompt_result` are separate events. `ChatClient` registers before posting, bounds a missing receipt and never resends. `Composer` retains editable text/images while awaiting admission, blocks duplicate submit routes without blocking Stop, and clears only an accepted unchanged revision. Unconfirmed originals and refused edited originals remain in explicitly dismissible recovery cards; Add to draft uses the existing append-and-renumber merge and does not duplicate an identical still-held message. Native command feedback remains until dismissal; model/thinking control feedback retains its existing transient lifecycle. This does not create a local queue or repair an unresponsive native dispatcher.

**Complete composer handoff.** Guest protocol version 7 (now 8, see above) carries current text, attachment counts and bounded original/recovery records. A matching capture request freezes composer-local mutation through replacement, including delayed admission, image edits and programmatic insertion/prefill; in-flight image reads, IME composition and queue edits refuse capture. Cancellation/failure releases only that capture token. The host binds replies to the exact source document and retains the transfer until the new guest document acknowledges it; repeated Ready cannot restore into the frozen source, and a wrong document or request cannot consume it. Restored originals are recovery cards, not submitted messages. Missing image bytes retain explicit reattachment warnings and reserved marker numbers. No text or images are added to saved editor state, logs or disk.

**IRC rows.** `irc:incoming`, `irc:autoreply`, `irc:relay` and `irc:workpool` custom messages are one flat, collapsed-by-default tool-style row (`omp-tool omp-native-irc`: chevron, `comment-discussion` icon, bold `IRC`, `from → to`, kind and a muted one-line truncating preview). Expanding shows pool/mode/reply-to and the full body as Markdown; disclosure is controlled by `Transcript` (`irc:<conversation>:<row id>`), so it survives virtualization. In Overview, these native custom-message cards join consecutive eligible tool cards in a counted summary run; expanding renders the individual messages with their existing disclosures. Incoming and outgoing messages are counted as messages, not all described as sent. Detailed keeps the individual rows. Run members retain source aliases and native focus/selection across density changes; storage and call/result ownership remain unchanged.

Combined ComposerDock/FlatGroups installed acceptance exercised the whole native 120-read history with real wheel input over an expanded Read body: no detached repin, zero source-anchor drift through expand/font/resize, at most 57 mounted rows and no nested vertical overflow owner. Explicit Latest and manual-bottom following both reached the measured bottom. The same artifact proved the rounded metadata dock, quota reset countdowns and slash badge spacing; canonical checks and packaged/built/installed bundle equality are recorded in the [design evidence](designs/2026-10-04-paseo-style-chat.md).

**Paced replies and actions.** Canonical text remains complete in the shared model. Mounted append-only live prose/reasoning uses grapheme-safe rAF reveal; historical/remounted/replaced/terminal/hidden/reduced-motion/paged content flushes without replay animation. Native selected Markdown DOM is retained until release. One finished-reply footer copies canonical prose only and reports clipboard failure. **Bottom-block HUD rows and detail tabs.** Two flat tool-style rows sit at the bottom of the chat column, directly above the composer card and below the transcript: `TodoHud` then `RunningAgents` (the TUI's order), rendered by `HudDock` at the top of `.omp-dock` (the rows plus `Composer`). They are in normal flex flow at the transcript's column width (about 840 px, aligned with messages and the dock), with no panel background or full-width band, and never inside or scrolling with the transcript, whose viewport ends above them. The rows are part of the measured bottom block: expanding, collapsing, appearing or disappearing one resizes the transcript viewport exactly like a growing composer, and `TranscriptScrollController` keeps the bottom visible line fixed against the block's top (following stays pinned, detached holds its line). Both start collapsed, AGENTS exists only while native registry members remain and TODO whenever tasks exist. Collapsed, each is one line: TODO shows the current task and one counter with an accessible name, Agents shows counts by state and who is doing what. Expanded they show the TUI's density, at most eight rows and a `+N more` button, with no scroll region and no status chips: TODO is a walking viewport (the phase holding the actionable task, closed lead-in, later phases as headers only), Agents is one line per agent (`id ⟨type⟩: description  tool · intent  elapsed`). Transport identifiers, timestamps, source/index, raw progress records and statistics never render in the pinned rows. Todo phases come from dispatch-time state cuts and later successful non-view live updates; old disk/RPC rows cannot overwrite live authority. Closed means completed or abandoned. The projections are in `src/chat/hud-summary.ts`. The full content opens in editor tabs ([design](designs/2026-10-06-todo-agents-rows.md)): the TODO tab (phases, blockers, details, notes), the Agents roster tab and one tab per agent with a read-only child transcript that re-reads the newest rows every two seconds only while the agent is `running` (a failed refresh keeps the rows already read and says so). A detail tab is a presentation page of an existing conversation, not an editor slot: `omp:open-detail` is accepted only from a panel route, the host builds it with `createDetailHtml` (same CSP as chat, `connect-src 'none'`, no identity or bridge meta, so VS Code has nothing to restore) under the view type `omp.detail`, and `DetailTabs` (`src/host/detail-tabs.ts`) keeps one tab per conversation, kind and agent id, forwards to the conversation only `omp:ready` and the child read, and closes the tabs when the conversation is forgotten or its terminal mode takes over. Leftover tabs from before a window reload are closed at activation (there is no serializer). Child history is lazy and read-only, native-id gated, limited to 200 retained rows per page and two nested levels, with explicit unavailable/reset/paging states and no composer or lifecycle controls. The bottom Tasks/Plan panel and all exclusive projection/staleness machinery are removed; plan content stays in the transcript.

**Roster identity for revived agents.** The native roster drops an agent when it parks, and the frames of an IRC wake carry the message as `task` with no label (a cold revive even reports its own id as the type), so the chat model keeps each agent's type, label and assignment in `agentIdentity` (snapshot-carried, bounded to 256) and re-applies them to a woken agent; with nothing remembered it reads the type and assignment from the transcript's `task` call, and otherwise shows the id alone. A detail tab may ask the host for a sibling detail tab (`omp:open-detail`), which `DetailTabs` answers itself without reaching the runtime, so a roster row opens or reveals that agent's own tab. **Registry liveness rows (2026-10-09, [ADR-0053](decisions/0053-merge-a-desk-published-registry-liveness-signal-into-the-agents-row.md)).**

- **The gap.** OMP 18.8.5's RPC roster hears only task-executor monitors. A finished subagent that a parent's `write agent://` steers into another run therefore never appears in it. Its registry ref also stays `idle` while it works.
- **Publisher.** `registerAgentLiveness` (`src/omp/agent-liveness.ts`) runs in every binding of the `-e` host-control module.
  - Subagent bindings record their own `agent_start`, `turn_start`, `tool_execution_start` (tool and intent) and `agent_end` in a process-global store.
  - The first `rpc`-mode main binding subscribes to `AgentRegistry.global().onChange`. It publishes `{v, instance, seq, sessionId, agents[{id, agent, state, sessionFile?, tool?, intent?}]}` through its own `ctx.ui.setStatus("omp-desk.agent-liveness", …)`, with at most 32 agents and 16 KiB, shedding detail rather than skipping.
  - It coalesces at 150 ms for edges and 1 s for activity. It re-checks every 2 s only while an agent is live as `idle`, and repeats a non-empty set every 10 s. Nothing runs while no subagent is live.
- **Shared derivation.** `subagentLiveState` is also the rule for `hasLiveSubagents`. It counts `running` (not a stale accepted run), `idle` with queued messages, and `idle` with a streaming session whose own binding observed new work after `lifecycle.terminalAt`.
- **Host and page.**
  - `RpcSession` takes that status key out of the status line. `AgentLivenessGuard` (`src/chat/agent-liveness.ts`) accepts only the bound session id, with a newer `seq` per publisher `instance`. It keeps the newest list, re-applied after a resync reset unless the replay was truncated.
  - The shared reducer folds the accepted list as `agents_liveness` (`reduceAgentLiveness`, `src/chat/agents.ts`). RPC rows stay authoritative and are only annotated with `liveState`. Unlisted ids become `origin: "registry"` rows, running with the published activity and the remembered spawn identity. The next publication that omits a registry row removes it.
  - Any RPC frame for an id takes its row over. A terminal frame removes it, unless the newest publication reported the agent `idle`-live, in which case the row is kept as a registry row. `get_subagents` snapshots keep registry rows.
- **Installed check (2026-10-09).** In owned isolated windows with real OMP 18.8.5, a parent spawned a subagent that finished, then sent it a `sleep 45` follow-up (receipt "Delivered").
  - The pre-fix build showed no Agents row for the whole 45 s.
  - The fixed build showed "Agents 1 running · <id>: bash · Sleeping forty-five seconds" throughout, and removed the row within about a second of the subagent's final reply.

**Waiting for background work (2026-10-13).** While OMP's `get_state.hasPendingAsyncWork` keeps the turn open but the agent is not working (`asyncPaused`, no stream, no dialog, no compaction), `src/chat/background-wait.ts` replaces the row's intent and whole-turn timer with “Waiting for background job: <name>”, “Waiting for N background jobs” or “Waiting for background work”, timed from the newest transcript message (when the agent last did something). OMP 18.8.5 reports background work over RPC only as that boolean: there is no job list, no job start/end event and no RPC command to cancel a bash job, so the names are inferred from the transcript (a started job is a tool result with `details.async.jobId` and the call's `i` or command; `job`/`wait` listings update it; an `async-result` custom message ends it). Jobs older than the loaded window, extra task spawns and jobs cancelled outside the transcript are not seen, so a count can be low and the generic sentence is used when none can be named. No cancel control is offered: the only cancel command OMP exposes over RPC is `cancel_subagent`, which covers subagents, not bash jobs, and Desk does not call it. When the agent works again the row returns to its intent and the turn timer.

**Catalog I/O and ledger size.** No catalog read, lock, write, `fsync` or rename retry runs synchronously on the extension host's thread (`src/host/profile-catalog.ts`), and the conflict ledger keeps the newest three records per `(key, identity, reason)` with an `earlier` count of the dropped ones, applied on the next committing transaction ([ADR-0034](decisions/0034-store-sessions-in-one-profile-catalog.md) amendment, 2026-10-12). `src/host/loop-lag.ts` logs every extension-host stall of 500 ms or more to the OMP Desk output with the marked Desk operations that overlapped it.

**Session ownership and witnesses (`session-availability.ts`, `session-index.ts`, `rpc-reconcile.ts`, `session-claim.ts`).** [ADR-0039](decisions/0039-refuse-only-on-a-verified-live-writer-the-extension-owns.md) governs every user action: only a local running runtime, an exact live child authenticated under the extension's own broker, or another verified-live extension-window holder may block or require stopping. A recorded RPC tuple `{slot, brokerId, brokerGeneration, childPid, childCreationTime}` is re-proven by the authenticated broker handshake and, for a current-build broker that holds its pipe child's handle, the broker's own attestation of that child ([ADR-0035](decisions/0035-distinguish-a-recorded-process-from-a-later-occupant-of-its-pid.md) amendment of 2026-10-13, accepted after independent architecture review); whatever is not attested is proved by this window's own kernel reading taken for that proof. Legacy broker children use their authenticated slot plus child generation. Unknown, missing, dead, mismatched and unanswerable observations are unowned, without a release step. No PID-only kill exists. Claims replace dead/unverifiable records under the identity mutex; unusable storage/mutex gives a process-local lease without namespace mutation. This accepts unrecorded-launch/external-writer races, not global exclusion. Accepted absence evidence still gates **automatic** running-intent relaunch only.

Concurrent RPC ownership reads for the same client, slot, recorded broker/child identity and kernel reader share only their in-flight proof. Settled and failed proofs are discarded, so later reads revalidate the live identity; the kernel creation-time readings under them follow the same rule (`PtyIdentityReadings` keeps nothing once a probe answers). Native proofs remain independent. This prevents simultaneous Sessions/Open checks from consuming redundant bounded broker connections and turning a live writer into an unowned observation.

**Legacy rows.** A missing managed `transport` discriminator denotes an earlier-build record; explicit `rpc` and `native` are managed transports. A positively verified historical `managed-omp` child is Running (legacy) and is not silently migrated. Its explicit confirmed stop-and-continue and truthful broker stop remain; unverifiable legacy rows are usable stopped/draft rows. Ordinary Open on any existing managed editor only reveals it. Reload requires an actual reattached runtime and preserves its mode.
Explicit Stop verifies that legacy broker's recorded child gone, then requests the existing protocol-v2 `shutdown` with `requireStopped:true`. It disconnects, forgets the conversation's broker mapping and clears its cached restore conflict; the broker's own record stays as recovery metadata. A shutdown refusal is disclosed without undoing the writer-gone proof.
A fresh fileless draft launch clears the previous draft host's session id before recording its new attempt, so the first current-runtime identity can be accepted and its file promoted. Existing-file resume IDs stay pinned; a confirmed not-started launch restores the prior draft identity. Current-runtime and differing-ID fences are unchanged.

An allocated native session path need not exist before the first assistant response. Repeated observations of the same runtime/file/session identity keep one pending promotion retry rather than restarting it or invalidating the Sessions projection. Materialization still requires the exact header and claim; a changed promotion failure remains diagnostic.

**Folder navigation and history query.** Folders are navigation only; they never change VS Code workspace roots or session ownership. Sessions shows one per-window list (`LauncherFolders`, `src/views/launcher-folders.ts`, [design](designs/2026-10-07-window-folders-and-other-window-state.md), [ADR-0045](decisions/0045-derive-window-folders-per-window-and-pin-with-identity-ids.md)): the folders VS Code has open in this window (local `file` roots, VS Code order, live on `onDidChangeWorkspaceFolders`, hidden by `ompDesk.showWorkspaceFolders: false`), then the other **pinned** folders (the profile-wide `WorkspaceFolderRegistry`, catalog key `omp.workspaceFolders.v1`, stored order), then folders kept visible only by a session running or launching in this window. Entries are deduplicated by `folderIdentityKey`; a folder both open and pinned appears once with the pin icon. Window folders are never persisted. A folder's id is `windowFolderId(path)` (a hash of its identity key), and Pin stores the record under that id, so Pin and Unpin never change a row's identity or a folder command's argument; records from earlier builds keep their ids. Collapsed state is in the pinned record for pinned folders and in this window's workspace state (`omp.windowFolderCollapsed.v1`) for the others. Pin and Unpin replace the old Remove; Unpin is metadata-only and never refused by a running session: a folder this window has open or runs a session in stays visible, unpinned. Every consumer (New Session, Resume Session, Open Terminal, `folderArgument`, the Add Selection/File picker, the welcome context) reads this one list. On-demand Resume Session scans readable exact files and canonical indexed paths, deduplicates them and exposes the same exact-path Delete transaction regardless of provenance. Header/path integrity is revalidated; ownership uncertainty is not a refusal.

**Agent root folder.** An open folder is shown as its repository's agent root when the repository's agent files are there and not in it (`src/views/agent-root.ts`, setting `ompDesk.useAgentRootFolder`, default on; [design amendment](designs/2026-10-07-window-folders-and-other-window-state.md#agent-root-substitution)). For an open root `R` with none of the markers (`AGENTS.md`, `CLAUDE.md`, `.agents/`, `.omp/`, `.claude/`, `.pi/`, one constant), the walk goes up from `R`'s parent to the nearest ancestor holding `.git` (file or directory), inclusive and never above it, and the nearest directory on that path with a marker replaces `R`; no `.git` ancestor, or no marker on the path, leaves `R`. The probe is asynchronous (`AgentRootResolver`, at most the depth to the repository root per open folder), runs at activation, on `onDidChangeWorkspaceFolders`, on window focus and when the setting changes, and the synchronous `LauncherFolders.list()` reads the remembered answer, so an unresolved folder shows as itself and the tree repaints when an answer differs. The substituted folder carries the opened roots as `openedPaths`; every consumer of a folder's path (New Session, the folder pickers, folder Resume and history, shells) therefore uses the ancestor. Rows are filed by recorded cwd, and `folderOwnsCwd` also files sessions recorded in an opened subfolder under the ancestor, unless another shown folder names that subfolder itself (a pinned one), so such sessions never disappear and never appear twice.

**Sessions state and actions.** Fresh positive ownership facts override cached availability for RPC, explicit native and legacy children. A verified rival-window holder has the `otherWindow` state (its row shows the holder's published status and that status's icon, plus a `⧉` file-decoration badge after it in the windows that do not run the session; the unread dot stays), with Stop available for the rival's recorded host. Open and a click switch to the owning window at once, with no notification or confirmation, and never launch; the claim is re-read first, so a released claim opens normally ([ADR-0056](decisions/0056-publish-window-state-in-a-leased-registry-and-switch-windows-by-request.md)). The state is an observation, not an authority; all launch paths still go through claim admission. It updates without a manual refresh when the other window opens or stops a session: `src/host/claim-watch.ts` watches the claims directory (`fs.watch`, non-recursive, not persistent, 150 ms debounce, spawns nothing), and changed claim names map only to affected rows for re-observation. A normal window close or crash releases no claim (children and claims outlive the extension host), so the row is rechecked on focus, visibility change or click. Processes uses the same displayed ownership state when it refreshes. Unowned records are Stopped/Draft. Native lifecycle reattaches rather than launching a process just to stop it, uses guarded SDK grace, and requires separate force consent when grace/control is unavailable. A missing transcript offers Forget. Stopped Chat paints history; stopped Terminal keeps an attachable broker screen or a recovery placeholder, never silently spawning.

Other-window rows show the status the holder publishes for that exact run (`sessionIncarnation`: owner generation plus host start and pid; Running when none is published or the run differs), with the unread mark derived from the shared reply markers like everywhere else; they are ordered, and their age shown, from the owner's published `lastActivityAt` (a current publication's `null` means no activity; only a row with no current publication falls back to this window's own reading of the same session file); the tooltip says `Open in another window: <label>`. Claims carry an optional display-only owning-window URI, separate from all ownership evidence: the saved local workspace file, or the single local folder when there is no workspace file. A click or Open on a row this window does not run, while a fresh claim read shows a live claim of another window, **switches** (`switchToSessionWindow`, `src/host/window-requests.ts`): it re-reads the claim, writes `window-requests/<holder id>.<id>.request` (naming the run and the editor binding (slot and generation) the holder published), arms a withdrawal timer for 5 s from that moment and calls `vscode.openFolder(uri, { forceNewWindow: true })`, which focuses the window that already has the folder or workspace and cannot replace this window when the owner has just closed (observed on VS Code 1.141.0). The owner serves a selection-only request (`selectHeldSessionTab`; one queue, four at a time, sixty-four waiting; rescanned on focus and heartbeat): only while the requester still waits and, read together after a fresh claim read, the claim names it as holder under its catalog's owner generation, its catalog records the requested run, it has a live host for the session and the editor binding is the slot and generation the request names (checked again after selecting; the serializer's restore of that tab is deferred until its revival, however late) does it select the editor it already has (a not-yet-revived editor is shown by VS Code, whose serializer path starts nothing while a live host exists); it never launches, stops, takes a claim, changes a mode or forwards a request, and answers in a correlated, bounded `.response` file that also says whether its window reported focus. A message appears only when switching is impossible or incomplete and says why: no usable URI (an unsaved multi-root window, whose record says `windowUri: null` authoritatively), two windows with one URI identity (`openFolder` cannot address a holder id), no answer within 5 s of posting, an owner without the editor or the run, or an owner that could not confirm its window came forward. Only sessions held through a claim are routed; a history-only editor in another window has no claim and is not.

**Window registry** (`src/host/window-registry.ts`, `atomic-file.ts`, `directory-watch.ts`; [design](designs/2026-10-10-multi-window-sessions.md), [ADR-0056](decisions/0056-publish-window-state-in-a-leased-registry-and-switch-windows-by-request.md)). Each extension host writes `<global storage>/window-registry/<holder id>.window` (versioned, bounded: at most 512 KiB, 64 folders, 256 live cwds, 512 rows; rows are budgeted first, an entry that does not fit is dropped whole, never truncated; reads are bounded): pid, start time, lease stamp, window URI and label, the `file` folders open as opened, the cwds of its live sessions and `{status, incarnation, binding, lastActivityAt}` per session it runs. Writes are serialized and atomic (exclusive stage, rename with the Windows retry of claims), on change (250 ms debounce) and every 15 s; a normal close deletes the record and cancels an in-flight write. A record of another window counts while its stamp is within 60 s and not more than 5 s ahead of the reader's clock **and** its pid exists; unchanged expired files are swept once their modification time is a lease old, whatever the pid. A directory watch, focus, view visibility and the heartbeat re-read it, repainting only when the shown content (not freshness) changed; the heartbeat also re-probes agent roots for the complete live root set, rescans the request directory and, while the Sessions view is visible, re-observes every row's ownership and conversation activity (a hidden view re-observes the rows shown as held by another window or Checking). A window publishes its snapshot before repainting its own tree. Bounds, scan included: about 0.4 s for a published change, 15 s for a missed event or a crash plus one observation, 75 s for a hung host; a hidden view converges when it is shown. `LauncherFolders` shows the union of every live window's folders (agent roots applied by the reader, deduplicated by identity), the pinned folders and live-session folders, in window-start order; the settings `ompDesk.showWorkspaceFolders` and `ompDesk.useAgentRootFolder` are `application` scoped. The registry is advisory: it never admits or refuses a launch, and expiry never frees a claim. A session whose host outlived its window is listed again in an unpinned folder only when that folder is open somewhere or pinned. Which row shows another window as holder, and which window a click goes to, use a reading of the holder's process start time taken by an asynchronous command, kept for 20 s and valid only for claims that existed when it was taken (`claimHolderSeemsAlive` in `session-claim.ts`); launches, stops and deletions still read it at their own verdict (`claimHolderMayBeAlive`). The same reading used to be a synchronous command per verdict on the extension host's event loop, which froze every window for seconds on every switch.

**Activation and the window's start time.** The claim holder's process start time (the start-time rule of [ADR-0035](decisions/0035-distinguish-a-recorded-process-from-a-later-occupant-of-its-pid.md)) is a PowerShell reading, hundreds of milliseconds idle and seconds on a busy machine. `activate` starts it (`readProcessCreationTime`, `session-claim.ts`) and does not wait: the `SessionIndex` is built with the holder without a start time and with the pending reading (`claimHolderCreationTime`), and only `acquireClaim` waits for it (`claimHolderReady()`), so what a claim files is still verified while the Sessions view, the commands and the editors register at once; everything that only compares holder ids never waits. The installed Nerd Font list (another PowerShell command, loading System.Drawing) is read when the first terminal pane asks for its font, not at activation.

**Startup restore concurrency (2026-10-13).** `SessionIndex.restoreAll` restores the activation cohort with at most four rows in flight (`RestoreAllOptions.concurrency`, pool in `src/host/session-restore-trace.ts`), starting rows in cohort order. Each row is still one restore under its own tab-lifecycle gate; catalog writes stay on the index's single persist chain. The "one writable session per pass" rule is decided in cohort order among rows that name the same identity (`IdentityTurns`), so the first row of the cohort to reach the check keeps it. The report is folded in cohort order, not completion order, and a row whose restore throws becomes that row's `failed` outcome. Controller elections after the pass remain sequential: `bindEditorSlot` rolls back to a pre-await snapshot of the bindings, so concurrent elections could undo each other. Each row logs `window timing: restore tab …` with its admission/reconcile/attach|launch/persist durations (attach split into connect and trusted or probed identity), and the pass logs one activation → catalog adopted → restore started → restore finished timeline line.

**Launch in the folder's window** (`planLaunchRoute`, `routeLaunchToFolderWindow`, `serveLaunchRequest` in `src/wiring/window-routing.ts`; `src/host/window-requests.ts`, `src/host/unity-project.ts`; [design](designs/2026-10-10-launch-in-folder-window.md), [ADR-0057](decisions/0057-start-a-session-in-the-window-that-suits-its-folder.md)). An explicit launch (New Session from any entry point, Resume Session from a folder's history, opening a stopped or draft row, in an explicit view or not) starts in a window that has the launch's workspace open: the Sessions folder, or for a Unity project (a directory with `ProjectSettings/ProjectVersion.txt` and `Assets/`, found in the folder or two levels below it, one asked once per folder and remembered) the project folder as one of the window's own roots, while the session's working directory stays the Sessions folder. Here when this window has it; else the most recently focused live window that has it (the registry record's `focusedAt`); else, for an ordinary folder here, for a Unity project a new window opened on it. A hand-over is a `launch` request on the ADR-0056 request channel (workspace, plus `new-session`, `resume-folder` or `open-session`; 11 s lifetime, 10 s answer wait): the receiver checks that it has the workspace and knows the folder or session, starts the launch through the same function a click there runs, never routes it again and answers on admission. The requester never launches locally afterwards: a refusal or a timeout is a message (the request is withdrawn on timeout). A new window's launch is a pending file `pending-launches/<identity key>.<id>.pending` (65 s lifetime, 60 s wait) that the new window claims by exclusively creating a `.claimed` marker, so exactly one window starts it. `ompDesk.launchInFolderWindow` (default true) turns it off. A window whose installed package changed under it publishes `stale: true` in its registry record and is never chosen (a launch whose only candidate it was starts here, also for Unity); one that is asked anyway refuses first with the reason `stale-build`, and only that definite answer makes the requester start the launch itself.

**Reload All Windows** (`ompDesk.reloadAllWindows`: `reloadAllWindows`, `serveReloadRequest` in `src/wiring/window-routing.ts`; `postReloadRequest`, `awaitReloadTakenUp` in `src/host/window-requests.ts`; [ADR-0056](decisions/0056-publish-window-state-in-a-leased-registry-and-switch-windows-by-request.md) amendment). The command (Command Palette, Sessions title overflow, no confirmation) re-reads the window registry, writes a `kind: "reload"` request, which carries no argument, to every other live window's `window-requests/<holder id>.<id>.request` and waits for all of them at once for at most 2 s (`RELOAD_ACCEPT_TIMEOUT_MS`), then runs `workbench.action.reloadWindow` here whatever each window did; a window that is not answering never holds this one back. A receiver takes the request up like a stop (one atomic rename to `.accepted`, so a requester's withdrawal and the take-up cannot both win), writes its response, deletes the accepted file and only then runs its own reload (`ServeOutcome.afterAnswer`), so the extension host that starts afterwards finds nothing to act on and cannot reload in a loop; a request older than 6 s (`RELOAD_REQUEST_TTL_MS`) is deleted unacted, and the requester withdraws one nobody took up when its wait ends. The requester tells the outcomes apart in the log: `.accepted` or `.response` present (the window is reloading), the request deleted with neither (a build that predates the kind: its parser rejects the unknown kind and deletes the file, so that window is not reloaded and must be reloaded by hand), or still present at the bound (withdrawn). A second invocation while one runs joins it.

**Outside OMP writers.** A plain `omp` (typically in a terminal) that writes a session holds OMP's session ownership lease, a named Windows mutex, until it exits; the extension only *opens and closes* it read-only ([ADR-0046](decisions/0046-probe-omp-session-lease-for-external-writers.md), [design](designs/2026-10-07-external-omp-session-lease.md)). `src/host/omp-session-lease.ts` derives the name (`Global\omp-file-lock-` plus two XXH64 values of the lock path `<home>/<PI_CONFIG_DIR or .omp>/run/session-owners/<session id>.lock`, verified against OMP 18.6.3) and `ExternalLeaseObserver` serves all rows with one run of the staged `session-lease-probe.ps1` (cached 2 s; a `fresh` request waits for a newer probe, bounded at 5 s; an access-denied answer reads as held). `launcherOwnershipFacts` adds `externalOmp` only when no claim of another window, no live claim of this window and no verified broker writer can be the holder (their children hold leases too; a child none of these can verify is reported as external); `sessionItemState` shows **Open in another OMP process** (`externalOmp`, `terminal` icon) after `otherWindow`, `starting` and `restoring`. A click or Open on such a row re-probes and asks; every explicit attempt that can start a writer (`openTabOnce`: verb *resumed*, or a row whose run intent is not stopped) asks the same question through `confirmOpenAnyway`, and `openSession` reports whether it proceeded so Add to Session adds nothing after Cancel; history views of stopped rows never ask. Known limitation: a restored editor and the activation pass's automatic relaunch do not consult the lease. A failed probe, an unknown derivation or an unreadable header leaves rows as before and logs. The lease exists only after the other process has written the session.

**Session row context menu.** The menu is the `when` clauses in `package.json` evaluated over the row's `contextValue`, `ompSession.<forgettable|held>.<state>.<resumable|live-only>.<deletable|file-kept>.<materialized|fileless>.view-<chat|terminal|none>` (built in `src/views/session-tree.ts`; the `view-*` segment is the view this window's open editor shows, from `SessionLauncherFacts.viewMode`). It follows what each command does: **Open in Chat/Terminal** (`openSessionInMode`, verb *open*) launches, so only stopped and draft rows get it, while a live row's **Show in Chat/Terminal** (`ompDesk.showSessionInChat/Terminal`, the same handler with verb *show*, hidden from the palette) reveals the existing editor, or reopens it when only the tab was closed, and is offered only for the view the open editor is not already showing (both when no editor is open or its view is unknown). `background` ("Waiting for subagents") is live everywhere `working` is. A folder node's `contextValue` is `ompWorkspaceFolder.[shells.]<collapsed|expanded>.<pinned|unpinned>`: Pin Folder is offered on unpinned folders (also inline) and Unpin Folder on pinned ones.

Sessions title navigation contains Open Stats, the layout button, Stop Orphaned and Idle and Kill All; New Session and Resume Session are rows of the list, not title buttons (2026-10-11); default-mode choices stay in overflow. An empty folder has a folder-scoped launch placeholder. Stopped and draft rows expose inline Open as well as their mode-specific menu actions, while existing single-click history and second-click resume behavior remains.

When a successful default-profile `omp models --json` read reports no available models, Sessions prepends one stable account-icon action, **Log in to a model provider to start**, which runs `ompDesk.loginProvider`. The window caches this observation and refreshes asynchronously on activation, when a provider login or logout completes, when a fallback **omp login** terminal closes and when a Chat reports changed model availability. An unresolved OMP adds no row; activation never waits for discovery. The row is independent of folder/session membership and disappears once models are reported.

Rename of a live row not yet attached in this window reattaches its verified writer first (as Reload does) and renames through it. The Delete button retains writer-stop, exact-file, ownership and frozen-target checks; Cancel returns without a redundant notification.

**Sessions panel.** Persisted rows publish immediately as **Checking** while ownership/title enrichment proceeds, rather than waiting for the complete restore scan. Only current-revision publication updates retained row/folder identities; superseded reads cannot mutate the visible projection. Positive local/authenticated ownership remains distinct from activity. Rows distinguish **Working**, **Waiting for subagents** (including asynchronous jobs and undelivered results), **Needs your answer** only for structured dialogs, and **Idle** only at proven idle. Fresh non-running sessions also use Idle; stopped saved sessions remain Stopped. **Unread reply** is supplementary, not proof of idle. Requests appear immediately; completion waits for full background/result-delivery drain. Stopped single-click remains non-mutating, rapid second-click/Open launches through the existing gate, and running clicks reveal their editor. Profile default-mode selection never changes existing tabs. The [Sessions startup/work-status design](designs/2026-10-04-sessions-startup-and-work-status.md#implementation-evidence) records the accepted coordinated checks, package and installed proof and the earlier runtime observations: one paired first-leaf measurement of 10.673 → 2.853 seconds from recorded launch, and real asynchronous waiting with one completion only at true idle. These are bounded observations, not a latency distribution.

**Flat Sessions list, unread marker and selection pin.** `ompDesk.sessionsGrouping` (`flat`, the default, `folders` or `terminals`) is read by `SessionTreeProvider` through `SessionLauncherSource.grouping`; the layout picker only writes the setting (and the `ompDesk.sessionsLayout` context key picks which icon shows), and a configuration event refreshes the view, which then fires one root change. Both layouts are built from the same per-folder rows, so every row action, context value and state icon is unchanged. The flat list has one root-level row per session of the folders the grouped view would show (a row is listed once), labelled `folder · title` with folders of equal name widened by parent components (`flatFolderLabels`), and ends with a `New Session…` row whose command is plain `ompDesk.newSession` with no argument: the existing folder QuickPick (or Add Folder flow) and `newSession` path are used, not forked. A `Resume Session…` row (`history` icon) follows it and runs plain `ompDesk.resumeWorkspaceFolder` the same way; like the New Session row it is not a session, so `selectionRestore` puts the pinned selection back when it is clicked. Empty with no folder at all, so the view's welcome content shows. Order (`src/views/session-order.ts`, pure; 2026-10-13 amendment, before it rows were ordered by unread mark and last activity): rows whose process is not stopped (`stopped`/`draft` are the stopped group) come first and stopped rows follow; each group is alphabetical by folder label, then by session title (`Intl.Collator`, case-insensitive, numbers in numeric order), then older ordinal. The folders layout orders the rows inside each folder the same way; folder nodes keep their own order. A reorder is a root change; a presentation change repaints the row. **Unread** reuses the two identities the index already persisted: `lastCompletedReplyId` (catalog, shared) and `lastSeenReplyId`, both in the shared catalog row (an earlier design kept the second in the window's workspace state, which a window that opened another folder lost, marking every finished session unread). `TurnNotifier` reports every earned event (a finished, not aborted, turn or a question), notice sent or suppressed, through `onEarned`; the native ledger does the same through its suppression callback. `recordSessionEvent` mints a fresh event identity (`src/host/session-unread.ts`) and, when the user is looking at the session (`isLookedAt`: the editor in front, visible, in the focused window; the notification-suppression notion without the `ompDesk.desktopNotifications` switch), also marks it seen. `settleViewedSession` marks the front session seen on refresh, tab change and window focus. The row carries a `●` decoration badge (a `FileDecorationProvider` the provider exposes, keyed by an `omp-session:` `resourceUri`), `Unread · ` before its status and an `Unread reply` tooltip line in both layouts; a row a plain `omp` runs is never shown unread here, while a row another window holds shows the mark like its owner does, because every window derives it from the same shared markers; reading a session in any window clears the mark in all of them. **Selection pin** (`src/views/session-selection.ts`, pure): while a session has an open editor in this window, `pinnedSessionTab` (the most recently focused session editor of `EditorRecency` whose row is shown) is what `revealActiveSession` selects, and `view.onDidChangeSelection` puts it back (`selectionRestore`) when the selection holds no session row; picking another session row is left alone and the selection follows once that editor is viewed. Reveals keep `focus: false`. VS Code limits: a TreeItem label cannot be styled and a long label truncates the description (observed: the description vanished), so the mark is a decoration badge, which stays visible; and a pinned row inside a folder the user collapsed cannot be selected without expanding it, so the grouped view leaves that selection alone.

**Reply identities only advance across windows (2026-10-14 amendment to ADR-0034).** The shared session row is merged whole (`mergeSessionIndexRecords`), and a window that adopts another window's row does not move its merge base, so it later writes that adopted copy back as if it had changed it. The unread marker used to be lost that way: after Reload All Windows a window that adopted the row before the user read it saved the row again with an unrelated change and replaced the newer `lastSeenReplyId`, while the window that runs the session (a live row, which `SessionIndex.refreshFromStore` leaves as it is) kept its own copy and, finding itself already read, never wrote again, so the row stayed Unread in every other window however often it was viewed. Both identities are now merged field by field with `laterReplyMarker` (`src/host/session-unread.ts`): the identities this module mints order by time and repeat count, and the later one wins whichever side holds it (an identity that cannot be ordered goes to the side that changed it since the base). `refreshFromStore` applies the same rule to rows the window runs, and writes the row back when its own identity is the later one, so a catalog that lost a read is repaired by the window that recorded it. Unread still means a reply earned while nobody looked; a row that is Working again after such a reply stays Unread until it is viewed, and viewing clears it from any window.

**Three Sessions layouts (2026-10-11 amendment).** `ompDesk.sessionsGrouping` is `flat`, `folders` or `terminals`. One title-bar button opens a QuickPick of the three layouts (`chooseSessionsLayout`, pure items `sessionsLayoutPickItems` in `src/views/session-order.ts`, the current one marked); the button is three commands (`ompDesk.chooseSessionsLayout.flat/.folders/.terminals`) that all open the same picker, shown one at a time by `ompDesk.sessionsLayout` so the icon shows the current layout, and `ompDesk.chooseSessionsLayout` is the palette entry. The context key `ompDesk.sessionsLayout` replaces `omp.sessionsFlat`. The `terminals` layout lists the background processes (see Sessions processes above). The Terminals group closes the flat and folders lists, after every session or folder and the New Session… and Resume Session… rows, set off by an inert blank row (`SpacerTreeItem`: no command, no context value; a TreeView has no separators); when nothing else is listed the group stands alone with no spacer. The title bar is Open Stats, the layout button, Stop Orphaned and Idle and Kill All.

New staged native hosts request-gate `nativeActivity({work:true})`; main/background work details come from one authenticated SDK state cut. Background work is the parent's async jobs and result deliveries **and** the live subagents of the OMP process: `hasLiveSubagents` (`src/omp/host-control.ts`) reads the process-global `AgentRegistry` through the injected SDK namespace (`pi.pi.AgentRegistry.global()`) and counts `sub` refs that are `running` (not an already accepted, no longer streaming run) or `idle` with messages queued for them; parked, aborted, advisor and main refs never count. A subagent revived from `parked` by an IRC message is in the registry but is neither a parent async job nor announced by a lifecycle frame, so without this a Terminal row showed Waiting for you and a Chat row settled while it ran. The Terminal path reads it inside `nativeActivity({work:true})`; a Chat (rpc-ui) child, which loads the same extension, answers the additive `subagentWork` control request (only to a child launched by a build that records the `subagents` capability), which the window polls every 3 s and merges through `withRegistrySubagentWork` into that tab's activity. Old hosts without that work detail remain Running unless idle is proved. Native end hooks strip async-specific claims: a fresh, non-aborted `willContinue` is provisional until authenticated SDK idle and every job/result delivery drain, and a new start/abort cancels it. A cancelled self-continuation that never starts is indistinguishable from an idle continuation gap; the maintainer explicitly accepted this hook-observation limit. Positive new-capability native background-work gating is covered by source/control-channel scenarios, not an installed long-running native case. Actual installed native detach/reattach was notification-silent; tagged WinRT history proves submission, not physical banner presentation. Same-artifact Chat and native/shell path-click receipts, restored fixture identities and retained shell-recovery/snapshot-link limits are recorded in the design.

Folder rows show the folder name followed by its cwd as a muted TreeItem description, middle-truncated to 40 characters while retaining root/drive and tail. Accessibility text includes the full path and session count. Session and folder tooltips are plain text with name, status and locale-relative last activity, plus one actionable line where needed. Last activity is the conversation's own: the `timestamp` of the last `message`, `custom_message`, `compaction` or `branch_summary` entry of the exact session file (`readSessionFileActivity`), read backwards from the tail only when an `fstat` on refresh shows the file changed; a folder shows its latest session's, and a fileless draft says No activity yet. File mtime is not used, because installed OMP also appends `session_exit`, model/thinking/service-tier and other bookkeeping entries and rewrites the title slot without a turn. The index's `lastActiveAt` is bookkeeping time (restore, reattach, conflict, failure, focus) that only recovers the focused tab; it keeps its persisted name for catalog compatibility and is never shown. The row context-menu **Copy Diagnostics** command copies the row's technical facts (including full paths, recorded identities and activity), using the existing capability redactor at the clipboard boundary.
Activity-signature transitions refresh Sessions directly, including dialog answer/cancel and work/wait changes; unchanged streaming text does not rebuild the tree. OMP queue facts stay count-only in Sessions; Chat lists the queued messages (see Queued messages). Background wait and continuation completion facts stay host-owned, not inferred from transcript wording.
The window-local launch/stop facts show **Starting/Stopping** while that operation is active. An unconfirmed attempt releases its lease and becomes saved/draft, never a stale-reservation state. Later actions probe current positive ownership anew.

**Sessions enrichment cost (2026-10-12).** The 15 s heartbeat's `refresh({ ownership: true })` marks every row's ownership, header and conversation observation dirty. A header is re-read only when the file's `mtimeMs` or `size` changed since the last reading (`readSessionFileHeaderReading(file, previous)`, one `fstat` otherwise; a title OMP rewrites in place changes the time), as the conversation activity already was. Reads that complete between two enrichment turns repaint the view once: a completed read marks a projection due, and the `setImmediate` turn that dispatches the next reads (at most four of a kind) projects first and fires `onDidObserveConversation` once when any activity changed.

**Restart recovery and row actions.** Activation attaches, before any launch, each recorded `managed-rpc` slot this window is responsible for through the read-only authenticated probe, so a running child is adopted and never respawned; only a row whose run intent is `running` and whose old writer is proved absent is relaunched with `--session <exact file>`, and a stopped-intent row stays stopped and opens view-only. Tree rows use internal `ompDesk.clickSession` with an injected-clock recognizer; palette `ompDesk.openSession` launches using the former Resume semantics and the obsolete `omp.resumeSession` alias is removed. It reuses an already-open view-only panel or surviving bridged editor. The row context menu is state-specific (table above); plain `ompDesk.openSession` is no longer a menu entry because its default view is chosen through the two explicit entries. Close refuses before confirming when this window drives no transport for the row. See [ADR-0031](decisions/0031-reattach-a-surviving-managed-host-through-its-broker.md) and the [broker-aware restart recovery design](designs/2026-09-27-broker-aware-restart-recovery.md) for the surviving transport pinning.
A stopped session's explicit Resume request is allowed even though its editor holds no writer. It enters the same
claim-and-launch admission as the palette and row actions; passive editors still cannot mutate a running session.

**Resume from a stopped Chat.** The composer's Resume button shows in the `view-only` and `stopped` phases, and the host answers it in both: a history shown read-only, a session whose process exited (the live conversation object is still attached, in phase `stopped`) and one whose conversation was already released (the page keeps its last state). `ChatRuntime.handleMessage` raises `resume-requested` for each, and `resumeFromChat` (`extension.ts`) runs the row Open's path (`openTab` with the `resumed` verb → `index.restore` with `allowStoppedResume`), so ownership and claim checks, the one-writer rule and the exact-file launch are shared. Success replaces the conversation, so the page goes `stopped → starting → live` and its composer becomes writable. A refused or failed admission puts its reason on the page (banner; a conflict is also an error notification); a request that never reached the admission, or a Resume sent while the session is running or starting, is answered in the footer (`ChatRuntime.notify` / the fixed `CHAT_ALREADY_RUNNING_SENTENCE`). Nothing is silently ignored.

**Commands during a fresh editor's election.** A new editor is published passive until the index has durably recorded its control of the session, and its page can already be talking by then: the footer asks for the host's controls when it mounts, and a prompt may follow within seconds. Such a command is never dropped and never sent by an editor that does not control the session. The page messages that need authority (`omp:control-request` and the write commands of the chat vocabulary) wait, bounded to 15 s, for the election in flight on that slot (`dispatchSlotMessage`, `trackElection`, `awaitElection` in `extension.ts`) and are then routed on its outcome: delivered exactly once when the editor became the controller, otherwise refused visibly — the conversation tells the page the reason, and a control request is answered as unavailable with it. The role is published before the view mode is recorded, so recording the mode no longer extends the passive interval. Promotion asks the footer to read the host's controls again.

**Editor ownership.** VS Code owns open Webview panel membership and serializer revival; persisted identity is not a capability ([ADR-0019](decisions/0019-vscode-owns-omp-editor-persistence.md)). Closing a managed editor detaches without stopping its process. An editor is bound to one conversation for its slot; the tab is named for the session it shows (`sessionHeadline`, the same title the launcher row uses, plus the OMP icon) and corrected wherever a panel becomes a chat surface or Rename records a new stored title. Rename of a running session is rpc `set_session_name`, a stopped one rewrites its file. There is no native `/resume` or A→B switching in a chat process (`new_session`, `switch_session`, `branch` and `handoff` are not offered), so the slot-to-conversation binding changes only by the extension's own open/resume paths.

**Chat column.** With `ompDesk.chatColumn` on (default), a session editor created by `openPanel` (`src/wiring/editor-panels.ts`) targets the editor group that already holds a session editor (the active group if it holds one, else the leftmost) by its exact column; with none, it opens in a new group beside the active one, or the active group of an empty editor area. `src/host/chat-layout.ts` then waits for the panel's view-state report, moves a new group `column - 1` steps left and locks the group while the session editor is still active. `arrangeSessionPanelGroup` (`src/wiring/editor-panels.ts`) takes that column from the tab VS Code reports (`panel.viewColumn` keeps the requested column until a view-state event), because VS Code does not put an editor into an *empty* locked group even by exact column: after the last session editor of the chat group was closed (VS Code keeps the empty locked group), the reopened session lands in a new group on its right. It is then moved left from where it really is, and the emptied locked group, now on its right, is closed (`strayEmptyGroups`) instead of staying beside the chat. VS Code puts no editor into a locked group unless it is targeted by column (`ViewColumn.Active` included, verified on 1.141), so files from Chat links, the Explorer and Quick Open, Stats, Models/Agents, TODO/Agents details and folder shells open to its right without their own placement code. Restored editors keep the group and lock VS Code saved; the extension never re-locks a group the user unlocked except when it places another session editor there. With the setting off, session editors open in `ViewColumn.Active`.

**File window.** VS Code's Move Editor into New Window takes no arguments and opens a 1024x768 window (`createAuxiliaryEditorPart()` with no options; 1.141 remembers no size and has no setting for it). The first Ctrl+Shift+M of a group whose tabs are all *text* files (`TabInputText`, none untitled) therefore reopens the first file, with its selection, through the workbench's internal `_workbench.open` command, targeting `AUX_WINDOW_GROUP` (-3) with `auxiliary: { bounds }` (`FILE_WINDOW_SIZE`, 1600x1000; Chromium clamps a larger request to the screen); the public `vscode.open` drops the `auxiliary` option. The group's other files are then reopened into the new window's group in order (`vscode.open`, the active one last so it stays active) and the original tabs are closed; the file's document, so unsaved edits, stays shared. `workbench.action.enableWindowAlwaysOnTop` then acts on the focused, new window: the `alwaysOnTop` window option of the same call produced no topmost window on 1.141, and the command did, in the window's own title bar toggle and in the OS topmost flag. When any tab is not such a file (diff, viewer, custom editor, untitled file) the focused group is moved whole with `workbench.action.moveEditorGroupToNewWindow` (VS Code 1.141: `createAuxiliaryEditorPart()` then `mergeGroup` of the active group, no bounds, so a default-size window). Returning reopens each tab of the window's group by its input (`vscode.open`, `vscode.diff`, `vscode.openWith`) in the files group and closes it in the window, which VS Code closes once empty; a tab with no such input (untitled, webview, terminal) stays in the window, which stays remembered, and is reported. VS Code's `workbench.action.restoreEditorsToMainWindow` is not used: it merges the focused part's groups into the main part's active group (a no-op when run from the main window, the chat group when that is active) and touches every auxiliary window. Without a files group, the first tab is opened into the chat group by its exact column (VS Code accepts that for a locked group that holds editors; `ViewColumn.Beside` is relative to the focused window's active group, which is the file window's own when the key is pressed there, so it put the files back into the file window), which makes the main window's group active whichever window had the focus, and is then moved with `workbench.action.moveEditorToRightGroup` into a new group on the chat's right; the other tabs follow into that group. An auxiliary window's groups appear in `window.tabGroups` after the main window's, with ordinary view columns that shift when the main window gains or loses a group, so `src/host/file-window.ts` remembers the `TabGroup` object (one per group, its `viewColumn` kept current by VS Code) rather than a column; the window is gone when that object is no longer in `tabGroups.all`. `openTerminalFile` (Chat and Terminal file links) passes the file window's column to `vscode.open`; the Explorer and Quick Open cannot be redirected, but a locked chat group sends them to the most recently used unlocked group of any window, which is the file window once the main window has no file group of its own. The window is remembered by the extension host only: after a reload VS Code restores the window, but the next Ctrl+Shift+M opens another one.

Session naming uses the installed OMP title slot or session header, then the cached name, then a trimmed single-line first-user-prompt summary capped at about sixty characters, and finally the stable unnamed ordinal. An empty current title slot clears a legacy header name. Header identity reads remain prefix-bounded; an unnamed prompt beyond that prefix is found by streaming only through the first user entry. Imported/promoted titles feed the common Sessions, Processes and editor headline; authenticated live RPC name readback updates that cache and open detail titles without replacing their panels. User renames remain authoritative through OMP's own naming contract.
Reopening a still-running conversation gives its replacement editor a fresh immutable slot. When the current default matches the live mode, it retains the writer: moving retained state retires the old slot's terminal pipeline, the new panel binds a fresh frontend to the same native handle, native watches and run intent survive, and Chat resends its retained conversation. This also applies when startup restored the runtime before the closed editor was reopened. If the default differs, reopening uses the existing guarded mode replacement rather than bypassing shutdown, durable-content or one-writer checks. An unanswered terminal request disables stale input and reports response silence; only a lost established authenticated bridge connection produces the host-connection-lost message.
Before capturing transition facts, a switch joins the exact native runtime's already-pending authenticated-control attempt or the exact RPC session's memoized initial startup when it is still attaching/resyncing. This happens outside the lifecycle gate, which control publication itself needs. Completion revalidates editor/runtime/session/authority and the existing window-local open/view request sequence; a close, rebind or newer explicit selection supersedes the pending request, even when the newer choice keeps the current mode. No new retry is started, and genuinely unavailable or mismatched state still refuses replacement.

**Surviving-Webview bridge (implemented; installed acceptance observed for the rpc chat).** New editors use tab- and editor-specific view types and an identity-only persisted `{tabId, editorId}`; the serializer still restores editors after Reload Window. The host stamps such an editor's own `(tab, editor)` namespace into every document it builds, so the bounded *fallback* page a panel shows while it has no bridge endpoint saves the same version-2 state as the guest document and a page that never received the guest bundle cannot make its editor unrecognizable at the next restart. For an editor whose already-saved state is the version-1 `{tabId}` identity (an earlier build's fallback page, or a guest document with no bridge ticket), the serializer adopts it once — binding the editor exactly as a version-2 revival would, so its next document heals the state — only when the registered view type, the saved tab and the durable **controlling** binding all name the same `(tab, editor)` pair; a missing, passive, mismatched or foreign identity is still refused, and an unidentified editor persists nothing. A legacy generic editor is migrated lazily to one typed successor on first post-upgrade reload. `src/host/editor-coordinator.ts` elects one actual editor per indexed tab against VS Code TabGroups membership, not against stale index rows. `src/host/bridge-records.ts` and `src/host/bridge-endpoint.ts` provision a private per-editor document credential and an exclusive exact-port loopback listener (`src/host/bridge-listener.ts`), bound to the chat host's verified identity (owner generation, broker slot and generation, child pid and creation time, session id and file) before the secret is sent to the page. `src/webview/bridge.ts` and `src/webview/lib/bridge-client.ts` reconnect a surviving original document after Restart Extensions without replacing its chat client; the per-document route is acknowledged and fenced, while native mutations share an admission sequence across panel and bridge. The new extension host reconstructs Sessions from actual editor membership and verified ownership. An orphan cannot be focused through a lost `WebviewPanel` handle; after a host-only restart the page names what stays unavailable until Reload Window (provider-account usage/settings refresh, provider login, `@` file completion, extension editor commands). Installed isolated windows (OMP 18.4.3) observed surviving pages dispatching and rendering prompts after repeated host-only restarts, including a session resumed from its view-only page, with model/thinking and Tools controls available. See [the reconnection design](designs/2026-09-25-reconnect-live-webviews-after-host-restart.md) and [ADR-0023](decisions/0023-reconnect-surviving-webviews-through-an-authenticated-bridge.md).

The rendered-document cache also keys on the embedded bridge document ID: upgrading a ticketless guest to a ticket-bearing document must actually reload its HTML. If the editor closes before its asynchronous endpoint bind finishes, its reservation is released synchronously and the late endpoint/records are forgotten; closing does not stop the native OMP process.

**Restored editors after a reload or workspace change.** VS Code revives a restored webview editor only when it is first shown, so after Reload Window every background tab exists in the tab strip but has no `WebviewPanel` in this window. `reviveEditorPanel` (`extension.ts`) is the one way to reach such an editor: it selects the tab through its group (`workbench.action.focus*EditorGroup`) and position (`workbench.action.openEditorAtIndex`), which makes VS Code hand the panel to the serializer, and waits (bounded) for `bindPanel` and then for the editor to finish taking its seat (`editorSettled`: controlling, not mid-open, not mid-transition), because Reload and mode switches refuse a passive editor and the election that records control follows the panel hand-over. The window's own hash follows its open folders and changes when a folder is opened or closed (an empty window becoming a workspace restarts the host and keeps the pages), so `BridgeRecords.homeWorkspace` looks an editor's own `(tab, editor)` directory up under every hash and takes the most recently written one; otherwise those pages find no document, bind a second port and show a lost connection. Activating a session's editor (tab switch, row click, Open) asks the next Sessions reveal to expand a collapsed folder and select the row (`requestSessionRowExpand`, `TreeView.reveal({select, focus: false, expand})`); other refreshes never undo a collapse. Notices shown to the user for these states are plain sentences, not component names.

A host-only restart adopts the unchanged document/binding. Native terminal attach/input/resize/focus/visibility travel over the authenticated bridge and retain document/role/runtime generation gates; no credentials travel in frames.
On a surviving bridge page, Chat and its supported controls or the native terminal remain usable. A selector without a panel handle explains that Reload Window is required rather than creating a second tab. Panel-only completion/editor operations remain unavailable. Removed usage/settings/tool panels do not return. **Provider usage status bar item** (`src/host/usage-status.ts`, `src/wiring/usage-status-wiring.ts`). It is a second reader of the footer's data, not a second source: the text is built from the `windows` the active tab's footer binding already holds (`FooterUsage`, projected by `projectProviderUsage` from the scope's `ProviderUsageCache`), so there is no extra `omp usage` loop and nothing is derived from tokens. **Runtime release and wire basis.** The extension resolves installed OMP, never bundles/pins it, and keeps protocol mismatch visible. Native entry/message parsers retain unknown content for reconciliation but never expose arbitrary internal details. `@oh-my-pi/pi-wire` supplies content types only. Frame decoding keeps the existing 64 MiB v2 chunk cap. Roster/TODO cuts apply synchronously at response dispatch. The VSIX retains licensed Codicon resources and `licenses/paseo/`; neither feature adds network permissions or host tools/MCP. Child history and display preferences use authenticated current-document bridge reads without conferring writer authority.

**Host-control pipe.** `src/omp/host-control.ts`, client/protocol and staged `out/verified-pipe.ps1` authenticate either managed child. Protocol 3 keeps bounded binding/tool observations and adds public native state plus exact epoch/file/id-guarded shutdown/name actions. The signed shutdown acknowledgement precedes SDK commitment; ACK/EOF never prove exit. Native credentials are launch/process-bound and follow row rebinding; session file is readback, not native handshake authority. Model/thinking/Rename remain RPC in Chat; native Rename uses SDK name readback, while unsupported methods/control are honestly unavailable. File-evidence hooks remain consent-gated. OMP seals its process key to the pinned recipient; SecretStorage retains private recipient/proven key, with no secrets in environment, terminal or RPC ([ADR-0005](decisions/0005-preload-control-key-before-omp-startup.md), [ADR-0006](decisions/0006-host-generated-key-peer-verified-pipe.md)). Broker/PTY versions are unchanged; guest protocol 6 carries the presentation contract above.
New RPC-process control verification waits for `RpcSession.start()` to complete with live identity, not merely rpc-ui's early `ready` frame: the installed runtime handles `get_state` only after extension initialization has awaited `session_start`. Native control instead authenticates the exact process generation and obtains public SDK state when the TUI context becomes available; it does not impose an RPC startup barrier or bind its handshake to a mutable session file. Cwd, peer PID/process-generation and proven-key checks remain. Confirmed Close, Reload and recorded-host Stop release the old recipient, proven key and control-process record under the tab lifecycle gate; an uncertain stop retains them. Record/key publication uses that same gate and rechecks the captured runtime, so an old asynchronous completion cannot resurrect the stopped process's credentials or overwrite a successor's key. A reconnect to the same child uses its already-proven key.
**Host-control reattach.** A host process serves one control server per slot: OMP binds the `-e` extension again for every in-process agent session (each task subagent), so the module keeps a process-wide claim and later bindings stay inert; earlier builds started a second server (new key, new random-suffix pipe) per subagent that overwrote or, on stop, removed the slot's last-writer-wins rendezvous record, which after Reload Window made the extension refuse the record as `key-changed` or wait for a record that never returned although the original server was healthy. Extension-side reattach (`HostControlClient.connectWithProvenKey`) first dials every `omp-vscode-control-<slot>-*` pipe through the unchanged pid/creation-time peer proof and handshake and accepts the one whose server proves the key this launch pinned, so hosts launched by older builds recover after an in-place update plus reload without restarting OMP. Only when no server holds the pinned key is a changed record key accepted, and only as a rotation by the same process (record pid is the pinned pid, sealed to this launch's recipient, peer proof, host proves the new key); any other changed key stays refused ([ADR-0006 addendum](decisions/0006-host-generated-key-peer-verified-pipe.md)). A pinned key bounds the missing-record wait to three seconds, the failure reads as one line ("Host control lost … Reload the session to restore them."), and failed native reattaches back off from 5 s to 60 s.
Windows atomic replacement and its retry live in one module, `src/host/atomic-file.ts`: `replaceFileAtomic` stages the content in a private `<target>.<pid>.<uuid>.tmp` sibling created exclusively (`stageBeside`, which the profile catalog's commit and the hard-link publishers of the runtime copies and the PTY records also use for their staging), renames it over the target and removes the staged entry on every exit; `retryFileOperation` retries only the transient Windows `EPERM`, `EBUSY` and `EACCES` sharing/access failures, retaining the staged file and existing identity lock and never unlinking the target. Two named budgets bound it: `RENAME_BACKOFF_MS` (nine attempts, waits summing to 2,070 ms) for the window registry, window requests and profile catalog, and `FILE_OPERATION_BACKOFF_MS` (seven attempts, 875 ms) for session claims, bridge records, the control rendezvous, native evidence, the native-file-observation store and OMP config, and for claim admission, which uses its first two waits (three attempts). Claim admission may retry transient failure before any launch; a restore that may already have started a writer is never replayed. Other errors and non-Windows failures propagate immediately.

**Staged runtime assets.** The helper and the host-control module a child process loads run from content-addressed copies staged under extension global storage rather than from the installed extension folder (as does the broker tree), so a reinstall can rename the installed folder while a session runs; the helper path and the digest of its bytes are configured by that staging, every copy is re-verified on every use (a helper whose bytes changed is refused before it is spawned), and an unconfigured helper refuses host control visibly ([ADR-0012](decisions/0012-run-child-process-entries-from-staged-copies.md)). Staging is not uniformly best-effort: where an asset is needed the stage is awaited and its failure surfaces (a host launch reports that the runtime entries could not be staged outside the installed folder), while the activation call is deliberately fire-and-forget so the helper path is configured before the process-generation probe used by the observation-history deletion proof, which re-awaits that same promise. The staged paths are not secret — they appear in the command line of the processes that load them — but the tree they live in is *verified*, not assumed: on Windows the access of the runtime directory, every digest directory, every copy, and every ancestor of the storage directory up to but excluding the OS-managed volume root must be limited to this account, SYSTEM, Administrators or TrustedInstaller — with the owner placeholders CREATOR OWNER, OWNER RIGHTS and SELF resolving to this account (the ancestor walk itself is derived by the shared private-storage convention from the layout root, not computed by the stager) — the copies and the directories that hold them with the strict rule, those carrier directories with the rule that no other principal may hold a right to replace the tree or change its permissions — a foreign principal that can only create or write inside them is tolerated, and so is a read-only shared ancestor — a directory this module owns that is not yet limited is rewritten non-recursively (a recursive `/T` rewrite leaves a file it reaches with no access entry at all), the owner of each of those paths is read and compared, and a symbolic link or reparse point is refused; on POSIX the mode bits and the owner count only while the listing shows no access marker, or GNU coreutils' context-only `.` (accepted on coreutils' documented meaning of that marker rather than on any check of the context itself): every path the store is reached through — the directories, every copy and the derived carrier walk — is read with the system's own listing, and the markers `+`, `@`, `%`, `?` or any unrecognised marker refuse the store, as does a listing whose mode cannot be read, so a macOS path carrying extended attributes or a Linux path with an ACL is refused rather than taken as proved. The cost is deliberate fail-closed rather than a narrow edge: on Apple's `ls` an attribute marker is printed instead of an ACL marker and accompanies the ordinary state of anything downloaded, tagged or unpacked, so such a chain makes the store unverifiable and the staged runtime unavailable on that machine. Anything unprovable refuses the stage, which is why a host launch can fail visibly on a machine whose storage directory is writable by another account. The volume root is the platform trust anchor: the walk stops there and the extension does not claim protection against a principal that controls it. This is protection against another *user* writing the staged code; arbitrary code running as this same user is outside ADR-0006's boundary and is not claimed against, and re-verifying a copy immediately before a spawn is a fresh reading rather than an atomic verify-then-execute. 

**Private Windows storage identity.** `src/host/private-storage.ts` reads owner and access identities as security identifiers using module-free .NET file/directory security APIs under Windows PowerShell, and reads the current token's SID rather than parsing an account name. Since 2026-10-13 one PowerShell process per verification pass reads the account SID and, for every path the pass needs (store, its directories, verified files and every carrier), its access rules and its owner as one bounded UTF-8 JSON document (`readStorageSecurity`, judged by `parseStorageSecurity`; the descriptor is read once per path and each distinct SID is translated to a display name once). Each of the three reads still fails on its own channel (null access list, null owner, null SID), and a failed, timed-out, oversize or malformed document, or one that names a path twice, leaves all three unread so every check refuses; the 20 s bound and the 64 KiB cap cover the whole read. `restrictPrivateStorage` runs the verification pass first (one process for a store that is already limited) and rewrites only when it refuses, deciding from that refusal's own reading (one fresh directory read when the pass stopped before reading), re-reading the remaining directories after each rewrite; when nothing was rewritten the refusal stands, and after a rewrite a closing pass from a fresh reading decides. When the whole reading failed there is no account SID and the rules are left untouched. Admission compares only SIDs; optional resolved names accompany SIDs in diagnostics but never grant trust. The non-recursive rewrite uses numeric SID grants, with independent readback. Localized `icacls` text and truncated `dir /q` owner columns are no longer parsed. PowerShell/security-API restrictions still refuse visibly rather than bypass the same-user boundary. [ADR-0054](decisions/0054-verify-private-windows-storage-with-security-identifiers.md) records the choice, its 2026-10-13 amendment and review status.

**Native provider login.** `OMP Desk: Log In to Provider…` (`ompDesk.loginProvider`) is available in the Command Palette, Sessions title overflow menu and the no-model Sessions row. With an active managed session it uses that exact executable, cwd and profile; without one it uses the default profile, or asks which profile when indexed sessions have another profile. It signs in through a dedicated short-lived `omp --mode rpc` process ([ADR-0070](decisions/0070-log-in-through-a-dedicated-short-lived-rpc-process-and-keep-the-terminal-login-as-the-explicit-fallback.md), [design](designs/2026-10-13-gui-provider-login.md)): a QuickPick of the providers OMP lists as available, a progress notification with Cancel, the sign-in address opened with `env.openExternal` and a pasted authorization code read through a masked InputBox that goes only to the child's stdin. API keys are not entered in VS Code: a provider that asks for anything other than a pasted authorization code, and the providers OMP's RPC refuses, end the login with a pointer to `omp` in a terminal and an **Open Terminal Login** action, which opens the visible `omp login` terminal that remains the explicit fallback (also the last picker item, **Other providers**). `OMP Desk: Log Out of Provider…` (`ompDesk.logoutProvider`, Command Palette and Sessions title overflow menu) removes a stored account after a modal confirmation. Chat's model picker always ends in **Log In to Provider…**, using that Chat's own scope, not another active editor. A successful session-profile `get_available_models` RPC read with no models changes the footer trigger to **Log In to Provider**, whose checked `omp:chat-command` opens the same native login path without selecting a model. Only the availability boolean is added to replayed footer metadata; catalogues stay host-local. Windows tools used by evidence and the control helper are resolved from `%SystemRoot%\\System32`, not a shadowable PATH. A terminal-only `/logout` typed into Chat is answered locally like `/login` and runs `ompDesk.logoutProvider` (palette scope: the active session's profile and folder); the Commands list's `/logout` runs the same flow in the profile and folder of the session that asked.

Every login and logout entry point shares one window-local guard (`providerAuthRun`): it is reserved before executable resolution and retained until the flow's OMP process has exited; repeated requests are answered, not queued, and closing the window ends the flow. An idle process ends by closing its stdin (OMP disposes its session and MCP connections; killed after 5 s); Cancel, a dismissed masked box and window disposal kill a login that is waiting on the user or browser, since OMP has no abort. The process starts the MCP servers the profile and folder configure (OMP 18.10.3 has no switch), so a kill is a process-tree kill (`taskkill /T /F`), issued before the plain kill. The pasted code and the sign-in address (only its origin is logged) never reach a log, notice, progress line or diagnostic; OMP's errors are classified into fixed sentences and OMP's own error text is never forwarded (ADR-0017). Text OMP sends for the user to act on (the masked box's prompt, `notify` progress, `instructions` such as a device code, and the account label of a log out) is shown, bounded and control-stripped, and never logged. A request while a fallback login terminal of this window is open is answered by showing that terminal (a same-named unrelated terminal does not release it); Chat's model picker, footer and the bridge `provider-login` request start the flow and are answered at once. A login or logout that sent its command, and a closed fallback login terminal, re-read this window's model catalogues and send every other live window of the profile a `models` request on the window-request channel (ADR-0056), so each re-reads its own without announcing it again; a window that does not answer is logged and reads the credential at its next availability read. Failed preflight releases the guard without dispatching. The page supplies no provider, profile, cwd or executable text; the host selects its indexed session scope, or the default profile when no session is available.

Model/thinking, running Rename and reads remain correlated by verified live RPC identity. Model availability is read once on live attach and after an effective model change or login-terminal close; successful picker reads also update it, and an automatic read that finds a turn running is deferred until the turn ends. Session catalogues use RPC only. Picker discovery works during a turn: OMP runs RPC commands in order and `get_available_models` waits for a provider refresh still in flight, so a Stop sent meanwhile can queue behind it. **Model and thinking choices at any time** (`RpcSession.chooseModel`, `chooseThinkingLevel`, `cycleModel`, `cycleThinkingLevel`; `ChatModel.pendingControl`, frame `control_pending`; 2026-10-11). Installed OMP 18.8.5 does not refuse `set_model`, `set_thinking_level` or the cycle commands while a turn streams (their handlers and the session code behind them have no streaming guard, while `fork`, `handoff` and `get_messages_page` do; the terminal UI cycles mid-turn too), and the agent loop reads the model and reasoning effort through getters per model request, so a mid-turn change applies to the next request. The former "OMP is busy; choose … after the turn ends" refusal was Desk's own guard on the catalogue reads. Choices are therefore sent at once. Only when the host must not write — a compaction pass (`get_state.isCompacting` or a running maintenance pass), a rewind in flight or fenced, the shutdown/view-change mutation fence, or a connection being restored — `RpcSession` holds the choice in `#held` (per kind, newest wins; unnamed "next" requests are counted, capped at 16, and an explicit choice replaces them) and publishes it to every page as the host-owned `control_pending` frame and snapshot field. The footer shows the held value with a clock icon, a dashed border and a tooltip; the readback stays OMP's own, and picking OMP's own value while another is held is a new choice that cancels it. Every transition that can lift the block (frame, phase change, fence, navigation end, snapshot) calls `#syncHeld`, which sends, in order, the model, its cycles, the thinking level and its cycles; a "not now" refusal keeps the choice held, anything else (OMP rejecting it, or no answer) drops it with a fixed notice, never retries it, and the footer returns to what OMP reports. `prompt`, `steer` and `follow_up` first wait for any held choice or in-flight application to reach OMP; a failed application refuses the message with `choice-failed` (the draft stays), and a choice that cannot be applied yet (compaction) refuses it as busy, so a message never runs on the old model silently. A held choice lives in the host session, so it survives a Webview reload; it is lost when the window or extension host restarts and when the session fails or stops.
The redundant persistent extension status bar is removed. Chat's authoritative model/thinking footer belongs to its own editor and uses model display names; Terminal already displays native model information. There is no global first-live-tab projection or permanent no-live-session item. Host-control commands remain available independently.

The authenticated channel retains a bounded names-only native tool catalogue for the independent clipboard command and the read-only Tools tree. Clipboard copy does not mutate selection. Live tool selection, cross-chat Paste and project startup presets remain absent under [ADR-0009](decisions/0009-read-only-native-tools-until-atomic-selection.md) and [ADR-0008](decisions/0008-native-tool-selection-at-session-start.md). A catalogue observation proves neither settled configuration nor approval/provider exposure. OMP's own capability providers still own context files, skills, plugins/extensions, MCP servers and agents. **Owning VS Code instance exit.** For a folder shell, the PTY broker's staged Windows helper attests the extension host's direct parent against an owning main-process generation, retaining a kernel handle to every admitted main. Host-role recognition requires exact legacy extensionHost argv, or modern utility/NodeService argv plus the independently read extensionHost role and extensionHostProcess entrypoint environment pair set by VS Code's utility factory. Generic NodeService utilities, incidental command-line substrings and unreadable or conflicting markers fail closed; no unrelated environment value is materialized or reported. Parent, executable-image, older-main and retained-generation checks remain mandatory. The broker starts finite grace only after all admitted handles signal; a verified new owner cancels pending grace and an unattestable authenticated owner disarms automatic cleanup. Grace authorizes one identity-safe shell stop *attempt*, still retaining `unknown`/`remaining` recovery, and never auto-stops managed OMP. An unverified owning instance leaves its shell alive for manual Close rather than guessing from frontend or extension-host loss ([ADR-0030](decisions/0030-watch-the-verified-owning-vscode-process-for-shell-grace.md)). Installed isolated acceptance now proves real modern owner-monitor arming with exact staged-helper and owning-main kernel-generation evidence. Actual last-window grace expiry and cross-window concurrency remain unexercised; read-only command-line topology alone proves neither.

**Folder shell (kept).** A staged broker runtime is proved before any session runs from it ([ADR-0032](decisions/0032-prove-the-pty-runtime-with-a-console-child.md)): the entry is started once with `--self-check`, must load the native addon, run a real console child and — since the rpc cutover — a pipe child, whose per-run markers are read back together with the backend's exit report; the exit code is not the proof. Since 2026-10-12 a run that only reached its 15-second deadline with nothing observed to be wrong is *inconclusive* (entry exit 8): `PtyRuntimeProof` (`src/host/pty-runtime-proof.ts`) admits the launch unproven without caching it, re-runs the check in the background 20 s later with a 90-second deadline per phase, keeps a proof, and holds a refusal for 60 s; an observed fault (including any pipe-child write error or inexact echo) refuses at once (exit 7), and the host accepts lateness only from a consistent exit-8 `inconclusive` answer to a default-deadline run, or a kill of an entry that printed nothing. See [ADR-0032](decisions/0032-prove-the-pty-runtime-with-a-console-child.md), 2026-10-12 amendment. Folder shells use separate `folder-shell` broker slots with post-close recovery; terminal input/resize/screen snapshots traverse a separately authorized document bridge and a passive editor cannot claim PTY input. A document-local nonce guard permits dynamically created xterm styles under strict CSP ([ADR-0028](decisions/0028-stamp-document-nonce-on-renderer-created-styles.md)). The prebuilt Windows ConPTY addon cannot prove whole-tree termination: stops report `unknown` or observed `remaining`, never a false `verified:true` ([ADR-0029](decisions/0029-report-uncontained-pty-tree-stop-as-unknown.md)). The chat no longer mounts a terminal pane.
After authenticated folder-shell attach, `openShellEditor` starts its terminal pipeline for an existing restored panel as well as a new panel. A folder shell's missing-pipeline fallback describes a detached folder terminal, never a missing OMP chat host.
The first proof in a window is logged with its times (`PTY runtime proved itself: self-check N ms, ready in M ms`: the entry's own run, and the whole `ensurePtyRuntime` including listing, staging and verifying the tree), or as `PTY runtime proof reused from <time>: ready in N ms` when a stored proof was used; a provisional admission and the repeated check log theirs. Measured on the development machine 2026-10-12: self-check about 4.3 s, the whole proof about 8.6 s, of which `stageRuntimeTree` alone 2.2–3.3 s even for an already staged tree (its two `ensureRuntimeAccess` passes each run the private-storage ACL and owner scripts under PowerShell; hashing is about 30 ms and the byte verification 17 ms). The ADR-0032 amendment of 2026-10-13 shares the self-check across windows (below); the staging passes are not shared.

**Re-adoption identity (2026-10-13, [ADR-0035](decisions/0035-distinguish-a-recorded-process-from-a-later-occupant-of-its-pid.md) amendment, accepted after independent architecture review).** A broker of the current build attests in its authenticated status that it is new enough to be believed about itself (`brokerSelfRead`, a version marker: every broker has always MAC'd its own creation time into `hello-ok`) and whether it still holds its child's process handle (`childHandleLive`, true only for a `managed-rpc` pipe child; false for a pseudo-console child). The one proof built on it (`connectRecord`, `provedBrokerPin`) serves re-adoption (`attachRpcHost`, `attachNativeHost`), the ownership-verdict probes (`probeRpcHost`, `probeBrokerSlotForRunningChild`) and the stop's pre-dispatch pin proof (`stopBrokerOwnedHost`). It checks the handshake (whose MAC covers the broker's pid and creation time) and the status against the record and the row's pin and takes no PowerShell reading; a malformed attestation counts as absent. A broker without the attestation, a child whose handle is no longer held, and every pseudo-console child, are read through the kernel as before, once per proof: `PtyIdentityReadings` shares only probes that are in flight and keeps nothing once one answers, so the attach that follows a reconcile reads again. Readings per re-adopted row (reconcile plus attach): `managed-rpc` with an attesting broker 0 (was 4), an older broker 4, a native Terminal row 2 (was 4). The first attach of a window stages no probe helper (`attachIdentity()` only hashes the packaged tree; the helper is staged when a reading is needed), and the broker state-directory access verification, which every attach still waits for, starts at activation. A proven PTY runtime self-check is stored under `runtime/pty-proof/` (`src/host/pty-runtime-proof-store.ts`; key: tree digest, runtime version, executable, platform, OS build number, so a cumulative update does not invalidate it; believed for 24 h; [ADR-0032](decisions/0032-prove-the-pty-runtime-with-a-console-child.md) amendment) and reused by later windows; a provisional admission is never stored, and a launch that fails before a broker exists while running on a reused proof deletes that proof and clears the in-process proofs, so the next launch re-runs the self-check. Staging and its access verification still run each time.

**Restore waits on PowerShell starts; each one is logged (2026-10-13).** Reload Window restores a session after the broker state-directory access verification (every attach waits for it) and, for a broker that does not attest itself, after the identity probe helper is staged (`stageRuntimeTree`: two access passes when it writes, one when the tree is already staged, see the next paragraph) and the broker's and the child's kernel creation times are read. All of that is PowerShell, and a start costs 0.3–0.6 s idle and 3.5–7 s on a loaded machine. Three changes shorten it without relaxing a check: (1) a private-storage pass is one process instead of four (above), so the state-directory gate is one start and a staging is at most two instead of eight; measured on an idle machine against a scratch store with a counting `spawn` wrapper: state-directory pass 4 starts / 1.5–1.8 s → 1 / 0.4–0.5 s, probe-helper staging of a staged tree 8 / 2.8–3.3 s → 2 / 1.0 s (one start since the next paragraph's change). (2) The two independent readings of one proof run together: reconcile's `unreachable`/`no-record` absence proof reads the child and the broker concurrently, and an attach or a reconcile probe starts the child's pin proof (`concurrentPinProof`, or `provedBrokerPin` in the probe) as soon as the broker's status is known, through the `whileConfirming` hook of `attachRpcRecord`/`attachRecord`, while the broker's own identity is confirmed; two readings 0.63–0.76 s one after the other, 0.30–0.39 s together. Each reading is still taken inside its own proof and compared with the recorded creation time, nothing is kept between proofs (ADR-0035 §3), and either failing refuses (the broker's reason first). (3) Every PowerShell or `icacls` start of the private-storage code, the identity probe helper and the session-lease probe is one line in the OMP Desk output, `tool spawn: <tool> <purpose> pid <pid> <ms> ms <outcome>` (`src/host/tool-spawn-trace.ts`; the purpose is a fixed phrase such as `broker state security read (9 paths)`, `process probe generation` or `session lease probe (3 names)`, never a path, argument or output; the window's own start-time reading already logs `process start time read`). The lines attribute each second of a restore to a purpose.

**Display reads wait for the restore; a staging that writes nothing is one pass; the state check starts first (2026-10-13, second pass).** A real Reload of three windows after the first pass still took 26.7–45.7 s per window to restore, with 36–41 PowerShell starts per window in the first minute: 22–26 `process probe generation` (the restore's own readings of the rows whose broker does not attest, plus readings that only paint Sessions: the Processes reader's creation-time and child reads of every live broker of the profile, and the ownership observation of every row this window does not run, whose verified-writer check reconciles it), 7–8 `runtime tree security read` (four stagings of two passes each: the host-control assets at activation, the identity probe helper, the session-lease helper and the PTY runtime proof) and 4–7 `session lease probe` (repeated 5 s timeouts). The split of the generation reads by caller is read from the code, not measured. Three changes follow, none of which relaxes a check. (1) **Display reads wait.** A row's ownership observation (its verified-writer reconcile and the session-lease probe, which stages the lease helper) and the Processes reader (its poll, the read when the view is shown, the read after a launcher refresh) wait until the window's startup restore is over (`startupRestoreOver()`; at most 120 s, so a pass that never settles cannot leave a row undetermined). Meanwhile a row the restore covers reads Restoring and another row reads Checking. An observation of a row another live window holds is not deferred (it needs no probe), and no explicit action waits: a click or an open (`fresh` reads), Stop, Kill All, Refresh and the Processes commands read at once. (2) **A staging that writes nothing verifies once** ([ADR-0012](decisions/0012-run-child-process-entries-from-staged-copies.md) 2026-10-13 amendment): `stageRuntimeAssets` and `stageRuntimeTree` read first, writing nothing, whether every copy already holds its digest, and then run one verification pass over the whole final layout and hash the copies again, instead of the pass over the runtime directory, the writes and the pass over the layout (a copy that no longer holds after the pass takes the writing flow); a staging that writes still establishes the rules before its first byte. Four such stagings are four PowerShell starts per window instead of eight, and a steady probe-helper staging measured 0.93–1.04 s → 0.41–0.44 s on an idle machine. (3) **The state-directory check starts first.** `activate` creates the broker client and starts `stateAccess()` before the profile catalog is read, the index is built or any registry exists, beside the window's own start-time read, instead of after them.

**The catalog is read without returning to the event loop, and the committing store no longer re-reads what it just wrote (2026-10-13, [ADR-0034](decisions/0034-store-sessions-in-one-profile-catalog.md) amendment).** A Reload of three windows at once once left a window restoring for 62.8 s with two PowerShell starts: its `intent` and `persist` steps (catalog commits) took 7–19 s and a slot binding was refused as "could not be recorded durably", while the windows' event loops stalled for seconds. On Windows a rename over the catalog fails while any process has it open, and a committing window holds the catalog lock while it retries (about 2.1 s) against a 4 s lock bound for everyone else. `readCatalogDocument` therefore reads with `readFileSync` (open, read and close without returning to the loop; an asynchronous read stayed open across the loop turns of a stalled window and kept a peer's rename failing for the whole stall; a stall inside the one synchronous call still holds the file and blocks this window's thread); the committing store applies the document it wrote (`CatalogCommitResult.document`, parsed from the committed text) instead of reading it back (the adoption the commit triggers still reads once); `startCatalogWatch` reports only `catalog.json` itself, not a commit's staged `catalog.json.<pid>.<uuid>.tmp`; and `adoptCatalogChanges` runs one adoption at a time through `CoalescedRun` (`src/host/coalesced-run.ts`), folding the triggers that arrive meanwhile (own commits, the watcher, focus, visibility, explicit refresh) into one follow-up that starts after them, so another window's commit is adopted when the adoption in flight ends. Measured with three processes on a copy of the real catalog, one of them stalling its loop right after starting each read (decisions 1 to 3 only; the coalescing is unmeasured): the other two committed with a median of 2.2–2.4 s and 13–18 of 25 commits refused before, 50–62 ms and none after. That the incident was this mechanism is an inference; a lock holder whose own loop stalls still delays the others. The session lease probe's failure backoff now doubles (15 s, 30 s, … 5 min) while probes keep failing and starts over after one that reports (`leaseFailureBackoffMs`), instead of one doomed 5 s PowerShell start every ~30 s per window.

**Sessions processes (2026-10-11 amendment; [design](designs/2026-10-11-sessions-unify-processes.md), [ADR-0060](decisions/0060-merge-background-processes-into-sessions-and-kill-all-through-authenticated-routes.md)).** The Processes view above is gone: its model, reader, records, authenticated stop and controller are unchanged, but the list is served by the Sessions provider (`setProcesses`, `src/views/process-rows.ts`, pure projection in `src/views/session-processes.ts`; `src/views/process-tree.ts` is deleted) and `process-wiring.ts` is now `registerSessionProcesses`, the one owner of the reader: every read, the poll's and each controller's, runs through one queue and is published to the provider. Background reads run only while Sessions is visible (every 5 s in the `terminals` layout, 30 s elsewhere, plus one debounced tick 2 s after a launcher refresh; a verified identity is trusted for 60 s of wall time); explicit actions always read fresh. A session row marks its process in the tooltip and accessibility label from its own evidence (this window runs the writer or an authenticated broker witnessed it; `otherWindow` says *held by another window*), with the snapshot only adding uptime or an idle note. Processes no session row stands for are served in a **Terminals** group after the sessions in the flat and folders layouts, and every process at the root of the new `terminals` layout (no session, folder or New Session rows; `beginReveal`, the pinned-selection rule and the notification reveal skip it). A process row opens what it stands for (`ompDesk.openProcess`: the session's row click, the terminal's editor or a reconnect, the Stats panel). Stop, **Stop Orphaned and Idle** and **Kill All** are Sessions title buttons; New Session and Resume Session left the title bar and stay as rows. Single Stop, the bulk stop and Kill All share one `stopRow`, which reports per row whether its route confirmed the stop. **Kill All** (`planKillAll`) offers *Stop in This Window* (sessions this window drives and folder terminals its editors carry, by exact identity; a session another window holds is that window's even with an editor here) and *Stop in All Windows* (rows other windows hold, and rows this window does not run) behind one modal, re-derives after the choice and never forces silently, signals a PID or stops another live window's processes itself. This window's rows are stopped serially through their own lifecycle or authenticated route (a recorded-host stop binds to the slot, attempt and broker id/generation it was derived from; local classification uses the exact slot, broker id and generation, editor-only runtimes included; a driven or recorded route proves the writer gone and the broker's exit is probed separately, so an unproven retirement is reported as not confirmed). *Stop in All Windows* sends each other live window a versioned `stop` request on the ADR-0056/0057 window request channel (`window-requests.ts`, at most 32 row identities, no PIDs); the receiver takes it up by atomic rename, re-derives its own rows, stops through its own lifecycle only those that still equal an identity named and that it provably runs, never forces, and answers per row (`stopped`, `unconfirmed`, `refused`, `changed`). A row no window answers for (refused by all, not taken up, or its window gone) is stopped through the authenticated broker and reported as stopped without its window; a live window that took the request up and went silent, whose request could not be withdrawn, or whose take-up evidence may have been lost while this window was suspended is left alone and reported as uncertain until its extension host (identified by process id and creation time when it was asked, `peer-executor.ts`) is positively proven gone; a lapsed lease, an unreadable registry or an undecided probe prove nothing, and a registry that cannot be read leaves every row another window may run alone. The receiver is graceful only (no Force Stop or other modal; a failed graceful stop answers `unconfirmed`), a window's `stopped` counts only after an independent broker-exit probe, and the fallback route is this window's own lifecycle for a row that became locally driven and otherwise the authenticated broker, never a recorded reattach. Rows no window runs (orphans, idle, detached terminals, Stats) are stopped through the broker as before. Every dispatch is revalidated against a fresh read (the target set never grows) and one report is written per target from a final fresh read. `ompDesk.refreshProcesses` stays as a hidden internal command (Stats panel, shell exit).

**Kill (2026-10-12 amendment, [ADR-0060](decisions/0060-merge-background-processes-into-sessions-and-kill-all-through-authenticated-routes.md), the only place a process id is signalled).** The context menu of a session row (and of a process row) offers Kill: `src/host/session-kill.ts` attempts a tree kill of the recorded broker, and of the recorded OMP child, with System32's `taskkill /PID <pid> /T /F` at once, with no question to OMP and no look at the session's state, claims or owner. The one check kept: a fresh reading of each id equals the creation time Desk recorded (the broker's record, or the session's recorded host); an id that is gone or now belongs to a later process is "already gone", and an unreadable identity kills nothing. The check and the kill are two steps, so this is best-effort against a reissued id, not atomic. Each recorded root is then shown gone by a liveness look and the creation-time probe; the tree is never claimed empty, because what `taskkill` reaches is its own behaviour (ADR-0029). Desk's records are retired only on evidence about the writer, bound to the examined incarnation: a session row is recorded stopped by `SessionIndex.reconcileKilledHost` only when the recorded OMP child (pid and creation time) was shown gone, under the tab's lifecycle gate, with no live rival claim holder and no runtime driven here, and with a conditional shared write that the catalog refuses when the committed row no longer records the same launch attempt, slot and broker (a replacement launch another window published is never recorded stopped); a broker's absence alone is never writer evidence. Kill forgets only the broker-slot mapping of a process row; a folder shell's recovery record stays until the owning window's shell watch proves the shell root gone too. A window that drives a runtime looks once a second (`src/host/broker-loss.ts`, no process spawn) for its broker's process and, when it is gone, waits up to 30 s for both recorded creation times (broker and OMP or shell root) to name gone processes before it publishes the ending (`handleRpcHostExited` for chat, `handleNativeHostExited` for a terminal, slot retirement for a folder shell, re-checked inside the slot's gate); an unprovable root keeps the runtime and records and warns. Failures, incomplete tree kills and failed record updates are warnings and log lines; a successful kill is silent. Stop, Stop Orphaned and Idle and Kill All never reach this module. The other direction holds too: a Close, Stop or Reload whose stop the broker could not confirm (it was killed, or the process cannot be reached) first asks whether the recorded OMP root already ended (`recordedRootGone` in `src/host/native-session.ts`: its id no longer in use, or now another process's by creation time) and, when it did, finishes as a confirmed stop, so a session ended from outside is never left needing a Force Stop.

**Reload and view switch of a session whose OMP process already ended (2026-10-13).** A Reload or a Chat/Terminal switch normally reads the session's facts, asks for its one confirmation, stops the exact process and launches the successor on the same file. When the facts cannot be read, or the stop cannot be confirmed, `switchSessionMode` (`src/extension.ts`) asks whether the recorded OMP root already ended (`alreadyEnded`, the check Close and Stop use). If it did, the request is finished instead of refused: a facts read that failed leads to `endEndedRuntime`, which ends the runtime the way its exit would (`handleRpcHostExited` / `handleNativeHostExited`) and then takes the request as one for a stopped session, a Resume of the row's exact file in the requested view; an abort or settlement a gone process cannot give, or an unconfirmed stop, counts as the confirmed stop and the ordinary replacement continues. No Force Stop is offered and nothing is reported as failed. A root that is not proven gone keeps today's refusals, and Reload of a draft without a file is still refused before any of this.

**Packaging and platform.** OMP Desk targets Windows only: the broker depends on ConPTY through `node-pty`, and the host control, identity probes and desktop toasts run PowerShell and named pipes. **Lifecycle and detail loading refinement (2026-10-08).** Session view requests project a pending context key so editor-title mode actions are disabled during a transition.
