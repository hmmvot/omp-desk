# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Move to This Window: take a running session from another window without stopping it.** A session shown as open in another window now has **Move to This Window** in its Sessions row menu, on the "Another OMP Desk window holds this session" notice, and as **OMP Desk: Move Session to This Window** in the Command Palette (for the editor in front, else the active session). The other window gives the session up, shows it as a read-only history with a note and names your window in a notification; this window then opens it and attaches the running OMP, as after a reload. The OMP process, its turn in progress, queued messages, background jobs and transcript are untouched, unlike **Stop** and **Kill**, which end the process. A working session is confirmed once: a tool call the other window was serving at that moment fails once and the turn goes on, a message it had sent and not yet seen acknowledged is not resent, and unsent text in its composer stays in its read-only editor. A busy, older-build or silent window, a session that is no longer held there and a Terminal session (which cannot be moved) are each reported in their own sentence, and "nothing was moved" is only said when that is proved ([design](docs/designs/2026-10-20-move-session-to-this-window.md), [ADR-0080](docs/decisions/0080-hand-over-a-live-session-through-a-taken-up-request-that-detaches-the-holder-without-stopping-it.md)).

### Changed

- **A session you start reads `Starting…` until OMP is ready, and the Chat says which step it is in.** The Sessions row used to turn `Running` as soon as OMP Desk had started the process, while OMP kept loading for 20 s and more (plugins, extensions, model providers) and the Chat only said "joining the session…". Now New Session, Resume, Open of a stopped session, Restart and a switch between Chat and Terminal keep the row at `Starting…` (with the seconds once it passes five, as for other actions) until the conversation is live (Chat) or host control is verified (Terminal), and then show `Running` or `Idle` as before. In the Chat the notice above the conversation, and the empty conversation under it in place of "joining the session…", name the step: `checking the runtime`, `starting the background process`, `OMP is starting`, `connecting`. OMP does not report what it loads while it starts (it only prints which phase it is in after 10 s, as free text that is not a stable interface), so `OMP is starting` is one honest step with the seconds, not a list of plugin and provider phases. A launch that fails or times out ends the starting state and shows the error where it always did.

- **Chat: `/` suggestions put commands above skills, keep an exact name in the list and turn it into a block at once.** The list is ranked: the entry named exactly what you typed (or its alias) is first and selected, then every command (OMP's own, file, extension and Desk's own) before any skill, so `/report` is no longer below a `/skill:…` whose name contains `report`. Typing a whole name no longer makes the list disappear: it stays, with that entry first and selected (`Enter` or `Tab` completes it with a space as for any suggestion; the next `Enter` sends). A name at the start of the draft that is exactly a command or a skill of the session is drawn as the command or skill block the moment it is typed, without waiting for Space; adding a character (`/reportx`) or deleting one (`/repor`) turns it back into plain text and completion continues, and `Backspace` or `Delete` next to such a block removes one character instead of the whole block. A block that has its space after it, and a command's arguments after it, work as before.

### Fixed

- **Sessions: a click on a row no longer fails with "Actual command not found, wanted to execute ompDesk.clickSession".** A row's click command carried the row as an argument, and VS Code keeps such a command only until the row is next repainted; Desk repaints a row in place whenever it changes (the clicked row at once, to show "Opening…"), so a click that reached the extension host in the short gap after a repaint (for example the second click of a double click, the one that resumes a stopped session) found the command already gone, showed that error and did nothing. The click commands of session rows and of process rows now carry no argument and take the row the view has selected, which VS Code selects before it runs the command, so no repaint can disown a click.

## [0.4.9] - 2026-10-19

### Added

- **Chat: OMP's magic keywords glow in the message box and in your sent messages.** `ultrathink`, `orchestrate`, `workflowz` and `jevify`, as standalone lowercase words of prose, are painted with OMP's per-letter hue gradient (it sweeps along the word while the message box has the focus; in a sent message it stands still), by OMP's own rule: `orchestrate()`, `foo-orchestrate`, `path/orchestrate`, `orchestrates` and a word in backticks, a code block or an HTML tag stay plain. Chat follows OMP's `magicKeywords.*` settings (`omp config list` in the tab's folder and profile, asked only while such a word is on screen, at most every 30 s and again when you come back to the message box or the window), so a word switched off in OMP Settings is not painted. The hues are OMP's with the lightness solved per theme kind for ordinary-text contrast (4.5:1, 7:1 in the High Contrast themes); High Contrast and forced colours add an underline, and reduced motion or forced colours stop the sweep. It is drawn with the CSS Custom Highlight API, so the message box, caret, IME and your text are unchanged. See [Chat](docs/guide/chat.md#magic-keywords).
- **Chat: an `html` block of a reply is a live page.** A closed top-level ```` ```html ```` fence of an assistant reply is shown as a page (a header row with Page | Source and Copy, never over the page) instead of code: an interactive explainer, a chart, a mockup. The page runs in a sandboxed frame served from a loopback address of your window and reaches nothing: no network (no CDN, `fetch` or web fonts and images; `data:` images only), no storage, no forms, popups, downloads or navigation, and no access to Chat, VS Code or your files. It reads your theme as CSS variables (`var(--bg)`, `--fg`, `--accent`, `--c1` … `--c6`, `--font`, `--font-mono`) and follows a theme change without reloading; it is as tall as its content up to about 800 px, then scrolls, with **Show full page** (and **Show less**) under a taller page to see all of it without an inner scroll; the model is asked to keep a page's height fixed when it switches tabs or steps, so the reply does not jump; and it cannot take the keyboard from the message box by itself. While the reply streams, in your own messages, tool output, thinking, lists and quotes the block stays code, and a page that is empty, over 200,000 characters or whose frame does not answer stays code with a muted line saying why. The new setting `ompDesk.chatHtmlPages` (on by default) controls both the display and the one short paragraph (about 240 tokens) added to the Chat system prompt that tells the model it may write a page; off, every `html` block stays code and the model is told nothing. Applies to sessions started or resumed afterwards; turning it on needs a window reload for Chats that were already open. See [Chat](docs/guide/chat.md#html-pages) and [ADR-0079](docs/decisions/0079-serve-reply-html-pages-from-a-constant-loopback-frame-document-with-its-own-policy.md).

### Changed

- **Optional: the reason leads a tool row.** While `ompDesk.toolIntentDescriptions` is on, a tool call that has an intent line shows it right after the tool name, in the normal text colour, and the file or command after it, muted: `Read  Check how the Jobs HUD cuts long paths  src/webview/components/JobsHud.tsx:28-45`. When the row is narrow the file or command gives way first and the intent last: a file path loses its leading folders and keeps the file name and line range, a command is cut at its end, and at about 320 pixels with a long intent the file or command is gone and the intent is cut with `…`. The full path or command stays in the tooltip, and the file name is still a link. Rows without an intent and group summaries are unchanged. The setting now also takes effect in open Chats at once, without restarting them. See [Chat](docs/guide/chat.md#tool-calls-thinking-and-the-overview).

### Fixed

- **Chat: the Figure | Source toolbar no longer covers the figure.** On an `svg` figure and a Mermaid diagram the toolbar (view toggle and Copy) sat over the top corner of the drawing and hid part of it. It now has a row of its own above the drawing, still shown on hover or focus.
- **Sessions: Rename's input no longer vanishes the moment it opens.** Rename opened its name box and a keyboard layout switch (Alt+Shift, or Alt alone, which moves the keyboard to the menu bar) made VS Code dismiss it, because the box hid itself whenever it lost focus; a name typed in the wrong layout could then not be corrected and the session could not be renamed again. The box now stays until you press Enter or Escape, like the other prompts that take typed text.
- **Chat: a `/compact` typed after a reply puts its divider below that reply.** The `Compacted · 366k → 62.2k tokens` divider appeared above the turns you had just had in that window (above your last message and the reply to it) instead of at the end, and a reload put it right. Each row Chat shows live is placed after the row that came before it, and after a finished turn that is often an entry the session file's reader never returns (a model-usage or title-change record). When Chat re-read the file after the report, those rows lost the row they were placed after and fell to the end of the transcript, below the compaction row that is saved later than they are. They now move to the nearest row the re-read still holds.
- **Chat: a disclosure row you reach with the keyboard shows the theme's focus ring.** The `Compacted` divider, the thinking block and the other folding rows of a reply drew the browser's default focus outline (a white box on a dark theme, with no relation to the theme's focus colour) when focused; they now draw the same 1 px ring as the tool rows and buttons.
- **A reload while a new session was starting no longer leaves a session you can only Kill.** A window whose installed extension was replaced on disk (an update installed over the running copy) still started new OMP processes, because the check that refuses it ran only once per window, when the window first prepared the files such a process runs from; the Sessions page said "updated on disk", you reloaded, and the window ended between starting the process's broker and reading its answer. The next window then saw its own row as a rival ("This session is already running. Stop it before opening a new editor.") and offered nothing but Kill. A window in that state now refuses every launch it is asked for ("OMP was updated while this window was open. Reload the window to finish updating, then try again.") before anything starts, and a row left in the middle of a launch, with the intent to run recorded with it, is re-adopted by the next window through the broker slot its launch reserved (the broker's own record and the child's creation time are proved at the attach) instead of being refused. A row that recorded a process, or a slot that holds another kind of host, is still only reported as running.
- **Chat: a session you cleared no longer fails with "The running OMP process is not serving this session file." after two reloads.** `/clear` makes OMP give the running process a new internal session id, which Desk records for the row beside the file's own id. The first Reload Window after the clear re-adopted the process and recorded the file's id in its place, so the second reload expected an id the same process, on the same file, no longer reports, and the Chat refused it. Re-adopting a process now keeps the id recorded for it. A row already in that state is fixed by the Chat's Restart (or Kill, then Resume); nothing in the session file was lost.

## [0.4.8] - 2026-10-19

### Added

- **Optional: tool calls that say why they ran.** The new setting `ompDesk.toolIntentDescriptions` (off by default) asks the model, through the Chat part of the system prompt, to fill the intent line OMP shows beside each tool name with what the call is for in terms of your task (the question it answers or the change it makes, naming the feature, bug, file or agent, at most 10 words) instead of a bare verb phrase such as `Find menu`. Chat sessions only; subagents and Terminal sessions are unchanged. Applies to sessions started or resumed afterwards. See [Settings](docs/guide/settings.md).
- **Quote a whole change of a diff.** In a diff editor, `Alt+Q` (or **Quote Selection to Session** from the editor menu) with **nothing selected** and the caret on a changed line now quotes the whole hunk the line belongs to, instead of only referencing the line: a `diff` block with the removed lines after `-`, the added lines after `+` and up to three unchanged lines each side, under a location that names both sides, the modified side first (`src/app.ts:1-7 was src/app.ts:1-5 @ HEAD (3f2a9c1)`; `@ index` for the staged side, `@ 3f2a9c1` in a commit's changes). It works in the inline view and on either side of a side-by-side diff, of a Source Control diff, of a commit's changes and of two compared files. A caret on an unchanged line keeps the line reference, and a selection quotes the selection as before. A hunk location is plain code in the transcript, never a link, because it holds lines of two versions. VS Code gives extensions no access to the changes its diff editor draws, so OMP Desk compares the two texts itself line by line: a hunk can be grouped differently from the editor's (a change of only trailing whitespace is a hunk here and none there), and a pair too large or too different for the comparison (over 20 000 lines or 1 000 changed lines) keeps the line reference. In the inline view the removed lines cannot hold the caret; quote a change that only removes lines from the original side of the side-by-side view.
- **Chat: MCP tools, Submit Result and autoresearch have cards like OMP's terminal UI.** An MCP tool call is titled `server/tool` with its first arguments on the row (each value cut at 24 characters, 160 in all), the full arguments as a tree in the open card and a JSON result as a folding tree, where the row showed the raw `mcp__server_tool` name. A subagent's `yield` is **Submit Result** with the section or workpool item it fills, the size (`13 fields`), a report as text or the data as a tree, a rejected or aborted submission's message in full, and a `schema overridden` mark when OMP accepted data that failed the output schema. `init_experiment`, `log_experiment` (disposition, metric against the baseline, confidence, scope deviations), `run_experiment` (PASS, FAIL or TIMEOUT with duration, metric and output tail, or the running time) and `update_notes` show what they did. See [Tool calls, thinking and the Overview](docs/guide/chat.md#tool-calls-thinking-and-the-overview).
- **Chat: goal, fast mode, slow mode and the usage limit show in the footer, as in OMP's terminal UI.** Small chips beside the model and thinking pickers, each only while it holds: `Goal 12.3k/50k` (tokens used against the goal's budget, a tooltip with the objective and the time it has run, a warning colour while it is paused or its budget is used up), `Fast`, `Slow` (the tooltip says whether it is OMP's setting for every session or this session's) and, in a warning colour, the usage-limit stage of your account in OMP's words (`limit reached · wrapping up · resets 14:30`, `low priority until 14:30 · 40% left`). They are read from OMP when the chat attaches and after each turn and command; the goal is also updated the moment OMP announces a change. The tokens-per-second figure of OMP's status line is not shown: OMP reports one sample, not a stream, and every reply already shows its own rate.
- **Chat: an extension's failure, and an event OMP had to drop, are lines in the conversation.** `Extension "<path>" error (<event>): <text>` (headed `Extension error`), as OMP's terminal UI prints it, replaces silence when an extension throws; a repeat is said once in a row, the text is shown exactly as written and never as markup, and Desk's own `/rewind` and `/clear` keep their own messages. When OMP drops an event that does not fit its connection, Chat shows `OMP dropped a "<type>" event` (headed `Frame dropped`), writes a line to the OMP Desk log, and reads the session file again when the lost event would leave the conversation behind: a reply whose end was lost no longer stays on screen as the live one.
- **Chat: a question's option preview and its time limit.** An option of OMP's question card that comes with a preview (Markdown: a mock-up, a code block) shows it under the list for the highlighted option, as OMP's terminal UI does, and a question with a time limit says `Answers itself in 1 min 30 s` and counts down to the moment OMP answers the recommended option for you.
- **Chat: what a turn cost, which model answered, how long it thought, and a provider error you can act on, as in OMP's terminal UI.** Under a finished reply the footer adds the turn's totals, `19K tok · $0.02 this turn` (the tokens and cost of every request of the turn, the tool-use requests included, cache reads left out as OMP does; the cost is left out when nothing was billed and reads `<$0.01` below half a cent; no usage, no line), with exact counts in the tooltip. When the provider answered with a different model than the one requested, the footer says `served claude-haiku-4-5 · requested claude-opus-5 · via openrouter/Amazon Bedrock` once for each such pair; whether two ids are the same model (a dated snapshot, a gateway prefix) is decided by the installed OMP's own classifier, so a snapshot or an id OMP cannot classify shows nothing. A thinking block reads `Thinking… 7s` while it streams and `Thought for 7s` after; saved history, or a block that was already streaming when the chat attached, has no time and reads `Thought`. A failed request is one frame: the HTTP status as a chip when OMP recorded it, the provider's message (cut to three lines when long, with **Show all**), **Copy error**, and on the last reply **Switch model** (opens the model picker) beside **Retry**.
- **Chat: `/btw` side questions, as in OMP's terminal UI.** `/btw <question>` asks about the conversation without touching it and streams the answer as Markdown into a panel above the message box, during a response as well as between them. The question and answer are never part of the session: no transcript row, nothing in the session file, nothing in the context or cost line, and Stop does not cancel it. The panel has **Cancel** (and `Esc` while the focus is in it, which never also stops the response), **Copy**, a **follow-up** row and **Close**; `/btw` alone lists the session's earlier side questions (OMP's own history, so it survives a reload, a second editor and an extension-host restart, and a question that was answering when its process ended reads as Interrupted). A refusal (a question already answering, no model, history that cannot be saved, an OMP without the feature, attached images) is one fixed sentence and keeps your text. `/btw` is listed in the slash picker and the Commands list. Not included: the terminal UI's branch key. See [the design](docs/designs/2026-10-19-chat-btw-side-questions.md).
- **Chat: SVG figures, charts under tables and LaTeX math, as in OMP's terminal UI.** A closed top-level ```` ```svg ```` fence of a reply is drawn as an image (Figure | Source toggle, Copy) in your theme's colours (the `var(--fg)`, `var(--accent)`, `var(--c1)` … tokens OMP gives models are resolved); the SVG is never run or fetched (scripts, links, animation, embedded HTML and external references are removed and the figure says so; an invalid SVG stays code with a reason). A table of numbers in a reply gets a bar, grouped-bar (two or three measures) or line chart under it by the terminal UI's own rules for those kinds (at least four categories, values not all alike, enough points or spread; prose, id, date and version tables and tables of a few rows get none; the terminal's other chart kinds, a heatmap among them, are not drawn), in inline SVG in your theme's colours, with a page-wide **Hide chart** (OMP's `tui.autoGraph` is not read). `$…$`, `$$…$$`, `\(…\)`, `\[…\]`, own-line `$$`/`\[` blocks and bare `\begin{align}`-style environments show as Unicode text (`x²`, `α → ∞`) and stacked fractions, matrices, cases and aligned rows, by a converter of our own ([ADR-0078](docs/decisions/0078-show-latex-math-as-unicode-text-from-a-project-owned-converter.md)); `$5 and $10` and `$5-$10` stay prices, and Find and Quote work on the shown text. See [the design](docs/designs/2026-10-19-chat-rich-markdown.md).
- **Chat: a Jobs row lists OMP's background jobs and cancels them, as in OMP's terminal UI.** A third pinned row beside TODO and Agents shows the `bash` and `eval` jobs OMP runs in the background (a background `task` is an agent and stays in the Agents row) (`2 background jobs · bash: npm run dev · 3m`), each with its age and a **Cancel** (OMP's own `/jobs kill`, also during a turn, with OMP's answer shown), and a **Cancel all** that asks to be clicked twice and is not offered while an agent runs; the list is read from the transcript and OMP's live events, so it says `at least N` when it may miss jobs and offers no Cancel for a job this OMP process did not report. When OMP reports pending work that no job names, the row is the yellow warning `Background work is pending · no job is named in this chat` only while nothing in the chat is running; while a tool call of the turn (`bash`, `eval`, `task`, any other) has not finished, or an agent runs, there is no Jobs row at all, because that call may be the work OMP means and its job is not named yet. `Waiting for background job…` in the working row opens the row, a job's tool card shows a live `running · 3m` / `done` / `failed` / `cancelled` chip and a Cancel while it runs, and `proc://bg_7` in tool cards and replies links to the job (a click only shows it; it never cancels). See [the design](docs/designs/2026-10-19-chat-background-jobs.md).

### Changed

- **Chat: OMP's commands work while a turn is running, as in OMP's terminal UI.** A builtin, extension or custom command sent with `Enter` or `Alt+Enter` during a turn used to reach the model as plain text (OMP queues a steered or queued message as typed, and refuses an extension command's), so `/compact` did nothing and a skill-like or extension command was not run. Chat now sends such a message as a prompt that OMP queues in the same way, and OMP decides what each command does mid-turn: `/compact` interrupts the turn, compacts and resumes it, an extension command runs at once, a custom command's text is queued, `/export` exports. Every command and skill is a block in the message box during a turn, as between turns, and the **Commands** list no longer greys OMP's commands out with "only between turns". Chat's own commands (`/rewind`, `/clear`, `/new`, `/delete`, `/fork`, `/fresh`, `/models`, `/agents`, `/settings`) keep their own rules, terminal-only commands are still answered by Chat instead of being sent, and an unknown `/name` or a path is still plain text. See [the design](docs/designs/2026-10-18-composer-command-skill-chips.md).
- **Chat: Find keeps the current match's block open.** When the row of the current Find match came back after you scrolled it out of the list (or a repaint rebuilt it), its thinking block was closed again, so the match was hidden until you pressed Enter. The thinking block, tool group or tool output that holds the current match now reopens, unless you closed it yourself after the jump; the next jump opens it again. Only the current match's own block is reopened, never the others.
- **Chat: an agent of a Task card opens closed.** Expanding a Task card used to open every agent's block too, so the whole assignment and result filled the card. An agent's block now opens closed: its head, current activity, time, tokens, errors and review verdict stay visible, and its assignment, result, nested agents and transcript open with a click on its head.

### Fixed

- **Chat: the ⋯ menu of a tool card is never cut off, and a running card with nothing to copy has no empty band.** The menu opened downward inside its card, so on the last card of the transcript or on a short card (a running `wait` or `task` with two rows) the card's edge hid its lower items. The list is now placed against the window: below its button, above it when only there is room, and scrolling inside itself when neither side fits it, and it follows its button while the transcript scrolls; Escape, the arrow keys, Home, End, Tab and a press outside work as before. A running or empty card whose output bar held only the ⋯ button (a `wait` on two tasks, a command that has printed nothing yet) showed that bar as a blank row between the header and the job list; the button now sits in the body's top-right corner and takes no row.
- **Chat: a finished TODO list leaves the pinned row, as in OMP's terminal UI.** The row stayed above the composer for good once every task was completed or abandoned: OMP's terminal UI hides such a list after `tasks.todoClearDelay` seconds (60 by default) and remembers it in the session file, but OMP sends a Desk window no event for it. Desk now keeps the same clock: when all tasks of the list are closed, the row is cleared after the delay it reads from the session's profile and folder (60 s when it cannot read it; a negative value never clears), and a change to the list restarts the count. A list the terminal UI dismissed (`todo_hud_state` in the session file) stays hidden and a revealed one stays shown, each only for the list it was recorded for. A session opened after its list was closed for longer than the delay (counted from the last change to the list in the transcript) shows no row at once. This changes presentation only: the TODO tab and the TODO tool cards still show the list, Desk writes nothing to the session file, and a changed list shows the row again.
- **Chat: a C# type with generated or split partial parts links instead of showing a choice.** The C# language server names a partial type's container after the file of each part, so a type split over `Session.cs` and a generated `Session.Generated.g.cs` counted as two types and its name was an "N definitions" choice. The parts are one type again and the name links to the first by path. Entries captured from a real source-generator project (member containers of nested generic types over 700 characters, in-memory generated documents with no path) are now the fixtures of the symbol tests.
- **A tab you close no longer leaves its record in the session catalog for good.** Each time you opened a session that had no tab, Desk remembered a new tab-to-session record, and the record of a tab you later closed stayed in the shared catalog even though no window could ever show that tab again; 0.4.6 cleaned up the records of removed sessions but had to leave these, because a window could not tell a closed tab from one VS Code restores later in another window. Every window now says in its registry record which tabs it holds. The window that held a tab and saw it close drops the record once the tab has stayed away for 30 seconds, only when every other open window has said since then that it does not hold it (a tab moved to another window is that window's now), and never the record of a tab the window did not hold itself: a window that is closed or still starting, or that is opening a tab right now, keeps its records, and the record that tells which window started a running session stays until another tab takes it over. A window that reloads in between finishes the clean-up on its next start, and an earlier Desk build in another open window pauses it until that window is reloaded.
- **Chat: a commit link says so when the Source Control Graph's filter hides the current branch.** Clicking the current commit's hash selects it in the Graph, but the Graph does nothing, silently, when its reference filter (the button beside the Graph's title, `Auto` by default) is limited to branches that do not include the current one: the Graph came into view with nothing selected. The click now shows a notice, `commit <hex> is not selected: the Source Control Graph's filter hides the current branch (main). In the Graph, choose "Auto" or include main in its filter.`, instead (for a tag or a detached HEAD, the current tag or commit), and the OMP Desk log line of the click says what the filter was. OMP Desk reads the filter from VS Code's workspace storage, which is not a public API: when it cannot be read, the click selects as before, and the log line says why. See [the design](docs/designs/2026-10-17-commit-hash-links.md).
- **Chat: orange is orange again in diagrams and figures under Dark Modern.** Dark Modern's chart orange is the find-match highlight, a colour with a third of its opacity, and Desk flattened that onto the background before using it as a series colour: the third pie slice of a Mermaid chart, and an SVG figure's `var(--c3)` and `var(--warning)`, came out a dark brown that hardly showed. Chart colours now take the theme's hue at full strength.

## [0.4.7] - 2026-10-18

### Added

- **Chat: `/review` works.** OMP's own code review runs in Chat: `/review` asks what to review in a dialog (uncommitted changes, a branch diff, a specific commit, a pull request, or custom instructions in a multi-line box) and sends OMP's review request as the turn; `/review <PR link>` and `/review <focus>` work too. Without the GitHub CLI, OMP's message says so. It is suggested as "Review code: pick uncommitted changes, a branch diff, a commit or a pull request…" with the hint `[PR link] [what to focus on]`. Pull requests were run against a real public repository with the GitHub CLI signed in: `/review <PR link>`, the dialog's list of open pull requests, its search row with `#123`, and a pull request that does not exist (OMP's error message of the window, nothing sent). See [the design](docs/designs/2026-10-18-chat-review-command.md).
  - **A dialog that `/review` (or any command) opens no longer makes the message "unconfirmed", and cancelling it leaves the composer idle.** A command that asks before it returns is acknowledged by OMP only after your answer, and a dialog left open for more than 30 s (host) or 45 s (page) would show "OMP has not confirmed this message. Your draft was kept…" although the command was running. Both deadlines now wait while a dialog is open and start over when it opens or settles. After **Cancel** the progress bar above the composer does not keep running with no turn behind it.
- **Chat: `Esc` cancels an open dialog.** A list, a text or multi-line prompt, a confirmation or a question card from OMP (`/review`'s pickers included) is cancelled by `Esc`, with the same answer as its **Cancel** button, wherever the focus is on the Chat page. While a dialog is open `Esc` no longer stops the running turn: the dialog owns the key through the same signal the find bar and the completion list use. From the "Other" field of a question one `Esc` cancels the whole card, as in VS Code's quick pick; `Esc` during an IME composition, and the find bar's own `Esc`, are left alone.
- **Chat: a command or a skill in the message box is one block.** `/compact`, `/skill:review` and every other command or skill of the session that the draft names is drawn like an attached image or file: a tinted chip with a terminal-prompt icon for a command and a book for a skill, and `Backspace` right after it, `Delete` right before it, `Ctrl+Backspace` or a selection that touches it removes the whole block (with the one space after it) as one undo step. The caret cannot go inside it and the arrow keys hop over it. The text is unchanged: the draft, the history, a draft carried to another editor and the message sent are still `/name args`.
  - **When it appears.** When the name is complete and a space or a line break already follows it: after you pick a suggestion, or after you type the name and a space. A name at the very end of the draft is still being typed (`/model` while you type `/models`), so it stays text until something follows. A recalled history entry (`↑`, `Ctrl+Alt+Y`), a restored draft, Undo and a paste show the block the same way, and it appears when the session lists its commands after the draft was restored.
  - **Only what OMP would run.** A command or a skill that the session lists, at the start of the draft; and a `/skill:name` anywhere else, because OMP (checked in 18.11.1) runs the first such token from the middle of a message, unless the message starts with another command, `!` or `$ `. An unknown `/foo`, a path such as `/usr/bin/x`, a name in another case and a command Chat refuses stay text. While a turn runs, a message is steered or queued, and OMP does not run a command from one, so only Chat's own commands (`/rewind`, `/clear`, `/new`, `/delete`, `/fork`, …) and the skills are blocks then.
- **Chat: a skill sent while a turn is running is run by OMP.** `/skill:review` (or a message with a `/skill:name` token in it) sent with `Enter` or `Alt+Enter` while a turn runs reached the model as the literal text `/skill:review`, because OMP expands a skill only in a `prompt`, never in the `steer` or `follow_up` Chat used for every message sent during a turn. Chat now sends such a message as a prompt that OMP queues with the same choice (`Enter`: steer, `Alt+Enter`: follow-up), so the skill's instructions reach the model and the transcript shows the skill row; the queue, Remove and Stop work as for any queued message. Every other message is sent as before. The skill is a block while a turn runs, too.
- **Fork a session into a new tab, and Branch and Clear from the Sessions view.** `/fork` in the Chat, or **Fork Session** in a running session's context menu (and in the Chat tab's `…` menu and the Command Palette), opens a copy of the conversation as a separate session in a new Chat tab beside the original, which keeps its process, file and tab untouched; both can be continued. The copy is started with OMP's own `--fork`, the mechanism OMP's `/fork` uses for a new pane or window, so OMP writes the copy and records the original as its parent. It needs a running, idle session with saved messages and says why otherwise (`Wait for the current response to finish or abort it before forking.` while a response runs); `/fork` takes no arguments in Chat, because the placement is always a new tab. **Branch…** in the same menu shows the session in Chat and opens the Rewind picker, as typing `/branch` does. **Clear Context…** in the same menu and the Chat tab's `…` menu asks first in a dialog, then runs the same `/clear` as typing it (typed `/clear` still asks nothing).
- **Quote a selection from a diff, with the file, the lines and which version it is.** `Alt+Q` (or **Quote Selection to Session** in the editor's right-click menu) in either side of a diff editor quotes the selected text with its location, in the Source Control diff of a changed file, a staged file, a commit's changes (the multi-file diff editor) and a diff of two files. Before, the side that is the file on disk was quoted with its location, but a side that is a Git version (the left of a Source Control diff, both sides of a staged or commit diff) was quoted as bare text, with no way to tell where it came from.
  - The lines are the lines of the side you selected in, so the right side of a diff is `src/app.ts:42-50` as in any file. A side that is a Git version says which one after ` @ `: `src/app.ts:3-4 @ HEAD (3f2a9c1)` (the commit `HEAD` named, written as `index` for the staged version, as `3f2a9c1` for a commit's side, and `main (3f2a9c1)` for a branch or a tag), so the agent can read the same lines with `git show`, and sees at once that it is not the file on disk. The location of a Git version is plain code in the sent message, not a link, because a link would open the file on disk at lines that are other lines there.
  - A version that cannot be named truthfully (an unusual ref, or no Git extension) is quoted without a location, as before. A `~` side of a Source Control diff is the index when the file is staged and `HEAD` otherwise, as the Git extension reads it.
  - In a diff shown inline (one column, which VS Code picks by itself when the editor is narrow), only the added and unchanged lines can be selected; the deleted lines are not editor text, so they cannot be quoted with the key (see the quote design, decision 10).
- **Chat: Ctrl+F finds text in the whole conversation.** It did nothing before (VS Code's own find is off for the Chat, and it could only see the rows the page keeps mounted anyway). `Ctrl+F` (`Cmd+F` on macOS) anywhere in the Chat, or **OMP Desk: Find in Chat** (Command Palette and the editor's `…` menu), opens a find bar that searches your messages, the replies and their thinking, and each tool call's name, target, intent and output text across every loaded row. The key is an ordinary VS Code keybinding (`ompDesk.findInChat`, only in a Chat), so it is in the Keyboard Shortcuts editor and can be rebound or removed there; it and `Alt+C` (Match Case) also work on a keyboard layout that types another script for the F and C keys, such as a Russian one.
  - It starts at the newest match; `Enter`/`F3` goes to the next and `Shift+Enter`/`Shift+F3` to the previous (both wrap), `Alt+C` toggles Match Case, and the bar shows `3 of 12`. Text selected in the Chat fills the field. `Ctrl+F` while the field already has the focus leaves what you typed alone; from anywhere else it returns to the field and selects it.
  - A match is loaded into the transcript, scrolled to and highlighted, and what hides it (a tool group, the call's output, a thinking block) is opened. `Esc` closes the bar from its field or any of its buttons and returns the focus, and never stops a running turn.
  - It does not search notices, summaries, attached files' text, history before a context reset, messages still on disk behind **load earlier messages** (the bar says how many earlier messages it did not search) or the reply still being written (it is searched once it is complete). The search runs when you pause typing; `Enter` searches at once.

- **Chat: OMP's internal addresses in a reply are links.** An `agent://<id>`, `history://<id>`, `artifact://<n>` or `local://<path>` written in a reply (in prose, in inline code such as `` `agent://DocsReview` ``, in bold, or as the destination of a Markdown link) becomes a link when this session has what it names, and stays plain text otherwise, so a link is never dead.
  - **`agent://<id>`** (a nested agent is `Parent.Child`; a `/path` after the id is ignored) opens the agent's read-only transcript tab, the same one the Agents row opens, while the live session knows the agent. When it does not (a stopped or resumed session), it opens the agent's published output, `<id>.md` in the session's folder, as a read-only document.
  - **`history://<id>`** opens the agent's transcript tab. **`artifact://<n>`** opens the full output of a truncated tool result, as the link in the tool row does. **`local://<path>`** opens a file of the session's scratch space as a read-only document.
  - **Ctrl+Shift+Click** shows the file behind a link (an output, an artifact or a scratch file) in File Explorer. Only this session's own files are reachable: the page names the address, never a path, and the host resolves it against the session it serves.
  - `skill://`, `memory://`, `rule://`, `omp://`, `pr://` and `issue://` stay text: OMP resolves them from its own loaded skills, memory, rules and remote services, which OMP Desk cannot ask.
- **Chat: the hash of the current commit in a reply is a link that selects it in the Source Control Graph.** A hash of 7 to 40 hex digits in an assistant reply (in inline code such as `` `c7398070` ``, or in the text when it has both digits and letters) becomes a link while it is the commit HEAD points at in the repository of the session's folder, and stays plain text otherwise (another commit, an unknown hash, or an abbreviation that several commits share). A click, or `Enter`, opens Source Control's **Graph** view and selects that commit there. Nothing else opens: no editor, no diff. VS Code's Graph can select only the current commit, so no other commit is linked, and no extension (GitLens, GitLess) is involved.
  - When HEAD moves (a commit, a checkout, an amend), the links update: the old current commit turns back into text and a hash of the new one already on the page becomes a link, usually within a few seconds of VS Code's Git extension noticing. Only commit hashes are asked again, not file or code-symbol links.
  - A click on a link whose commit has just stopped being current opens nothing, shows a short notice and makes the hash plain text. Each click writes one line to the OMP Desk log naming the steps it ran.
  - Only this session's repository is searched (the checkout that contains the session's folder, the deepest first), through VS Code's Git extension, and the commit is looked up again on every click.

- **Chat: an empty session shows the keys you really have.** The five hints are now four groups of one-line hints in two columns (one when narrow): **Start**, **While the agent works**, **In the conversation** and **From the editor and anywhere**, each key in a `<kbd>`, with a link, **All keyboard shortcuts (Ctrl+/)**. The key of an OMP Desk command is the one you have: a rebinding or a removal in your own `keybindings.json` of the active profile replaces it (a removed key shows `none`), and another extension's removal is honoured. When another command is bound to the same key (another extension's keybinding, or one in your `keybindings.json`) and its `when` is not obviously false in a Chat, the key gets a warning icon naming it, for example *Ctrl+Alt+T may be taken by IntelliJ IDEA Keymap: git.sync*; a click opens Keyboard Shortcuts on that key. The result is recomputed when `keybindings.json` or the installed extensions change, and never blocks activation. VS Code's own built-in keybindings are not read, and a profile that shares only part of its settings with the default one may read the wrong file. See [the design](docs/designs/2026-10-18-chat-keys-and-empty-state.md).
- **Chat: `Ctrl+/` shows all OMP Desk shortcuts, and the composer has a keyboard button.** Both open Keyboard Shortcuts filtered to `ompDesk.`; the key follows the physical `/` key, so it works on a Russian layout.
- **`Alt+Q` with nothing selected references the caret's line.** In a text editor (or either side of a diff) `Alt+Q` or **Quote Selection to Session** now inserts `` `src/app.ts:42` `` as inline code (with ` @ HEAD (3f2a9c1)` for a Git version) into the Chat draft, by the quote's session choice and path rule, instead of warning "Select some text first." An untitled document, which has no file, is refused with a reason. The editor menu entry no longer needs a selection.

### Changed

- **Two Chat keys moved so they stop clashing with the IntelliJ IDEA Keymap.** Show/hide all thinking is `Ctrl+Alt+T` (was `Ctrl+T`, the keymap's Git Sync) and Search Prompt History is `Ctrl+Alt+Y` (was `Ctrl+R`, the keymap's Replace). Both work only in a Chat. Rebind either in Keyboard Shortcuts if you prefer other keys.

### Removed

A user keybinding or old `omp.sendSelection` alias that names the command does nothing now (91 old command ids keep their alias; [ADR-0068](docs/decisions/0068-rename-contributed-ids-to-ompdesk-and-migrate-settings-at-activation.md) amendment).

### Fixed

- **Chat: `Enter` submits a question dialog's answers on its review step.** After the last answer of a multi-question dialog (a picked option, or an "Other" answer committed with `Enter`), the review step opened with nothing focused, so `Enter` did nothing and only a click on **Submit answers** sent them. The button now has the focus there, and `Enter` submits from anywhere on the review step except a review row, which still opens its question.
- **Chat: code links that were asked while the C# language server was still loading now appear when it is ready.** After a reload with a Unity project open, `SessionService.Dispose` stayed plain text even though Ctrl+N found it a minute later: while Roslyn loaded the project, the answer was "not ready", and Unity's file activity kept discarding the lookups under way; the page counted these as failed tries, gave up after its few retries and never asked again. Now a lookup that the provider could not answer yet, or that a file change dropped, only waits: it does not use up the page's retries, the OMP Desk output no longer reports it as "gave up", and the host asks the Chat again when the provider has answered, or about one second after the file changes settle (about a minute apart at most in a workspace that never stops changing). A real failure (a timeout, a provider error) keeps its three tries. The output now says, at info, when a language server became ready and how many lookups a burst of file changes dropped and which change it was (the first file of the burst is in the debug log).
- **Chat: code links no longer stay plain after a reload with several Chats open, or because of generated code.** In a Unity project with a source generator, a type name and its members could stay plain for good: the language server lists many generated declarations with very long signatures and containers, and one such entry made Desk give up on every lookup of the name, again and again. Desk now reads those entries by their name and the type they belong to, and an entry it cannot read at all only leaves plain a name that it could be a second declaration of, as an answer and not as a failure to retry. Separately, after a reload that restored three Chats while the language server was still loading, hundreds of symbols and file names were asked at once; the overflow was counted as failed tries, so whole replies had no links. A lookup that finds the line full now just waits: a Chat takes only its share of the language server at a time, a language server that does not answer is not asked more than a few calls at once, the file search asks the Chats again when its line is free, and what is on screen is asked first. The OMP Desk output no longer reports these waits as "gave up".
- **Chat: file and code links are less likely to stay plain in a workspace with a Unity project open.** Every file Unity (or Git) created or deleted in `Temp/`, `Library/` or `.git/`, even while you were idle, made Desk discard the link lookups under way, and the page's retries and then its minute of rest fit inside such a stream, so a link such as `Session.cs:1353` or `Session.Copy` could stay plain. Events for files no lookup can return (anything below `.git`, and anything your own `files.exclude` / `search.exclude` hides in its folder) are now ignored, and a burst of the other events discards the lookups once, not once per file. When a link lookup still gives up after its retries, the OMP Desk output says so at the default log level, once per name every five minutes, with the reason (invalidated, timeout, language server not ready, queue full); the per-lookup lines stay at Debug.
- **Chat: `Ctrl+N` finds a qualified name.** With `SessionData.Load` selected in a Chat, VS Code's symbol search listed nothing, because its `#` search compares only the member's own name with the whole text typed. `Ctrl+N` now looks a qualified selection up the way the Chat's code-symbol links do: one definition opens at its line, several are listed in a picker (name, container, file), and when none is found the symbol search opens for the name after the last dot. A name without a dot, and a selection that is not a code symbol, go to the symbol search as before.
- **Chat: a code symbol is a link when written with its namespaces, or when the type inherits the member.** `OmpDesk.Core.Catalog.Profile.Load` (up to eight segments, every one before the type and the member starting with a capital letter) now links to the member of `Catalog.Profile`, because a language extension reports the type but not the namespaces above it. A member the written type does not declare itself (`Profile.Merge`, declared in its base class) links to the base class's declaration when the language extension has a type hierarchy (the C# extension does): the type's base classes and interfaces are asked level by level (at most 8 levels and 24 calls, within the existing time bounds), and the link is made only when exactly one declaration is found at the nearest level. Without a type hierarchy, or when the type is not unique, the symbol stays plain code.
- **Chat: quoting text inside one table cell quotes that text, not the whole table row.** Selecting a cell's text in a reply and pressing `Alt+Q` put the table's header, its separator and the whole row with every cell into the draft. Now a selection inside one cell quotes only what you selected, as a paragraph does (a bold run you selected whole stays `**bold**`, a part of it is its plain text), with no header and no pipes. A selection across several cells or rows quotes a valid table cut to the columns between the first and the last cell you touched, with the cells at its two ends cut to your selection. A selection that starts before the table or ends after it still quotes the touched rows whole, with every column.
- **A slow OMP start no longer leaves a Chat tab saying "This OMP process cannot serve chat control".** When OMP took more than 10 seconds to answer the broker's chat-protocol handshake (a large session loading while the machine was busy), the broker gave up on the chat protocol for good and the tab stayed failed until you killed the process. The broker now keeps waiting for the answer, and the tab goes live when it arrives. If OMP never answers, the tab fails with "OMP did not finish starting the chat protocol. Reconnect, or restart this session if it keeps failing." and offers **Reconnect**. The old sentence is now shown only for an OMP process that really lacks the chat protocol. A session already running under the previous build keeps its old behaviour until it is restarted.
- **A restored chat tab keeps its own session after a slot was switched to another conversation, and opening an unshown tab no longer falsely warns that VS Code "could not bring it to the front".** At startup the window reserved each restored editor for the session its tab type was first created for instead of the session it serves now, so two editors could claim one session and the real one was closed as a duplicate, leaving a running session with no tab. Editors are now reserved by their saved binding, the same rule the editor restore and the focus-composer shortcut use. Separately, VS Code starts showing a tab after the select command returns, so Desk reported a still-opening tab as unreachable. It now waits for VS Code to report the tab active (and retries once), reaches groups beyond the eighth, and writes the reason to the log whenever it does give up.
- **Sessions that were running when Windows logged off or shut down come back on the next start, instead of being left stopped.** When Windows ends your session, the OMP processes die a moment before VS Code does (exit code 4). A window that was still attached to a process recorded that as "you stopped this session", so the next start skipped it and you had to resume it by hand, while sessions whose window was already gone came back on their own. Only a normal exit (`/exit`, `/quit` or Ctrl+D in the Terminal, exit code 0) now counts as your stop. A crash, any non-zero exit code, a signal, or a process that disappeared with its background process leaves the session as it was, so the next start relaunches it; its tab shows the process ended in the meantime, and its row says it restarts when VS Code next starts. Stop, Close and Kill from OMP Desk still keep a session stopped (Kill now records that before it ends the process, and puts it back if the kill fails). A session whose process crashes at once is retried each time VS Code starts. The end of the process is also recorded in one catalog write (stopped intent, cleared process and released claim together), so a VS Code that is killed in the middle can no longer leave a "stopped" row that still names a process.
- **A change made in one VS Code window is no longer taken back by another window's unrelated action, and the session catalog stops filling with false conflicts.** A window that learned of another window's change to a session (a new title, a stopped or restarted run, a read reply) still treated that change as its own the next time it saved anything. It then reported a conflict between two identical copies, and if the first window had changed the same session again in between, it wrote the older value back. In a real catalog 87 of 87 such reports were identical copies and the conflict history was 84% of the file that every window rewrites on each change. A window now keeps track of what it has adopted, and the history drops reports of identical copies the next time any window saves. Conflicts where two windows really changed the same session differently are still kept.
- **Editor tabs no longer pile up hidden records in the session catalog, and restoring a tab no longer rewrites the catalog.** Each time you opened a session that had no tab, Desk remembered a new tab-to-session record and never forgot it, even after the session was removed; one real catalog held 88 of them for 9 open tabs, 52 of them for sessions that no longer existed. A removed session now takes its tab records with it, records left by earlier versions for sessions that are gone are cleaned up the next time a window saves, and re-binding a tab to the session it already shows (or selecting the view it already has), as every restored tab does, no longer rewrites the catalog. Records of closed tabs whose session still exists are kept, because a tab VS Code restores later, possibly in another window, still needs its record to find its session.
- **Sessions whose process ended while no window was watching no longer keep a record of a process that is gone.** If a session's process ended after the window that ran it had closed (or the window never noticed), its row kept naming that process and its claim stayed in place until you resumed it. About 20 seconds after VS Code finishes restoring its tabs, each window now checks the sessions it is not responsible for: when the recorded process is provably gone and the window that claimed the session is gone too, the record of that process is cleared and the claim is released. A session that was running stays marked as running, so it still restarts when a tab for it is opened, and a session another open window runs, starts or reconnects to is never touched. Claim files that no session refers to and whose window is gone are deleted.

## [0.4.3] - 2026-10-15

### Added

- **A running Chat survives a VS Code update.** A Chat's background broker, the process that keeps its OMP alive when VS Code closes, used to be VS Code's own `Code.exe`. VS Code's updater ends every `Code.exe` of the install, and with it the Chat's OMP process and any unfinished turn. A new Chat now starts its broker on the `bun.exe` that runs its OMP when Desk can prove that Bun is safe to use (Bun 1.4.0 or newer, in a folder only you and administrators can change, confirmed by a self-check that uses nothing but a pipe). The updater does not touch it, and the next window re-adopts the same OMP process and transcript. This needs OMP launched through Bun (the Bun global install, `bun omp.js`): an OMP installed as its own program (the winget package `can1357.oh-my-pi`, the `omp.sh` binary install, a mise install) has no Bun to share, so its Chats keep a `Code.exe` broker and still end in an update. Anything else (no Bun launch, an older Bun, a refused check, the new setting **`ompDesk.chatBrokerRuntime`** set to `vscode`) starts the broker on `Code.exe` as before, and the OMP Desk output says which one each Chat uses and why. Terminals, folder shells and Stats still end in an update. A Bun broker keeps about 110 MB more committed memory than a `Code.exe` one (working set about the same). Chats already running keep the broker they have; changing the setting affects new brokers only, so to move a running Chat, stop it and open it again.
- **Ctrl+Alt+N starts a New Session and Ctrl+Alt+R resumes one, from anywhere.** The keys run the same commands as the **New Session…** and **Resume Session…** rows of Sessions (`OMP Desk: New Session`, `OMP Desk: Resume Session`) and work in an editor, a Chat, a Terminal-mode session, the Sessions view and the integrated terminal. With several folders shown they ask for the folder first, as the rows do; the work they start shows its progress in the status bar like any command-started action. They sit next to **Ctrl+Alt+Q** (Go to Session). In the integrated terminal Ctrl+Alt+R replaces VS Code's own key for Terminal: Run Recent Command; give that command another key in Keyboard Shortcuts to keep it. Rebind either chord there like any other key; on a keyboard layout where AltGr is Ctrl+Alt the chord can type a character first.
- **Chat: type code blocks in the composer.** Inside a fenced block of the draft (a line of three or more backticks with an optional language, up to the closing fence, or to the end of the draft while there is none) `Enter` is a new line that keeps the line's indentation instead of sending, `Tab` indents with four spaces and no longer moves the focus (a selection over several lines indents every line; `Shift+Tab` outdents to the previous tab stop), and `Ctrl+Enter` sends (`Ctrl+Alt+Enter` for a follow-up while a turn runs). Typing the opening fence and pressing `Enter` supplies the closing one, and Undo takes it back in one step. `Shift+Tab` on a line with nothing to outdent leaves the box backwards, so the keyboard is never trapped; a status line under the composer names these keys while the caret is in a block. While the draft holds a block the composer is set in your editor's font and a band marks the block's rows; no `/` command, argument or `@` file completion opens inside a block. Outside a block `Enter` still sends and `Tab` still moves the focus, and the text that is sent is unchanged (plain Markdown). The editor's own undo keeps working, an IME composition is left alone, and an image marker inside a block stays atomic. Design: [Code blocks in the Chat composer](docs/designs/2026-10-15-composer-code-blocks.md).
- **A native module that Windows blocks, or that is missing, is explained.** OMP Desk's Windows checks now run through one unsigned file, `koffi.node` (see the first entry under Changed and [ADR-0076](docs/decisions/0076-call-win32-in-process-through-a-staged-koffi-module-instead-of-starting-powershell.md)); an application-control policy (AppLocker, WDAC) or an antivirus can refuse it, and there is no PowerShell fallback. A window where it cannot load now shows one message with the cause where Windows names it (policy block, missing or quarantined file, a stage that timed out, anything else), what does not work meanwhile (New Session, Resume, re-attaching a running Chat) and three buttons: **Copy diagnostics** (both file locations, the SHA-256, the error, the versions), **Open troubleshooting** and **Reload Window**. The user guide's [troubleshooting page](docs/guide/troubleshooting.md#the-native-module-is-blocked-or-missing) says how an administrator allows the file by hash or path and how to restore it from quarantine, and a launch that is refused for this reason names it instead of "the broker state directory is not usable". The file's hash changes only with the koffi version, which a release that changes it says in its notes.
- **A privacy gate for maintainers and contributors.** `node scripts/check-privacy.mjs` fails when personal information (names of unrelated private projects, local paths, account names, listed in a local denylist that is not in Git) is in the tracked tree, in any commit of a range (messages, changed paths and added lines) or in a VSIX, and lists the images a range adds or changes. It is a blocking step before every push and release ([docs/publishing.md](docs/publishing.md#privacy-gate)).

### Changed

- **OMP Desk's Windows checks no longer start PowerShell.** Four checks that used to start a PowerShell, at every window start, attach, restore or control connection, are now in-process Windows calls through a prebuilt, MIT-licensed `koffi.node` that the extension stages and hashes like its other loaded files ([ADR-0076](docs/decisions/0076-call-win32-in-process-through-a-staged-koffi-module-instead-of-starting-powershell.md)). Each VSIX now carries one `out/native/koffi.node` for its architecture; the staged broker tree carries it too, so the broker-runtime proof and the tree digest cover it, and a broker that cannot load it does not start. A module that cannot load never turns a check into a pass: a reading that cannot be made is `unknown`, never "gone", and an unreadable path or an unavailable module refuses visibly.
  - **The session-lease check.** Whether another OMP holds a session's lease (the Sessions view's external-writer state, refreshed every 15 s per window with the view visible, and the question before Resume and Open) is one `OpenMutexW` call of about 0.04 ms instead of a PowerShell start of 0.7 s and more (and 5 s timeouts in every window while the machine was busy at restore).
  - **Access and owner checks of Desk's private storage.** The check that decides whether the staged runtime tree, a broker's state directory and a broker's executable are writable only by your account now reads each path's owner and access list in process (`GetNamedSecurityInfoW`, one batched call under the same 20 s bound) instead of one PowerShell start of 0.3–7 s per pass. The verdicts are unchanged: it compares security identifiers and numeric rights, an unknown kind of access entry refuses, and account names are looked up only to name the principal in a refusal.
  - **Process identity readings.** The check that tells a session's recorded process from a later one that reused its id (the creation time of a broker, of the OMP process and of this window, and the walk of a process's descendants used by Close, Stop and the Processes reads) is one in-process call (`GetProcessTimes` and a process snapshot) in the extension host and in the PTY broker, instead of 22–26 PowerShell starts per window while a restore ran.
  - **Host control's peer proof.** Every control connection to an OMP process (at a launch, a re-adoption after a reload, a reconnect) used to start a Windows PowerShell with an inline C# compile that opened the pipe and relayed every frame. The pipe is now opened in process (`CreateFileW`), the server's process id is read from that same handle (`GetNamedPipeServerProcessId`) and its creation time from the kernel, and only a server that is exactly the expected process is given the handle as the socket; nothing is read or written before that, and a mismatch closes the handle unread. The staged `verified-pipe.ps1` is gone.
  - **The module's own verification.** The staged copy is verified by one short-lived child process (`out/native-stage.js`, shown as `tool spawn: node native module staging`) before the host loads it. A reload no longer waits for it: the child records what it verified, and a later activation that finds the same layout (the same account, a local fixed NTFS volume, the staged file and its directory unchanged, every directory above them still the same directory, a record under a day old) loads the staged copy in one synchronous step, only after the owner and access list of its whole path chain have been read natively and judged by the verifier's rules, and still re-hashing the bytes before every load ([ADR-0076](docs/decisions/0076-call-win32-in-process-through-a-staged-koffi-module-instead-of-starting-powershell.md), decision 11). That child used to cost 0.6–1.6 s on the critical path of every tab's first attach.
- **A reload and a re-adopted Chat are faster.** On a busy machine a reload spent seconds waiting for file calls: at a reload with three windows an asynchronous file call took a median of 11–31 ms (up to 693 ms) while the same call made synchronously took 0 ms, because every asynchronous call waits in the host's four file threads and then for a turn of an event loop that other extensions keep busy. A session claim (about fifteen calls) took 0.2–5.4 s per tab, the first read of the profile catalog 0.8 s and a catalog write up to 4.7 s.
  - On a local fixed NTFS volume the claim and catalog file calls, the owner and access reads of paths a verification has just shown to be plain, and the verification of a broker's state directory (directory creation, the plain-path checks, the listing and the write probe: about twenty-five thread-pool jobs before) are now made as synchronous steps, with the same calls in the same order ([ADR-0076](docs/decisions/0076-call-win32-in-process-through-a-staged-koffi-module-instead-of-starting-powershell.md), decision 12). A lock that has to wait still sleeps on a timer. Elsewhere (a network drive, no native module) the calls stay asynchronous.
  - A tab's restore no longer waits for the save of the session index that ends it: the save is queued in order behind and ahead of every other write, a failure is still logged and shown, and the restore finishes when the tabs are attached. Saves of the session index that queue behind each other write the catalog once instead of once each, and re-adopting a running session no longer writes it a second time.
  - The packaged broker tree's digest (what decides "same build") is hashed once in the background when the window activates, with eight reads in flight, instead of when the first tab attaches and one read after another.
  - The native staging and the profile catalog read start at the top of `activate()`, so their waits overlap the rest of the setup.
  - A bun-installed OMP's release is read from its package manifest instead of by starting `omp --version`, a process start that on a saturated machine ran past its 15 s limit (the slash-command registry then went unread for that window). A standalone OMP program still answers the probe, with the same transient timeout ([ADR-0011](docs/decisions/0011-use-installed-omp-without-version-gate.md), 2026-10-15 amendment).
  - With all of this, a warm reload re-adopts a live Bun-broker Chat with the reconcile step at about 130 ms per tab in a test window (it was 8.6 s in a user's window while the checks ran in PowerShell); nothing in the restore waits for the PTY runtime self-check.
- **The OMP Desk log says where a slow start goes.** At Info level, with wall and CPU time:
  - One `window timing: activation …` line per window breaks `activate()` into its phases (and what the host spent before it, loading the bundle). A bundle evaluation reports its CPU time too.
  - Two lines say when the native module was ready and where its staging child spent its time (runtime start, load, stage and verify, start and exit). Every Windows check, a session's claim and the first attach wait for that module, so on a loaded machine a restore's `admission` and `state access (shared)` are that wait. The load is split into read, hash, `dlopen` and bind. The activation line also carries `catalog read`.
  - The `window timing: restore tab …` line breaks `reconcile` into its pieces, for example `reconcile 8594 (broker client 2, record 3, tree digest 8100, state access (shared) 410, connect 12, status 8, child identity 6, broker confirm 4, pin proof 9)`, and `admission` into `session file`, `workspace directory`, `identity turn`, `claim read`, `claim holder alive`, `claim holder` and `claim take`. A piece that waited for work another tab started is named `(shared)` (the packaged-tree digest, the broker state directory check, a proof already in flight), so two tabs with almost the same time are told apart from two slow ones.
  - One `window timing: startup file-system turnaround …` line reports, for the first ten seconds after activation, the median and the largest turnaround of an asynchronous and of a synchronous `stat`, which tells a queue in the host's file-system threads from a slow volume.
  - Resume and Open log their timing like New Session. A launch you start from the composer's **Resume** button, **Resume Session** or a folder's history, or by opening a stopped session in Chat or Terminal, logs one line with where it spent its time from the moment the command was entered (`window timing: resume <tab> running in N ms · panel … · runtime proof … · broker spawn … · conversation …`, or `open` for a stopped row's Open) and a second with the time to the verified host control (`window timing: resume <tab> host control verified N ms after the command`). A launch that is not yours (the startup restore, a session another window runs) logs none; a Restart and a view switch of a running session log theirs as `restart` and `view switch`.
- **A click that starts slow work now says so at once.** Resume in the Chat composer, Open in the Sessions view, New Session, Resume Session, Restart, the Chat/Terminal switch, Close, Kill, Delete, Forget, Rename, Export HTML, Reload All Windows and the checkboxes of the Skills, Tools, MCP and Extensions views used to show nothing for seconds while OMP Desk checked for another writer or probed processes. Now, in the frame after the click, the composer's Resume button is disabled and spins with a banner, the session's row shows `Opening…`, `Starting…`, `Closing…`, `Killing…`, `Deleting…`, `Forgetting…` or `Renaming…` with the step it is in (`checking for another OMP process`, `waiting for your answer`, …) and the seconds once it passes 5, the Sessions view shows a progress bar, and the actions that have no row or button of their own (Command Palette, Go to Session, Export HTML, Reload All Windows) show status-bar progress. An inventory row reads `Saving <name>…` and cannot be switched again until its write is done. The Close, Kill, Delete and Forget checks that precede their confirmation are named (`Checking…`) instead of silent. A second click on a row that is already pending only tells you what is happening; while Close waits for your Force Stop answer the row says so, and shows `Stopping` only after you choose Force Stop.

The native-module notice and its **Open troubleshooting** button point at the guide's troubleshooting page, and two new README screenshots, `models.png` and `omp-settings.png`, show the Models and OMP Settings editors.

### Fixed

- **Chat: an ordinary screenshot attaches.** The composer refused an image over 512 KiB (`image.png: 770 KB exceeds the 512 KB limit per image.`) and a prompt over 576 KiB of images, which is below most screenshots. The limits are now 5 MiB per image and 10 MiB per prompt (still at most 8 images), the numbers of the chat message grammar (`MAX_CHAT_IMAGE_BYTES`, `MAX_CHAT_IMAGES_BYTES`), which the composer reads from there. The bound that sets them is the broker's 16 MiB line to OMP: 10 MiB of images is 13.3 MiB of base64, which leaves room for the longest prompt text and the command's own fields. OMP resizes an attached image (to at most 1568 px a side, about 500 KB) before the model sees it and before it stores it in its blob store, so the panel does not downscale and the session file stays small. The check that an image is base64 no longer overflows the JavaScript regular-expression stack on a multi-megabyte string (it is a linear scan). A prompt with large images sent from an editor that reconnected after an extension-host restart (the fallback connection carries one sealed frame of at most 256 KiB per request) is now refused with a sentence that says so, instead of dropping the connection and ending `unconfirmed`; reload the window to attach such images.
- **Chat: dragging an image onto the composer attaches it (hold Shift).** VS Code's workbench takes a file drag over a webview editor before the page sees it (its drop overlay opens the image in an editor tab), unless Shift is held; no setting or extension API changes that, and a drag that enters the window over another part (the usual case) is blocked before the page is told. With Shift held, a file dragged from Windows attaches, and so does an image dragged from VS Code's own Explorer or an editor tab: such a drag carries `file:` addresses, not files, so the page asks the extension host (`omp:attach-uris`), which reads only a local drive path that is a regular PNG, JPEG, GIF or WebP file within the new size limits (no network share, no other scheme, no device path) and answers with the images and one sentence for each refusal. The drop is taken anywhere on the Chat page and the composer card shows a dashed outline while a droppable drag is over it. The attach button's tooltip and the empty chat's key hints say "Shift+drag".
- **Chat: a bare file name in a project opened next to its repository links.** With a workspace of two folders, one nested in the other and hidden by the outer folder's `files.exclude`, a name such as `session-index.ts` stayed plain text: only the outer folder was searched, with its exclude. Every workspace folder is now searched with its own `files.exclude` and `search.exclude`, and a file found twice counts once.
- **A New Session followed within seconds by a Reload no longer leaves a running OMP the window will not attach to.** The session's OMP id is learned when the Chat's first state answers, which on a loaded machine can be after the reload; the restore then refused the live process as "this index never recorded an OMP session id" and Resume refused it again, so the session was stuck. A live process whose id was never recorded is now attached (the session reads the id from it, and a session with a file is checked against that file); a differing recorded id is still refused. A conflict that remains now says to Stop or Kill that process in Sessions and then Resume, instead of offering a Resume that cannot work.
- **New Session no longer creates two sessions on a double click.** While the first New Session for a folder is still starting, a repeated New Session for that folder is ignored and the editor of the one that is starting is revealed.
- **The New Session folder picker says where each folder is open.** A folder that is not pinned was described as "open in a window", which read as if picking it opened a new window. It now says "open in this window" or "open in another window"; a pinned folder says the same after "pinned".
- **Host control is no longer lost for good when the machine is busy.** When the probe that reads the new OMP process's identity (a 5 s PowerShell run) timed out at launch, the Chat or Terminal stayed without host control until the session was restarted (`host control unavailable — the process generation could not be read (generation probe did not answer in time)`). A timed-out probe is now retried up to three more times, a few seconds apart, and logged once per attempt as `host control paused — … it is retried`; only a probe that fails for another reason, or that times out every time, still ends in `host control unavailable`. Likewise, a Chat or Terminal whose OMP did not answer the control channel in time (a loaded machine right after VS Code started or updated) logged `host control paused … it is retried`, but nothing retried: the session stayed without host control (statuses, model readback, subagent indicators) until it was restarted. The attempt is now repeated up to five times (2, 4, 8, 16 and 30 s later), only for the process the tab still runs and only while it holds no channel; the first success restores host control, and if all five find OMP busy `host control unavailable` is reported once.
- **A session-index save that loses the profile catalog lock to another window no longer shows a toast.** Starting several VS Code windows at once (a restart after a reboot) showed "The OMP session index could not be saved: … Another VS Code window is writing the OMP Desk profile catalog … It will be retried by the next action", although the other window finishes in moments and nothing was wrong. Contention between windows is now a line in the OMP Desk log with its cause, and the window saves its state again by itself (after 1 s, then 2, 4 … up to every 30 s while the lock is held, no matter whether you do anything); the Sessions folder list does the same. Any other save failure is still shown, but once per window for each distinct cause, and contention that lasts two minutes (a lock nobody releases) is shown once as a fault. Switching an editor between Chat and Terminal during such contention no longer fails, and when it does fail the message now says why (`The editor mode could not be recorded durably: …`) instead of dropping the cause.
- **The footer's provider usage no longer logs `Provider usage executable resolution failed` nine times in five seconds with no cause.** A session re-adopted after a reload has no recorded OMP, so each tab's footer resolved it again, each with its own `omp --version` probe (15 s under load); the resolutions now share one probe, and a failure is logged with its cause (a resolution failure and a failed usage read are told apart), once per distinct cause for each tab.

A session whose OMP process survived is re-adopted without PowerShell identity probes when its broker is from this build (before: four per session, seconds each on a busy machine): the broker reports its own and its child's identity in its authenticated status. A recorded process id that no process runs under is read as gone at once, without PowerShell. The check that the extension's private folders are limited to your account needs one PowerShell start instead of four, and the broker folder's access check starts at activation. A session started by an older build has its broker and OMP process read at the same time. The PTY runtime self-check result is remembered on disk per broker tree and executable, so a reload or another window reuses it instead of repeating the 4–13 s check; a stored proof expires after 24 hours and one that a failed broker start contradicts is deleted. A window restores its rows four at a time, and Sessions' own background reads (other sessions' ownership checks, the Processes list) wait until the restore is over: a restored row shows Restoring and another row shows Checking until then, and every explicit action still reads at once. One consequence: when the single folder-permission read fails as a whole, Desk no longer tightens folder permissions in the same pass; the folders stay refused until a later check succeeds.

The record is now read in a single step that a busy window cannot interrupt, a saving window reads it once after saving instead of twice, only changes to the record itself wake the other windows, and a burst of wake-ups is answered by one refresh at a time. A machine too busy for the session-ownership probe (a PowerShell start that times out after 5 s) is probed less and less often while it keeps failing (15 s, 30 s, 1 min, doubling up to 5 min) instead of every half minute in every window. Saving stays durable and every merge and ownership rule is unchanged; a window that is itself stalled while saving still delays the others for that long.

The shipped bundles (`out/extension.js`, `media/guest.js` and the others) are minified, 1.1 MB each instead of about 2 MB; the watch build (`npm run watch`) stays readable.
- The OMP Desk output explains slow restores and launches. A `tool spawn: <tool> <purpose> pid <pid> <ms> ms <outcome>` line for every PowerShell start behind a restore (never a path or text a process printed); one `window timing: restore tab …` line per restored session with each step's duration, a `restore pass` line and a `startup restore timeline` line; and the PTY broker's health-check times on the first launch in a window (`PTY runtime proved itself: self-check N ms, ready in M ms`, `PTY runtime proof reused from <time>`).
- Internal structure (no behavior change): `src/` is divided into layers (`shared`, `chat`, `protocol`, `host`/`broker`/`omp`, `views`, `webview`, `wiring`, `runtime`) with one import direction checked by `npm run typecheck`; opening, restoring, launching, stopping, Kill and the Chat conversation surface go through a `SessionRuntime` port in `src/runtime/`, which may not refer to `vscode` (ADR-0066); the extension host's state is one `WindowState` object; five regions of `extension.ts` and the session index are split into their own modules; and every writer that replaces a file goes through `src/host/atomic-file.ts`.
- Test environments (contributors): `scripts/test-vscode.ps1` says so when VS Code is waiting to install an update, instead of starting a window that exits after 30 s with no window and no log; `-VsCodeDir` starts another VS Code install.

- Chat: sending a message from the composer (Send, Enter, a steer or a queued follow-up) while the transcript is scrolled up returns it to the latest messages and follows them again, so your message and its reply are no longer left off-screen. New output that arrives while you read earlier messages still leaves you where you are.
- Chat: an `eval` call is titled by the language it runs, `JavaScript` for `js` and `Python` for `py`, instead of always `Python`; the title is a neutral `Eval` while the language is not known yet or the cells of one call mix languages.

A long inline-code path, file or symbol link, web link, URL or unbroken word in a reply, list item, heading or quote broke the line in no place, so the transcript grew a horizontal scrollbar above the composer and cut the line off; they now wrap at the edge of the text. A long path or URL wraps after a `/` or `\` (and, inside a segment longer than 20 characters, after `.`, `_` or `-`) instead of in the middle of a word; copying and selecting give the same text as before. A wide table scrolls inside a block of its own instead of widening the transcript.
- Chat: a fast reply (a model streaming hundreds of tokens per second) no longer makes the page spend most of its time reparsing. OMP sends one `message_update` per token chunk, each carrying the whole partial message, and the page validated, reduced and rendered every one; the host now passes on at most one per message every 33 ms (the latest wins, order is kept, a pause flushes on the next turn), and the Markdown of a reply that streams in parses only the block the new text touches (a 20 KB reply rendered at 400 growth steps: 562 ms of parsing became 16 ms).
- Chat: while only a background job (for example a `git push` started in the background) keeps a turn open, the working row no longer keeps showing the last tool's wording and the whole turn's timer, which looked like a hang after an hour. It says "Waiting for background job: <name>" (or "Waiting for N background jobs", or "Waiting for background work" when no job can be named) and times how long the wait has lasted; when the agent works again the row returns to its normal wording and timer. OMP reports only that background work is pending, so the job names come from the transcript.
- Chat: `/clear` typed right after an aborted turn is no longer refused as "wait for the current response to finish" while nothing is streaming. A refusal now says why: a response is streaming, OMP is still finishing the interrupted turn, a message is waiting in OMP's queue, a dialog is open, or a sent message is not confirmed yet. When the reason is only that OMP is finishing the interrupted turn, has a queued message, or has not confirmed a sent message, Chat shows "/clear will run when OMP finishes the interrupted turn." (and says what it waits for), and runs the clear as soon as OMP is ready. Sending a message, starting another command, the session stopping, or 60 seconds without readiness cancels it; a second `/clear` does not double it.
- Chat: the result of Shake or Compact (for example "Shook 12 tool results") no longer appears and then disappears when Chat re-reads the session file straight after it. A result row belongs to the last message it followed; when the re-read does not hold that message yet, the row now stays under the nearest earlier message instead of being dropped with it.
- Chat: a path in inline code that is only the end of a path in the project, such as `host/session-index.ts:579` or `shared/code-symbols.ts`, is now a link to the file VS Code's file search finds, like a bare file name already was: one file links to it at the line, several files link to the pick list. Paths written from a fixed place (`./`, `../`, a drive, `~` or a leading slash) are not looked up this way, and `files.exclude` and `search.exclude` still hide files, so in a Unity project whose settings hide `*.meta`, `*.asset`, `*.prefab`, `*.unity` and `*.mat` those names stay plain.
- Chat: file names and path ends in inline code linked far less often while files were being written in the project (an agent running tests, Unity importing assets): every changed file anywhere dropped the lookups under way, and a large repository's search takes seconds, so a name such as `WorldStateSnapshotTests.cs` stayed plain for a minute. A changed or saved file no longer discards file lookups at all (it cannot change which files exist), and a lookup running while files are created, deleted or renamed answers with the files it found that still exist.
- Chat: terminal styling in native output is drawn instead of shown as raw text. OMP's `/context` report (typed or sent by the Context view's **Read Breakdown**) listed fragments such as `[38;2;107;114;128m░░░░[39m` because the escape byte was dropped and the rest of each sequence printed; the colored bars now render in the theme's terminal colors. Bash tool previews, bash executions and extension widgets use the same renderer; every other escape sequence (cursor moves, titles, hyperlinks — link text stays) is removed whole, and the copied text is plain.
- Chat: a long session (tens of MB of session file) reopened in a window, after a reload or from another window, no longer stays disconnected while Sessions shows it Running. Its catch-up answer (sent by OMP as a train of 1 MiB chunks) pushed the earlier answers out of the broker's 4 MiB line ring before the paced replay reached them, so the broker disconnected the Chat as "fallen behind the retained lines" on every attempt, every 30 s. Answers to an attached client now wait under their own 128 MiB budget until it has read them. Sessions started before this update keep the old broker until they are restarted.
- The broker connection (Chat, Terminal and folder shells) no longer closes with "more than one frame's worth of bytes without a line end" when one socket read carries many complete lines or one large complete line. Only the unterminated tail of the buffer and each single line are held to the 256 KiB frame limit; a socket read of any size is split into its frames first. Node rarely delivers such reads.
- Stop and close of a Chat whose connection the broker had already closed no longer fail with "The session could not be confirmed stopped": the stop now opens a fresh, identity-checked connection to the same broker instead of using the closed one.
- Close, Stop and Reload of a session whose OMP process had already ended (killed from another window or Task Manager, or crashed together with its background process) no longer fail with "could not be confirmed stopped" and offer a Force Stop that has nothing to stop. When the stop cannot be confirmed, Desk checks the recorded OMP process itself (its id no longer in use, or now another process's) and, when it is gone, closes the session normally. A window still on a build from before Kill existed does not notice such a kill by itself; reload it.
- **When VS Code's updater ends your running sessions, OMP Desk now says so.** **Restart to Update** makes VS Code's installer stop every `Code.exe` of the install after waiting 30 s, and the processes that keep sessions alive between windows run as `Code.exe`, so their OMP processes end with them and the sessions are resumed from their files instead of re-adopted (a turn in progress and its sub-agents are lost). This cannot be avoided from an extension; OMP Desk now reads the updater's log, and when it names one of its processes it logs the pids and shows one notice. README states the limit.
- Starting a session no longer fails on a busy machine because the PTY broker's health check was slow. The check runs the staged broker's console child and pipe child once per window before the first launch; with the CPU saturated it took up to 14 s against 4 s idle and a phase that missed its 15 s deadline refused the launch (`the runtime self-check failed with exit code 7: the pipe child did not finish within the self-check deadline`). A check that only ran out of time, with nothing observed to be wrong, is now inconclusive: the session starts and a repeated check with a 90 s deadline settles it in the background (the OMP Desk output logs `PTY runtime admitted unproven` and the outcome). A check that observed a fault (an addon that does not load, a child that cannot start, a nonzero exit, a wrong echo) still refuses the launch at once, and so does one that still delivers nothing after the 90 s window; launches in the next minute get that refusal.
- Launching on a busy machine no longer silently starts an older OMP. When the `omp --version` probe of the OMP your PATH selects does not finish in time (it timed out at 15 s under CPU load, and Desk then used a stale compiled `omp.exe` later on PATH), or Desk could not start or read it right now (out of handles or memory, the file busy), the launch, the Terminal, the CLI reads and the stopped-session rename now stop with a message naming that OMP and the cause and never fall back to another one; try again once the machine is less busy. The Skills, Tools, MCP and Extensions views do the same on their first read and keep showing what they already had when a later read hits it. A launcher that is plainly not OMP (missing file, foreign launcher, a probe that exits with an error) is still skipped in favour of the next one on PATH. Settings, the rename and the inventory read the package source of the OMP Desk resolved and no longer borrow another install's from a global Bun or npm folder. When PATH offers two different OMP installs, the OMP Desk output logs both paths and releases once per window.
- The extension host no longer freezes for seconds on a busy machine (a Sessions title-bar button such as **Sessions Layout** took seconds to react, and VS Code reported "Extension host is unresponsive" with OMP Desk as the cause). The window's own start time and every launch/stop/delete check of another window's holder were synchronous PowerShell commands (0.2 s idle, 5 to 17 s under CPU load), and every catalog commit, lock, read and refresh was synchronous file I/O with an `fsync` and up to 2 s of sleeping rename retries; all now run off the host thread. A new always-on monitor logs `event loop blocked for N ms` to the OMP Desk output with the Desk operations (commands, catalog adoption, Sessions refresh) that overlapped the stall and the process's CPU time, so a stall of Desk's or of someone else's can be told apart.
- The shared session catalog no longer grows without bound: its conflict ledger (one record each time two windows changed one session row at once, each holding both whole rows) had reached 613 KB on a real profile, and every window parsed, rewrote and fsynced it on every change. It now keeps the newest three records per disagreement with a count of the dropped ones, and an oversized ledger shrinks the next time any window saves a change.
- Sessions: a row no longer stays **Unread** after you have looked at the session. When several windows were open, a window holding an out-of-date copy of a row (for example right after Reload All Windows) saved it whole together with an unrelated change and took back that you had read the reply. A read is now never taken back by an older copy (the later of two reply marks wins), the window that runs a session follows a read recorded in another window, and writes back one the catalog lost, so the next write or refresh repairs a row that is already stuck.
- Sessions: a row another window runs keeps its ⧉ mark and the status that window publishes on a busy machine, and a click on it switches to that window at once. The holder is now found in the window registry (a current lease and a live process) instead of a PowerShell start-time reading that timed out after 5 s and made the row look like an ordinary Running row. A failed session lease probe is no longer retried at once by every row observation (up to three 5 s PowerShell attempts in a row); it answers unknown for 15 s first.
- Sessions: a row another window runs is no longer left highlighted as the selected session. Clicking it switches to that window and VS Code selects the row; the selection stayed there after you came back, so the view showed another window's session as this window's, while the Chat tab in front was a different one. The selection now returns to this window's own session when the switch ends, when the window regains focus and on any later refresh, and a row you picked here is left alone.
- Sessions: a folder's path is shown with an upper-case drive letter (`C:\Users\…\repo`) instead of the lower-case one VS Code reports (`c:\Users\…\repo`), in the folder row, the folder pickers, the Unity project picker and the "no longer records" notice.
- Sessions: a session whose first prompt could not be read once (the file was busy) keeps trying on later refreshes instead of showing the fallback title until the file changes, and an error while repainting the view no longer stops every later refresh of the window.
- Skills, Tools, MCP and Extensions: the `List may be incomplete: some sources failed to load` banner now says which source failed and why (for example `[MCP Config] Failed to parse JSON in D:\project\.mcp.json`); it names the provider and, where OMP names one, the local file, never a plugin id, URL or error text, shows at most two and the OMP Desk output lists every one. An MCP server that OMP's discovery drops because another server has the same command or URL is shown `shadowed by <that server>` instead of the vague `shadowed by a higher-priority item of the same name`, and a lower definition of a name that a higher-priority file also defines is listed in the row's tooltip as `shadowed by <the file that owns the name>`.
- Skills, Tools, MCP and Extensions lists no longer take 10 s or more to appear, and a refresh no longer fails with "a compiled-only OMP install cannot supply it" on a busy machine. Opening the views one after another started one Bun worker run per view (each importing OMP's modules, 1.5 to 1.9 s idle and several times that on a busy machine) and re-resolved Bun, the OMP package and the OMP launcher every time, and a launcher probe that ran past its limit under load fell through to a compiled `omp.exe` that has no package source. Now one read is shared by every view and by concurrent reads, a read less than five seconds old is reused, an older one is shown at once marked `refreshing…` while a fresh one runs, the resolution is kept when a later one fails because the machine was busy, and when nothing can be found the message names the launcher Desk resolved or the missing Bun. The OMP Desk output logs each read's duration.
- MCP view: a server that one file defines and another file only switches off (a project's `.mcp.json` with servers and `.omp/mcp.json` with `{"unity": {"enabled": false}}`) is one row, not two. The row shows the definition's transport and command or URL and says `disabled by mcp.json`, its tooltip lists every contributing file and what each does, it is no longer called `shadowed`, no switch is offered where a by-name project entry keeps it off, and the banner `List may be incomplete: some sources failed to load` no longer appears for such an entry.
- Context view: a Chat that is running a long turn no longer shows only the live groups. The deep read (the "This context window" statistics, the Auto-compaction row, the Session file and Context files groups) used to wait for the end of the turn, so a read made when the view opened was dropped by any compaction pass or epoch change inside the turn and nothing asked again until the turn ended; it now runs at attach and after such a change while the turn goes on (never during a compaction or a pass; once one exists, automatic refreshes still wait for idle). A read the session could not answer yet (not live, refused, timed out) is logged and retried at the session's next phase change or snapshot instead of staying empty.
- Agent debugger: breakpoints the agent set stay the agent's after Reload Window. Desk kept who owns each breakpoint only in memory, so after the window's extension host restarted (VS Code keeps the breakpoints and their ids) the agent's own breakpoints were listed as `owner: user` and `vscode_debug_breakpoints clear` left them behind. The owner records are now saved in the workspace state and read back. A breakpoint you delete and set again at the same place is a new breakpoint and stays yours: it is never handed to the agent. Ending a debug session (for example when Unity reloads its domain) never changes an owner. `vscode_debug_handoff` now lists the breakpoints that passed to you and tells the agent to remove the ones it does not want to leave behind before it hands off; the breakpoint list explains each owner, and a refused removal says who owns the breakpoint and asks the agent to leave it to you.

### Added
- **Skills, Tools, MCP and Extensions views** replace the single Tools view. MCP shows configuration and name-matched tools, never a connection state.

If a clear does not finish, Chat says so and keeps the earlier history visible. Main session only; sessions started by an earlier Desk build must be restarted. They are the first user of a new host tool channel ([ADR-0055](docs/decisions/0055-expose-vscode-capabilities-as-rpc-host-tools-run-by-the-owning-window.md)): the broker keeps an unanswered tool call until its result is written or OMP cancels it, only the window that holds the session's input executes and answers calls, and every call OMP does not cancel gets exactly one result, even after a reload, a lost connection or a takeover.

The Editor needs Debug code optimization (a headless Editor needs `-debugCodeOptimization`), and the reproduction must not block on the paused thread, so start tests asynchronously and then wait for the stop.

A session that ends, or whose adapter connection fails, reports the last adapter error (for example `write EPIPE`) in `vscode_debug_wait` and `vscode_debug_configs`. A control result says the next stop has a higher generation than the one it names, not necessarily the next number.
- **A bare file name in inline code is a link.** `session-index.ts:849` in a Chat reply opens that file at the line when VS Code's file search finds exactly one file of that name in the session's folders (a file in the working folder wins); several matches link to a pick list. Search exclusions apply, and the lookup is bounded and never delays the reply.

### Changed

- Ctrl+Shift+L focuses the chat composer from anywhere, replacing Ctrl+Shift+Q; it takes over VS Code's Select All Occurrences of Find Match key, which you can rebind.
- The notice shown in a chat or terminal tab, and in the warning, after OMP Desk was updated while the window was open is one sentence, "OMP Desk was updated. Reload the window to continue.", and the tab has a **Reload Window** button.
- **The Processes view is part of Sessions.** A running session says `Process: running` in its tooltip. Terminals and processes that no listed session stands for are in a **Terminals** group after the sessions, and the new **Terminals** layout (third Sessions layout, next to the flat list and folders) lists every background process with its folder; a click opens its session or terminal. **Stop Orphaned and Idle** and **Kill All** are Sessions title buttons. Kill All stops what this window runs through its own stop lifecycle and, if you choose *Stop in All Windows*, asks each other open OMP Desk window to stop its own sessions and terminals the same way, then reports one result per process. Processes no window runs, and those of a window that never takes the request up or is gone, are stopped through their authenticated broker and reported as stopped without their window; no process id is signalled and nothing is force-stopped without a prompt. A window asked to stop its own processes never prompts or forces, and a stop another window reports is counted only once its background process is confirmed gone. A window that took a stop request up and went quiet is left alone until its process is proven gone, and nothing owned by another window is stopped while the window list cannot be read. A notification for a session that has since ended no longer does nothing in the Terminals layout: it switches to your last session list layout and shows the session. **New Session** and **Resume Session** are no longer title buttons; their rows in the list stay. The Processes view and `omp.processes` are removed ([design](docs/designs/2026-10-11-sessions-unify-processes.md), [ADR-0060](docs/decisions/0060-merge-background-processes-into-sessions-and-kill-all-through-authenticated-routes.md)).
- Processes are read only while Sessions is visible (every 5 s in the Terminals layout, every 30 s otherwise), and a verified process identity is trusted for 60 s rather than a number of ticks.
- **The Sessions layout is chosen with one title button** that opens a picker of Flat List, By Folder and Terminals (the current one marked); its icon shows the current layout. It replaces the buttons for the two layouts the view was not showing. In the flat list and the folders layout the **Terminals** group is the last row, after the sessions (or folders) and the New Session… and Resume Session… rows, set off by a blank row.
- **Skills, Tools, MCP and Extensions views are quieter.** The permanent explanatory paragraph above each list is gone: one short line appears only when the list is incomplete, the project overrides the global list, the session is not running or the inventory could not be read. Standing notes (no MCP connection status, providers disabled in OMP, unlisted project plugins, unreadable session tool list) are in a folded "About this list" row at the end; rows show state compactly, with details in the tooltip.

### Fixed

- **OMP: Open Terminal in Folder** and **OMP: Reconnect Terminal** run from the Command Palette ask which folder to use, as New Session does, instead of warning "Choose a registered OMP folder".
- **A checkbox switch in the Skills, Tools, MCP or Extensions views is traceable and can be undone.** Tab from such a view's list reaches each row's checkbox, and Space or Enter on it switches the row at once (a click on a row's label or icon only opens its source and never switches). Disabling now shows its notice with an **Undo** button that switches the row back on. OMP Desk writes every switch to its output: the request (view, item, enabled→disabled, the list shown, the profile) and the outcome (what was written to which file, already as requested, or the refusal), and every failed read. Before, a change to `config.yml` from those views left no trace to tell it from an edit by anything else.
- Clicking into the Chat composer of a window that did not have the focus no longer leaves the composer without it. VS Code refocuses a webview editor when its window gains the focus, which cleared the focus the click had just given to the composer (or to whichever element in the page you clicked); the page now puts it back, only when the loss is that refocus and not you moving away.
- The Chat composer keeps the keyboard focus while the session is re-attached under you. A session whose connection drops or goes silent, or whose state is rebuilt, is "resyncing" for a moment, and the composer is disabled for that moment; a disabled field cannot hold the focus and the browser does not give it back, so the composer could lose focus at a moment you did not choose and typing went nowhere. The composer now takes the focus back when it is writable again, unless you moved elsewhere in the meantime. A composer that loses focus without a click, Tab or Escape is now written to the OMP Desk output as `tab …: focus: …`, with what the page saw just before and the function that called `focus()` or `blur()`, so a future report can be attributed.
- In the Chat composer, Up and Down recall prompt history only when the caret is already on the first or last visual row. A soft-wrapped paragraph used to count as one line, so Up anywhere inside it replaced the text with an older prompt; now the arrows move the caret through the wrapped rows first.
- A C# member named with its class in Chat (`SessionIndex.Reload`, `Outer.Inner.Member`, `Box<T>.Put`) is a link again when its class has exactly one such member. The C# language server describes a member's class as `in SessionIndex (project omp-vscode (net8.0))` (translated in a non-English VS Code), which the class match did not understand.
- `/clear` (and Rewind) in a chat whose OMP process was started by an earlier OMP Desk build no longer says "not supported by this OMP version"; it says the process predates the command and the session needs a restart.
- `Esc` in a VS Code list with search (a model picker, the Command Palette) opened over a working Chat only closes that list; it no longer also stops the turn.
- A Shake or other maintenance result row in Chat no longer vanishes when OMP reports it while the next reply is already streaming. OMP's automatic shake (and the other automatic passes) report their outcome, for example "Shake failed: Auto-shake reclaimed ~N tokens but context is still above the threshold", at that moment; the re-read of the session file that follows every such report dropped the row because it was attached to the reply still being written.

## [0.3.0] - 2026-10-11

### Added

- Folder paths in Chat are links too. A click opens a file in a tab; **Ctrl+Click** selects the file or folder in the Explorer without opening it, and **Ctrl+Shift+Click** opens its folder in File Explorer with it selected. A plain click on a folder selects it in the Explorer. The Explorer can show only paths inside a folder open in the window. The same three actions are in the link's right-click menu, and a web link's right-click menu offers **Open in Editor** and **Open in Browser**.
- In Chat sessions the model is asked to write the files and folders it mentions as paths in inline code (`src/app.ts:42`, `docs/`), so they become links, and to link every code symbol it names, at each mention and in tables and lists, to the definition line it has seen (`` [`World.Current`](src/World.cs:42) ``) or to the file alone, so a click opens the definition.
- **Code symbols in Chat replies are links when VS Code can tell where they are defined.** An inline code span such as `Session`, `SessionData.Load()`, `SessionStoreBase<T>` or `[Tracked]` in an assistant reply becomes a link, with the same underlined look, click and `Ctrl+Click` as a file path, when VS Code's language extensions (C# Dev Kit, TypeScript and others) report exactly one definition of it inside the session's folders; a click opens the file at the definition. A partial class or an overloaded method links to one of its declarations (the type's own file, else the first); a symbol with several different definitions (same-named types in different namespaces) is a link with a dotted underline and the tooltip "N definitions — click to choose" that opens VS Code's workspace symbol search for its name, never a guessed definition; unknown symbols and code blocks stay plain. Each lookup is logged in the OMP Desk output (counts and verdict). Symbols in bold, italic and strike-through text count too. While a language server is still loading its projects, or when its queue is full, symbols stay plain code and are linked as soon as it answers, without reloading the window. It is asynchronous, bounded and cached, and never delays a streaming reply. Language servers rank and may cap workspace symbol results, and a server that has not loaded the workspace yet answers nothing, so a symbol can be missed. Turn it off with `omp.linkCodeSymbols`.
- **A bare file name in a Chat reply is a link when VS Code can find the file.** An inline code span such as `session-index.ts:849`, `session-index.ts(849)` or `index.ts` in an assistant reply becomes a link, like a path, when VS Code's file search finds exactly one file of that name in the session's folders; a click opens it at the line. The file in the session's own folder wins, `files.exclude` and `search.exclude` are honoured, and on Windows the case of the name does not matter. A name that several files carry links to a list of those files (dotted underline, tooltip "N files"): a click lets you pick one. Nothing is guessed and nothing delays the reply; `omp.linkCodeSymbols` turns it off together with the symbol links.
- **An optional per-message reminder keeps the model linking files and code symbols.** With `omp.linkReminder` on, a short reminder follows each prompt you send, on its way to the model only (a separate message that is never saved to the session or shown in Chat; your prompt is not changed and the prompt cache keeps working): write the files and folders you mention as paths in inline code and every class, method, property, field and type as a link with its definition line. In a test fixture the share of symbols left as plain code dropped from about 50% to about 30%. It adds about 120 tokens per prompt. It is off by default; turn it on with `omp.linkReminder`; it applies to sessions started or resumed afterwards.
- **Compact…** in the context popover asks for OMP's compaction mode, with `snapcompact` (no model call) preselected; `soft` and `remote` then ask for optional instructions. A new **Shake…** beside it drops heavy content from the context, with `elide` preselected, or `images` or `thinking`. Both are also in the editor title menu and the Command Palette.
- **Ctrl+Shift+Q** puts the cursor in the chat composer from anywhere, the integrated terminal included: the active session, else the one showing next to your files. With no session open it opens the OMP Desk side bar. In a Terminal-mode session it no longer reaches OMP as Ctrl+Q; press Ctrl+Q itself for a follow-up message.
- **Ctrl+N** in a Chat opens VS Code's symbol search with the text you selected in the Chat (or in the composer) already typed in, the way it does in a text editor; with nothing selected it opens the empty symbol search. It is the command **OMP: Search Symbol from Chat Selection**.
- Sessions open in their own editor group on the left, and that group is locked, so files you open from Chat links, the Explorer or Quick Open appear in a group on the right and the chat stays visible. Turn it off with `omp.chatColumn`.
- **Ctrl+Shift+M** (**OMP: Toggle Files Window Next to Chat**) moves every tab of the group next to the chat into a window of its own, kept on top of other windows, wherever the focus is. That file window stays: files you open from Chat links go into it until you close it, then everything goes back to the right of the chat. Pressing Ctrl+Shift+M again, from any window, brings all its tabs back into the group next to the chat (created to the right of the chat if missing) and closes the window; the next press detaches again. The window is larger than VS Code's default when every tab is a text file; with a diff, a viewer or an unsaved file among the tabs, VS Code moves the group as it is, into a default-size window. Tabs that cannot be reopened in the other window (unsaved files, custom views) stay where they are when coming back. It replaces VS Code's Problems key and the Chat's Cycle Model key; Cycle Model stays in the Command Palette. A keymap extension that binds the key in the text editor (IntelliJ IDEA Keybindings uses it for Move Caret to Matching Brace) wins there; add a user keybinding for `omp.moveFileToNewWindow` to take it back.
- **Sessions is one flat list by default.** Every session of the shown folders is a row labelled `folder · title`: sessions that are not stopped first (unread on top, then the most recent activity), stopped sessions last, and **New Session…** and **Resume Session…** rows at the end that ask for the folder. The button in the view's title bar (`omp.sessionsGrouping`) switches to the previous layout, grouped under folders, and back.
- **Unread replies.** A **●** marks a session whose agent finished a reply or asked you something while you were not looking at its editor; it clears when you look at the session, and it survives a window reload. Both layouts show it.
- While a session has an open editor, its row in Sessions stays selected: the session you viewed most recently. Clearing the selection or selecting a folder or the New Session or Resume Session row puts it back.
- **Ctrl+Alt+Q** (**OMP: Go to Session…**) opens a searchable list of every session, from anywhere including the integrated terminal: title, folder and status, in the Sessions order (unread first, stopped last). Picking one opens it as a click in Sessions does; **New Session…** at the end of the list asks for the folder and starts one.
- **Resume Session** is a button in the Sessions title bar, next to New Session, and a **Resume Session…** row under **New Session…** at the end of the flat list, so it is reachable there, where there are no folder rows. It asks for the folder when several are shown, then lists that folder's saved sessions.
- **Sessions shows the repository's agent root for a subfolder.** A folder opened inside a Git repository whose root holds the agent files (`AGENTS.md`, `CLAUDE.md`, `.agents`, `.omp`, `.claude`, `.pi`) while the folder itself has none, as a Unity project under `repo/` does, is shown as that ancestor, so new sessions start where OMP finds them; sessions already recorded in the subfolder stay listed under it. Turn it off with `omp.useAgentRootFolder`.
- **Sessions is the same in every window.** The folders open in any window of the profile now appear in all of them, so a project open only in another window shows its sessions too; a window that closes takes its folders away after a few seconds. A session another window runs shows that window's live status (Working, Needs your answer, Idle, Unread reply) instead of "Running · in another window"; its icon is the status icon, and a `⧉` mark after the status says it is open in another window. Selection, a row's available actions and the collapsed state of an unpinned folder stay per window. `omp.showWorkspaceFolders` and `omp.useAgentRootFolder` now apply to all windows.
- **Clicking a session another window runs switches to that window at once.** The window comes to the front with the session's tab selected; the "Switch to Window" question is gone (the row's menu keeps **Switch to Window** as the same direct switch). A message appears only when switching is impossible, and says why (the window has no saved workspace or folder, two windows show the same folder, it did not answer, or it no longer has the session open). Sessions that only show history in another window are not switched to.
- **A session starts in the window that has its folder open.** New Session, Resume Session and opening a stopped session of a folder that is open only in another window now run in that window, which comes to the front with the session's tab (the most recently used one when several have it). A **Unity project** (a folder with `ProjectSettings/ProjectVersion.txt` and `Assets/`, found in the session's folder or two levels below it; several are asked once) runs in a window that has the project folder open, or in a new window opened on it, because the Unity extensions need that; the session's working directory stays the repository folder. If the other window does not answer, a message says so and nothing is started. The `omp.launchInFolderWindow` setting (default on) turns it off.
- **A window that was not reloaded after an update is skipped when sessions start in another window.** Such a window cannot open views any more; a session for its folder now starts in the window you used, with a note to reload the other one, instead of ending in an "OMP was updated while this window was open" page there.

### Changed

- **Switching to another window is fast.** Clicking a session another window runs, or starting a session in another window, took up to 22 seconds, because every check whether another window is alive ran a PowerShell command on the extension host's event loop, once per row on every change. The check is now done once per window, in the background, and a switch takes about a fifth of a second. The OMP Desk output log gained `window timing:` lines for the steps of a hand-over.
- **Unpin Folder** no longer refuses while a session in that folder runs. A folder with a running session in the window stays visible, unpinned.

### Fixed

- An `@path` mention written in inline code in Chat (`` `@CHANGELOG.md` ``) is now a link, as it already was in plain text.
- Inline code in a Markdown link label in Chat (`` [`World.Current`](…) ``) is shown as code, not with its backticks.
- **Session cost** in the context popover covers the whole session, as the terminal UI's status line does. After a compaction it used to count only the spend since that compaction.
- The context ring and its popover under the Chat composer show the new usage after **Compact** / **Shake** (from the popover or typed), after `/handoff` and after an automatic compaction. They used to keep the figure from before the pass until the next turn.
- **Chat's model and thinking pickers work during a turn.** Choosing a thinking level or a model while OMP was working was refused with "OMP is busy; choose a thinking level after the turn ends". OMP accepts both changes mid-turn (the next model request uses them), so Chat now sends them at once. When Chat cannot send a change yet (OMP is compacting, a rewind is running, the connection is being restored), it keeps your choice, shows it in the picker with a clock icon and sends it as soon as OMP is ready, before any message you send in the meantime; the newest choice wins. If OMP rejects it, the picker goes back to what OMP uses and a notice says so. **Cycle Model** and **Cycle Thinking Level** (`Ctrl+Shift+U`) behave the same. A choice that is still waiting is lost if the window is reloaded.

## [0.1.0] - 2026-10-07

First public preview of OMP Desk: a Windows-only VS Code extension that runs your installed [Oh My Pi](https://github.com/can1357/oh-my-pi) (`omp`) sessions in editor tabs.

### Added

- **Sessions view** listing the folders open in the window, pinned folders and every running or stopped OMP conversation for them, with live status (Working, Waiting for subagents, Needs your answer, Idle, Unread reply) and row actions: Open, Rename, Reload, Close, Forget, Delete and Resume Session. Sessions held by another VS Code window or written by a separate `omp` process are marked, and opening them asks first.
- **One editor, two modes.** Each session opens as a rich **Chat** or as the unmodified native OMP **Terminal** TUI, switchable from the editor title. **OMP: Choose Default Session View…** sets the mode for new sessions.
- **Sessions survive restarts.** Each session runs in a detached background process that keeps working when its tab closes, the window reloads or VS Code exits; reopening reattaches to the same process and screen. Only one window writes a session at a time.
- **Chat**: streaming replies, saved history, steer and queued follow-ups (editable before they run), questions and approvals as a card above the composer, slash-command argument suggestions, model and thinking pickers, a footer with context usage, provider quotas and the Git branch, an Overview or Detailed view of tool calls, pinned TODO and Agents rows with detail tabs, a working status row and progress bar, clickable file links, and web links that open in an editor tab (`Ctrl+Click` for the external browser). Drafts stay until OMP confirms them; if OMP stops responding, **Reconnect** or **Restart** keeps the conversation and unsent text.
- **Terminal**: the genuine OMP TUI with Nerd Font glyphs, clickable file and web links, live theme colors, **Copy screen** and **Redraw Terminal**.
- **Windows desktop notifications** when a session finishes or asks for input (`omp.desktopNotifications`).
- **Add Selection to Session** and **Add File to Session** (`Alt+Shift+K`) insert an `@path` reference into a session you pick, without sending it.
- **Folder shells**: **Open Terminal in Folder** and **Reconnect Terminal**.
- **Processes view** for the background processes behind sessions and terminals, with Stop and a one-step cleanup of orphaned and idle processes.
- **Stats** opens OMP's usage dashboard in an editor tab.
- **Tools view** listing the tools and skills of the active session.
- **Models and Agents settings** tabs for OMP's model roles and agent overrides (`/models`, `/agents`).
- **OMP: Log In to Provider…**, **OMP: Show Diagnostics**, **Copy Diagnostics** on rows, and file change observation commands.
- Windows packages for `win32-x64` and `win32-arm64`.

### Notes

- OMP is not bundled. The extension launches the `omp` found on `PATH` and never installs, downloads or updates it.
- OMP Desk is an unofficial, independent integration, not an official OMP distribution.
